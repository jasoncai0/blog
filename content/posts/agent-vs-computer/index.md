**这篇文档在做什么：**把 LLM agent 当成一台计算机，从处理器、存储层次、I/O、操作系统、程序、网络到安全，逐层与冯·诺依曼计算机做对照：哪些层机制同构、可以直接借用计算机系统几十年的方案，哪些层只是表面相似、照搬会出问题，最后据此给出对 agent 架构设计的启发和未来演进的判断。它是《Claude Code 父子 Session 架构调研》第十三章“会话管理 ≈ 进程管理”的延伸，文中涉及 Claude Code 的具体机制和数字，都来自那篇文档里的源码核实和实测。**姊妹文档：**《Claude Code 父子 Session 架构调研》（未公开）。

## 一、结论速览

把 agent 看成计算机，最有解释力的一条主线是：**LLM 是处理器，上下文窗口是内存，检索与文件是外存，工具是 I/O，harness 是操作系统内核。**这条主线不是新提法：Karpathy 多次用“LLM OS”描述它（LLM 对应 CPU、上下文窗口对应 RAM），MemGPT（2023）直接把操作系统的分层内存移植成“虚拟上下文管理”，AIOS（2024）则把调度、上下文、内存、存储、访问控制做成一个独立的 agent 内核。本文的贡献是把这条线逐层走完，并标出它在哪里断裂。

对照的结果可以归纳为三句话。第一，**管理层几乎完全同构**：进程、调度、存储层次、缓存、IPC、隔离、权限、恢复，计算机都有成熟答案，agent 系统正在一一重新发明它们，越早直接借用越省事。第二，**“硬件”层是本质差异的来源**：处理器是概率性的、按语义而不是按地址访问内存，内存换出是有损的，每读一次内存都要按 token 付费。这些差异决定了上层哪些方案不能照搬。第三，**agent 重演了冯·诺依曼架构的老问题**：指令和数据混放在同一个上下文里，所以提示注入之于 agent，就像代码注入之于早期计算机。计算机花了几十年才用 NX 位、带标签内存、特权分离把它管住，agent 现在正处在这条路的起点。

| 层 | 计算机 | Agent | 同构程度 |
| --- | --- | --- | --- |
| 处理器 | CPU，确定性执行机器码 | LLM，概率性解读自然语言 | 低：差异的根源 |
| 指令集 | ISA / syscall ABI | tool schema、函数调用协议 | 高 |
| 缓存 | L1–L3、页缓存 | KV cache、prompt cache | 高（但命中条件更苛刻） |
| 主存 | DRAM | 上下文窗口 | 中：容量有限相同，访问与计费方式不同 |
| 外存 | SSD / 磁盘 / 文件系统 / 数据库 | 记忆文件、transcript、RAG、搜索 | 中：没有缺页中断 |
| I/O 与驱动 | 设备、驱动、总线、中断 | 工具、MCP、hooks、通知 | 高 |
| 操作系统 | 进程、调度、内存管理、权限 | harness：会话、子 agent、上下文管理、权限 | 高 |
| 程序与编译 | 源码 → 编译 → 可执行文件 / 库 | prompt → skill / workflow | 中 |
| 网络与分布式 | 协议栈、集群、共识 | 多 agent、MCP / A2A、交叉验证 | 中：故障模型是拜占庭式的 |
| 安全 | 代码注入；NX、capability、特权分离 | 提示注入；来源标签、授权隔离、双 LLM | 高（同一病根） |

## 二、一台“Agent 计算机”

下图把计算机与 agent 系统逐层并排。越往下越接近“硬件”。理解 agent 系统的关键在于：上层机制大多能照搬，但每一层能照搬多少，取决于最底下两层，也就是处理器和主存的性质。

## 三、处理器：LLM ≈ CPU

**相同点。**两者都是“取一条输入、执行、产生输出”的执行核心，都由外层软件决定它看到什么、能调用什么。工具定义就是 agent 的指令集：CPU 只能执行 ISA 里定义的指令，模型只能发起 tool schema 里声明过的调用；系统调用通过固定的 ABI 进入内核，函数调用通过固定的 JSON 协议进入 harness。“思考”token 类似微架构内部的流水线状态，对程序员不可见、却决定了执行质量；按 token 生成相当于时钟节拍，生成速度（token/s）就是主频。

**根本差异。**CPU 的语义是精确定义的：同一条指令、同样的寄存器状态，结果完全确定，错误只来自硬件故障，而且非常罕见。LLM 的“指令”是自然语言，执行是一次概率采样：同一个 prompt 可能走出不同路径，可能“执行”了没有被要求的事，也可能声称完成了实际没完成的事。这带来两个直接后果。其一，计算机里“只看退出码”的结果处理方式不再够用，返回值本身需要验证。其二，处理器的能力不是固定的：换一代模型，就像换了一颗指令集不变、但“理解力”跳变的 CPU，上层软件的最优写法也会随之改变。这在计算机史上几乎没有先例，最接近的是从顺序执行 CPU 换到乱序执行 CPU 后，编译器优化策略的重写。

## 四、存储层次：上下文 ≈ 内存，RAG ≈ 外存

存储层次是这组类比里最有用的一层，也是差异最需要讲清楚的一层。计算机的存储层次遵循“越快越小越贵”的金字塔，agent 也有一座几乎一样形状的金字塔。

{{< fig "diagrams/02.svg" "存储层次" >}}

### 4.1 上下文窗口 ≈ 主存

相同的地方：容量有限；程序（agent）所有的“计算”都只能直接作用于主存（上下文）中的内容，要用外存里的东西必须先读进来；主存是易失的，会话结束、或者内容被压缩掉，里面的东西就没了。

不同的地方有三点，而且都很要紧。第一，**访问方式不同**：DRAM 按地址随机访问，读哪个字节就只付那个字节的代价；transformer 对上下文是“全量注意”，每生成一个 token 都要让它与上下文里的所有 token 发生关系，n 个 token 产生 n² 个两两关系。Anthropic 把这称为“注意力预算”，并观察到“context rot”：上下文越长，模型准确回忆其中信息的能力越弱。也就是说，主存越满，处理器越“笨”，这在计算机里没有对应物。第二，**读取要付费**：每一轮都要把整段上下文重新发给模型，即使命中 prompt cache 也要按约 0.1 倍计费，所以单个 agent 的总成本随轮数近似平方增长。第三，**寻址是语义的**：计算机靠地址找数据，agent 靠“注意力”找相关内容，相当于一块巨大的内容寻址存储器（CAM），找得到与否带有概率性。

### 4.2 上下文管理 ≈ 内存管理

既然上下文是内存，那么操作系统内存管理的每一个操作，在 agent 里都能找到对应物。下图逐一对照，红色三项是不能照搬的关键差异。

{{< fig "diagrams/03.svg" "上下文管理与内存管理" >}}

**换出是有损的。**操作系统把页换到磁盘，是一字不差地写出去，需要时原样换回；agent 的 compaction 是一次语义重写，摘要里没写的细节就永久丢失了。Claude Code 的做法很有代表性（见姊妹文档 10.1）：上下文到 144k 时就在后台预先生成摘要，相当于 kswapd；到 167k 同步压缩，相当于直接回收；到 177k 拒绝发请求，相当于 OOM，并配有失败熔断和“快速回填”熔断，相当于 thrashing 检测。但这套水位机制解决的只是“什么时候换出”，换出的内容会丢失这个问题，要靠另一件事来补：**把细节外置到可以重新读取的地方**。Anthropic 推荐的结构化笔记（NOTES.md、待办列表），本质上就是给有损的内存配一个无损的交换分区。

**没有缺页中断。**程序访问一个不在内存里的页时，CPU 会触发缺页中断，内核自动把页加载进来，程序完全感知不到。agent 没有这种机制：模型不知道自己“忘了什么”，也就不会主动去取回。just-in-time 检索（只在上下文里保留文件路径、查询、链接这类轻量标识符，需要时再用工具加载）之所以有效，是因为它给模型留下了一个“这里有东西”的指针，相当于手动实现的页表项。设计 agent 时，与其指望模型自己意识到缺了信息，不如在上下文里显式留下指向外部内容的引用，让“缺页”变得可见。

**回收与共享。**tool result clearing（清理很早以前的工具调用结果）是最轻量、最安全的回收：这些内容已经被模型消费过，其结论通常已体现在后续回复里，就像 GC 回收不再被引用的对象。共享则对应 prompt cache：fork 出来的子 agent 共享父的前缀，同构的 workflow agent 互相读对方写入的缓存，就像多个进程共享同一份共享库的物理页。

### 4.3 RAG、记忆文件 ≈ 外部存储与文件系统

RAG 对应的是“磁盘 + 索引”。向量库相当于数据库的二级索引，只是索引键不是 B 树里的精确值，而是 embedding 空间里的近似邻居，所以检索是按语义寻址、召回有损的。预检索（推理前先把可能相关的文档取进上下文）对应 prefetch / readahead，猜错就白白占用宝贵的主存；agentic search（让 agent 自己用 grep、搜索工具逐步查找）对应按需调页，更准但更慢。Claude Code 在代码库场景下几乎完全放弃了向量预检索，改为让模型用 Glob、Grep、Read 自己查找，相当于宁可多几次 I/O，也不让错误的预取挤占主存。

记忆文件对应文件系统里不同用途的文件。CLAUDE.md 和 rules 相当于 /etc 下的配置，开机（会话启动）时加载；NOTES.md、待办列表相当于程序自己写的日志或检查点；transcript 是完整的执行日志，可用于 resume，相当于事务日志；auto memory 相当于用户目录下跨会话持久的数据。它们与 RAG 的区别在于：文件是按路径精确寻址的，读到的一定是原文；RAG 是按语义近似寻址的，读到的是“可能相关”的片段。需要可靠回忆的东西放文件，需要大范围检索的东西放 RAG，这和计算机里“配置放文件、海量数据进数据库”的分工一致。

### 4.4 缓存：KV cache 与 prompt cache

KV cache 是一次请求内部的缓存，类似 L1/L2：推理引擎自动管理，应用层看不见。prompt cache 是跨请求的缓存，类似页缓存：前缀逐字节一致才能命中，命中后按约 0.1 倍计费，过期时间是 5 分钟或 1 小时。它与 CPU 缓存最大的不同是命中条件：CPU 缓存按地址命中，改一个字节只影响一条缓存行；prompt cache 按前缀命中，前缀里任何位置改一个字，后面所有内容都失效。这条规则直接决定了 agent 的上下文布局：不变的内容（system prompt、工具定义）放最前，会变的内容放最后，绝不在中间插入时间戳之类的易变信息。姊妹文档 11.2 的实测也显示了缓存过期的代价：会话闲置超过一小时后，第一次请求要按最贵的写入价重写整段 47 万 token。

## 五、I/O：工具 ≈ 系统调用与设备，MCP ≈ 驱动模型

**工具就是系统调用。**用户程序不能直接操作硬件，只能通过系统调用请求内核代劳；模型不能直接读文件、执行命令，只能发起工具调用，由 harness 代为执行、检查权限、返回结果。两者都在这一层做权限检查，都把调用记入审计日志（strace ↔ transcript）。

**MCP 就是驱动模型加总线标准。**早期计算机每接一种外设都要专门写代码，直到 USB、PCIe 这类总线标准和统一的驱动模型出现，外设才变成即插即用。MCP 在 agent 世界扮演同样的角色：工具提供方实现一个 MCP server（驱动），任何支持 MCP 的 harness 都能挂载它（总线）。驱动带来的问题也一并复制过来：驱动运行在高权限上下文中，一个恶意或有缺陷的驱动能影响整个系统；MCP server 返回的内容直接进入上下文，一个被投毒的 MCP 工具同样能影响整个 agent。

**延迟加载与动态链接。**程序不会在启动时把所有共享库都加载进内存，而是通过 PLT/GOT 做延迟绑定，第一次调用时才解析。Claude Code 的“延迟工具”是同一个机制：大量工具只在上下文里登记名字，需要时先用 ToolSearch 加载完整 schema 再调用；skill 也是按需加载，启动时只放一行描述，被选中时才读入全文（渐进式披露）。这两种做法都是在节省最贵的资源，也就是主存（上下文）。

**中断与轮询。**后台任务完成时给 agent 发通知、文件变化时由 Monitor 推送事件，相当于中断驱动 I/O；让 agent 定期检查状态则是轮询。计算机早就证明了中断优于轮询，agent 也一样：轮询每次都要消耗一轮完整的上下文读取，代价远比 CPU 轮询一个寄存器高。hooks 则相当于内核的 LSM / eBPF 挂载点，可以在每次工具调用前后插入检查或改写。

## 六、操作系统：harness ≈ 内核

这一层在姊妹文档第十三章已有详细对照，这里只列要点。harness 管理会话和子 agent（进程）：fork 子共享父前缀（写时复制），fresh 子换上新的系统提示词（exec）；后台子完成发通知（SIGCHLD），孙子比父活得久时回报主会话（孤儿被 init 收养）；中断按父子树级联，转后台时解绑（setsid）；消息只在工具批次边界投递（安全点）。权限模式相当于保护环：plan 模式只读，default 每次询问，acceptEdits 放行文件写入，bypassPermissions 相当于 ring 0。沙箱和 worktree 相当于容器和 chroot。AIOS 论文把这一层做得最彻底：它把调度、上下文管理、内存管理、存储管理、访问控制从 agent 应用中剥离出来，放进一个独立的 AIOS 内核，统一服务多个 agent，报告称执行速度最高可提升 2.1 倍。这正是“把公共机制下沉到内核”的经典操作系统思路。

与真实内核最大的不同有两点：调度只能协作式，不能抢占，正在跑的工具无法被打断，只能靠看门狗兜底；最高权限属于人，而人的响应以秒到小时计，所以调度必须能容忍“等人”。

## 七、程序与编译：prompt ≈ 源码，skill / workflow ≈ 编译产物

如果模型是处理器，那么写给它的 prompt 就是程序。早期程序员直接写机器码和汇编，每一行都要精确控制硬件；今天的 prompt engineering 有很多类似的特征：对措辞敏感、可移植性差、换一代模型就可能要重写。计算机的出路是更高层的语言和编译器，agent 正在走同样的路，表现为三个层次。skill 相当于库：把一类任务的做法封装成可复用、按需加载的单元。workflow 相当于编译产物：把“由模型逐回合判断下一步”的编排，固化成一段确定性的脚本，循环、分支、中间结果都在代码里，模型只负责每个叶子节点的执行，因此可以重放、可以规模化（姊妹文档第九章）。从历史执行轨迹里蒸馏出 skill 和 workflow，则相当于 profile-guided optimization 或 JIT：先解释执行，发现热点路径后编译固化。

这一层的启发是：**agent 系统的可靠性，很大程度上来自把越来越多的“解释执行”变成“编译执行”。**模型擅长处理开放问题，但对于已经被验证过的流程，每次都让模型重新推理，就像每次都让 CPU 解释执行同一段脚本，既慢又不稳定。

## 八、网络与分布式：多 agent ≈ 分布式系统

多个 agent 协作，本质上是一个分布式系统：节点之间只能通过消息通信，没有共享内存（每个 agent 有独立的上下文窗口），消息有延迟、可能丢失，节点可能失败。MCP、A2A 这类协议相当于协议栈，规定消息格式和语义；共享任务表、收件箱文件相当于分布式协调服务。

关键差异在于**故障模型**。分布式系统里最常见的是崩溃故障：节点挂了就不再响应，容易检测。agent 的典型故障却是拜占庭式的：节点不会挂，而是给出一个看似合理但错误的结果，比如编造的结论、声称完成实际未完成的工作。经典理论告诉我们，容忍 f 个拜占庭节点至少需要 3f+1 个节点，远比容忍崩溃故障（2f+1）昂贵。deep-research 用“三个验证者投票、需要两票才能否决”，就是一个小规模的拜占庭容错。但这类投票有一个分布式理论里没有的弱点：几个“节点”往往是同一个模型，错误高度相关，投票的有效性会打折扣。姊妹文档的实践中，三票验证就曾否决过一条其实正确的结论。

## 九、冯·诺依曼的老问题：提示注入

冯·诺依曼架构把程序和数据存放在同一块内存里，这既是它灵活性的来源，也是一类经典漏洞的根源：只要攻击者能把数据写进内存，并让 CPU 跳转过去执行，数据就变成了代码，例如缓冲区溢出。agent 完全重演了这个问题：系统指令、用户指令、网页内容、文件内容、工具结果全部以 token 的形式放在同一个上下文窗口里，模型无法从格式上区分“这是要执行的指令”还是“这是要处理的数据”。所以提示注入不是某个实现上的 bug，而是这种架构本身的固有风险。

{{< fig "diagrams/04.svg" "提示注入与冯·诺依曼" >}}

计算机花了几十年，逐步建立起三层防御，agent 系统正在一一找到对应物。第一层是 NX 位 / W^X：数据页不可执行，可执行页不可写。agent 的对应物是来源标签和“数据不是指令”的约定，Claude Code 用 system-reminder、agent-message 等标签包裹所有非用户输入，并明确声明它们不构成授权。但这层防御是“软”的：它依赖模型遵守约定，不像 NX 位那样由硬件强制。第二层是带标签的内存，例如 CHERI 让每个指针携带权限和来源，由硬件检查。agent 的对应物是不可伪造的来源标记：hand-back 报告逐行缩进、控制标签被中和、指令形状被扫描，auto 模式的分类器逐条审查 agent 之间的消息。第三层是特权分离和哈佛架构：指令和数据走不同的通道，不可信输入只能在低权限进程里处理。agent 的对应物是“双 LLM”一类设计：负责规划、有权限的模型只看可信输入；处理不可信内容的模型没有工具权限，它的输出只能作为数据被引用，不能改变控制流。CaMeL 一类工作沿这个方向，把控制流和数据流在架构层面分开。

历史经验是：在计算机里，“让代码更小心”从来不足以根除注入，真正有效的是在架构层面让数据**无法**被当成指令执行。对 agent 也一样，靠提示词告诉模型“不要听网页里的指令”属于第一层软防御，长远看必须走到第三层，在结构上隔离控制流。

## 十、本质差异汇总

| 维度 | 计算机 | Agent，以及由此带来的设计约束 |
| --- | --- | --- |
| 执行语义 | 确定性，出错极罕见 | 概率性，会“声称完成”。结果必须验证，且要能重试 |
| 内存访问 | 按地址、读多少付多少 | 全量注意、每轮重读、按 token 付费。上下文越长越贵也越“笨”，要主动做减法 |
| 换出 | 无损，可原样换回 | 有损摘要。细节必须外置到可重读的文件 |
| 缺页 | 硬件自动触发 | 没有中断，模型不知道自己缺什么。要在上下文里显式留引用 |
| 寻址 | 精确地址 | 语义近似（注意力、embedding）。需要精确回忆的内容走文件而不是 RAG |
| 指令与数据 | 已有硬件级隔离（NX、MMU） | 同处一个上下文。注入是架构性风险，要在结构上隔离控制流 |
| 故障模型 | 以崩溃故障为主 | 以拜占庭故障为主，且同模型错误相关。投票有效性打折扣 |
| 调度 | 可抢占 | 只能协作，正在跑的工具不能打断。需要看门狗和上限 |
| 最高权限 | 内核自动判定 | 属于人，响应慢。调度要能容忍“等人” |
| 处理器演进 | 指令集长期稳定 | 能力随模型代际跳变，最优“程序”随之改变。harness 要能随模型升级而简化 |

## 十一、对 agent 架构设计的启发

把上面的对照落到设计上，可以得到一组原则。前一半是“照搬计算机的成熟方案”，后一半是“为本质差异专门设计”。

**1. 把上下文当最稀缺的内存来管。**给 system prompt、工具、历史、检索结果分别设预算；设水位和熔断；优先做“减法”（清理用过的工具结果、子 agent 只回传摘要），而不是一味扩大窗口。目标是 Anthropic 所说的“最小的高信号 token 集合”。

**2. 为有损内存配一块无损外存。**凡是丢了会出错的东西（约束、决定、进度、待办），都写进文件或任务表，压缩之后能原样读回。摘要只是提示，原文在磁盘上。

**3. 让缺页可见。**上下文里不放大块原文，而是放指针：文件路径、查询、链接、子任务 id，并告诉模型“需要细节时去读”。这相当于手工实现页表，弥补没有缺页中断的缺陷。

**4. 按前缀命中来布局上下文。**稳定内容在前、易变内容在后；工具集和 system prompt 尽量保持跨请求不变；需要大量背景的短任务用共享前缀的 fork，长任务用独立的 fresh 子 agent。

**5. 内核与应用分离。**调度、上下文管理、权限、记账、持久化下沉为 harness / 内核的公共能力，业务 agent 只描述任务。AIOS 与 Claude Code 都在走这条路。

**6. 用标准接口连接外设。**工具通过 MCP 这类标准协议接入，按需加载 schema；同时把每个工具视为“驱动”，审查它的来源和权限，因为它返回的内容会直接进入主存。

**7. 把热点路径编译掉。**被验证过的流程沉淀为 skill 和 workflow，让确定性代码负责编排、模型只负责叶子任务；从执行轨迹中持续蒸馏，形成“解释 → 编译”的闭环。

**8. 按拜占庭故障设计验证。**关键结论由独立上下文的 agent 复核；投票时尽量引入异构性（不同模型、不同提示、不同证据来源），以降低错误的相关性；保留“无法验证”这一状态，不把它当成通过或否决。

**9. 在结构上隔离指令与数据。**所有非用户输入打上来源标签且不带权限；处理不可信内容的组件不持有危险工具；规划者只看可信输入。不要把安全寄托在“请模型别听坏指令”上。

**10. 为协作式调度配看门狗。**每一个可能让 agent 再跑一轮的机制都设次数上限；任何循环都要有超时和熔断；用量按任务树汇总（类似 cgroup），父任务看到的成本必须包含所有后代。

**11. 让 harness 随模型升级而变薄。**今天为弥补模型能力不足而写的大量规则和脚手架，在下一代模型上可能变成负担。把这类“补丁”与核心机制分开，定期评估哪些可以删掉。这是计算机史上没有的要求：硬件很少会自己变聪明。

## 十二、未来演进：agent 正在快速重走计算机史

把两条时间线并排，会发现 agent 系统在短短三年里，几乎把计算机前几十年的关键步骤都走了一遍。2022 年的单轮对话是批处理时代，一次跑一个“程序”就结束；2023 年的工具调用和 ReAct 给处理器接上了 I/O；2024 年的 harness 和子 agent 带来了多道程序和早期操作系统；2024 到 2025 年的 MCP 和上下文工程，对应驱动标准化和内存管理；2025 年的 workflow 和后台 agent，对应作业调度和守护进程。

{{< fig "diagrams/05.svg" "演进对照" >}}

以计算机史为参照，接下来几步大致可以预期。以下是基于类比的判断，不是已经发生的事实。

**虚拟上下文成为默认能力。**MemGPT 提出的虚拟上下文管理会从研究原型变成 harness 和模型服务的标配：应用不再关心上下文窗口有多大，系统自动在上下文、记忆文件、检索库之间换入换出，就像今天的程序不关心物理内存大小。真正的突破点在于让换出变得接近无损，例如保留可回溯的原文指针，以及让“缺页”可感知，例如模型能可靠地意识到并请求缺失的信息。

**出现“硬件级”的指令与数据隔离。**今天靠标签和约定的软防御，会逐步下沉到模型和协议层：模型训练时就区分指令通道和数据通道，协议层给每段内容附带不可伪造的来源与权限，类似 NX 位从软件约定变成 CPU 特性的过程。在这一步完成之前，提示注入会一直是 agent 规模化落地的最大障碍。

**标准化的 agent 内核与 ABI。**就像 POSIX 让程序可以在不同 Unix 之间移植，会出现一组事实标准，覆盖进程模型（派生、通信、取消、恢复）、记账（按任务树汇总成本）、权限（能力模型）。MCP 已经覆盖了“驱动”这一层，A2A 一类协议正在尝试覆盖“网络”这一层，中间的“系统调用”层仍是空白。

**可抢占的调度与确定性的编排。**推理服务会支持在生成过程中安全地中断和恢复，使抢占式调度成为可能；同时越来越多的编排逻辑会被“编译”成确定性的 workflow，模型只在叶子节点做判断，与“解释器 → 编译器 → JIT”的演进一致。

**agent 网络与跨组织信任。**再往后，类似计算机从单机走向互联网，agent 之间会跨组织通信、调用对方的能力。那时最难的问题和互联网早期一样：身份、信任与计费，需要类似 TLS、PKI 和支付清算的基础设施。

最后有一个需要警惕的地方：类比是理解的工具，不是设计的模板。计算机系统的很多方案建立在“处理器是确定的”这一前提上，而 agent 的处理器每一代都在变强。今天必须由 harness 承担的工作（例如精细的上下文管理、复杂的编排脚本），明天可能由模型自己完成。好的 agent 架构，应当在借用计算机系统成熟机制的同时，保持让这些机制随模型进步而退场的能力。

## 十三、池化与编排：agent 会走向 Docker / K8s 吗

**结论：会，但三层的进度不同，最上面一层不会照搬。**沿着“agent ≈ 计算机”这条路往下走，下一站自然是“agent ≈ 数据中心”：计算机从单机走到虚拟化、容器、编排，是因为机器多了以后，资源要池化、负载要调度、故障要自愈、交付要标准化。agent 系统规模上来之后面对的是同一组问题。目前的情况是：**算力层已经池化，执行层正在容器化，agent 层只借到了 K8s 的控制面思想**，而它的调度单位，即有状态的会话，与 K8s 擅长的无状态 pod 有本质差异。

{{< fig "diagrams/06.svg" "池化与编排三层" >}}

### 13.1 算力层：模型推理已经池化

这一层最接近传统云原生，也走得最快。原因很简单：推理是无状态请求加上一块可复用的缓存，形态和 Web 服务相似，只是更贵。

**按模型路由的推理网关。**Kubernetes 的 Gateway API Inference Extension 把一组推理 pod 抽象成 InferencePool，网关从请求体里读出模型名做路由，再由一个 endpoint picker 根据队列长度、显存占用、已加载的 LoRA 适配器挑选具体 pod。这相当于把 Service 的“随便挑一个副本”升级成了“挑最合适的那个”。

**缓存亲和调度与 prefill / decode 分离。**llm-d 在 vLLM 和 K8s 之上做了两件事：一是 KV cache 感知路由，读 vLLM 的缓存事件，把请求发到已经持有相同前缀的副本上，这和前文讲的 prompt cache 是同一个道理，只是从“单机缓存命中”扩展成了“集群级缓存亲和”；二是把算力密集的 prefill 和延迟敏感的 decode 放在不同的 worker 上，中间通过网络传 KV cache。官方文档给出的收益是前缀感知路由比轮询吞吐高约 3 倍，属于厂商实测，需要按自己的负载复核。

**KV cache 成为独立的存储池。**月之暗面的 Mooncake 更进一步，把 GPU 集群里闲置的 CPU、DRAM、SSD 和网卡汇成一个分离式 KV cache 池，由全局调度器为每个请求挑选 prefill 和 decode 实例对。论文报告在真实负载下 Kimi 能多处理 75% 的请求。在计算机系统里，这一步对应的是“存算分离”：计算节点无状态、状态放进共享存储池，正是云数据库和对象存储走过的路。

这一层的结论很明确：**token 正在像电力一样成为公用事业**，应用侧只看到按模型、按 token 计费的端点，背后是池化的 GPU 和缓存。它和传统云原生的唯一大区别是缓存的权重：传统 Web 服务的副本几乎可以互换，推理副本因为 KV cache 的存在，“发给谁”直接决定成本和延迟。

### 13.2 执行层：沙箱正在容器化

agent 要跑代码、读写文件、开浏览器，就需要一个隔离的执行环境。这一层正在快速标准化，而且直接长在容器生态上。

**K8s 官方的 agent 沙箱。**SIG Apps 下的 agent-sandbox 项目新增了 Sandbox 这种资源，配套 SandboxTemplate（模板）、SandboxClaim（申领）和 SandboxWarmPool（预热池）。它要解决的问题很说明情况：agent 的执行环境既不像 Deployment 那样无状态、可多副本，也不像 StatefulSet 那样编号固定、成组部署，而是**单个、有身份、有持久盘、可能长时间空闲**的 pod。底层隔离交给 gVisor、Kata 这类安全运行时。

**microVM 沙箱。**E2B 这类服务用 Firecracker microVM 给每个沙箱一个独立内核，靠预热快照把启动压到百毫秒量级（公开资料多为约 150 ms，属厂商与第三方数字）。这对应计算机里“进程隔离不够，就上虚拟机”的老思路，代价是比容器更重，换来的是更强的边界。

预热池加按需申领，本质上是数据库连接池和 PVC 申领模式的组合：创建成本高的资源提前备好，用的时候借，用完还或销毁。这一层的方向基本确定：**每个 agent 会话配一个一次性或可挂起的沙箱**，会成为和“每个请求一个线程”一样的默认做法。

### 13.3 Agent 层：借控制面，不借数据面

最上面一层，即 agent 本身如何被定义、部署、发现和调度，目前还在早期。已有的尝试主要是把 K8s 的**控制面思想**搬过来：kagent（CNCF 沙箱项目）把 agent 定义成 CRD，用 GitOps 和 RBAC 管理；A2A 协议用 Agent Card 描述一个 agent 的身份、能力和端点，起到服务发现的作用。下表把常用的 K8s 概念与 agent 世界逐一对照。

| K8s / Docker 概念 | Agent 世界的对应物 | 能否直接照搬 |
| --- | --- | --- |
| 镜像（image） | system prompt + 工具清单 + skill + 模型版本，合起来是一个“agent 镜像” | 能。需要版本、签名、灰度，和镜像一样不可变 |
| 镜像仓库 | skill / agent 仓库 | 能。还要多一项：评测分数随版本一起发布 |
| 容器 | 一个会话实例（上下文 + 沙箱） | 部分。会话有状态，见 13.4 |
| Service + DNS | A2A Agent Card、agent 注册表 | 能。能力描述是自然语言，匹配要靠语义 |
| Ingress / Gateway | LLM 网关、推理网关 | 能。已在发生 |
| requests / limits | token 预算、上下文上限、工具调用次数 | 能。计量单位从 CPU 变成 token 和钱 |
| ResourceQuota / namespace | 按团队、按任务树汇总的预算 | 能。要按任务树记账，而不只是按进程 |
| HPA 自动扩缩 | 按队列长度、KV 利用率、预算扩缩 | 部分。会话不能随意缩容，只能挂起 |
| Job / CronJob | 后台 agent、定时 routine、workflow | 能。但“成功”要验收，不是退出码 0 |
| liveness 探针 | 卡死检测、循环检测、看门狗 | 部分。agent 会“活着但在原地打转” |
| Operator / reconcile | supervisor：持续把任务推向完成 | 部分。期望状态难以声明，需要验收器 |
| sidecar / service mesh | hooks、护栏模型、出口策略、审计 | 能。还要加一层：检查内容是否越权，而不只是检查连接 |
| PVC 持久卷 | 记忆文件、工作区、虚拟文件系统 | 能。这是会话可挂起、可迁移的前提 |

### 13.4 为什么最上面一层不能照搬

K8s 的核心假设是“cattle, not pets”：pod 无状态、可替换，坏了就删掉重建，状态放在外部。agent 会话恰好相反，它是 pet，而且最贵的那部分状态就在它自己身上。

{{< fig "diagrams/07.svg" "Pod 与会话生命周期" >}}

**第一，状态重，重启贵。**上下文就是会话的工作记忆。删掉重建意味着重新读文件、重新理解任务，prompt cache 也随之失效，要按全价重付一遍。所以 agent 调度的基本动作不是“扩缩副本”，而是“挂起和恢复”：把 transcript 和沙箱快照存下来、释放模型和沙箱资源，需要时再恢复，必要时迁移到别的节点。这更像虚拟机热迁移，而不是 Deployment。

**第二，计量单位变了。**K8s 按 CPU 和内存调度；agent 的稀缺资源是 token、上下文窗口、KV cache 占用、工具调用次数，最终都折算成钱。配额、扩缩、优先级都要围绕这些指标重新定义。

**第三，时间尺度和占用模式不同。**pod 秒级启动、持续占用；agent 任务从分钟到数天，大部分时间在等模型、等人审批、等子任务回报。等待期间如果仍占着沙箱和缓存就是浪费，所以“按会话缩到零”是刚需。

**第四，重试不幂等。**K8s 的自愈建立在“重启就好”上；agent 的动作有副作用（发消息、改数据、提交代码），失败后简单重来可能重复执行。需要前文讲过的 journal 重放、幂等工具和补偿动作，这更接近数据库事务，而不是容器重启。

**第五，期望状态难以声明。**reconcile 循环的前提是能比较“期望”和“实际”，例如“期望 3 个副本，实际 2 个”。agent 的期望状态是“任务完成且正确”，是否达成本身就要判断，所以 agent 的控制循环里必须有一个验收器，而验收器本身也是概率性的。

**第六，隔离边界不够用。**容器和 microVM 防的是恶意代码越界；agent 被提示注入后，做的可能全是“边界内的合法动作”，例如用自己有权限的 token 把数据发出去。所以沙箱之外，还需要第九章讲的权限、出口策略和审批，这些不在容器的职责范围内。

### 13.5 演进判断

综合上面三层，可以给出一个分阶段的判断。以下是基于类比和现状的推断，不是已经发生的事实。

**已经发生：算力池化。**推理网关、缓存亲和路由、prefill / decode 分离、KV cache 池都已有开源实现和生产案例。接下来的竞争点在缓存：谁能让跨请求、跨会话的缓存命中率更高，谁的单位 token 成本就更低。

**正在发生：沙箱成为标准件。**预热池、按需申领、快照恢复会变成平台默认能力，就像今天没人自己管理线程池一样。

**下一步：会话成为一等调度对象。**会出现类似“Session”这样的资源，把上下文、沙箱、预算和权限打包成一个可调度单元，原生支持挂起、恢复、迁移，调度器同时考虑缓存亲和、预算余额和等待时长。agent 仓库会像镜像仓库一样管理版本、签名和灰度，并附带评测结果。

**更远：声明式任务与 agent 网格。**用户只提交“任务 + 预算 + 验收标准”，平台决定用哪个模型、派几个子 agent、开多少沙箱，相当于把 K8s 的声明式思想从“资源”提升到“结果”。跨组织的 agent 调用会需要类似服务网格的身份、计费和审计层，A2A 一类协议是它的起点。

一句话概括：**算力会像电力一样池化，执行环境会像容器一样标准化，agent 本身会借用 K8s 的控制面思想，但它的调度对象是有状态的会话，形态上更接近“虚拟机热迁移 + 连接池 + 事务日志”的组合，而不是无状态副本。**

### 13.6 落到自己的系统上

如果拿这张对照表看一个已有的 agent 平台，可以快速定位缺口。以我们自己的系统为例，仅作类比：LLM 网关对应推理网关层，skill 仓库对应镜像仓库，画布的虚拟文件系统对应持久卷，工具服务对应执行层。按 13.4 的六点检查，最值得优先补的通常是三项：**会话级的挂起与恢复**（不让等待中的会话占资源），**按任务树的预算与记账**（而不只是按单次调用计费），**验收器进入控制循环**（“完成”需要判定，而不是模型自己声称完成）。
