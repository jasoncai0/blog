## 一、概念与架构

这三道是地基。后面所有题都在假设你已经分得清「谁在做决定」。

### Q1 什么是 Agent？与大模型有什么本质不同？

Agent 是一个由外部程序维护的「目标 → 决策 → 行动 → 观察」闭环，模型负责决策，程序负责让动作真的发生。普通调用大模型，控制流在调用方手里：prompt 怎么写、调几次、下一步做什么，都是你的代码定死的。Agent 把控制流交给了模型，程序退到后面提供动作和观察。

两者的差距可以拆成三个具体限制。知识冻结，训练数据有截止日期，问今天股价它不知道；不能行动，它能写出完美的邮件正文，但点不了发送；没有持续状态，两次调用之间完全失忆，除非你手动把历史塞回去。Agent 对应补的是检索、工具、记忆加循环。

判断一个系统算不算 Agent，不要看它有没有调工具，看它能不能根据执行结果改下一步。固定顺序调三次搜索，那是 workflow。

常见追问：

1. **加了插件算不算 Agent？** 取决于插件结果会不会改变后续路径。只会按固定顺序调一次，仍然是被编排的流程。
2. **Agent 一定比 workflow 好吗？** 不。可控性、成本、可评测性都更差，能用固定流程解决就别上 Agent。

### Q2 Agent 的基本架构由哪些核心组件构成？

四个核心组件是 LLM、工具、记忆、规划模块，但只报名词会被追问「它们怎么串起来」。要能画出一次循环：装配上下文 → 模型决策 → 解析动作 → 工具执行 → 结果回填 → 更新状态 → 下一轮。

规划模块可以很轻，轻到只是 prompt 里的一份待办清单，也可以是独立的 planner 调用。记忆分两层：上下文窗口里的短期状态，和外部存储的长期记忆。工具是唯一能改变外部世界的组件，所以它的描述、粒度和错误信息直接决定模型选不选得对。

实际工程里还有第五个组件，通常没人主动提：执行器。它管权限、超时、重试、结果规范化和日志。没有它，模型输出的工具请求落不了地。这个组件就是后面 Q25 讲的 harness。

常见追问：

1. **哪个组件最容易出问题？** 工具设计。模型选错工具，八成是描述写得像文档摘要，没写清什么时候该用、什么时候不该用。
2. **记忆和上下文窗口是一回事吗？** 不是。窗口是易失的工作台，记忆是要主动读写的外部存储。

### Q3 Workflow、Agent、Tools 三个概念怎么区分？

粒度从小到大，区别只有一句话：谁决定下一步。Tools 不决策，只执行，输入输出确定；Agent 自己决策，判断调哪个工具、要不要继续、什么时候停；Workflow 由开发者提前把节点顺序和分支写死，节点内部可以嵌 Agent。

| | 谁决定下一步 | 确定性 | 成本 | 可调试性 | 典型场景 |
|---|---|---|---|---|---|
| Tools | 调用方 | 高 | 低 | 高 | 查订单、发邮件、跑测试 |
| Agent | 模型 | 低 | 高 | 中 | 开放目标、路径不确定 |
| Workflow | 开发者 | 高 | 中 | 高 | 审批流、ETL、固定 SOP |

生产上主流是混着用：外层 Workflow 保证主流程可控可测，需要灵活判断的节点嵌一个 Agent。纯 Agent 的系统很少，因为出了问题没法复现。

常见追问：

1. **Agentic Workflow 是什么？** 外层是确定性编排，内层节点有局部自主权。它保住了可评测性，又拿到了灵活性。
2. **三者能互相替代吗？** 不能。Tools 是能力，Agent 是决策者，Workflow 是编排，层级不同。

### 跨题追问：概念与边界（本节 6 条）

- **四个组件里，规划和记忆必须分开吗？** 分开是因为生命周期不同。规划每一步都可能重算，记忆要跨轮甚至跨任务存活。合成一个模块的后果是改计划时把记忆一起洗掉。（合并第 2 篇的四个追问）
- **Workflow 的节点一定是 Agent 吗？** 不必。节点可以是 LLM 调用、一个工具、甚至一段脚本。关键不在节点是什么，而在边由谁定：边写死在代码里是 Workflow，边由模型选是 Agent。（第 3 篇第 2 问）
- **为什么 Agent 是现在才爆发，不是三年前？** 三个条件同时到位：模型能稳定输出结构化的动作、工具生态（搜索、代码执行、浏览器）足够便宜、上下文长度撑得住多步任务。少一个都只能做演示。（引申：原文只给了趋势，没给因果）
- **怎么快速判断一个新系统是不是真 Agent？** 三个测试：换一个没见过的输入还能不能走通、失败后能不能自己换路径、外部状态是否真的变了。三个都过才算。（引申）
- **问「Agent 和大模型有什么不同」，标准答法是什么？** 一句话加一个动作：模型只输出下一个 token，Agent 是一个由程序驱动的闭环，模型负责决策，程序负责让动作真的发生。然后立刻给一个闭环的例子，别停在定义上。（合并第 1、2 篇的答法差异）
- **概念题为什么会答成「工具调用」？** 因为工具调用是最容易观察到的部分。只要回答里没有「谁决定下一步」，面试官一定会把话拉回到自主性上。（引申，来自第 1 篇的追问节奏）

## 二、设计范式与规划

这五道是高频区。答得对不对，差别不在记不记得住名词，在说不说得清「什么时候该换另一种」。

### Q4 有哪些 Agent 设计范式？Agent 和 Workflow 到底差在哪？

差在控制流归谁，这一点和 Q3 是同一个答案的两种问法。范式上除了纯 Agent，常见的有 ReAct、Plan-and-Execute、Reflection，再往外还有 Router（先分类再分派）、Orchestrator-Worker（主 Agent 拆活派活）、Evaluator-Optimizer（生成与评分交替）。

选范式看两个变量：路径确定性和步骤数量。路径确定、步骤少，直接 Workflow；路径不确定但每步能拿到反馈，ReAct；步骤多、依赖强、可以并行，Plan-and-Execute；输出质量要求高且能定评估标准，加 Reflection。

常见追问：

1. **为什么生产系统很少用纯 ReAct 跑长任务？** 步数一多，token 线性涨，中途走错没有全局纠偏，最后只能靠步数上限兜底。
2. **范式能混用吗？** 能，而且应该。外层 Plan-and-Execute，每个计划步骤内部是 ReAct，交付前跑一次 Reflection。

### Q5 ReAct 是什么？具体怎么实现？

ReAct 是 Reasoning 和 Acting 交替：模型先写一段思考，再输出一个动作，程序执行后把观察结果拼回上下文，模型基于新观察继续想。它把「想」和「做」放进同一个循环，所以每一步都能用上刚拿到的真实信息。

实现就是一个循环加三段协议。思考、动作、观察三个字段约定好格式，程序解析动作、执行、把结果作为观察追加。早期靠文本解析，现在直接用模型的原生 tool call，解析失败率低很多。

```python
messages = [system, user]
for step in range(MAX_STEPS):
    out = llm(messages, tools=TOOLS)
    if not out.tool_calls:
        return out.content          # 模型认为可以收尾
    for call in out.tool_calls:
        result = execute(call)      # 权限、超时、幂等在这里
        messages.append(tool_result(call.id, result))
messages.append("步数用尽，请汇报当前进展")
```

四个常见坑：工具名幻觉（模型编一个不存在的工具）、参数不合法、观察结果太长把窗口撑爆、没有停止条件导致空转。前两个靠工具 schema 和错误回传解决，后两个靠上下文预算和步数上限。

常见追问：

1. **和 CoT 的区别？** CoT 只在模型内部推理，信息全来自参数；ReAct 每步可以从外部拿新信息，推理依据是真实的。
2. **ReAct 一定能收敛吗？** 不能。它没有全局计划，遇到需要回退的场景容易在两条路之间来回跳。

### Q6 ReAct、Plan-and-Execute、Reflection 怎么选？

三者的差别在「决策和执行的关系」：ReAct 边想边干，Plan-and-Execute 先想全再干，Reflection 不产生新流程，是给前两者加的检查环节。

| | 决策时机 | 纠错粒度 | Token | 典型失败模式 |
|---|---|---|---|---|
| ReAct | 每步 | 单步，就地改 | 随步数线性 | 路径震荡、原地打转 |
| Plan-and-Execute | 开始一次，必要时重规划 | 计划层，整段重来 | 前期高、执行稳定 | 计划本身错，全盘错 |
| Reflection | 生成后 | 输出层 | 至少多一次调用 | 自我确认，越评越自信 |

选型看三个维度：任务复杂度、流程确定性、输出质量要求。任务简单且要求快，直接调模型；路径不确定且工具多，ReAct；步骤多、依赖强、能并行，Plan-and-Execute；质量要求高且评估标准写得出来，加 Reflection。

{{< fig "diagrams/02-traces.svg" "同样的任务在三种范式下的轨迹差别：ReAct 每步都能改方向，计划式只在计划层纠偏，反思式在交付前补一轮检查。步数、token 和纠错时机是三者的真实分界线。" >}}

常见追问：

1. **计划什么时候重规划？** 观察和计划假设冲突、连续失败到阈值、预算过半但进度不足，三个条件任一触发。
2. **Reflection 会陷入自我确认吗？** 会。评估必须引入外部信号，测试、schema 校验、检索到的证据都算，纯靠模型自评不可靠。

### Q7 复杂任务怎么拆分？拆了为什么效果更好？

拆分的收益来自三处：单步聚焦一件事，模型出错率下降；每一步有可判定的完成条件，错了当场能发现；无依赖的步骤可以并发，端到端延迟能降下来，我经手的项目里常见 40% 到 60% 的降幅。

拆分有两种。静态拆分按业务模板写死，稳定但覆盖不了新情况；动态拆分让模型自己规划，灵活但难控制。工程上第三种最实用：自适应拆分，先粗粒度拆，某一步做不好再往下拆一层。

拆完要定义验证标准，这一步最容易被跳过。标准必须是机器可判定的：测试通过、字段存在、行数匹配、状态码 200。写成「看起来合理」就等于没写。

常见追问：

1. **拆太细有什么代价？** 调用次数涨、上下文重复传、步骤间协调成本上升。粒度控制在「一步一个可验证产物」。
2. **并发的边界在哪？** 写同一份资源、有前后依赖、需要共享中间状态的步骤都不能并发。

### Q14 怎么给 LLM 加规划能力？

三条路，成本递增：CoT 让它把推理步骤写出来，ToT 让它同时探索多条路径并打分选优，GoT 把推理组织成图，节点可以复用和合并。

工程上真正常用的是第四种：Plan-and-Execute 加一份显式的待办清单。计划落成结构化数据（步骤、依赖、验收条件），执行时逐步更新状态，比让模型「在心里规划」可靠得多。提示词层面加「先列步骤再动手」「每步写验收条件」确实有效，比「请仔细思考」这种空话管用。

成本上 ToT 的调用量大概是 CoT 的 3 到 5 倍，GoT 目前基本停留在论文里。

常见追问：

1. **规划能力能靠 prompt 提升多少？** 结构化输出加分解示例，能明显改善步骤质量；但计划本身的正确性上限，还是受模型对领域的理解限制。
2. **计划要多细？** 细到每步有一个可判定的产物就够，再细就是浪费 token。
### 跨题追问：范式与规划（本节 13 条）

- **ReAct 的循环是谁在驱动，模型自己会转吗？** 不会。模型一次只输出一段文本。外层代码解析出动作、执行工具、把观察拼回历史、再调一次模型。所谓循环是代码写的 `for`，不是模型的自省。（第 5 篇连问三遍，这是这题最常见的错误答案）
- **CoT 最大的问题是什么？** 单链。方向一开始错，后面每一步都在错的前提下推进，链条内部没有纠偏机制。（第 14 篇第 2 问）
- **ToT 怎么做，成本多少？** 把一条链展开成树，每个节点生成多个候选，打分剪枝再往下走。成本约为 CoT 的 3–5 倍，因为要生成和评估多条路径。（第 14 篇第 3 问；倍数是原文经验值）
- **GoT 比 ToT 多解决什么？** 结果复用。树上的分支不能合并，图可以：两条推导出的中间结论能共享，省掉重复推理。代价是实现复杂、状态难管。（第 14 篇第 4 问）
- **Reflection 是第四种范式吗？** 不是同一个层面。它挂在 ReAct 或 Plan-and-Execute 后面做检查，自己单独不成立。（第 6 篇第 2、3 问）
- **三种范式的 token 消耗差多少？** 同一任务下 ReAct 与步数线性增长；Plan-and-Execute 多一次规划、每步更短；Reflection 至少翻倍，生成和评估各算一遍。（第 6 篇小节设问）
- **动态 Replan 和 Reflexion 差在哪？** Replan 改的是这一轮的计划，Reflexion 改的是下次的策略（把失败教训写进记忆）。一个在任务内，一个跨任务。（第 6、7 篇小节设问）
- **任务拆分有两种思路，怎么选？** 静态拆分按业务模板写死，稳定可测；动态拆分让模型自己定，灵活但难控。工程上多用第三种：粗粒度先拆，某一步做不好再往下拆一层。（第 7 篇第 3 问）
- **拆完的验证标准怎么写？** 必须机器可判定：测试通过、字段齐全、行数匹配、状态码 200。「看起来合理」不算标准。（第 7 篇小节设问）
- **为什么生产系统很少用纯 ReAct 跑长任务？** 步数一多 token 线性涨，中途走错没有全局纠偏，最后只能靠步数上限兜底。（引申）
- **计划要不要给人看一眼再执行？** 高风险或长周期任务要。计划评审是成本最低的纠偏点，等执行到一半再发现问题，返工代价高一个数量级。（引申）
- **「规划能力」和「会写计划」是一回事吗？** 不是。会写计划是输出格式，规划能力是计划能被后续执行验证并在失败时修正。只要求输出列表的 prompt，产出的常是不可执行的计划。（引申）
- **ToT 在生产里为什么少见？** 成本乘数太高，而且任务需要「可枚举的分支」才划算。多数工程问题用 Plan-and-Execute 加一次重规划就够。（引申）

## 三、记忆与上下文

这一层决定模型每轮能看到什么。答不好这两道，前面的范式讲得再熟也会被判定成「只会调 API」。

### Q8 Agent 的记忆机制怎么设计？

记忆要解决的是「多步任务保持状态」和「跨任务积累经验」两件事，设计时拆成三层就够了：短期（当前任务的工作台）、长期（外部存储，按需检索）、实体（抽出来的结构化事实）。

| 类型 | 存在哪 | 活多久 | 怎么取 |
|---|---|---|---|
| 感知 | 当前输入 | 一次调用 | 直接进 prompt |
| 短期 | 上下文窗口 | 一个任务 | 每轮重放或压成摘要 |
| 长期 | 向量库 / 文档库 | 跨任务 | 语义检索召回 |
| 实体 | 关系表 / KV | 长期，可更新 | 按实体主键精确取 |

实际设计绕不开三个问题：存什么、怎么存、什么时候取。存的标准是「下次决策会用到」，不是「说过的都存」。怎么存看更新方式：会变的事实用结构化字段，覆盖旧值；不会变的经验用文本加向量。什么时候取分两种，主动注入（每轮必带的任务状态）和按需检索（模型自己调一个记忆工具）。

常见追问：

1. **记忆和 RAG 什么区别？** 记忆是自己产生的，要设计写入、更新、遗忘；RAG 是外部语料，只读。
2. **记忆污染怎么防？** 每条记忆带来源和时间，结论类记忆必须附证据；冲突时以新为准，但保留旧值备查。

### Q9 长短期记忆具体怎么存、粒度多大、怎么用？

短期记忆就是上下文窗口里的消息加结构化状态。消息保原话，状态保已经确认的实体、约束、当前步骤。任务结束就清掉，不需要持久化。

长期记忆我按「一个事件」或「一次交互」为单位存，不按单句存。太碎检索出来全是噪音，太粗又丢细节。一条记忆带上元数据：用户、时间、类型、来源、时效。写入前先做一次抽取，把「用户说下周要去上海出差三天」变成 `{subject: user, action: travel, place: 上海, duration: 3d, time: 下周}`，这样后面能按时间合并、能覆盖旧值。

检索用混合策略：向量相似度加时间衰减加重要度加权，取回后再让模型判断相关性。只按向量取，最新的偏好经常输给语义相似的旧记忆。

常见追问：

1. **过期的偏好怎么处理？** 三类分开：事实类只增不改，按时间取最新；偏好类可覆盖；临时状态带 TTL。
2. **粒度怎么定？** 用一个反例判断：如果你需要把两条记忆拼起来才能回答一个问题，说明粒度太细。

### Q12 记忆压缩有哪些方法？

四种：滑动窗口、摘要、重要性过滤、结构化抽取。它们的区别是丢什么：窗口丢时间，摘要丢细节，过滤丢低分，抽取换载体。

| 方法 | 丢什么 | 成本 | 风险 |
|---|---|---|---|
| 滑动窗口 | 最老的历史 | 零 | 早期约束被丢掉，后面重复犯错 |
| 摘要 | 细节与措辞 | 一次调用 | 摘要本身有损，约束容易漏 |
| 重要性过滤 | 低分内容 | 打分调用 | 打分标准难定，容易丢关键小事实 |
| 结构化抽取 | 原始表达 | 抽取调用 | 抽错比丢更麻烦 |

我在项目里常用组合：窗口快满时先对最老的一段做摘要，摘要里强制保留「目标、约束、已确认事实」三项，再做结构化抽取把事实落到外部状态。这样丢掉的是对话过程，留下的是决策依据。

常见追问：

1. **压缩完怎么验证没丢关键信息？** 用后续步骤做检验：压缩后如果模型重复问已经答过的问题，说明约束丢了。
2. **为什么不直接换个长窗口模型？** 窗口变长不等于注意力均匀，超长上下文里的中段信息经常被忽略，而且每轮成本线性涨。

### Q17 上下文工程怎么设计？

把上下文当成每轮运行时装配出来的工作台，不是一直堆着的聊天记录。每次调用前，按当前子任务从几类材料里挑：指令、用户需求、任务状态、近期对话、长期记忆、工具定义与结果、检索证据。

排序即优先级。System 和 Developer 指令在最上面，负责「要做什么、不能做什么」；任务状态（目标、约束、待办、当前步、已完成结果）紧随其后；记忆、检索证据和工具结果放后面，负责「这一步需要知道什么」。旧记忆和外部资料不能覆盖更高优先级的指令。

网页、文档、工具返回值一律按数据处理。用分隔符和显式声明隔离，里面出现「忽略以上规则」也只能当文本，不能变成命令。这是提示词注入的防线。

预算在装配前分配，不是超了再截断。先扣掉模型输出的预留空间，再给每一类分配上限和不可丢失项。超预算的顺序是：去重 → 裁剪低相关证据 → 去掉本轮用不上的工具定义 → 压缩旧历史。

和 Prompt Engineering 的区别：Prompt 是静态模板，上下文工程是每轮都要跑一遍的装配流程，还要把执行后的状态增量写回外部存储。

常见追问：

1. **To-Do 清单为什么有用？** 它把「做到哪了」变成显式文本，模型不用从长历史里自己推断，注意力自然集中到下一步。
2. **上下文里最该删的是什么？** 与当前子任务无关的工具定义和已经过期的检索片段，这两类占空间且干扰最大。

### Q29 上下文压缩阈值怎么定？

没有通用的 80%。阈值要由「剩余空间够不够撑完接下来的任务」决定，而不是由「用了多少」决定。

先算实际占用。窗口里除了聊天记录，还有系统指令、几十个工具定义、刚返回的大段工具结果，工具定义在有些框架里能占到三成，只盯聊天记录会误判。

然后给输出留位置。最大输出长度、下一轮的推理文本、可能的工具参数，都要提前扣掉。

再按任务类型动态调。下一步要读大量测试日志，就算当前只用了 50% 也该先压缩；只是做一次短查询，后续几乎不增长，就可以保留原文。压缩本身有代价，压太早丢细节，压太晚直接超限报错。

压到哪也要算。压完只剩 10% 余量，下一轮又要压，等于每轮付一次摘要成本。目标是一次压到能撑过接下来若干轮。

{{< fig "diagrams/03-budget.svg" "窗口不是只装聊天记录：指令、工具定义和工具结果常常比历史更占地方。左边是预算怎么分，右边是超预算时的处理顺序，摘要排在最后而不是最先。" >}}

常见追问：

1. **怎么验证阈值合适？** 看四个量：任务完成率、关键信息保留率、压缩延迟、token 成本，在真实任务上比，不看压缩率。
2. **压缩完要检查什么？** 目标、约束、未完成步骤三项是否还在。少了任何一项，后面一定重复劳动。

### 跨题追问：记忆与上下文（本节 14 条）

- **记忆除了短期长期，还有哪两类？** 感知记忆和实体记忆。前者是当前输入的原始内容，只在一次调用内有效；后者是从对话里抽出的结构化事实，可以长期更新。（第 8 篇第 2、3 问）
- **长期记忆存在哪，怎么查？** 向量库存语义，关系表或 KV 存实体。查询走混合策略：向量相似度加时间衰减再加重要度，取回后让模型判断相关性。（第 9 篇第 2 问）
- **关键词搜不到、语义相近怎么办？** 纯关键词匹配不了「代码习惯」和「Python 风格偏好」。语义靠向量，新旧靠时间衰减，两个都要。（第 9 篇第 3 问）
- **记忆拆得越细越好吗？** 不是。拆太细检索噪音大，一条完整偏好被拆成五条，只命中两条就是碎片。以「一个事件」或「一次交互」为单位存，够用且可回溯。（第 9 篇第 4 问）
- **记忆模块真正的难点是什么？** 三个问题：存什么值得存、用什么介质存、什么时机取出来。三个都答不上，就只是把聊天记录搬了个地方。（第 8 篇第 4 问）
- **知识图谱在记忆里解决什么？** 关联。向量只能找「像」，图谱能答「谁和谁有关」。代价是抽取和 schema 维护，实体一多就得有人管。（第 8 篇小节设问）
- **用户三天前确认的决策被压缩丢了，Agent 又提被否决的方案，怎么办？** 压缩时把「目标、约束、已确认决策、已否决方案」列为不可丢项，单独存成结构化字段，不进摘要。（第 12 篇第 2 问）
- **滑动窗口的本质缺陷是什么？** 硬截断。窗口一滑，最早那段整段消失，而那里往往是目标和约束。它省的是 token，丢的是前提。（第 12 篇第 3 问）
- **摘要之外还有哪些压缩思路？** 重要性过滤按价值筛而不按时间、结构化抽取换载体、证据裁剪只留命中段落、工具定义按需挂载。四种可以叠加，顺序是先无损后有损。（第 12 篇第 4 问，合并第 12、17、29 三篇）
- **上下文里哪些必须放，按什么顺序放？** 当前目标、硬约束、执行到哪一步、工具返回的事实，这四类必须放。顺序上把「现在要做什么」放最后，模型对末尾更敏感。（第 17 篇第 3 问）
- **网页里藏着「忽略之前的要求」，旧记忆和用户新话冲突，听谁的？** 外部内容一律当数据不当指令；冲突时以用户最新表述为准，旧记忆降级为参考。这两条写在装配逻辑里，不靠模型自觉。（第 17 篇第 4 问）
- **Context Engineering 和 Prompt Engineering 差在哪？** Prompt 工程管一句话怎么写，Context 工程管这一轮给模型看什么、什么顺序、占多少预算，是每一步都跑的装配流程。（第 17 篇小节设问）
- **还有空间，也该压缩吗？** 该。判断依据是剩余空间够不够撑完接下来几步，不是占满没有。下一步要读大日志、要生成长回答，就得提前压。（第 29 篇第 2、3 问）
- **压到多少合适？** 一次压到能撑过接下来若干轮。压到只剩 10% 余量，下一轮又触发，每轮付一次摘要成本。（第 29 篇第 4 问）

## 四、多 Agent

这一层是加分项，也是翻车高发区。答得好不好，看你有没有真的被协调问题折磨过。

### Q10 什么是 Multi-Agent？

多个各有角色和独立上下文的 Agent 协作完成一个任务，通过消息或共享状态交换中间结果。它解决的是单 Agent 的两个瓶颈：上下文装不下长流程的全部信息，一个模型什么都要会导致每件事都是泛才。

第三个收益常被忽略：隔离。一个子 Agent 跑偏，不会污染主控的上下文；它的探索过程可以整体丢弃，只交回结论。

代价同样实在：token 消耗成倍增加，协调本身要写代码，错误会沿交接链放大，调试时要在多个上下文之间来回切。

常见追问：

1. **什么任务值得上多 Agent？** 子任务之间边界清晰、可以并行、或者需要完全不同的工具集和上下文。
2. **多 Agent 一定比单 Agent 强吗？** 不。任务能用单 Agent 加几个好工具解决，就别拆。

### Q11 Single-Agent 和 Multi-Agent 的方案怎么选？

Single-Agent 就是一个循环加一套工具，实现简单、链路短、好测。它适合流程清晰、复杂度中等的任务，也是大多数线上系统的实际形态。

Multi-Agent 有两种拓扑。中心化是 Orchestrator-Worker：主控拆任务、派活、收结果，Worker 各自带独立上下文。去中心化是 Peer-to-Peer：Agent 之间直接 handoff，没有主控。

去中心化听起来更灵活，工程上很少用。没有全局视图，责任边界模糊，容易出现 A 把任务推给 B、B 又推回 A 的循环，出问题只能翻全量日志。

选型看四个量：任务能不能分解、上下文压力大不大、并行收益是否真实、团队能不能维护。四个里有两个不确定，就先用单 Agent。

常见追问：

1. **Worker 要不要共享上下文？** 不共享。只传任务描述、必要输入和验收标准，传全量历史等于没拆。
2. **主控会不会成为瓶颈？** 会。主控只做分派和汇总，不要自己下场干活，否则又退化成单 Agent。

### Q16 多 Agent 的协作与动态切换怎么设计？

协作靠两件事：消息和共享状态。消息用结构化信封，带 from、to、任务、产物引用、状态，不要传自然语言长文。共享状态是单一事实源，所有 Agent 读写同一份带版本号的任务状态，避免各自维护一份副本。

动态切换有两种做法。静态路由按规则或意图分类决定交给谁，稳定、可测；动态决策把候选 Agent 的能力描述给模型，让它选。我的做法是主流程静态，边缘情况动态，因为路由错了整条任务就废了。

Handoff 要带四样东西：任务目标、上下文切片（只给该 Agent 需要的）、验收标准、已完成和未完成的部分。少了验收标准，接手的 Agent 只能猜。

常见追问：

1. **怎么防止 Agent 之间踢皮球？** 记录交接次数和责任归属，同一任务交接超过 N 次就升级给主控或人。
2. **共享状态用锁还是版本号？** 优先版本号加乐观并发，锁只在热点资源上短租约使用。

### Q22 子 Agent 超时、失联、并发冲突怎么处理？

先把通信问题和一致性问题分开。心跳断了只说明协调器暂时看不到它，不代表它停止了。所以任务分配要带租约和递增的执行代次：子 Agent 定期续租，租约过期协调器才安排接管，旧执行者即使恢复也不能用过期代次提交结果。

接管不能从头重跑。要保存 checkpoint，记录已完成步骤、产物版本和已经产生的外部副作用。重试带稳定的任务 ID 和幂等键，遇到结果未知的写操作先查外部系统，再决定继续、补偿还是交给人。

多个 Agent 改同一个仓库时，按依赖和文件所有权先减少重叠，再让每个 Agent 在独立 worktree 或分支里干活。提交时校验基线版本，普通文件用乐观并发，热点文件用带租约的短锁。最后只有 Integrator 有权合入主分支，合完跑静态检查和测试。

{{< fig "diagrams/04-multiagent.svg" "左边是中心化拓扑：主控派活、Worker 各自在独立 worktree 干活、只有 Integrator 能合入。右边是租约接管的时间线：心跳一断不等于死亡，必须等租约过期，新执行者带新代次才能接管。" >}}

常见追问：

1. **租约时间设多长？** 短了误判频繁接管，长了故障恢复慢。按任务平均步长设，并允许续租时延长。
2. **两次 Agent 都写了同一个文件怎么办？** 后提交者校验基线失败，把冲突、最新基线、失败测试一起交回对应 Agent 修正，不要让人工去合。
### 跨题追问：多 Agent 的拆、接、收（本节 19 条）

- **单 Agent 的结构性上限到底是什么？** 上下文容量和专业深度。长流程的信息装不下，多领域都要精通就都平庸。这两条不是「容易出错」，是硬约束。（第 10 篇第 3、4 问）
- **「任务复杂」有没有可操作的判断标准？** 四个：能不能拆成独立子任务、上下文压力是否超预算、并行收益是否真实、团队能不能维护。四个里有两个不确定，就先单 Agent。（第 11 篇第 2 问）
- **盲目上 Multi-Agent 的代价是什么？** token 成倍、协调要写代码、错误沿交接链放大、调试要在多个上下文之间来回切。（第 11 篇第 3 问）
- **去中心化协作为什么工程上几乎没人用？** 没有全局视图、冲突没人裁决、责任边界模糊、失败难复现。灵活是演示里的优点，不是生产里的优点。（第 11 篇第 4 问）
- **消息传递和共享状态怎么选？** 依赖弱、要解耦，用消息；依赖强、要读最新值，用共享状态加版本号。混着用最容易出竞态。（第 16 篇第 2、3 问）
- **路由全交给 LLM 有什么问题？** 每次路由多一次调用，还会路由错，系统行为不可预测。主流做法是主流程静态路由，边缘情况才让模型选。（第 16 篇第 4 问）
- **Handoff 要带哪几样东西？** 任务目标、切片后的上下文、验收标准、已完成与未完成清单。少了验收标准，接手的 Agent 只能猜。（第 16 篇小节设问）
- **超时、失联、失败是一回事吗？** 不是。超时是没等到响应，失联是心跳断，失败是明确报错。混淆它们就会把「可能成功」当成「需要重试」。（第 22 篇小节设问）
- **为什么用租约而不是永久锁？** 永久锁在进程崩溃后要人工解锁；租约到期自动失效，接管不需要人。代价是要配代次，否则旧执行者恢复后会写入过期结果。（第 22 篇第 2、3 问）
- **两个实例一起写数据，怎么防？** 每次提交带代次号，接收方只认最新代次，旧代次的写入直接拒绝。（第 22 篇第 2 问）
- **大家改不同文件，也要串行吗？** 不用。按文件所有权分 worktree 并行，只有合入点串行。全部串行等于放弃 Multi-Agent 的意义。（第 22 篇第 3 问）
- **没有文本冲突，为什么程序还是坏了？** 逻辑冲突。一个 Agent 改接口签名，另一个按旧签名写调用方，Git 能合并，编译或运行会炸。所以要有一个跑完测试才合入的最终提交者。（第 22 篇第 4 问）
- **接管以后要从头重跑吗？** 不用，但要先核对。已完成的步骤、产物、未决的外部调用都要对一遍，再从 checkpoint 续。（第 22 篇小节设问）
- **子 Agent 要不要共享完整上下文？** 不共享。传任务描述、必要输入、验收标准。传全量历史等于没拆，还多一份副本身。（第 11、16 篇的隐含结论）
- **怎么防止 Agent 之间踢皮球？** 记录交接次数和责任归属，同一任务交接超过 N 次就升级给主控或人。（引申）
- **并行度开多大合适？** 由写冲突面和预算决定，不是越多越好。每个子 Agent 都是一份上下文成本，10 个并行常常比 3 个慢。（引申）
- **中心化编排会不会成为瓶颈？** 会。所以主控只做分派和汇总，不下场干活，也不做细粒度审阅。（引申）
- **多 Agent 的错误率为什么比单 Agent 高？** 每一步都有成功率，链路一长，乘积就掉下来。拆分的收益必须大于这个乘积损失。（引申）
- **怎么证明多 Agent 比单 Agent 好？** 同一批任务各跑一遍，比成功率、端到端时延、总 token。只在演示样例上比，等于没比。（引申）

## 五、执行、状态与可信完成

这一层的问题是「真的做了吗」。面试官问得很细，因为这里出的事故都赔钱。

### Q13 为什么有时候宁愿手搓 Agent，不用成熟框架？

框架上手快，但有三类实际痛点。抽象层太厚，出错时你不知道是模型、解析、还是工具执行的问题，只能一层层往下扒；版本升级有破坏性变更，线上稳定性捏在别人手里；通用设计和具体业务对不上，定制要绕开框架自己的抽象，比手写还费劲。

手搓拿到的是完全掌控：上下文怎么拼、循环怎么转、工具怎么执行、日志记什么，全是你自己的代码。可观测性好，性能优化也能直接做。

代价也要说清楚：工具协议、流式输出、重试、状态持久化这几块都要自己写，写不好比框架还脆。我的做法是核心循环手写，协议层用官方 SDK，边缘能力（比如某个向量库客户端）直接用库。

常见追问：

1. **怎么判断该手搓了？** 出现第二个框架绕不过去的业务限制时，或者线上故障定位超过半天还找不到是哪一层。
2. **手搓怎么避免重复造轮子？** 只写业务相关的循环和状态，模型调用、工具 schema、流式解析这些用官方 SDK。

### Q18 多轮状态怎么管理？怎么防跑偏、支持中断恢复？

先把信息分成四类，全部塞进 messages 一定乱：对话历史保原话，业务状态保存已确认的实体和约束，任务状态记目标、当前步骤、工具进度，长期记忆只存跨任务有用的偏好。

当前任务显式维护五个字段：`core_intent`、`current_subtask`、`pending_tools`、`completed_steps`、`context_snapshot`。每轮先判断用户这句话是补充、纠错、回答澄清，还是换了个任务，再更新状态。

防跑偏靠意图锚点。`core_intent` 是模型不能自己覆盖的字段，只有用户明确换题才新建任务或开新版本。执行层用状态机控制合法流转：`PLANNING → EXECUTING → WAITING_USER → CHECKING → DONE`，模型不能在状态不允许的时候直接宣布结束。

中断恢复靠三层标识：`session_id` 隔离会话，`task_id` 标识任务，checkpoint 保存关键步骤。恢复时加载最近一次已提交状态，核对未决的工具调用。所有写外部系统的动作带幂等键，不能简单从失败位置重跑，否则会重复付款、重复发消息。

常见追问：

1. **状态机还是自然语言历史说了算？** 状态机决定「现在能做什么」，历史保留「为什么这么做」，两者不能互相替代。
2. **checkpoint 存多密？** 每个有外部副作用的动作之前存一次，其余按步数间隔存。

### Q23 什么是「任务幻觉」？怎么避免没执行却声称完成？

任务幻觉是把计划、尝试，或者一段看起来成功的输出，当成真实完成，然后向用户声明「已经退款了」「已经改好了」。它和普通文本幻觉的区别在于后果：文本说错只是信息错，任务幻觉会让用户以为动作已经发生。

堵法有三层。第一层是状态机，`PLANNING → EXECUTING → EXECUTED → VERIFIED → DONE` 不能跳步，模型说完成只能把状态推进到 EXECUTED。第二层是证据链，VERIFIED 必须由确定性检查给出：数据库查到的状态、测试结果、文件内容。第三层是出口约束，最终回复只能基于已验证状态生成，没验证的部分明确写「待确认」。

超时是最危险的场景。动作可能已经执行了，直接重试会造成重复副作用。正确做法是带幂等键，然后查业务状态；查不清就返回「结果待确认」，不能包装成成功。

{{< fig "diagrams/05-statetrace.svg" "任务状态机的关键是被堵住的那条捷径：模型自称完成不能直接进 DONE，必须先有确定性证据把状态推到 VERIFIED。红叉那条边是任务幻觉最常见的发生位置。" >}}

常见追问：

1. **异步任务怎么验证？** 提交后状态是 PENDING，要轮询或等回调把状态推到 SUCCEEDED，中间不能当成完成。
2. **怎么评测这套机制真的有效？** 专门构造六类样本：没调工具、伪造成功返回、异步未完成、响应丢失、陈旧缓存、部分成功，统计错误完成声明率。

### Q24 Agent 连数据库怎么防越权、泄漏和查询幻觉？

Prompt 不是安全边界。用户身份和租户范围来自可信的登录态，由网关传给策略层，模型只负责表达「想查什么」，授权在模型之外逐次校验。

权限要一层层收。查询用独立的只读账号，只开放必要的库、表、视图和列，再用行级策略强制租户隔离。能封装成「查订单」「统计销售额」这类业务工具的，就不要暴露通用 SQL。

必须做 Text-to-SQL 时，校验要看语法树，不能只看字符串开头。解析后按语句类型、表、列、函数、查询规模做 allowlist，再走参数化查询、只读事务、超时和行数上限。

数据在进入模型之前就要变少。优先查脱敏视图和聚合结果，进出模型都做字段裁剪。库里的文本也是不可信数据，里面出现「忽略规则」只能当内容展示，不能改变工具权限。

查询安全不等于查询正确。还要校验字段是否存在、指标口径、租户过滤、时间范围、结果是否合理，并保存查询依据，否则模型会给出一个语法正确、口径全错的数字。

常见追问：

1. **为什么不用数据库账号做租户隔离就够了？** 账号粒度太粗，同一租户内的越权查不到。行级策略加应用层校验才够。
2. **写操作怎么办？** 走独立通道：先预览变更，再权限校验和人工审批，最后靠事务、幂等、影响行数限制和审计兜底。

### 跨题追问：执行、状态与可信完成（本节 17 条）

- **框架出 bug，stack trace 四五十层，怎么定位？** 先看最后一层自己的代码，再看第一层入口，中间基本是框架内部。还定不下来就关掉抽象，用最小复现脚本跑一遍。（第 13 篇第 2、3 问）
- **框架升级的 breaking change 和隐性开销怎么防？** 锁版本、升级前跑评测集、把框架调用收在一层薄封装里，换实现只改这一层。（第 13 篇第 4 问）
- **历史消息为什么不够用？** 目标是自然语言，步骤埋在对话里，模型每轮都要重新猜「做到哪了」。状态要显式化，不能靠模型从历史里考古。（第 18 篇第 2 问）
- **用户说「先暂停，改成订票」，算跑偏吗？** 不算。防跑偏防的是系统在用户没授权时悄悄改目标，不是禁止用户换任务。换任务建新版本，旧任务的上下文留着。（第 18 篇第 3 问）
- **消息其实发出去了只是响应丢了，恢复后会不会发两遍？** 会，如果没有幂等键。恢复时先按幂等键查业务状态，查到已发送就跳过，查不清就报「待确认」。（第 18 篇第 4 问）
- **文本幻觉、工具幻觉、任务幻觉怎么分？** 文本幻觉是内容错，工具幻觉是编出不存在的工具或参数，任务幻觉是把没发生的事说成发生了。只有第三种会让用户以为钱退了。（第 23 篇小节设问）
- **提示词拦不住假话，拿什么拦？** 状态机和证据链。模型只能把状态推到 EXECUTED，VERIFIED 由代码写，DONE 只能引用已验证字段。（第 23 篇第 2 问）
- **接口返回 200 就是成功吗？** 不是。200 常常只代表受理，异步任务还在跑。要看业务状态字段，或者等回调把状态推到终态。（第 23 篇第 3 问）
- **两个模型互相检查，会不会一起猜错？** 会。它们都只能看文本。能用程序验证的（订单状态、邮件投递、测试结果）就别让模型作证。（第 23 篇第 4 问）
- **SELECT 能有多危险？** 跨租户读、调危险函数、子查询碰不该碰的表、全表扫描拖垮库。只看开头几个字符等于没校验。（第 24 篇第 3 问）
- **为什么不让审核模型当数据库防火墙？** 它也会被注入、也会漏判，而且是概率的。权限、SQL 结构、敏感字段用确定性规则控，模型只负责表达意图。（第 24 篇第 4 问）
- **审计和测试要覆盖哪些攻击？** 至少四类：提示词注入（含库内文本）、跨租户查询、越权写、慢查询拖库。（第 24 篇小节设问）
- **超时后最危险的操作是什么？** 不加判断地重试。动作可能已经执行，重试就是重复副作用。正确做法是带幂等键查状态，查不清返回「待确认」。（第 23 篇小节设问）
- **执行成功以后为什么还要再验证一次？** 因为工具的成功和业务的结果不是一回事。写文件成功不代表内容对，接口 200 不代表状态变更。（第 23 篇小节设问）
- **恢复时最容易被忽略的一步是什么？** 核对未决调用。日志里可能有「已发起未返回」的工具调用，不知道结果的直接重跑会出事。（引申）
- **只读权限能降到多低？** 到表、列、行三级。绝大多数问数场景不需要任意 SQL，能封装成业务工具就别开放查询。（第 24 篇的结论）
- **状态机是不是太重了？** 五个状态不算重，真正重的是把状态写进数据库并让所有写入方遵守。只在一处写状态的「状态机」等于没有。（引申）

## 六、质量、性能与稳定性

这一层考的是「上线之后怎么办」。答案里没有数字，基本会被判定为没做过。

### Q15 反思机制是什么？为什么要用？怎么实现？

反思是让 Agent 在完成一步或整个任务后，按标准评估自己的输出，不达标就重试或改策略。用它的原因是第一次输出通常不是最好的，加一轮检查能明显提升质量，代价是至少多一次模型调用。

循环固定三步：生成、评估、改进。评估必须有明确标准，最好能外部验证：测试跑没跑过、schema 合不合规、引用能不能在原文里找到。没有标准的自评，多半是自我确认。

粒度分两种。步骤级每步检查，适合高风险操作；任务级只在交付前检查，成本低。多 Agent 互评比自评有效，因为评估者的上下文里没有生成时的自我辩解。

Reflexion 是把失败反思写进长期记忆，下次同类任务带上，这一步才让它从「一次检查」变成「持续变好」。

常见追问：

1. **什么时候不该反思？** 简单确定性任务、评估标准说不清、预算已经很紧的时候。
2. **反思几轮合适？** 一般一到两轮。第三轮的收益通常抵不过成本和延迟，还会开始改坏原来对的部分。

### Q19 怎么评估一个 Agent？评测集和指标怎么设计？

不能只看最终答案，要分四层，才能把问题定位到具体环节：工具层看该不该调、选得对不对、参数和返回处理对不对；轨迹层看每步决策是否合理，有没有漏步骤、重复调用、越权；端到端看任务是否完成、外部状态是否达到目标；线上看成功率、接管率、延迟、成本、安全事件。

评测集来自真实请求、历史 badcase、边界场景和对抗样本。每条样本不只存问题和参考答案，还要存目标状态、允许和禁止的动作、关键检查点、评分规则。有多条正确路径的任务，不要强行要求轨迹逐步一致。

评分优先用确定性手段：schema 校验、数据库状态、单元测试、权限规则。开放式质量再交人工和 LLM-as-Judge，裁判要用人工样本校准，防位置偏好和篇幅偏好。

指标要能当发布门禁：安全和关键业务约束设成硬门禁，其余按场景切片和基线比。上线后靠 Trace、用户反馈、业务结果发现 badcase，回流到离线集。

常见追问：

1. **LLM 当裁判可信吗？** 校准过才可信。同一批样本人工打一遍，看一致率，低于阈值就换评分规则。
2. **怎么防评测集被过拟合？** 留一份不参与调优的 holdout，改动前后都在上面跑。

### Q20 为什么会出现路径震荡、重复调用和死循环？怎么治理？

常见原因有四个：目标和停止条件写得模糊；工具失败只返回空结果，模型以为「再试一次就好」；任务状态没随执行更新，模型不知道已经做过；多 Agent 职责边界不清，交接成 A → B → A。

检测不能只看动作重复。动作重复只是预警，更可靠的信号是「状态长时间没有向完成标准推进」。实现上记录每步的 Agent、工具、规范化参数、结果摘要、执行前后状态，再结合动作指纹、输出相似度、状态变化量和调用图判断，同时给步数、时间、token、成本、交接次数设全局预算。

处置分情况：临时错误走有界重试加退避；参数或权限错误直接修正或问用户；判定无进展就禁用当前失败路径，换参数或工具，必要时从 checkpoint 重规划；预算耗尽或风险越界，停下来把已完成结果、卡点和可选方案交给人。

常见追问：

1. **重试几次合适？** 看错误类型。网络抖动两三次，业务错误一次都不该重试。
2. **为什么要禁用路径而不是直接重跑？** 同一个参数组合重跑大概率还是同一个结果，禁用它才能逼系统换策略。

### Q21 线上延迟升高，怎么用 Trace 定位？

先定义「慢」是什么。是 TTFT 变慢（用户多久看到第一个字），还是总时延变慢（任务从接收到完成）？两个的优化方向完全不同。然后按任务类型、模型版本、工具、租户、发布时间切分 P50、P95、P99，先判断是整体变慢还是少量长尾。

Trace 用同一个 trace id 串起网关、排队、上下文构建、检索、模型调用、工具调用、编排决策、最终生成。每个环节独立 span，记耗时、状态、重试次数、输入输出规模、token 数、错误类型，不记密码和完整提示词。

定位顺序是先指标后 Trace：用指标圈定异常范围，再抽慢请求和正常请求对比瀑布图，看关键路径。重点看排队时间、模型 TTFT 和生成速度、检索和工具的长尾、步数和重试次数是否膨胀、原本并行的步骤是不是被串行了。

优化对症下药：排队问题做容量和并发治理；模型问题从路由、上下文裁剪、输出长度、缓存入手；检索和工具做连接复用、缓存、批量；编排问题减少无效步骤和过度反思。改完用历史轨迹回放加灰度，比分位数，同时守住成功率和成本。

常见追问：

1. **P95 涨了但均值没变，说明什么？** 长尾问题，通常是某个工具、某个租户或某类任务，先切片再定位。
2. **为什么要看步数？** 步数膨胀会让延迟和成本一起涨，而且掩盖了真正的慢点。
### 跨题追问：质量、性能与稳定性（本节 21 条）

- **「再生成一次」和「反思后改进」差在哪？** 前者是随机重试，没有判断依据；后者必须先按标准评估再针对缺陷改。没有评估环节的反思，等于多花一次钱掷骰子。（第 15 篇第 2 问）
- **评估 prompt 最重要的设计是什么？** 给出可判定的标准，并要求证据。只说「看看有没有问题」，模型一定回「看起来不错」。（第 15 篇第 3 问）
- **为什么必须有 PASS 出口？** 没有「够好了就停」，模型会无限挑毛病，把原本对的部分改坏。（第 15 篇第 4 问）
- **步骤级和任务级反思怎么选？** 高风险操作走步骤级，每步都查；交付前检查走任务级，成本低。多数场景是任务级加关键步骤的定点检查。（第 15 篇小节设问）
- **多 Agent 互评为什么比自评准？** 评估者的上下文里没有生成时的自我辩解，立场更干净。代价是多一个 Agent 的调用。（第 15 篇小节设问）
- **回复「退款成功」但没调接口，能打高分吗？** 不能，这是任务幻觉，直接判零。答案完整性只占一小部分，外部状态是否改变才是主分。（第 19 篇第 2 问）
- **退款成功但绕过身份校验、还重复调了两次，综合分高能上线吗？** 不能。安全和资金约束是硬门禁，不是加分项，一票否决。（第 19 篇第 3 问）
- **评测题从哪来，多条正确路径怎么判？** 真实请求、历史 badcase、边界场景、对抗样本。多条路径只约束关键检查点，不要求轨迹逐步一致。（第 19 篇第 4 问）
- **最大步数为什么只能兜底？** 它只能防死循环，不能区分「该多步」和「在空转」。深度研究任务会被提前杀掉，而真空转的可能在步数内跑完。（第 20 篇第 2 问）
- **有限重试和空转怎么区分？** 看重试是否改变参数和证据。接口限流后原样重试是合理容错；每次只改一个搜索词却拿不到新证据，是在空转。（第 20 篇第 3 问）
- **发现无进展之后，四类处置怎么触发？** 临时错误有界重试，参数错误直接修正，无进展换路径或重规划，预算耗尽或越界交人。（第 20 篇第 4 问）
- **均值正常但用户抱怨慢，看什么？** 看 P95、P99 和 TTFT。少量请求慢几十秒，均值看不出来，用户感知到的正是长尾。（第 21 篇第 3 问）
- **并行 Span 的耗时能直接相加吗？** 不能。要看关键路径：串行依赖上的耗时才叠加，并行的取最长那条。（第 21 篇第 4 问）
- **先换模型还是先定位？** 先定位。可能是工具排队，换模型没用还可能掉效果。（第 21 篇第 2 问）
- **优化完怎么证明有效？** 同一批请求前后对比同一组指标（P50/P95/TTFT/成功率/token），不是看演示时快了几秒。（第 21 篇小节设问）
- **线上 badcase 怎么回流？** 按 Trace 抽样本，补齐真值后进回归集，进集之前先确认它能复现。（第 19 篇小节设问）
- **为什么指标要分场景切片？** 全局成功率会把「简单任务多」误读成「系统变好」。按任务类型、模型版本、租户切开看。（引申）
- **六类瓶颈分别怎么在 Trace 上看？** 排队看首 Span 延迟，模型看 TTFT 与生成速度，检索看召回条数与耗时，工具看调用时长与重试，编排看无效步数，异常看错误码分布。（第 21 篇小节设问）
- **怎么防评测集被过拟合？** 留 holdout、定期换题、把评测集的题从训练和调优流程里物理隔开。（引申）
- **延迟预算怎么分给各环节？** 先定端到端 SLO，再按关键路径分配：排队、模型、检索、工具各占多少，超了就报警而不是等用户投诉。（引申）
- **成功率涨了但成本翻倍，算改进吗？** 要一起看。常用的口径是「同等成功率下的单位成本」，或者「成本上限内的最高成功率」。（引申）

## 七、Harness、自进化与控制权

最后五道是「系统怎么运行」而不是「模型怎么思考」。这也是这两年面试分水岭最明显的一段。

### Q25 Agent Harness 是什么？

Harness 是模型之外的那层运行支撑，核心是一个循环：准备上下文、调用模型、接住工具请求、执行、把结果放回下一轮。模型只输出意图，读文件、跑命令、调接口这些动作要程序真的去做，结果要真的回填。

它至少管五件事：循环本身、每轮的上下文装配、工具执行（权限、超时、结果规范化）、任务状态持久化、结束判断。任务变长以后还要管预算和中断恢复。

和框架的关系要分清：框架是代码库，可能封装了 harness，也可能只提供工具封装。判断标准是它实际包含哪些能力，不是它的名字。

常见追问：

1. **有了 LangGraph 还需要 harness 吗？** 需要。图编排解决的是控制流怎么写，权限、幂等、完成验证还是要自己补。
2. **Harness 会不会限制模型能力？** 会，这是有意的。限制的是越权和无限循环，不是推理。

### Q26 怎么设计一个完整的 Harness？

按一次修 bug 的任务走一遍，要搭的部分就清楚了。

1. **执行循环**：准备输入、调模型、解析动作、执行、回填、判断是否继续。
2. **上下文装配**：每轮保留目标、约束、当前进度和相关材料，完整日志放外面按需读。
3. **工具执行器**：限定工作区和权限，限制耗时，把结果规范成成功、失败、未知三态。
4. **状态持久化**：记录做过的操作、产物、未解决的问题，中断后先核对实际文件和未决调用。
5. **完成条件与预算**：验收条件事先写好，比如测试通过、字段齐全；步数、时间、费用都要有上限。
6. **过程记录**：每轮的输入、工具结果、状态变化都落盘，出问题才能分清是模型、工具还是运行程序的锅。

最初这些模块放一个服务里就够，接口分清以后按需拆。

常见追问：

1. **完成判断交给模型还是代码？** 模型提建议，代码做判定。判定依据必须是可验证的外部状态。
2. **日志要记多细？** 记到能重放出同一轮决策。模型请求、工具参数与返回、状态差异，三样都要有。

### Q27 自进化的机制怎么实现？

先分清两件事：这次答对，和下次少犯错。前者靠推理，后者要靠一条独立于执行的改进流程。

回路分五步：收集执行记录、用户纠正、测试结果；归因到具体哪一步出了问题；提炼成带适用条件的经验；下次同类任务在决策之前把经验放进上下文；多条同类经验再升级成 prompt 或 skill 的变更。

关键在「带适用条件」。统计有效订单漏了状态条件，不能只记住「答案是 4」，要记住「这类指标先查业务定义，再按定义生成查询」。前者换个时间就错，后者能复用。

新经验和新流程要先用没参与优化的任务验证，同时回归原来的成功用例，确认能推广且没退化，再灰度启用，保留版本以便撤回。要改模型本身，才轮到用校验过的数据做训练。

常见追问：

1. **自进化和微调什么关系？** 微调是最后一档，前面四步都能在不改参数的情况下完成，而且能撤回。
2. **怎么证明它真的在变好？** 用新任务的平均通过率，不是重做那道已经修好的题。

### Q28 什么时候该请求人工确认？

判据分三层。第一层看是否在已授权范围内：目标清楚、参数明确、符合执行规则，就继续做，不要每调一个工具问一次。第二层看后果：对外发送、删除唯一数据、扩大权限、花钱，这类必须停下来讲清楚对象、内容和影响。第三层看歧义：关键对象指代不清、要求本身矛盾，先澄清再动手。

三类动作别混：澄清是缺事实，审批是有后果，接管是 Agent 做不了。混在一起会让确认变成噪音，用户开始无脑点同意。

确认要绑定具体任务和参数版本。方案没变，同一操作的批准可以沿用；恢复执行时重新核对权限。用户说「同意」不等于后端有权限，也不能证明一次超时的操作没发生。

减少重复确认靠保存委托范围：本次会话内、这类操作、这个额度以下，记下来，下次不再问。

常见追问：

1. **确认次数太多用户会烦吗？** 会，而且会训练出无脑同意。所以要按后果分级，低风险批量授权。
2. **人在休假怎么办？** 超时策略要提前定：挂起、降级到只读、还是走代理审批。

### Q30 相同输入为什么结果不同？

先确认「相同」是哪一层。是同一句用户问题，还是完整请求相同，还是连运行条件都相同？Agent 还会带系统指令、历史、记忆、工具定义和任务状态，这些一变，模型收到的请求就已经不同了。

即使请求完全一样，还有四个变化源：采样策略（temperature、top_p、seed）；模型版本和推理实现；工具观察（时间、库存、并发返回顺序）；调度（并发完成顺序、超时重试、共享状态竞争）。这些差异进了多步循环会被放大，第三步的一个分支不同，后面全不同。

排查要存全量现场：实际请求（含 system、历史、工具定义）、模型配置、每次工具的参数与返回、状态变化。对齐两次记录，先找最早出现分歧的位置，再分层回放：固定观察只回放模型，或固定模型只回放工具。

稳定性定义要分层。事实、计算结果、权限约束、写操作去重必须一致；路径和措辞可以不同。用逐字一致当标准，会把正常的合理差异也当成 bug。

常见追问：

1. **temperature 设 0 就完全确定了吗？** 不一定。浮点累加顺序、批处理、推理实现都会带来差异，只能降低不能保证。
2. **seed 能解决什么？** 能固定采样那条随机流，解决不了模型版本和工具观察的变化。

### 跨题追问：Harness、自进化与控制权（本节 21 条）

- **一次模型调用为什么不算任务执行？** 模型只输出意图，文件没变、命令没跑、消息没发。要有人接住意图、真的执行、把结果回填，这才叫执行。（第 25 篇小节设问）
- **谁执行工具，谁把结果交回去？** Harness 的工具执行器。权限、超时、结果规范化、错误分类都在这一层，模型拿到的是成功/失败/未知三态，不是原始报文。（第 25 篇第 2 问）
- **执行到一半断了，怎么继续？** 靠持久化的任务状态加 checkpoint。恢复时先核对实际文件和未决调用，不能从失败位置盲跑。（第 25 篇第 3 问）
- **框架提供的能力和任务实际怎么跑，差在哪？** 框架管控制流怎么写，Harness 管权限、进度、完成判断、中断恢复。前者是库，后者是运行支撑。（第 25 篇第 4 问）
- **测试日志把上下文塞满了怎么办？** 日志放外部存储，每轮只取相关片段和结论，完整日志留档用于回溯。（第 26 篇第 3 问）
- **服务重启后，进度还找得回来吗？** 能，前提是状态和产物都落了盘。找回来之后还要核对：文件是不是真的改了，未决的工具调用结果是什么。（第 26 篇第 3 问）
- **「准备修改」和「已经改好」怎么区分？** 前者是模型的表述，后者是文件系统的状态。用确定性检查判定，不看模型怎么说。（第 26 篇第 4 问）
- **存了错误的经验怎么办？** 经验带适用条件，先在小范围任务上验证再推广，错了能回滚，因为经验是版本化的一条记录。（第 27 篇第 2 问）
- **用户点赞能定位到该改哪一步吗？** 不能。点赞只说明结果讨喜，不说明哪一步对。要归因得看执行记录和用户纠正的内容。（第 27 篇第 3 问）
- **用户已经授权整理报告，为什么每读一个文件还要问？** 不该问。读取在已授权范围内，确认只应出现在有外部后果或关键歧义的地方。（第 28 篇第 2 问）
- **模型很确定，就代表用户授权了吗？** 不代表。确定性是模型的置信度，授权是用户的意图，两件事。收件人、金额、对象要单独核对。（第 28 篇第 3 问）
- **批准后方案改了，原批准还有效吗？** 无效。批准的是一组具体参数，参数变了要重新确认。（第 28 篇第 4 问）
- **批准人没有资源权限怎么办？** 审批不等于授权。执行前还要过一次权限校验，没权限就走代理审批或降级。（第 28 篇第 4 问）
- **澄清、审批、接管，三者差在哪？** 澄清补事实，审批看后果，接管是 Agent 做不了。混在一起会让确认变成噪音，用户开始无脑同意。（第 28 篇小节设问）
- **怎么减少重复确认？** 保存委托范围：本次会话内、这类操作、这个额度以下，记下来下次不再问。（第 28 篇小节设问）
- **只存用户问题，能复现当时的请求吗？** 不能。系统指令、历史、记忆、工具定义、任务状态都参与构造请求，少一样就不是同一个输入。（第 30 篇第 3 问）
- **要求「逐字一致」合理吗？** 不合理。事实、计算、约束、写操作去重要一致，措辞和路径可以不同。用逐字一致当标准，会把合理差异当 bug。（第 30 篇第 4 问）
- **Harness 怎么和框架配合？** 框架负责控制流的表达，Harness 负责运行约束。换框架不该影响权限、审计和恢复逻辑，这层要自己写。（第 25、26 篇的结论）
- **怎么给 Harness 做灰度？** 按任务类型或租户切流量，新版本先跑只读任务，比对新旧两版的完成率和事故率再放量。（引申）
- **「人在环」放在哪一步最划算？** 放在有外部后果的写操作之前，以及模型自称完成之后。这两处错了代价最大，其余地方加确认只是增加摩擦。（引申）
- **自进化最容易被忽略的风险是什么？** 把一次偶然成功总结成通用经验，然后推广到所有任务。经验必须带适用范围，否则越用越偏。（引申）

## 合并说明：同一件事的不同问法

原站 30 篇，每篇开头 4 轮面试官追问，正文里还有 171 个设问式小标题。逐条收进来接近 300 条，多数是同一件事换了个说法。合并规则有四条。

1. **同一个机制在不同层被问到，按「谁负责」归位。** 压缩这件事在记忆篇、上下文篇、阈值篇各问了一遍，答案的三个侧面（丢什么、怎么丢、什么时候丢）分开放在第三节，不重复。
2. **面试官的纠错陈述改写成问题。** 原文很多轮不是提问，是「不对，你只说了工具调用」。这类话还原成「加了插件就算 Agent 吗」，才能当条目用。
3. **设问小标题只在问的是独立机制时单独成条。** 「ToT 是什么」独立，「三者的演进关系」并入 ToT 与 GoT 两条。
4. **原文没问但顺着追问一定会到的，标「引申」。** 每节末尾两三条，答题时用得上，不标来源。

## 答题模板

30 道题背完，最后要落到一个可复用的结构上。面试官听的是判断力，不是知识点数量。

1. **一句话定义**，说清核心机制，不超过两句。
2. **一次数据流**，谁在什么时候做什么，能画出来最好。
3. **一个取舍**，为什么不用另一种方案，代价是什么。
4. **一个项目证据**，数字、报错、上线后的变化，有一个就够。

四个部分讲完通常两分钟。剩下的时间等追问，追问才是真正打分的部分。

常见翻车点，按被追问的概率排：

1. **只报名词不讲数据流。** 说「有规划模块、记忆模块、工具模块」，追问一句「它们怎么串起来」就断。
2. **把 Workflow 说成 Agent。** 判断标准只有一个：下一步谁决定。
3. **把 Prompt 当安全边界。** 权限、租户、写操作校验必须在模型之外。
4. **说「框架会处理」。** 框架处理了什么、没处理什么，答不出来就等于没做过。
