> 每个 bad case 的处理路径都差不多：翻日志、猜原因、改一段 prompt、上线、再观察一周。一个循环两周起步，改完还可能把别的场景弄坏——因为没人说得清这次变好到底是哪一处改动带来的。

做 Lovart 的这一年，Agent 能力是从零搭起来的。资产树、上下文、Skill 与工具、画布协同，一层层铺完之后，我发现真正难的不是让它跑通，而是让它稳定地变好。

后来我意识到，这不是流程问题，是结构问题。Agent 的效果不由模型单方面决定，它由上下文供给、资产召回、能力描述、编排策略共同决定。既然效果分散在这么多层，调优也应该分散在这些层上，而且得让机器自己跑这个循环。

下面这套结构，是我按这个思路设计的。前半段讲边界和分层，后半段是四个最难的步骤怎么真正落地：归因怎么判、候选怎么改、回放怎么算数、灰度怎么放。

## 一、先划三条线：什么能让它自己改

自我调优听起来很激进，落地时必须先划边界。我给自己定了三条：

**只改配置，不改代码。** 能自动改的是 prompt 片段、检索参数、Skill 描述、路由权重、超时与预算这类声明式配置。代码、计费规则、权限模型一律人审。

**不改权限边界。** 调优可以改「怎么找」，不能改「能看什么」。资产可见范围由权限树决定，Agent 自己动不了。

**每次只改一个面，并且可回滚。** 一个周期最多五个变更，每个变更带 diff 和预期指标。不满足这三条的改动不生效。

这三条看着保守，实际是把「可归因」和「可回滚」焊死在流程里。没有这两样，自动调优会迅速变成一个没人敢碰的黑盒。

把第一条落成一张表，就是可调面白名单。表外的东西，调优器看不见；它看不见，就不会去改。

| 层 | 可调参数 | 取值域 | 步长 | 谁批 |
| --- | --- | --- | --- | --- |
| L1 上下文 | 各段预算占比、压缩触发阈值、记忆召回条数 | 占比 5–40%，阈值 0.80–0.95 | 一档 | 自动 |
| L2 资产 | topK、相似度阈值、查询改写模板、重排权重 | topK 4–16，阈值 0.45–0.75 | 一档 | 自动 |
| L3 能力 | Skill 描述与触发词、工具超时、重试次数、降级开关 | 描述 ≤ 400 字，超时 ≤ 45s | 一句 | 自动（描述）/ 人审（超时） |
| L4 编排 | 步数上限、单任务 token 预算、模型档位 | 步数 ≤ 40，预算 ≤ 32k | 一档 | 半自动 |
| L5 评估 | rubric 版本、档位阈值 | 冻结，改动留痕 | 一版 | 人审 |
| L6 治理 | 灰度比例、回滚阈值 | 只升不降 | 一档 | 人审 |

白名单之外还有一条更细的约束：**一个变更单元 = 一个参数 × 一个方向 × 一个依据**。依据指的是这次改动对应的归因结论，比如「17 条失败 trace 里 12 条 recall@8 = 0」。没有依据的改动不进回放队列，因为没有预期的改动没法判它成没成。

我刻意不让调优器重写整段 prompt。重写看起来灵活，实际把三件事一次改了：约束加了、示例换了、语气变了；回放涨了 3 个点，你说不清是哪一句起的作用。片段级改动才能让 diff 和指标一一对应。这条不是洁癖，是归因能力的前提。

## 二、七层：把 Agent 拆成能观测的层

{{< fig "diagrams/01-architecture.svg" "两条回路。下面一条是每次请求的装配链路，上面一条是调优回流；回流只落在策略版本库，生效点是 Context 的预算与 Skill 的描述。" >}}

一次请求的装配链路是：用户画布操作 → Agent Loop → Context 组装（读 Memory 与资产树）→ Skill / MCP → LLM Gateway → 画布与产物；产物提交给 Review Agent 巡检，巡检结果进指标与归因。上方是调优回流：指标与归因 → 调优器与灰度 → 策略版本库，生效时改的是 Context 的预算与 Skill 的描述。

从下往上：

**L0 模型层**，LLM Gateway，只负责多模型路由。应用层不该自己维护模型清单。

**L1 上下文层**，Context 组装。System Prompt、对话历史、记忆、资产片段各占多少预算，在这里分配。

**L2 资产层**，租户资源树、血缘、权限树。检索和召回都落在这层。

**L3 能力层**，Skill 注册表与 MCP 网关。工具怎么注册、怎么鉴权、结果怎么回写。

**L4 编排层**，Agent Loop，负责规划、调用、观测、收敛，以及把产物写进画布。

**L5 评估层**，Review Agent 加指标聚合。它既是产物质量的裁判，也是调优闭环的信号源。

**L6 治理层**，策略版本、灰度、回滚、审计。

分层的意义不在画得好看，而在于每一层都能被单独观测和单独改动。调优只发生在 L1 到 L4 的参数上，L0 的模型清单和 L6 的发布规则由人维护。

每层要能被单独归因，得先产出结构化字段。这是七层里最容易被跳过的一步：

| 层 | 必须落的字段 | 用来回答什么问题 |
| --- | --- | --- |
| L0 | 模型名与版本、温度、输入输出 token | 这次波动是模型换了还是策略换了 |
| L1 | 装配后各段占比、压缩是否触发、记忆命中 id | 上下文是不是被挤掉了 |
| L2 | 召回列表（asset_id + 分数 + 名次）、过滤原因 | 该有的资产为什么没进来 |
| L3 | 激活的 Skill 与版本、每次工具调用的参数与结果摘要 | 该调的没调，还是调了没用 |
| L4 | 步数、收敛原因、画布 op 流 | 是策略提前收敛还是被截断 |
| L5 | Review 逐条结果、裁判分、rubric 版本 | 是产物差还是尺子偏 |
| L6 | policy_version、灰度桶、变更单号 | 这次差异归到哪一次发布 |

字段不是为了「以备不时之需」。每个字段都要能指向一次具体的判定，落不上的字段就别落，落多了没人看，还会拖慢写入。

## 三、七步闭环：一轮改动怎么走

{{< fig "diagrams/02-loop.svg" "七条泳道，一轮改动从 trace 到生效的全部消息。绿色是主路径请求，紫色是异步追踪，灰色是返回。" >}}

一轮改动的时序。线上运行只产信号，归因与候选生成在离线侧完成，灰度发布是唯一能改线上行为的环节，回滚是它的逆操作。

1. **采集。** 每次任务落一条 trace，包含用户输入、检索到的资产、激活的 Skill、工具调用与结果、产物、用户后续动作。这一步复用现有调用日志，加字段就行，一天的工作量。

2. **判分。** 自动分来自 Review Agent 的检查项加一个裁判模型，人工分来自抽样评审。只靠点赞会样本太少，只靠模型裁判会有偏，两个都要。

3. **归因。** 这是整套东西的核心。把失败分成六类：召回缺失、技能未激活、提示歧义、工具超时、模型能力不足、预算不足。分类错了，后面全是白干。

4. **生成候选。** 针对归因结果改配置。召回缺失就调 topK 或阈值，技能未激活就改 Skill 描述，提示歧义就改 prompt 片段。

5. **离线验证。** 用历史会话加一份 golden set 回放，核心指标不下降才允许进入下一步。回放只跑采样集，不然 token 成本会失控。

6. **灰度。** 5% 流量跑 24 小时，看指标和违规率。

7. **提升或回滚。** 全量生效或者一键回滚，写审计记录。

一轮下来，从信号到生效大约几天，比人肉的两周快一个数量级。更重要的是每步都留痕，出问题能定位到具体是哪一次变更。

七步里每一步都有它自己的失败方式，写清楚比写得全更重要：

| 步 | 输入 | 产出 | 谁做 | 这一步会怎么坏 |
| --- | --- | --- | --- | --- |
| 采集 | 线上请求 | trace 行 | 埋点 | 字段缺一半，后面全部降级为猜测 |
| 判分 | 产物 + trace | 通过 / 不通过 + 分项 | Review + 裁判 | 尺子偏，把好产物判成坏，调优器去修一个不存在的问题 |
| 归因 | 失败 trace 批次 | 类 + 置信度 + 证据指针 | 规则 + 人审 | 类分错，改错参数，指标不动 |
| 候选 | 类的统计 | 一个 diff | 动作卡 | 一次改三个参数，回放涨了也不知道谁的功劳 |
| 回放 | 候选 + 三个集 | 红黄绿 | 回放服务 | 变量没冻住，结论不可复现 |
| 灰度 | 通过的候选 | 分桶配置 + 观测 | 发布系统 | 分桶按请求不按租户，同一个团队看到两种行为 |
| 提升 | 灰度结论 | 版本 + 审计记录 | 人 + 系统 | 没写回滚点，下次出事只能全部停服 |

下面四节展开的是第 3 步到第 6 步。它们是这套系统的重活，也是「听起来都对、做起来全错」集中的地方。

## 四、采集与判分：先有能重放的样本

### 一条 trace 要能重放

判断 trace 合不合格只有一个标准：**任取一条失败任务，能不能凭记录把它重放出来**。能重放，归因才有证据；不能重放，归因就退化成「看日志猜」。

可重放需要三样东西：输入冻结、环境锚定、产物指纹。少一样，回放出来的就不是同一条任务。

| 组 | 字段 | 缺了会怎样 |
| --- | --- | --- |
| 输入 | task_id、租户、原始指令、画布快照 hash | 没快照 hash 就没法复现「当时画布上有什么」 |
| 上下文 | 装配后 system prompt hash、各段预算、召回列表（id + 分数 + 名次） | 归因缺失类问题全靠这段，缺了只能猜 |
| 能力 | 激活的 Skill 与版本、工具调用序列（参数 + 结果摘要 + 耗时） | 分不清是没调、调错、还是调了超时 |
| 产物 | 产物指纹、画布 op 流、导出规格 | 判分只能看最终图，看不出是哪一步写坏的 |
| 结果 | Review 逐条结果、裁判分、用户后续动作（重生成 / 撤销 / 编辑深度） | 一次通过率就没有真值，只能拿点赞凑 |
| 元数据 | policy_version、model_version、rubric_version、采样率 | 回放结论不可信：你都不知道在比哪两版 |

采样上不要追求全量。失败全采，成功按 10% 分层抽，长会话和长尾品类加权。一条 200 步的会话存下来是几十 KB，全量落盘的存储成本不高，真正的成本在后面：**每条 trace 都可能被拉去回放**，回放一次就是真金白银。采的时候就要想好这条以后会不会被回放。

### 判分分三层

判分器不是一件事，是三层不同可信度的东西叠起来。混在一起谈，就会出现「分数涨了但没人信」。

第一层是**硬门禁**，规则可判，布尔值：品牌色 ΔE2000 超 3、品牌字体被替换、文字溢出容器、元素越出安全区、命中禁用词、导出规格不符。这层不需要模型，错判率接近零，任何一条挂掉，这条任务就是失败，不进后面的讨论。

第二层是**软分**，裁判模型打 0–1：指令遵循度、构图与留白、层级是否清楚。这层必须和 `rubric_version` 一起冻结，换裁判模型等于换尺子，要重跑锚点集。

第三层是**人评**，每天抽 20 条，双人标注。它的作用不是替代自动分，是给自动分校准。

裁判要校准，看四个数：

- 双人标注一致性：50 条样本，Cohen's κ ≥ 0.6。低于这个数说明标准没写清，先改 rubric 再谈调优。
- 人机一致率：裁判与专家判定一致的比例 ≥ 85%。
- 重测差异：同一张图跑两次，分数差 ≤ 0.03。
- 锚点集：30 条固定样本，每季度复测一次，看整体分数有没有漂移。

还有两个必须防的偏差。一是长度偏好，裁判容易给信息更密、描述更长的产物高分；对策是 rubric 里把「简洁」写成显式检查项，而不是让它自然发生。二是位置偏好，同一批候选换个顺序分数会变；对策是候选顺序随机化，或者正向反向各跑一次取平均。

### 一次通过率要写死口径

北极星指标必须有一个不会随埋点版本变化的口径，否则每改一次埋点，历史曲线就断一次。我用的是三条同时满足：

1. 用户没有点重生成；
2. 没有大改（画布 op 的编辑量低于阈值，比如 30% 的图层被重新布局）；
3. 同一个任务 7 天内没有返工（用户没有回来重开同一份稿）。

三条都能从 trace 里算出来，且都不依赖用户主观打分。点赞率只作为辅助信号，不进北极星。原因很简单：愿意点赞的人是少数，且偏向满意的用户，样本偏差比噪声更麻烦。

## 五、归因：不是分类，是证伪

归因是整套系统里最容易被低估的一步。多数团队把它做成一个分类模型：输入 trace，输出六选一的标签。这么做在 demo 里能跑，在生产里会持续给出「看起来合理但改不动指标」的结论。

原因是分类和证伪要的东西不一样。分类只要一个标签，证伪要的是「这个判断被什么证据支持，又被什么反例排除」。

### 输出不是一个标签，是四个字段

每一条失败 trace，归因器要落四样东西：

| 字段 | 内容 | 用途 |
| --- | --- | --- |
| 类 | C1–C6 之一，或「未知」 | 决定去改哪个参数 |
| 置信度 | 0–1，按证据强度分档 | 低于 0.6 不进候选生成，进人审 |
| 证据指针 | trace 里的具体字段路径与值 | 人审时不用重看整条 trace |
| 反例检查 | 这次判定排除了哪一类，依据是什么 | 防止「哪个类顺手就归哪个类」 |

置信度按证据来源分三档，不要拍脑袋给小数：规则命中（0.9，比如 recall@8 = 0 且资产确实在库里）、需要重放确认（0.7）、需要换模型对比（0.5）。这样置信度才有可比性，也才能拿它做排序。

### 十个筐到六个类

我在评测那篇里把失败分成十个筐，每个筐对应一个 owner。到了调优侧，这十个筐必须收敛成六个类。原因很直接：**筐是为了找人，类是为了找旋钮**。一个筐如果落不到任何可调参数上，它就不该出现在调优器里，它应该走人审或者修代码。

| 评测侧的筐 | 调优侧的类 | 处理方式 |
| --- | --- | --- |
| 资产召回 | C1 召回缺失 | 调 topK、阈值、查询改写 |
| Skill 路由 | C2 技能未激活 | 改 Skill 描述与触发词 |
| 工具环境 | C3 工具超时 | 调超时、重试、降级开关 |
| 上下文预算、成本截断 | C4 预算不足 | 调预算档位与压缩阈值 |
| 意图理解 | C5 提示歧义 | 改 prompt 片段、补 few-shot |
| 生成能力 | C6 模型能力不足 | 调路由权重，升档模型 |
| 品牌约束、画布写入 | 非策略 | 修规则或修代码，不进调优器 |
| 评测本身 | 非策略 | 改尺子，先改 rubric 再谈 |

合并的原则是「同一个旋钮解决的两类问题，就是一类」。上下文预算和成本截断被我并成 C4，因为它们的对策都是调预算，分开只会让动作卡重复。反过来，技能未激活和工具超时不能合并，虽然它们都表现为「工具没跑起来」，但一个改描述、一个改超时，改错方向指标一点不动。

### 级联：从上往下问，命中即停

归因按一条固定的级联走，顺序不是按严重程度，是按**因果链的上游到下游**，同时兼顾查证成本从低到高。这样做的副作用是好的：先问便宜的问题，大部分 case 在前两闸就分完，只有少部分要花重放和换模型的成本。

{{< fig "diagrams/03-attribution.svg" "六道闸按因果链上游到下游排，一条失败 trace 从上往下过，命中即停。六闸全否进未知桶，不硬塞进最近的一类。" >}}

第一件事永远是把「不是策略问题」的 case 摘出去。硬约束回归（昨天还好今天崩了，且 diff 指向代码）走回滚加修代码；评测误判（人判好机判差）走改尺子。这两类如果混进调优器，会得到一个很荒谬的结果：为了修一个判错的分数去调 prompt。

摘干净之后，六道闸依次问：

| 闸 | 问题 | 可计算的判定信号 | 命中 → 类 |
| --- | --- | --- | --- |
| G1 | 资产在库里，召回却没带上？ | `recall@8 = 0` 且 `asset_id` 存在于租户资产树 | C1 召回缺失 |
| G2 | Skill 存在且可用，却没被激活？ | `skill_calls` 里没有该 Skill，且输入满足其 schema 必填项 | C2 技能未激活 |
| G3 | 工具失败、超时或降级？ | 工具 error_rate 突增，或 `latency > timeout`，或返回降级标记 | C3 工具超时 |
| G4 | 上下文或预算被截断？ | 上下文利用率 > 0.9，或触发过 compaction / 降级 / 强制收敛 | C4 预算不足 |
| G5 | 工具调用正确，但理解偏了？ | 调用参数与 Skill schema 一致，产物偏离指令；用户后续在原句上改措辞 | C5 提示歧义 |
| G6 | 换强模型、多跑 3 次仍不过？ | 升一档模型 3/3 失败，同输入可复现 | C6 模型能力不足 |

六道全否，进「未知」桶。这个桶必须有，而且要允许它长期存在。没有未知桶的归因器，最后一定会把 15% 的疑难 case 硬塞进最近的那一类，然后你就得到一堆改了没用的候选。

两个细节决定级联能不能用。

一是**同时命中怎么判**。G1 和 G3 可能同时为真：topK 没带上资产，同时工具还超时了。这时取更上游的类（G1），因为上游能解释下游的一部分表现，反过来不成立；但置信度取低一档，因为下游那部分失败被掩盖了。

二是**跳过的闸要记下来**。命中 G2 就停了，但 G3–G6 没检查过，这四条要写进「反例检查」字段。下次指标没动，第一个要问的就是「当时跳过的闸里有没有真的问题」。这是把近因偏差挡住的最笨也最有效的办法：出事的是最后一步，不代表原因在最后一步。

### 归因质量怎么度量

归因器自己也需要被评测，否则你不知道自己是在调 Agent 还是在调一个随机数生成器。

每周从当周失败里抽 100 条，两个人独立打类，然后看三个数：

- **一致率**：人机判定一致的比例 ≥ 80%。掉到这个数以下，说明规则跟不上线上分布了。
- **混淆矩阵**：只看对角线两侧的相邻类。实际经验里最容易混的是 C4 和 C6：预算不够导致模型看起来「能力不行」，因为上下文被截断后模型确实表现差。区分的办法是看有没有触发过压缩或降级，有就是 C4。
- **未知桶占比**：健康区间是 5%–15%。高于 15% 说明规则漏了场景，该补闸；低于 3% 说明有人在硬塞，该查复核是不是走过场。

发现规则失效要按周修，而不是按季度。线上任务分布变得比想象中快，一个新品类的上新就能让召回类的占比翻倍。

### 两个偏差

**近因偏差**：人看 trace 会盯着最后出错的那一步。级联按上游优先排序，就是为了在流程上抵消这个偏差，而不是靠人自觉。

**可调面偏差**：归因者会倾向于归到「有旋钮」的类，因为归到那里感觉能做事。C6 模型能力不足是最舒服的筐，一归进去就可以申请换模型。对策是让「未知」和「非策略」也必须是合法输出，并且在周会上专门看这两类，而不是只看六个类的分布。

## 六、调优：从归因到候选

归因给出「该改哪一层」，调优要回答「改成什么」。这一步我不建议让模型自由发挥，用动作卡更稳：每个类预先写好一张卡，卡上固定参数、步长、边界和预期副作用。

### 每类一张动作卡

| 类 | 参数 | 步长与方向 | 边界 | 预期副作用 |
| --- | --- | --- | --- | --- |
| C1 召回缺失 | topK、相似度阈值 | topK 8→12（对数档）；阈值 −0.07 | topK ≤ 16 | 噪声进上下文，P95 抬升 |
| C2 技能未激活 | Skill 描述、触发词 | 一次加一句触发描述 + 一句反例 | 描述 ≤ 400 字 | 误激活，工具滥用 |
| C3 工具超时 | 超时、重试次数、降级开关 | 20s→30s；重试 1→2 | 超时 ≤ 45s | 长尾拖慢整体 P95 |
| C4 预算不足 | 上下文预算、压缩阈值 | 24k→30k；0.85→0.92 | ≤ 32k | 单任务成本上浮 |
| C5 提示歧义 | prompt 片段 | 一次加一条约束或一个 few-shot | 片段 ≤ 3 条 | 挤压其他段预算 |
| C6 模型能力不足 | 路由权重 | 升一档，权重 +0.15 | 只升到下一档 | 成本上升最猛 |

「预期副作用」这一列不是装饰。它是灰度阶段护栏阈值的来源：C1 的改动一定会抬 P95，那灰度时 P95 的允许上浮就要按它来定，而不是所有改动共用一个 15%。

### 步长：用对数档，别做网格搜索

参数搜索最容易犯的错是开一个大网格让机器扫。设计 Agent 单次回放 ¥0.15–0.30，扫 20 个组合 × 200 条 × 3 trial，一轮就是小一万。更糟的是网格里的中间点大多没有业务含义，topK=11 和 topK=12 的差别在设计场景里基本是噪声。

用对数档：topK 取 4 / 8 / 12 / 16，阈值取 0.45 / 0.55 / 0.62 / 0.70，预算取 16k / 24k / 32k。每次只走一档，方向由归因的证据决定（recall@8 全空说明 8 不够，往上走一档）。这样一轮只需要三四个候选，且每个候选都能被解释。

一个变更单元只动一个参数。这条在压力下最容易被破坏：指标掉了，人会想「topK 和 prompt 一起改，效果肯定更好」。真这么做，回放涨了 3 个点，你没法判断是哪个起的作用，下次同类问题来了也没有可复用的结论。**归因能力的上限，取决于你允许多少个变量同时动。**

并发也不是完全不行，但要满足两个条件：变更落在不同的层，且不同层之间没有已知耦合。比如同时改 C2 的技能描述和 C6 的路由权重是可以的，因为一个影响「调不调」，一个影响「调了之后算得好不好」；同时改 C1 的 topK 和 C5 的 prompt 就不行，因为召回变了，模型看到的输入就变了，prompt 的效果无从比较。

### 候选从三个地方来

比例大致是 80 / 15 / 5，按这个顺序排优先级。

**规则生成（80%）**：动作卡加当前值，直接算出下一档。这类候选最无聊，也最可靠，因为每一步都能追溯到一条归因结论。

**历史检索（15%）**：找历史上相似的归因、相似的租户结构，看当时哪个改动有效。这需要把「变更 + 回放结果 + 灰度结果」存成一条可检索的记录，否则历史经验永远只存在于某个人脑子里。

**模型提议（5%）**：让模型读失败 trace 和当前 prompt，提出改法。这类候选必须人审后才能进回放。原因不是不信任模型，而是它的改动天然倾向于「写得更长更详细」，回放常常能涨，线上往往因为挤占预算、增加延迟而崩。让它提案有价值，让它直接上线是灾难。

### 候选的准入检查

进回放队列前过四道检查，全过才排队：

1. 有 diff，且 diff 可读（人能一眼看出改了什么）；
2. 有预期指标，且写明了预期方向与量级（「C1 类失败率下降 5pp」）；
3. 有回滚点（回滚到哪个 policy_version）；
4. 不引入新依赖（新工具、新模型、新数据源一律人审）。

## 七、离线验证：回放要能算数

回放的目的是在不影响用户的前提下，把明显会坏的候选挡掉。它的定位要摆正：**回放负责「不放宽」，不负责「证明变好」**。指望 200 条样本证明 +2pp 的提升，在统计上做不到；那件事交给灰度。

### 三个集，各有各的职责

| 集 | 怎么来 | 规模 | 职责 |
| --- | --- | --- | --- |
| 回归集 | 线上分层采样，固定快照 | 120 条 | 不许下降，降了就红灯 |
| 黄金集 | 设计师人工精标，覆盖六个模块 | 40 条 | 出报告，看整体水位 |
| 挑战集 | 新品类、新能力、竞品对比 | 30 条 | 只报告不阻断，每季度换 1/3 |

回归集和黄金集必须冻结输入。冻结的意思是连画布快照、资产版本一起冻，只换策略配置。有人图省事只冻文本指令，回放出来的是另一条任务，结论自然对不上。

挑战集不进阻断，是因为它代表还没做好的能力。用挑战集卡发布，结果就是永远发不出去。

### 冻结四个变量

回放要可复现，四个变量必须冻住，缺一个结论就不成立：

- **模型版本**。换模型等于换被试，不能和策略改动混在一轮里。
- **工具结果**。外部 API 会波动，回放时用录播的结果，否则你测到的是第三方服务的抖动。
- **随机种子与 trial 数**。同一个候选跑 3 次取通过率，不看单次最好成绩。
- **判分器版本**。rubric 和裁判模型都要带版本号，跟着结论一起存。

还有一条常被忽略的检查：**环境保真度**。同一批 100 条，离线跑一遍、线上影子跑一遍，结论一致率低于 90%，说明离线环境和线上不是一回事。这时候先修环境，不要修 Agent，否则你优化的是一台和线上不同的机器。

### 判定：总体非劣、分层不许塌、成本有上限

| 档 | 条件 | 动作 |
| --- | --- | --- |
| 红 | 回归集通过率低于基线 1pp；或任一硬门禁项失败数上升 | 打回，不进灰度 |
| 黄 | 黄金集掉 1–3pp；或某一难度层掉超 3pp；或成本上浮 10–20% | owner 签字才放行 |
| 绿 | 回归集非劣，分层无塌陷，成本上浮 ≤ 10% | 进灰度 |

分层这一条比总体更重要。总体通过率是加权平均，难任务占比低的时候，把简单任务做差、难任务做对，总体还能涨。所以每个候选都要按难度层和品类层各看一遍，只要有一层塌了 3pp 以上，就是黄灯，哪怕总体是涨的。

成本也别只当护栏。预算类改动（C4）天然会让成本上涨，如果回放阶段就把成本卡在 +10%，那这类改动永远过不去。做法是**按类的副作用预算分开算**：C4 允许 +20%，C1 允许 P95 +15% 但成本不变，C6 允许成本 +30% 但要证明通过率涨了 3pp 以上。这个预算就写在动作卡里。

### 成本

一轮回放的实际开销：120 条 × 3 trial × 4 个候选 × 0.25 元 ≈ 360 元，加上裁判模型的判分成本，一轮四五百块。一个周期五个候选，串行跑就是两千多。

压成本的办法不是砍 trial 数（砍了噪声就盖住信号），是**共享基线**：同一批回归集的基线结果算一次存下来，之后每个候选只跑自己那一份，对比时用缓存的基线。这样 4 个候选的边际成本是 4 份而不是 5 份，长期看能省掉三分之一。

## 八、灰度：把 1% 的错误关在 1% 里

回放只能证明「没明显变坏」，证明不了「线上真的更好」。灰度就是拿真实流量做最后一轮验证，同时把最坏情况的伤害限制在一个小比例里。

### 分桶按租户，不按请求

第一版我按 user_id 哈希分桶，很快出了问题：同一个设计团队里两个人协作同一份稿，一个在旧策略、一个在新策略，产出的画布行为不一致，客诉完全没法解释。

改成按 `tenant_id` 哈希取模，同一个租户全程落在同一个桶里。代价是有效样本变少（一个租户可能有很多任务，也可能只有一个），所以最小样本量要按任务数算，而不是按租户数算。

分桶还要排除几类租户：内部账号（会污染指标）、注册 7 天内的新租户（行为不代表稳态）、白名单大客户（出问题代价太高）、正在跑营销活动的租户（行为异常）。排除逻辑写在发布系统里，不写在业务代码里，否则每次调优都要发一次版。

### 阶梯与最小样本

比例不是时间驱动的，是样本驱动的。每级停了多久不重要，攒够样本才重要。

| 级 | 比例 | 最小任务数 | 最短停留 | 放行条件 |
| --- | --- | --- | --- | --- |
| 影子 | 0%（只比对不返回） | 200 | 1 天 | 成对胜负不劣于线上 |
| 1% | 1% 租户 | 300 | 24h | 三条护栏全绿 |
| 5% | 5% 租户 | 800 | 24h | 护栏全绿 + 序贯检验显著 |
| 20% | 20% 租户 | 2000 | 48h | 同上，且成本曲线平稳 |
| 50% | 50% 租户 | 3000 | 48h | 同上 |
| 全量 | 100% | — | 观察 7 天 | 无回滚，进版本库 |

影子这一级值得单独说。它把新策略挂在真实请求上跑一遍，但结果不给用户，只用来做新旧两版的成对比较。它的价值是把「明显算错」的候选挡在 1% 之前，成本是一份额外的推理费用，但比 1% 用户看到坏结果的代价低得多。

### 为什么用序贯检验，不用固定 p 值

灰度最容易犯的统计错误是：每天盯着 p 值，绿了就进下一级。这叫 peeking，反复检验会让假阳性率翻倍，你会放进一堆其实没用的改动。

用 always-valid 的序贯检验（mSPRT 这类），p 值在任何时点看都成立，可以随时停、随时判。工程上实现不复杂：每 2 小时算一次，`p* < 0.05` 且效应量 > 1pp 才放行。

放行条件里必须同时有「显著」和「有量级」。只看显著，样本一大，涨 0.2pp 也显著，但这种改动不值得冒风险；只看量级，样本不够时 3pp 的波动可能全是噪声。

### 三种动作，别混着用

| 动作 | 触发 | 做什么 | 恢复 |
| --- | --- | --- | --- |
| 冻结 | CUSUM 检测到指标漂移，连续 2 个窗口 | 停止推进，流量不降，继续观察 | 漂移消失则继续，否则回滚 |
| 回滚 | 护栏越界连续 2 个窗口；违规率 > 0.5%；成本 +15%；P95 +15% | 切回默认快照，1 分钟内生效 | 修完重新从影子开始 |
| kill | 人工判断（事故、舆情） | 60 秒内终止所有候选，全量回默认 | 事后归因 |

冻结和回滚的区别常被弄混。冻结是「不确定，先别动」，流量保持当前比例，你还有观察窗口；回滚是「确定坏了，撤」。把漂移直接做成回滚，会导致频繁抖动，每个小波动都把改动撤掉，最后什么都发不出去；把越界做成冻结，用户就在持续受损。

### 灰度期的纪律

灰度的价值一半在机制，一半在纪律。三条必须写进流程：

**灰度期冻结其他变更。** 包括 prompt 热修、超时调整、模型商发的新版本。模型商静默升级是最阴的一种：指标变了，你以为是自己的策略改动，实际上是上游换了模型。发布系统要能记录灰度窗口内的所有外部变更，包括你没主动做的。

**不许手动改桶。** 除了白名单排除，任何人不得把某个租户挪进或挪出新策略。一旦挪过，这次的指标就不可信了。

**事故时先回滚再归因。** 顺序反了，会在用户还在受损的时候讨论原因。

## 九、指标：一个北极星，三个护栏

北极星只有一个：**任务一次通过率**。用户不需要重生成、不需要大改就接受，算通过。

护栏有三个：P95 时延、单任务成本、Review 违规率。任何一项越过阈值，灰度自动回滚。

另外三个副指标决定改哪一层：召回命中率、Skill 激活率、工具成功率。它们不上报给业务，但归因时必须看。

指标要能用，得把口径、数据源、窗口、阈值一次写清：

| 指标 | 口径 | 数据源 | 窗口 | 阈值 |
| --- | --- | --- | --- | --- |
| 一次通过率 | 无重生成 + 编辑量低于阈值 + 7 天无返工 | trace 后续动作 | 7 天滚动 | 涨 1pp 才算有效 |
| P95 时延 | 端到端，含出图 | 网关埋点 | 24h | +15% 回滚 |
| 单任务成本 | token + 出图 + 工具调用 | 计费流水 | 24h | +15% 回滚 |
| Review 违规率 | 硬门禁失败数 / 总任务 | Review 结果 | 24h | > 0.5% 回滚 |
| 召回命中率 | 品牌资产进 top-8 的比例 | 召回日志 | 日 | < 60% 触发归因 |
| Skill 激活率 | 应调且调了的比例 | 调用序列 | 日 | 掉 5pp 触发归因 |
| 未知桶占比 | 归因未分类 / 总失败 | 归因记录 | 周 | > 15% 补规则 |

这里有个容易忽略的点：只看一次通过率，策略会学会回避难题。难题不接，通过率自然高。所以评测集要按难度分层，同时保留抽样人工评审。

难度分层的做法是把任务按「需要几步、几个工具、几次澄清」打成三档，分别看通过率。健康的形态是三档一起缓慢上升；如果只有简单档在涨，难档在跌，说明策略在往「少做事、少冒险」的方向漂，这是要拦的。

## 十、落地节奏

| 阶段 | 内容 | 工时 | 验收物 |
| --- | --- | --- | --- |
| P0 | trace 采集与回放基础设施 | 2 周 | schema v1，能重放 10 条历史 bad case |
| P1 | 评测集、判分与归因分类 | 3 周 | 100 条双标，κ ≥ 0.6，归因一致率 ≥ 80% |
| P2 | 单点调优：prompt 与 Skill 描述 | 3 周 | 5 个变更走完闭环，至少 1 个被回滚 |
| P3 | 策略调优：检索、路由、预算 | 4 周 | 参数改动可自动生成候选并回放 |
| P4 | 自动闭环与护栏 | 4 周 | 无人值守跑通一个完整周期 |

MVP 是 P0 到 P2，六到八周能跑通一条「发现问题、改配置、离线验证、灰度、生效」的链路。先跑通一条窄链路，比一次铺开五类调优更划算。

「至少 1 个被回滚」也是验收标准，不是开玩笑。一个周期五个变更全部成功，通常不是系统好，是门槛太低或者回放集太软。

第一周只该做两件事：定 trace schema，定一次通过率的口径。这两件不定死，后面的判分、归因、回放全部要返工，而返工的成本是把历史数据重新采一遍。

## 十一、六个坑

**奖励作弊。** 指标一旦固定，策略就会绕着它走。对策是难度分层加人工抽样，别让单一数字成为唯一真相。

**过拟合线上分布。** 线上流量偏某几类设计任务，回放集如果只来自线上，调出来的策略在长尾上会更差。golden set 要定期补新场景。

**变更叠加。** 一周改五个地方，下周指标变了谁也说不清是哪一处。所以有每周期变更数上限，这不是保守，是保留归因能力。

**回放成本。** 全量回放很贵。采样集加分层抽样，能把成本压到可接受范围。

**归因漂移。** 新模型、新工具上线后，老的判定规则会失效，而失效是静默的：归因器还在输出类，只是类错了。对策是每周那 100 条复核，一致率掉 5pp 就重写规则。这条比想象中重要，因为它的症状是「指标改了不动」，很容易被误诊成参数没调对。

**灰度期的隐形变更。** 运维调了超时、模型商发了静默升级、上游改了默认参数，这些都不在你的发布记录里，但都会改指标。对策是把灰度窗口内所有外部变更也记进变更日志，对不上账的时候先查这一栏。

## 十二、写在最后

这套结构解决的问题不是「让 Agent 更聪明」，而是「让 Agent 的变好过程可观测、可解释、可回滚」。

模型会一直换，能力会一直加，但只要分层、信号、闸门这三件事在，每次改动就都还在掌控之内。

如果想看这套结构里「判分」那一环怎么搭，可以接着看[设计 Agent 的评测系统](/posts/design-agent-eval-system.html)；那篇讲的是尺子，这篇讲的是用尺子的人。

还有一篇是给它挑毛病的：[自调优不是 RSI](/posts/self-tuning-to-rsi.html)——按 RSI 的判据量一遍，这套闭环只覆盖了回路的三段，闭合点在同族模型上，动作空间由白名单给定。那篇把差距拆成四个缺口，并给出了从参数级弱闭环往外走的四级路线。
