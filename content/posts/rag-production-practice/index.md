检索 p99（改写 + 双路召回 + 融合）控制在 120 ms，两路各取 50 条候选，融合后取 30 条精排，最终给 LLM 6 条带引用的证据。这是本文的默认工作点；规模变了，四个数字要重算，但结构不变。

BM25 和向量索引不是二选一。线上同时跑两路：倒排负责字面命中，ANN 负责语义近邻，融合用排名而不是分数，精排放在融合之后。这套组合能同时接住「ERR_CONN_RESET 怎么解决」和「为什么连接总是被重置」两种问法。

读者已经能用向量库跑通 demo，现在要回答上线后的四个问题：怎么切块、两路怎么融合、超时怎么降级、怎么证明改动有效。文中的容量数字按 1000 万 chunk、20 QPS 估算，换规模按公式重算。

不在本文范围：embedding 模型怎么训练、prompt 怎么写、LLM 怎么选。检索层的原理（BGE、IVF、PQ、HNSW）在[上一篇](/posts/bge-ann-vector-retrieval.html)里拆过，这里只讲怎么把它们装成一条能运维的链路。

## 一、先把目标定成四个数

上线前把四个数写进设计文档，后面每个选择都用它们换。没有这四个数，「要不要加一路召回」会变成口味之争。

| 指标 | 默认目标 | 为什么是它 |
| --- | --- | --- |
| 检索 p99（改写 + 双路召回 + 融合） | ≤ 120 ms | 用户能感知的等待从 LLM 首 token 开始，检索必须在 120 ms 内交棒 |
| 精排 p99（30 条候选） | ≤ 80 ms | 精排是线性成本，30 条是质量和延迟的平衡点 |
| recall@50 | ≥ 0.90 | 候选集上限决定答案上限；低于 0.9 时后面的精排和 LLM 都在补救 |
| 索引新鲜度 | ≤ 5 min | 从源文档更新到可检索；用增量水位 + 5 分钟批量实现 |

四个数里没有「整条链路」：检索（改写 + 双路 + 融合）120 ms、精排 80 ms、组装 20 ms，合计 220 ms，预算封顶 300 ms。

四个数互相拉扯：召回从 50 加到 200，recall 涨两三个点，召回延迟涨 40 ms，融合要处理的列表长四倍（精排窗口仍是 30，成本不变）。先定 p99 和 recall@50，另外两个跟着算。

指标要分层测。检索层测 recall@k 和 nDCG@k，生成层测答案正确率和引用准确率；混在一起测，出了问题不知道换哪一层。

## 二、总体架构：离线、在线、旁路

{{< fig "diagrams/01-architecture.svg" "RAG 的三条链路：离线只写索引，在线只读索引，旁路采集日志与评估；三者共享同一层索引、元数据和权限。" >}}

三条链路共享一层索引，边界只有一条：离线只写，在线只读。在线服务不允许在请求路径上建索引、改索引、等索引，这些操作全部放进离线任务，用别名切换让线上感知。

在线链路从左到右：网关做鉴权和租户解析，缓存挡掉重复查询，改写只做轻量归一化，然后并行发两路召回，融合、去重、精排、组装上下文，最后交给 LLM 流式输出。

离线链路只做一件事：把文档变成带元数据的 chunk，同时写进倒排和向量两套索引。切块、向量化、批量写入都在这里，失败重试和死信也在这里。

旁路链路不在请求路径上：采样日志、记录每阶段耗时和候选、跑离线评估、挖 badcase。它决定下一版怎么调，但不影响这一版的延迟。

| 组件 | 故障表现 | 兜底 |
| --- | --- | --- |
| 网关 | 全站 5xx | 多副本 + 限流，租户级隔离 |
| 倒排索引（ES） | 只剩语义召回，精确串变差 | 降级为单路 ANN，标记 `degraded=true` |
| 向量索引 | 只剩字面召回，改述问法变差 | 降级为单路 BM25，同样标 `degraded=true` |
| 精排服务 | 排序退化，延迟升高 | 用融合分数直接排序 |
| LLM | 无输出 | 返回检索结果和引用，提示稍后重试 |

## 三、离线摄入：文档怎么变成双索引

离线链路的所有幂等、重试、回滚都围绕一个键设计：`chunk_id = doc_id:version:seq`。同一个键重复写入结果一致，换版本就是新键。

{{< fig "diagrams/02-ingestion.svg" "离线摄入：源文档经解析、切块、富化、向量化后双写 BM25 与 ANN 索引，别名切换完成发布，失败进死信重放。" >}}

### 3.1 解析与切块

1. **先统一成纯文本，再谈切块。** PDF 走版面解析（标题、段落、表格分开），Word 读样式，HTML 去导航和页脚。扫描件先 OCR，OCR 置信度低于 0.8 的页标记 `needs_review`，人工复核前不进索引；把错字页放进检索，比暂时搜不到更糟。
2. **按语义边界切 350–450 字，重叠 10%–15%。** 按标题层级和段落切，不要按固定字符数硬切；硬切会把一个条件句拆到两个块里，两半都答不了。重叠只给跨段落的句子，不给整段复制。
3. **保留父子关系。** 子块用于检索（短、指向明确），父块用于送模型（上下文完整）。命中子块后按 `parent_id` 取父块，再截断到 token 预算。
4. **元数据跟着块走。** `tenant_id`、`acl`、`doc_type`、`source_url`、`section_path`、`updated_at`、`lang`，一个都不能少。过滤和权限全靠它们，后补等于重建索引。
5. **表格单独处理。** 表格转成「表头 + 行」的文本块，每行带表名和列名；整张表塞进一个块会让检索命中率变差。

### 3.2 向量化与双写

1. **同一批 chunk 写两套索引。** 倒排存 `chunk_id + text + 元数据`，向量库存 `chunk_id + embedding + 元数据`；两边用同一个主键，融合和去重才有依据。
2. **embedding 先归一化，再记录模型版本。** 归一化后内积等于余弦，索引 metric 用 IP 或 cosine 都行，但必须和训练时一致；`model_version` 写进索引元数据，换模型时能按版本回滚。
3. **批量 256–512 条，失败重试 3 次后进死信。** 单条失败不阻塞整批；死信队列按 `doc_id` 重放，重放前先查 `content_hash`，避免把旧版本写回去。
4. **写入用 upsert，不要先删后插。** 先删后插会有一段窗口查不到这篇文档；upsert 按 `chunk_id` 覆盖，旧 chunk 在版本切换后统一清理。
5. **删除写墓碑，不物理删。** 删除标记进元数据，检索时过滤；物理清理放在低峰期的 compaction，避免删一个 hub 把图走断。

### 3.3 发布、增量与回滚

1. **新索引先建后切。** 新版本写到 `chunks_v2`，构建完成后从 7.1 的标注集里分层抽 100 条 query，对比新旧 recall@50；绝对差在 1 个点内才切别名。
2. **别名切换是唯一允许线上感知的变更。** 读别名 `chunks_current`，切换是原子操作；切换后旧索引保留 24 小时，回滚就是切回去。
3. **增量按水位推进。** 用 `updated_at` 水位拉变更，5 分钟一批；删除事件单独走一条流，不能只靠水位（删除不会更新 `updated_at`）。
4. **重建要能重放。** 每个 chunk 的 `content_hash`、`model_version`、`parser_version` 都落库，重建时按版本重放，不依赖源系统还能不能访问。

## 四、混合召回：ANN 与倒排怎么结合

**会，而且倒排和 ANN 在线上是并用的。** 生产里同时用三种结合方式，各管一件事：并行两路做召回，倒排做过滤，精确串走 must。

三种方式分开看，混在一起谈会得出「BM25 和向量哪个更好」这种没有答案的问题。

### 4.1 并行双路，用排名融合

{{< fig "diagrams/03-hybrid-recall.svg" "混合召回：BM25 与 ANN 各出 50 条，RRF 按排名融合并去重，取 30 条精排，最后 6 条进上下文。" >}}

1. **两路并行发出，各自取 50 条。** 倒排查 BM25 top-50，向量库查 ANN top-50；两路共享同一份过滤条件，超时各自独立。
2. **用 RRF（Reciprocal Rank Fusion）融合，不要直接加分数。** BM25 分数是无界的，余弦相似度在 `[-1, 1]`，加权求和前必须归一化，而归一化参数每个领域都不一样。RRF 只看排名：

```text
score(d) = Σ_{r ∈ 两路排名} 1 / (k + rank_r(d))，k 常取 60
```

3. **求和前按 `chunk_id` 去重。** 同一块被两路同时召回很常见；同一 `chunk_id` 只保留名次更高的那一路的 `1/(k+rank)`，否则重复块会把自己的分数抬两倍。去重也必须在精排之前，否则 30 个精排名额会被重复块占掉。
4. **保留两路的原始名次。** 日志里记 `bm25_rank`、`ann_rank`、`rrf_score`，调权重和查 badcase 都靠它；只存最终分数，出了问题无法归因。

RRF 的缺点是丢掉分数幅度：两路都排第 3 的块，和一路第 1、一路第 5 的块，得分接近。领域内差距大时，可以用加权 RRF：系数乘在 `1/(k+rank)` 上，两路系数不必归一，整体尺度不影响排序；系数要用标注集调，不要拍脑袋。

### 4.2 倒排做过滤，不做补丁

1. **过滤条件下推到两路。** 租户、权限、文档类型、时间范围，必须在召回时生效；先召回再过滤，等于用 `k` 去赌命中率。
2. **权限过滤放在检索层，不放在应用层。** 应用层过滤会把无权文档带进候选，既浪费精排预算，也可能泄漏到日志。
3. **低命中率时改走 pre-filter。** 命中率 = 满足过滤条件的条数 / 索引总条数；低于 10% 时，先把这个子集捞出来再做 ANN，不要硬调大 `k`，`k/hit_rate` 会迅速把候选集撑爆。子集小于 5 万条直接精确扫，大于 5 万条再走 ANN。

### 4.3 精确串走 must，别指望向量

1. **先识别精确串。** 型号、错误码、订单号、引号里的短语，用正则或词典识别；命中后把倒排条件从 `should` 提升为 `must`。
2. **向量路继续跑，但只做补充。** 精确串命中的文档排前面，语义近邻排后面；两者都进融合，但 `must` 的结果单独加一路高权重。
3. **纯向量检索接不住这类 query。** embedding 会把 `ERR_CONN_RESET` 和「连接被重置」压到很近，但版本号 `v2.3.1` 和 `v2.3.2` 在向量空间几乎重合；这类差异只能靠字面匹配。

路由规则要可观测：命中精确串的 query 占比、这类 query 的点击率和无结果率，单独看一组指标。

### 4.4 为什么精排放在融合之后

1. **精排需要一份候选列表。** 分两路各排一次，成本按候选路数翻倍（100 条对 30 条，约 3 倍），而且两路分数不能直接比较，最后还是要融合。
2. **融合是排名操作，成本接近零。** 50 + 50 条做 RRF 是微秒级；把它放在精排前，可以用便宜的操作先把候选压到 30 条。
3. **精排窗口决定质量上限。** 只精排 10 条时，融合阶段漏掉的相关块没有机会回来；30 条是常见的平衡点，延迟敏感的场景可以降到 20。

### 4.5 候选预算与配置

| 阶段 | 数量 | 单次成本（估算） |
| --- | --- | --- |
| 每路召回 | 50 | 8–20 ms |
| RRF 融合 + 去重 | 50–100 | < 2 ms |
| 精排 | 30 | 40–80 ms |
| 进入上下文 | 6 | — |

两路各 50，去重后落在 50–100，取决于重复率。Elasticsearch 8.14 之后可以直接在一条查询里做 RRF：

```json
POST /chunks/_search
{
  "retriever": {
    "rrf": {
      "retrievers": [
        { "standard": { "query": { "match": { "text": "退款流程" } } } },
        { "knn": { "field": "embedding", "query_vector": [0.01, 0.02], "k": 50, "num_candidates": 200 } }
      ],
      "rank_constant": 60,
      "rank_window_size": 50
    }
  },
  "size": 50
}
```

示例里的 `[0.01, 0.02]` 是占位，真实是 1024 维；两段 JSON 都省略了 filter，线上必须带 `tenant_id` 和 ACL 条件。

Qdrant 用 `prefetch` 分别查 dense 和 sparse，再在服务端融合：

```json
{
  "prefetch": [
    { "query": { "indices": [12, 34], "values": [0.7, 0.3] }, "using": "sparse", "limit": 50 },
    { "query": [0.01, 0.02], "using": "dense", "limit": 50 }
  ],
  "query": { "fusion": "rrf" },
  "limit": 50
}
```

Postgres 用两条 CTE 各取 50 条（`tsv` 是全文索引列，`ts_rank_cd` 是按覆盖密度算的排名），再按 RRF 聚合：

```sql
WITH bm25 AS (
  SELECT id, row_number() OVER (ORDER BY ts_rank_cd(tsv, plainto_tsquery('退款')) DESC) AS r
  FROM chunks
  WHERE tsv @@ plainto_tsquery('退款') AND tenant_id = :tenant
  LIMIT 50
), ann AS (
  SELECT id, row_number() OVER (ORDER BY embedding <=> :q) AS r
  FROM chunks
  WHERE tenant_id = :tenant
  ORDER BY embedding <=> :q
  LIMIT 50
)
SELECT id, SUM(1.0 / (60 + r)) AS score
FROM (SELECT * FROM bm25 UNION ALL SELECT * FROM ann) u
GROUP BY id
ORDER BY score DESC
LIMIT 50;
```

三个示例都只取到融合层（50 条），精排服务再从中取 30 条。实现的选择只看现有基础设施：已经有 ES 就用 ES，已经有向量库就用它的融合接口，只有 Postgres 就用 SQL。融合逻辑一致，换存储不影响上层。

## 五、在线查询：一次请求的时序与降级

{{< fig "diagrams/04-online-sequence.svg" "一次查询的时序：缓存、改写、并行召回、融合、精排、组装、生成；每个阶段独立超时，任一段失败都有降级路径。" >}}

整条检索链的预算是 300 ms：改写 20 ms、双路召回各 90 ms、融合 5 ms、精排 80 ms、组装 20 ms，合计 215 ms，余下 85 ms 留给抖动。超时按阶段切分，不按整条链路切；任何一段超时只降级这一段，不重试整条链路。

### 5.1 八个阶段

1. **网关：鉴权、租户、限流。** 解析 `tenant_id` 和 ACL，写进上下文；限流按租户做，避免一个大客户打满全站。
2. **缓存：先查再算。** key 用 `hash(normalized_query + filters + model_version + index_alias)`，命中直接返回检索结果，不回源。
3. **改写：只做轻量归一化。** 全半角、大小写、缩写扩展（`k8s` → `kubernetes`）、指代消解取上一轮 query，会话状态按 `session_id` 存 Redis，TTL 30 分钟，和检索缓存分开。HyDE 那类「先让 LLM 写一段再检索」的方案会多一次生成，延迟 +300 ms 起，直接吃掉检索预算，只在离线评估证明有收益、且能接受 P95 变差时开。
4. **并行召回：两路同时发。** 倒排和向量库各自 90 ms 超时，互不等待；任何一路先返回就先占位，另一路超时后直接用已到的结果。
5. **融合：RRF + 去重。** 纯内存操作，2 ms 内完成；同时记下两路名次，供日志和归因。
6. **精排：30 条。** 80 ms 超时，按 query 批量打分；超时就用 RRF 顺序，不阻塞。
7. **组装：父块、去重、配额、引用。** 按 `parent_id` 取父块，按 token 预算截断，给每块分配引用编号。
8. **生成：流式输出。** 首 token 目标 800 ms 内；流式过程中把引用标记透传给前端。

### 5.2 超时与降级

| 故障 | 行为 | 用户感知 |
| --- | --- | --- |
| 单路召回超时 | 用另一路结果继续，标记 `degraded=true` | 结果略差，不报错 |
| 两路都超时 | 返回第 2 步的检索缓存（已过期也返回，标 `stale=true`）；无缓存则返回「暂时无法检索」+ 兜底话术 | 明确失败，不编答案 |
| 精排超时或 5xx | 用融合分数排序，熔断 30 秒 | 排序略差 |
| 组装超 token 预算 | 从低分块开始截断，至少保留 3 块 | 可能少一条证据 |
| LLM 超时 | 已生成部分照常返回，附引用 | 回答不完整 |

降级要可观测：`degraded` 比例、各阶段超时率、空结果率，三个指标一起看。只看成功率会漏掉「降级后仍然返回 200」的情况。

### 5.3 缓存

1. **缓存检索结果，不缓存最终答案。** 答案依赖模型版本和 prompt，缓存答案会让同一问题在模型升级后返回旧答案；检索结果只依赖索引和 query，安全得多。
2. **key 必须含过滤条件。** 同一句话在不同租户下结果不同，`tenant_id`、`acl`、`filters` 都要进 key；漏一个就是越权。
3. **TTL 5–10 分钟。** 文档更新后按 `doc_id` 精确失效很难（一个 doc 对应多个 chunk），短 TTL 更实际。
4. **语义缓存只在低风险场景用。** 「相似问法命中同一缓存」在客服场景可能把两个不同订单的问题混在一起；要用就把订单号、用户 ID 加进 key。

## 六、精排与上下文组装

### 6.1 精排输入

1. **query 用归一化后的原文，不要用改写后的长句。** reranker 训练时见的是用户问法，塞进去一段扩写会分布漂移。
2. **passage 用子块，不拼父块。** 子块 350–450 字（中文约 350–450 token），截断到 512 token 不会伤到正文；拼父块会让关键句被淹没，也让延迟翻倍。
3. **逐条打分，不做列表级模型。** 30 条独立打分可以批量并行，列表级模型（listwise）要一次进 30 条，显存和延迟都不可控。
4. **设一个分数下限。** 精排分数低于阈值的块直接丢弃，宁少勿滥；阈值用标注集定，不要用默认 0.5。

### 6.2 去重、多样性与配额

1. **同一文档最多 2 块。** 一个文档的相邻块内容高度重叠，占满上下文只会挤掉其他来源。
2. **按 section 去重。** 同一小节被切成多块时，只保留分数最高的一块，其余在组装阶段丢弃。
3. **MMR 控制多样性。** `λ=0.7` 时在相关性和差异之间偏向相关性；只在「对比类」问题里调低 λ，让不同来源都能进来。
4. **来源配额。** 单一来源最多 3 块，避免一个站点霸屏。

### 6.3 上下文组装

1. **token 预算 2–3k，按 6 块分配。** 每块 250–400 token，6 块 1.5–2.4k，留 20% 余量给引用和系统提示。
2. **最强证据放首尾。** 模型对上下文中间内容的利用率最低；把分数最高的块放开头，第二高的放结尾。
3. **每块带引用编号和来源。** 组装阶段按顺序生成 `[1]`…`[6]`，来源 URL 写全；前端只渲染白名单里的编号，模型编造的编号直接隐藏。
4. **冲突不合并。** 两个来源给出不同数字时，两块都保留并标注来源，让模型说明冲突；合并成一个「平均答案」是错的。

## 七、评估与灰度：怎么证明变好了

{{< fig "diagrams/05-eval-loop.svg" "评估回路：标注集驱动离线评测，shadow 与 canary 验证线上指标，badcase 回流再更新标注集。" >}}

### 7.1 标注集

1. **300 条 query 起步，按意图分桶。** 事实查询、流程步骤、对比、精确串各 50–80 条；只测单一路径会漏掉另一类 query 的退化。
2. **从线上日志采样，不要自己编。** 编出来的 query 分布偏整齐，测不出真实问法的省略和错别字。
3. **相关性分 3 级。** 2 = 直接回答问题，1 = 相关但不完整，0 = 不相关；两人独立标注，分歧仲裁，一致率低于 0.8 就重新对齐口径。
4. **每个 chunk 标注「是否足以回答」。** 只标文档级相关度不够，RAG 失败常常是「文档对，但块里没有答案」。

### 7.2 指标与门禁

| 指标 | 测什么 | 门禁 |
| --- | --- | --- |
| recall@50 | 检索有没有捞到 | 降 1 个点阻断发布 |
| nDCG@10 | 排序排得对不对 | 升 2 个点才允许发布 |
| answer accuracy | 最终答案对不对 | LLM judge 全量 + 人工抽检 100 条，错答 > 5 条阻断 |
| p99 | 延迟 | 涨 20% 阻断 |
| 空结果率 | 召回到没到 | 涨 1 个点阻断 |

指标要分意图看。总体 recall 涨了，可能只是「精确串」这一类涨了，而「流程」类掉了 5 个点；只看总分会在下一个版本翻车。

门禁和回滚线不是同一把尺：7.2 的阈值是发布前的一次性门禁（阻断发布），7.3 的是线上实时回滚线（触发回滚），后者留的余量更大。

### 7.3 灰度与回流

1. **先 shadow，再 canary。** shadow 复制 5% 流量跑新链路，只记录不返回，对比 recall 和延迟；recall@50 绝对降 2 个点以上、或 p99 涨 20% 以上，就不进 canary。
2. **canary 按 5% → 25% → 100% 推进。** 每档观察 24 小时，看业务指标（点赞、追问率、转人工率）而不只是技术指标。
3. **回滚条件写死。** 空结果率 +2 个点、p99 +30%、差评率 +1 个点，任一触发就切回旧版本，不讨论。
4. **badcase 每周回流。** 从低分、无引用、用户重问的会话里抽 20 条，补进标注集；标注集不增长，评测会很快饱和。

## 八、容量、监控与故障处理

### 8.1 容量估算

按 1000 万 chunk、1024 维、20 QPS 估算：

| 资源 | 估算 | 公式 |
| --- | --- | --- |
| 向量存储 | 41 GB | 1000 万 × 1024 × 4 B |
| HNSW 图 | 1.3 GB | 2MN 条边 × 4 B，M=16 |
| 倒排索引 | 8–12 GB | 原文 5 GB（英文）× 1.5–2 |
| 精排算力 | 2 张 T4 | 20 QPS × 30 条 = 600 对/秒，单卡约 400 对/秒 |
| 检索内存 | 48 GB + 副本 | 向量常驻 + 图 + 元数据 |

中文语料按 3 B/字重算：同样 1000 万 chunk，原文约 12–15 GB，倒排 18–30 GB，48 GB 内存装不下，要分片或压缩。

向量必须常驻内存，这是 HNSW 的硬约束；内存不够时先降 M 或上 PQ，不要指望换 SSD 解决。

### 8.2 监控

| 指标 | 告警阈值 | 说明 |
| --- | --- | --- |
| 检索 p99（改写 + 双路 + 融合） | > 150 ms | 目标 120 ms，150 ms 是告警线；不含精排和 LLM |
| 空结果率 | > 3% | 按意图分桶看 |
| 精排超时率 | > 1% | 超过说明 GPU 不够或 batch 太大 |
| 索引延迟 | > 10 min | 源文档更新到可检索 |
| 缓存命中率 | < 20% | 太低说明 key 设计有问题 |

### 8.3 故障处置

| 现象 | 先查 | 处置 |
| --- | --- | --- |
| 延迟突然翻倍 | 精排排队、向量库 GC | 降精排窗口到 20，扩容 |
| 某类问题全错 | 该意图的召回名次 | 看 `bm25_rank`/`ann_rank`，补精确串规则 |
| 回答引用不到原文 | 组装阶段的截断 | 提高块配额，检查 `parent_id` |
| 新文档搜不到 | 增量水位、删除事件 | 查 DLQ，重放失败批次 |
| 结果突然变差 | 别名是否被切 | 切回旧索引，对比 recall |

## 九、上线检查清单

结构：

1. 离线链路能重放：`chunk_id`、`content_hash`、`model_version`、`parser_version` 都有记录。
2. 两套索引主键一致，融合前能按 `chunk_id` 去重。
3. 过滤条件（租户、ACL、时间）在两路都下推，并有测试用例覆盖越权查询。
4. 别名切换和回滚演练过至少一次，回滚时间小于 5 分钟。
5. 标注集覆盖四类意图，每类不少于 50 条。

运行：

6. 每个阶段有独立超时和降级开关，`degraded` 比例有监控。
7. 检索 p99、空结果率、精排超时率、索引延迟四个指标有告警。
8. 缓存 key 含租户和过滤条件，越权测试通过。
9. shadow 和 canary 的流量比例、观察时长、回滚条件写进发布单。
10. badcase 回流有负责人和固定节奏，标注集每月增长不少于 50 条。
