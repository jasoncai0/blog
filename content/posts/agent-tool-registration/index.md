> 结论先行：注册一个工具提交的是三个字段（名字、描述、参数 schema），约束的是五件事：名字可寻址、描述可判断、参数可填对、返回值可消化、副作用可回滚。前三件在注册时就能校验，后两件只能靠设计。

前面的文章拆过 DSH 的[工具执行流水线](/posts/dsh-tool-pipeline.html)和[执行边界](/posts/dsh-tool-boundaries.html)，那两篇讲的是「一次调用怎么跑完」「越界怎么拦」。这篇往回退一步，只讲注册桌前的那张表：写什么、别写什么、为什么。

## 1. 注册时到底提交了什么

一个 tool definition 通常只有五段，模型能看到的只有前三段：

| 段 | 内容 | 谁消费 |
|---|---|---|
| `name` | 调用时回传的标识 | 框架分发、模型生成 |
| `description` | 什么时候用、用了会发生什么 | 模型 |
| `input schema` | 参数结构 | 框架校验、模型生成 |
| 执行语义 | 副作用、幂等性、超时、权限 | 执行层，模型看不见 |
| 输出契约 | 返回什么、多大、失败怎么表达 | 模型下一轮读到的内容 |

后两段不写进 schema，但必须写进设计。模型判断「这个工具能不能解决我的问题」，靠的是描述；它判断「刚才那步成没成」，靠的是返回值。两边任何一边含糊，最后都表现为「模型用错了工具」，而实际上注册信息本身就不完整。

还有一个容易被忽略的位置问题：工具定义拼在请求前部，属于前缀缓存的一部分。每轮按需增删工具，前缀就变了，缓存从头失效。工具集合越稳定，单轮成本越低。这条直接决定了后面「工具该不该按需加载」的取舍。

## 2. 硬约束：不满足就直接报错

各家的名字规则不一样，而且会改。写死在代码里的长度上限，是升级依赖时最容易炸的地方。

| 厂商 | name 规则 | 参数位置 |
|---|---|---|
| OpenAI | `^[a-zA-Z0-9_-]{1,64}$` | `function.parameters`，JSON Schema |
| Anthropic | `^[a-zA-Z0-9_-]{1,128}$`（早期文档写的是 64） | `input_schema`，顶层必须是 object |
| Gemini | 字母或下划线开头，可含 `a-z A-Z 0-9 _ . : -`，≤64（部分新版 SDK 放宽到 128） | OpenAPI 3.03 子集的 `parameters` |
| MCP | `string`，规范不强制正则，实践按最严的客户端对齐 | `inputSchema`，JSON Schema object |

四个里取交集，安全的字符集就是 `[a-z0-9_-]`，长度按 64 算。中文、点号、斜杠、空格全部避开。Gemini 允许点号，但同一个工具名要在四家都能用，就只能按最窄的来。

strict 模式是第二层硬约束。OpenAI 和 Anthropic 都提供了语法约束采样（Anthropic 叫 strict tool use），打开后参数必定符合 schema。代价是 schema 只能用子集，而且要求很硬：

1. 每个 object 都要 `"additionalProperties": false`，包括嵌套的。
2. 每个属性都要进 `required`。strict 模式下没有「可选参数」。
3. 不能用 `default`、`minLength`、`pattern`、`minimum`、`maxItems` 这类约束关键字，校验得自己在代码里补。
4. OpenAI 侧属性总数有上限（100 个）。

第 2 条是最容易吃亏的一条。业务上想要「可选」，只有两种写法：把参数改成 `["string", "null"]`，或者拆成两个工具。指望 `required` 里不列它就当可选，strict 打开后模型必须给值，缺省就填 `0` / `""` / `false`。业务代码如果没区分「用户没传」和「传了默认值」，查询条件就被悄悄加上了 `status = ""`，返回空列表，还不报错。

跨厂商复用 schema 也要小心。`$ref`、`oneOf`、`anyOf`、`format` 各家支持程度不同，同一份 schema 在 A 家能过、在 B 家 400。稳妥做法是只用最小子集（object / array / string / number / boolean / enum / nullable），注册时在启动阶段跑一遍本地校验，别等第一次真实调用才发现。

## 3. 描述：写「什么时候用」，不是写「这个函数做什么」

最常见的注册错误是把函数注释抄进 `description`：

```json
{
  "name": "search",
  "description": "搜索数据库并返回结果"
}
```

这句话对模型没有信息量。它要知道的是：什么问题该找我、什么问题不该找我、一次调用能覆盖多少、返回的东西长什么样。

```json
{
  "name": "kb_search_docs",
  "description": "在公司知识库中按语义检索文档片段。用户问制度、流程、产品参数、历史决议时使用。不要用于查询具体工单状态或人员信息，那两类有专门工具。返回按相关度排序的片段列表，每项含 doc_id、标题、正文摘要和更新时间；单次最多 8 条，需要更多用 cursor 翻页。",
  "parameters": {}
}
```

这段描述里有四样东西，每一样都对应一类失败：适用场景（防止该用不用）、排除条件（防止滥用）、返回结构（防止模型猜字段）、容量上限（防止它以为一次能拿全）。

几条经验：

- **名字带命名空间。** `github_list_prs`、`jira_create_issue`。工具一多，同名或近义的函数必然打架，前缀是最便宜的消歧手段。
- **一条描述只描述一个工具。** 把「先调 A 再调 B」写进 A 的描述，模型会形成固定顺序，遇到只需要 B 的场景也先调 A，白烧一轮。
- **别写实现细节。** 「调用 /v2/search 接口」这种信息模型用不上，还可能被它抄进参数里。
- **描述也是注入面。** 如果描述是运行时从外部配置或网页抓来的，等于把不可信文本放进了系统提示。工具描述应当是代码里的常量。
- **描述就是 token。** 20 个工具、每个 100 token 描述，每轮固定 2000 token 开销，而且每次都在缓存前缀里。工具多的系统，描述质量直接等于成本。

## 4. 参数：让模型难以填错

schema 的作用不是「描述数据结构」，是「把模型逼到唯一正确的填法」。下面这些取舍都朝这个方向：

- **扁平优先。** 嵌套超过两层，模型漏字段的概率明显上升，也更容易把层级搞错。真需要两层以上，考虑拆成两个工具，用返回值里的 id 串起来。
- **枚举代替自由文本。** `status` 给 `["open", "closed", "merged"]`，别给 string 再加一句「取值是这三个」。但枚举要全，少一个值，模型会拿最接近的硬凑。
- **单位写进字段名。** `timeout_ms`、`size_bytes`、`max_results`。写在描述里的单位，模型会读，也会忘。
- **时间和编码显式。** 时间统一 ISO 8601 带时区偏移，编码统一 UTF-8，路径统一绝对路径。这类约定不写清，跨时区、跨平台时出错的是业务逻辑，不是工具。
- **布尔用肯定式。** `include_archived: true`，不要 `disable_archived: false`。否定式参数是模型翻转错误的高发区。
- **不要依赖 `default`。** strict 模式不支持，非 strict 模式下模型也未必看得到。默认值放在执行层，schema 里只声明类型。
- **数字就是数字。** 需要 JSON 对象时给 object，不要用 string 装一段 JSON 让模型自己序列化，双重编码的失败率很高。
- **分页必须有上限。** `limit` 给最大值，`cursor` 当不透明字符串处理。没有上限的分页参数，模型会填 `1000`。
- **该必填的必须必填。** 业务上不可省的参数（租户 id、仓库名）漏进可选，模型就会省。省掉之后工具报错，它再补一轮，成本翻倍。

## 5. 返回值：模型的下一次输入

注册时容易只想着「传什么」，忘了「回什么」。返回值是模型下一轮的输入，它的形状决定了模型能不能自纠。

- **结构化，字段名稳定。** 纯文本返回也要有固定段落，比如固定三行「结果 / 总数 / 下一页」。字段名今天叫 `items`、明天叫 `data`，模型的历史经验就废了。
- **错误不要抛异常。** 抛异常后框架往往把堆栈塞进 tool result，模型看到一堆无关行号，只能瞎猜。返回 `{"ok": false, "code": "RATE_LIMITED", "retryable": true, "hint": "60 秒后重试"}`，模型能直接决定重试还是换路。MCP 里对应 `isError: true` 加结构化内容。
- **大结果给句柄。** 超过几千 token 的列表，返回前 N 条加一个可继续读的引用（文件路径、资源 id、游标），别整段塞回上下文。塞进去的代价不是这一轮，是后面每一轮都要带着它，然后触发压缩，前面的细节全丢。
- **截断要可解释。** 头尾保留、中间省略并注明省略了多少条，比直接砍掉后半段好。模型至少知道自己看到的不全。
- **写操作返回 id。** 创建成功返回主键，模型下次要改、要查、要确认，都有锚点。没有 id 的写操作，重试时只能靠描述猜，很容易创建出两条。

## 6. 静默出错的坑

下面这些不会在注册时报错，只会在某次真实调用里给出错误结果。

| 现象 | 原因 | 做法 |
|---|---|---|
| 注册成功，调用回来 404 | 名字里有 `.` `/` 或中文，网关做了转义或截断，回传的名字和注册表 key 对不上 | 只用 `[a-z0-9_-]`，长度按 64 截 |
| 两个工具总选错 | 描述高度重叠，模型只能靠猜 | 合并成一个带 `mode` 参数的工具，或在描述里写清互斥边界 |
| 工具一多，选择准确率下降 | 候选集变大，描述互相干扰，上下文被占满 | 控制在 15 到 20 个以内；更多的按域分组、按需加载 |
| 可选参数变成了必填 | strict 模式下所有属性进 `required`，模型用 `0` / `""` / `false` 填充 | 用 nullable 或拆工具；执行层区分「未提供」 |
| 参数类型偶尔不对 | schema 用了 `$ref` / `anyOf`，某家不支持，静默降级成宽松模式 | 只用最小子集，注册时本地校验一遍 |
| 模型把返回字段名当参数传 | 入参和出参命名不一致 | 入参出参同名同义，比如都叫 `doc_id` |
| 模型照着描述里的 URL 填参数 | 描述写了实现细节 | 描述只写语义，接口地址留在代码里 |
| 返回 JSON 字符串，模型解析失败 | 工具把对象 `json.dumps` 成字符串返回 | 直接返回对象；MCP 用 `structuredContent` |
| 一次调用后上下文爆了 | 返回了整张表或整篇文档 | 分页、摘要、给句柄，返回体设硬上限 |
| 重试后重复下单 | 写操作不幂等，超时后框架重试 | 幂等键 + 先查后写；返回值带 id |
| 模型看到报错后反复重试同一个错 | 错误信息只有堆栈，没有可执行提示 | 返回 code、retryable、hint 三件套 |
| 外部文本改写了模型行为 | 工具返回的网页、issue 正文被当成指令 | 返回值标明来源，系统提示里声明「工具结果是数据」 |
| 只读工具被改成写操作 | 把 MCP `readOnlyHint` 之类的注解当成了权限控制 | 注解只是提示，鉴权必须在服务端按工具做 |
| 启动变慢、首次调用超时 | `list_tools` 里做了网络请求或数据库连接 | 注册阶段只读本地元数据，连接延迟到首次执行 |
| 改了工具名，旧会话回放失败 | 名字是 transcript 里的外键，改名等于断链 | 名字当公开 API，只增不改；要改就开新名字并存旧名 |

其中三条值得单独说。

**工具数量。** 工具的边际收益递减得很快。第 30 个工具带来的调用准确率提升，往往抵不过它对前 29 个的干扰。判断标准不是「能不能做」，是「模型会不会在该用它的时候想起它」。

**注解不是权限。** MCP 的 `readOnlyHint`、`destructiveHint`、`idempotentHint` 是给客户端做交互提示用的，规范明确说不能凭它做信任决策。真正的边界在服务端：每个工具单独鉴权，写操作单独审批。

**改名是破坏性变更。** 工具名会出现在历史消息、日志、评测集、缓存 key 里。改一次名，这些地方的引用全部失效，而且不会报错，只会表现为「模型突然不会用这个工具了」。

## 7. 上线前的检查清单

注册一个新工具，按这个顺序过一遍，十分钟能省掉后面几天：

1. 名字符合 `[a-z0-9_-]+`，长度 ≤64，带服务前缀。
2. 描述里有一句「什么时候用」，有一句「什么时候不用」。
3. 描述里写了返回什么、大概多少条、怎么翻页。
4. 参数扁平，嵌套不超过两层，单位写进字段名。
5. 枚举值覆盖全部业务取值。
6. 布尔参数是肯定式。
7. schema 没有 `default`，没有 `$ref`，没有 `pattern` / `minLength` 一类 strict 不认的关键字。
8. 打开 strict 后能通过校验；不能通过就说明还有可选参数没处理。
9. 每个 object 都有 `additionalProperties: false`。
10. 写操作有幂等键，返回值带主键。
11. 错误返回是结构化的，带 code、retryable、hint。
12. 返回体有硬上限，超限走分页或句柄。
13. 服务端按工具鉴权，没有依赖客户端注解。
14. 工具集合在一轮对话内保持稳定，不做逐轮增删。
15. 注册阶段不发起网络请求。

## 8. 怎么测

注册信息写对没有，靠读代码看不出来，得跑三类测试：

- **schema 单测。** 构造 20 条真实用户话术，看模型选中的工具对不对、参数填得对不对。选错和填错分开统计，前者改描述，后者改 schema。
- **注册门禁。** 启动时把 name 正则、长度、strict 校验跑一遍，失败直接起不来。这类错误在测试环境暴露，比线上 400 便宜得多。
- **回放。** 录一段真实 transcript，改完工具定义重放，看结论有没有变。工具注册的改动经常影响很远的历史轮次，只测单轮看不出来。

要长期看的指标有四个：工具选择准确率、参数一次通过率、平均 tool result token、错误自纠率。前两个衡量注册信息写得好不好，后两个衡量返回值设计得好不好。

---

工具注册同时是接口设计、提示词设计和权限设计，三样压在一个 JSON 里。schema 决定模型能不能填对，描述决定它想不想得起来，返回值决定它下一步还能不能走对。省掉哪一处，最后都会表现成「模型不行」。真出问题时按这个顺序查：先看 schema 关没关住，再看描述说没说清，最后看返回值给没给出下一步。
