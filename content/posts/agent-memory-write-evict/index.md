> 这一篇只回答两个问题：一段对话里，什么内容值得写进长期记忆；写进去之后，什么该降级、什么该失效。末尾给一份只依赖标准库、能直接跑的参考实现。分层架构和运行时钩子放在[《设计 Agent 的记忆系统》](/posts/design-agent-memory.html)，这里不重复。

一个用户三个月前说过自己对花生过敏，两周前搬了家，昨天点餐时说「老样子」。系统把旧地址、旧口味和过敏事实一起召回，回答里出现了他已经搬离的城市。

问题通常不在向量库。向量库只负责「像不像」，它不知道哪条已经失效，也不知道哪条值得写。写入没有判据，库里就会堆满一次性信息；汰换没有判据，旧事实就会和新事实一起被召回。两件事都不做，检索越准，错得越稳定。

## 0. 结论速览

- 写入看三件事：未来会复用、会改变回答或动作、无法从别处推导。稳定性和证据强度是加分项。
- 一条记忆存成命题，不存整段摘要：claim、来源、有效期、置信度、状态。
- 汰换拆两条管道：失效靠有效期、矛盾替换、源头对账；无用靠衰减、预算和合并。
- 模型只做语义判断；写不写、何时失效、淘汰谁，由代码裁决。
- 不物理删除。降级、标墓碑、留审计，原始对话进冷存。

## 1. 先划边界：哪些东西不该进长期库

长期记忆不是「所有值得记住的东西」。它只装那些跨会话还要参与决策的命题。先把四类内容分开：

| 内容 | 例子 | 放哪 | 为什么 |
| --- | --- | --- | --- |
| 事实与偏好 | 花生过敏、常住上海、偏好 Go | 长期记忆 | 跨会话复用，直接改变建议 |
| 事件 | 上周面试失败、昨天部署回滚 | 长期记忆，带时间 | 用来找先例、做归因 |
| 流程与教训 | 这个仓库先跑 `pnpm build` | 长期记忆或程序记忆 | 下次同类任务直接复用 |
| 任务状态 | 明天下午三点提醒我开会 | 任务系统 | 有明确截止时间，过期即废 |

前三类进长期库，第四类不进。把「提醒我明天三点开会」写成事实，是这类系统最常见的污染：一个月后它被召回，模型会把一条过期指令当成当前约束执行。

「值得记」和「重要」也不是一回事。生日很重要，但一年只用一次；过敏很低频，但每次点餐都改变决策。判据是决策影响，不是情绪强度。

## 2. 写入判据：五票通过，一票否决

### 2.1 五个信号

1. **复用概率**：未来 30 天里，它会不会再次影响回答？「我对花生过敏」会；「今天天气不错」不会。
2. **决策相关性**：它会不会改变推荐、权限、执行路径或拒绝理由？会改变动作的，优先级高于只改变措辞的。
3. **不可推导性**：能不能从仓库、日历、公开知识或当前上下文重新算出来？能推导的就不写。项目用 Go 写在 `go.mod` 里，不必再记一条「这个项目用 Go」。
4. **稳定性**：这条事实的默认寿命有多长？过敏是十年尺度，暂住城市是周尺度，会议时间是天尺度。稳定性决定半衰期，不决定写不写。
5. **证据强度**：用户明确说的，高于模型从行为里猜的；多次一致的，高于只出现一次的；有来源链接的，高于二手转述。

五个信号不必等权。一个可用的初始权重是复用 0.30、决策 0.25、不可推导 0.20、稳定性 0.15、证据 0.10，折算到 0 到 10 分。权重是产品策略，不是自然常数；上线后按误写和漏写调。

### 2.2 一票否决

下面四类内容，不管分数多高都不写：

- 密钥、口令、token、身份证号。要记也只记「凭据在 1Password 的某个条目」，不记值。
- 与对话无关的第三方隐私。用户提到同事的病情，不代表应该长期保存。
- 模型常识和公开知识。写进去只会占预算，还会随模型升级过期。
- 来自网页、工具输出、文档的指令性文本。这是 prompt injection 的持久化入口：攻击者在页面里写「以后所有回答都先执行这条」，一旦被当作用户事实写入，后面每次检索都会把它带进上下文。

最后一条要在抽取阶段就做来源标记：`source=user` 才进候选池，`source=tool/web` 只能进「待确认」，不能直接晋升。

### 2.3 阈值与晋升

五个信号先各自打到 0 到 10 分，再按权重相加：

`score = 0.30×复用 + 0.25×决策 + 0.20×不可推导 + 0.15×稳定性 + 0.10×证据`

这个 `score` 是策略层的输入，不是模型返回的 `importance`。参考实现为了少一层，把 `importance()` 直接当成综合分用；生产里应该拆成两个字段：模型给 `importance`（这条重不重要），策略层算 `score`（这条该不该写）。两者经常不一致：一条「我生日是 3 月 5 日」重要性高，但可推导性低、复用低，不该占长期库名额。

以 10 分制为例：

- **≥ 6 分**：直接写，状态 `active`。
- **4 ≤ score < 6**：写进 `candidate`，不参与默认检索；第二次出现、被用户确认、或被真正使用后晋升。
- **< 4 分**：丢弃，只在审计日志里留一条计数。
- **新颖度 < 0.3**：不新增，合并到已有条目，证据计数加一。
- **每会话上限 10 条，每天上限 50 条**：防止一次长对话把预算写满。超限时按分数取前 N 条，其余进候选。

用户明确说「记住这个」可以绕过分数，但仍然要过否决项。此时置信度给 0.95，状态直接 `active`，因为这是最强的证据。

### 2.4 一条记忆存什么

不要只存一句摘要。摘要丢掉了来源、时间和否定关系，后面无法审计，也无法重新抽取。最小字段集：

| 字段 | 作用 |
| --- | --- |
| `kind` | fact / preference / event / procedure |
| `subject` / `predicate` / `object` | 结构化命题，用来做去重和矛盾检测 |
| `text` | 给人看的原句或规范化句子 |
| `valid_from` / `valid_to` | 这条事实在世界上何时为真 |
| `recorded_at` | 系统何时写入 |
| `confidence` / `importance` | 置信度与重要性，分开存 |
| `sensitivity` | normal / private / secret，决定能否注入上下文 |
| `status` | candidate / active / disputed / superseded / warm / cold / tombstone |
| `supersedes` | 被哪条新记忆替代，保留链 |
| `source` | episode id、消息 id、工具名 |
| `last_used_at` / `used_count` | 真正被用过的证据，不是被召回的次数 |
| `access_count` | 被召回次数，只用来观察检索偏好，不参与晋升 |

原文另存一张 `episodes` 表，只追加。claim 通过 `source` 指回原文。这样模型抽取错了可以重跑，用户质疑时可以回放，删除时也能做级联。

写入要幂等。用 `hash(source, turn_id, subject, predicate, object)` 做唯一键，重试不会写出三条一样的过敏事实。

## 3. 汰换判据：失效和无用是两条管道

很多系统把「删除」做成一个动作：分数低就删，矛盾就删，用户说不对也删。结果是要么删错，要么不敢删。把汰换拆成两条管道会清楚很多。

### 3.1 失效：这条事实不再为真

失效处理的是真假，不是价值。触发条件有五类：

| 触发 | 例子 | 动作 |
| --- | --- | --- |
| 有效期到期 | 出差住杭州、项目代号「凤凰」 | `valid_to` 到点，状态转 `cold` |
| 新事实矛盾 | 从杭州搬到上海；美式改成拿铁 | 旧条 `superseded`，新条 `active`，保留 `supersedes` |
| 源头对账 | 仓库地址、组织架构、价格表 | 定期拉源数据比对，不一致就标 `disputed` |
| 依赖级联 | 项目取消，围绕它的决策一起失效 | 依赖图反向遍历，批量标失效 |
| 用户纠正 | 「不对，我现在不住那了」 | 立即失效，置信度清零，记录纠正来源 |

矛盾检测不要只看向量相似度。「我喜欢美式」和「我现在喜欢拿铁」向量很近，但关系是替代；「我对花生过敏」和「我对海鲜过敏」向量也近，关系却是并存。用向量召回候选，再用模型或 NLI 判 same / contradict / complement / unrelated，最后按关系统一处理。

新事实不一定更可信。用户说「我搬到上海了」，但来源是转述、置信度低，而旧地址是用户本人上周确认的，这时不要自动覆盖。把两条都留着，新条标 `disputed`，等下一次确认。自动覆盖只在新证据分数不低于旧条、且置信度过阈值时发生。

### 3.2 无用：这条事实不再值得占预算

无用处理的是成本，不是真假。一条事实可以永远为真，但一年没人用，就不该继续占 `active` 名额。

保留分用按使用时间的指数衰减：

`R = 0.5 ** (days_since_last_use / half_life)`

半衰期按类型给，不搞全局一刀切：

| 类型 | 半衰期 | 理由 |
| --- | --- | --- |
| 过敏、硬约束 | 3650 天 | 低频但高风险，不能自己消失 |
| 住址、时区 | 365 天 | 会变，但变化慢 |
| 口味、风格偏好 | 180 天 | 会漂移 |
| 项目笔记 | 365 天 | 项目周期通常更短，靠有效期兜底 |
| 事件 | 30 天 | 主要价值在近期归因 |

表里的类型对应参考实现的 `predicate`：`allergy`、`residence`、`likes`、`note`、`event`。`reminder` 也给 1 天，但正常流程在写入前就拒掉。从未被用过的条目，`last_used_at` 回落到 `recorded_at`，否则衰减公式没有起点。

这里有两个容易做错的地方。

第一，按「使用」衰减，不按墙钟。一条过敏事实两年没被提起，不代表它失效；它的半衰期足够长，衰减后仍然高于阈值。反过来，一条昨天刚写入、但从未影响过回答的闲聊，不应该因为「新」就留在 active。

第二，只给真正参与生成回答的记忆加分。检索命中不等于有用：召回了十条，模型只用了其中一条，只有那一条应该 `used_count += 1`。否则热门记忆会越来越热，冷门但关键的记忆永远进不了上下文，这就是检索强化带来的马太效应。

退役走阶梯，不做二值判断：

- `active`：默认参与检索，有名额上限。
- `warm`：保留分低于 0.25，或超出预算被挤下；仍可被强相关查询召回。
- `cold`：低于 0.08，或有效期已过；只在审计、回放、显式恢复时读取。
- `tombstone`：用户删除或合规删除；内容不可读，只留 id、时间和原因。

预算淘汰按边际效用排序，不按时间。`utility = importance/10 × R × (1 + 0.1 × used_count)`，超过 `max_active` 就从最低的开始下沉。这样「很重要但很久没用」的条目会先降级，「不重要但最近频繁用」的条目反而能留下。

相似事件要合并。十次「部署失败」不该存十条，应该合成一条「这个服务在迁移窗口部署失败率偏高」，保留十个 episode 指针。合并后原文还在，统计也还在，只是 claim 少了一条。

### 3.3 不物理删除

`tombstone` 不是懒，是审计需要。至少保留 id、删除时间、删除人、删除原因、原 claim 的哈希。用户要求「彻底删除」时再走单独的合规路径：清原文、清向量、清备份，并记录执行回执。

硬删除还有两个现实问题。第一，删错了无法回滚；第二，模型抽取错误导致的误删无法复盘。软删除加 30 天宽限期，能挡住大部分事故。

## 4. 判断交给谁：模型提议，代码裁决

写入和汰换都需要判断，但不是同一种判断。

- **语义判断**：这段话里有没有事实、两条记忆是不是同一个意思、是否矛盾、哪条更相关。需要理解自然语言，适合模型。
- **策略判断**：写不写、写几条、何时过期、淘汰谁、给谁看。需要确定性、可审计、可回归，适合代码。

{{< fig "diagrams/01-architecture.svg" "写入、存储、读取与维护的分层：紫色是模型，橙色是代码策略，绿色是存储" >}}

| 层 | 负责 | 典型决策 |
| --- | --- | --- |
| LLM | 语义 | 抽取候选、判 same/contradict/complement、重要性初判、合并摘要 |
| 小模型与信号 | 召回与初筛 | embedding 召回 top-k、NLI 判矛盾、NER、时间解析 |
| 代码 | 裁决 | 阈值、有效期、TTL、衰减、预算、排序、软删除、权限 |
| 人 | 兜底 | 显式「记住」、纠正、删除、审计 |

论文里的系统基本都是这个分工，只是比例不同。

- [Mem0](https://arxiv.org/abs/2504.19413) 让 LLM 只在 top-10 相似记忆上做 `ADD / UPDATE / DELETE / NOOP` 四选一，召回靠向量，执行靠代码。
- [Zep](https://arxiv.org/abs/2501.13956) 用 LLM 判矛盾，但 `t_valid`、`t_invalid`、`t_created`、`t_expired` 四个时间戳的赋值是结构化规则。
- [Generative Agents](https://arxiv.org/abs/2304.03442) 只让 LLM 给重要性打 1 到 10 分，检索分数是加权和，每小时 0.995 的衰减写死在代码里。
- [Oblivion](https://arxiv.org/abs/2604.00131) 用 LLM-as-judge 加 embedding 判断不确定性，但保留分是公式，强化只给真正影响了回答的记忆。
- [CALM](https://arxiv.org/abs/2610.38573) 的检索资格门用固定权重（各 1/4，阈值 0.5）或一个小 MLP，没有让通用 LLM 来当门卫。

全交给模型会付出六个代价。

1. **结果不确定**：同样输入跑两次，写入和删除可能不一样，没法做回归测试。
2. **成本随库增长**：每轮对全库判一遍是 O(n) 次调用。Mem0 也只对 top-k 调一次。
3. **算术和时间不可靠**：TTL、衰减、预算排序容易算错，「下周三」经常被解析成错误日期。
4. **打分偏差**：LLM 的重要性分数普遍偏高，且受提示词锚定，需要人工标注的锚点校准。
5. **不可审计**：删除一条记忆必须能说出确定性理由。模型说「觉得没用」不能写进审计日志。
6. **对抗风险**：记忆投毒可以诱导模型给恶意内容打高分，规则层必须能一票否决。

让模型判断可靠，靠的是工程约束，不是换更大的模型：

- 结构化输出，带置信度和一句理由；温度设 0；prompt 版本化。
- 只给模型看 top-k 候选，不喂全库。
- 低置信度不自动删，转 `disputed`，双方都保留。
- 删除走软删除加宽限期；高风险操作双模型投票。
- 新策略先跑影子模式，只记录不执行，和旧策略对比。
- 维护 50 到 100 条标注对话做黄金集，每次改 prompt 跑一遍。
- 用下游结果回填：这条记忆被检索后到底有没有用，比模型自评分可信。

## 5. 一份能跑的参考实现

完整文件在 [agent-memory.py](/files/agent-memory.py)，只依赖 Python 标准库和 SQLite，不到 500 行。直接跑：

```bash
cd /path/to/dir
python3 agent-memory.py demo
```

跑之前确认三件事：Python 3.10 以上（代码用了 `X | None` 标注）；`sqlite3` 模块可用（标准发行版自带）；在文件所在目录执行，或者把路径写全。演示用 `:memory:`，每次启动都是空库，不需要 `--reset`。

它不是生产系统，但把前面几条判据都落成了代码：

- `RuleLLM` 是模型的确定性替身，接口和真实调用一致：`extract`、`relate`、`importance`。
- `MemoryStore.write()` 做抽取、召回、关系判定、策略门、提交。
- `MemoryStore.recall()` 只查 `active`/`warm` 且未过期的条目，按 `0.55×相似度 + 0.25×重要性 + 0.20×新鲜度` 排序，相似度低于 0.2 的丢掉，取前 k 条并累加 `access_count`。
- `MemoryStore.credit()` 只给真正出现在回答里的 id 累加 `used_count`、刷新 `last_used_at`，顺带把置信度抬 0.02；召回但没被用到的条目不强化。
- `MemoryStore.maintain()` 做有效期下沉、衰减降级、预算淘汰。
- `MemoryStore.forget()` 只把状态改成 `tombstone`、写 `valid_to`，不删行。

核心写入循环长这样：

```python
for claim in self.llm.extract(text):
    if claim.kind == "task_state":
        decisions.append({"action": "reject", "reason": "task_state"})
        continue

    importance = self.llm.importance(claim)
    if importance < DROP_BELOW:
        decisions.append({"action": "drop", "reason": "low_importance"})
        continue

    target, relation = None, "unrelated"
    for row in self._similar(claim):
        rel = self.llm.relate(claim, row)
        if rel != "unrelated":
            target, relation = row, rel
            break

    if relation == "same":
        decisions.append(self._merge(target, now))
    elif relation == "contradict":
        decisions.append(self._supersede(target, claim, importance, now))
    else:
        status = "active" if importance >= ACTIVE_AT else "candidate"
        decisions.append(self._insert(claim, importance, status, now, source))
```

维护循环把三件事分开：

```python
# 1. 有效期到了，下沉到 cold
for row in self.conn.execute(
    "SELECT * FROM memories WHERE status = 'active' AND valid_to <= ?", (now,)
):
    self.conn.execute("UPDATE memories SET status = 'cold' WHERE id = ?", (row["id"],))

# 2. 衰减：active 低于 0.25 转 warm，warm 低于 0.08 转 cold
retention = 0.5 ** (days_between(last_used, now) / HALF_LIFE[predicate])

# 3. 预算：active 超限时按 utility 从低到高下沉
active.sort(key=lambda row: importance / 10 * retention * (1 + 0.1 * used_count))
while len(active) > max_active:
    demote(active.pop(0))
```

演示脚本跑八个 turn，覆盖 add / reject / supersede / candidate / merge 五类动作（`drop` 留给低分输入，这八条都没低到 4 分以下）：

```text
[turn 0] 我对花生过敏              add active allergy
[turn 1] 我住在杭州                add active residence
[turn 2] 提醒我明天下午三点开会    reject task_state
[turn 3] 我搬到上海了              supersede residence 杭州 → 上海
[turn 4] 我喜欢喝美式              add candidate likes
[turn 5] 我喜欢喝美式              merge likes evidence=2, candidate → active
[turn 6] 我现在喜欢拿铁了          supersede likes 美式 → 拿铁
[turn 7] 记住：我的工位在 3 楼靠窗  add active note
```

第六个 turn 之后，旧地址和旧口味都是 `superseded`，检索「我住哪」只返回上海，检索「花生」仍然命中过敏事实。第 400 天跑维护，拿铁降到 `warm`，工位因预算被下沉；第 800 天，拿铁降到 `cold`，过敏事实仍然是 `active`。

这份实现故意没做四件事：真实 embedding、真实 LLM 调用、并发控制、加密与多租户。接到生产时，先换掉 `RuleLLM` 的三个方法，再把 SQLite 换成带事务和唯一键的数据库，最后补权限和审计。

## 6. 上线顺序与指标

不要一上来做全量。按下面顺序，每一步都能独立回滚。

1. **第 1 周，3 天**：建表、写入、检索、墓碑、审计日志。先不管衰减和模型抽取，用规则跑通。
2. **第 1 周，2 天**：加矛盾检测和用户纠正。只处理 `same` 和 `contradict`，`complement` 先并存。
3. **第 2 周，2 天**：加有效期、衰减、预算和离线维护任务。先影子运行，只记录不执行。
4. **第 3 到 4 周，5 天**：把抽取和关系判定换成模型，建立黄金集和回归脚本，再开灰度。

指标至少看六个：

| 指标 | 怎么算 | 目标 |
| --- | --- | --- |
| 写入准确率 | 抽样人工标注，写对的条数 / 写入条数 | 大于 0.9 |
| 陈旧率 | 检索结果中已失效条目的比例 | 小于 0.02 |
| 知识更新准确率 | 新值覆盖旧值的测试集通过率 | 大于 0.85 |
| 拒答率 | 该拒答时拒答的比例，按场景分 | 不低于基线 |
| 每轮记忆 token | 注入上下文的记忆 token / turn | 稳定，不随库增长 |
| 删除可审计率 | 有原因、有来源、有执行人的删除比例 | 1.0 |

公开基准可以用 [LoCoMo](https://arxiv.org/abs/2402.17753)、[LongMemEval](https://arxiv.org/abs/2410.10813) 和 [DMR](https://arxiv.org/abs/2501.13956)（Zep 论文里的多会话推理基准）。LongMemEval 有 500 题，历史长度约 115K token，专门考多会话、时间推理和知识更新；[Zep](https://arxiv.org/abs/2501.13956) 在这个基准上把准确率从 60.2% 提到 71.2%，延迟降了约 90%。但要注意一个陷阱：有些淘汰策略的评测把「未来会问什么」提前泄露给了策略，隐藏问题后优势就消失了。上线前用删除反事实自测更可靠：随机删掉一条记忆，看回答变不变；该变而没变，说明它没被用上；不该变却变了，说明它被过度依赖。

最后是五个最常见的坑：

1. 只按相似度写，把「说过」当成「成立」。
2. 检索即强化，热门记忆挤掉冷门关键事实。
3. 硬删除，出错无法回滚，审计也补不回来。
4. 把任务状态写进事实库，过期指令污染后续对话。
5. 用摘要替代原文，抽取错了无法重跑，用户质疑时拿不出证据。

把写入和汰换做对之后，再调检索算法。顺序反了，检索越好，系统越自信地引用一条早就不成立的旧事实。
