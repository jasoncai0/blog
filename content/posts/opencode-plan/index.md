> 源码版本：`opencode 2.2.5`，commit `a687c047`（2026-11-08）。代码引用以工作区 `.opencode-src/` 为基准。
> 系列第十篇。前九篇讲系统怎么跑；这一篇讲一个具体问题：**它怎么"做计划"**。

## 0. 先说结论

OpenCode 没有"规划器"。你在代码里找不到任务分解、依赖图、执行计划这些对象。

它有**三个尺度上的三件事**，互不依赖，各自解决一个不同的问题：

| 尺度 | 机制 | 回答的问题 | 一句话 |
| --- | --- | --- | --- |
| 会话 | Plan 模式 | 能不能改？ | 一套权限 + 一条提醒，把 agent 关进"只讨论" |
| 步 | `todowrite` | 做到哪了？ | 一份可覆盖的清单，模型自己维护 |
| 轮 | `/goal` | 还要不要继续？ | 一个 judge 在 idle 时裁决，决定再跑一轮 |

{{< fig "diagrams/01-three-surfaces.svg" "三层规划的分工" >}}

先给三个容易踩的结论：

1. **Plan 模式不是沙箱**。它 deny 了 `edit`，但没 deny `shell`——所以 plan 之下仍然能跑命令、仍然能通过 `bash` 改文件。
2. **`todowrite` 没有任何强制力**。它不阻塞、不校验、不影响执行；模型可以永远不更新它，也可以写一份与实际不符的清单。
3. **`/goal` 不是新 agent**。它还是同一个会话、同一个 agent，只是多了一个"空闲时自我裁决"的钩子。

## 1. 会话尺度：Plan 模式

{{< fig "diagrams/02-plan-mode.svg" "模式不是开关，是历史里的一条提醒" >}}

### 1.1 它由三样东西拼成

- **一条 agent 记录**：`plan`，`mode: "primary"`，权限里 `edit` 被 deny、只有 `~/.opencode/plan/*` 例外；
- **两条提醒**：进入/离开时各插一段 `system-reminder`；
- **一个目录**：`~/.opencode/plan`，唯一允许写的地方。

有个细节值得注意：**它没有专属 system prompt**。plan 的"人格"就是一条 agent 记录（名字、描述、权限），行为约束全部落在提醒里。

目录也有意思：它是**全局**的（`~/.opencode/plan`），不按项目分；而且插件激活时**不创建**它，第一次写文件时才由工具的"自动建父目录"落地。

三样缺一不可：只有权限没有提醒，模型会不断尝试然后被拒；只有提醒没有权限，它可能"忘了"。

### 1.2 提醒是怎么进出的

进入 Plan 时（`session.created` 或 `agent.selected` 到 plan），注入一段 enter 提醒；离开时注入 leave 提醒。文案很短，核心是三句：讨论而不是修改、只写 plan 目录、要改就请用户切换 agent。

注入位置在**最后一条 user 消息之前**，与 agent 切换提醒的落点一致。

这里有两套注入路径，缺一不可：

- **事件路径**：订阅 `session.created` / `session.agent.selected`，把提醒以 `synthetic` 消息落库（`resume: false`，只入队不唤醒）；
- **请求路径**：`context` 钩子在每次请求前把提醒 `splice` 进本次消息数组。

为什么两套都要：synthetic 是异步投递的，当前这个 Step 可能还没看到它——`splice` 保证"立刻生效"；而 synthetic 保证"历史里有一条"，让下一次对账有依据、也不会重复注入。

### 1.3 为什么还需要"对账"

提醒是历史里的一条普通 user 消息，而历史会被改写：**压缩**会把它换掉，**revert** 会把它删掉。提醒一丢，模型就"忘了"自己在 plan 模式。

所以每个 Step 的 `context` 钩子都做一次对账：

```text
last = 扫描历史里最后一条 enter/leave 提醒
if agent === plan && last !== enter  → 补 enter
if agent !== plan && last === enter  → 补 leave
```

这是一个"从状态推导提醒、而不是相信提醒"的设计：真正的事实是会话的 `agent` 字段，提醒只是它的渲染产物。

更细的一层：`lastReminder` 只认"整条消息文本完全等于 enter/leave"的消息。而压缩会把历史包进 `<recent-context>` 之类的包装里，提醒就不再"原样可见"——所以**压缩之后必然要补一次**。revert 更直接：它物理删除边界后的消息，但 `session.agent` 不会跟着回滚，于是"agent 还是 plan、提醒却没了"，必须补。

### 1.4 只读的边界

`plan` 的权限表里，`edit` 是 deny，`question` 是 allow，其他沿用默认。`shell` **没有被 deny**。

这意味着：

- 用 `edit`/`write`/`patch` 改文件 → 被拦，`execute.after` 钩子还会把错误改写成一句更好懂的话；
- 用 `shell` 跑 `sed -i`、`git apply` → **照常执行**（`shell` 只断言 `shell`，而 plan 的默认规则是 `*` allow）；
- 让子代理去改 → enter 提醒里明确写了"不要让子代理去改"，但这只是文字；子会话用自己的权限求值，父的 plan 限制不自动继承；
- 配置或会话级权限**追加在 plan 规则之后** → 后写的规则覆盖先写的 deny，等于把只读解开了。

### 1.5 界面上怎么进入（以及一个坑）

- **TUI**：`shift+tab` 循环切换，或 `/agents` 打开选择框。切完之后输入框元数据行会显示 `Plan · 模型 · 供应商`，并给输入框描边着色；时间线出现一行 "Switched agent from Build to Plan"。
- **提醒本身在时间线里看不见**：它没有 `description`，两端都把这类 synthetic 隐藏了——所以没有"你正在计划"的横幅，唯一的提示就是那个 agent 名字。
- **Web 有个坑**：agent 选择器默认**不显示**（`settings.general.showCustomAgents` 默认 false，隐藏时回退到 build）。也就是说默认界面里既看不到 Plan、也进不去——要在设置里打开 "Show agent"。
- **plan 目录没有 UI**：没有浏览、没有列表、没有 API，也没有命名约定。写不写文件、写什么，全看模型自己。


所以"Plan 模式"约束的是**编辑工具**，不是整个进程。想要真正的只读沙箱，得在 `shell` 上也加规则，或者干脆在容器里跑。

## 2. 步尺度：todowrite

### 2.1 它简单到有点意外

任务项只有两个字段：

```text
{ content: string, status: "pending" | "in_progress" | "completed" | "cancelled" }
```

没有 id、没有优先级、没有依赖、没有截止时间。整份列表就是一个数组，每次调用**全量替换**。

工具的输出除了回显列表，还会生成一句摘要："3/5 completed, 1 in progress. In progress: …"。这句摘要是给模型看的——它下一次读到的工具结果里就有自己刚写的东西。

### 2.2 存在哪

存在**消息里**，而且有两份副本：

- 调用的入参写进工具 part 的 `state.input`；
- 结果的 `metadata: { todos }` 写进 part 的 metadata。

两者随 durable 事件一起落库、重放、回退。**没有 todo 表**—— V1 曾经有一张（还带 `priority` 和 `position` 列），V2 重建这个工具时把它精简成"两条字段 + 消息里的一份快照"，旧表在迁移里被直接丢掉。

所以：

- 它没有独立存储、没有投影、没有状态机；
- 压缩不会删除消息，但摘要模板只保留"目标/完成/阻塞"几行，**不保留原列表**——所以模型侧可能"忘记"，描述才强制每次全量重发；
- 前端取"回退边界之前最后一条 completed 的调用"作为当前清单，两端各自从消息推导。

"最后一份就是当前状态"——这就是它被称为无状态的原因。

### 2.3 工具描述里的三条规矩

`todowrite.txt` 写得很克制，基本就是三条：

1. 3 步以上的任务、或用户一次给了多件事时主动用；单个简单任务别用；
2. 每次传**完整列表**，它会替换上一份；
3. 只在列表变化时调用，开始一项标 `in_progress`，真正做完才标 `completed`。

没有"必须每步更新"的强制，也没有"完成后必须清空"的要求。

### 2.4 它的真实作用

它是一份**给人看的进度条 + 给模型看的备忘**。人靠它知道"现在做到哪了"，模型靠它对抗长上下文里的遗忘。

但它不参与执行：不阻塞、不校验、不影响工具选择。模型完全可以写一份漂亮的清单然后不照做——这在设计上是接受的，因为"强制"要靠权限与计划模式，而不是靠一张便签。

### 2.5 两端渲染得完全不同

- **TUI**：时间线内联，每次调用一块 `# Todos`，用 `[✓] [•] [ ] [-]` 表示四种状态，`in_progress` 用警告色、`cancelled` 加删除线；侧栏还有聚合面板，超过 2 项可折叠。
- **Web**：时间线**完全不渲染** `todowrite`（避免每次更新刷屏），改成输入框上方的一个胶囊，显示当前项与 `+N`；只有"会话在跑且还有未完成项"时才出现，结束即隐藏，防止陈旧计划残留。

同一个工具、同一份数据，两种信息密度。Web 的选择更接近"进度指示器"，TUI 的更接近"工作日志"。

### 2.6 两个暗坑

1. **`experimental.todo` 开关**：关闭时工具直接不注册（不是隐藏，是根本没有这个工具）。默认 local/dev 开、release 关——所以"我的模型怎么不写清单"可能不是它不想，而是工具不存在。
2. **并发调用没有合并**：同一步里并行多次调用时，按 assistant content 数组顺序取最后一条，谁在后谁赢；晚到的旧状态会覆盖新状态。没有锁、没有 CAS。


## 3. 轮尺度：/goal

{{< fig "diagrams/03-goal-loop.svg" "一轮 = 一次裁决 + 五种去向" >}}

### 3.1 它是唯一"会自己继续跑"的机制

`/goal <objective>` 之后，会话在每次即将空闲时被拦一下：一个 reviewer 看当前进展，给一个判词，决定"再跑一轮"还是"收工"。

reviewer **不是独立 agent，也不是另一个模型**——它就是当前会话的 agent/model 再跑一次 `session.generate`：同一套系统提示、同一份历史，末尾追加一条"停下，评判一下"的请求，不带工具。所以它更像"同一个人的复盘视角"，而不是外部裁判。

判词只有五个值（`packages/schema/src/goal.ts`）：

| verdict | 含义 | 动作 |
| --- | --- | --- |
| `continue` | 还没完，继续 | 注入下一轮的 continuation，唤醒会话 |
| `done` | 目标达成 | 标 complete，停 |
| `paused` | 需要人介入 | 标 paused，停 |
| `blocked` | 被卡住 | 同样落成 `paused`，只是 reason 不同 |
| `wait` | 在等后台任务 | 什么都不做，等下一次 idle |

`wait` 是专门为后台任务留的：如果还有后台 shell 在跑，judge 看不到结果就没法判断，于是选择"等"。但它不能无限等——`WAIT_LIMIT = 30 分钟`，超时就暂停。

它有两个保险：只在**确实有后台 shell** 时才被接受（否则会重问一次），以及 `WAIT_LIMIT = 30 分钟` 的看门狗。

判词解析很宽松：从文本里截第一个 `{` 到最后一个 `}` 再按 JSON 解，允许代码围栏和前后废话。但**解析不出来会重问一次**，两次都不可用才暂停——不猜、不默认继续。

### 3.2 三个上限

- `MAX_ROUNDS = 50`：轮次上限。到了就 `paused`，理由写"Reached the limit of 50 rounds"。
- `MAX_STALLS = 3`：停滞上限。判定停滞有两个条件——**理由与上一轮相同**，或者**这一轮根本没调用工具**（说明它在空转）。连续 3 次就 `paused`。

计数从第一轮就开始了：首轮没调工具已经算 1 次，所以"连续三轮无工具"在第三个判词处就停；"理由重复"的路径则是首轮加三次重复、共四个判词。
- `WAIT_LIMIT`：等待上限，如上。

三个上限都是"硬停"而不是"报错"：目标被标成 paused，会话回到正常状态，用户可以 `/goal resume` 或换个目标。

### 3.3 状态存在插件存储里

`goal` 不是会话字段，而是**插件自己的 storage**，key 是 `session:<id>`。

这带来两个直接后果：

- **子会话与 fork 不继承目标**。父在做 goal，派出去的子会话没有 goal——这是对的，子任务不该自己续跑。
- **跨进程不续跑**。goal 状态里带一个 `boot` 标识（当前进程的 UUID），上一个进程留下的 goal 在新进程里会以 paused 回来，需要人确认。

写入用的是"比较后替换"：只有 `id`、`updatedAt`、`status` 都没变才写，避免循环的写覆盖掉用户刚下的 `/goal pause`。

### 3.4 它不阻塞用户

goal 不是后台定时器，只是"停止钩子"：每一步跑完、会话本要空闲时问一次"还有输入吗"。所以：

- 执行期间用户消息照常进 inbox，在安全边界作为 steer 插入；
- 有用户输入时 idle 钩子不触发，用户优先；
- 用户按中断 → 立即暂停（"Stopped by the user"）；
- `/goal pause` 与 GUI 按钮是更温和的版本；`resume` 会把 rounds 重置为 1，并补一条 continuation。

### 3.5 三份注入文本

| 文本 | 作用 | 是否落库 |
| --- | --- | --- |
| `kickoff` | 目标激活后的开场：跨轮工作、只信证据、卡住直说 | 是（synthetic） |
| `continuation` | 每轮推进：重述目标 + 上一轮 reason/next_step | 是（带 `goalID`） |
| `reminder` | 防遗忘补丁：上下文里看不到目标块时补一条 | **否**，只在请求时插入 |
| `judge` | 给 reviewer 的评分提示，要求一行 JSON | 否 |

`reminder` 的触发条件值得记：它检查上下文里还有没有 `<untrusted_objective>` 块——压缩把它冲掉之后才会补。所以它不是"每轮都念一遍"，而是"目标从视野里消失时补一次"。

三个文本都把目标包进 `<untrusted_objective>` 并做 HTML 转义，明确声明这是用户数据、不是高优先级指令。

judge 的输出是被 Schema 解析的；解析不出来就当作"没有可用判词"，直接 paused——宁可停，也不猜。


## 4. 三者怎么配合

它们之间**没有代码级耦合**：plan 不产生 todo，todo 不影响 goal，goal 不强制更新 todo。组合方式是外部的——用户切换、模型自觉。

一个典型的长任务会这样走：

```text
1. 用户切到 plan，讨论方案        ← Plan 模式（管"能不能改"）
2. 切回 build，模型写一份 todo    ← todowrite（管"做到哪了"）
3. 逐项实现，随手更新清单
4. （可选）下 /goal，让它自己盯到测试全绿  ← /goal（管"要不要继续"）
```

注意第 2 步不是自动的：切回 build 之后，模型要自己决定"这件事值得列清单"。第 4 步也是显式的——没有人下 goal，它不会自己出现。

### 4.1 为什么不做成一条流水线

因为三件事的触发者不同：

- Plan 模式的触发者是**人**（切 agent）；
- todo 的触发者是**模型**（工具调用）；
- goal 的触发者也是**人**（`/goal`），之后的推进才是系统。

把它们串成"自动流水线"，等于让 harness 替人决定"什么时候该规划、规划到什么粒度"。这与前面几篇反复出现的取向一致：**把判断留给模型或人，harness 只提供原语**。


## 5. 边界与坑

| 机制 | 坑 | 后果 |
| --- | --- | --- |
| Plan 模式 | `shell` 没被 deny | 仍能跑 `sed -i`、`git apply`，甚至 `cat > file` |
| Plan 模式 | 子代理可能绕开 | 子会话用自己的权限，父的 plan 限制不自动继承 |
| Plan 模式 | 提醒会被压缩/回滚冲掉 | 靠 context 钩子对账，但如果提醒被改写过就认不出 |
| todowrite | 没有任何强制 | 模型可以写一份不执行的清单，也可以永远不更新 |
| todowrite | 旧清单会被压缩 | "当前清单"可能只剩最近一份，更早的不可见 |
| todowrite | 开关只影响注册 | `experimental.todo` 关掉后工具根本不存在；TUI 侧栏却不按它过滤，Web 会 |
| /goal | 每轮一次 judge 调用 | 50 轮就是 50 次额外模型调用，成本要算进去 |
| /goal | 停滞判定是启发式 | "理由相同"或"没调工具"都可能误判，导致提前暂停；计数从第一轮就开始 |
| /goal | 跨进程不续跑 | 重启后 goal 以 paused 回来，需要人 resume |
| /goal | 子会话不继承 | 派出去的子任务不会自己续跑（这是对的，但要知道） |

最值得记住的一条：**这三层都不保证"计划被遵守"**。Plan 模式保证"编辑工具被拒"，todowrite 什么都不保证，goal 只保证"到点会问一次要不要继续"。真正的约束力来自权限，其余都是提示。


## 6. 实践建议

**按"你想约束什么"选机制**，而不是按"看起来高级"：

| 你想… | 用 |
| --- | --- |
| 先讨论、别动代码 | 切 plan agent（Web 需先在设置里打开 Show agent） |
| 让进度可见、别漏步骤 | 让模型用 todowrite（或在提示里要求） |
| 让它自己跑很久直到某个条件成立 | `/goal <objective>` |
| 禁止它改某类文件 | 权限规则（不是 plan 模式） |
| 两个会话并行不打架 | 按目录拆任务 / worktree |

几个常见误用：

- **把 plan 当沙箱**：它只拦编辑工具，不拦 shell。
- **把 todo 当验收**：清单写 completed 不代表真的完成，验证要靠测试或 diff。
- **把 goal 当无限续跑**：50 轮、3 次停滞、30 分钟等待，任一触发就停。
- **在 goal 里放模糊目标**："优化一下"会让 judge 每轮都说 continue，然后耗尽轮次；目标要可判定。

反过来说，最有效的组合是：**用 plan 把方案谈清楚，用 todo 把步骤固定下来，再用 goal 盯一个可判定的完成条件**。三者各管一段，谁都不越界。
