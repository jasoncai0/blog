> 原文的结论一句话：生产里跑得好的 agentic 系统，多数没有用复杂框架，而是把几个简单模式拼起来。复杂度本身不产生效果，能证明它带来更好结果时才加。下面按「先问要不要、再问用哪种」的顺序重排原文，把五种工作流的边界和 agent 的代价放在一起看。

原文 2024 年 12 月发布。页首现在多了一段 2026 年的说明，指文中工具生态已经变化，并给了一个新链接（Claude Managed Agents）。这篇整理的是原文的架构判断；文中举的工具和模型版本只作当时语境。

## 1. 两个词先分开：workflow 与 agent

Workflow 里，LLM 和工具由**预定义的代码路径**编排。谁先谁后、什么条件走哪个分支，写在代码里。Agent 里，LLM **自己决定**过程和工具用法，代码只提供循环和边界。

一个可操作的判断：把 LLM 拿掉，系统还能不能跑？workflow 能，路径还在，只是每步没人执行；agent 不能，下一步是什么取决于模型的输出。

这个区分决定了三件事。

1. **可预测性。** workflow 的调用次数和路径在写代码时就定了，能估延迟和成本；agent 要跑起来才知道会调几轮。
2. **调试入口。** workflow 出错先看代码路径，agent 出错先看 transcript：模型当时看到了什么、为什么选了这个工具。
3. **失败代价。** workflow 单步失败可以重试或回退；agent 的早期误判会沿着后续步骤放大。

原文把两类统称 agentic system，但坚持在架构上分开。混着叫的后果是拿 agent 的灵活性去要求 workflow，或者用 workflow 的可预测性去承诺 agent。

混合结构按节点判：外层路径写死、里面挂一个 agent 节点，整体仍算 workflow，那个节点单独按 agent 对待。判断落在出问题的那一环，不用给整条链路贴一个标签。

## 2. 复杂度阶梯：默认停在最低一档

原文的建议是先找最简解，只在需要时加复杂度。Agentic 系统用延迟和成本换任务表现，这笔交易不是所有场景都划算。很多应用把单次调用加检索、加几个 in-context 示例就够。

{{< fig "diagrams/01-ladder.svg" "四档复杂度各自的形态，以及从下一档升上来的信号；多数任务停在第一档，加层要有可测的理由" >}}

四档从低到高：

1. **单次调用。** 一个提示词，加检索结果和少量示例。适合分类、抽取、改写、带资料问答。
2. **增强 LLM。** 同一次调用里给模型工具、记忆、检索接口，由它决定用哪个。适合需要外部事实或要执行动作的任务。
3. **工作流。** 代码写死路径，下一节的五种拓扑。适合步骤固定、能拆、每步可校验的任务。
4. **Agent。** 模型在循环里决定下一步，靠环境反馈推进。适合步数无法预知、路径无法硬编码的任务。

升级信号也在图里：单次回答缺外部事实或做不了动作，升到第 2 档；步骤固定且能拆，升到第 3 档；步数无法预知、必须按环境反馈改计划，才到第 4 档。

有一个反直觉的点：从第 2 档到第 3 档不一定提升效果。工作流把任务拆小，每步更容易，但拆错边界会丢上下文。原文的说法是「用延迟换准确率」，前提是拆分本身合理。拆完每步都答不准，说明拆错了，不是模型不行。验证方法是同一批样本跑整段和拆步两种，逐步比准确率：中间步骤掉下去、末端也补不回来，才是拆错；只有末端差、中间稳，多半是这一步本身难。

## 3. 唯一的积木：被增强的 LLM

所有模式的最小单元是同一个东西：LLM 加检索、工具、记忆。原文叫 augmented LLM。后面的链式、路由、并行、agent 循环，都是这个单元的不同接法。

两个实施重点：

1. **能力按场景裁剪。** 给模型十个用不上的工具，等于给它十种选错的机会。工具表的每一项都在占用上下文和注意力。
2. **接口要好读、有文档。** 原文把这件事单列在附录里讲，因为它比换模型更能决定成败。

MCP 是原文给的一种接法，不是唯一接法。它解决的是「工具从哪来、怎么接」，不解决「工具描述怎么写」，后者在第 7 节。

### 框架不是必需品

原文列了几个框架（Claude Agent SDK、AWS 的 Strands、Rivet、Vellum），紧接着给了一条相反的建议：先从 LLM API 直接写起，很多模式几十行代码就能实现。

理由有三个：框架多一层抽象，提示词和响应被藏在里面，出问题难查；抽象层会让人不自觉地加复杂度；对底层行为的错误假设，是客户报障的常见来源。真要用框架，先读一遍它替你发出去的那个请求。

## 4. 五种工作流

五种拓扑的共同点：路径由代码写死。区别在「怎么拆」和「拆完怎么合」。

{{< fig "diagrams/02-workflows.svg" "五种工作流的控制流：拆法、合点、以及子任务是否预先确定" >}}

### 4.1 提示链：把大任务拆成固定顺序的小任务

每次调用处理上一次的输出。中间可以插程序化校验（gate），不通过就回退或终止。原文图里那个 gate 是关键：它是代码，不是模型。

适合任务能干净地拆成固定子任务，且每一步单独做比一次做完更准。原文的例子是先写营销文案再翻译；先出大纲，检查大纲是否满足条件，再按大纲写正文。

代价是串行，延迟叠加。gate 设计得太严会把正确结果挡在外面，太松等于没有。

### 4.2 路由：先分类，再交给专用流程

一个分类步骤把输入分到不同分支，每个分支有自己的提示词、工具和模型。分类器可以是 LLM，也可以是传统分类模型。

适合类别清晰、分类准确率可接受的任务。原文的例子是客服请求分到退款、技术支持、一般咨询；简单问题走小模型，难问题走大模型。

代价是分类错了后面全错。要留一个「分不清」的兜底分支，不要把每个输入都硬塞进某一类。

### 4.3 并行：分段求速度，投票求置信度

两种用法。

1. **分段。** 任务拆成互不依赖的子任务同时跑，最后程序化合并。例子：一个模型回答用户，另一个模型同时做内容审核；多个调用分别评估回答的不同维度。
2. **投票。** 同一个任务跑多次，按多数票或阈值决定。例子：多个提示词分别找代码漏洞；多个角度判断内容是否违规，用不同阈值平衡误报和漏报。

适合子任务能并行，或需要多视角提高置信度。原文有个经验：复杂任务涉及多个考量时，让每次调用只关注一个考量，通常比一次全考虑更准。

代价是 token 成倍，合并逻辑要自己写。合并不好，并行等于把一个问题变成三个问题。

### 4.4 编排者-工作者：子任务运行时才定

一个中心 LLM 拆任务、派给 worker、汇总结果。

它和并行长得像，区别在子任务什么时候定：并行是预先定义的，编排者-工作者是运行时由编排者看输入决定。原文特意点出这一点，因为两者画出来几乎一样。

适合无法预知要改几个文件、查几个来源的任务。原文的例子是跨多个文件的代码修改，以及多来源检索后汇总。

代价是编排者会拆错、漏派、重复派。worker 之间不共享上下文，汇总时容易丢细节。可行的做法是给 worker 定返回契约：结论在前，证据和原文另起字段；编排者只拿摘要汇总，要原文时按字段回查。

### 4.5 评估者-优化者：生成和评审分成两个角色

一个调用生成，另一个按标准评估并给反馈，循环到通过或达到轮数上限。

原文给了两个适合信号：人给出反馈后回答能明显变好；LLM 能给出这种反馈。两个都成立才值得做，缺一个就会变成两个模型互相客气。判断「LLM 能给出这种反馈」看两点：评语能指到具体位置，改法能直接执行；只给「还行」「可以更好」，循环就是在烧钱。

例子是文学翻译的细节打磨，以及需要多轮搜索才能覆盖的复杂检索，由评估者决定要不要继续搜。

代价是成本随轮数增长。轮数上限不设，一个没通过标准的回答能让循环跑到预算耗尽。

## 5. Agent：把决定权交给模型

Agent 和 workflow 的分界是控制流归谁。Agent 的典型实现很短：一个循环，模型看环境反馈决定下一步调什么工具，直到没有工具调用或触发停止条件。

{{< fig "diagrams/03-agent-loop.svg" "一次 agent 任务里谁在什么时候做决定：模型选工具、环境给反馈、人只在检查点介入" >}}

三样东西决定它能不能用。

1. **ground truth。** 每一步都要从环境拿真实结果：工具返回、测试输出、页面状态。拿不到真实反馈的 agent 是在猜，猜得越久越难纠正。
2. **停止条件。** 最大轮数、预算、超时。原文明确说这是维持控制的手段，不是可选的装饰。三个条件任一触发即停，已产出的中间结果标成未完成、转人工，不要当成交付物。
3. **人工检查点。** 遇到阻塞、要做不可逆动作、需要判断时停下来问人。agent 可以独立跑，不等于应该无人值守。

适合的任务：步骤数无法预知、路径无法硬编码、允许模型多轮试错、环境可信。

代价有三项：成本随轮数增长；错误会累积，第 3 步的误判到第 10 步可能已经改不回来；调试从读代码变成读 transcript。原文的建议是先在沙箱里大量测试，再加护栏。SWE-bench 编码 agent 和 computer use 是两个已公开的例子。

## 6. 选型：四个问题决定停在哪一层

把原文散在各节的「什么时候用」收成一条判断链，按顺序问，先答「是」的先停。

{{< fig "diagrams/04-choosing.svg" "四个问题筛出该停在哪一档：单次调用、工作流、编排者-工作者，还是 agent" >}}

1. **单次调用加检索、示例够吗？** 够就停，别搭工作流。
2. **步骤能提前写死吗？** 能，进第 3 问；不能，进第 4 问。
3. **子任务的数量和内容随输入变化吗？** 变，用编排者-工作者；不变，在五种固定工作流里按形状选：串行用链式，分类用路由，独立用并行，有明确评分标准用评估者-优化者。
4. **需要按环境反馈多轮改计划吗？** 需要，用 agent；不需要，先把任务拆小，回到第 2 问。

四个问题问的是同一件事：控制流能不能提前确定。能，就写进代码；不能，才交给模型。原文没有给这张图，这条链是我按它的判据排的。

## 7. 工具接口：ACI 是新的 HCI

原文附录 2 的观点：工具定义要和提示词一样认真写。作者在 SWE-bench agent 上花在工具上的时间，比花在总提示词上的还多。

一个具体例子。agent 切换工作目录之后，用相对路径的工具开始出错。改成强制绝对路径，错误消失。这不是模型变聪明了，是接口把出错的空间去掉了。

三条建议：

1. **给模型留思考的 token。** 让它先写计划再写结果，别逼它一次写对。
2. **格式贴近自然文本。** diff 要求写代码前先算行号，JSON 里的代码要转义换行和引号，这两类额外负担都会变成错误。
3. **Poka-yoke。** 参数设计成难以用错：必填、绝对路径、枚举代替自由字符串、一个工具只做一件事。

自检方法：把自己当第一次用这个工具的初级工程师，看描述能不能直接上手；拿一批真实输入在 workbench 里跑，统计模型犯的错，再改描述和参数。

| 失败模式 | 接口上的修法 |
|---|---|
| 切目录后相对路径失效 | 参数只收绝对路径 |
| 同一动作有多种写法，模型选错 | 只暴露一种，其余封装进工具内部 |
| 参数含义靠猜 | 描述里写例子、边界、和相邻工具的区别 |
| 一次调用要做太多事 | 拆成多个小工具，名字用动词开头 |

## 8. 两个已被验证的场景

原文附录 1 给了两个场景，判断标准相同：对话加动作、成功标准清楚、有反馈回路、人能在关键点介入。

1. **客服。** 对话是天然形态；工具有客户数据、订单、知识库；动作有退款、改工单。成功可以用「问题是否解决」度量，所以有公司按解决结果收费。
2. **编码。** 测试是免费的验证器，agent 能用测试结果迭代；问题空间结构化，质量可客观测量。SWE-bench Verified 上能只凭 PR 描述解决真实 issue。测试通过不等于方案对，人工 review 仍然必要。

这两个场景的共同点是有便宜的验证信号：客服靠用户确认解决，编码靠测试。换成没有验证信号的领域，agent 的循环就失去了纠错依据。

## 9. 三条原则

1. **简单。** 能一次调用解决就不搭工作流；能写死路径就不交给模型。
2. **透明。** 把规划步骤显式展示出来。出问题时，人能看到 agent 当时在想什么。
3. **认真做 ACI。** 工具的文档和测试按产品接口的标准做，不是按「能跑就行」的标准。

原文最后一句值得单独抄下来：先在简单提示词上做评测，简单方案不够时再加多步系统。加之前先量。

## 10. 边界：原文没回答的

1. **没有数据。** 五种模式各自的成功率、成本倍数、延迟，原文都没给。它是一篇模式分类，不是 benchmark 报告。
2. **评测只说了要做。** 怎么做评测集、怎么定 rubric 没展开。实际落地时，评测往往比选模式更花时间。
3. **上下文管理没讲。** agent 跑多轮之后 context 会胀，压缩、剪枝、外部记忆都不在原文范围内。
4. **多 agent 协作没讲。** 编排者-工作者是最接近的一种，但 worker 之间不通信，也不共享状态。
