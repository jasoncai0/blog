## 一、原理：模型凭什么会调工具

这三道是地基。答不好这一层，后面所有协议都只是在背名词。

### Q1 什么是 Function Calling？原理是什么？

Function Calling 是模型输出结构化调用请求、宿主执行、结果回填后再生成的一套机制。开发者用 JSON Schema 描述工具，模型判断需要时不再输出自然语言，而是输出 `tool_calls`，说明调哪个函数、参数是什么；宿主代码执行，把结果塞回对话，模型基于结果给出最终答案。

整个流程是两轮对话：第一轮模型说「我要调这个」，宿主执行，第二轮模型拿到结果说「答案是这个」。核心分工只有一句：模型只做决策，执行一律由宿主完成。模型从来没有直接联网或直接跑代码的能力，它输出的是一段 JSON，真正发生副作用的是你写的那段执行代码。

工具定义的每个字段都影响选择。名字决定模型怎么称呼它，描述决定模型什么时候想到它，参数 Schema 决定它能填对多少，必填项和枚举决定校验能不能拦住。名字含糊、描述写成文档摘要，是选错工具最常见的原因。

常见追问：
1. **并行调用怎么处理？** 一轮里返回多个 tool_calls，宿主并发执行，按 call_id 一一对应回填。有依赖关系的调用不能并行，得靠下一轮。
2. **和普通 JSON 输出的区别？** 普通输出是内容，模型可以随便写；tool_calls 是结构化的动作意图，有 schema 约束、有 id、由宿主执行。前者给人看，后者给程序用。

### Q2 LLM 是怎么学会调用外部工具的？

靠两个训练阶段，加上运行时的一套拼接流程。预训练只教会模型预测下一个 token，工具调用要求输出可解析的结构化 JSON，这个模式在预训练语料里基本不存在，参数量再大也不会自动涌现。

第一阶段 SFT：喂大量「工具定义 + 用户问题 + 应输出的调用 JSON + 执行结果 + 最终答案」的完整样本，让模型模仿这套流程。第二阶段 RLHF：人类标注哪种回答更好，训练奖励模型，再用它调整主模型，学会「能直接答就别调工具」的边界感。一句话：SFT 教会不会调，RLHF 教会该不该调。

训练数据要覆盖的场景比想象中多：单工具、多工具并行、调用失败后重试、不需要工具直接回答、多轮对话里的连续调用。缺哪一类，线上就在哪一类翻车。

常见追问：
1. **为什么 SFT 之后模型会滥用工具？** SFT 是模仿，样本里调用出现得越多，模型越倾向调用。RLHF 用偏好数据把「该答的时候答」拉回来。
2. **运行时还要做什么？** 把工具 Schema 拼进 system 或 tools 字段，解析返回的 tool_calls，执行后按 call_id 回填。训练决定能力上限，运行时决定这一次能不能用对。

### Q3 Function Call 能力具体是怎么训练出来的？两个阶段各管什么？

SFT 管「会不会」，RLHF 管「该不该」，两件事的失败表现完全不同。SFT 没做好，模型输出不了合法 JSON，或参数填得离谱；RLHF 没做好，JSON 很漂亮但该答的时候去调工具、该调的时候不调。

SFT 的数据构造有三个要点：样本必须包含完整的工具定义（否则模型学不会读 Schema）、必须包含执行结果（否则学不会用结果）、必须包含「不需要调用」的负样本（否则学不会停）。只看正样本训出来的模型，遇到什么问题都想调一次。

RLHF 阶段的数据来自人工对比：同一个问题给两个回答，一个直接答、一个调工具，标注哪个更好。奖励模型学到的是「什么时候值得付一次调用的成本」，包括延迟、失败风险和用户等待。

常见追问：
1. **为什么不直接用强化学习从零训？** 从零探索的搜索空间太大，且工具调用有明确格式，SFT 先把分布拉到位，RL 只做微调。
2. **小模型能做工具调用吗？** 能，但要专门蒸馏或微调。通用小模型在「选对工具 + 填对参数」上掉得比大模型快。

### 跨题追问：原理与训练（本节 12 条）

- **模型真的能自己访问网络吗？** 不能。它输出的是调用请求，联网发生在宿主进程里。把「模型会调工具」理解成「模型会上网」，后面所有权限设计都会做错。（第 1 篇第 2 问）
- **为什么不能让模型直接输出一段代码去执行？** 可以，但那就变成代码执行而不是工具调用，校验、权限、审计全要重做。工具调用的价值是参数有 Schema、动作有边界。（第 1 篇第 3 问，合并第 1、21 篇）
- **工具名和描述哪个更重要？** 描述。名字只用于称呼，描述决定模型在什么场景想到它。描述写成「查询数据」，模型就只能靠猜。（第 1 篇小节设问）
- **Schema 里哪些字段最影响成功率？** 参数描述、枚举、必填项。枚举把开放填空变成选择，必填项让校验能拦住缺参。（第 1 篇小节设问）
- **一次调用到底几轮对话？** 两轮起步：请求 + 结果。工具链更长时按需要增加，每一轮都可能并行多个调用。（第 1 篇小节设问）
- **模型输出非法 JSON 怎么办？** 宿主侧先做 Schema 校验，把具体错误回给模型重生成，别直接抛给用户。重试两次仍不合法就降级或转人工。（第 18 篇第 2 问）
- **预训练和微调的边界在哪？** 预训练学语言和世界知识，微调学格式与偏好。指望预训练学会 JSON 调用格式，等于指望它学会一种语料里没有的方言。（第 2 篇第 2 问）
- **RLHF 的奖励模型会不会把模型带偏？** 会，标注标准不一致时尤其明显。所以工具调用的偏好数据要看结果对不对，不只看话说得顺不顺。（第 2 篇第 3 问）
- **训练数据里的失败样本怎么造？** 真实线上回放加人工构造：缺参、类型错、超时、权限拒绝、业务失败各造一批，让模型见过错误的形状。（第 3 篇第 3 问）
- **为什么很多模型在中文工具名上表现差？** 训练分布里英文工具多，中文名和描述会被切成更碎的 token，语义对齐更弱。命名用英文、描述用中文是常见折中。（引申）
- **工具调用能力会随模型升级自动变好吗？** 格式类的能力会，选型和边界感不一定。换模型必须重跑工具选择评测集，不能假设只升不降。（引申）
- **能不能用提示词替代训练？** 能凑合，把 Schema 和示例写进 prompt，小规模可用。工具一多、场景一杂，提示词就撑不住稳定性和 token 成本。（第 2 篇第 4 问）

## 二、MCP：协议与组成

这两道是协议题的门槛。答不出三层结构，后面的选型和排障都无从谈起。

{{< fig "diagrams/02-mcp-call.svg" "一次 MCP 调用：模型只输出 tool_call，宿主校验权限，Client 转发，Server 执行，结果按 call_id 回填。整个过程里模型没有碰过任何外部系统。" >}}

### Q4 什么是 MCP？它的核心内容有哪些？

MCP（Model Context Protocol）是一套让 AI 应用接入外部工具与数据的开放协议。它统一了能力发现和调用方式：工具实现一次，任何兼容 MCP 的宿主都能直接接上，不用每家重写一遍对接代码。

核心内容分三层。角色层：Host 是 AI 应用本身，负责模型交互、上下文和权限；Client 是 Host 内部的通信组件，一个 Client 对接一个 Server；Server 提供外部能力。一个 Host 可以同时挂多个 Server。能力层：Tools 是可调用的功能，Resources 是只读的上下文数据，Prompts 是预定义的提示模板。协议层：消息用 JSON-RPC 2.0，传输支持 stdio（本地子进程）和 Streamable HTTP（远程服务）。

一次调用把这些层串起来：模型通过 Function Calling 提出工具名和参数，Host 检查授权，经 Client 用 JSON-RPC 请求 Server 执行，结果回给模型生成回答。所以 MCP 不是替代 Function Calling，它跑在 Function Calling 之上。

常见追问：
1. **Tools 和 Resources 怎么分？** Tools 是模型主动调用的动作，Resources 是宿主或应用读取的上下文。标准答案是看谁发起、要不要参数、有没有副作用，不是单纯看读还是写。
2. **Prompts 为什么也算能力？** 它把「这一类任务的提问模板」也标准化了，宿主可以直接取来用，不必在代码里硬编码提示词。

### Q5 MCP 由哪几部分组成？

三层：角色、能力、协议。缺一层，答案就只答了半个 MCP。

角色层三个角色职责不同：Host 是宿主应用（Claude Desktop、Cursor、IDE 插件），管模型、上下文、权限和用户交互；Client 是 Host 内的通信模块，一对一连接某个 Server，负责握手、请求、通知；Server 是工具提供方的独立进程或服务，暴露能力并执行。

能力层三类：Tools（可调用的函数，可只读也可写）、Resources（可读取的数据，用 URI 标识）、Prompts（提示模板）。人们常把「有没有副作用」当成 Tools 和 Resources 的分界，这是错的：一个只读的搜索工具仍然是 Tool，因为它由模型主动调用；一份被写进上下文的文档仍然是 Resource，即使它来自数据库。

协议层两件事：消息格式 JSON-RPC 2.0（请求、响应、通知，带 id 对应），传输方式 stdio 或 Streamable HTTP。2024-11-05 版的远程方案是 HTTP+SSE 双端点，2025 年 3 月被标记为 deprecated，新项目用 Streamable HTTP。

常见追问：
1. **一个 Host 连多个 Server，Client 是一对多吗？** 不是。一个 Client 对应一个 Server，Host 管多个 Client。这个设计让连接状态和权限边界清晰。
2. **Server 一定要单独部署吗？** 不必。本地工具做成子进程由 Host 启动即可；要被多个宿主共享时才独立部署成 HTTP 服务。

### 跨题追问：MCP 协议（本节 12 条）

- **MCP 解决的具体痛点是什么？** 每接一个工具就要写一套对接代码。MCP 把「能力描述 + 调用方式」标准化，接一次到处能用。（第 4 篇第 1 问）
- **为什么用 JSON-RPC 不用 REST？** 双向、轻量、天然支持请求-响应与通知，还能承载流式。工具调用不是资源增删改，REST 的语义套不上。（第 4 篇小节设问）
- **stdio 和 HTTP 怎么选？** 本地进程、延迟敏感、不想开端口用 stdio；要多人共享、要独立部署和扩缩容用 Streamable HTTP。（第 13 篇第 2 问）
- **协议版本不一致会怎样？** 新客户端连老服务端，初始化阶段的 capabilities 对不上，可能出现「教程里能跑、我这里报错」。先看双方声明的版本和能力。（第 4 篇小节设问）
- **MCP Server 要不要做鉴权？** 要。协议本身不管授权，Host 负责权限判断，远程 Server 还要自己做 token 校验和租户隔离。（第 4 篇小节设问）
- **Resources 的 URI 有什么用？** 它让「读哪份数据」变成可寻址的动作，宿主能精确注入上下文，而不是把整个库塞给模型。（第 5 篇小节设问）
- **Prompts 会不会让提示词更难维护？** 会分散，但换来跨宿主复用。团队要做的是版本管理和评审，不是禁止使用。（第 5 篇小节设问）
- **MCP 会不会成为厂商锁定？** 协议是开放的，风险在实现：某些 Server 只对特定宿主开放能力。选型时看 Server 是否独立可测。（第 9 篇第 3 问，引申）
- **一个 Host 挂太多 Server 有什么问题？** 工具数量爆炸、上下文膨胀、启动变慢。要配合路由和按需启用，不是挂得越多越强。（第 17 篇第 1 问）
- **MCP 的「初始化」为什么要单独一步？** 双方要协商版本、能力和传输参数，后续请求都建立在这个协商结果上。跳过初始化直接发请求，只在兼容模式下侥幸可用。（第 4 篇小节设问）
- **Server 崩了 Host 会怎样？** 取决于 Client 的实现，好的实现会隔离故障、标记该 Server 不可用，而不是整场对话失败。（第 18 篇第 4 问，引申）
- **本地 stdio Server 能访问文件系统，安全吗？** 能，而且默认继承宿主权限。想隔离得靠容器、低权限用户和只读挂载，协议本身不提供沙箱。（第 21 篇第 3 问）

## 三、MCP 与 Function Calling：层次、选型与冲突

这三道最容易被答成「两个竞品」。真正的答案是层次不同，而且互相依赖。

### Q6 MCP 和 Function Calling 有什么区别？

不是竞争关系，是两个层次。Function Calling 是调用语言，定义模型怎么表达「我要调哪个函数、参数是什么」；MCP 是工具生态协议，定义工具怎么打包、注册、被发现和调用。

MCP 底层仍然靠 Function Calling 驱动：模型照样输出 tool_call，只是这个调用由 Host 翻译成 JSON-RPC 请求发给 Server。所以 MCP 不是替代 FC，而是在 FC 之上加了工具管理和复用的一层。

打个比方：Function Calling 像 HTTP 请求的格式，MCP 像 REST 的设计规范加服务注册发现。前者规定一句话怎么说，后者规定服务怎么被找到、怎么被复用。

常见追问：
1. **那 MCP 是不是让 FC 变得不重要了？** 相反，模型不会 FC，MCP 就用不起来。协议解决连接，调用还是要模型表达。
2. **实际接一个 MCP Server 要写多少代码？** 配置里加几行（命令、参数、环境变量），宿主自动发现工具。这也是它相对手写 FC 的主要收益。

### Q7 什么场景用 Function Calling，什么场景用 MCP？

判断标准只有一句：这项能力会不会在这个应用之外被用到。会，就值得封装成 MCP；不会，直接 FC 更省事。

Function Calling 适合：单个应用内的一两个工具、场景临时、不需要跨项目复用、团队不想引入额外进程和配置。MCP 适合：工具要跨项目或跨团队复用、工具数量多到管理麻烦、社区已有现成 Server、在做多工具 Agent 系统。

常见追问：
1. **项目大就一定要用 MCP 吗？** 不一定。规模只是因素之一，还要看复用范围、部署约束和团队维护能力。内部专用的大项目，手写 FC 反而更可控。
2. **两者能混用吗？** 能，而且常见。核心业务工具走 MCP 标准化，临时工具直接 FC，宿主统一管理两类来源。

### Q8 为什么有些推理模型不支持 MCP？

因为推理模型的生成范式和工具调用天然冲突，而 MCP 又依赖 Function Calling，所以连带着用不了。

推理模型先连续生成一段思维链再给答案，这段 thinking 不能中途打断。工具调用恰恰要求中途暂停：输出请求、等外部执行、拿结果再继续。在思维链中途暂停，之前的推理上下文就断了。

后来的折中方案是让工具调用发生在思考阶段结束之后：先完整想完，再进入可以暂停的调用阶段，拿到结果后重新开一段思考。这解释了为什么早期推理模型在 MCP 上不可用，以及现在的模型是怎么绕过去的。

常见追问：
1. **上下文窗口是根本原因吗？** 不是。窗口大小只影响能装多少，冲突在生成范式：能不能在生成中途停下。
2. **不支持 FC 就一定不支持 MCP 吗？** 是。MCP 的工具调用最终仍由模型的 FC 能力触发，底层缺失，上层无从建立。

### 跨题追问：层次与选型（本节 12 条）

- **MCP 是 Anthropic 的私有协议吗？** 不是，规范开放，多家宿主和 Server 实现。生态成熟度不均匀才是真问题，不是锁定。（第 6 篇第 3 问）
- **手写 FC 的维护成本具体在哪？** 每个工具的 Schema、鉴权、错误处理、版本升级都要自己写，工具一多就散落在各个服务里。（第 6 篇第 3 问）
- **社区有现成 Server 时还要自研吗？** 先用，再评估。看它的维护频率、权限模型和是否支持你要的调用方式，别为了可控重复造。（第 7 篇第 3 问）
- **MCP 会不会拖慢一次调用？** 多一层进程或网络，延迟增加通常很小，主要成本在首次握手和工具发现，长连接下可摊薄。（第 13 篇第 2 问，引申）
- **团队只有一个人，值得上 MCP 吗？** 工具少就不值得。MCP 的收益来自复用和标准化，单点场景是纯成本。（第 7 篇第 1 问）
- **怎么向面试官证明「跑过 MCP」？** 说清接了哪个 Server、配置文件里改了什么、遇到什么错、怎么定位。只报名字最容易露馅。（第 6 篇第 1 问）
- **MCP 和普通 HTTP API 的差别在哪？** API 是人或程序调用，MCP 是让模型能发现和调用。差别在能力描述和调用语义，不在传输。（第 5 篇第 1 问）
- **推理模型的折中方案有什么代价？** 工具结果只能在思考段之间插入，无法在推理中途纠偏；多轮调用会把思考切成碎片，成本和延迟都上升。（第 8 篇第 6 问）
- **工具调用要在思考前还是思考后？** 取决于任务：需要外部事实才能推理的，先调；推理后发现缺信息的，后调再补一轮。（第 8 篇第 7 问）
- **为什么早期 o1 这类模型不给工具？** 产品上先保证推理质量，工具会破坏「一次性完整思考」的假设。后来发现真实任务绕不开工具，才做折中。（第 8 篇第 5 问）
- **MCP 和插件系统的区别？** 插件是宿主私有的扩展机制，MCP 是跨宿主的协议。前者绑定生态，后者绑定规范。（引申）
- **未来 FC 会被协议层吸收吗？** 不会。协议再标准化，模型仍要说「调哪个、传什么」，这层表达始终在模型侧。（引申）

## 四、Skill：把工作方法打包

这一段是近一年最容易被问新的地方。四道题其实只回答一件事：Agent 有了工具之后，怎么知道该怎么用。

### Q9 Skill 是什么？

Skill 是把「指令、脚本、模板」打包成一个可复用能力包的机制，关键在于 Agent 能自动发现它、按需加载它、在需要时调用里面的资源。它不是一个文件夹里的提示词，而是一份 Agent 能自己翻阅的操作手册加工具箱。

每个 Skill 是一个目录，核心是 `SKILL.md`：开头用 YAML frontmatter 写名称和描述，后面是正文步骤，还可以带脚本、模板、参考文档。宿主启动时只读名称和描述，形成一份能力目录；模型判断这次任务需要它，才把正文读进上下文，脚本和模板等执行到那一步再取。

和普通 prompt 的差别在发现与加载：prompt 要人记得贴，Skill 由宿主列出、由模型按描述自行选中。同一份 Skill 在十个对话里被复用，写法只有一份，改一次全部生效。

常见追问：
1. **Skill 会更新模型参数吗？** 不会。它补的是当前上下文里的工作方法，模型能力没变，换掉 Skill 就换掉方法。
2. **装了 Skill 就等于会执行吗？** 不等于。加载只是把步骤读进上下文，真正执行脚本仍然要走工具调用，由宿主校验参数和权限。

### Q10 MCP 和 Agent Skill 的区别是什么？

一个给手，一个给手册。MCP 解决 Agent 怎么获得外部能力：把数据库、API、文件系统封装成标准服务，接上就能查、能调、能读写。Skill 解决拿到这些能力之后按什么步骤和标准完成任务：把流程、判定标准、脚本和模板打包。

几个维度对比更清楚。形态上，MCP 是运行中的服务端进程，Skill 是磁盘上的文档包。加载上，MCP 靠协议握手发现工具，Skill 靠元数据目录加按需读正文。失效时，MCP 断连立刻表现为工具不可用，Skill 写错了表现为步骤走偏、标准漏项。维护者不同：MCP 常由平台或工具方维护，Skill 常由业务团队自己写。

实际系统里两者叠着用：Skill 里写「先查订单、再核库存、最后按模板回信」，其中每一步查和写都由 MCP 工具完成。

常见追问：
1. **没有 MCP 能只用 Skill 吗？** 能，Skill 可以让模型用宿主已有的工具或直接生成代码，但能碰到的外部世界受限于宿主给了什么。
2. **有 MCP 还要 Skill 吗？** 工具多、流程长的时候要。工具只告诉你能做什么，不告诉你该按什么顺序做、做到什么程度算合格。

### Q11 Function Calling、Skill、MCP 这三个有什么区别？

三层，从下往上：Function Calling 是调用语言，MCP 是工具通道，Skill 是工作方法。

Function Calling 解决模型怎么把「调哪个、传什么」表达成结构化数据；MCP 解决工具怎么标准化暴露和跨宿主复用；Skill 解决拿到工具后按什么流程和标准完成任务。上层依赖下层：Skill 的步骤里调用的工具走 MCP，MCP 的调用最终由模型的 Function Calling 触发。

一个具体故事串起来：用户说「把上周的退款工单按政策核一遍」。Skill 提供核查步骤和判定表；步骤里的「查工单」调 MCP 的工单 Server；Server 的工具由模型用 Function Calling 发起。三层各管一段，缺一层就有一段要靠人补。

常见追问：
1. **三者能互相替代吗？** 不能。只有 FC 缺工具生态，只有 MCP 缺流程知识，只有 Skill 碰不到外部系统。
2. **学哪个优先级最高？** 先 FC，它是所有工具调用的地基；再 MCP，决定能不能接上真实系统；Skill 是工程化之后的事。

### Q22 Agent 的 Skill 加载机制是如何实现的？

渐进式加载，分三层：元数据常驻、正文按需、资源执行时再取。

第一层，宿主扫描 Skill 目录，只读每个 `SKILL.md` 的 name 和 description，形成一份几十到一两百 token 的目录放进上下文。第二层，模型按任务和描述选中某个 Skill，或用户显式指定，宿主把正文读进来，里面有步骤、检查项、输出格式。第三层，正文提到的参考文档、模板、脚本留在磁盘上，执行到对应步骤时才读或运行。

这个设计解决的是上下文预算问题：装二十个 Skill 不等于二十份手册全进上下文，常驻的只有目录。代价是选择依赖描述质量，描述写得含糊，模型就选不中或选错，所以 description 要写「什么时候用」而不只是「这是什么」。

常见追问：
1. **谁来发现 Skill？** 宿主。它扫描目录、维护目录、按选择读文件，模型只看到目录和选中的正文。
2. **脚本算加载还是执行？** 两件事。读脚本进上下文是加载，运行脚本是工具调用，要过参数校验和权限检查。

### 跨题追问：Skill（本节 14 条）

- **Skill 和「存一段 prompt」到底差在哪？** 差别在发现和加载。存 prompt 要人记得贴，Skill 由宿主列目录、模型按描述自己选，还能带脚本和模板。（第 9 篇第 2 问）
- **Skill 的目录结构长什么样？** 一个文件夹，`SKILL.md` 打头（frontmatter 写名称描述，正文写步骤），旁边放 scripts、templates、references。宿主只认这个约定。（第 9 篇小节设问）
- **为什么描述比正文更重要？** 模型只看得到描述就决定选不选。描述写「处理文档」，等于没写；写「用户要求把 PDF 表格转成结构化数据时使用」才可选。（第 9 篇小节设问）
- **Skill 会不会让上下文更乱？** 会，如果一次加载太多。渐进式加载就是为了避免这点：常驻目录，选中才读正文。（第 22 篇第 2 问）
- **Skill 写错了怎么发现？** 看输出格式和检查项有没有被漏掉。Skill 的失败往往是「步骤跳了」而不是报错，要靠评测集覆盖。（第 9 篇第 3 问）
- **一个 Skill 能调用另一个 Skill 吗？** 能，但要有层级和终止条件。互相调用没有边界，就是另一种死循环。（第 22 篇第 3 问，引申）
- **Skill 该由谁维护？** 业务团队。它写的是业务判定标准，平台团队写不出这些细节，只能提供格式和校验。（第 10 篇第 3 问）
- **MCP 工具和 Skill 会不会重复？** 不会。工具是可执行的动作，Skill 是「什么时候按什么顺序做哪些动作」，同一个工具会被多个 Skill 复用。（第 10 篇第 2 问）
- **为什么 Skill 要作为开放标准发布？** 一家平台的格式没法跨平台复用。标准化的收益和 MCP 一样：写一次，多个宿主认。（第 9 篇第 4 问）
- **Skill 和系统提示词冲突听谁的？** 系统提示词管边界和禁止项，Skill 管流程。冲突时以更严的约束为准，别让 Skill 绕开安全规则。（引申）
- **Skill 能携带可执行代码，安全吗？** 和工具一样，代码执行要过沙箱和权限。Skill 只是分发方式，不是信任凭证。（第 21 篇第 2 问，引申）
- **Skill 加载失败会怎样？** 好的实现是降级到「无此 Skill」并告知模型，差的实现是静默跳过，模型按自己的理解硬做。（第 22 篇第 4 问）
- **怎么评估一个 Skill 好不好？** 同一批任务，有 Skill 和无 Skill 的完成率、返工率、输出格式合规率对比，不看写得多漂亮。（第 22 篇第 5 问）
- **Skill 多了以后怎么管？** 按业务域分组、命名带前缀、定期清理无人使用的。没有治理的 Skill 库，半年后就是一堆没人敢删的文档。（引申）

## 五、通信与传输：消息怎么走

这四道是工程细节题。答对了不加分，答错了会暴露「只会调 API、没排过障」。

### Q13 MCP 协议通常采用什么通信方式？

两种传输，加一种统一的消息格式。本地用 stdio，远程用 Streamable HTTP，消息一律是 JSON-RPC 2.0。

stdio：Client 把 Server 作为子进程启动，通过标准输入输出收发消息。延迟极低，不开端口，不存在网络暴露面，适合本机工具（文件系统、Git、本地数据库）。缺点是只能本机、生命周期跟着宿主。

Streamable HTTP：Server 独立部署成 HTTP 服务，多个 Client 共享，适合团队统一管理工具。它在一个端点上支持请求-响应和流式推送，是 2024-11-05 版「HTTP + SSE 双端点」方案的替代。旧方案在 2025 年 3 月被标记 deprecated，老项目还能跑，新项目别再用。

JSON-RPC 2.0 是消息层：请求带 method 和 id，响应按 id 对应，通知没有 id 不回包。传输方式只决定「怎么送」，消息长什么样与传输无关，这个解耦是 MCP 能换传输而不改生态的原因。

常见追问：
1. **MCP 用 WebSocket 吗？** 不用。本地 stdio，远程 HTTP。需要双向实时推送的场景另说，协议标准里没把 WebSocket 列为传输。
2. **stdio 会不会有安全问题？** 会。子进程默认继承宿主权限，能读写宿主能读写的一切。要隔离得靠低权限用户、容器和只读挂载。

### Q14 WebSocket 和 SSE 的区别及局限？

方向不同：SSE 是服务端单向推，客户端要发消息得另起一个 HTTP 请求；WebSocket 是全双工，两边随时能发。

SSE 建立在普通 HTTP 上，响应头声明 `text/event-stream`，服务端一直写、客户端一直读。优点是轻、走标准 HTTP、天然穿代理、断线自动重连。局限是单向、HTTP/1.1 下同域连接数有限、只能传文本。

WebSocket 通过 HTTP Upgrade 建立独立连接，之后是双向帧。优点是真正的双向实时。局限是有状态：连接绑在某个实例上，横向扩容要做连接路由或共享状态；企业代理和防火墙经常拦；心跳、重连、背压全要自己实现。

选型看交互：模型往外吐 token、用户只是看，SSE 够用，OpenAI 和 Anthropic 的流式接口都是 SSE。用户要在模型说话途中打断、要双向实时，才值得上 WebSocket。

常见追问：
1. **为什么功能更强的 WebSocket 反而没成为主流？** 因为主流场景是单向流式。SSE 的简单和无状态在运维上是实打实的优势。
2. **SSE 断线怎么办？** 浏览器 EventSource 自动重连，配合 `Last-Event-ID` 从断点续传。这比 WebSocket 自己写重连逻辑省事。

### Q15 为什么要用 WebRTC？它和 WebSocket 在 AI 对话流中的核心差异是什么？

核心差异在底层：WebSocket 跑在 TCP 上，WebRTC 跑在 UDP 上。实时语音场景里，TCP 的重传是负担而不是保障。

丢一个 20ms 的音频包，TCP 会等重传，后面的包全被堵住，延迟一层层堆积，通话就卡死了。语音能容忍一点音质损失，不能容忍延迟。UDP 丢了就丢，用插值或 PLC 补一个近似帧，延迟稳定在 50–150ms。

WebRTC 也不只是一个传输协议，它是一套组合：SDP 做能力协商，ICE/STUN/TURN 做 NAT 穿透，内置回声消除、噪声抑制、自适应码率。这些用 WebSocket 全要自己造。OpenAI Realtime API 选 WebRTC，就是因为语音场景的延迟要求 TCP 撑不住。

常见追问：
1. **WebRTC 是 P2P，服务端还要参与吗？** 要。信令、鉴权、模型推理都在服务端，P2P 只是媒体通道的一种可能，NAT 严苛时还要 TURN 中继。
2. **文本对话也需要 WebRTC 吗？** 不需要。文本流没有丢包容忍度的问题，SSE 更简单。

### Q12 A2A 协议是什么？和 MCP 有什么区别？

A2A（Agent-to-Agent）是让多个 Agent 互相发现、委派任务、交换结果的开放协议，由 Google 发布。MCP 是 Agent 连工具和数据，A2A 是 Agent 连 Agent，一个向下、一个向外。

A2A 里 Task 是一等公民：调用方不是「调一个函数」，而是「提交一个任务」，接收方按自己的 Skill 声明承接，可以异步执行、流式推进度、中途要补充信息。配套的是 Agent Card，声明这个 Agent 能做什么、怎么认证、支持哪些交互方式，相当于 Agent 的服务目录。

和 MCP 的关系是纵横两层：MCP 管纵向的能力接入，A2A 管横向的协作编排。多 Agent 系统里两者同时存在，一个 Agent 通过 A2A 接活，干活时用 MCP 调工具。

常见追问：
1. **A2A 会不会取代 MCP？** 不会，方向不同。除非 Agent 之间不再需要工具，否则两套都要。
2. **A2A 的任务和一次 RPC 调用差在哪？** 生命周期。任务可以跑几分钟、可以暂停等输入、可以取消，状态要持久化；RPC 是一次请求一次响应。

### 跨题追问：通信与传输（本节 16 条）

- **MCP 为什么不像普通 RPC 那样只用一个端点？** 它要同时支持本地子进程和远程服务，还要支持流式。消息层统一，传输层分开，才能两种都覆盖。（第 13 篇第 1 问）
- **SSE 被弃用是因为不好用吗？** 不是。双端点方案（一个发请求、一个收流）在实现和部署上麻烦，Streamable HTTP 把两者合到一个端点，是简化不是否定。（第 13 篇第 4 问）
- **stdio 模式下 Server 崩溃怎么感知？** 子进程退出会带退出码，Client 应标记该 Server 不可用并上报，而不是让后续请求一直挂着。（第 13 篇第 2 问，引申）
- **HTTP/2 下 SSE 的连接数限制还在吗？** 多路复用后同域连接上限基本消失，这是 SSE 在生产里更稳的原因之一。（第 14 篇小节设问）
- **SSE 只支持文本，二进制怎么办？** Base64 编码后当文本传，或者换协议。音频视频这类场景本来就不该用 SSE。（第 14 篇第 3 问）
- **WebSocket 横向扩容难在哪？** 连接有状态，粘在某个实例上。要么做连接路由，要么用 Redis 之类的共享通道广播，成本比无状态的 HTTP 高。（第 14 篇第 4 问）
- **企业网络里 WebSocket 为什么容易失败？** 代理和防火墙对 Upgrade 的支持不一致，有的直接断开长连接。SSE 走标准 HTTP，穿透性好得多。（第 14 篇第 4 问）
- **语音场景能不能用 WebSocket 加优化凑合？** 局域网内可以，公网抖动一大就露馅。TCP 的重传机制不是调参能绕过的。（第 15 篇第 2 问）
- **WebRTC 的信令为什么不在协议里规定？** 信令只需双方约定，用 WebSocket、HTTP 都行。协议留白是为了适配不同部署。（第 15 篇小节设问）
- **TURN 中继会不会成为瓶颈？** 会。所有媒体都过中继时带宽成本高，所以要尽量让 ICE 打通直连，中继只做兜底。（第 15 篇小节设问）
- **A2A 的 Agent Card 和 MCP 的工具列表像吗？** 都是能力声明，粒度不同。Card 声明「这个 Agent 能接什么任务」，工具列表声明「能调哪些函数」。（第 12 篇第 2 问）
- **多 Agent 协作为什么不能直接用 MCP？** MCP 是「调用一个能力」，没有任务生命周期、进度回传、取消语义。硬套会把协作写成一场 RPC 编排。（第 12 篇第 3 问）
- **A2A 的鉴权怎么做？** 标准里用 OAuth 2.0 一类的方案声明认证方式，具体实现由双方约定。跨组织协作时这是最容易被忽略的一环。（第 12 篇小节设问）
- **流式传输对 Agent 体验的影响有多大？** 首字延迟是感知延迟的主要来源。同样的总时长，边生成边推和攒完再发，用户感受差一个量级。（引申）
- **为什么大模型 API 都用 SSE 而不用 gRPC 流？** 浏览器原生支持 SSE，gRPC 要 grpc-web 代理。面向 Web 客户端时 SSE 的接入成本最低。（引申）
- **传输层选错会有什么后果？** 不是跑不起来，是延迟和稳定性在高峰才崩。选型时按最差网络条件算，不按演示环境算。（引申）

{{< fig "diagrams/03-cli-vs-mcp.svg" "入口和协议是两个维度：横轴看有几个宿主要接，纵轴看流程长度。四象限里的选择都不影响部署位置。" >}}

### Q19 为什么要把 Agent 的工具执行流程封装成 CLI？

为了把工具从 Agent 里拆出来，让它能被独立运行、独立调试、被多个调用方复用。

直接写个函数听起来更简单，但它绑死在 Agent 进程里：要复现一个问题得重放整场对话，要让脚本或定时任务用同一能力得再写一遍，要单独测某个工具得绕开模型。封装成 CLI 之后，同一套能力有三种入口：Agent 调用、开发者手动跑、CI 或定时任务跑。

对机器友好的 CLI 有明确契约：参数怎么传、结果用什么结构输出、退出码代表什么。这里最容易出错的是「退出码 0 就等于成功」：进程跑完不等于业务成功，业务成功也不等于产物已经生效。所以要做三层：退出码说明执行是否正常结束，结构化结果说明业务状态，产物校验说明副作用真的发生了。

常见追问：
1. **CLI 会增加什么成本？** 进程启动、数据传递、部署打包。高频小调用不值得拆，长流程和重工具才划算。
2. **封装了 CLI 就有权限隔离了吗？** 没有。子进程默认继承宿主权限，隔离要靠沙箱、低权限用户和资源限制。

### Q20 Agent 接入工具时应该选择 CLI 或 MCP？

先分清两件事：执行入口和接入协议。CLI 是入口，MCP 是协议，两者可以组合，不是二选一。

只有一个可控宿主、已有稳定 CLI 时，直接适配最省事：宿主写工具说明，把模型给的参数转成命令行参数，解析输出。这项能力要被多个兼容 MCP 的宿主复用时，MCP 更值：工具描述、参数结构、调用方式由协议统一，别人接一次就能用。

已有 CLI 也能被 MCP 包装：MCP Server 内部调用 CLI，业务逻辑不重写，外面获得标准化发现和调用。反过来，只有 MCP 没有 CLI，调试时就得写一段客户端代码才能复现。

部署位置和协议无关：MCP 可以 stdio 连本地进程，也可以 Streamable HTTP 走网络；CLI 同样可以调用远程 API。所以「本地用 CLI、远程用 MCP」是错的划分。

常见追问：
1. **包装一层会不会多一次开销？** 会，多一个进程或一跳网络。换来的是复用和统一治理，工具越多越值。
2. **协议选对了就够了吗？** 不够。权限、幂等、超时、审计这些和协议无关，选哪个都得自己做。

### Q21 Agent 的代码执行沙箱应该如何设计？

按最小权限给环境，按预算限资源，按生命周期管执行。模型生成的代码一律当不可信代码，不能靠提示词约束。

访问边界：只挂载本次任务的输入且设为只读，给一个临时目录写输出，用低权限身份运行，宿主凭据和管理接口不给代码，网络默认关闭按需开放。资源边界：CPU、内存、进程数、运行时间都要限，而且要作用于整个进程组，只限启动进程的话它 fork 一个子进程就绕过了。隔离强度：容器够用于可信度中等的代码，但它共享宿主内核，面对任意用户代码要评估虚拟机或微虚拟机，代价是启动更慢。

沙箱只管「影响范围」，不管「结果对不对」。任务由沙箱外的运行器管理：准备输入、启动受限执行、超时或取消时杀掉整个执行单元、核对并导出允许的产物、清理环境。业务正确性另做验证。

常见追问：
1. **提示词里写「不要删文件」有用吗？** 没有。操作系统不读提示词，真正拦住它的是挂载权限和用户身份。
2. **超时杀了主进程就够了吗？** 不够。子进程和后台任务会残留，要按进程组或 cgroup 整体回收。

### 跨题追问：接入形态（本节 14 条）

- **工具写成 CLI，模型怎么知道有哪些参数？** 宿主维护工具说明，或在 CLI 里加 `--help` 的结构化输出，由宿主读进来当 Schema。不能指望模型猜。（第 19 篇第 2 问）
- **CLI 的输出该给人看还是给机器看？** 分开。结构化结果走 stdout 或文件，诊断日志走 stderr。混在一起，调用方只能靠正则猜。（第 19 篇第 3 问）
- **一个 CLI 工具该做多细？** 一个命令做一件事，参数语义清晰。做成「万能脚本」的工具，模型填不对参数，人也记不住用法。（第 19 篇小节设问）
- **CLI 也能被远程调用吗？** 能，通过 SSH 或包一层 HTTP。这时候它和 MCP 的差别只剩「有没有标准化发现」。（第 20 篇第 3 问）
- **MCP 包装 CLI 时错误怎么传？** 把退出码、stderr、结构化错误一起映射成 MCP 的错误响应，别只回一句「failed」。（第 20 篇第 6 问）
- **团队里 CLI 和 MCP 并存会不会乱？** 会，如果没有统一注册。做法是同一份能力只留一个权威入口，另一个做适配层。（第 20 篇第 4 问）
- **沙箱里能不能装依赖？** 能，但要预装或从受控源装。允许任意 `pip install` 等于把供应链风险交给模型。（第 21 篇第 3 问）
- **容器逃逸的风险怎么评估？** 看内核共享、挂载方式、capabilities 和 seccomp 配置。默认 Docker 不等于安全边界。（第 21 篇第 4 问）
- **沙箱启动慢怎么办？** 预热池、快照恢复、按任务复用。冷启动几百毫秒在高频场景里就是瓶颈。（第 21 篇第 4 问，引申）
- **代码执行结果怎么判定成功？** 看产物和业务状态，不看退出码。生成了文件要校验内容，调了接口要查外部状态。（第 19 篇第 3 问，引申）
- **沙箱日志要不要留？** 要，而且要和 trace 关联。出事时能还原「哪段代码、什么输入、改了什么」。（第 21 篇第 5 问）
- **为什么很多团队先用 CLI 后来换 MCP？** 早期只有自己用，CLI 够；接入方变多、工具变多，标准化收益才显现。（第 20 篇第 5 问）
- **沙箱能不能直接给模型看文件系统？** 能看只读输入区，不能看宿主目录。给整机等于把权限设计交给运气。（第 21 篇第 2 问）
- **接入形态的选择会反过来影响工具设计吗？** 会。CLI 要求参数扁平、输出结构化，MCP 要求 Schema 精确，两者都会逼你把工具边界想清楚。（引申）

{{< fig "diagrams/04-routing.svg" "工具路由是漏斗：注册表 → 硬过滤 → 粗分类 → 候选检索 → 动态绑定。前两步是确定性的，不能交给模型。" >}}

### Q17 工具很多时，Agent 如何做 Tool Routing，减少 Token 并避免选错工具？

五步：建注册表、硬过滤、粗分类、候选检索、动态绑定。

先把工具注册成可路由的目录：命名空间、标签、适用场景、参数 Schema、权限要求、风险等级、可用状态。每次请求先做确定性过滤，把当前租户、角色、环境、任务状态下不可用的工具直接隐藏，这一步不靠模型。

再做两级召回：一级用规则或小分类模型判断业务域（检索类、订单类、支付类），二级在域内用关键词、BM25 或向量混合检索，召回十几个候选。最后只把候选工具的完整 Schema 绑定给模型，由它判断调不调、调哪个、怎么填参。

两个常见误区。一是把 Tool Routing 和 Multi-Agent Routing 混为一谈：前者决定这个 Agent 此刻能看到哪些工具，后者决定任务交给哪个 Agent，拆了 Agent 之后单个 Agent 里仍然可能有几十个工具。二是「向量搜到就直接调」：相似不等于可调用，权限、状态、参数条件都得先过。

常见追问：
1. **路由错了怎么兜底？** 低置信度时先澄清或扩大召回，不要让模型在高风险工具上猜。没有合适工具时允许拒选。
2. **怎么评估路由质量？** 候选 Recall@K、最终选择准确率、无工具场景的拒选率、参数合法率、Schema token 数，一起看。

### Q18 工具调用格式非法、参数错误、超时或失败时，Agent 如何容错？

按阶段分治：决策、校验、执行、确认、恢复，每个阶段错法不同，处置也不同。

格式和参数错误：Schema 校验拦住，把具体错因回给模型重生成，最多两次，仍不合法就降级或问用户。权限和业务约束：服务端再查一遍，不信任模型自述的权限。瞬时故障（限流、连接失败、部分 5xx）：有界重试，退避加抖动，尊重 `Retry-After`，同时受次数和总时间预算约束。参数错误、权限不足、明确业务失败：不重试，改参数、重新规划或转人工。

最危险的是「结果未知」：发邮件、付款这类操作，超时发生在请求已发出之后。做法是调用前生成幂等键并写 checkpoint，重试和恢复复用同一个键；超时后先按幂等键查状态，确认没执行再决定重试，查不清就暂停转人工。宁可慢一步，不要重复副作用。

常见追问：
1. **为什么不能对所有错误都重试三次？** 下游过载时一起重试会把服务压死。重试只对可安全重放的瞬时故障有意义。
2. **模型修好的参数就一定有权限吗？** 不一定。权限在服务端判，模型只能提议。

{{< fig "diagrams/05-failure-taxonomy.svg" "六类失败的处置不同：格式和参数错误修了再来，权限和业务失败不重试，瞬时故障有界重试，结果未知先查状态。" >}}

### Q16 有没有用过大模型的网关框架？网关层解决了什么问题？

用过 LiteLLM 这类开源网关。它架在应用和模型 API 之间，解决的是「多团队、多模型、多租户」之后的治理问题。

统一接口：业务代码只调一个端点，换模型改配置不改代码。Key 集中管理：密钥只在网关存一份，服务不各自持有，泄漏面小。配额与限流：按团队、按 key 设 token 预算，防止一个服务把额度吃光。成本追踪：每次请求的 token 和花费都记账，能回答「钱花在哪」。故障转移：主模型超时自动切备用。语义缓存：语义相近的问题命中缓存直接返回，省钱也降延迟。安全过滤：统一的输入输出审查，不必每个服务各写一遍。

它和 Nginx 的区别在于懂 LLM 语义：按 token 计量、按模型路由、流式透传、缓存按语义匹配，这些 Nginx 做不了。

常见追问：
1. **网关会不会成为单点？** 会。要部署多实例、做健康检查和超时兜底，关键链路留直连降级方案。
2. **语义缓存的风险是什么？** 相似但答案不同的问题被误命中。阈值要按业务调，敏感场景直接关掉。

### 跨题追问：规模化（本节 15 条）

- **工具注册表里哪些字段最值钱？** 适用场景、权限、风险等级。前两个决定能不能被选中，第三个决定选中后要不要人工确认。（第 17 篇第 2 问）
- **硬过滤会不会误杀？** 会，规则写太严就把可用工具藏了。所以过滤只放确定性条件（租户、权限、开关），语义判断留给召回。（第 17 篇第 3 问）
- **粗分类用模型还是规则？** 能用规则先用规则，稳定且便宜。业务域模糊、说法多样时再上小模型。（第 17 篇第 4 问）
- **候选工具留几个合适？** 十几个到二十个。太少容易漏，太多又回到「Schema 塞爆上下文」。（第 17 篇第 5 问）
- **命名空间怎么写？** `域.对象.动作`，例如 `order.refund.create`。前缀让模型在同类工具里比较，减少跨域误选。（第 17 篇小节设问）
- **工具描述写多长？** 一句话说清「什么时候用」，再一句说「不要用于什么」。写得像 API 文档，模型反而选不准。（第 17 篇小节设问）
- **重试要不要区分工具？** 要。查询类可重试，写入类必须先确认幂等。同一套策略套所有工具是隐患。（第 18 篇第 2 问）
- **幂等键由谁生成？** 调用方生成并持久化，服务端去重。让服务端生成，重试时你拿不到同一个键。（第 18 篇第 3 问）
- **checkpoint 该记什么？** 已完成步骤、产物位置、幂等键、外部副作用的确认状态。恢复时靠它判断从哪继续。（第 18 篇第 4 问）
- **熔断和重试什么关系？** 熔断是重试的上游保护。连续失败到阈值就快速失败，避免把已经过载的下游继续打穿。（第 18 篇第 5 问）
- **降级怎么做才有意义？** 降级要给出可用但更弱的结果，比如只读不写、返回缓存。降到「报错」不算降级。（第 18 篇第 5 问）
- **审计日志记到什么粒度？** 能还原一次调用：工具版本、参数摘要、耗时、重试决策、幂等键、最终状态，敏感字段脱敏。（第 18 篇第 6 问）
- **网关该按 key 还是按团队限额？** 两层都要。key 防单服务跑飞，团队防整体超支。（第 16 篇第 4 问）
- **多模型路由怎么选？** 按任务难度分档：简单任务走小模型，复杂任务走强模型。路由规则要可观测，否则降本变成降质。（第 16 篇第 3 问）
- **没有网关的小团队要不要上？** 一个模型、一个团队时可以不上。多模型或多团队之后，缺网关的成本会以账单和事故的形式出现。（引申）

## 答题模板

22 道背完，落到一个能复用的结构上。工具调用这块面试官考的是边界感，不是协议版本号。

1. 一句话定义，说清它在哪一层、解决谁的问题。
2. 一次调用的数据流，从模型输出到副作用发生，能画出来最好。
3. 一个取舍，为什么不选相邻的那层方案，代价是什么。
4. 一个排障经历，什么错、怎么定位、改完指标怎么变。

四个部分讲完通常两分钟。剩下的时间等追问，追问才是真正打分的部分。

常见翻车点，按被追问的概率排：

1. 只报协议名不讲链路。说「我们用了 MCP」，追问一句「一次调用怎么走」就断。
2. 把四层说成竞品。FC、MCP、Skill、A2A 各在一层，答成「选一个用」直接出局。
3. 说沙箱靠提示词约束。权限和资源限制必须在代码之外，提示词不是安全边界。
4. 把重试当万能药。不区分瞬时故障和业务失败，线上会重复扣款。
