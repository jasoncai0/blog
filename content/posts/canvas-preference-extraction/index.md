用户在一次会话里做了 37 个操作，说了 6 句话。系统要把这些变成 3 条能注入下一轮上下文的偏好。

这件事的难点不在抽取模型。难在每个操作都可能有三四种解释，而用户从不会把解释说出来。下面这套设计按六步走，每一步给出输入、产出和失败点。

文中的阈值、半衰期、置信度先验都是设计默认值。它们是怎么定的，理由写在对应小节里，不代表某条线上数据。

## 0. 先看一次会话

样本来自一次 8 分钟的海报修改。对话 6 轮，画布操作 37 个，导出 1 次。下面是压缩后的样子。

对话：

1. 用户：帮我做一张双十一促销海报，3:4，复古一点。
2. Agent：生成三个版本。v1 满版排版，v2 大留白，v3 大字报。
3. 用户：第二个方向对，但留白太多，标题再大一号。
4. Agent：标题字号 48 改到 56。
5. 用户：那个宋体别用了。
6. Agent：换成思源黑体。
7. 用户：行。底部加个二维码位。以后海报都按这个来。
8. 用户：导出。

操作流（节选 9 条，编号是真实顺序里的第几条）：

| 序号 | 操作者 | 操作 | 参数 |
| --- | --- | --- | --- |
| op 12 | 用户 | 选中 v2 | batch 3 |
| op 15 | 用户 | 移动标题 | +8, −6 |
| op 18 | 用户 | 改字号 | 48 → 56 |
| op 21 | 用户 | 改字体 | 宋体 → 思源黑体 |
| op 24 | 用户 | 删除装饰元素 | 2 个 |
| op 27 | 用户 | 改页边距 | 32 → 48 |
| op 30 | 用户 | 插入二维码位 | 120×120 |
| op 33 | 用户 | 再次改字号 | 56 → 54 |
| op 36 | 用户 | 导出 | PNG 3:4 |

这场会话加上之前两次，一共产出 3 条生效偏好、2 条候选：

1. 版式：标题左对齐，页边距不小于 48，留白率 18% 以上。置信度 0.82。
2. 字体：标题字阶 54/28/14，正文字体思源黑体。置信度 0.86。
3. 禁令：不用宋体。置信度 1.0，不衰减。
4. 结构：底部常驻二维码位。三次海报都加了，置信度 0.60，还在候选。
5. 流程：先看三版再选方向。三个会话都是这样，置信度 0.63，还在候选。

注意两件事。`3:4` 没有进用户偏好，它被记成这个项目的参数，因为一次性任务参数跨项目复用率极低。op 33 把字号从 56 改回 54，说明 op 18 的 56 只是中间值，最终值要取导出时的状态，不能取最后一次修改。

## 1. 结论

1. **先补 `turn_id`，其余都是后话。** 操作流和对话靠它对齐。没有这个键，两路数据只能各自做整会话摘要，做不了归因。补这一列并回填历史，一天。
2. **先上计数器和差分，三周后再考虑 LLM。** 计数器从操作流算分布，差分从 agent 产物和终稿之间挖规则，两者都能人工复核。对话抽取只用来补命名和禁令。
3. **每个操作先归因，再进抽取。** 一次改字体可能是修 agent 的错，可能是试一下，可能是定稿前最后一步。三种情形的证据强度相差 5 倍。
4. **维度先定死，再谈抽取。** 40 个维度写进 schema，结果才能比较、注入、失效。让模型直接写一段「用户画像」，第二周就没法更新了。
5. **稳定判定比抽取本身值钱。** 频次、时间跨度、是否跨项目、有没有反向证据，这四项决定一条观察能不能升级成偏好。
6. **禁令优先处理。** 「不用宋体」这类硬约束误判代价最高，也最好抽：否定词、撤销、重复修正，三个信号里有两个就能定。

## 2. 两路数据各自的缺口

只读对话，会漏掉大部分偏好。用户不会在对话里说「我习惯标题左对齐、页边距 48」，他直接在画布上拖。显式说出口的偏好能覆盖的维度，经验上不到三成。这个数字我没在线上实测过，可以按自己的日志重新数：把每条消息里的偏好声明标出来，看覆盖了几个维度。

对话还有两个问题。修饰词是相对的，「再大一点」「稍微收一收」没有绝对值，必须回到操作流里找它对应到 48 还是 56。模型自己的措辞会污染，agent 说「已采用复古风格」，这句话不能反过来当成用户偏好。

有个具体例子。用户连着三个项目都手动把标题从居中改成左对齐。对话里他没提过这件事，只说「看着不对」。只读对话的系统会记录「用户对标题位置不满意」，下个项目照样先给居中版。读了操作流的系统会记下「标题左对齐」，第一个回合就直接给左对齐版，用户那句「看着不对」就不会再出现。

只读操作，问题在解释不唯一。同一个 move 操作，可能是排版微调，可能是躲开遮挡，也可能是手滑。同一个删除，可能是明确否定，也可能是临时隐藏。

两路合起来才有解释力。对话给出用户自己的用词和意图，操作给出他最终接受的取值。两者冲突时按操作算，但把冲突本身记下来：「用户说复古，实际选的是低密度版」，这条冲突在下一轮生成时应该被优先满足。

## 3. 数据基线

三张表加一个连接键。这套结构决定了后面所有归因能做到多细。

操作事件表 `canvas_op`：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `op_id` | text | 主键，单调递增，用于排序与幂等 |
| `turn_id` | text | 关联到对话轮次，归因的唯一入口 |
| `actor` | enum | `user` / `agent`，反自证靠它 |
| `node_id` | text | 作用对象，跨 op 追踪同一个元素 |
| `kind` | enum | move / resize / style / text / insert / delete / group |
| `before` / `after` | jsonb | 只存被改的字段，不存整个节点 |
| `batch_id` | text | 一次 agent 生成的产物批次，区分 v1/v2/v3 |
| `ts` | timestamptz | 毫秒精度，切分回合要用 |

对话表 `chat_msg`：`msg_id`、`turn_id`、`role`、`content`、`intent`、`slots`、`ts`。`intent` 是粗分类（生成、修改、否定、确认、导出），抽取器要用。

产物表 `artifact_rev`：`rev`、`scene_snapshot`、`export_at`、`export_format`。终稿判定和差值计算都读它。

三张表里最重要的字段是 `turn_id`。它把「用户说了一句话」和「画布上变了 12 个东西」绑在一起。多数设计 Agent 的数据模型里没有这个字段，只有会话 id 和画布版本号，于是只能做「整场会话总结」，无法回答「他这句话导致了哪些改动」。

存储粒度上有一条硬规则：事件表只存改动字段和 id，不存节点正文、不存图片二进制。图片走对象存储，表里留引用。一万个回合大约 120MB，压缩后三十兆左右，滚三十天没问题。把节点全量快照塞进事件表，两周后就要开始删日志，而删掉的那部分正好是归因依据。

## 4. 切回合

回合是归因的最小单位。一个回合从用户提出设计意图开始，到这次产出一个结论（导出、放弃、被新意图替代）结束。

四个边界条件，满足任一条就结束当前回合：

1. 用户发出新意图消息，并且指向不同对象或不同任务。
2. 导出动作发生。
3. 静默超过 90 秒。
4. 会话结束。

还有一种要合并：10 分钟内针对同一对象的连续意图，视为同一回合的延续。用户先让改标题，再说「再大点」，这是两次消息、一个回合。

导出这个边界值得单独说。导出之前的操作都可能还在试，导出之后的操作几乎没有参考价值（用户可能在导出后随手拖一下看效果）。从统计上看，导出前 3 个 op 的证据权重最高，导出后的 op 权重降到十分之一。

回合产出一张 `turn` 表：

```json
{
  "turn_id": "t_20261118_0417",
  "session_id": "s_88f2",
  "intent": "修改既有海报",
  "op_start": 12,
  "op_end": 36,
  "outcome": "export",
  "duration_s": 412,
  "batches": ["b3", "b4"],
  "final_rev": 41
}
```

三种边界情况要单独处理：

1. 跨天挂起：用户开着一个画布，第二天接着说「把标题再改一下」。静默超过 90 秒已经关掉了上一个回合，新回合的起点落在新消息上，`turn` 表里两条记录共享同一个 `canvas_id`。跨回合沿用信号正是靠这个共享关系找。
2. 批量生成：一次生成三个版本（v1/v2/v3），用户选了 v2 去改。v1 和 v3 不进负样本，被丢弃的版本只能说明这一次不合口味，不构成否定证据。只有用户退回并重新生成同一版本时，才算一次弱负向。
3. 撤销跨回合：用户在下一个回合撤销了上个回合的操作。撤销事件记在发生它的回合里，但证据指向被撤销的那个 op，归因时按原 op 的回合计算。这一条如果不处理，前面所有正向证据都会虚高。

切分是流式的，每来一个事件更新一次状态机，回合结束时落一行。单次判定 p95 在 30ms 以内，可以放在操作同步链路里跑，不阻塞用户。

## 5. 归因：四象限加三个修饰项

归因要回答一个问题：这个操作在多大程度上表达了偏好。

先按两个维度分四类。横轴是改动对象的来源（agent 生成的，用户自建的），纵轴是用户对它的动作（保留，改动）。

| | 用户保留 | 用户改动 |
| --- | --- | --- |
| agent 生成 | 采纳，弱正向 | 修正，强负向，且带落点 |
| 用户自建 | 定稿，强正向 | 探索，弱信号 |

「修正带落点」是这套设计里信息量最大的一格。用户把字体从宋体改成思源黑体，`before` 和 `after` 直接给出了偏好的取值，不需要再做语言理解。四格里只有这一格能产出绝对值。

「采纳」要打折。用户没动 agent 的输出，可能是满意，也可能是没看见。所以采纳只在两种情况下计正分：导出时它还在，或者下一个回合里同类元素沿用了同样的设置。

「探索」里的操作基本是噪声。用户在空白画布上试排版，试完撤销，这一串操作对偏好没有信息量。判定方式是看它有没有活到回合结束。

三个修饰项，把四象限的强度再调一档：

1. 撤销：强度 −1.0，是这套系统里最干净的否定信号。用户撤销一次，比说三句「不好看」更确定。
2. 导出时留存：强度 +0.9。活到导出的东西才算定稿。
3. 跨回合沿用：强度 +0.5。下一个回合里同类元素用了同样的设置，说明这个设置被接受了。

合起来，一条证据的强度可以写成：

```
strength = w_quadrant × w_modifier × w_persist
```

给一组默认值：

| 情形 | w_quadrant | 典型强度 |
| --- | --- | --- |
| 修正，且导出时保留 | 1.0 | 0.9 |
| 撤销 | −1.0 | −1.0 |
| 定稿（用户自建且导出时在） | 0.9 | 0.8 |
| 采纳（agent 产物未改，导出时在） | 0.4 | 0.35 |
| 探索（回合内被撤销或替换） | 0.2 | 0.05 |

批量生成要单独说。一次生成三版、用户选了 v2，说明 v2 的属性被接受得更多。处理方式是给 v2 的每个属性记一次采纳，给 v1 和 v3 记 0 分，不记负分。三版都被用户大改过，才说明这一批的方向整体不对，那是提示词层面的问题，不进偏好库。

还有一条反自证规则，必须落在数据层：`actor = agent` 的事件不进入证据表。agent 生成时用了渐变，不能推断用户喜欢渐变。反过来，agent 产物被用户保留，可以算采纳，因为那是用户的选择。

## 6. 三路提取器

三个提取器并行跑，输入不同，先验置信度不同，盲区也不同。它们不互相替代。

| 提取器 | 输入 | 产出 | 先验 | 盲区 |
| --- | --- | --- | --- | --- |
| 计数器 | 操作流 | 分布（字号、色相、对齐、留白率、密度） | 0.9 | 分不清用户偏好和 agent 的一贯做法 |
| 差分规则 | agent 产物与终稿 | `attr: from → to` 及支持度 | 0.7 | 只覆盖被改过的属性，没改的不能推断 |
| 对话抽取 | 会话文本 | 结构化候选加原文引用 | 0.4 | 幻觉、过度概括、相对量词无绝对值 |

**计数器**做的是统计，不做判断。它输出「这个用户的标题字号出现过 14 次，中位数 54，四分位距 6」，不输出「用户喜欢大标题」。命题化留给后面的判定。

计数器有一个坑：如果 agent 每次都默认生成 56 号标题，用户的 14 次里可能有 12 次来自 agent 的默认值。所以计数器必须只统计 `actor = user` 的改动，并且用差分规则校正。

**差分规则**比较两个东西：agent 交付的版本，和用户导出时的版本。对每个属性求差，得到一组 `(attr, from, to)` 三元组。同一个用户身上，某个三元组重复出现 3 次以上，就升成规则：

```
title.font_family: 宋体 → 思源黑体   support 4/4  confidence 1.0
title.font_size:  48 → 54          support 3/5  confidence 0.6
```

支持度直接用次数算，不做平滑。样本少的时候宁可不升规则。

**对话抽取**是唯一用到模型的环节。输入是切好的回合文本，输出是结构化候选：

```json
{
  "dimension": "font.forbidden",
  "value": "宋体",
  "polarity": "negative",
  "scope": "user",
  "quote": "那个宋体别用了",
  "msg_id": "m_0419",
  "confidence": 0.4
}
```

这一步只做两件事：把用户的原话映射到维度，把否定词识别出来。不做「用户是一位注重留白的设计师」这类概括，那种句子没法验证，也没法更新。

三路结果按 `先验 × 证据强度` 加权融合。同一维度上出现相反结论时不合并，两条都留，标 `contested`，等第三条证据。允许长期挂着冲突，比强行投票好：冲突本身告诉注入阶段「这里要保守」。

一个融合的例子。字体维度上，计数器给出「标题字号中位数 54，样本 14 次，先验 0.9」；差分给出「`title.font_family: 宋体 → 思源黑体`，support 4/4，先验 0.7」；对话抽取出「不用宋体，先验 0.4」。三路在字族这件事上同向，做法是取差分给出的具体值（思源黑体），用计数器和对话的结论给它加置信度。

如果对话说的是「要高级一点的字体」，三路就不同向了。差分给出的是具体字族，对话给的是形容词。这种情形下形容词不单独成卡，只作为字族卡上的一个标签，注入时用「思源黑体（用户口中'高级'的那一种）」。

## 7. 维度本体：40 个槽位

抽取结果要能比较、能注入、能失效，前提是维度先定死。自由文本的偏好卡做不到这三件事。

40 个维度分 6 组。每组挑几个代表列在下面，完整表在代码里的 `dimensions.yaml`。

| 组 | 维度 | 观测源 | 取值类型 | 半衰期 |
| --- | --- | --- | --- | --- |
| 版式 | 标题对齐、页边距、留白率、元素密度、栅格列数 | op + 产物 | 枚举 / 数值 | 180 天 |
| 字体 | 字族、字重、字号阶梯、行距、中英混排 | op + 产物 | 枚举 / 数列 | 180 天 |
| 色彩 | 主色相、饱和度区间、背景色、强调色密度 | op + 产物 | 区间 / 枚举 | 120 天 |
| 图像 | 裁切方式、滤镜、素材类型、圆角半径 | op + 产物 | 枚举 / 数值 | 180 天 |
| 流程 | 首版接受率、平均改稿轮次、先改哪个部位 | op | 数值 | 365 天 |
| 语言 | 指令粒度、常用修饰词、禁用语 | 对话 | 文本 / 枚举 | 90 天 |

维度粒度要够细。`font` 一个维度装不下字族、字重、字号三件事，三者变化节奏完全不同：字族几年不变，字号每个项目都在动。混在一起的后果是整条偏好的半衰期取中间值，谁也测不准。

维度也不能太细。120 个维度意味着每条偏好平均只有 3 条证据，永远到不了判定阈值。40 是我的取值，判断依据是：一个活跃用户三周能产出 1200 条左右的证据，均匀分布到 40 个维度是每个 30 条，刚好够做稳定性判定。少于 30 个维度覆盖不了设计场景，多于 60 个维度维护不动。

每个维度在 schema 里写五个属性：`key`、观测源、取值类型、作用域、半衰期。半衰期决定衰减，作用域决定它能不能跨项目复用。

## 8. 稳定判定

一条观察要升级成偏好，得证明它稳定。稳定性用四项加权，再减掉反向证据：

```
S = 0.35·freq + 0.25·span + 0.25·cross_project + 0.15·persist − 0.30·contradiction
```

四项的含义：

1. `freq`：同一维度同一取值的出现次数，按 `min(1, n/5)` 归一。5 次封顶。
2. `span`：首次和最后一次证据的时间跨度，按 `min(1, days/30)` 归一。跨一个月才算稳定。
3. `cross_project`：出现在几个不同项目里，按 `min(1, projects/2)` 归一。只在一个项目里出现的，多半是项目风格。
4. `persist`：导出时还存活的比例，直接用比例值。
5. `contradiction`：反向证据的加权和，归一到 0–1。

阈值两档：

| S | 状态 | 处理 |
| --- | --- | --- |
| ≥ 0.75 | active | 进入注入池，带置信度与证据链 |
| 0.50–0.75 | candidate | 只观察，不注入 |
| < 0.50 | 丢弃 | 归档，不再计算 |

三条特例绕过公式：

1. 硬禁令：否定词加一次撤销，直接 active，半衰期设为不衰减。误判一条禁令的代价太高，宁可直接生效。
2. 任务参数：`3:4`、`800×1200`、`明天要` 这类，进项目作用域，不进用户作用域。
3. 品牌约束：色值、logo 安全区、禁用词属于品牌资产，不进偏好系统。它们由品牌包注入，和偏好走两条不同的路。

拿第 0 节那条字体偏好算一遍。四次改动分布在 28 天里，跨两个项目，导出时四张卡都还在，中间有一条反向证据（某次把字族改回了宋体，但那个项目结束了）：

| 项 | 原始值 | 归一 | 权重 | 贡献 |
| --- | --- | --- | --- | --- |
| freq | 4 次 | 0.80 | 0.35 | 0.280 |
| span | 28 天 | 0.93 | 0.25 | 0.233 |
| cross_project | 2 个 | 1.00 | 0.25 | 0.250 |
| persist | 0.9 | 0.90 | 0.15 | 0.135 |
| contradiction | 0.12 | 0.12 | −0.30 | −0.036 |

合起来 S = 0.862，落在 active 区间，写卡时四舍五入成 0.86。

反向证据的归一方式是加权求和再除以正向证据总量。一次小项目的回退算 0.12，一次明确的用户否定（「别再用这个」）单独走禁令通道，不参与这个公式。

时间衰减按维度的半衰期算，每次判定前对旧证据的权重做一次指数衰减。用户换了工作方向，旧偏好会自己沉下去，不需要人工清理。

## 9. 偏好卡

一条偏好落成一张卡。卡的结构固定，注入时按卡渲染，不做自由文本拼接。

```json
{
  "id": "pref_7f21",
  "dimension": "font.family",
  "value": "思源黑体",
  "polarity": "like",
  "scope": "user",
  "confidence": 0.86,
  "evidence": ["op_0418", "op_0441", "op_0512"],
  "exemplars": ["rev_39", "rev_44"],
  "valid_until": null,
  "contested_with": null,
  "updated_at": "2026-11-18T09:12:00+08:00"
}
```

四个字段是关键。

`evidence` 存 op id 列表，最多 5 条，指向最硬的那几次。用户点开「为什么给我推荐这个」时，展示的就是这几条。

`exemplars` 存 2 张缩略图的版本号。注入时给模型看画面比给一句话有效，也省 token：一张 160px 缩略图约 40 token，比描述「低饱和、米色底、大留白」精确。

`valid_until` 给短期偏好用。项目结束、节日结束、活动结束，这类偏好的有效期可以写死，过期自动失效。

`contested_with` 指向冲突卡。注入时遇到冲突，两条都降权，或者干脆都不注入。

注入形态控制在 60 token 以内，一句话加两个 exemplar：

```
用户偏好：标题字族用思源黑体，字阶 54/28/14。（依据 4 次改动，2 张例图）
```

一个用户通常有 20–40 张 active 卡，全部注入要 2k token 以上，超预算。所以注入阶段按当前回合的任务类型过滤：做海报时只取版式、字体、色彩三组，做详情页时取图像和流程两组。过滤后一般剩 8–12 条，按置信度排序，截到 1.1k token。

冲突要在这里处理。同一维度上有 `contested` 的两条卡，注入时都降到 0.6 倍权重，或者干脆都不注入。前者适合软偏好（留白率），后者适合硬维度（字族），因为两条都注入会让模型自己选一个，结果不可预期。

人在回路只需要一个动作：确认或否定。点否定时把这条卡连同证据一起标 `rejected`，并把它加进负样本，下一轮判定不再提升同维度同取值的卡。

## 10. 冷启动

新用户没有证据，硬凑偏好只会生成噪声。前三个回合只观察，不注入。

第一个项目的冷启动靠三样东西，都不用提问卷：

1. 品牌包：有品牌资产时直接用，色值与字体先按品牌走。
2. 模板三选一：给三个差异化明显的版式让用户选，选中的那个直接产出 6 条初始偏好，先验 0.5。
3. 首版接受与否：第一次生成的产物被保留还是被大改，是信息量最大的一次观察。

第四回合开始注入 candidate，权重打到 0.5，只影响排版建议的语气，不影响硬约束。等到某条卡升到 active 再全权重注入。

项目收尾时问一句「这次的哪些设置下次沿用」，给三个复选框，30 秒能答完。这比在首次使用时填偏好问卷的完成率高得多，因为用户此时已经看到了结果。

## 11. 验证

提取质量不能靠感觉。四个指标加一个人工集。

`gold set`：抽 200 个回合，人工标注出真实偏好，标注一条 40 秒左右，全部标完约 2 天。这 200 个回合是后续所有阈值调整的依据，值得先做。

四个指标：

1. 准确率：抽出的 preference 里有多少是对的。目标 0.85 以上。误报的代价高于漏报，一条错误的禁令会让所有后续生成都避开某个字体。
2. 覆盖率：gold set 里被抽出来的比例。第一版做到 0.6 可以接受。
3. 下游命中率：注入后同类操作次数是否下降。版式类偏好应该让「改对齐」这类操作减少三成以上。
4. 冲突率：同维度长期 contested 的比例。高于 20% 说明维度切得太粗，或者用户在两个项目间风格差异大。

四条线一起看，单独看任何一条都会误判：

| 指标 | 目标 | 怎么量 | 掉下去说明什么 |
| --- | --- | --- | --- |
| 准确率 | ≥ 0.85 | gold set 抽样复核 | 抽取过宽，维度边界模糊 |
| 覆盖率 | ≥ 0.60 | gold set 命中数 / 标注总数 | 维度缺失，或信号采集断了一段 |
| 下游命中率 | 版式类 ≥ 30% 降幅 | 注入组同类操作次数对比基线 | 偏好抽对了但注入位置不对 |
| 冲突率 | ≤ 20% | contested 卡数 / active 卡数 | 维度切太粗，或用户风格本就多套 |

再加一个反事实：随机抽 20% 的回合不注入偏好，比较注入组和对照组的编辑次数与导出率。这是唯一能证明「这些偏好有用」的证据。没有它，你只能证明提取在统计上自洽。

## 12. 成本

按每天一万个回合估算，主要开销三块：

| 项 | 量级 | 说明 |
| --- | --- | --- |
| 事件存储 | 100MB / 天 | 每回合约 10KB，压缩后 25MB，滚 30 天约 750MB |
| 批处理算力 | 90 秒 / 天 | 计数器和差分是纯 CPU，一万回合跑不满两分钟 |
| 对话抽取 | 320 万输入 token / 天 | 只有 40% 的回合带对话文本，每回合约 800 token |

判定和注入几乎不花钱：active 卡总量在几千条的规模，一次判定是全表扫描，毫秒级。

真正容易被低估的是回填。上线那天要把历史数据跑一遍，三个月的画布操作大约是 90 万个 op。按上面的吞吐，重算一遍要 4 小时左右。这个任务要能在后台跑、能断点续跑，否则上线窗口里做不完。

## 13. 六个失败案例

1. **把 agent 的输出当证据。** 现象：第一次生成用了深色背景，系统记下「用户偏好深色」。原因：事件表没有区分 `actor`。修法：在数据层过滤，`actor = agent` 的事件不进入证据表。
2. **用整会话摘要代替回合。** 现象：一场 40 分钟的会话产出 20 条互相矛盾的偏好。原因：没有 `turn_id`，只能把整场对话喂给模型。修法：先补 `turn_id`，按回合抽取。
3. **让模型直接写画像。** 现象：生成的段落读起来很顺，但没法注入、没法更新、没法解释。原因：维度没有定死。修法：先定 40 个维度，模型只做映射。
4. **作用域错层。** 现象：一个项目的节日配色被写进用户级偏好，下个项目全变红。原因：没有区分项目作用域和用户作用域。修法：写入时由调用方显式给 scope，不接受模型推断。
5. **只记正向。** 现象：系统知道用户喜欢什么，不知道他讨厌什么，反复推荐被明确否定的方案。原因：否定信号没进库。修法：撤销和否定词单独建表，优先级高于正向偏好。
6. **维度太粗。** 现象：字体偏好一条卡同时装着字族和字号，改字族的时候字号偏好也被推翻。原因：维度粒度和变化节奏不匹配。修法：按变化节奏拆维度，字族与字号分开。

## 14. 先做三件事

给同样在做这件事的人，按这个顺序：

1. 补 `turn_id` 并回填历史数据，大约 1 天。做完这一件，后面三件才有可能。
2. 上计数器和差分规则，3 天。只统计用户操作，先出一批可复核的分布和规则。
3. 建否定信号表，2 天。撤销、删除、「别用」三类事件单独存，禁令直接生效。

对话抽取和 LLM 归纳可以放到第四周。前面三步产出的数据，正好是训练和评估抽取器要用的标注集。反过来先上模型，你会得到一堆无法验证的结论，还要花更多时间清理。

这套东西接进上下文注入时，和记忆系统其余部分共用一个预算池：偏好卡最多占 1.1k token，超了就按置信度截断。架构那部分在[设计 Agent 的记忆系统](/posts/design-agent-memory.html)里。
