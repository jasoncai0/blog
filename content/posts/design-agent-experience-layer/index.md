设计 Agent 的执行记录里，trace 通常存得下来，归因结论也能写进周报。丢的是中间那段：这次为什么错、错在什么范围、下次在哪个步骤提醒它、什么时候这条提醒该作废。

小林那篇《[Agent 的自进化机制如何实现？](https://xiaolinnote.com/ai/agent/27_self_evolution.html)》把这段拆得比较清楚。原文的主线是：执行记录先变成可核对的失败原因，再写成带范围和失效条件的经验，在决策之前召回，用新任务和反例验证，最后灰度发布、按版本撤回。观点标「原文」，我往设计 Agent 上落的改造标「推断」。

这篇不重讲记忆分层，也不重讲反思回路。[记忆那篇](/posts/design-agent-memory.html)讲的是事实怎么存，反思那篇讲的是经验怎么从一次失败里分叉出来。这里只补设计 Agent 缺的三个接口：**归因要带哪些证据、召回按什么信号、晋升和撤回由什么触发。**

## 1. 原文的六步，落地时缺三样

原文讨论的是 Agent 怎么从自己的执行记录里长出下一次的行为改进。按 RSI 的严格口径，这只是一段经验回路；它要成为 RSI，还得让改进缩短下一代系统的研发周期。先把这段回路做扎实，再谈递归。

原文的回路可以压成六步：

1. 留下执行记录，包括任务要求、当时的规则版本、模型实际做了什么、工具返回了什么。
2. 在固定快照上重跑原动作和修正动作，确认失败原因，不拿线上先后两次查询的差值当证据。
3. 写成经验条目，至少包含适用范围、症状、做法、证据、限制、重新核验条件。
4. 在生成动作之前召回，先按业务范围缩小，再按语义找，最后核对规则版本。
5. 用新任务、换问法、反例和原成功场景做验证，预期结果独立计算。
6. 灰度发布，记录每次任务用了哪条经验、哪个 Prompt/Skill 版本、哪个模型版本，按版本撤回。

这套东西的重心是让一条结论有证据、有范围、有失效条件，不在让模型多反思一轮。原文里那个订单例子很能说明问题：系统约定有效订单只算 paid，六笔里只有四笔 paid，Agent 返回了六。用户说「你查错了」只是错误信号；把原查询和修正查询放到同一份数据快照上逐行对，才能确认原因是状态条件没落到查询里。线上隔一天再查，数值变了可能只是新增了订单。

我的设计 Agent 已经有[七步闭环](/posts/design-agent-self-tuning.html)：采集 trace、判分、归因、生成候选、离线回放、灰度、全量或回滚。归因也要求落四个字段：类、置信度、证据指针、反例检查。但归因输出的是「这一次该改哪个旋钮」；它没有回答「以后遇到同类任务，在哪个步骤提醒」。两者之间少了一个持久对象。

按我在 [RSI 那篇](/posts/rsi-self-improvement.html)里的口径，这套东西仍然属于 B 类：评测门控的策略调优，不是闭环 RSI。它缩短的是经验从产生到生效的时间，模型代际不受影响。把这一点说在前面，后面就不容易把「经验层」吹成「自进化」。

缺的三样，按顺序是：

- **归因证据不够。** 设计 Agent 没有编译器，产物对不对往往要靠人看；裁判分又不够稳。只凭「用户重生成了一次」就写经验，写出来的多半是噪声。
- **召回没有判据。** 现有运行时只有「按需检索」这个动作，没有回答「什么信号该召回哪一条、最多召回几条、召回后放在上下文的哪个位置」。
- **晋升和退役没有闸。** 「重复三次就沉淀成 Skill」只给了计数，没有准入测试；版本升级时哪些条目该一起过期，也没有人算依赖。

## 2. 先把三种记录分开

经验层最容易和记忆、技能混在一起。混了之后，写入门槛会互相传染：记忆可以靠用户一句话写入，经验也跟着一句话入库；技能可以人写，经验也被人写成操作手册。

| | 回答的问题 | 典型内容 | 写入条件 | 召回方式 | 生命周期 |
| --- | --- | --- | --- | --- | --- |
| 记忆 | 这个用户/项目是什么样 | 品牌色、禁用风格、常用尺寸、交付偏好 | 用户明确说，或行为反复确认 | 按 key 与场景钩子确定性注入 | 用户改口、项目结束、过期 |
| 经验 | 这类任务在什么条件下该怎么做 | 检索前先读品牌包版本；logo 留白不够时先查约束段 | 失败有证据、原因可回放、失效条件写得出来 | 按任务类、版本、症状匹配 | 版本变更、被反例推翻、长期未命中 |
| 技能 | 一类任务的标准流程 | 「品牌海报」Skill：读包→选资产→排版→查约束→交付 | 多条经验收敛，或人直接编写 | 按能力路由激活 | 版本化，随发布包上下线 |

三者的差别落在**证据门槛**上，格式只是表象。记忆可以被「告知」，经验必须被「验证」，技能必须能被「路由」。所以它们不该共用一张表，也不该共用一个写入接口。

[反思那篇](/posts/agent-reflection.html)给过经验的最小结构：`when`、`do`、`evidence`、`scope`、`support`、`confidence`、`expires`。这个结构对代码任务够用，因为 `when` 可以写成报错原文。设计任务的 `when` 是一条症状描述，天然更模糊，字段要再加三样：**产物差异、反例、版本依赖**。

## 3. 归因：设计 Agent 的四类证据

设计 Agent 的归因比代码 Agent 难。代码有测试，测试红了就是红了；设计只有评审意见、用户行为和裁判分。裁判分我在 [RSI 那篇](/posts/rsi-self-improvement.html)里核过，和人类的一致率只有五成多，拿它当判决会把错误诊断传播下去。

能用的证据有四类，最好同时具备前两类，后两类用来加强或排除：

| 证据 | 具体内容 | 能回答什么 | 不能回答什么 |
| --- | --- | --- | --- |
| 规格快照 | 任务卡七字段、品牌包版本、资产树版本、规则版本、预算档位 | 当时的要求是什么 | 模型有没有照做 |
| 执行轨迹 | 检索 query 与命中资产、prompt 各段长度、工具调用与返回、模型路由 | 模型实际看到了什么、做了什么 | 产物哪里不对 |
| 产物差异 | 图层 diff、画布操作、重生成次数、评审发现、用户手动改动 | 哪里不符合要求 | 为什么会这样 |
| 反事实回放 | 固定快照，只改一个变量，重跑策略层 | 这个原因是否成立 | 线上会不会同样发生 |

举个具体的。任务卡是「春季新品海报，品牌包 brand-pack@v5，主视觉用资产库里的产品图，logo 四周留白不小于 logo 高度」。Agent 交稿后，用户手动把主图换成了另一张，又把 logo 往右挪了 24px。

轨迹里能看到：检索 query 是「春季 新品 主视觉」，top1 命中 `asset_a2231`，版本是 2025 款；检索参数里没有品牌包版本这个过滤项。产物差异里，评审标记了「主图与当前产品线不符」和「logo 留白不足」。

把快照冻住，只加一个过滤条件「`brand_pack_version = v5`」再跑，top1 变成 `asset_a3102`，留白也够了。这一步能把原因收到「检索范围没跟品牌包版本对齐」上，同时排除「模型不会排版」。再做一个反例：同一个 Agent 跑「自由创作，无品牌包」的任务，如果也强加品牌版本过滤，会把可用资产全滤掉。所以这条经验的适用范围必须限定在「有品牌包约束的任务」。

归因结论按证据强度分四档，不同档位进不同的库：

| 档位 | 判据 | 能做什么 | 不能做什么 |
| --- | --- | --- | --- |
| A 档 程序可判定 | 约束检查器直接报错：缺资产、超边界、违反禁用色 | 自动写候选经验 | 解释审美类失败 |
| B 档 可回放复现 | 固定快照改一个变量后结果翻转，且有产物差异佐证 | 自动写候选经验 | 证明线上同样有效 |
| C 档 仅裁判/人判断 | 评审说「不够高级」，没有可计算差异 | 写「待查问题」，人审后才转经验 | 自动入库、自动晋升 |
| D 档 无法归因 | 证据互相矛盾，或回放不复现 | 只记录，不写经验 | 硬塞进最近的一类 |

这张表的作用是挡住最常见的污染路径：把「用户不满意」直接写成「prompt 要加一句更高级」。C 档和 D 档必须允许长期存在，否则归因器会为了产出而编原因。

## 4. 一条经验长什么样

设计 Agent 的条目我用 YAML 存，方便 diff 和人审。字段比反思那篇多三个：`artifact_diff`、`negative_example`、`depends_on`。

```yaml
id: exp-brand-asset-version-001
status: candidate          # candidate | verified | active | suspended | expired | rejected | disputed
scope:
  tenant: brand-a
  task_class: poster.brand-bound
  brand_pack: v5
  asset_tree: "2026-11"
  model_route: design-pro
symptom: "品牌海报主视觉命中旧款产品图，logo 留白不足"
cause: "资产检索未按 brand_pack_version 过滤，top1 命中 2025 款资产"
action: "检索前读取 brand_pack.asset_version，作为硬过滤；topK 保持 8"
artifact_diff: "用户替换主图 1 次、移动 logo 1 次；评审标记 2 条"
evidence:
  - trace: tr_20261124_0917
  - replay: rp_20261124_1042   # 只加版本过滤，结果翻转
  - review: rv_20261124_0930
negative_example: "自由创作、无品牌包的任务不得加此过滤，否则会滤掉可用资产"
limits: "只适用于有品牌包约束的海报任务；v5 之前的资产不适用"
depends_on: ["brand-pack@v5", "asset-tree@2026-11"]
expires_when: "brand_pack 版本变更，或 asset_tree 重建"
owner: design-platform
created_at: "2026-11-24T10:50:00+08:00"
last_validated_at: "2026-11-24T10:50:00+08:00"
```

几个字段的取舍：

**范围里写版本，不写日期。** 日期看起来精确，实际上不能触发任何动作。`brand_pack: v5` 可以在品牌包升级时被程序扫描到，日期只能靠人记得回来改。

**证据存指针，不存结论。** `trace`、`replay`、`review` 的 id 让人能在十分钟内复核，而不是读一段「经分析，原因是……」的自述。自述会随着写的人变化，指针不会。

**限制和反例分开。** 限制是「什么情况下不适用」，反例是「长得很像但绝不能触发的任务」。前者防过度推广，后者防误触发，审查时看的是不同的东西。

**必须写 `expires_when`。** 写不出来的条目不许入库。这句话听起来霸道，但一条永远有效的经验，通常意味着它的适用范围没写清楚。

**一条只写一个原因。** 「检索没过滤 + prompt 约束段被截断」是两个原因，拆成两条。合在一起，回放时改了哪个变量都说不清，晋升时也没法判断哪一半起了作用。

条目还分两层，混在一起会出事：

- **事实型**：brand-pack@v5 的主视觉资产是 `a3102`。换一个品牌就废，只能留在本租户。
- **方法型**：品牌约束任务在检索前先读品牌包版本。可以跨品牌复用，但触发条件要写窄。

事实型不能直接晋升成全局 Skill；方法型晋升前要至少在两个品牌上验过。原文说的「只存答案，换数据就废；只存口诀，会过度推广」，就是这个分层。

## 5. 召回：在检索和组装之前

召回的位置比召回的技术重要。设计 Agent 有两个决策点值得挂钩子：

1. **资产检索之前。** 这时候经验能改 query、改过滤条件、改 topK，成本最低。
2. **prompt 组装之前。** 这时候经验能决定约束段放哪、要不要加一条「上次这里错过」的提醒。

生成之后再召回，只剩两条路：重做，或者让评审挑毛病。两条都贵。

召回按四层过滤，顺序不能反：

| 顺序 | 过滤 | 作用 |
| --- | --- | --- |
| 1 | 租户、任务类、品牌包/规则版本 | 把不可能适用的条目直接排掉 |
| 2 | 症状匹配 | 用任务卡和资产元数据匹配 `symptom`，避开主题词相似 |
| 3 | 依赖可用性 | `depends_on` 里的版本必须当前有效，否则条目标为 stale |
| 4 | 语义相似度 | 只在前三层剩下的条目里排序 |

落到代码就三层过滤加一个上限：

```python
def recall(task, pool, versions):
    cands = [e for e in pool
             if e.status == "active"
             and e.scope["tenant"] == task.tenant
             and e.scope["task_class"] == task.task_class
             and all(versions.get(k) == v for k, v in e.depends_on.items())]
    ranked = sorted(cands, key=lambda e: (symptom_score(task, e), e.last_validated_at),
                    reverse=True)
    return ranked[:2]
```

`versions` 是任务开始时冻结的版本表。`symptom_score` 只在前三层剩下的条目里算，别拿它对全库排序。

第 2 层最容易做错。「春季海报」和「春季上新 Banner」主题词几乎一样，但一个要品牌约束、一个不要；「有效订单数」和「订单总数」也是。按主题词召回，会把「所有订单都筛 paid」这种经验搬到「订单创建总数」上。原文对这个问题的说法是：先按业务范围缩小，再看语义。

排序不只看相似度，还要看「上次验证离现在多久」和「历史命中后的有效率」。一条三个月没验证过的条目，相似度再高也只能当参考。

注入预算按条算：最多 2 条，合计 300–400 token。格式固定成四行，放在任务卡之后、资产检索之前：

```text
[过往失败] 品牌海报 · 资产检索
症状：主视觉命中旧款产品图，logo 留白不足
做法：检索前读 brand_pack.asset_version 做硬过滤
限制：仅品牌约束任务；自由创作不适用
```

只给「做什么」，不给「为什么」的长篇解释。为什么放在条目里，人审和复盘时看；运行时上下文里塞原因，会挤掉资产描述和约束段。

每次注入都把 `experience_ids` 写进决策记录。任务结束后回填三件事：有没有被采纳、采纳后有没有效、有没有误触发。没有这三列，你只能知道条目被读过，不知道它有没有用。

召回失败要分三种，不要都归成「检索不准」：

- **没召回到**：索引里没有、范围过滤太紧、症状写得不像人话。
- **召回错**：版本过滤没生效，把别的品牌/别的规则版本搬过来了。
- **召回了没用**：注入位置太靠后、格式太长被截断、模型读了但没执行。

三种对应三种改法。混在一起，最后只会不断调相似度阈值，把召回率调上去，把有效率调下来。

## 6. 晋升与退役

一条经验从观察到进发布包，我分五级。每一级都写清楚「凭什么进」和「谁批」，避免「重复三次」变成「重复三次就上线」。

| 级别 | 进入条件 | 需要的证据 | 谁批 |
| --- | --- | --- | --- |
| 第 0 级 观察 | 任意失败 | trace + 任务卡 | 自动 |
| 第 1 级 候选 | A/B 档归因成立，失效条件写得出来 | 回放翻转 + 产物差异 | 自动 |
| 第 2 级 已验证 | 2 个独立任务 + 1 个新任务（新数据或换问法）通过，反例不误触发，回归不塌 | 四套题的记录 | 人抽审 |
| 第 3 级 技能补丁 | 同一做法覆盖 ≥3 个任务或 2 个任务类 | 文本 diff + 触发词 + 反例 + 前后对比 | 人签 |
| 第 4 级 发布包 | 技能补丁或数值参数进入 bundle，灰度通过 | 灰度护栏 + 回滚点 | 发布负责人 |

第 2 级的「独立」指不同 trace、不同资产、不同日期，同一会话里重跑三次不算。第 3 级的门槛落在触发范围能写窄：Skill 描述里要有一句「什么时候不要用」，否则它会从品牌海报蔓延到所有海报。

权限、计费、合规这类规则不能进经验层。经验是提示，提示可以被忽略、被截断、被更长的上下文挤掉；权限必须由工具和后端强制执行。原文也强调这一点，我把它写成硬规则：**这类条目连候选都不建，直接进代码需求。**

退役由四类事件触发：

| 触发 | 动作 | 要不要人看 |
| --- | --- | --- |
| `depends_on` 版本变更 | 整批标 stale，停止召回 | 程序自动，人确认新版本映射 |
| 被反例推翻 | 标 disputed，停止召回 | 人审后改条目或删除 |
| 连续 2 次应用后失败 | 降回 candidate | 人看失败 trace |
| 90 天未命中 | 进复审队列，不自动删 | 人决定保留或退役 |

最后一条要留余地。有些经验命中率低但价值高，比如「客户名含‘集团’时要走法务审核」；自动删会把这类稀有规则清掉。90 天只是提醒人回看，不是判决。

## 7. 验证：四套题，一次只动一个变量

验证经验比验证参数麻烦。参数有 golden 集，经验的效果取决于「在哪个任务上、什么时候被召回」。我用四套题，各有各的职责：

| 题集 | 抽什么 | 通过标准 | 防什么 |
| --- | --- | --- | --- |
| 修复集 | 催生这条经验的原失败任务 | 100% 通过 | 经验根本没修好原问题 |
| 泛化集 | 同规则、新数据、换问法 | ≥80% 通过 | 只记住原题 |
| 反例集 | 长得像但不该触发的任务 | 0 误触发 | 过度推广 |
| 回归集 | 之前通过、且可能被影响的同类任务 | 通过率下降 ≤1pp | 修一个坏两个 |

反例集最容易被省，也最值钱。品牌海报的版本过滤经验，反例就是「自由创作、无品牌包」；「主视觉优先用新品」的反例是「清仓专题，要求用旧款」。没有反例，经验一定会从「这个品牌的海报」长成「所有图都用新品」。

验证时冻结四个变量：模型路由、工具版本、资产快照、上下文预算。一次只改经验这一项。预期结果独立算：修复集和泛化集的通过标准在跑之前写死，不能让生成经验的模型自己定，也不能跑完再改答案。

样本量要说实话。200 条 golden 对 +3pp 的提升没有功效，双比例检验大约要 4000 条；200 条只能稳定看出 10pp 以上的差别。经验层的验证单位是任务族，不是单条任务，所以更适合配对：同一批任务，跑「有经验」和「无经验」两版，看逐对差值，报置信区间，不报一个孤零零的通过率。

样本量这笔账我单独算过，结论没变：**回放负责挡住明显变坏，不负责证明变好。** 经验层的验收也一样，四套题全过只说明「没明显错」，有没有用要看灰度。

裁判模型只做诊断，不做放行。它可以提示「这条产物可能违反留白约束」，但最终判据是约束检查器、用户行为（替换、移动、重生成、返工）和人抽审。裁判分进验证记录，不进放行条件。

## 8. 发布与撤回

经验不能一条一条上线，要打包。一个 bundle 里至少四样东西：

- 经验条目及其状态；
- Skill 版本与触发词；
- prompt 片段版本；
- 数值参数（topK、预算、超时、路由权重）。

bundle 有版本号，任务执行时把版本号写进 trace。出问题回滚的是整个 bundle，不是单条经验。原因很实际：一条经验可能依赖某个 Skill 的触发词，单独撤经验、不撤 Skill，会留下一个「按旧经验写的流程」。

依赖关系要显式存：`experience → skill → prompt → knob`。品牌包 v5 升到 v6 时，扫描所有 `depends_on` 含 v5 的条目，整批标 stale；由这些条目生成的 Skill 补丁也进复检队列。原文说的「撤回要考虑依赖」，落到工程上就是这张图。

{{< fig "diagrams/03-gates.svg" "经验进入发布包要过的四道闸。下面两层是程序判定，第三层是线上护栏，最上面是人审；裁判模型只提供线索，不单独放行。" >}}

灰度按租户分桶，取 5% 的租户跑 24 小时，护栏看四个数：一次通过率、单任务成本、P95 延迟、约束违反率。通过率允许 −1pp 的非劣边界，成本 +10%，P95 +15%；任一破线回滚。回滚目标 60 秒内完成，回滚后 bundle 版本回到上一个，下一轮任务按旧版本注入。

每次变更记一条账：预期改什么、验证花了多少、观察窗口多长、结果如何、有没有回滚。这条账同时是 T 的测量：

- `T_policy`：从失败被观察到 bundle 生效的时间，p50 和 p90；
- `T_skill`：从条目晋升到 Skill 补丁的时间；
- 每个变更的验证成本（回放条数 × 单条成本 + 人审工时）。

没有这本账，「自进化」只剩一个感觉。有了它，至少能回答：这个季度经验层让哪类失败下降了，代价是多少，下一次该不该继续投。

## 9. 指标与三个坑

经验层只看五个数：

| 指标 | 口径 | 健康区间（建议） |
| --- | --- | --- |
| 召回命中率 | 注入后任务通过，且归因确认与条目相关 | ≥60% |
| 有效率 | 命中条目里，采纳后确实改变行为且通过 | ≥50% |
| 误触发率 | 反例集上被错误激活的比例 | 0 |
| 过期未撤 | 已 stale 但仍在召回池的条目数 | 0 |
| 归因人机一致率 | 抽 100 条失败，人机同类的比例 | ≥80% |

阈值是建议值，不是实测最优。先用一个月把基线跑出来，再定线。

三个坑，按踩到的概率排：

**经验库变成第二本百科。** 每条失败都写，条目数涨得比召回质量快，注入预算被挤爆，模型开始忽略提醒。对策是限制条目长度（≤400 字）、限制单次召回条数（≤2）、每月清一次重复条目。

**用裁判分自证。** 条目上线后裁判分涨了，就认为经验有效。裁判和生成器同族时，这只是同一个偏好被加强了两次。对策是验收看程序检查、用户行为和人抽审，裁判只做诊断。

**只加不撤。** 版本升级后旧条目还在召回池里，模型同时收到「v5 用 a3102」和「v6 用 a4001」，两条都像对的。对策是 `expires_when` 必须可执行，版本变更时程序化扫描，不靠人记。

## 10. 落地：先做三件，再做召回

这四段是叠加在现有 P0–P4 上的增量，不替代原计划。按依赖排序，P0 不做完，后面的召回和晋升都是猜。

| 阶段 | 工时 | 做什么 | 验收 |
| --- | --- | --- | --- |
| P0 | 2 周 | 证据包（四类证据落一张表）、条目 schema、失效条件扫描、20 条人工归因 | 任取一个 bad case 能凭记录重放；20 条条目全有证据和 `expires_when`；0 条无失效条件入库 |
| P1 | 3 周 | 两个召回钩子、`experience_ids` 进决策记录、30 个任务族跑四套题 | 误触发 0；回归下降 ≤1pp；命中率与有效率有基线 |
| P2 | 4 周 | bundle 版本化、依赖图、5% 灰度、60 秒回滚、T 账本 | 灰度 24 小时护栏不破；回滚演练通过；`T_policy` p50 有数 |
| P3 | 2 周 | 经验晋升 Skill 的人签流程、跨品牌方法型条目的复用 | 至少 1 条方法型经验在两个品牌生效，且反例不误触发 |

P0 里最容易被砍的是「失效条件扫描」，它看起来只是一个字段。但没有它，经验库会在第一次品牌升级后变成污染源；而污染是静默的，模型不会报错，只会照做。

这三件做完，经验层至少是可审计的：每条结论知道从哪来、什么时候失效、被谁用过。召回准不准、晋升快不快，才有讨论的基础。

它不改变模型，也不缩短模型代际；它缩短的是经验复用的时间。把经验层做好，是 RSI 的必要条件之一，离充分条件还很远。
