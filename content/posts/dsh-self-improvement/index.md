**这篇在做什么**：把 DSH（DeepSeek Harness）当前版本里与「自进化」有关的零件逐个找出来，判断它们是否构成一条闭环；如果不构成，给出一套不改 core 的补齐方案，以及分阶段路线。

**不做什么**：不评价 DeepSeek 内部的研发路线，不预测 DSH 什么时候「起飞」，也不把「agent 能改自己的配置」直接当成自进化。文中所有关于 DSH 的判断都来自发布产物里的文档与代码，口径写在第三节。

## 一、结论速览

1. DSH 有完整的自改执行器。插件组合、插件代码、技能、`AGENTS.md`、agent 预设、profile 补丁，都能被 agent 修改，而且改完对后续会话生效。当前 profile 里有 233 个插件条目，运行时可装卸。
2. DSH 有观察面。append-only 的 session log 记录每一个模型可见事实，另有 telemetry、用户评分、token 与延迟统计。日志是唯一事实源，这一点在 `docs/subsystems/core.md` 里写得很清楚。
3. DSH 没有裁判。340 个 `@deepseek-ai` 包里找不到 benchmark、eval suite 或 quality gate；用户评分只写日志、不进模型历史；telemetry 是 best effort；`ralph` 的 README 自己写明轮间报告「不被独立验证」。
4. DSH 没有记账。没有变体登记，没有配对实验，没有归因，没有晋升与回滚账本。forge 能读 PR、评审、合并，但评审和合并仍然由人决定。
5. 所以现状是一条开环：能改，改完靠人看。按五段乘积给一组示意值，0.6 × 0.8 × 0.25 × 0.1 × 0.9 ≈ 1.1%，整圈通过率不到百分之二。数字是示意的，结构性结论不是。
6. 补齐方案不需要动 core：评测、变体、归因、晋升做成四个挂在 profile 外面的零件，用 headless 模式加独立 `DSH_HOME` 隔离运行，人在晋升点做决定。

| 阶段 | DSH 现有零件 | 缺口 | 评级 |
| --- | --- | --- | --- |
| 选题 | goal、schedule、plan | 不会从失败日志里自动选题 | 弱 |
| 实现 | agent-loop、fs/bash、plugin_manager、cordis、skills、AGENTS.md | 变更没有版本化与影响面分析 | 强 |
| 评估 | session log、telemetry、feedback、stats | 没有成功标签、回归集与 judge 校准 | 弱 |
| 归因 | forge PR、session 对比 | 没有变体登记、配对实验与置信区间 | 无 |
| 部署 | profile patch、HMR、plugin install、preset | 没有灰度、自动回滚与变更账本 | 中 |

## 二、三种「自进化」，别混着说

RSI 这个词在 2026 年被用坏了。落到 DSH 这种工程系统上，至少有三件事都被叫作自进化：

1. **模型自我改进**：模型改自己的权重。这是训练侧的事，DSH 不碰。
2. **agent 改自己的配置与代码**：改提示词、加技能、写插件、换工具集。DSH 有一堆这样的执行器。
3. **研发闭环**：系统自己提出改动、自己实施、自己判断改动是否有效，并把有效的留下。这才是我在[上一篇](/posts/rsi-self-improvement.html)里用的严格口径。

DSH 属于第 2 类里的系统侧。它能把第 2 类做到很深，但第 2 类本身不等于第 3 类。区别只有一个：**有没有独立信号证明改动真的更好，以及有没有把这份证明记下来**。

还有一个容易混的分法：改代码与配置，和改记忆。前者是 harness 层的变异，后者是把经验沉淀成技能与 `AGENTS.md`。两者都能让下一次任务变好，但评测方式不同：前者可以用同一批任务做对照，后者要测「同类任务第二次是否更少走弯路」。这篇主要谈前者，记忆层放在第八节末尾。

## 三、审计方法与范围

审计对象是发布产物 `/Applications/DeepSeek Harness.app/Contents/Resources/app.asar`。它是一个 asar 归档，不是目录，我写了个小解析器把文本文件抽出来：

- 归档共 21,821 个条目，其中 340 个 `@deepseek-ai` 包。
- 主包 `@deepseek-ai/dsh` 只是启动器，真正的实现分散在各 `dsh-*` 包里。
- 当前 profile 有 233 个插件条目，`plugin_manager` 工具在本会话可用。

读的材料：`docs/architecture.md`、`docs/subsystems/core.md`、`docs/capability-seams.md`，以及 plugin-manager、tool-cordis、agent-instructions、session-telemetry、message-feedback、tool-goal、schedule、tool-ralph、auto-review、forge、headless 等 30 多个包的 README。代码只做关键词检索，没有逐行读。

局限要说清楚：只看发布产物，不含内部仓库、未发布插件和训练侧；「没找到」只说明发布版里没有，不说明公司内部没有。另外，DSH 的插件生态是开放的，第三方完全可以在外面搭一套评测，本文说的是「harness 自带什么」。

## 四、执行器：DSH 能改自己

### 4.1 改组合：`plugin_manager`

`plugin_manager` 是暴露给模型的工具，能启停单个插件、选择 bundle、安装或移除外部 bundle。它直接改当前 profile 的 `cordis.patch.yml` 和 `package.json` 的 `dsh.profile.bundles` 列表，改动跨会话持久。

三个限制值得记住：

- 需要 `danger-full-access`，或者逐次审批。低权限模式下 `ask` 会弹审批，`never` 直接拒绝。
- 装进来的 Host 代码在进程内执行，**在 workspace 沙箱之外**。这是供应链风险的入口。
- 开着 HMR 时配置即时生效；没开则要重启。也就是说，一次错误的组合变更可以立刻打断正在跑的会话。

### 4.2 写插件：`cordis` 工具加 Creator 预设

`cordis` 工具本身是只读的：列服务、查 API、看事件。真正能写代码的是 agent 的通用能力（fs、bash）加上 Creator 预设：在 Creator 里，agent 可以写一个新插件包，再用 `plugin_manager` 装上。插件作者手册和 `adding-a-tool.md` 这类文档就在发布产物里，模型可以自己读。

这意味着「给 DSH 加一个工具」的门槛，已经从「改 core 发版」降到「写一个包、装进 profile」。

### 4.3 改行为：技能、`AGENTS.md`、预设

- 技能从 `~/.dsh/skills` 等目录发现，按需加载。本机装了 46 个，`skill-creator` 本身就是一个技能。
- `AGENTS.md` 在首轮请求时加载，有字节预算，不持续 watch；恢复会话时会重新对齐。
- agent 预设用 Cordis YAML 定义子插件，编辑后只影响之后创建的 agent。

这三样加起来，等于「提示词、工具集、工作习惯」都可以被写进文件、被下一轮读到。写文件用的是普通 fs 工具，没有任何额外的门禁。

### 4.4 改部署：三层补丁与 forge

profile 的配置有三层：bundle 层、profile 补丁 `cordis.patch.yml`、home 补丁 `$DSH_HOME/cordis.patch.yml`，后面覆盖前面。改哪一层、生效范围多大，是可以设计的。

对外发布走 forge：读 PR、读 diff、读写评审线程、标记 ready、合并。它把「改完怎么上线」这一段接上了 GitHub，但合并动作仍然是人点的。

### 4.5 执行器盘点

| 执行器 | 改什么 | 生效范围 | 主要风险 |
| --- | --- | --- | --- |
| plugin_manager | 插件启停、bundle 装卸 | 整个 profile，跨会话 | 装进来的代码在沙箱外执行 |
| cordis + Creator | 新插件、新工具 | 装到 profile 后全局 | 需要写代码与评审能力 |
| skills | 任务指令、流程 | 下一次加载该技能时 | 指令冲突、上下文膨胀 |
| AGENTS.md | 长期约束与偏好 | 下一次会话 | 写坏了会一直带偏 |
| agent preset | 工具集与子插件 | 之后创建的 agent | 预设漂移，难复现 |
| profile patch + HMR | 组合与配置 | 即时或重启后 | 改错会打断运行中的会话 |

结论很直接：**执行器不是瓶颈**。一个拿到 `danger-full-access` 的 agent，已经能在一次会话里给自己加工具、改提示、换组合。缺的是改完之后的那一半。

## 五、传感器：DSH 能看自己

### 5.1 session log

每个会话一份 append-only 的 `SessionEvent` 日志，落盘是 zstd 压缩的 JSONL，按 workspace 分目录。本机现在有 148MB、179 个会话目录。日志记录模型可见的每一条事实：消息、工具调用与结果、审批、错误、turn 的终止原因。

它是唯一事实源，也是做评测时最可靠的数据。headless 的 `--json` 事件流只是投影，字符串超过 8KiB 会被截断，不能当完整日志用。

### 5.2 telemetry

`session-telemetry` 把会话活动的有序副本发给部署方选定的后端，支持脱敏。两个限定词很关键：**non-blocking** 和 **best effort**，进程崩溃时队列里的记录可能丢。它适合做运营报表，不适合做「这次改动是否有效」的判据。

### 5.3 用户评分

`message-feedback` 记录正负评分、固定分类和备注，写进 session log。README 的原话是「Feedback is log-only and does not enter model history」。也就是说，评分是给人看的，模型自己学不到。

### 5.4 统计与检索

`stats` 面板给每个 turn 的 token、缓存命中、首 token 延迟、模型与工具耗时；`token-meter` 提供上下文压力测量。`tool-session-query` 和 `session-search` 能让模型检索历史会话，但 `session-search` 这个 bundle 在 Web 和 Desktop 里默认关闭，本会话也没有挂。

### 5.5 传感器盘点

这些零件能回答「发生了什么」，不能回答「这次任务成功了吗、为什么成功」。差别在于标签：日志里没有「任务通过/失败」这个字段，只有模型说了什么、工具返回了什么。

## 六、缺的两件：裁判与记账

{{< fig "diagrams/01-current-loop.svg" "把 DSH 的自改流程画成回路，断点位于「观测」和「提出变更」之间。执行器与传感器都在，中间缺的是判定与归因。" >}}

### 6.1 裁判

裁判要给出任务级的结果标签。可选的信源有三种：

- **确定性检查**：测试、类型检查、构建、文件断言。最可靠，覆盖窄。
- **人工验收**：真实用户点通过或打回。最贵，最慢。
- **模型评审**：可扩展，但要校准，否则只是把偏差换了个方向。

模型评审要能用，得先校准：拿 50 条人已标注的样本跑一遍，报告一致率和混淆矩阵；之后每批评测混入 20% 已标注样本，一致率掉到 80% 以下就停用这一路 judge。judge 只对开放式任务生效，且不单独决定晋升，只作为确定性检查的补充。

DSH 现在三样都不缺零件，缺的是把它们组织成「一批任务、跑完出分」的流程。已有的 `auto-review` 容易被误认为裁判：它在每次工具调用前用当前模型判断 allow/deny，是安全审批，不是质量评分，而且它自己就写明可能放行不安全动作、也可能拒绝有用工作。

`ralph` 也不是裁判。它跑「同一目标、fresh agent 多轮」，但 README 明说轮间报告不被独立验证。没有验证的多轮循环，只是把同一个错误重复更多次。

### 6.2 记账

记账要回答四个问题：这版改了什么、在哪些任务上变好或变坏、这个变化有多可信、出问题怎么退回去。

DSH 现在只有 git 和人的记忆。没有变体 id，没有「假设—改动—结果」的对应表，没有置信区间，没有晋升记录。forge 能承载 PR，但 PR 描述不是实验记录，评审意见也不是归因。

### 6.3 为什么这两件不能省

上一篇里有一条结论可以直接搬过来：生成侧变快、验证侧不变时，回路的漏损会指数级放大。DSH 的执行器越多、改得越快，没有裁判时产生的「看起来变好了」的噪声就越多。区别只是模型侧的单位是月，harness 侧的单位是天。

## 七、五段映射

把五段逐段落到 DSH 上：

- **选题**：现在靠人给目标，goal 负责续轮，schedule 负责定时。没有从失败日志里聚类、排序、生成候选改动的机制。这一段缺的不是工具，是「什么问题值得改」的自动化。
- **实现**：最强的一段。agent 能写插件、改技能、改提示、换组合，而且改完能立刻跑。
- **评估**：最窄的一段。有日志没有标签，有评分没有校准，有统计没有基线。
- **归因**：基本为零。没有变体登记就没有对照，没有对照就没有归因。
- **部署**：中等。能持久化、能 HMR、能走 PR，但没有灰度和自动回滚。

这五段是相乘的。实现段从 0.6 提到 0.9，整圈只涨 50%；评估段从 0.25 提到 0.6，整圈能翻一倍多。这和模型侧「评估带宽是瓶颈」是同一个结构。

## 八、目标架构

{{< fig "diagrams/03-target-architecture.svg" "四个新零件挂在 DSH 外面：评测运行器、变体登记、归因、晋升与账本。底座全部复用已有能力。" >}}

### 8.1 设计原则

1. 不改 core。所有新东西是脚本加插件，装在一个专用 profile 里，坏了不影响日常使用的 profile。
2. 评测在独立 `DSH_HOME` 里跑。`--profile` 解析的是 `$DSH_HOME/profiles` 下的目录，换一个 home 就等于换一套 profile、技能、会话存储，互不污染。
3. 候选生成与判定分离。提出改动的 agent 不能给自己打分。
4. 人只出现在晋升点。前面全自动，最后一步由人批。
5. 每个改动都带假设和预期效应，否则不进入队列。

### 8.2 Bench 与 Runner

任务集是评测的地基。一个任务至少包含：

| 字段 | 含义 |
| --- | --- |
| id | 稳定标识 |
| repo | 代码仓库与起始 commit |
| prompt | 交给 agent 的原始任务描述 |
| setup | 依赖安装、数据准备、超时 |
| checks | 确定性验收命令与期望退出码 |
| hidden | 不给 agent 看的检查，评分时才跑 |
| budget | 墙钟、token、工具调用上限 |
| tags | 语言、难度、能力维度 |

运行器调 headless：

```
DSH_HOME=/tmp/si/run-<id> dsh --profile si-eval \
  --permission-mode workspace-write --add-dir "$repo_git" \
  --json - < task.txt > run.jsonl
```

三件事必须同时检查：进程退出码为 0、`final.reason.kind` 是 `completed`、确定性检查通过。少一个都不算成功。JSON 流里没有完整 token 用量，要回到 session log 里取。

一条运行记录至少存这些字段：

| 字段 | 说明 |
| --- | --- |
| runId / taskId / variantId | 三元组，归因的最小单位 |
| model / route / temperature | 模型侧混淆项 |
| harnessCommit / profileHash | harness 侧版本 |
| exitCode / finalReason | 进程与 turn 的结果 |
| checks | 每条检查的通过情况与耗时 |
| tokens / cachedTokens | 成本 |
| steps / toolCalls / toolErrors | 过程指标 |
| interventions | 人工介入次数，来自真实会话 |
| wallMs / costEstimate | 时间与钱 |
| artifacts | 日志路径、diff、失败截图 |

### 8.3 变体登记

一个变体就是一次可回滚的 harness 改动：

```
variants/2026-11-20-session-search/
  variant.yaml
  patch.diff
  notes.md
```

`variant.yaml` 里写假设、预期效应、影响面、回滚方式。隔离方式有两种：文件级改动直接复制进独立的 `DSH_HOME`；需要改 profile 组合的，复制整个 profile 目录再打补丁。模型路由固定，避免「换了模型也算改进」。

### 8.4 归因

单次跑分不能归因。做法是交错对照：

1. 同一任务，baseline 与 variant 交替跑，顺序 ABBA，抵消机器负载和时间漂移。
2. 每个任务跑 5 次，取通过率；配对比较，算 bootstrap 置信区间。
3. 报告三件事：总体 Δ、逐任务 Δ、回退清单。总体涨但某类任务跌，要单独看。
4. 记录混淆项：模型版本、缓存命中、并发度、机器负载、任务集版本。

样本量要提前算。30 个任务、每任务 5 次，能稳定检出 10 个百分点左右的差异；想检出 5 个百分点，任务数要翻倍。这是预算问题，不是统计技巧问题。

### 8.5 晋升、灰度与回滚

| 等级 | 改动 | 审批 | 上线方式 |
| --- | --- | --- | --- |
| L0 | 提示词、单个技能 | 自动 | 先 canary，指标不跌再全量 |
| L1 | 插件配置、工具默认值 | 人工 | canary 一周 |
| L2 | 插件代码、新依赖 | 人工 + 代码评审 | 固定版本，分批 |
| L3 | core 与评测器自身 | 不走这条线 | 正常发版流程 |

晋升门槛写成配置，不写死在代码里：Δpass ≥ +5pp 且置信区间下界大于 0；没有单任务回退超过 10pp；成本涨幅不超过 20%；安全检查全过。

账本 `ledger.jsonl` 每次晋升追加一行：变体 id、评测报告路径、批准人、上线时间、回滚命令。回滚要演练，至少每月一次。

### 8.6 记忆层

失败挖掘是「选题」自动化的入口：从 session log 里找重复出现的工具错误、反复重试、用户纠正、被中止的 turn，聚类后生成候选问题。每个问题让 agent 写一条「教训」，形式可以是技能补丁、`AGENTS.md` 条目或一个检查脚本。

记忆层的改动同样要过评测，只是任务集换成「同类任务的第二次尝试」。否则就会变成「往提示词里堆越来越长的经验」，短期像变好，长期是上下文膨胀。

### 8.7 一个具体例子

假设我们从日志里发现：同一个仓库里，agent 反复踩同一个坑，先用了废弃的 API，报错，再改回来。候选改动是启用默认关闭的 `session-search` bundle，让 agent 能检索以前的会话。

- 假设：能看到上次的报错，就能第一次就选对 API。
- 改动：profile 补丁里启用 bundle，其余不动。
- 预期效应：这类任务的步数下降 10%，通过率 +3pp。
- 评测：30 个任务 × 5 次 × 2 臂，交错跑；主指标是通过率，次指标是步数与 token。
- 风险：检索结果污染上下文，可能让本来能做对的任务变差；如果逐任务回退超过 10pp，直接否掉。

这个例子的价值不在结论，而在格式：每个变体都能被写成「假设—改动—预期—判据—风险」五句话。写不出来的改动，不应该进评测队列。

## 九、一条夜间回路

把上面的零件串起来，一个晚上是这样过的：

1. **02:00 选题**：扫过去 24 小时的 session log，按「错误频次 × 影响面」排出前 5 个问题。去重，跳过已经在队列里的。
2. **02:30 生成**：每个问题一个 agent，读相关代码与文档，写一个变体，附假设与预期效应。预算上限：每变体 800k token、40 分钟。
3. **03:30 评测**：变体进队列，Runner 串行跑，避免互相干扰。30 个任务 × 5 次 × 2 臂，约 300 次运行；单次 2 分钟，墙钟 10 小时，拆到两台机器上跑。
4. **06:00 汇总**：产出日报：每个变体的 Δ、置信区间、回退清单、成本变化。没过的变体直接归档，不占人时间。
5. **上午 人工批**：人只看通过的 1–2 个，批完写进 profile 补丁，进 canary。
6. **一周后 复盘**：canary 指标和 baseline 对比，决定全量还是回滚；账本更新。

这条回路里，人每天投入约 20 分钟，机器投入一晚上。T 大约是 1 天，比模型一代短两个数量级。

## 十、为什么 harness 自进化可能比模型自进化快

{{< fig "diagrams/04-generation-time.svg" "三类改进的代际时间：单次评测小时级，harness 变体天级，模型一代月级。T 小两个数量级，一年内的迭代次数就多两个数量级。" >}}

同样的 β，T 从 90 天缩到 2 天，一年内的迭代次数从 4 次变成 180 次。即使每次只涨一点点，累积起来也很可观；反过来，迭代快但没有裁判，只是更快地积累噪声。

这也是我说「DSH 的瓶颈不在执行器」的原因：它的 T 已经足够小，小到评估带宽成了唯一的限制。这和模型侧「生成快、验证慢」是同一个瓶颈，只是尺度不同。

但别把这当成起飞证据。β 仍然由「改动质量 × 评估准确率」决定；T 小只放大已有的斜率，不改变斜率本身。要判断斜率有没有变大，还是得回到指标：通过率随代际的变化、每次晋升的实际增益、回退率。

## 十一、度量回路本身

| 指标 | 口径 | 健康区间（示意） |
| --- | --- | --- |
| T | 从问题进入队列到晋升上线 | 1–3 天 |
| 变体吞吐 | 每周完成评测的变体数 | 5–10 |
| 评测带宽 | 每天完成的 run 数 | 200+ |
| judge 一致率 | 与人工复核的一致率 | > 80% |
| 晋升率 | 通过门槛并上线的比例 | 10–30% |
| 回退率 | 上线后因指标下跌被回滚的比例 | < 10% |
| 单次晋升成本 | token + 机器时间 + 人工 | 可解释、稳定 |
| 真实会话干预率 | 需要人接手的会话比例 | 持续下降 |

前四个衡量回路转得快不快，后四个衡量转得对不对。只报前面，很容易做出一个「每天产出很多报告、没人看」的系统。

## 十二、安全与反 Goodhart

自改系统最危险的不是改错，是**改出一个能通过评测但更糟的系统**。几条硬约束：

1. **不可自改清单**：审批、沙箱、权限预设、telemetry、评测器自身、隐藏测试、`plugin_manager` 的保护行。这些文件只读挂载，改动需要人。
2. **隐藏测试**：agent 能看到的检查是一套，评分用的是另一套。防止改测试、绕检查。
3. **作弊检测**：diff 里出现测试文件改动、评分脚本改动、网络外联、跳过标记，直接判失败。
4. **judge 轮换与校准**：固定 judge 会被针对；每次评测混入人已标注的样本，算一致率。
5. **预算与熔断**：单变体 token 上限、单夜总预算、连续失败自动停。
6. **插件代码风险**：Host 代码在进程内、沙箱外跑，装之前要评审、锁版本、留哈希。这条比评测更重要，因为它的失败不是「分数低」，是「机器被控」。
7. **回滚演练**：没演练过的回滚等于没有回滚。

## 十三、路线图

| 阶段 | 交付物 | 验收 | 工时 |
| --- | --- | --- | --- |
| P0 观测 | RunRecord schema、headless 运行器、10 个任务的冒烟集 | 能稳定产出记录，字段齐全，重复跑结果可复现 | 2 天 |
| P1 评测 | 30–50 个任务、确定性检查、隐藏测试、基线测量 | 基线通过率与方差可解释，flake 任务被隔离 | 1 周 |
| P2 变体归因 | 变体登记、隔离运行、交错 A/B、报告 | 能检出 10pp 差异，报告含逐任务回退 | 1 周 |
| P3 晋升 | 门槛、canary、账本、回滚脚本 | 一次真实晋升走完全流程并留下记录 | 1 周 |
| P4 自动选题 | 失败挖掘、聚类、候选生成 | 每晚产出可评测的变体，人工只做筛选 | 2 周 |

P0 和 P1 不做完，后面的归因都是假的。P2 之前不要接自动晋升，否则会把噪声写进 profile。

## 十四、风险与反面意见

- **评测集会腐化**。任务写出来就开始过时，模型和工具都在变。每季度重跑一遍基线，淘汰不再有区分度的任务。
- **样本太小**。30 个任务只能支撑粗粒度结论，别用它证明 2pp 的提升。宁可少做几个变体，也别把噪声当信号。
- **评测通过不等于用户满意**。通过率是必要指标，不是充分指标；真实会话的干预率、返工率要一起看。
- **维护成本**。评测集、运行器、报告、账本都要人维护。如果没人看报告，这套系统会在三个月内退化成脚本化石。
- **组织问题**。自进化的瓶颈经常不是技术，是「谁有权批准改动」。没有明确的 owner，晋升流程会卡在评审。
- **反面意见**：harness 的改进空间可能远小于模型，做这套只是把工程流程自动化，不构成 RSI。这个批评是对的，所以第一步应该是测上界：先用 P1 量出「同样的模型，harness 改动最多能带来多少」。如果上界只有 3pp，后面的投入就该重新算。

## 十五、结论

DSH 现在的位置：**执行器到了第 2 级偏上，证据停在 2 级**。它能自主改自己，但没有独立测量证明改动带来了真实增益。

补齐 P0 到 P3 之后，能到「有真实增益的自主研究」的工程版：不是模型层面的 RSI，而是一条可审计的 harness 改进流水线。它离「闭环」还差一步：自动选题的质量，以及评测集能不能跟上真实使用分布。

一句话：DSH 缺的不是改自己的能力，是改完被判定的能力。
