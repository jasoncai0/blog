> 同一段 38 条消息的会话，剪枝之后还是 38 条，工具结果从 9,400 token 缩到 420；压缩之后只剩 12 条，中间 27 条换成一条摘要。剪枝不动消息骨架，压缩换掉整个区间。这个差别决定了它们各自会怎么坏。

## 0. 结论

剪枝删内容、留消息；压缩删消息、换摘要。判断只看一件事：后面的步骤还要不要引用这段内容的原文。要原文就留着，只要结论就压，都不要就丢。

失败方式跟着分。丢掉整条消息（截断）事后能翻出来；剪枝留下一个「省略 194 行」的空壳，看起来像读过；压缩把约束改写成一句通顺的话，读起来没有异常，发现不了。

## 1. 先看一段会话的账

例子是修一个登录 500。38 条里，1 条系统提示排在最前、不占编号，编号消息 m01 到 m37。前 12 条逐条列出，后面 25 条是同类动作的重复。下面的会话和 token 数是构造的示例，比例按常见的 agent 会话取，不是 benchmark。

| # | 角色 | 内容 | token |
|---|---|---|---|
| m01 | 用户 | 登录接口报 500，日志在 logs/api.log | 28 |
| m02 | 助手 | 调 read 读 logs/api.log | 22 |
| m03 | 工具 | 200 行日志，3 处 duplicate key | 9,400 |
| m04 | 助手 | 调 grep "duplicate key" src/ | 18 |
| m05 | 工具 | 命中 auth/store.go:88 与 3 个测试 | 260 |
| m06 | 助手 | 调 read auth/store.go | 16 |
| m07 | 工具 | 312 行源码 | 6,800 |
| m08 | 助手 | 根因：先查后插，两步之间不原子 | 210 |
| m09 | 用户 | 别动数据库 schema | 12 |
| m10 | 助手 | 方案：捕获唯一键冲突后重试 | 160 |
| m11 | 工具 | go test ./auth/... 失败，并发下仍重复 | 2,100 |
| m12 | 助手 | 改成事务内重试，冲突时回滚 | 190 |

后面 25 条：读 3 个测试文件，改 4 个文件，跑 5 次 go test（前三次失败，后两次通过），中间插 3 次 grep 确认改动，用户说提交（m36），助手提交（m37）。整段 38 条，52,000 token。

按角色拆开：15 条工具结果 39,000 token（75%），18 条助手消息 9,300，4 条用户消息 700，系统提示 1 条 3,000（没有 m 编号）。1 + 4 + 18 + 15，正好 38 条。单条最大的是 m03 那份 200 行日志，9,400 token，占全部的 18%。

上下文窗口按 60,000 token 算，这段会话已经用掉 87%，只剩 8,000。

m09 只有 12 个 token。它在第 9 条，到第 30 条左右就落到窗口边缘。三种做法都会在这里出事，出事的形状不一样。

## 2. 剪枝：删内容，不动消息

剪枝改的是一个节点内部的内容，消息条数不变。对这段会话做三件事：

1. 工具结果留首尾各 3 行，中间写「省略 194 行」。
2. 超过 2,000 token 的助手消息只留最后一段。
3. 旧图片换成 [image omitted]。

删完，33,000 token 的旧工具结果只剩 4,600，总数从 52,000 降到 23,600。38 条一条没少，顺序也没变。

好处有三条，都不花模型调用：

1. **成本为零。** 删内容是字符串操作，不请求模型。
2. **原文还在。** 磁盘上仍是完整日志，把标记去掉就恢复。
3. **结构安全。** tool_call 和它的 result 仍然相邻，请求不会因为缺 id 报错。

代价是有下限。留首尾 3 行，一条工具结果仍有 400 token 上下：12 条被剪的加起来 4,600，最近 3 条原样留着 6,000。工具结果从 39,000 压到 10,600，省下 28,400，到 23,600 就见底。可下一轮 go test 的输出就 9,400，比窗口剩下的 8,000 还多。

## 3. 压缩：删消息，换一条摘要

压缩选一段连续区间，用一次模型调用写一条摘要，把区间里的 N 条换成 1 条。

同一段会话，区间取 m02 到 m28，27 条共 37,000 token，换成一个 700 token 的节点。

{{< fig "diagrams/02-two-rewrites.svg" "图注：同一段会话的三种状态。左边原始 38 条；中间剪枝后条数不变、工具结果只剩首尾；右边压缩后区间变成一条带固定字段的摘要，尾部原样保留。" >}}

请求从 38 条、52,000 token 变成 12 条、15,700 token。

摘要写得好不好，取决于它有没有固定字段。本例至少要有四项：

| 字段 | 本例内容 | 缺了会怎样 |
|---|---|---|
| 目标与当前状态 | 登录 500；根因是先查后插不原子 | 模型重新读日志 |
| 硬约束 | 别动数据库 schema | 模型写 migration |
| 否掉的方案与原因 | 加唯一索引被否；纯重试并发仍重复 | 重走死路 |
| 报错原文与路径 | duplicate key on login_attempts；auth/store.go:88 | 定位不回具体表 |

摘要的成本是一次模型调用：输入是整个区间，输出是一条消息。区间 37,000 token，这次调用就按 37,000 计费。

先剪后压能把这笔输入降到 8,600（37,000 减去剪枝省下的 28,400），最终体积不变。DSH 里这套顺序、成对性和崩溃恢复的实现见[《压缩：把 transcript 当堆来回收》](/posts/dsh-compaction.html)。

## 4. 同一段会话跑三遍

| | 原始 | 只剪枝 | 先剪后压 |
|---|---|---|---|
| 请求里的消息条数 | 38 | 38 | 12 |
| 每轮上下文 token | 52,000 | 23,600 | 15,700 |
| 一次性模型调用 | 0 | 0 | 1 次，输入 8,600 |
| 不先剪时的摘要输入 | — | — | 37,000 |
| 原始内容能否取回 | 能 | 能，去掉标记 | 要按序号翻块 |
| 丢东西时能否发现 | 不丢 | 能，请求里有省略标记 | 不能 |

两列都能用。区别在留下什么：剪枝留下 38 条骨架，每条结论都能逐条对照；压缩只留 12 条，中间 27 条不能再回查。后面只剩两三步，选剪枝，零成本、信息更全；后面还有几十轮，选压缩，给每轮多留 7,900 的余量。

## 5. 三种失手

1. **截断坏在丢整条，翻记录能发现。** 窗口见底之后按最老优先丢，m09 那条 12 token 的约束在第 30 条时最先被挤掉。模型写了一个 migration，跑迁移脚本时被用户拦住。事后翻日志能看到 m09 没了，但已经浪费两轮。
2. **剪枝坏在留空壳，看起来像读过。** 日志中间 194 行被省掉，恰好把 duplicate key 那几行也省了，剩下首尾都是成功日志。模型据此判断「没有报错」，转头重读磁盘上的原文件。
3. **压缩坏在改写，读起来没有异常。** 换成一个粗糙的三字段模板（目标 / 进展 / 下一步，不是第 3 节那四条），m09 被写成「用户要求尽快修复登录问题」。这句读起来比原文更像一条目标，可「别动数据库 schema」这层约束没了。摘要通顺，模型不知道自己缺一条。

还有一种是名字混用：把「每条消息各砍一半」叫剪枝，结果 tool_call 的 id 和它的 result 对不上，API 直接返回 `tool_call_id not found`。这类错误该在请求发出前就拦住。格式坏的最先暴露，语义坏的要等用户在下一轮撞见。

## 6. 四种处置

{{< fig "diagrams/03-decision-tree.svg" "图注：两个问题分出四种处置。会被引用且需要精确值就保留，只需结论就压缩；不会被引用但可能回查就剪枝，查也没用就丢弃。" >}}

落到清单上：

| 处置 | 判据 | 本例 |
|---|---|---|
| 保留不动 | 后面要引用原文，或本身是约束 | m09、m36、m37 |
| 压缩 | 只要结论，不要原文 | m02 到 m28 的排查过程 |
| 剪枝 | 可能回查，但不需要全文 | m03 日志、m11 测试输出 |
| 丢弃 | 已经消费完，结论写在别处 | 通过的测试输出 |

用户消息、约束、当前任务这三类默认走「保留不动」，不参与判断。它们加起来通常不到总 token 的 2%，压它们省不下空间，丢一条要赔两轮。

## 7. 共同的代价：前缀变了，缓存就废

两种做法都改下一次请求的前缀。prompt cache 按前缀匹配，前面改一个字，后面全部重算。

所以频率比力度重要。攒到窗口 80% 再动一次，比每轮都动一次便宜。一次性剪 10 条工具结果，和分 10 次各剪 1 条，省下的 token 一样，重算前缀的次数差 10 倍。

## 8. 落地四条

1. 先剪后压，剪枝做第一道，压缩做第二道。剪枝零成本，它解决得了的不必花钱。
2. 摘要固定字段：目标、约束、否掉的方案、报错原文与路径。少一个字段就是一类误判。
3. 剪枝的保留清单写进代码，不靠模型判断：用户消息、约束、当前任务、最近两轮工具结果。
4. 每次压缩留一条审计记录：压了哪些序号、摘要用的哪个模型、花了多少 token。
