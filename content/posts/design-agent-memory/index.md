> 这不是一篇框架综述。它是我给一个设计 Agent 做记忆方案时，从「手上有一堆用户偏好、画布资产、Brand Kit、Skill 和几十万条对话」推到「系统能自己变好」的那条路径。文中的预算、阈值、延迟都是方案里的默认值，不是线上实测——但每个数字为什么是这个量级，理由都写在旁边。

## 0. 一句话里有四个指代

用户说：**还是上次那个调性，标题再收敛一点**。

这句话里藏着四个指代。**上次**指上一版被接受的画布；**那个调性**指品牌语气规则和这个用户过去的选择；**标题**指场景图里某个具体的文本节点；**收敛**指他前几次说这个词时实际做过的操作——字号减 2、字重降 100、行距加 0.05。

一个把所有东西切块、灌进向量库的系统，在这一步就开始漂。它可能召回三段不相干的对话，可能把「上次」理解成上一个项目，也可能把「收敛」匹配到一篇讲版式收敛的文章上。召回率看起来还不错，体验是错的。

问题不在检索算法。在于这六类资源根本不是同一种东西：

| 手上的资源 | 它其实是什么 | 该怎么读 | 漏了会怎样 |
| --- | --- | --- | --- |
| 用户偏好 | 命题，可被推翻 | 常驻摘要 + 检索 | 重复问同一件事 |
| 画布资产 | 状态，可回放 | 按焦点注入 | 改错层、改错节点 |
| Skill 资产 | 程序，有适用条件 | 任务开始时匹配 | 每次从零摸索 |
| Brand Kit | 约束，不可漏 | 编译期直通，不检索 | 品牌事故，且不报错 |
| 对话记录 | 事件，只追加 | 回放、抽先例 | 说不清「为什么改成这样」 |
| Agent 提示词 | 策略，要版本化 | 灰度、回放对比 | 改一次全局退化 |

把它们塞进同一个库，是这类系统最常见的第一个错误。

## 1. 结论速览

- **五层，不是一个库**。 M0 工作记忆、M1 情节、M2 语义、M3 程序、M4 资产。只有 M0 在上下文里，其余四层都是被编译器搬进来的。
- **品牌是约束，不是记忆**。记忆是概率性的，约束是确定性的；检索一次没命中就是事故，所以它不进召回池，也不参与预算裁切。
- **画布是状态，不是上下文**。存 op 流和快照，别存聊天摘要。对话只是「为什么这样改」的注释。
- **运行时只有两处同步**。编译进上下文（读）和提交落事件（写），其余全部异步。
- **记忆的敌人是污染，不是遗忘**。遗忘是设计的一部分；污染是模型把自己的输出当证据，几轮之后所有人都长一个样。
- **自演进 = 三速 × 六站**。每 turn、每天、每版三种速度，跑同一条「信号→候选→回放→影子→灰度→监控」的闭环。没有回放和影子，那不叫演进，叫自污染。
- **先做 M1 和编译器，再谈向量库**。没有情节记忆，语义记忆无据可依；没有编译器，存了也进不去上下文。

## 2. 三个容易搞混的东西

### 2.1 约束不是记忆

Brand Kit 里是这些东西：主色与辅助色的 hex、字体对与字重阶梯、logo 安全区、禁用词、图片处理规范。它们是**确定性**的——要么满足，要么不满足，没有「大概」。

记忆是概率性的：「这个用户可能偏好左图右文」，置信度 0.82。

把两者放进同一个检索池，会得到一个很隐蔽的失败：某次召回没命中品牌色，模型就用了上一版的蓝。产物看起来「有点不对」，但没有一条报错。等用户发现，已经发了三张图。

所以品牌走两条腿：**编译期注入**保证模型一定看得到，**产物侧校验**保证就算模型没看也跑不出去。校验是规则引擎（色值、字号、安全区、禁用词）加低频的 VLM 抽检。约束不占召回名额，也不能被预算裁掉。

### 2.2 状态不是上下文

画布不是一个 document，是一棵场景图加一条 op 流。

把所有对话摘要塞进上下文，解决不了「刚才那个蓝色方块是哪个」——因为模型需要的是**当前状态的索引**，不是历史叙述。反过来，只给场景图也不够：它不知道这个节点为什么被挪了三次。

正确的切法是：状态给场景图，理由给 op 流上的注释，两者用 `node_id` 和 `rev` 对齐。这样「第 7 版和第 12 版差在哪」是一个 diff 查询，而不是一次回忆。

顺带一个好处：op 流能统计。风格指纹（用了哪些色相、字号阶梯多密、圆角多大、文案平均句长）全部从 op 流和产物里算，不需要问用户「你喜欢什么风格」——他说的和他做经常不是一回事。

### 2.3 记忆的敌人是污染

遗忘是设计的一部分：候选会过期，长期不命中的会归档，置信度会随时间衰减。这些都可控。

污染不可控。路径是这样的：模型在总结里写了一句「用户喜欢极简」，下一轮这句话被当成事实召回，再下一轮它进了常驻画像，第四轮它开始影响所有新用户——因为这条「偏好」被错误地挂在了租户级而不是用户级。

防污染只有三条，且都必须落到数据结构上，不能只写在提示词里：

1. 证据只从**用户行为与产物**取：接受、编辑、撤销、重做、导出的文件。
2. 每条记忆带 `evidence[]`，指向具体的 episode；没有证据的条目只能是候选。
3. **agent 自己的输出永不作证**。它的回复、它的总结、它写的「用户偏好」都不算数。

## 3. 五层结构

{{< fig "diagrams/01-five-planes.svg" "五层记忆。只有 M0 在模型上下文里，M1–M4 都是外部存储，由上下文编译器按需搬进来。右侧标注的是每层的写入时机、读取路径和存储介质。" >}}

分层依据不是「内容像不像」，是**读写节奏**。节奏不同的东西放在一起，TTL 就没法设，索引也没法建。

| 层 | 存什么 | 谁写 | 谁读 | 寿命 / 存储 |
| --- | --- | --- | --- | --- |
| M0 工作记忆 | 焦点子图、最近 6 轮、召回卡片、待执行计划 | 编译器重建 | 每次调用 | 一轮 · 进程内 |
| M1 情节 | turn、工具调用、op 批次、提交快照、反馈 | commit 追加 | 回放、先例 | 永久 · 事件日志 |
| M2 语义 | 命题：偏好、事实、禁令、关系 | 异步巩固 | 常驻 + 检索 | 数月 · 关系库 |
| M3 程序 | 技能：触发条件、步骤、参数、约束 | 挖掘、编辑、灰度 | 任务启动匹配 | 版本化 · 技能库 |
| M4 资产 | 品牌 token 与规则、组件模板、素材、场景图、指纹 | 导入、提交 | 图查询 + 向量 | 随资产 · 图库 |

**M0 为什么不落库**。「当前在看什么」变化太快，持久化只会让它变旧。每轮从场景图 + 焦点重建，成本是几十毫秒，换来的是永远不会拿上一轮的焦点做这一轮的决定。

**M1 为什么只追加**。它是唯一的事实来源。M2 的每一条命题都必须能从 M1 重算出来；这条性质决定了系统可修复——发现某条偏好是错的，可以回放证据链，找到它是哪三次操作推出来的。

**M2 为什么是命题而不是段落**。段落没法合并、没法判冲突、没法失效。命题可以：`key` 相同就比 `value`，值不同就比证据。用户在九月喜欢居中、十月改成左边，这在库里是 `superseded` 的两条，不是两段互相矛盾的文字。

**M3 为什么单独一层**。技能有适用条件。一个「大字报风格」的技能不该在奢侈品品牌的项目里被匹配到；一个「快速出三版」的技能不该在精细排版任务里触发。这些条件依附在技能上，不依附在偏好上。

**M4 为什么是图**。「这个素材在哪些画布里用过」「这个组件属于哪个模板」「这版用了品牌色里的哪两个」——都是关系查询，向量检索答不了。

五层之间不是流水线，是双向的：M1 蒸馏出 M2，M2 反过来给 M1 打标签（哪些 turn 值得留作先例）；M4 的指纹约束 M2 的候选（统计上与用户历史风格差异过大的，降权）。

## 4. 接到运行时上

记忆系统不是「一个可以被调用的服务」，是挂在 turn loop 上的一组钩子。这个区别决定了成败：服务要等模型想起来去调，钩子是每一轮必然发生。

{{< fig "diagrams/02-turn-sequence.svg" "一个 turn 内的时序。只有两处是同步的（红色实线）：编译进上下文、提交落事件。其余全部在 turn 结束后异步执行，失败只降级、不阻塞回复。" >}}

| 钩子 | 触发 | 记忆层做什么 | 同步？ | 预算 |
| --- | --- | --- | --- | --- |
| `session.start` | 会话创建或恢复 | 装载画像、品牌、项目上下文，建 M0 骨架 | 是 | ≤150ms |
| `turn.pre_model` | 每次模型调用前 | 编译 M0：组 query、三路召回、重排、打包 | 是 | p95 ≤80ms |
| `step.pre_tool` | 每次工具调用前 | 查这个工具的历史用法与失败案例 | 是，可跳过 | ≤50ms |
| `canvas.commit` | 画布提交后 | 追加 episode、更新指纹统计、算 diff | 是（只写事件） | ≤30ms |
| `turn.post` | turn 结束 | 抽候选、采反馈信号 | 否 | ≤300ms |
| `context.compact` | 上下文压缩前后 | 把将被丢弃的段落映射到 episode，pin 住硬约束 | 是 | 必须成功 |
| `session.end` / `on_error` | 结束或出错 | 巩固、写负证据、清理缓存 | 否 | 后台 |

三条规则，比钩子表本身更重要。

**同步只读**。同步路径上只做读和一次事件追加。任何「顺便更新一下画像」都是异步的。理由很直白：编译延迟直接压在用户等待上，而画像更新晚 30 秒没有任何人会发现。

**超时降级**。编译超时（默认 80ms）就退到常驻块：品牌约束 + 偏好摘要 + 最近 3 轮。宁可这一轮少带先例，也不能让用户盯着转圈。降级要打点，降级率超过 2% 说明预算或者索引有问题，不是运气问题。

**压缩即写入**。这是最容易漏的一环。harness 在上下文超限时会丢掉早期消息——而早期消息往往正是「我们已经定了不改配色」这种关键约定。做法是：压缩前把将被丢弃的段落按 episode 映射成索引（保留 `episode_id`、一句话标题、涉及的 node），压缩后把硬约束重新 pin 回系统段。压缩不是删除，是一次降采样，降采样点要有指针。

### 为什么读取不做成工具调用

很多框架把 `memory.search` 暴露给模型，让它自己决定什么时候查。这在设计 Agent 里行不通，两个原因：

一是**它不知道要查什么**。用户说「还是上次那个」，模型没有画布状态，编不出有效的 query；它只能拿原文去搜，而原文里的指代在库里根本没有对应文本。

二是**延迟**。让模型先调一次工具再回答，等于每轮多一次往返；而编译器的活本来可以在模型开始前就干完。

工具仍然要有，但定位变了：`memory.remember` / `memory.forget` 是给**用户明确要求**用的（「记住这个品牌以后都用这个字号」），不是给 agent 日常工作的。

### 钩子契约必须是确定性的

每个钩子收到的输入要包含 `memory_rev`（记忆库版本号）和 `turn_id`。给定同一组输入，编译结果必须可复现。

这条约束看起来只是工程洁癖，其实是自演进的地基：没有确定性，就没法用同一批历史 turn 重放两套策略、比较结果。第 9 节的影子对比全部依赖这一点。

## 5. 写入：从一次 turn 到一条记忆

{{< fig "diagrams/03-write-pipeline.svg" "写入六道关。采集和抽取是廉价的，贵的是归并与判定——它们决定这个库会不会越用越脏。" >}}

一次 turn 结束后，后台跑完整条管线。失败只丢这一批，不影响已经发生的 turn。

**01 采集**。从 episode 里取：用户原话、op 批次、diff、撤销与重试。注意「撤销」是最强信号——它比任何一句「我不喜欢」都干净。

**02 抽取**。按 schema 抽命题，一条只表达一件事。「用户偏好左图右文，且不喜欢大圆角」要拆成两条，否则将来只会一条被推翻。schema 尽量窄：设计场景里常见的也就六七类——布局、配色、字体、密度、语气、素材偏好、禁用项。

**03 归并**。同义合并（「左边」「左侧」「左对齐」）、细化为子项（「排版偏好」→「标题对齐」）、泛化上提（三次具体的字号调整→「标题偏小」）。这一步用 embedding 做候选、用规则做裁决，不要直接让模型决定合并。

**04 判定**。和已有结论对质：支持就加分，反驳就进冲突队列。绝大多数记忆系统只做「写进去」，不做「和已有的对质」，于是库里同时存在「喜欢留白」和「喜欢信息密度高」两条高置信条目，检索命中哪条全看运气。

**05 打分**。 `证据数 × 来源可靠度 × 时间衰减`。三个因子相乘而不是相加，是为了让「只有一条证据」的条目无论多新都进不了常驻上下文。

**06 落库**。写 `candidate`，够阈值才升 `active`。阈值默认 0.7，升级需要至少两条独立证据。

一条记忆长这样：

```json
{
  "id": "mem_01J8QK3M",
  "layer": "M2",
  "scope": { "tenant": "t_18", "user": "u_3312", "project": "p_9" },
  "key": "layout.text_align",
  "value": "left",
  "confidence": 0.82,
  "evidence": [
    { "episode": "ep_7f2c", "turn": 41, "signal": "accept", "op": "set_align" },
    { "episode": "ep_8a11", "turn": 57, "signal": "edit", "from": "center", "to": "left" }
  ],
  "evidence_count": 7,
  "source_reliability": 0.9,
  "contradictions": 1,
  "status": "active",
  "supersedes": "mem_01J7XW02",
  "last_hit": "2026-11-08T09:12:00Z",
  "schema_version": 3
}
```

`evidence` 只留最近两条，完整链路在 episode 表里查。

`scope` 是三级：租户、用户、项目。层级写错是污染的主要来源之一——把项目级结论写成租户级，整个租户的所有新项目都会继承一个不该继承的偏好。写入时 scope 只能由调用方显式给，不接受模型推断。

### 三条写入门禁

**幂等**。同一个 op 批次重放十次，只产生一条事件、一条记忆。幂等键是 `(session_id, turn_id, op_batch_id)`。没有这条，重试机制会把一条偏好写成七条，置信度虚高到 1.0。

**溯源**。每条记忆必须能回到 episode。用户说「忘掉」的时候要能删干净；审计的时候要能回答「你凭什么这么认为」。

**反自证**。agent 自己的回复、总结、以及它写下的「用户偏好」都不算证据。只有用户行为（接受、编辑、撤销、重做）和产物（导出的文件、最终画布状态）算。这条如果不硬性写进写入路径，模型会在总结里自我循环。

### 冲突怎么收

同一 `key` 出现不同 `value`，按证据强度分三种处理：

| 情形 | 处理 |
| --- | --- |
| 新证据 ≥ 2 条，且时间更近 | 旧条目标 `superseded`，新条目 `active` |
| 双方证据相当，时间跨度都长 | 标 `contradicted`，降低两者权重，进人工/用户确认队列 |
| 用户明确否定过 | 直接 `superseded`，并打 `hard_negative`，同类候选写入时直接拦 |

第三种值得单独说。用户说过「别再用渐变」，这不是一个偏好，是一个禁令。禁令要能和偏好区分存储，因为禁令的衰减应该接近零——半年后它仍然有效。

「问用户」也别做成弹窗。更好的做法是：下一次生成给两个变体，用户选了哪个就是证据。选择比问卷的信噪比高，而且不打断创作。

## 6. 生命周期：一条记忆会被推翻，也会过期

{{< fig "diagrams/04-memory-lifecycle.svg" "记忆条目的状态机。写入只产生候选，提升、取代、归档都由后台巩固器判定，热路径不参与。" >}}

候选态存在的理由只有一个：模型抽出来的东西默认不可信。只有被第二条独立证据或用户明确确认过，才允许升到 `active`、进入常驻上下文。

衰减按类别给不同的半衰期，不搞全局一刀切：

| 类别 | 半衰期 | 理由 |
| --- | --- | --- |
| 瞬时偏好（这版想要更亮） | 7 天 | 属于当前项目阶段，不属于人 |
| 审美偏好（对齐、密度、圆角） | 180 天 | 会变，但变得慢 |
| 工作习惯（先看三版再定） | 365 天 | 极稳定 |
| 硬禁令（不用渐变、不用这个字体） | 不衰减 | 只有用户能撤销 |

热路径只读 `active`。`superseded` 不删，留着回答「以前为什么那样」——这是设计评审里最常被问的问题。

归档不等于删除：180 天未命中的条目下沉到 `archived`，仍然可以被显式检索到，但不进常驻上下文、不参与默认召回。

删除是异步三步：写墓碑 → 重建索引 → 用检索测试验证它不再被召回。少一步都会留下「幽灵记忆」——用户要求删掉的东西还在影响生成，而且没有任何报错。墓碑本身永不参与召回。

## 7. 读取：在 32k 里抢六个槽位

{{< fig "diagrams/05-context-budget.svg" "上下文预算的分配。上面是 32k 窗口的四段切分，下面把 9.4k 的记忆块展开成六个槽位。" >}}

记忆不是「塞进上下文」，是在固定预算里分配。图示的默认分配：系统与工具 6.0k、记忆块 9.4k、本轮工具结果 8.0k、生成余量 8.6k。记忆块再切成六份：

| 槽位 | 默认 | 内容 |
| --- | --- | --- |
| 品牌硬约束 | 0.9k | token、规则、禁用项，直通不检索 |
| 画布聚焦 | 2.6k | 焦点子图 + 相关节点属性 |
| 偏好摘要 | 1.1k | 5–8 条高置信命题，带来源 |
| 先例 | 1.5k | 2–3 条相似任务的历史做法 |
| 技能 | 0.5k | 匹配到的技能名称与要点 |
| 最近轮次 | 2.8k | 最近 3–6 轮原文 |

四条规则：

**硬约束不参与打分，直接拼在系统提示后面**。它不占召回名额，也不允许被裁掉。裁预算时先砍先例，最后才动约束。

**召回不够就空着**。记忆块的空缺不补满。补满只会稀释注意力——五条弱相关的先例，比两条强相关的更糟。

**每段都带来源标记**。模型可以引用「按你上次的偏好」，用户也能点开看是哪一条。可解释不是装饰，它是用户纠正系统的入口。

**默认权重不是常数**。快环每轮在三种配比里选一个：偏好优先（改风格类任务）、先例优先（重复性任务）、最近优先（连续微调）。选择依据是任务类型加最近一次反馈，切换本身也是一次可回放的决策。

召回本身是三路并行：BM25 抓精确词（品牌名、组件名）、向量抓语义、图扩展抓关联（这个节点的父级、这个素材用过的画布）。三路各取 40 条，重排用小模型打分，再用 MMR 去重，最后按槽位裁切。

## 8. 资产：画布是状态，品牌是约束

{{< fig "diagrams/06-asset-graph.svg" "画布、品牌、技能、素材、指纹之间的关系。品牌走硬约束注入，技能按条件匹配，指纹从产物统计。" >}}

这几类资产在记忆系统里的地位完全不同，混在一张表里就必然出错。

**画布** 是状态树：场景图 + op 流 + 每 50 步一个快照。它回答「现在是什么样」和「怎么变成这样的」。检索按 `canvas_id` + `rev`，不做语义搜索。

**品牌** 是约束，走注入和校验两条路，前面说过。它还要一个「变更审计」：品牌色改过一次，那么历史上所有用旧色的产物都要能被找出来。

**技能** 是可执行的程序，带适用条件和成功率。用户级适配层覆盖在通用技能上——同一个「快速排版」技能，对 A 用户默认三版横排、对 B 用户默认两版竖排。

**素材** 是零件，关键是 license 和使用次数。「这个图在 12 个画布里用过」是很有用的信号：它说明这是用户的心头好，值得进常驻；而「这个素材只在一次实验里用过」就不值得。

**风格指纹** 从产物统计，不问用户。色相分布、字号阶梯密度、圆角半径、留白比例、文案平均句长。它有两个用途：给偏好打分时做先验（统计上与用户历史差异过大的候选降权），以及在用户说「这不是我的风格」时提供一个可量化的解释。

它们的失败代价不同，所以不该同表同权重：品牌漏一条就是事故，素材漏一个只是少个零件，指纹错一次会被下一条证据覆盖。

## 9. 自演进：六个站点转一圈

{{< fig "diagrams/07-evolution-loop.svg" "自演进回路。左边六个站点构成一圈，右边是按速度分层的三类改动。越往下越慢，因为越往下改的东西越难回滚。" >}}

「让 Agent 自己变好」这句话很容易被理解成「让模型改自己的提示词」。那不是演进，那是掷骰子。

可控的自演进有一个前提：**变更的单位是一个策略，不是一个想法**。策略是可版本化、可回放、可回滚的东西——检索配比、抽取 schema、写入门控阈值、某个技能的默认参数。改动的每一步都走同一条闭环：

**① 信号**。三类信号聚合到「策略-结果」对上。显式的有接受、撤销、重做、「这不是我的风格」；隐式的有接受后编辑的 op 数、生成到导出的时长、变体选择分布；系统的有编译 p95、降级率、冲突队列长度、用户点开来源的比例。

**② 候选**。规则挖掘（某个槽位命中率长期偏低）加人工 review 队列。候选必须写明「改什么、预期哪个指标动、怎么回滚」。

**③ 回放**。取最近 N 个真实 turn，冻结输入（包括 `memory_rev`），旧策略和新策略各跑一遍。这一步只有因为钩子契约是确定性的才成立。

**④ 影子**。线上并跑，新策略只计算不返回，100% 流量。看一致性：同样的输入，两边输出差在哪、差异是否可解释。

**⑤ 灰度**。1% → 10% → 全量。分桶要稳定，同一个用户始终落在同一侧，否则体验会抖。

**⑥ 监控**。指标跌就回滚。回滚是一键的，因为策略本来就是版本化的。

### 三级变速

| 速度 | 频率 | 改什么 | 失败代价 |
| --- | --- | --- | --- |
| 快 | 每 turn | 检索配比、写入门控阈值、prefetch | 丢一个 turn |
| 慢 | 每天 | 巩固、消解冲突、挖技能 | 产出一批脏候选 |
| 元 | 每版 | 抽取提示、检索器、schema | 影响所有人 |

往下的三级不是「更高级」，是「更难回滚」。所以快环可以自动调，元环必须过门禁、影子、灰度三道。这三档具体落在哪些表、谁来决策、怎么预算探索，下一节展开。

### 一个真实的循环长什么样

连续两周，先例槽位的命中率只有 12%——25 次注入里用户点开看过 3 次。回放发现这类任务里先例的相关性打分普遍低于 0.3，但编译器仍然按固定 1.5k 分配预算。

慢环产出候选：把先例槽位改成自适应 0.5–2.0k，省下的预算给画布聚焦。影子跑三天，编辑深度下降 8%，撤销率没变。灰度 10% 一周后全量。

这个改动没有一行「智能」，全是计数器加阈值。但它确实让系统变好了——而如果交给模型去「反思自己哪里做得不好」，它多半会写出一段读起来很对、改不动任何东西的总结。

### 防止自演进变成自污染

四条硬约束：

1. **评估器与生成器不同源**。用同一个模型给自己打分，分数会收敛到「它擅长生成的东西」，不是「用户想要的东西」。
2. **指标要成对**。只看接受率，系统会学会生成平庸但安全的东西。配一个反向指标：编辑深度、变体差异度、首次导出时长。两者一起看。
3. **评估器的提示词不参与自演进**。否则它会往「更容易通过」的方向漂。
4. **每一版策略的变更都写审计日志**：改了什么、基于哪批回放、谁批的。出问题时要能回到具体那一版。

第 3、4 站（回放、影子）是分水岭。没有它们的「自演进」，本质上是让模型把自己的输出当证据——几轮之后，所有用户的记忆都长一个样。

## 10. 实现：把回路接上

上一节讲的是回路的形状。这一节讲把它接起来要写的东西，五样：一个策略对象、一张决策日志、一套归因规则、一个回放器、一条带刹车的灰度。代码量不大，我见过的最大一份实现也没超过三千行；真正贵的是另外一件事——你得愿意在还没有收益的时候先写三个月的日志。

{{< fig "diagrams/08-data-loop.svg" "自演进的数据回路。策略驱动编译器，编译器每 turn 写一行决策日志；用户行为变成信号，两者归因后得到样本，再训练出候选策略。左侧那条虚线是唯一需要人批的环节。" >}}

### 10.1 策略是一个对象，不是一段提示词

```json
{
  "id": "mem.compile",
  "version": 37,
  "params": {
    "slots":  {"brand": 900, "canvas": 2600, "pref": 1100,
               "precedent": 1500, "skill": 500, "recent": 2800},
    "recall": {"paths": ["bm25", "vector"], "topk": 40},
    "rerank": {"threshold": 0.32, "bypass": ["brand"]},
    "write":  {"min_evidence": 2, "auto_active": false}
  },
  "rollback_to": 36,
  "expected": {"precedent_hit_rate": "+8pp"}
}
```

四条约束，一条都不能省：

- **参数是声明式的**。只有数字、枚举、白名单，没有自由文本。要表达「自适应」，是在参数里加一个区间加一个函数引用（`precedent: {min: 500, max: 2000, fn: "by_hit_rate"}`），不是写一句话。
- **版本不可变**。改一个数字就是新版本，老版本永远留着。生效靠一个指针，不靠覆盖。
- **每个参数有 owner 和上下界**。快环能动哪些、慢环能动哪些、元环能动哪些，写在 schema 里而不是写在文档里。上界是防自演的刹车：没有上界，bandit 迟早把一个槽位推到占满整个预算。
- **必须带 `rollback_to` 和 `expected`**。前者让回滚是一行更新，后者让「这次改动有没有用」在事前就有一个可对照的说法。

为什么不让模型直接改提示词，理由不是「不可靠」，是四个更硬的东西：

| 障碍 | 写提示词 | 改参数 |
| --- | --- | --- |
| 可回放 | 同一输入两次可能不同 | 同一输入必然相同 |
| 可归因 | 一个 diff 里混了十处语义改动 | 一次改一个数 |
| 可回滚 | 语义没有二分，只能整段换回 | 指针指回上一版 |
| 可二分 | 没法做 A/B，因为两边不是同一种东西 | 天然可 A/B |

同一个改动，如果只是「先例槽位从 1.5k 改成按命中率在 0.5–2.0k 之间浮动」，它在提示词里是一句话，在策略里是一个参数加一个函数加上一个上界。后者能回滚，前者只能后悔。

### 10.2 每个 turn 写一行决策日志

```sql
create table decision_log (
  id             text primary key,
  turn_id        text not null,
  policy_version int  not null,
  compile_ms     int  not null,
  injected       jsonb not null,  -- [{mem_id, slot, tokens, score, rank}]
  dropped        jsonb not null,  -- [{mem_id, reason, profit}]
  dropped_tokens int  not null,
  degraded       text,            -- null | timeout | index_miss | no_quota
  created_at     timestamptz not null default now()
);
create index decision_turn_idx on decision_log (turn_id, created_at desc);
```

三条纪律：

1. **注入和裁剪都要记**。只记 `injected` 的日志能回答「用了什么」，回答不了「为什么没用那条」。而后者才是改策略的依据——先例槽位命中率低，可能是因为它压根没被召回，也可能是因为召回了但被预算挤掉，两者的修法完全不同。
2. **`reason` 用枚举**。`budget` / `below_threshold` / `duplicate` / `stale` / `conflict`。自由文本的 reason 三个月后就是一堆无法聚合的句子。
3. **写失败不影响 turn**。日志是旁路，异步写，失败计入降级率。但降级率本身是一级指标：日志断了，自演进就断了，而它断的时候系统看起来一切正常。

存储上要注意的是粒度。每 turn 一行、只记 id 和分数、不记记忆正文，一条大约 1.2KB；十万 turn 一天是 120MB，压缩后三十来兆，滚动三十天完全可控。反过来，如果把注入的正文也写进去，一天就是十几个 G，然后你会为了省存储把日志裁到没法用。

### 10.3 归因：信号挂在 decision 上，不是挂在 turn 上

一轮对话结束，用户点了撤销。这条信号该记到哪？记到「这一轮」是最省事的做法，也是最没用的做法——一轮里注入了六条记忆、四次工具调用，你无法知道是哪一条把事情弄坏的。

三类信号，归因方式不同：

| 类型 | 例子 | 归到哪 | 延迟 |
| --- | --- | --- | --- |
| 即时 | 撤销、点开来源、切换变体 | 被引用的那一条 | 秒级 |
| 延迟 | 接受后 5 个 op 内的编辑距离、二次追问 | 被引用的那一条，按 0.5^n 折扣 | 分钟到小时 |
| 反事实 | 影子/灰度两侧的结果差 | 整份策略版本 | 天级 |

「被引用的那一条」怎么判？做引用检测：模型输出里出现的品牌色值、标题文案、组件名，能不能反查到某条记忆。能反查的才计数，反查不到的一律算「无归因」，不摊派。

这一点值得单独说，因为大多数实现会选均摊：一轮注入了五条，用户撤销了，就每条各扣 0.2。均摊看起来公平，实际上把有效信号稀释成了噪声——好记忆和坏记忆一起被扣，几次之后所有记忆的置信度都趋同，检索退化成随机。宁可大部分信号归不到任何一条（这是真实情况），也不要平均分给五条。

反事实那一类最硬。灰度的两侧是同一批用户、同一时间段、只差一个策略版本，两边结果差就是因果，比任何离线打分都可信。代价是慢，而且有伦理成本——你得接受一部分用户在用「可能更差」的版本。

### 10.4 回放器的四个必需输入

{{< fig "diagrams/09-replay-bundle.svg" "回放的四个必需输入。四样东西少冻一样，回放就退化成「用今天的系统解释昨天的行为」。" >}}

四样东西，缺一不可，其中「记忆库时点」最容易被漏掉：记忆库是活的，你今天回放上周的 turn，如果不指定 `memory_as_of`，编译器读的是现在的库，召回结果和当时完全不同——你测的其实是「今天的记忆库碰上旧策略」，而不是「当时的输入碰上旧策略」。

运行参数上，我的默认值：

- **样本量 300–500 个 turn**，覆盖至少 20 个用户、3 类任务。低于 300 噪声盖过效果，高于 500 收益递减。
- **不调生成模型**，只跑编译器。300 个 turn 约 40 秒；需要看生成质量时抽样 5% 调模型，约 12 分钟。
- **判据是「不劣 + 显著」**：新策略在撤销率、编辑深度、编译 p95 上都不劣于旧版（允许 2% 的抖动带），且在目标指标上有 ≥5% 的相对提升。只满足一条不进影子。

如果钩子契约不确定，这一步根本做不了——同样的输入两次编译给出不同的注入，你就分不清差异来自策略还是来自随机。这也是为什么第 4 节把它列成硬约束：确定性不是工程洁癖，是可回放的前提。

### 10.5 灰度是带着刹车的放量

{{< fig "diagrams/10-guardrail.svg" "灰度的 guardrail。指标连续三个窗口越过阈值即自动回滚；回滚只是把策略指针指回上一版，不动任何数据。" >}}

四个细节决定它是刹车还是摆设：

1. **分桶要稳定**。`hash(user_id + policy_id + version) % 100 < rollout`。用随机数分桶的话，同一个用户会在两侧来回跳，体验抖，指标也全是噪声。
2. **guardrail 是三条硬指标**：撤销率、编辑深度、编译 p95。任一越线就回滚，不看总体「感觉还行」。阈值取基线 + 2σ，σ 用前两周的同期数据算。
3. **窗口是 200 个 turn 或 30 分钟**，先到者为准。连续 3 个窗口越线才动手，避免一次抖动就回滚——单窗口回滚会让系统在阈值附近反复横跳。
4. **回滚是一行更新**：把 `policy.pointer` 指回 `rollback_to`。不做数据迁移、不清缓存（缓存键里带 version）、不回滚已经写进 M1 的事件。因为策略本来就是版本化的，回滚本来就应该这么便宜。

回滚之后还有一件事：把这次失败写成一条 negative memory，挂在新版本上。下次有人想提出同一个改动，回放器会先把这段记录甩出来。这是这套系统里少有的「记忆作用于自己」的地方。

### 10.6 三速怎么调度

| 环 | 触发 | 谁决策 | 输入 → 输出 | 回滚 |
| --- | --- | --- | --- | --- |
| 快 | 每 turn | bandit（3 个预设里选） | 500 turn 的归因样本 → 本 turn 的配比 | 一个 turn |
| 慢 | 每天 02:00 | 批处理 + 规则/人审 | 一天的日志与信号 → 候选 + 回放报告 | 一个版本 |
| 元 | 每版（周级） | 人工门禁 + canary | 回放与影子的累积 → 新抽取器/检索器 | 一次发布 |

快环这里有一个容易做错的地方：**不要在连续参数空间里调**。槽位预算从 2600 调到 2613 没有任何意义，只会让归因变难、让灰度不可比。正确做法是把配比压成三个预设（偏好优先 / 先例优先 / 最近优先），bandit 只在这三个里选，每 200 turn 重算一次后验。

重算用 Wilson 下界而不是均值。原因很实际：某个预设只被试了 7 次、成功了 6 次，均值 0.857 会让它看起来最好，但置信区间很宽；Wilson 下界会把它压回合理位置，等样本够了再让它上位。用均值的系统会不停地把预算押在小样本的运气上。

再加一条 floor：至少 80% 的流量走当前最优预设，剩下 20% 用于探索。没有 floor 的 bandit 会在几个预设之间反复横跳，用户感知到的就是「这个 Agent 今天有点不一样」。

### 10.7 回路自己要三张表

核心的 `episode` 与 `memory_item` 放在下一节，这里只写回路本身需要的三张。

```sql
create table policy (
  id         text not null,
  version    int  not null,
  params     jsonb not null,
  rollback_to int,
  expected   jsonb,
  status     text not null,  -- candidate | canary | active | retired | rolled_back
  created_by text not null,  -- human | slow_loop | fast_loop
  created_at timestamptz not null default now(),
  primary key (id, version)
);

create table experiment (
  id          text primary key,
  policy_id   text not null,
  version     int  not null,
  rollout     int  not null,        -- 1 | 10 | 50 | 100
  guardrail   jsonb not null,       -- {metric: {threshold, windows}}
  status      text not null,        -- running | promoted | rolled_back
  started_at  timestamptz not null default now(),
  ended_at    timestamptz
);

create table assignment (
  subject_id  text not null,        -- user_id，分桶主体
  experiment_id text not null,
  bucket      int  not null,        -- 0..99
  assigned_at timestamptz not null default now(),
  primary key (subject_id, experiment_id)
);
```

`policy` 存参数快照（不是指向配置中心的一个键——配置中心会变，回放会废）；`experiment` 存这一次放量的门禁定义，回滚的时候要照着它判断「是不是真的越线了」；`assignment` 存分桶结果，保证同一个用户在实验期间始终在固定一侧。

加起来四张表：`decision_log`、`policy`、`experiment`、`assignment`。都是只追加或只更新状态，没有删除。

### 10.8 最贵的不是代码

跑起来之后你会发现，成本主要在三处：

- **日志存储**。按前面估算，每天 30–120MB，一年几十个 G。这是必须付的，但要对齐粒度，别把正文写进去。
- **回放算力**。每次候选都要跑 300–500 个 turn 的编译器。如果编译 p95 是 80ms，一次回放是 24–40 秒机时，一天十次候选就是几百秒，可以接受；但如果编译器里有同步的向量检索，这个数字会翻十倍。
- **人的注意力**。慢环产出的候选里，真正值得看的不到三成。不做预筛（比如只把「目标指标预期提升 > 3% 且回放无回退」的候选推到人面前），一周之后就没有人看了。

五个翻车点，按我踩过的顺序：

1. **日志太细**。把注入的正文写进 `decision_log`，两周后存储告警，然后为了省空间把日志裁成「只记条数」，自演进直接失去依据。
2. **归因均摊**。看起来公平，实际把信号稀释成噪声，记忆的置信度全部趋同。
3. **分桶用了随机数**。用户体验抖，指标噪声大，灰度的结论全部不可信。
4. **回滚不原子**。指针改了，但编译器里缓存了旧参数，一半流量还在新版本上，你以为回滚了其实没有。
5. **bandit 没有 floor**。探索太猛，最好的预设被反复冷落，长期收益反而下降。

这套东西做完，你得到的不是「一个会自我改进的 Agent」，而是「一个改坏了能立刻知道、并且能退回去的系统」。前者听着厉害但没法验证，后者才是能长期跑的形态。

## 11. 数据模型

M1 事件表只追加，`payload` 只写不查（查询走单独的投影表）：

```sql
create table episode (
  id             text primary key,
  tenant_id      text not null,
  user_id        text not null,
  project_id     text,
  canvas_id      text,
  turn_no        int  not null,
  kind           text not null,   -- turn | commit | tool | feedback
  payload        jsonb not null,
  schema_version int  not null,
  created_at     timestamptz not null default now()
);

create index episode_scope_idx on episode (tenant_id, canvas_id, turn_no desc);
```

M2 记忆条目，`active` 状态在同一个 scope 下对 `key` 唯一：

```sql
create table memory_item (
  id             text primary key,
  tenant_id      text not null,
  user_id        text,
  project_id     text,
  layer          text not null,        -- M2 | M3
  key            text not null,
  value          jsonb not null,
  confidence     numeric(4,3) not null,
  evidence_count int not null default 0,
  status         text not null,        -- candidate|active|superseded|archived|contradicted|tombstone
  supersedes     text,
  valid_from     timestamptz not null,
  last_hit       timestamptz,
  schema_version int not null
);

create unique index memory_active_uniq
  on memory_item (tenant_id, coalesce(user_id,''), coalesce(project_id,''), key)
  where status = 'active';
```

向量索引单独一张表，只存 `id + embedding + model_version`，和主表不做 join：先查向量拿 id，再 `where id = any($1)` 批量取详情。换 embedding 模型时整表重建，不影响主表。

`payload` 走 JSON 是刻意的例外：它只写不查，是原始报文，且带 `schema_version`。任何需要按字段过滤的东西，都要投影成列或者单表，不要伸手进 JSON 里做路径查询——那会在数据量上来之后变成全表扫。

## 12. 怎么知道它有用

| 指标 | 怎么量 | 目标 |
| --- | --- | --- |
| 指代消解 | 抽 200 条「上次/那个/还是」类指令，人工判是否改对了对象 | ≥90% |
| 偏好命中 | 用户没有再次重复同一条指令的轮次占比 | ≥85% |
| 撤销率 | 每 100 次生成被撤销的次数 | 逐月下降 |
| 编辑深度 | 接受后用户又改了几个 op | 下降 |
| 污染率 | 抽检 `active` 条目中由 agent 自证来源的比例 | 0 |
| 编译延迟 | p50 / p95 | 40 / 80ms |
| 降级率 | 超时降级占比 | <2% |
| 遗忘准确率 | 删除后跑检索测试 | 100% |

其中「指代消解」「编辑深度」「污染抽检」要靠人判，其余都能自动算。

这套指标不是为评估单独埋的点，它和第 10 节的自演进用的是同一份数据：`decision_log` 加上信号表，既能算这里的指标，也能算归因样本。多埋一套「给报表看的」指标是浪费，而且两套口径迟早会对不上。

回路本身也要两个健康指标：**自动回滚率**（灰度里因 guardrail 触发回滚的比例）和**日志降级率**（`decision_log` 写入失败或超时的占比）。前者长期不降，说明候选质量差；后者一旦抬头，自演进其实已经停了，而系统看起来一切正常。

值得单独投入的标注只有一样：**200 条带指代的真实指令，配上当时的画布快照**。这一份数据同时能测编译器、检索器和整个 M0 的组装，是全系统性价比最高的一笔投入。

## 13. 落地顺序

顺序错了会浪费两个月。

| 阶段 | 做什么 | 为什么排这里 |
| --- | --- | --- |
| 第 1–2 周 | M1 事件表、画布快照、`canvas.commit` | 先把事实留下来，后面所有东西都能重算 |
| 第 3 周 | 编译器 v0：品牌 + 焦点子图 + 最近轮次，不做检索；`decision_log` 从第一天就写 | 没有检索也能显著改善体验；日志不补历史，越晚开写，能回放的数据越少 |
| 第 4 周 | 向量召回 + M2 抽取（只写候选） | 有 M1 才有 ground truth |
| 第 5 周 | 巩固 job、冲突队列、生命周期 | 决定库会不会变脏 |
| 第 6 周 | 回放 + 影子 + 快环三种配比 | 有数据可回放，自演进才有意义 |
| 之后 | M3 技能挖掘、M4 风格指纹 | 依赖前面的稳定信号 |

反过来做——先搭向量库、先做抽取、先让模型「反思」——会在没有事实基础的情况下训练一个抽取器，然后花更久时间排查它为什么越用越偏。

## 14. 几个反模式

**把画像写成一段自然语言塞进 system prompt**。不可合并、不可失效、不可解释，改一个字全靠重写。它看起来最像「记忆」，实际是最难维护的形态。

**让模型给自己打分**。分数会朝它擅长生成的方向漂，而不是朝用户想要的方向。

**在一个 turn 里同步更新画像**。延迟直接压在用户等待上，收益要等到下一轮才体现。做异步。

**只增不删**。半年后库里全是过期偏好，而且它们互相矛盾的程度超过了模型的处理能力。衰减、归档、墓碑三件套缺一不可。

**用一个 embedding 空间混存品牌、素材、对话**。品牌需要的是确定性命中，素材需要的是关系查询，对话需要的是时间序。三种检索需求塞进一个索引，谁的召回都不对。

**把记忆做成设置页**。「请选择你的风格偏好」这种表单的完成率极低，且填出来的东西和实际行为经常相反。让用户在创作中做选择，行为本身就是标注。

## 15. 如果只做三件事

给同样在做这件事的人，我的建议是按这个顺序：

1. **先把事件流和画布快照做对**。这是一切的地基。没有它，你无法回答「为什么变成这样」，也无法回放、无法评估、无法自演进。
2. **再把编译器做出来，哪怕只注入三样东西**——品牌约束、焦点子图、最近三轮。这一层的收益在第一天就能被用户感知，而检索的收益要等到库里有东西。
3. **最后才做抽取和自演进**。有了前两步，你才有一个能测量的系统；没有它们，抽取出来的每一条记忆都无从验证。

至于向量库选哪个、用不用图数据库、要不要上知识图谱——这些在架构里都是可替换的零件。真正决定这套系统能不能用的是两件事：**证据链是否完整**，以及**每一次改动是否可回放**。
