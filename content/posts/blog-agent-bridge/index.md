> 这是待评审的设计稿，代码还没写。结论先放这里：这套东西不需要 NAT 穿透，也不需要把静态站改成动态站。缺的只是一条 Mac 主动连出去的常驻连接、一张任务表，和一个在本机跑 `dsh headless` 的小进程。总工作量 4.5–5 个工作日。

## 0. 要做到的三件事

1. 用 agent 发文章时，文章里带上来源会话（哪一次对话写出来的）。
2. 读者在页面上写批注或回复时，消息能送到那条会话，会话被唤醒、接着原来那轮对话继续回答。
3. 回答写回页面，页面自己更新，不用手动刷新。

验收按一条具体路径看：在《协同编辑的三种答案》里选一句、写「这里为什么不用向量时钟？」，两分钟内那一条批注下面出现 AI 楼层，并且回答能引用文中别处的细节。这一点是硬指标：能引用的回答说明会话上下文真的在，而不是套模板。

## 1. 现状和三条硬约束

| 组件 | 位置 | 现在负责什么 |
|---|---|---|
| nginx + Hugo 产物 | 62.234.122.22 `/var/www/blog` | 只发静态文件，不执行代码 |
| notesd（Python，stdlib + SQLite） | 同机 `127.0.0.1:8099` | 存笔记、阅读进度，`/api/` 由 nginx 反代 |
| DSH 会话 | 你的 Mac，`~/.dsh/sessions/` | 每次对话的事件日志，上下文在这里 |

约束一：静态站没有执行能力，任何「收到评论就做点什么」都得有第二个进程。约束二：会话数据只在 Mac 上，服务器拿不到，也不该复制一份上去。约束三：Mac 在 NAT 后面，公网进不来。

## 2. 通道怎么选

候选有三条：

| 方案 | 做法 | 代价 |
|---|---|---|
| 反向隧道 | 复用 8443/8444 那条 ssh 反向转发，再加一个端口 | 隧道要有人守着。我刚在服务器上看，7681 和 3001 现在都没在监听，说明它已经断过一次 |
| NAT 穿透 | frp / cloudflared / tailscale 之类 | 多一个外部依赖，多一份证书与暴露面，换来的延迟收益很小 |
| 出站长连接 | Mac 主动 `GET /api/jobs/stream`，服务器顺着这条连接写事件 | 只需要一个 HTTP 客户端，断线重连 1s→30s |

选第三条。NAT 挡的是「外面主动连进来」，挡不住「里面主动连出去」；连接建立之后就是双向的，服务器随时可以往回写。这在效果上就是推模式，延迟和长连接一样，但不用打洞。

## 3. 整体结构

{{< fig "diagrams/01.svg" "浏览器、服务器、Mac 三边的连接关系。橙色是常驻长连接与它承载的事件，灰色是普通请求与进程调用" >}}

四条链路，各自职责单一：

1. 页面 → nginx → notesd：写批注、写回复、订阅事件。
2. notesd ↔ SQLite：笔记、进度、会话映射、任务队列，四张表同一个库。
3. Mac 上的 bridge → notesd：一条 SSE 长连接承载「有新任务」的事件，另用普通 POST 交回结果。
4. bridge → `dsh --profile headless` → 原会话：一次任务起一个进程，跑完就退。

bridge 只做三件事：连上去、领任务、调命令。它不读文章内容，也不拼 prompt 之外的任何业务判断。

## 4. 一条批注走完的十步

{{< fig "diagrams/02.svg" "从提交批注到页面出现 AI 楼层，十步。第 3 步和第 10 步都是 SSE，方向相反：一条推给 Mac，一条推给浏览器" >}}

时间预算：第 1–4 步 1 秒内；第 5 步起进程 1.2 秒；第 6–7 步 30 秒到 3 分钟，取决于文章长度和模型速度；第 8–10 步 1 秒内。

页面在第 9 步之前显示「已收到，AI 正在处理」，这行字由 job 状态驱动，不让前端自己猜。等得久的时候，用户能看见队列里排到第几位。

## 5. 数据模型与接口

四张表，都在现有的 `notes.db` 里：

```text
sessions(slug PK, session_id, workspace, title, token, created)
jobs(id PK, slug, note_id, session_id, prompt, status,
     attempts, heartbeat, error, created, updated)
notes(...)      -- 已有
progress(...)   -- 已有
```

`workspace` 这一列不能省。会话按 workspace 分目录存放，`dsh headless --session-id` 只在对应的 workspace 下认得出这个 id，bridge 得先 `cd` 过去。

接口在现有 notesd 上加五个：

| 方法 | 路径 | 用途 |
|---|---|---|
| GET | `/api/jobs/stream` | SSE，bridge 订阅；断线重连后先补拉 `pending` |
| POST | `/api/jobs/<id>/claim` | 认领，`pending → running`，写心跳 |
| POST | `/api/jobs/<id>/done` | 交付结果，`running → done` |
| POST | `/api/jobs/<id>/fail` | 失败，决定退回 `pending` 还是 `blocked` |
| GET | `/api/notes/<slug>/stream` | 页面订阅，`note.updated` 事件 |

回复仍然走已有的 `POST /api/notes/<slug>/<id>/replies`，不新开一条写入路径。这样楼层顺序、50 层上限、`thread` 结构都不用再实现一遍。

## 6. 失败路径

{{< fig "diagrams/03.svg" "四个状态。失败退回 pending 还是直接 blocked，取决于重试次数和失败原因" >}}

| 情形 | 表现 | 处理 |
|---|---|---|
| Mac 关机或休眠 | `pending` 堆积，页面停在「排队中」 | 开机后 bridge 重连，先补拉全部 pending |
| 会话正开在 GUI 里 | `dsh` 抢锁失败 | 退避重试 3 次（5s、15s、45s），仍失败置 `blocked`，页面写明「会话正被占用」 |
| 进程中途被杀 | `running` 但心跳断了 | 心跳超 10 分钟判死，放回 `pending`，`attempts + 1` |
| 回复写入失败 | 回答已生成但没存上 | 保留结果，重试写入 3 次，避免重跑整个会话 |

`blocked` 不是终点。页面上那条批注显示「AI 回复失败」加重试按钮，点一下把同一条 job 放回 `pending`。

## 7. 安全边界

- 读保持公开，和现在一样。
- 写要口令：沿用现有的 `NOTES_EDIT_KEY`，页面第一次写时弹一次，存在本机。
- bridge 用独立 token，只能调 `claim`/`done`/`fail`，不能读写笔记本身。
- SSE 订阅只推 slug 维度的事件，不推全文；每 IP 同时最多 3 条连接。

## 8. 成本与落地顺序

| 阶段 | 内容 | 天数 |
|---|---|---|
| M1 | `sessions` 表、文章 front matter 写入、模板展示来源会话 | 1 |
| M2 | `jobs` 表、四个接口、SSE 推送、过期与重试 | 1.5 |
| M3 | bridge（launchd、重连、单并发、锁重试） | 1.5 |
| M4 | 页面增量渲染、「回复中」状态、失败重试按钮 | 0.5 |
| M5 | 测试（断网、锁冲突、重连、超时）与上线 | 1 |
| 合计 | | 4.5–5 |

运行成本按 token 算：每条评论唤醒一次完整会话，长文一次 10 万 token 量级，短文一万出头。按你实际用的模型价格换算，一天二十条的话是笔可见但不算大的开销。真正贵的是延迟等待，不是钱。

## 9. 不做什么

- 不把静态站改成动态站，页面仍然是构建产物。
- 不做多人协作编辑，批注仍然是一人写、全家看。
- 不承诺秒回，端到端按 1–3 分钟设计。
- 不做跨文章聚合问答，一次批注只唤醒它所属的会话。

## 10. 还差两个决定

1. 什么批注才触发回复？全部触发，还是只回带问号的？全回会让每条划线都跑一次会话，成本线性上涨；只回问号，写「这里写错了」就不会有回应。我倾向：带问号或含「为什么/怎么/是不是」的触发，其余只存不回，页面上留一个「让 AI 回答」的按钮手动触发。
2. 回复要不要显示你在会话里说的话？会话可能很长，只回最后一段结论更干净，但读者看不到推理过程。我倾向只回最后一段，长于 400 字先给摘要。

这两条确认之后，就可以按 M1–M5 排计划。
