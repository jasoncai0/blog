> 这篇文章写的是我给设计 Agent 搭评测系统的那套东西：一个 Task 怎么定义，题从哪来，尺子怎么分四层，回测怎么接进 CI，线上坏了怎么归因。骨架借自美团技术团队的《Agent 评测白皮书》，落点是一个有画布、有品牌约束、产物是像素的设计 Agent。文中的条数、阈值、单价都是可以直接开工的默认值，不是线上实测；每个数字为什么在这个量级，理由写在旁边。

## 0. 评测系统交付的是判断，不是分数

改了一版提示词，跑二十条 case，感觉变好了，发上去。第二天客诉多了，或者设计师在群里说「最近怎么老是把 logo 压到字上」。

这类翻车和模型能力关系不大。真正缺的是一个能回答「这次改动能不能发」的装置：同一批题、同一把尺子、同一个环境，跑出来的结论和上次可比。

设计 Agent 让这件事变难的地方有三处。产物是一张图，人眼抽样看五张就累了，剩下的靠运气。标准散在设计师脑子里，「这个不够高级」没法直接变成代码。一次任务要跑几十个 op、出几张候选图，跑一轮就有成本。

所以评测系统的产出物不是排行榜，是四样东西：一批冻住的题、一把标定过的尺子、一道能拦住合并的门禁、一条能把线上问题搬回题集的回路。

{{< fig "diagrams/design-agent-eval-01.svg" "评测系统的四个模块与两条 Loop。离线守住已知，在线发现未知，归因把线上的异常搬回评测集，观测在底下托住全部三段。虚线是资产复用，实线是流转。" >}}

这套结构里，评测集和 Rubric 是唯一有复利的部分。门禁会改，看板会换，题和尺子会一直用下去。

## 1. 设计 Agent 和文本 Agent 的五处不同

把通用 Agent 评测的做法直接搬过来会漏东西。差别集中在五个地方。

| 维度 | 文本 Agent | 设计 Agent | 直接后果 |
| --- | --- | --- | --- |
| 正确答案 | 一个，或一小族 | 一族，且好坏连续 | 没法用精确匹配，只能分层加阈值 |
| 判分方式 | 规则、单测、语义相似 | 规则 + 视觉测量 + 裁判 + 人评 | 判分器本身要校准 |
| 产物形态 | 文本、diff | 像素图 + 画布状态 | 要比对图层、位置、颜色，不止比文本 |
| 过程可见性 | 调用链基本够 | 调用链 + 画布 op 流 | 得专门记 op，否则改错哪一层说不清 |
| 单次成本 | 几厘到几分 | 一次出图几毛，一轮回测几百块 | 不能每次都跑全量，必须分层 |

第一行决定了 Rubric 的形态。文本任务可以写「答案等于 X」，设计任务写不了。能写的是「主标题字号在全图前 10%」「品牌色 ΔE ≤ 3」「logo 留白不小于 1 倍字高」这类可判定的命题。

第二行决定了预算结构。判分不是免费的，尤其 L2 用多模态模型逐张打分的时候。一把不准的尺子比没有尺子更贵，因为它会让团队按错误方向优化。

第四行是设计 Agent 特有的。用户说「标题再收一点」，Agent 改了字号、改了位置、还顺手换了配图。如果只记最终图，你没法判断它是改对了还是碰巧看起来还行。画布 op 流能回答「它动了什么」。

第五行决定了工程形态。全量回测放在合并前，冒烟放在 PR 上，全量加多次 trial 放夜里。

## 2. 借一副骨架：四个模块落到 Lovart 的七层上

美团那篇白皮书把评测拆成四个模块：离线评测、在线评测与监控、Case 挖掘与归因、观测基建。三条能力是发现问题、定位问题、驱动演进。两条 Loop 咬合在一起：线上的异常样本进 Case 池，归因之后要么改 Agent，要么改评测集和 Rubric。

这套骨架和具体业务无关，所以能直接借。落到 Lovart 的七层架构上，每个模块都有明确的承载体。

| 白皮书的模块 | 落在哪一层 | 具体载体 | 起点 |
| --- | --- | --- | --- |
| 离线评测 | L5 评估 + CI | 冻结 Task 集、回测脚本、三档门禁 | 从零建 |
| 在线评测与监控 | L5 + L6 治理 | 影子、AB、周巡检、告警 | 有一部分 |
| Case 挖掘与归因 | L6 + 周会 | Case 池、归因表、owner 指派 | 口头在做 |
| 观测基建 | L0–L4 全链路 | trace、画布 op 流、版本号、判分记录 | 埋点不全 |

第二条 Loop 在这套架构里有个现成的落点：L5 的 Review Agent 本来就是裁判。它平时在线上拦违规，回测时可以把同一套判定拿过来当 L0 和 L1 的执行器。裁判复用，是这套系统里省下来的最大一笔工程。

第一条 Loop 的落点是 Case 池。线上任何一条被 Review 拦下、被用户退回、被设计师手工改过的任务，都应该能生成一条候选 case。它进池子之前要先过一道判断：这条是 Agent 错了，还是尺子错了。

两条 Loop 共享同一批样本，这是它们咬合的地方。分开建两套样本，最后一定会出现「线上修好了，回测还是红的」这种对不上的状态。前作里写过这套自调优的七步闭环，评测系统是它的量具部分。

## 3. 一个 Task 长什么样：三段，七项冻结

离线评测要控制变量，Task 的定义就必须包含三样东西：给什么、期望发生什么、怎么算过。

{{< fig "diagrams/design-agent-eval-02.svg" "一个设计 Task 的三段。输入包和过程期望一起冻结，验收才有意义；只换模型、不换输入包，两次分数才可比。" >}}

写成文件大概是这样：

```yaml
task_id: e2e-poster-0031
module: poster          # poster | ecom | longform | deck | edit | brandkit
difficulty: hard
input:
  brief: "秋季新品，主标题「薄雾」，副标题一行价格，渠道天猫首焦"
  canvas_rev: cvs_8f21@rev-47
  asset_rev: brand_kit@v12
  memory_rev: mem_9c02@rev-8
  tenant: acme
process:
  must_call: [brand_check, export_preflight]
  must_hit: [logo_primary, product_packshot_02]
  forbid: [full_repaint, overwrite_user_layer]
  budget: {tokens: 60000, images: 4, seconds: 900}
accept:
  l0: all
  l1_pass_rate: 0.95
  l2_weighted: 0.80
  l3_win_rate: 0.50
reference: refs/poster-0031.png
rubric_version: r18
```

输入包里的 `canvas_rev` 和 `memory_rev` 是最容易漏的两项。画布是状态，记忆是上下文，两者都会随用户操作变化。不冻结这两个版本号，同一个 Task 下周跑出来的分数和本周不可比，团队会开始怀疑评测本身。

过程期望不是标准答案。写「先排版后换图」没有意义，写「必须调用 brand_check」「禁止覆盖用户图层」才有意义。前者是可断言的动作，后者是可检测的违规。

验收部分在下一节展开。

七项冻结清单：`canvas_rev`、`memory_rev`、`brand_kit_rev`、`prompt_version`、`model + seed`、工具桩版本、`rubric_version`。任何一项变了，历史分数作废，整批重跑。这条规矩听起来笨，它能省掉后面无数场「到底是不是同一个东西」的争论。

## 4. 题集：两类题，四个池子

评测集分两棵树。端到端按功能模块切，回答「要不要报警」。过程按能力层切，回答「报警之后找谁」。

{{< fig "diagrams/design-agent-eval-03.svg" "评测集的分层。端到端按功能模块切，负责回答「要不要报警」；过程按能力层切，负责回答「报警之后找谁」。左侧是 120 条的模块分布。" >}}

只有端到端，你知道坏了但不知道哪坏，排查全靠猜。只有过程，每个模块的单测都绿，用户还是不满意，因为没人测「合起来能不能交付」。

端到端 120 条按模块分：海报 30、电商主图 25、长图 20、PPT 15、改图 20、品牌套件 10。这个配比跟着真实流量走，不跟着团队组织架构走。

过程 200 条按能力层分，每层 40 条：

| 能力层 | 每条测什么 | 判法 |
| --- | --- | --- |
| 召回 | 品牌节点、产品图有没有进 top-8 | 命中率、排序位置 |
| Skill 路由 | 该调的没调，或调错工具 | 调用序列断言 |
| 上下文预算 | 长会话后段品牌约束是否还在 | 关键约束存活率 |
| 品牌校验 | ΔE 超限、字体替换有没有被拦 | 拦截率、误拦率 |
| 画布写入 | 层级、覆盖、快照一致性 | op 断言 |

题集按用途再分四个池子。这四个池子的维护节奏不一样，混在一起管会烂。

| 池子 | 从哪来 | 规模 | 进不进 CI | 维护 |
| --- | --- | --- | --- | --- |
| 黄金集 | 设计师人工精标，覆盖 6 个模块 | 40 | 进，算分基准 | 半年复核一次 |
| 必过集 | 每次线上事故回灌，一条对一个 bug | 80 | 进，一票否决 | 只增，季度归档 |
| 挑战集 | 新能力、新品类、竞品对比 | 30 | 不进 | 每季度换掉 1/3 |
| 错题集 | 归因确认「Agent 错」的 case | 只增 | 抽 20% 进冒烟 | 每月去重 |

错题集的回报最直接：犯过的错不再犯。黄金集的价值容易被低估，它定义的是「到什么程度算行」。没有黄金集，团队会一直争论「这版是不是比上版好」，争不出结论。

挑战集要定期换血。业务扩量之后，半年前的边界题早就不边界了，留着只会让分数虚高。

题集本身也会腐化。业务从单图转向多图、从海报转向详情页，题没跟着变，评测就在测一个不存在的产品。每季度做一次覆盖检查：按模块 × 难度列一张矩阵，空格就是缺口。

## 5. 尺子：18 条 Rubric 分四层

Rubric 要做的事是把「做得好不好」拆成一组是或否的检查项。不要用 1 到 5 分，五个人打出来是五个分布，校准成本高到没法维护。

分层的依据是「谁来判、判错的代价多大」。越往下越主观，判分器越贵，校准越频繁。

{{< fig "diagrams/design-agent-eval-04.svg" "四层 Rubric 与判分器。越往下越主观，判分成本越高，校准频率也越高。L0 和 L1 不进加权，避免用高分掩盖硬伤。" >}}

| 层 | # | 检查项 | 怎么判 | 门槛 |
| --- | --- | --- | --- | --- |
| L0 | 1 | 画布尺寸与安全区 | 读场景图，比对渠道规格 | 任一元素越界即失败 |
| L0 | 2 | 品牌色 | 采样主色，ΔE2000 | > 3 即失败 |
| L0 | 3 | 品牌字体 | 字体名、字重、度量 | 被替换即失败 |
| L0 | 4 | logo 完整 | 模板匹配 + 留白区检测 | 变形、遮挡、压字即失败 |
| L0 | 5 | 禁用词与敏感内容 | 文本抽取 + 词表 + 分类器 | 命中即失败 |
| L0 | 6 | 导出规格 | 分辨率、格式、色彩空间 | 不符即失败 |
| L1 | 7 | 图层结构 | 场景图节点树 | 层级错或命名缺失 > 2 处 |
| L1 | 8 | 元素越界与裁切 | 几何判定 | 主要元素被裁切 |
| L1 | 9 | 文案溢出 | 文本框与容器比对 | 溢出 > 0 行 |
| L1 | 10 | 对象数量与文件大小 | 计数 | 超上限 20% |
| L1 | 11 | 图片分辨率 | DPI 与像素 | 低于印刷阈值 |
| L1 | 12 | 可编辑性 | 文字未转曲、组件完整 | 关键文本被转曲 |
| L2 | 13 | brief 覆盖度 | 裁判按清单逐条核 | 加权 ≥ 0.85 |
| L2 | 14 | 最小改动 | 与用户图层做 diff | 未改区域被重绘即扣分 |
| L2 | 15 | 图文语义 | 图与文案是否对得上 | ≥ 0.80 |
| L2 | 16 | 信息层级 | 主、次、正文是否可辨 | ≥ 0.80 |
| L3 | 17 | 版式节奏 | 与参考稿成对比较 | 胜率 ≥ 50% |
| L3 | 18 | 整体完成度 | 是否可直接交付 | 胜率 ≥ 50% |

L0 六条是一票否决。它的作用不是打分，是保证「不该发的东西发不出去」。一条海报品牌色错了，其他十七项全满分也没有意义。

L1 六条是结构正确性。它的特点是能用程序判，单条几十毫秒，零方差。这一层做到位，回测成本能降一个数量级。

L2 四条测意图。改没改对地方、有没有动不该动的、图文对不对得上。这层必须用多模态裁判，也是最需要校准的一层。

L3 两条测审美。做法是同一 brief 内成对比较：给裁判或设计师看 A、B 两版，选一个更好的。不跨 brief 打绝对分，跨了就没有意义。

聚合公式：

```
Pass = 全部 L0
     ∧ L1 通过率 ≥ 95%
     ∧ L2 加权 ≥ 0.80
     ∧ (L3 胜率 ≥ 50% ∨ 人工复核通过)
```

权重只给 L2 和 L3。L2 四项按覆盖 0.4、最小改动 0.3、语义 0.2、层级 0.1；L3 两项各 0.5。L0 和 L1 不进加权，是为了避免「十八项里过了十六项，分数 0.89，可以发」这种结论。硬伤就是硬伤。

## 6. 判分器：三种，各自会怎么错

尺子定完，接下来是执行器。三类自动判分器加人工抽检，覆盖四层，各自的误差模式完全不同。

| 判分器 | 覆盖 | 单条成本 | 主要误差 | 校准动作 |
| --- | --- | --- | --- | --- |
| 规则与几何测量 | L0 全部、L1 全部 | < ¥0.001 | 字体转曲后识别不出替换 | 每周抽 20 条人工核对 |
| 多模态裁判 | L2 四项 | ¥0.02–0.05 | 偏好留白多、文字少的图 | 50 条双标，κ ≥ 0.6 |
| 成对比较 | L3 两项 | ¥0.04 / 对 | 位置偏差，总选左边 | A/B 正反各跑一次取平均 |
| 人工抽检 | 各层抽 5% | ¥8–15 / 条 | 疲劳、品牌偏好 | 双人标注 + 争议仲裁 |

多模态裁判的偏好很稳定：干净的、留白多的、字少的图得分高。这在海报任务上问题不大，在电商主图上会系统性压低信息密度高的正确稿。解决办法是把「信息密度」写进 Rubric 的检查项，让它变成显式判定，不靠裁判自己权衡。

裁判也会漂移。换一版模型，同一批图的分数可能整体偏移 0.05。所以裁判提示词要版本化，和 `rubric_version` 一起冻结；换模型必须重跑锚点集。

校准有四个数要看：

- 双人标注一致性：50 条样本，Cohen's κ ≥ 0.6。低于这个数，说明标准本身没写清。
- 人机一致率：裁判与专家判定一致的比例 ≥ 85%。
- 重测差异：同一张图跑两次，分数差 ≤ 0.03。
- 锚点集：30 条固定的图，每季度复测一次，看整体是否偏移。

人工抽检放在最后，不是因为不重要，是因为贵。它的作用是给自动化判分做校准，不是替代。

## 7. 回测：冻住变量，跑够次数

回测是评测集、尺子、执行环境三样东西合起来跑一遍。工程上有四个决定。

{{< fig "diagrams/design-agent-eval-05.svg" "回测流水线与三档门禁。红灯阻断合并，黄灯要 owner 签字，绿灯才进影子。门禁不接 CI，前面四段都只是报表。" >}}

第一，每个 Task 跑 3 次 trial。设计 Agent 有采样随机性，跑一次的好成绩可能是运气。看通过率，不看单次最好成绩。用 Pass@k 的时候要写清 k，不然「通过率 60%」这句话没有意义。

第二，一次跑 4 个候选。真实产品里用户也是从几张里挑，评测要贴近这个形态。候选之间可以互相比较，L3 的成对数据就是这么来的。

第三，分层跑。PR 上跑 20 条冒烟，合并前跑全量 120 条，夜里跑全量加过程集。全量一轮 1440 张图，按 ¥0.15–0.30 一张算，单轮 ¥216–432。这个钱不能每个 PR 都花。

| 触发 | 跑什么 | 时长 | 阻断 |
| --- | --- | --- | --- |
| PR 打开 | 20 条冒烟 × 1 trial × 2 候选 | 3–5 分钟 | 红灯 |
| 合并前 | 120 条 × 3 trial × 4 候选 | 45–70 分钟 | 红灯、黄灯 |
| 每晚 | 全量 + 过程集 200 条 × 2 trial | 2–3 小时 | 只出报告 |
| 发布前 | 挑战集 + 影子 200 条真实请求 | 半天 | 人工看 |

第四，门禁分三档。只有红灯能真正拦住合并，这就是它存在的全部意义。

| 档 | 条件 | 动作 |
| --- | --- | --- |
| 红 | L0 任一失败，或 L1 通过率 < 90%，或均分环比掉 > 5pt | 阻断合并 |
| 黄 | L1 在 90–95%，或 L2 掉 3–5pt，或单任务成本涨 > 20% | owner 书面确认 |
| 绿 | 全部达阈值，且 L3 胜率不低于基线 | 可合并，进影子 |

还有一个容易漏的检查：环境保真度。同一批 100 条，离线跑一遍、线上影子跑一遍，结论一致率低于 90%，说明离线环境和线上不是一回事。先修环境，不要修 Agent。这项检查每季度一次。

## 8. 在线：影子、AB、巡检

离线只能发现已知。题集里没有的场景，跑一万遍也测不出来。线上要补三件事。

{{< fig "diagrams/design-agent-eval-06.svg" "在线三条线。影子在上线前兜底，AB 在放量时分桶，巡检每周把离线集拿线上配置重跑一遍。" >}}

影子模式用在上线前。真实流量复制一份给新版本，结果不回给用户，只用来比对新旧两版的产物。它比的是成对胜负和硬约束违规，不是平均分。新版本不劣于线上，才允许放量。

AB 用在放量时。按租户或会话分桶，先放 5% 到 10%。主指标是一次通过率，护栏是时延、成本、违规率。主指标涨 2pt 但 P95 涨了 40%，这次改动不算成功。

巡检是评测和监控的交集。每周抽 100 条离线集，用线上配置重新跑一遍。分数漂移超过 3pt 就触发归因。它的好处是不依赖用户反馈，能在客诉之前发现退化。

监控和在线评测要分开看。在线评测回答「系统工作得好不好」，监控回答「系统有没有在正常工作」。工具成功率 100%，但返回的数据是错的，监控全绿，评测全红。两个都要有。

| 组 | 看什么 | 设计 Agent 特有 |
| --- | --- | --- |
| 可用性 | 工具成功率、失败率、超时率、异常类型 | 出图队列积压、渲染服务降级 |
| 成本 | 单任务 token、步数、P95 时延 | 单任务出图张数 |
| 行为 | 任务类型分布、Skill 频次、平均轮次 | 画布 op 数量、撤销率 |
| 质量 | 一次通过率、Review 违规率、导出率 | 文字渲染失败率、品牌色 ΔE |

稳定性和行为指标要一起读。完成率掉 5pt，同时某个工具失败率从 2% 涨到 15%，这是工程问题。工具全绿，但对比类任务占比从 10% 涨到 35%，这是用户结构变了，评测集该扩。

## 9. Bad Case 从哪来：六个来源

单一来源一定有盲区。线上反馈只能看到愿意抱怨的人，监控只能看到已经被指标刻画的维度，规则挖掘只能看到已经想到的风险。

| 来源 | 能看到什么 | 看不到什么 | 频率 |
| --- | --- | --- | --- |
| 线上反馈 | 用户明确不满意的地方 | 默默流失的人 | 实时 |
| 监控异常 | 失败、超时、成本突增 | 成功但结果错 | 实时 |
| 规则挖掘 | 已知风险的变体 | 没想到的风险 | 每日 |
| 随机采样 | 没想到的问题 | 无，但命中率最低 | 每周 |
| 设计师访谈 | 标准的边界、审美判断 | 规模化 | 每月 |
| 竞品对比 | 能力差距 | 内部实现问题 | 每季度 |

随机采样不能省。它成本最高、命中率最低，但它是唯一能发现「没人想到要测」的问题的来源。每周抽 50 条真实任务，人工看一遍，产出通常比看一周的告警更有价值。

Case 池分两个标签：Good 和 Bad。Good case 用来定义下限，也是黄金集的补充来源。Bad case 进错题集，归因之后决定走哪条出口。

## 10. 归因：十个筐，两条出口

一条失败的任务进来，先问「哪一段坏了」，再问「是 Agent 坏了还是尺子坏了」。

{{< fig "diagrams/design-agent-eval-07.svg" "归因的十个筐。前九个改 Agent，第十个改尺子。两条出口都要有人走，只走第一条会把 Agent 训成迎合评测的样子。" >}}

| # | 环节 | 典型信号 | owner |
| --- | --- | --- | --- |
| 01 | 意图理解 | 首轮修改集中在尺寸、风格词 | 策略 |
| 02 | 资产召回 | top-8 里没有品牌节点，命中率 < 60% | 检索 |
| 03 | Skill 路由 | 该调的没调，或调错工具 | 能力 |
| 04 | 上下文预算 | 长会话后段品牌约束丢失 | 上下文 |
| 05 | 生成能力 | 文字糊、logo 变形、结构崩 | 模型 |
| 06 | 品牌约束 | ΔE 超 3、字体被替换、logo 位移 | 校验 |
| 07 | 画布写入 | 层级错、覆盖用户图层、快照不一致 | 编排 |
| 08 | 工具环境 | 超时、降级、素材 404 | 工程 |
| 09 | 成本截断 | 提前收敛、降级模型、少出候选 | 预算 |
| 10 | 评测本身 | 人判好机判差，或机判好人判差 | 评测 |

归因顺序有讲究。先看 trace，再看模型；先查硬约束，再谈审美。一条图看起来「不够高级」，可能只是 logo 位置偏了 8px，修完就对了。直接归到「模型审美不行」，会去调一个不需要调的东西。

第十个筐是这套系统里最重要的设计。负向 case 有两条出口：进 Agent 迭代，修复、回测、上线；或者校验 Rubric，判错了就改标准，case 进错题集。

很多团队只走第一条。结果是 Agent 被优化成「迎合评测标准」，而不是「解决用户问题」。Rubric 里写「留白不小于 20%」，Agent 就学会把所有东西缩小；写「对比度不低于 4.5」，它就学会加黑边框。标准是手段，交付是目的，这条边界要有人守。

具体做法是每周一次三十分钟的归因会，只看五条 case，每条给出结论和 owner，结论必须落到「改什么」上。第十类占比超过 10%，就停下来先校准尺子。

## 11. 观测：trace 里少了什么，归因就断在哪

归因高度依赖观测。看不见的问题，基本不可能被稳定解决。

| 字段 | 记什么 | 少了会怎样 |
| --- | --- | --- |
| trace_id、task_id | 串起一次任务的所有调用 | 只能按时间猜 |
| canvas_rev | 起始快照 + 每 50 步快照 | 复现不出当时的画布 |
| memory_rev | 注入了哪几个槽、各占多少 token | 分不清是模型错还是上下文缺 |
| asset_rev | 品牌包、素材、先例的版本 | 素材换了导致的差异算到模型头上 |
| prompt_version | 系统提示、Skill 描述、裁判提示 | 改了什么无法对照 |
| model + seed | 模型名、版本、温度、seed | 换模型后的回归无法定位 |
| 召回 | top-k 列表与分数 | 召回缺失这一类永远查不出 |
| Skill 调用 | 入参、出参、耗时、状态 | 工具超时和降级看不见 |
| 画布 op 流 | op 类型、目标、结果、被拒原因 | 画布写错无法复盘 |
| 判分记录 | 每条 Rubric 的判定与证据 | 争议时说不清为什么扣分 |
| 成本 | token、图数、时延 | 优化没有基线 |

最小可归因的标准只有一条：任取一条 Bad Case，能凭记录把它重放出来。做不到这条，就说明还缺埋点。

画布 op 流是设计 Agent 特有的部分。它记录的不只是最终状态，还有每一步意图：想改哪个节点、改成了什么、有没有被拒绝。用户说「它把我原来的标题删了」，op 流能直接指到那一步。

埋点有成本，保留期要分级。全量 trace 保留 30 天，聚合指标保留一年，判分证据和产物图按租户策略保留。

## 12. 指标：一个北极星、四个护栏、三个切片

指标的定义比数值重要。同一个名字，两种口径，团队会各说各话。

北极星是一次通过率：不需要返工就被采纳或导出的任务数，除以总任务数。口径要写死三件事：怎么算采纳、返工窗口多长、按什么维度聚合。

四个护栏：

| 指标 | 口径 | 默认阈值 |
| --- | --- | --- |
| P95 时延 | 从提交到出第一版 | ≤ 8 分钟 |
| 单任务成本 | 出图 + 判分 + 存储 | ≤ ¥3.5 |
| Review 违规率 | Review Agent 判违规的任务占比 | ≤ 2% |
| 周回滚次数 | 因质量问题回滚的发布 | ≤ 1 |

三个切片：模块、难度、租户年龄。切片是为了避免辛普森悖论。整体通过率涨了 3pt，可能是新租户大量涌入拉高的，老租户其实在跌。不切片看不出来。

还有一个口径问题：不要用平均分当北极星。平均分会被长尾拉平，一个把 logo 压到字上的版本，可能均分只掉 0.02。北极星要能反映「不能交付的比例」。

## 13. 六周落地

体系是终局，不是起点。冷启动阶段的目标是让飞轮转起来，先跑通一条窄链路。

{{< fig "diagrams/design-agent-eval-08.svg" "六周冷启动。前两周只做观测和题集，第三周才开始写尺子；门禁放在第四周，是因为前三周还没有资格拦人。" >}}

| 周 | 交付 | 验收标准 |
| --- | --- | --- |
| W1 | trace 埋点 + 七项冻结清单 | 能重放 10 条历史 Bad Case |
| W2 | 种子题集 120 + 200 + 双人标注 50 条 | κ ≥ 0.6 |
| W3 | 18 条 Rubric + 判分脚本 | 120 条规则判分 10 分钟内跑完 |
| W4 | 回测链路 + CI 红灯 | 一个故意破坏的 PR 被拦下 |
| W5 | 影子 + 周巡检 | 影子跑 200 条真实请求，一致率 ≥ 90% |
| W6 | 归因会 + 规则沉淀 | 5 条 case 有 owner 和结论 |

顺序不能换。没有 trace，归因靠猜；没有题集，尺子没有对象；没有尺子，门禁拦不准；没有门禁，前面全是报表。

W4 的验收标准值得单独说：故意提交一个把品牌色改错的 PR，看 CI 是不是真的红了。门禁最怕的状态是「配置了但从不触发」，团队会以为有保护。

## 14. 成熟度：四级，看短板

| 能力 | L0 | L1 | L2 | L3 |
| --- | --- | --- | --- | --- |
| 观测 | 只有应用日志 | trace 可重放 | 自动给出归因建议 | 全链路因果 |
| 题集 | 零散 case | 350 条分层 | 自动挖掘补充 | 难度自适应 |
| 尺子 | 人眼看 | 18 条 + 已校准 | 判分自动化 | 能预测业务指标 |
| 门禁 | 无 | CI 红灯 | 分层 + 影子 | 自动灰度决策 |
| 归因 | 口头讨论 | 十个筐 + owner | 规则沉淀 | 反哺题集 |

看短板，不看平均。观测 L1、题集 L3 的团队，归因一定做不动，因为题集里的 case 复现不出来。门禁 L3、尺子 L0 的团队更危险，自动化在放大一个错误的判断。

冷启动阶段，观测 L1、题集 L1、门禁 L1 就够了。这三块凑成最小闭环，能回答「这次改动能不能发」。

## 15. 五个坑

**有评测集，没门禁。** 分数天天看，合并照旧。评测变成报表，团队两周后就没人看了。

**用均分掩盖硬伤。** 十八项过十六项，均分 0.89。发出去之后品牌事故。L0 必须一票否决。

**裁判不校准。** 换了一版多模态模型，分数整体偏移 0.05，团队以为是 Agent 变好了。锚点集和 κ 是防这个的。

**题集不换血。** 业务从单图转多图，题还是半年前那批。分数很好看，线上一直出问题。

**归因只有一条出口。** 所有 case 都归到 Agent 头上，Rubric 永远是对的。半年后 Agent 很会考试，不会干活。

## 16. 如果只做三件事

1. 冻结输入包，先攒 40 条黄金集和 80 条必过集。不用等工具链，一个目录加一份 YAML 就能开始。
2. 把 L0 和 L1 写成规则，接进 CI，红灯阻断合并。这一条做完，硬伤类事故能挡掉大半。
3. 每周一次三十分钟归因会，只看五条 case，结论必须落到「改 Agent」或「改尺子」。

其余的部分，等这三件事跑顺了再补。
