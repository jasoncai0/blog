Agent 操作电脑这件事，落到实现上只有四个决定：界面怎么读、动作怎么落、步骤怎么串、状态存在哪。选完这四个，剩下都是工程细节。

这篇是我对得物技术「羊羽」那篇[《Computer Use与Browser Use：揭秘Agent如何操作电脑和浏览器》](https://mp.weixin.qq.com/s/kWKHYMCwmMFp54iJU3ZkXQ)的整理。原文按「桌面 / 浏览器」分两节讲，我把它的机制拆成上面四个维度重排，顺带补了两处原文只用文字带过的地方。原文声明未经许可不得转载，所以文中的图全部重画，没有复用原图。

先对齐两个名字。Computer Use 指通过操作系统的接口操作桌面软件，Browser Use 指通过浏览器的接口操作网页。分界不在「操作的是窗口还是标签页」，在接口从哪来：前者要可访问性 API、截图、输入注入，后者要 DOM、CDP、标签页管理。这条分界决定了后面每个选择的可用选项。

{{< fig "diagrams/01-layers.svg" "从目标到应用共五层。观察沿左侧上行进入模型，动作沿右侧下行落到界面。模型永远看不到像素和句柄，它只读执行器整理后的结果。" >}}

## 1. 判断和执行分开，是为了让两边各自演化

一次操作要经过三个角色：模型决定做什么，执行器负责看和点，界面是被操作的对象。原文把这条链路拆得很清楚，值得补的是「为什么非得拆」。

模型这一侧三个月换一次，换模型、换提示、换工具描述。执行这一侧很稳定，操作系统的可访问性接口十几年没大改，Playwright 的 API 也基本冻结。拆开之后，换模型不用动执行器，写新执行器不用重调提示。如果两边揉在一个循环里，每次换模型都要重新验证整套点击逻辑。

拆开还有一个不那么明显的好处：失败被分到了两层。模型读错了要改提示或改观察格式，执行器点空了要改定位或换通道。合在一起时，这两种错都表现为「任务没完成」，只能从头查。

原文还有一句提醒：文字未必更省。控件树整理不好，一样能把上下文塞满，一棵两千行的树比一张 1080p 截图更贵。所以这一层的差异主要不在「能不能操作」，在「整理成什么格式给模型」。

顺带把三个容易混的东西分开：

- **Skill** 是给模型看的说明书，讲有哪些工具、参数怎么填。
- **CLI** 是给执行器的入口，一个命令一个动作，Agent 通过 shell 调。
- **MCP** 是把 CLI 包成工具协议，让模型直接调用，省掉「先写命令再执行」这一跳。

三者可以任意组合，能力上限由最底下那层接口决定，跟包装方式无关。

## 2. 读界面：先结构，后像素

同一个窗口有两种读法，原文用一张保存对话框做了对照。

{{< fig "diagrams/02-two-readings.svg" "左边是截图，模型要靠推断认出「这是一列标签加一个输入框」；右边是控件树，类型、名称、值、可用状态都写好了，位置和外观一个都没有。" >}}

可访问性树这个东西本来不是为 Agent 设计的。它是给屏幕阅读器用的，让人不看屏幕也能操作软件。也就是说，软件早就被要求对外声明「我是一个按钮，我叫保存，我现在可用」，只是过去只有一个用户在用这份声明。Agent 是白捡的第二个用户。

结构通道给的是语义和状态：角色、名称、当前值、是否可用、是否选中、是否展开。像素通道给的是外观和空间关系：长什么样、在哪、有没有被挡住、有没有红框报错、加载动画转没转。这两组信息几乎没有重叠，所以问哪个更好没有意义，取决于下一步要判断什么。

真正的约束在覆盖面。结构只覆盖作者写了语义的那部分。自绘控件在树里经常是一个空节点：canvas 里的按钮、Electron 里手写的 div、游戏界面。这类界面只有像素可读。

树大也有树大的问题，所以要修剪。常见的修剪只留可交互节点加名称和状态，把布局属性、装饰容器、离屏内容丢掉。修剪规则写得好不好，直接决定模型这一步判断得准不准。

另一头的约束在语义。截图上「灰色不可用」和「浅灰但仍可用」要靠模型猜，而结构里就是 `enabled: false`。纯视觉方案在长流程里出错，多半错在这类状态判断上，而不是认不出按钮。

还有一点常被忽略：结构可以算差分。两轮之间只发变化的子树，模型看到的增量可能只有几十个 token。截图只能整张重发，一张 1080p 图折成千 token 量级，不会因为「只变了一个输入框」而下降。

## 3. 四种组合，两种失败

读法是一条轴，做法是另一条轴。两条轴交叉出四格，每一格都有明确的适用条件。

{{< fig "diagrams/03-matrix.svg" "纵轴是怎么读界面，横轴是怎么落动作。四格分别是常见折中、最短路径、兜底和少见组合。右上角依赖应用把「可执行动作」暴露出来。" >}}

**结构 + 元素动作**是最短路径。按名字查到控件，直接调用它的动作，不产生鼠标事件，不受遮挡、缩放、多屏影响，也不抢用户的鼠标。代价是支持面窄：应用得声明这个控件可执行，而很多应用只暴露「读」，不暴露「做」。

**结构 + 坐标**是工业实现里最常见的一格。靠结构定位，不怕窗口挪动和换分辨率；靠坐标点击，走的是系统真实输入，兼容性最好。风险在两步之间的时间差：查到位置到发出点击之间隔了几十毫秒，界面可能已经变了。

**像素 + 坐标**是兜底。画布、游戏、远程桌面这些没有可访问性实现的界面只能这么办。每一步都要重新认一遍目标，相似元素容易混，窗口一挪就点偏。

**像素 + 元素**用得少。从截图认出控件，再到树里找对应元素触发，两套信息要对上，通常靠位置或名称匹配。匹配错等于点错。

实际系统很少只选一格，多数是按控件降级：先试元素动作，失败退到坐标，再失败退到截图识别。降级链写死的坏处是慢，好处是可预测，出问题时能说清是哪一级失败。

## 4. 找到和点到，是两个决定

原文那句「怎么找到按钮和怎么点击按钮是两件事」值得单开一节。把这两步分开之后，重试才有层次。

{{< fig "diagrams/04-locate-trigger.svg" "定位有三条路（结构查询、视觉识别、复用旧坐标），触发有两条路（元素动作、坐标输入）。两者可以任意组合，失败模式也分开报。" >}}

定位失败和触发失败是不同的病。定位失败说明「我不知道点哪」，要换查询条件、换描述、或者重新截图。触发失败说明「我知道点哪但没生效」，要换通道、等一等、或者查是不是被遮罩拦住了。混在一起写的执行器只能整体重跑，一步错退回起点。

第三件事是验证，这一步最容易被省。在坐标路径里，「点击成功」只表示事件投递到了系统；在元素路径里，它只表示动作被调用。两者都不表示任务完成。文件有没有生成、内容对不对、页面有没有跳转，得单独查。原文的总结里把这句放在了最后一条：做完要验结果。

顺带说清鼠标动画。有些工具会把指针平滑移动到目标再点击，看起来很像人。这个动画是给人看的，方便人确认「它要点哪」。决定输入是否生效的是事件落在哪个窗口、哪个控件，跟指针有没有真的移过去无关，也跟输入焦点无关。所以关掉动画不影响正确性，只是人看不懂它在干什么。

## 5. 脚本：用确定性的代码换往返

一轮循环长这样：

```text
while not done:
    view = observe()                  # 结构优先，必要时截图
    if is_goal_reached(view): break
    action = model.decide(goal, view) # 只有这一步用模型
    result = act(action)              # 元素动作优先，坐标兜底
    if not verify(goal, result):
        retry_or_escalate()
```

每次 `model.decide` 都要把系统提示、工具说明、全部历史重新发一遍。步数一多，输入 token 就按平方涨。

{{< fig "diagrams/05-round-trips.svg" "左边每一步都要一次往返，每次重发全部上下文；右边把已确定的连续动作写成脚本，一次下发，执行器内部跑完只回一条结果。" >}}

按一组假设值粗算：上下文 20K，每一步新增 0.5K 观察，共 20 步。逐步推理的总输入约 495K token；把这 20 步折成 4 次决策，每次脚本内跑 5 步，总输入约 90K。差五倍多。这是估算，不是实测；开了 prompt cache 之后前缀单价下降，倍数会缩小，但每一轮仍然要等一次生成，延迟降不下来。

所以脚本编排真正省的是「等模型」。一段稳定的流程写成脚本后，拼文件名、算坐标、循环翻页、过滤表格都在本地算完，这些事交给模型就是把确定性的算术换成了采样。

要说清一点：脚本同样是模型写的，区别在写一次还是每步写一次。写一次意味着这段流程的中间状态不再回到模型面前，模型也就失去了在中间改主意的机会。

代价就在这里。脚本内部看不见意外，边界要划在「已知输入、已知输出」的地方，中途任何不符合预期的情况都应该抛错交回模型，而不是在脚本里猜着补救。

```js
// 一段脚本内完成 5 步，只回一次结果
const win = await ui.findWindow("保存PDF");
const box = await win.find({ role: "textbox", name: "文件名" });
await box.setValue("会议纪要.pdf");
const btn = await win.find({ role: "button", name: "保存" });
await btn.invoke();                       // 直接触发；不支持时退回 btn.click()
await ui.waitForFile("~/Downloads/会议纪要.pdf");
```

## 6. 浏览器多出来的那一层

桌面和网页的机制是同一套，浏览器多给了两样东西：可寻址的元素，和更全的接口。

{{< fig "diagrams/06-three-views.svg" "同一个搜索框的三种读法。画面给外观和布局，DOM 给元素和属性，可访问性树给类型、名称和状态。桌面应用缺中间那层。" >}}

DOM 让「定位」变得便宜。元素有 id、有 name、有 role，选择器在重排之后仍然指得中。桌面那边做到同样的事要靠可访问性树的路径，稳定性差一截。

可访问性树是 DOM 的语义投影，桌面那边是原生控件的语义投影。这件事的价值在于同一套提示能操作两边：模型看到的都是「按钮，名字叫保存，可用」。原文强调的「通用语义」就是这个意思，换了平台，模型不用换读法。

浏览器还多出一批桌面没有的能力：标签页切换、文件上传、下载落盘、iframe 穿透、直接读网络请求。这些让浏览器场景比桌面场景好做，接口更全，出问题也更好查。

有个实现细节值得记下来：网页上的「点击」有两种。一种是用脚本派发事件，`isTrusted` 是 false，某些依赖真实用户手势的逻辑会拒绝执行；另一种是走 CDP 的输入域，发出的就是真实鼠标事件。Playwright 的 click 走的是后者。自己用 `dispatchEvent` 拼的点击，在登录、支付、上传这类有风控的页面上经常失败，而错误信息通常只说「元素不可点击」。

## 7. 三层状态，各有各的失效条件

「记住当前窗口」只是第一层。整个系统里同时存在三份状态，它们不会一起失效。

{{< fig "diagrams/07-state-layers.svg" "会话状态在执行器进程里，应用状态在应用自己的内存里，屏幕状态是渲染出来的一帧。三者各自失效，重置一个不会重置另外两个。" >}}

原文附录里点出了几个具体现象：重新选中标签页，表单不会自己恢复；清掉工具会话，网站的登录仍然有效；关掉执行器，已填的内容还在。这三句背后是三层状态的独立性。

- **会话状态**由执行器持有：连接句柄、当前窗口或标签页、上一步的元素引用、超时计数。它的作用是省掉重复传参。
- **应用状态**由应用或网页自己持有：表单内容、登录 cookie、上传进度、展开的文件夹。它才决定「下一步还能不能接着做」。
- **屏幕状态**是渲染出来的一帧：当前像素、焦点、滚动位置、弹层。它变化最快，几乎每步都不同。

混在一起管理的实现，重试时会重复执行已经成功的步骤，比如重新填一遍已经填好的表单，或者在一个已经保存过的对话框上再点一次保存。

## 8. 接入的四种形态

同一套能力有四种包装，选哪种取决于「要不要用用户已经打开的浏览器」。

| 形态 | 谁维护连接 | 能否用已有登录态 | 隔离性 | 典型场景 |
| --- | --- | --- | --- | --- |
| 库（Playwright / PyAutoGUI） | 你自己的进程 | 能，但要用持久化 profile | 弱，出错影响整个进程 | 写爬虫、写测试、做固定流程 |
| CLI | 每次一个短进程 | 取决于它连的是哪个浏览器 | 中，进程退出即断开 | 编码型 Agent 通过 shell 调 |
| MCP / Skill | 包一层协议给模型 | 同上 | 同上 | 模型直接选工具、填参数 |
| 浏览器扩展 | 扩展的后台脚本 | 能，直接接当前标签页 | 强，不动用户的其它标签 | 操作需要登录的后台系统 |

扩展这一行，原文写得很细：后台服务在浏览器外面（多次 CLI 命令都调它，它负责接命令、存会话），扩展在浏览器里面（走 `chrome.debugger` 到 CDP，再到底层标签页）。MV3 之下扩展的后台是 Service Worker，随时可能被浏览器回收，所以「会话」不能只存在扩展里。这一点和上一节的三层状态是同一件事的另一面。

## 9. 边界

四个限制，做之前先认一下。

1. **结构覆盖率不由你决定。** 目标软件或网站没写语义，结构通道就是空的，只能退回像素。选型时先拿真实目标试一遍 `role` 和 `name` 有多少。
2. **验证比操作难。** 点一个按钮容易，判断「这件事办成了」难。文件、数据库、页面状态至少要对上一个，否则「点击成功」会一路骗到用户面前。
3. **时序是主要 bug 源。** 界面有动画、有异步请求、有防抖。固定 `sleep` 在慢机器上必然失败，在快机器上白等。要等具体条件，不要等时间。
4. **权限等于全部登录态。** 给一个进程操作你的桌面，等于把浏览器里所有已登录的账号交给它。隔离环境（独立 profile、独立容器、独立账号）应当在设计阶段就定下来，不要等出事再补。

上线前先答四个问题：观察用哪种格式、动作走哪条通道、哪些步骤折叠成脚本、失败时怎么验证。四个都答得出来，剩下的就是调参。
