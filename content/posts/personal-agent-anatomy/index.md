> 上一篇讲「一个设计助手该怎么分层」。这一篇反过来：先把 2026 年这一批 Personal Agent 拆开，看它们共同做对了什么，再回头检查那套分层缺了哪几块。Muse 的资料来自公开报道和一份流传的系统提示词文档，产品细节随版本变化，结构和判断比具体字段更值得记。

## 0. 先给结论

Personal Agent 这一轮的分水岭在用户关掉 App 之后发生了什么，不在模型。Muse 的答案是一台还在跑的机器、七种后台循环、三道守卫。这三样决定它是一件长期服务，还是一个加了记忆的聊天框。

结构上四条。

1. **先给机器，再谈记忆。** Muse 给每个用户一台独立的 `Muse Secure VM`，会话结束机器还在，`~/` 下的文件、记忆、技能都留着（§3）。把预算全投在检索和窗口上，产品形态仍然是一个输入框，第二天所有上下文从头再来。
2. **不可撤销的动作先拦。** 编译期校验防「做错」，外发闸防「发出去」。Muse 的发布每次都要一键批准且批准不持久，支付走一次性虚拟卡和单笔 / 日 / 30 天限额（§3）。图发到客户群里，撤回不了。
3. **主动性的单位是提案。** 一句判断、一个能一键执行的动作、一个撤销点。只有判断没有动作的是新闻，只有动作没有撤销点的是风险。
4. **后台结果先回主 agent。** Muse 把这步叫 handoff：worker 交回的是一份写给主 agent 看的报告，不是直接发给用户的消息（§4）。跳过这步，你会一次收到五条互相矛盾的播报。

运行侧还有四条。

5. **循环要产出能开工的东西。** Muse 每天生成 Ideas 卡和目标简报，用户点一下就能开工（§4）。跑三个月只留一屏日志，等于没做。
6. **每个动作留一条能追问「为什么」的 trace。** Muse 用 `muse.db` 记录 run、step、handoff、消息（§3）。没有它，助手说不出理由，你也没法判断它是在推理还是在猜。
7. **重复三次的动作固化成 skill。** Muse 每天做一次技能评审，跑两周没效果的退役（§4）。排版、命名、导出这类固定动作，写一次省一年。
8. **模型分档。** Muse 分 Spark 和 Wonder 两档。个人助手的对应做法：收活与评审用小模型，生成与长链任务用大模型。

落地的顺序：先做常驻工作目录加一个每天跑一次的调度器，半天能搭完，之后所有功能都有地方放。外发闸要在接第一个发布渠道之前做，闸门后补，历史里会留下一批说不清发没发的记录。提案卡、handoff、trace 是一套，同一周做完，拆开做会互相将就。

## 1. 这一轮和上一轮差在哪

{{< fig "diagrams/01-generations.svg" "三代 Personal Agent。分界线不在能力清单，在「用户离开之后」：会话结束就停、任务结束才停、一直在跑。" >}}

三年三代，每代的差别一句话能说清。

第一代是聊天助手，2023 到 2024。会话是中心，工具是插件，记忆靠用户手动贴。关掉窗口，一切归零。

第二代是任务型 agent，2025 年的 Manus 是代表。它把规划、执行、交付做成产品：接一个目标，在云端虚拟机里跑，产出文件，通知你。这一代解决了「能做完一件事」，没解决「两件事之间有没有关系」。

第三代是常驻主体，2026 年 9 月集中出现。Muse 9 月 8 日上线，Manus 2.0 和 Cue 9 月 28 日发布，OpenClaw 生态在开源侧同步铺开。这一代把四件事装进同一个产品：

1. 常驻环境。一台属于你的机器，App 关了它还在跑，重启能恢复现场。
2. 身份。Muse 用你自己的账号行动，Cue 给每个 agent 配独立邮箱和钱包，两条路线的差别见 §5。
3. 触发。不再只靠你开口，定时、事件、后台循环都能启动工作。
4. 审批。花钱、发消息、发布页面这些动作，要过一次人工闸。

Muse 的数字能给这一代定个量级：上线三周下载 250 万，美国移动端日活 64.2 万，是 ChatGPT 上线同期的近三倍（[央广网转界面新闻](https://tech.cnr.cn/gstj/20261003/t20261003_527832952.shtml)）。同一篇报道里还有一条更值得记：亚马逊以「未经授权的 AI 代理持续访问」为由封了 Muse 的代购功能。需求被验证了，模式没有。

## 2. 产品面：六个 tab，三种作者

{{< fig "diagrams/02-muse-surfaces.svg" "Muse 的六个产品面，按作者分三类。主 agent 写对话与产物，后台进程写提案与简报，你只负责提问、定目标、签字。" >}}

打开 Muse 看到六个面：Chat、Feed、Ideas、Goals、Library，加上可以放进侧边栏的 Spaces。按「谁写的」分一下，结构就清楚了：

| 面 | 内容 | 谁写 | 你的动作 |
| --- | --- | --- | --- |
| Chat | 对话与任务 | 主 agent | 提问、打断、批准 |
| Feed | 排好版的短文 | 后台进程，按 brief 写 | 读、爱、讨论、删 |
| Ideas | 可以开工的建议卡 | 后台进程，每天刷新 | 点「开始做」或长按忽略 |
| Goals | 长期目标与进展 | 你定，agent 记进展 | 加子目标、看简报 |
| Library | 产物与文件 | agent 产出 | 下载、分享、删除 |
| Spaces | 页面与小应用 | agent 构建 | 放进侧边栏、发布 |

这张表说明三件事。

1. **输入框只占六分之一。** 产品重心从「你说一句它答一句」挪到「它准备好几件事等你挑」。Feed 和 Ideas 都不需要你先开口，这是常驻在界面上的样子。
2. **每个面都有明确的写者和读者。** Feed 的文章由后台写、你读；Ideas 的卡由后台写、你决定要不要执行；Goal 简报由后台写、挂在目标下面。这种约定让后台循环的产出有落点，不至于变成一堆通知。
3. **设计已经拆给连接器。** Muse 上线就带 Canva 连接器，用户可以让它做视觉内容（[Tech Guide 报道](https://www.techguide.com.au/news/apps-news-feed/meta-launches-muse-in-australia-a-personal-ai-agent-built-for-everyone/)）。同一个连接器列表里还有房产、零售、健身、票务。Muse 自己不画图，它负责收活、找工具、验收。这个分工和我从设计助手里得出的结论一致，只是它面向所有人，我面向一个设计师。

## 3. 运行面：一台机器，三道闸

{{< fig "diagrams/03-muse-architecture.svg" "Muse 的运行结构。中间是一台属于用户的常驻机器，右侧三道闸拦住出网、发布与付款，左侧是记忆与技能的沉淀。" >}}

每个用户一台独立的云电脑，里面有浏览器、文件系统、终端、连接器凭据，还有一套给 agent 自己读的文档目录（`~/docs/`）。记忆在 `~/memory/`，技能在 `~/workspace/custom-skills/`，反思在 `~/dreams/`，运行记录在 `muse.db`。

这台机器的意义是连续性，不是算力。上一次任务下载的素材、上次登录过的站点、上次被否掉的方案，都还在原地。agent 不需要每次从零重建环境，用户也不需要每次重新解释背景。

官方文档里没有统一的闸门名字，但行为是清楚的，外面报道里管系统级那道叫 Sentinel（[搜狐唐健盛的分析](http://news.sohu.com/a/1087495815_114986)）。按动作类型分，实际有三道：

1. **浏览与凭据：四个权限可分别设成允许、询问、拒绝。** 密码只走 Secure Vault，不进聊天、不进文件、不进记忆。验证码和机器人检查由浏览器自己处理，处理不了才把控制权交回用户，交回期间人和 agent 不同时操作。
2. **发布：每次都要重新点批准，批准不持久。** 没有「以后都自动发」。只有静态产物能发布，交互式应用不能公开。
3. **支付：一次性虚拟卡，带单笔、每日、30 天三档限额。** 走 Stripe Link，加 Shop Pay 和 PayPal。一次结账占一个浏览器窗口，结果未知时不许换路线重试，必须先对账。

还有一道软的：审批卡由客户端渲染，agent 看不到也改不了卡片的布局和措辞。这条防的是「agent 说服用户批准」，比任何提示词约束都硬。

这套设计的取向很清楚：安全边界画在动作上，不画在模型上。模型可以说服自己这是安全的，但它改不了一张它看不见的确认卡。

## 4. 时间面：七种循环，一次交接

{{< fig "diagrams/04-muse-loops.svg" "一天的后台节律。小时级的记忆整理与关系维护，日间生成提案与简报，夜间做反思与技能评审，长对话结束后还有一次静默清扫。" >}}

后台循环按频率排开，一共七种：

| 循环 | 频率 | 产出 |
| --- | --- | --- |
| 记忆整理 | 有新信号时每小时 | 合并进 `MEMORY.md`，旧结论被新结论覆盖，原始笔记留档 |
| 关系维护 | 每小时 | 每个人、每个群一个页面，记录事实、历史、亲疏 |
| Ideas 生成 | 每天 | 建议卡，按可行性、贴合度、新颖度打分排序 |
| 目标简报 | 每天，夜间 | 目标相关的调研简报与进度提示 |
| 反思 | 每晚 | `~/dreams/` 下的带日期笔记、需要修复的关系 |
| 技能评审 | 每天 | 重复流程固化成技能，无效技能下线 |
| 静默清扫 | 长对话结束后，一天最多几次 | 把刚发生的事内化一遍 |

七种里只有两种和生成内容有关，其余都在做维护。这个比例值得抄：常驻主体的成本大头在整理，不在推理。整理做不好，记忆就是一个越滚越大的垃圾桶。

调度语义有四个反直觉的地方：

1. **是轮询，不是监听。** 定时检查按间隔跑，两次检查之间发生又撤销的事会漏掉。所以文案只能说「我每三十分钟看一次」，不能说「一有动静就告诉你」。
2. **运行成功不等于用户收到。** worker 跑完先产出一份给主 agent 看的 handoff，主 agent 决定要不要转成给用户的消息。worker 不能反过来给主 agent 派活。
3. **运行历史才是真相。** 判断一个定时任务有没有跑，看的是运行记录，不是调度表。失败和超时可能一条消息都不发。
4. **持久阻塞会自己暂停。** 连接器掉线、需要人工、站点过不去，任务会暂停并在下次调度时重试；恢复后接着来。

{{< fig "diagrams/05-run-handoff.svg" "一次计划任务的交接。调度器唤醒 worker，worker 在自己的窗口里干活，结果以 handoff 形式回到主 agent；需要用户决定的地方停下来，用户批准后才继续。" >}}

这张图里最容易被忽略的是中间那一步：worker 的结果是报告，不是消息。它带来两个好处。主 agent 可以合并同一天的多份报告，避免你被五条播报轰炸；也可以判断「这件事不值得说」，直接丢掉。

代价是延迟和失真。worker 不知道你刚在聊天里改过主意，主 agent 也可能把一份重要报告压下去。Muse 的处理方式是把两边都留在 `muse.db` 里，事后能查。

## 5. 横着看四家

| | Muse | Manus 2.0 / Cue | OpenClaw | ChatGPT agent |
| --- | --- | --- | --- | --- |
| 常驻环境 | 每用户一台 Secure VM | 项目一台 Cloud Computer | 你自己的机器，Gateway 常驻 | 任务期一台虚拟电脑 |
| 身份 | 你自己，进你已有的账号 | Cue 自带邮箱、电话、钱包 | 你配的渠道账号 | 你自己 |
| 触发 | 对话、定时、事件、后台循环 | 对话、定时、Cue 可被外部唤起 | 渠道消息、cron、webhook | 对话为主 |
| 审批 | 三道闸，逐次批准 | 预算内自主，超限问人 | 靠配置与权限文件 | 敏感动作需确认 |
| 产物 | 文档、页面、应用、Feed | 项目文件、网页、视频、自动化 | 文件与渠道消息 | 文件、报告 |
| 记忆 | 分层，后台维护 | 项目内累积 | 会话加工作区文件 | 会话级 |
| 部署 | 闭源云 | 闭源云 | 开源自托管 | 闭源云 |

这张表读出两件事。

底座趋同。四家都在做同一套东西：一个持续存在的执行环境、一个把任务拆成步骤的循环、一层连接器、一个调度器、一套审批。2026 年做 Personal Agent，难在把它们做稳；想到这些并不难。

分岔在身份与门禁。Muse 的身份是「你」，它进你已有的 Gmail、日历、Instagram，产出直接落在你的数字生活里。Cue 的身份是它自己，有自己的邮箱和电话号码，可以被「雇佣」。这两个选择决定后面所有设计：Muse 的权限问题是你敢不敢把账号交出去，Cue 的权限问题是它花谁的钱。

OpenClaw 走第三条路：不给你机器，用你自己的机器。好处是数据和凭据不出门，坏处是关机就停、换设备要迁移。它把控制平面做成一个常驻网关，会话、cron、渠道、子 agent 都挂在上面（[架构拆解](https://developer.aliyun.com/article/1717849)）。个人项目要自建的话，这个形状最接近可落地的方案。

## 6. 抽出来的五个部件

把四家共有的部分抽掉厂商差异，剩下五个部件和三条闸。

{{< fig "diagrams/06-five-parts.svg" "四家产品抽出来的五个共同部件与三道闸。底座趋向一致，差别集中在身份和门禁上。" >}}

五个部件：

1. 主体：一台（或一个目录）持续存在的执行环境，带文件、凭据、工具。
2. 循环：把目标拆成步骤、调用工具、检查结果、决定继续还是停。
3. 记忆：分层存放，工作集进上下文，长期事实进存储，后台定期合并。
4. 调度：定时、事件、手动三种触发，加上运行记录和失败重试。
5. 账本：每个动作一条记录，能回答「谁在什么时候对什么做了什么、为什么」。

三条闸：

1. 编译期闸：进模型之前，把该带的约束带上。防的是模型不知道。
2. 产物侧闸：产物出来之后，用确定性规则校验。防的是模型知道但没照做。
3. 外发侧闸：离开你的机器之前，停下来问一次。防的是做对了但发错了地方。

前两条闸决定产物质量，第三条闸决定你敢不敢用。大多数个人项目只做了前两条，然后在第一次「发到错误渠道」之后才开始补第三条。

## 7. 设计助手抄什么，不抄什么

抄五条。

1. **主体层：本地 daemon + 项目目录。** 不需要云 VM。目录里放当前项目的 spec、素材、候选、版本树；daemon 负责调度和文件监听。这一层加进去，前面那套六层架构才有时钟。
2. **提案卡：一句判断、一个动作、一个忽略入口。** 比如「上周那张海报的方图还没导出，现在导？」比「你有 3 条待办」有用得多。
3. **外发闸：发布、发邮件、买授权都要过闸。** 闸门记录「谁批的、批的什么、什么时候」，不记录「以后都行」。
4. **handoff：后台结果先回主 agent。** 由主 agent 决定合并成一条还是丢掉。设计场景里这条尤其重要：夜间预取的十个候选，不该变成十条通知。
5. **trace 查询：能答出「为什么推荐这张」。** 哪条规则过了、哪些特征算出来偏好它、上次类似的判断是什么。

不抄四条。

1. **支付钱包：不做。** 设计场景没有即时支付，字体和图库走月结，做一个预算计数器就够。
2. **社交 Feed：不做。** 没有读者就没有信息流。硬要做的话是给自己看的周报，一周一封邮件即可。
3. **关系图：不做。** 个人助手的 n=1，客户不超过二十个，一张表比一套关系维护循环划算。
4. **多租户隔离：不做。** 一台机器一个人，隔离靠目录，不靠租户 ID。

这份清单的共同点：时间结构值得抄，商业结构不值得。Muse 的七个后台循环、三道闸、handoff 是产品形态的结果；钱包、Feed、关系图是它有几十亿用户才长出来的器官。

## 8. 三个没解决的问题

第一个是成本：一台常驻机器加七种循环，一个人一个月要花多少？Muse 用订阅摊平，个人项目没有订阅可摊。粗略估：闲置机器一天几毛，七种循环里最贵的是夜间反思和技能评审，一次几毛到几块。一个月二十到五十块是合理区间，超过就得砍循环。

第二个是幻觉：后台循环最危险的失败是生成一条「看起来合理但没发生」的提案。答错还能被检查出来，凭空发生的「事实」没有对照物。「你上周说过这版太暗」可能你根本没说过。做法和评审一样：提案里的每个事实都要能追到一条事件，追不到的降级成问句。

第三个是可审计不等于可信：trace 能回答「为什么推荐这张」，回答不了「这条建议值不值得」。前者是工程问题，后者要等你接受或拒绝几十次之后才有答案。品味模型的样本必须来自动作，不来自自述。
