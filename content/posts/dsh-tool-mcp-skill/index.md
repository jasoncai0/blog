同一个需求通常有三种做法：加一个工具、接一个 MCP server、写一份 SKILL.md。它们经常被并列成「扩展能力」，其实不在同一层。

工具是可执行的能力契约，MCP 是工具的一种来源协议，技能是模型读的说明书。混着用不会报错，代价是多出来的那一层：为一个内部函数起 MCP server，多一个进程和一条重连预算；把整套流程写进工具描述，每个请求都为它付一次前缀；在 SKILL.md 里写「运行 pytest」，以为技能会执行。

下面按三个问题拆：落在哪、谁执行、什么时候用。例子取 DSH 的实现，源码细节放在文末那两篇里。

## 0. 结论

| 维度 | 工具 | MCP | 技能 |
| --- | --- | --- | --- |
| 是什么 | 带 schema 和执行体的能力 | 把外部工具接进工具表的协议 | 一段给模型读的指令 |
| 落在哪 | 请求头 `tools[]` | `tools[]` 里带 `mcp__` 前缀的条目 | 消息尾部的目录，正文按需加载 |
| 谁执行 | harness 进程内的 handler | 进程外的 server | 没人执行，模型照着做 |
| 增删的代价 | 声明变了，前缀缓存失效 | 一次连接与握手，之后还要维护 | 追加一条消息，前缀不动 |
| 失败的典型形态 | 准备阶段失败，或结果不合法 | 掉线后调用返回错误，预算耗尽才注销 | 目录里没有它，模型不知道 |

区别可以压成一句：前两个要能被机器调用，最后一个只要能被模型读懂。

## 1. 三个位置

一次请求的骨架是 system、`tools[]`、messages 三段，三种能力分别落在这三段里的不同位置。

1. **工具声明进 `tools[]`。** 模型看到的是 `name`、`description`、`parameters` 三个字段，`timeoutMs`、`output` schema 这些东西不发给模型。同一类工具里同名直接抛错，因为两个实现抢一个名字时，静默选一个比崩掉更危险。
2. **MCP 不产生新位置。** 接一个 server，`tools[]` 只是多出若干条 `mcp__github__create_issue` 这样的条目，服务器名和原始名拼进工具名。resources 是例外：不是每个资源一个工具，而是三个固定工具加一个 `server` 参数。
3. **技能落在 messages 尾部。** 每一步 pre-step（模型调用前的准备步骤）把目录发成一条 user 消息，内容是一行一个 `name: description`，描述截断到 500 字符；目录的 digest（内容哈希）没变就不重发。模型调用 `skill` 工具，正文以一条 tool/result 回到上下文。

{{< fig "diagrams/01-three-positions.svg" "技能、工具与执行体在请求里的位置。技能在消息里，工具声明在请求头，执行体分处进程内外；技能没有执行体，MCP 没有自己的工具表。" >}}

位置决定三件事：谁能看见、改动要付什么代价、以及它有没有执行体。工具改了，声明表变了，从这一段起的缓存全部重算；技能加一条，消息尾部追加，前面的前缀照常命中。

还有一个容易忽略的耦合：技能的目录能不能发布，绑定在 `skill` 这个工具是否活着上。技能单独占着消息尾部这一段位置，但没有自己的执行体，挂在 `skill` 工具上。工具被移除，技能就从「可见」变成「不存在」，且没有任何报错。

## 2. 谁执行：一条进程边界

工具和技能看起来都是「模型调用一下」，执行路径完全不同。

{{< fig "diagrams/02-call-paths.svg" "一次工具调用与一次技能加载。工具的 dispatch 在进程内是函数调用、在进程外是 JSON-RPC；技能加载只是一次读文件，正文回到上下文后，真正动手的仍是别的工具。" >}}

所有 `tool_call` 进的都是同一条流水线：快照并冻结参数，跑 pre-execute（allow、deny 或 ask），dispatch 时再查一次注册表，结果过一遍 output schema，最后物化成一条 `tool/result`。进程内工具的 dispatch 就是一次函数调用；MCP 工具在这一步多一跳，把名字和参数包成 JSON-RPC 发出去，传输是 stdio 或 streamable http。

结果在回到模型之前被抹平。server 返回的是 content 数组，harness 把它变成普通工具结果，模型这一侧看不出差别。审批也没有专用通道：MCP 工具进了注册表就是普通工具，审批走同一条 pre-execute。这是「MCP 是来源，不是另一类工具」最直接的证据。

技能这条链路里没有执行。`skill` 工具只做三件事：校验名字、找到候选、把正文取出来。正文进了上下文，后面每一步仍然是普通工具调用。SKILL.md 里写「运行 `pytest -x`」，真正跑它的是 bash 工具。技能只影响模型下一步选哪个工具、按什么顺序选；它不替模型动手。

失败形态也跟着位置分岔：

| 阶段 | 工具 | MCP | 技能 |
| --- | --- | --- | --- |
| 声明期 | 注册抛错：缺 output schema、同名、占用保留名 | 握手失败，这一轮工具暂缺；连接活过窗口后掉线才走重连 | 目录没发布，或某个目录坏掉只 warn、整体标成不完整 |
| 调用期 | 参数不合法、超时、结果过不了 schema | transport closed；工具仍在表里，重试到预算耗尽才注销 | 没有调用可失败；正文加载失败就是一次普通工具错误 |
| 静默消失 | `when` 条件返回 false，不进声明表 | 重连预算耗尽，补一条 tool-removal | 与更高优先级目录同名被丢弃，或目录不可见 |

第二行值得单独看。MCP server 被 `kill -9` 之后，工具表不会立刻变：模型还能调，每次拿回一段 `MCP transport closed`，一直调到重连预算耗尽，下一轮 `tools[]` 才少掉那几项。这是有意为之：短暂抖动不用重排工具表，代价是模型会在一段时间里反复调到坏工具。

看到这段错误时，先确认两件事：server 进程是否还活着，以及这一轮的重连预算是否已经用完。预算没用完，条目就还在表里，改配置没有意义；预算用完了，才轮到看 server 的 stderr 和传输层日志。

## 3. 什么时候用哪个

{{< fig "diagrams/03-decision.svg" "选型决策树。先问要不要动手，再问能力在不在外部；两个都否定时，需求还不该进工具表。" >}}

1. **要模型动手，写工具。** 动作需要参数校验、审批、超时、结构化结果时，工具是唯一能提供这些的载体。
2. **要接外部系统，先找现成 MCP server。** 内部 API 也算外部：它在 harness 进程之外。有现成 server 就用，别为了几个动作自己写一个——进程、重连、凭据、升级都有人管，代价是这些也都不在你手里。
3. **要让做法一致，写技能。** 步骤、判断标准、坑位、产出格式都属于技能。它不保证模型照做，只保证模型读过。

三种东西的成本不在一个量级：

- 工具开发最重，换来的是确定的校验、审批和最低延迟。
- MCP 接入最省，运维最重：掉线后的重试行为要提前知道，别把它当成本地函数。
- 技能改动最便宜，改 markdown 下一轮就生效；但没有强制力，模型可能只做一半。正文进上下文要花 token，目录摘要又只有 500 字，光看摘要容易选错技能。

选型顺序可以先问两个问题：这件事有没有外部系统？有且已有 server 就接 MCP，没有就写工具。这件事需不需要每次做法一致？需要就补一份技能。

## 4. 组合：一次任务里三者同时出现

修一个 GitHub issue，三者会同时出场。

1. 技能给流程：先复现，再定位，改完跑测试，最后回评论。
2. MCP 读外部状态：issue 正文、历史评论、相关 PR。
3. 内置工具改本地状态：grep、read、edit、bash。
4. MCP 写回结果：把结论发成一条评论。

分工是清楚的：技能决定顺序和取舍，MCP 管外部系统的读写，工具改变本地环境。技能里可以写具体命令，但执行永远发生在 bash 里；MCP 里可以读 issue，但改代码永远发生在文件工具里。

## 5. 三个常见误解

1. **MCP 是「另一种工具」。** 它是工具的来源，落点还是 `tools[]`，审批、超时、结果投影全走同一条流水线。判断一个能力是不是工具，看它有没有出现在 `tools[]` 里。
2. **技能会执行脚本。** 技能只提供文本，脚本由 bash 工具跑。技能里能写「运行 X」，不能写「我运行 X」。
3. **把流程写进工具描述能省掉技能。** 工具描述每个请求都随 `tools[]` 发出，常驻付费；技能目录只有一行摘要，正文按需加载。长流程塞进工具描述，等于每一步都为它付一次前缀。

判断标准只有一条：要模型动手，还是让模型知道怎么动手。前者进工具表，自己写或接 MCP；后者进上下文，写一份技能。
