> 源码版本：`opencode 2.2.5`，commit `a687c047`（2026-11-08）。代码引用以工作区 `.opencode-src/` 为基准。
> 系列第八篇。前七篇讲的是系统怎么运转；这一篇讲一件更具体的事：**"写代码"这个能力到底由什么构成**，以及它和"生成一段文本""生成一张图"差在哪。

## 0. 先给一个不讨巧的结论

模型不会"写代码"。它只会输出 token。所谓 coding 能力，是 harness 把 token 变成**动作**、再把动作的后果变成**证据**的一整套装置：

- **动作面**：读文件、搜代码、改文件、跑命令。模型输出的是工具调用，不是文件内容。
- **物理面**：真正落盘的是 `write` / `edit` / `patch` 三个工具，它们各自有前置条件与失败模式。
- **证据面**：改完要能看见 diff、能回滚、能重跑。快照与 revert 是 harness 提供的，不是模型自带的。
- **边界面**：哪些路径能碰、什么时候要问人、输出超了怎么截、失败了怎么退。

所以这一篇不按"模块"组织，而按**一次编码任务的四个面**组织：动作、物理、证据、边界。最后拿文本生成、图像生成、语音转写作对照——它们和 coding 走的是同一条模型调用路径，差异全在 harness 的外壳。

## 1. 动作面：模型能做的四件事

在一个编码会话里，模型真正能做的只有四类动作。其余工具（subagent、skill、question、todo）是编排层，不直接改代码。

| 动作 | 工具 | 在 coding 里的角色 |
| --- | --- | --- |
| 看 | `read`、`glob`、`grep` | 建立"代码长什么样"的事实 |
| 改 | `edit`、`write`、`patch` | 把意图变成字节 |
| 跑 | `shell` | 验证、构建、测试、git |
| 编排 | `subagent`、`skill`、`question`、`todowrite` | 拆任务、取知识、问人、记进度 |

这四类构成一个最小完备集：没有"看"就只能瞎改，没有"改"就只是聊天，没有"跑"就无法验证，没有编排就做不了多步任务。

注意这里**没有"必须先读才能改"的硬门禁**。edit 执行时自己读文件，不检查模型是否读过——"先读"是提示词与语义约束（`oldString` 要逐字匹配），不是代码强制。

值得强调的是**"跑"也是 coding 的一部分**。模型不能内省代码行为，它只能通过 shell 去跑测试、看报错、再改。所以 coding 循环在结构上是一个"编辑—执行—观察"的回环，而不是"一次性生成一段代码"。

### 1.1 读的三个约束

`read` 不是 `cat`。模型看到的每一行都带 `<行号>: ` 前缀，文件头还有一行 `Read file <path>, lines A-B`——这是为了让模型能可靠地引用位置，也让 `edit` 的 `oldString` 有明确的文本形态。

截断是分级的：行数上限 2000、总字节 50 KiB、单行 2000 字符、大文件按 256 KiB 分块。这里有个容易说错的边界：**2000 行是"分页上限"而不是全局硬上限**——一个 45 KiB、5000 行的短行文件，在不传 `offset`/`limit` 时会走整文件分支，不受 2000 行限制。所以"read 只能读 2000 行"是错的，准确说是"分页请求最多 2000 行"。

二进制判定不看扩展名，看内容里有没有 NUL 字节；图片与 PDF 按 MIME 白名单（png/jpeg/gif/webp/pdf）整份 base64 返回，上限 20 MiB。

`glob` 与 `grep` 则直接 shell out 到外置的 ripgrep（优先 PATH，否则下载校验后落到全局 bin）。默认上限 100 条、30 秒超时、**不排序**（就是 rg 的遍历顺序），忽略规则交给 rg 自己（`.gitignore` 生效，但只在 git 仓库内）。工具层从不传 `--follow`，默认不跟随符号链接。

两者有个不对称：`glob` 默认排除隐藏文件，而 `grep` 恒带 `--hidden`——**内容搜索会进点文件，路径搜索不会**（`.git` 除外）。这解释了为什么 grep 能搜到 `.github/` 里的内容，glob 却列不出来。

另一个常被误会的点：TUI 里 `@` 补全用的那套文件名索引（fff）**不是模型工具**，只服务客户端；模型能用的只有 read / glob / grep 三个。

## 2. 物理面：一次改动怎么落盘

{{< fig "diagrams/02-mutation.svg" "改一个文件要走八步，格式化只是其中一步" >}}

### 2.1 三种写法的分工

| 写法 | 输入 | 前置条件 | 适合什么 |
| --- | --- | --- | --- |
| `write` | 整份内容 | 无（可直接覆盖） | 新文件、整体重写 |
| `edit` | `oldString` / `newString` | `oldString` 必须在文件里**唯一匹配**（除非 `replaceAll`） | 局部、精确的改动 |
| `patch` | 一段补丁文本 | 补丁的上下文必须能对上 | 多文件、成组的改动 |

`edit` 的输出是 `{files, replacements}`，`patch` 的输出是 `{applied, files}`——两者都会把 diff 带回工具结果，`write` 则只报告"写了哪个文件、是否已存在"。

实现上还有一条分叉：`write` 与 `edit` 共享 `FileWrite` 这条"resolve → 审批 → 写 → 格式化"的独木桥，而 `patch` 绕过它，自己用 `FileAccess` + 文件服务，把多个文件的 hunk 全部预备好、一次审批、再逐个写。

### 2.2 edit 的匹配是模糊的，写入是精确的

这是整个编码链路里最值得抄的一段设计。模型给的 `oldString` 经常带"排版噪声"：弯引号、长破折号、不间断空格、行尾空格差异。如果严格按字节匹配，模型会频繁失败——而失败一次就浪费一整个 Step。

所以 `edit` 在**定位**时做归一化，在**写入**时保持原样：

- 定位前把 `‘’‚‛ → '`、`“”„‟ → "`、`‐‑‒–—―− → -`、` ` 与各种窄空格 → 普通空格；
- 先试整体字符串匹配；匹配不到再退化为**按行匹配**，逐行比较时容忍行尾空白；
- 匹配数必须恰好为 1（`replaceAll` 时例外），否则报错——不允许"猜一个改"。

归一化只用于"找到位置"，替换进去的 `newString` 一个字节都不改。

### 2.3 行尾与 BOM 按区域保留

更细的一层是行尾。`withRegionEndings` 会拿被替换区域与替换文本做一次**最长公共子序列对齐**：保留下来的行沿用原行的行尾（CRLF 还是 LF），改动或新增的行沿用"它替换掉的那一行"的行尾，只有完全新增的尾部才用文件的**主导行尾**。

于是"混合行尾文件里改一行"不会把整个文件的换行风格搅乱。BOM 同理：`writeTextPreservingBom` 保证最多写一个 BOM，且原本有就保留。

这类工作模型完全做不了，也不该让它做。

### 2.4 路径、并发与外部目录

- 相对路径在 Location 内解析；Location 内的绝对路径也接受；
- 显式指向 Location 之外的绝对路径，会先要一次 **external_directory 审批**，再要 edit 审批——两道关；
- 同一个文件上的并发写由 `FileMutation.withLock`（按**解析后的绝对路径**）串行化，避免两个工具调用互相覆盖。注意 `write` 没有包这把锁，它的预览读与 commit 理论上可被并发的 `edit` 插队。

### 2.4.1 越界判断是词法的，不是真实的

`resolvePath` 展开 `~`、归一 `..`，然后用 `contains` 做纯字符串判断：在 location 或 worktree 内就算内部，否则走 `external_directory` 审批。它**不做 `realpath`，也不拦 symlink**。

后果很具体：项目里有一个指向项目外的符号链接时，词法上它仍是"项目内路径"，模型只申请 `edit` 就能改到真实的外部文件。仓库里有测试把这个行为固化了下来——这不是漏洞报告，是当前的设计选择。

### 2.5 格式化：三种写法都跑，位置不同

`write` 与 `edit` 在 `FileWrite.commit` 里跑 formatter，`patch` 在全部文件写完后逐个跑。所以"改完自动格式化"是全局行为，不是某条路径的特权。

细节：先按扩展名精确过滤，再按注册顺序问每个 formatter 的 `enabled`（探测 `package.json` 依赖、`biome.json`、`.clang-format`、`pyproject.toml` 等），第一个退出码为 0 即停。内置约 26 个，覆盖 go / js-ts / python / rust / c-cpp / zig / ruby / php 等。

**格式化失败不阻断**：spawn 失败或非 0 退出都只记日志，文件保持未格式化，调用方把 `false` 当"没格式化"继续。所以它是个尽力而为的旁路，不是质量门禁——项目该有的 pre-commit hook 还是要自己配。

一个实现细节：`edit` 最终返回的 diff 用的是**格式化后回读**的内容，所以模型看到的 diff 是"写进去并格式化之后"的真实结果，不是它提交的字符串。

### 2.6 失败模式

| 失败 | 结果 |
| --- | --- |
| `edit` 的 oldString 匹配到 0 处 | 工具失败，把"没找到"告诉模型，让它重试 |
| 匹配到多处且没开 replaceAll | 工具失败，要求提供更长的上下文 |
| `patch` 的上下文对不上 | 该文件不应用，返回失败 |
| 写盘失败（权限、磁盘） | 该次调用失败；但 `patch` 是逐文件写的，中途失败不会回滚已写文件，错误里会列"失败前已完成"的路径 |
| 格式化失败 | 视实现而定：格式化是旁路，不应把已成功的写入判失败 |

前三行的共同点是：**失败信息本身就是给模型的下一步指令**。这和"抛异常给程序员看"是两种不同的错误设计。


## 3. 证据面：改完怎么知道对不对、怎么退回去

{{< fig "diagrams/03-revert.svg" "回滚的单位是「一步」，不是「一次写」" >}}

### 3.1 diff 不是 UI 算的，是工具算的

diff 有两条独立来源，这点容易混：

1. **工具内联 diff**：三个写工具都返回 `FileDiff.Info`（路径、变更类型、patch 文本、增删行数），存在工具结果的 `metadata.files` 里，给 TUI 内联渲染。它是"这次写"的 diff。
2. **快照树 diff**：由两个 Step 快照的 git 树直接比出来，覆盖这一步的**所有**改动——包括模型用 `shell` 跑的 `mv`、`sed` 之类。它是"这一步"的 diff。

前者精确到调用，后者覆盖到副作用。两者都有存在价值，不能互相替代。

还有省 token 的小动作：`trimDiff` 会把 diff 内容行的**公共缩进**裁掉。模型看到的 diff 仍能对齐，但每行少几个空格。

还有一个省 token 的小动作：`trimDiff` 会把 diff 内容行的**公共缩进**裁掉。模型看到的 diff 仍然能对齐，但每行少几个空格——在几十个文件的改动上这就是几百 token。

### 3.2 快照按 Step 拍，不按文件拍

这是 revert 语义的根：快照的粒度是**一步**，不是一次写。

- Step 开始时（发请求前）fork 一个 start 快照；
- Step 结束时（工具跑完后）拍 end 快照，并算出这一步改了哪些文件；
- `Step.Ended` 里带的就是这两个东西：快照 id 与文件清单。

所以"回滚到某一步之前"是天然支持的，"回滚某一个文件的某一次写"不是——后者需要从两个快照之间做文件级 diff，harness 没提供这个粒度。

### 3.3 revert 的三段状态

| 状态 | 事件 | 含义 |
| --- | --- | --- |
| staged | `revert.staged` | 按边界算出每个文件的恢复树，**立刻 restore 工作区**，并记下原始快照供撤销 |
| committed | `revert.committed` | 只删投影：消息、收件箱、指令回退、blob 释放；**不动工作区** |
| cleared | `revert.cleared` | 把文件恢复到 stage 之前的原始快照 |

顺序与直觉相反：**文件在 staged 那一刻就回滚了，历史是之后才删的**。点"回滚"能立刻看到文件变化，原因就在这里。

`committed` 唯一的工作是删——按边界消息的 seq 删掉其后的消息与收件箱项、把指令状态回退到边界、释放不再被引用的 blob。它不碰工作区，因为工作区已经被 staged 改过了。

还有一个默认行为：不显式 `commit` 的话，下一次 `prompt` 或 `compact` 会自动提交，等于永久改写历史。所以"暂存回滚"不是无限期可撤销的。

### 3.4 验证手段：harness 只做了一半

| 手段 | 谁做 | 说明 |
| --- | --- | --- |
| 语法/类型检查 | 模型（跑 shell） | harness 不内置编译，靠项目自己的命令 |
| 测试 | 模型（跑 shell） | 同上，跑什么由模型决定 |
| 格式化 | harness（仅 patch） | 见 2.5 |
| diff 审视 | harness | 工具结果与 UI |
| 诊断（LSP） | **没有** | 2.2.5 只有配置面，没有运行时 |
| 回滚 | harness | 快照 + revert |

这个分工是有意的：**通用性交给 shell，一致性交给 harness**。语言生态太多，内置编译器不现实；但"改动可回滚、diff 可见、权限可控"是跨语言通用的，所以由 harness 保证。

代价是没有 LSP 那种"改完立刻知道类型错了"的即时反馈，模型只能靠跑测试或编译器来发现——慢，而且要求项目本身配好了这些命令。


## 4. 另一条路：写程序来改代码

先纠正一个想当然的前提：**这条路目前走不到文件编辑上**。

v2.2.5 把 `read`、`write`、`edit`、`glob`、`grep`、`shell`、`webfetch`、`websearch`、`todo`、`question` 全部标了 `codemode: false`，它们根本不进程序目录。真正进 Code Mode 的只有两类：MCP 工具（默认进）与 `opencode.*` 那组管理工具。

所以"用程序改三个文件"在 2.2.5 里没有形态：要么直调三次 `edit`，要么先把写文件能力接进去。

### 4.1 它解决的问题

逐个调工具，最小单位是**一次模型轮次**：输出工具调用、停下、等结果进上下文、再推理。N 步串联就是 N 次往返，而且每步的完整结果会永久留在上下文里，哪怕后面只用一个字段。

写程序把 N 步压进**一次往返**：循环、条件、`allSettled` 并行都写在代码里，中间值留在程序变量里，只有 `return` 的部分回到模型。

所以它换掉的不是"工具调用次数"，是"模型轮次"。

### 4.2 沙箱：只实现需要的语言特性

它没有把 V8 关进笼子，而是只实现了自己需要的那部分 JS。README 写得很直白：与其沙箱任意 JS，不如只跑我们实现的语言特性。

- 全局是一张四十多项的白名单，没有 `setTimeout`、`setInterval`、`process`、`globalThis`、`Buffer`；
- 没有定时器是刻意的：等一个永不 settle 的 promise 会被判成死锁，并提示"Code Mode 没有 timer、没有 sleep"；
- `Function` 构造器保留只为让 `fn.constructor === Function` 成立，调用与 `new` 都直接抛错；
- `import` 不通向磁盘，只能回查已有全局，所以 `import fs from "fs"` 会报"不能加载包或文件"；
- 单条内建不能一次造出无限值：字符串 2^24、数组 10^7、并发 promise 10^4、跨界值深度 32。因为超时只在解释器步与步之间生效，管不住一次 `"x".repeat(1e9)`。

唯一的出口是 `fetch` 扩展：拒绝 `file:`、拒绝带凭据的 URL、复用 webfetch 权限且**每跳重定向都重新校验**、上限 20 跳、30 秒超时。

### 4.3 程序怎么跑

入口是名为 `execute` 的工具，入参只有 `{ code }`。程序里每次 `tools.xxx(...)` 都回到真实工具管线：解码输入、跑 before hook、执行、解码输出、跑 after hook，并检查 `maxToolCalls`——只是主路径没有传 limits，所以默认既没有超时，也没有调用上限。所以"程序里的调用"和"模型直调"在权限、审计、错误文本上完全一致。

失败是**全有或全无**的：首条 throw 即终止，未 await 的宿主调用会被主动 interrupt（超时是协作式的，只在解释器步与步之间检查）；程序级失败返回 `ok: false`，core 把它变成带 `error` 标记的文本。

### 4.4 两种形态的对照

| | 直调 | 写程序 |
| --- | --- | --- |
| 轮次 | N 次，每次看结果再决定 | 1 次，N 处参数一次写对 |
| token | N ×（上下文增量 + 输出） | 代码 + 过滤后的结果 |
| 失败 | 局部、可重试、中间态可见 | 全有或全无，中间输出被吞 |
| 并发写同一文件 | 由工具层按路径加锁 | 程序里没有事务，会互相覆盖 |

所以适合写程序的是**批量、组合、循环过滤密集**的场景（多个 MCP 工具、批量读取）；需要逐步判断、看中间结果，以及今天所有的文件编辑，适合直调。

### 4.5 为什么文件编辑被排除在外

这不是遗漏。文件编辑的特点是"每一步都要看结果"：改完要看 diff、要决定下一步改哪里、失败了要局部重试。这些恰好是程序形态最弱的环节——中间输出看不见、失败不局部。

把编辑放进程序，等于要求模型"一次写对一串修改"，而 harness 花那么大力气做的模糊匹配、diff 回显、按步回滚，全都白费了。

顺带一个工程细节：解释器并不在 `core` 里。core 只有五个外壳文件（tool / catalog / instructions / fetch / execution，约 900 行），真正的解释器与 VM 在独立的 `packages/codemode` 包里（两套引擎分别约 2500 与 3100 行）。默认用 legacy（acorn AST 解释器），VM 默认在 dev/local 开、发布版关。

## 5. 对照组：文本、图像、语音

生成类请求和 coding 走的是**同一条底层路径**——`ai.request()` 造出 `LLMRequest`，`LLMClient.generate/stream` 消费它。`ai.request` 本身极简：`prompt` 变成一条 user 消息，`tools` 默认空，`system` 默认空。

所以"生成"之间的差别，全在**谁往上叠了什么**：叠 agent system、叠工具定义、叠 transcript、叠输出上限，或者干脆换一套协议。

### 5.1 六种生成，叠的东西不一样

| 生成 | 叠了什么 | 输出去哪 |
| --- | --- | --- |
| 编码（primary） | 全部：system + instructions + 工具 + 历史 + 媒体，多步循环 | 工具调用 → 文件 + 消息 |
| 会话文本生成 | 同样的 transcript 与工具目录，但只发一次 `generate` | 直接返回字符串，**不落库** |
| 标题 | 只有 title agent 的提示 + 一条被框住的消息，无工具、无 instructions | 会话 `title` 字段 |
| 压缩摘要 | 完整 transcript + 工具目录 + 摘要 prompt 追加在最后 | compaction 消息（持久化） |
| 图像 | prompt + 可选参考图 | base64 内联（工具层再落盘） |
| 决策 / 语音 | 完全不同的协议 | 答案 / 实时 transport |

最反直觉的是"会话文本生成"：它**带着真实工具目录**，但只发一次 `generate`，工具永远不会被执行。测试把这个说得很清楚——请求里 `tools` 有 `lookup`、`toolChoice` 为 undefined、执行前后 durable state 完全相等。

它的用途也合理：让插件或 SDK "带着当前上下文问一句"，但不污染会话。

### 5.2 为什么标题不给 maxTokens

`prepare` 里只有 primary 与 compaction 两个分支算输出上限，其余一律空。注释的理由是：输出上限同时管住可见文本与 reasoning token，而标题这种短任务的 reasoning 占比不可预估——给小了截断答案，给大了撑爆窗口，不如交给 provider 默认。

标题用另一种预算手段替代：**先选便宜的小模型 + 最低 variant**，失败才回退主模型。所以"省钱"不是靠压 maxTokens，是靠选模型。

压缩摘要正相反：它有明确的预算计算与下限（最低 1024，尽量给到 32k），因为它必须在窗口内产出结构化摘要。

### 5.3 图像生成不在会话里

`Generate.image` 是纯函数：模型返回 URL 就下载、嗅探真实 MIME，最终结果是内存里的一段 `{type:"image", data, mime}`——**不落库、不进 blob、不是 file part**。

真正回到会话的是工具 `experimental_image_generate`：它把 base64 写到 `global.tmp/images/<sessionID>/`，调用是后台 job，立刻返回 `{id, path, model}` 和一段"别 sleep、别轮询"的提示；完成或失败后用 `sessions.synthetic` 注入一条合成消息。所以产物以**磁盘文件 + 合成通知**的形式出现。

它也不是 `Artifact`（那是用户级文件存储），不会被 `media.get` 读到——除非之后被读图工具或用户附件重新引入成 blob。

### 5.4 决策与语音是另外两套协议

决策不用 chat 协议：它有自己的 `DecisionModel` 与路由，请求是"一段输入 + 一组问题"（predicate / choice / score），响应是每个问题一条答案，可以局部失败，还带 provider 报价的成本。没有会话、没有工具、没有 system 角色。

语音更彻底：不问不答文本，只拿凭据换一条实时通道（WebRTC/WebSocket），音频流完全不经过 opencode 的消息体系——没有上下文、没有持久化、没有 token 预算。

### 5.5 一句话对照

编码与其他生成的差别，不在"模型怎么想"，而在**产物有没有副作用**：

- 文本生成的产物是字符串，错了重发；
- 图像的产物是文件，但通常独立于仓库；
- 编码的产物是**工作区的状态变化**，错了要回滚、要解释、要防止再发生。

所以只有编码这条路上长出了"证据面"：diff、快照、revert、权限审批。其余生成只需要"参数对不对、格式合不合规、成本多少"。

## 6. harness 层到底做了什么

把前面几节的动作摊开，harness 在 coding 上做的工作可以归成六类：

| 面 | 具体工作 | 模型做不了的部分 |
| --- | --- | --- |
| 动作 | 提供读/搜/改/跑四类工具，按权限过滤 | 决定"能做什么" |
| 物理 | 路径解析与越界审批、按路径加锁、BOM 与行尾保留、模糊匹配定位 | 让"改"在真实文件系统上可靠 |
| 证据 | diff 生成与裁剪、按 Step 拍快照、revert | 让改动可审视、可回滚 |
| 规范 | 系统提示、工具说明、AGENTS.md、CodeMode 目录 | 告诉模型"这里怎么做事" |
| 边界 | 输出截断、上下文预算、超时与中断、沙箱 | 让失败可控 |
| 恢复 | 执行声明、孤儿工具结算、重启续跑 | 让中断可续 |

一句话：**模型负责"想改什么"，harness 负责"改得对不对、能不能退、谁允许改"。**

### 6.1 为什么这些必须放在 harness

三个理由，按重要性排：

1. **不可逆的动作需要外部约束**。模型可以提议删文件，但不能自己决定"不用问"。权限、审批、沙箱都在模型之外，才有意义。
2. **跨模型一致**。同一套工具语义、同一套 diff 与回滚，换模型不用换工作流；反过来，如果把这些塞进 prompt，每换一个模型都要重新调。
3. **可测试**。工具管线、匹配算法、快照恢复都能写单测；prompt 里的"请小心修改文件"不能。

### 6.2 与"纯生成"的分界线

生成任务的产物是**文本或媒体**，错了重发一次就行；coding 的产物是**副作用**，错了要回滚、要解释、要防止再发生。这条分界线决定了 harness 的重心：

- 生成侧重点是"参数对不对、格式合不合规、成本多少"；
- 编码侧重点是"改到了哪、能不能看见、能不能退、谁批准的"。

同一个 harness 同时服务两者，但只有编码侧需要"证据面"这一整层。


## 7. 边界与代价

**harness 在猜模型的意图。** 模糊匹配、行尾推断、BOM 保留，本质都是"模型给的东西不精确，帮它对齐"。这提高了成功率，也意味着一次改动可能落在模型没预期的地方——所以 diff 必须给模型看，不能只给人看。

**格式化只覆盖一条路径。** 只有 `patch` 会跑 formatter，`write`/`edit` 不会。同一个会话里，"用 patch 改的文件被格式化、用 edit 改的没有"，这种不一致会让模型对结果产生错误预期。

**没有 LSP，反馈靠跑。** 类型错误只能通过编译或测试发现，比 IDE 里的即时诊断慢一个数量级。harness 用"可回滚"补偿了这一点，但没有消除它。

**revert 的粒度是一步。** 想撤掉"十分钟前那次写"而不是"整步"，做不到——快照按 Step 拍，文件级恢复只能整体回到某个 Step 的边界。

**CodeMode 把调试成本转移给了模型。** 程序内部的错误栈不可见，模型只能根据返回文本猜哪里错了；批量改动省下的往返，可能被一次失败的程序抵消。

**写入不是崩溃原子的。** 没有临时文件 + rename，直接 `writeFile`；写到一半进程被杀，可能留下截断文件。快照在 Step 边界，救不了"半步之内"的损坏。

**没有崩溃恢复的写入日志。** `Tool.Called` 到真正持久化之间没有幂等重放，`file-mutation` 里的 TODO 自己也承认这一点。

**最根本的代价是复杂度。** 读、改、跑、快照、权限、恢复，每一层都有自己的失败模式；这些失败叠加起来，就是"agent 改代码"偶尔会出现的那种难以复现的错位。harness 的价值在于把这些错位收敛到可观测、可回滚的范围内，而不是消灭它们。
