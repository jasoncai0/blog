当代码提交主力从人类工程师变成 24 小时在线的 AI Agent 集群，Git「假设客户端离线工作、每份克隆都是完整自治仓库」的对称设计会从优势变成算力黑洞；Anthropic 由 7 名工程师组成的团队用 5 个月构建并全量切换至自研中心化版本控制系统 Scion，将版本控制集群的 CPU 与内存占用缩小到原先 Git 镜像方案的 1/200，CI 与科研任务代码检出耗时从分钟级缩短至秒级。

本文面向负责大型单体仓库（Monorepo）、CI/CD 基础设施与大规模编码 Agent 沙箱平台的工程师，完整拆解 Anthropic Engineering 于 2026 年 10 月 13 日发布的《Redesigning source control at Anthropic》（10 月 15 日增补技术渊源说明）。读完后，你能看清在日合并量跨过万级门槛后 Git 镜像与浅克隆为何失效，以及即使不自研 VCS，如何借鉴 Scion 的非对称 RPC 与分层对象缓存改造现有代码托管流水线。

## 一、为什么 Git 镜像与浅克隆撑不住 Agent 规模

Git 为离线分布式协作而生，但 Anthropic 单体仓库的实际负载是「单一权威主干 + 数千万个永远在线的 CI 与 Agent 临时沙箱」，架构假设与真实负载完全错位。

从 2026 年 5 月到 9 月，Anthropic 单体仓库的日均代码合入量从约 2,500 次飙升至超过 30,000 次（4 个月内变为原来的 12 倍以上）。与此同时，仅主分支历史体积已逼近 100 GB，单份压缩工作区超过 25 GB，而仅 CI 每天就要执行约 2,500 万次代码检出（尚未计入开发环境、Agent 沙箱与科研训练任务）；如果朴素拉取，每天产生的 Git 网络流量将超过 600 PB。

在决定自研前，团队把行业通用的 Git 扩容手段全部用到了极限，并逐一撞上天花板：

1. **数百台内部 Git 镜像节点撞上单机磁盘与内存上限。** 高峰期团队维护了数百台内部 Git Mirror 分担读流量，但每台镜像仍需在本地保存完整的对象库并定期执行高消耗的 Packfile（Git 将大量松散对象增量压缩打包成的单文件存储与传输包）重打包维护；一旦仓库体积突破单机存储或内存水位，水平扩容立刻失效。
2. **对象存储快照种子（Seeds）跟不上每秒合入的分支尖端。** 预制快照放到对象存储供客户端下载后再做增量 `git fetch`，在日合入两千次时尚可应付；当日合入突破三万次，两次快照刷新之间主干已向前推进数千个提交，增量追赶与压缩计算的开销重新压垮上游。
3. **浅克隆与按需补拉导致历史查询脆弱易碎。** 组合使用 Shallow Clone（截断历史深度）、Sparse Checkout（仅检出部分目录）与 Promisor Remotes（允许本地缺失对象、读到时再向远端延迟补拉的 Git 部分克隆机制）后，任何依赖提交图的日常操作（如 `git diff`、`git blame`、自动二分排查 `bisect`）都需要频繁跨网补拉缺失历史，大量内部自动化工具被迫在本地维护沉重的仓库副本。

## 二、Scion 核心数据模型：WAL 增量变更集与递归派生数据

Scion 借鉴了 Google Piper 与 Meta Sapling 服务端 Mononoke（尤其是仅存储相对父提交文件级变更而非全量目录树的 Bonsai 数据模型）的核心思想，彻底抛弃客户端本地提交再推送的流程，让每一次提交、变基与合并直接发生在服务端，保证单次写入代价只与「本次改动的文件数」成正比，与 100 GB 仓库总历史无关。

{{< fig "diagrams/02-changeset-derived-graph.svg" "Scion 服务端存储与索引派生模型：WAL 增量 Changeset 负责无锁高吞吐写入，递归 Derived Data 按需生成 Blame 与跳表索引" >}}

1. **无锁写入的 Changeset 取代全量目录树指针。** 在 Git 中，每个 Commit 指向一棵完整的根目录 Tree 对象，推送时需要打包协商 Packfile 并锁住分支引用（Ref）。Scion 的基本工作单元是写入预写日志（WAL）的一条 `Changeset`：它只记录相对于第一父提交（在全员基于单一主干开发的 Trunk-based 模式下，人们查询行级归属与文件历史只关心主线演进）发生增删改的文件路径列表，以及指向对象存储中压缩文件内容的寻址指针（Content-Addressed Blob Pointers）。整个服务端不存在任何一份「完整物化的仓库副本」，也没有 Packfile 重整任务；创建 Changeset 无需跨机协调或加锁，立即可见。
2. **压缩全局可变状态，分支推进退化为 Spanner 单行 CAS。** 所有需要全局达成一致的可变指针（Refs，如分支和标签）都是高并发扩展的隐患。Scion 在开发生命周期中默认不鼓励创建分支 Ref，仅保留 `main` 与发布分支；拉取与创建提交完全绕开 Ref，而推进 `main` 指针只是对 Google Cloud Spanner 单行记录执行一次原子比较并交换（Compare-and-Swap）。
3. **用统一递归机制按需计算派生数据（Derived Data）。** 由于 Changeset 只存增量变更，直接读它无法快速回答「某行代码最后由谁修改（Blame）」或「待变基改动与主干的最近公共祖先（Merge Base）」。Scion 将文件 Blame、路径历史、加速图遍历与求公共祖先的提交图跳表（Skip Lists，允许按指数步长跨代跳跃查询祖先的索引结构）以及后续新增的拷贝检测、路径搜索索引全部抽象为递归定义的派生数据：主线归属类索引沿第一父节点与本次增量变更递推，提交图跳表则根据父节点跳表指针递推更新。

```text
# 派生数据统一递归求值（服务端内部透明演进，客户端零感知）
function get_derived(changeset_id, dtype):
    cached = spanner_or_memcache.get(changeset_id, dtype)
    if cached != null:
        return cached
    cs = wal_store.read_changeset(changeset_id)
    parent_val = get_derived(cs.first_parent, dtype)
    # 复杂度仅取决于 cs.changed_files 大小，与仓库总文件数无关
    val = dtype.step(parent_val, cs.changed_files)
    spanner_or_memcache.put(changeset_id, dtype, val)
    return val
```

这段递归求值逻辑带来了三项工程收益：新增索引类型时无需改动底层变更集格式；每种派生数据可独立配置「提交时急切计算（Eager）」或「首次查询时惰性计算（Lazy）」以免浪费算力；所有元数据查询均通过服务端 API 直接暴露，CI 算差异、自动回滚管线做二分定位时连本地工作区都不需要检出。

## 三、三级缓存四跳检出协议：只报缺失对象，逐级命中率均超 99%

当任务确实需要落盘读取代码文件时，Scion 客户端 `scn` 放弃了 Git 昂贵的「汇报本地已有提交以协商增量包」协议，改用「客户端本地缓存 → 宿主机 `scion-daemon` → 区域 `scion-cache` → 权威 `scion-server`」的三级缓存四跳内容寻址拉取，把检出耗时降低了两个数量级。

{{< fig "diagrams/03-checkout-sequence.svg" "Scion 四跳同构检出时序：客户端仅递归请求缺失 Tree 与 Blob，三级缓存与权威源共享同一套 RPC 且严格隔离故障域" >}}

1. **客户端只请求「缺什么」，天然兼容稀疏与虚拟化检出。** Git `fetch` 需要服务端根据客户端上报的 `have/want` 集合动态计算差集并实时增量压缩成单个多 GB 的 Packfile，极耗服务端 CPU 且中途断连难以续传。`scn` 从目标根 Tree 出发，先查客户端有界缓存，仅对缺失的目录树发起递归请求，再同理拉取缺失的 Blob；因为所有对象均按内容哈希寻址、写入后永不改变，任何中间缓存节点都能直接应答，稀疏检出（只拉指定子目录）与按需虚拟化挂载无需任何特殊补丁即可原生工作。
2. **宿主机守护进程、区域内存缓存与权威服务同构分层。** 宿主机上的任务通过本地 Socket 访问整机共享的 `scion-daemon`（从定期刷新的快照启动，同一物理机上的并发任务直接复用对象）；单机未命中的新提交对象请求发往同可用区的 `scion-cache`，由于集群内数千台宿主机都在并发检出同一批最新主干改动，首台机器回源预热后其余机器全部命中区域内存缓存，直接流式吐出与守护进程磁盘格式一致的数据块（零压缩转换开销）；极少数冷对象才回源 `scion-server` 读取 Spanner 与对象存储。因此每一级缓存层各自的命中率均稳定在 99% 以上。
3. **同构 RPC 降低客户端复杂度，严格分层阻断缓存雪崩。** `scion-daemon`、`scion-cache` 与 `scion-server` 对外暴露完全相同的 RPC 接口，客户端无需感知底层拓扑；但服务端在路由策略上强制逐层访问、严禁跨层直连，确保单区域 `scion-cache` 异常时流量不会直接击穿上游权威 `scion-server`。上线后仅 CI 集群就因此额外释放出 25% 的全局 CPU 算力。

## 四、7 人 5 个月迁完百 GB 仓库：AI 时代基础设施工程的三个转折

Scion 的诞生本身就是「用 Agent 解决 Agent 制造的瓶颈」的样本：在日合并量涨至原来 12 倍以上的窗口期内，7 名工程师不仅交付了 Scion 并完成全量切换，还顺带交付了配套代码审查平台 Antique、代码搜索与细粒度目录级 IAM 权限系统。

| 工程维度 | 迁移前（Git + 数百镜像集群） | 迁移后（Scion + Antique 体系） | 实测变化幅度 |
|---|---|---|---|
| 单体仓库日均合入量 | 约 2,500 次 / 天（2026 年 5 月） | 超 30,000 次 / 天（2026 年 9 月） | 变为 >12 倍 |
| 服务端镜像/缓存资源占用 | 数百台全量 Git Mirror 节点 | 无状态分层缓存 + 少量权威节点 | CPU 与内存缩至 1/200 |
| CI 与科研任务检出耗时 | 分钟级（受限于网络与解压） | 秒级（稀疏按需 + >99% 逐级命中） | 提速约 100 倍（CI 省 25% CPU） |
| Git 导入管线原型重写 | 人工手写初版原型 | Claude Mythos Preview 零提示重写 | 内存降至 1/20，吞吐提升 4 倍 |

1. **人类工程师的核心价值从「逐行写码」转向「守住系统约束并对模型说不」。** 团队全员承认内部预览版超前沿模型 Claude Mythos Preview 的编码能力已超过自己（例如把人工编写的 Git-to-Scion 导入管线交给它重写，未给额外指令便产出了内存占用低 20 倍、速度快 4 倍且完整保留隐式顺序不变式的实现，还顺手抓出祖先查询漏走索引等优化点）。但 Agent 经常为了局部跑通而破坏全局架构红线：迁移期间多个子系统里的 Agent 试图通过「线性扫描整条提交日志」暴力查询某次改动的合入时间，而非调用代码审查服务接口；内部广泛使用的对抗性代码审查有时又因过度防御内部可信服务，诱导 Claude 堆砌冗余校验。工程师审查 PR 的重心随之从检查语法细节转向审查「设计意图与跨系统边界」。
2. **放弃阻塞全仓的全局合并队列锁，转向无锁合入后验证与冲突秒级自愈。** 人类规模下的标准实践是用全局加锁的串行合并队列保证每次合入前跑完全套主干 CI；但在测试运行期间就有成百上千个改动涌入的 Agent 规模下，全局锁直接锁死吞吐。团队在 Antique 合入流水线中放弃了全局仓库锁，改为投入合入后（Post-merge）与部署前（Pre-deploy）自动化测试闭环；并发合入引发的代码冲突交由 Claude 自动修复，处理速度比人类定位冲突还快。
3. **用单组件专属「Superfan」Agent 替代一维阈值告警。** 团队利用内部协作代理平台 Claude Tag 在 Slack 频道里为 `scion-daemon`、`scion-cache`、Antique 合并提交通道各配备了一名「狂热粉丝（Superfan）」Agent，全天候盯住对应组件的日志与遥测曲线，像一名只管这一个模块的资深值班工程师一样捕捉传统静态阈值告警发现不了的微妙毛刺。

如果你的团队尚未达到千万级日检出规模，切勿盲目抛弃 Git 生态去自研全套 VCS（Scion 强绑定自研代码审查、搜索与 CI，不具备通用开箱移植性）；更务实的演进路线是先将 CI 与 Agent 的历史/Blame 查询改为调服务端 API 免除本地全量克隆，并在构建集群宿主机落地只读对象共享缓存。诊断与排障时盯紧三项指标：判断是否需要重构 Git 检出链路，先查镜像同步延迟是否随合入速率超线性攀升、CI 是否有超过 20% 的 CPU 耗在拉代码与解压上；落地分层对象缓存后若出现检出退化或上游负载陡增，优先查宿主机守护进程的快照刷新周期是否滞后，以及路由层是否漏配了阻断跨层直连权威存储的熔断策略。
