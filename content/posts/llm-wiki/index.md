同一篇论文读到第三遍，模型还是从零拼一遍。RAG 的结构性浪费在这里：知识没有积累，每次提问都在重新发现。

2026 年 4 月，Karpathy 发了一份叫 [LLM Wiki](https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f) 的 idea file，给了一套相反的做法：让 LLM 在摄入时就把知识整理成 wiki 页面，查询时只读页面、不再重推。这份文件没有配套代码，只写了目录职责和工作流，但结构足够清楚，值得逐个环节拆开看。

## 「每次提问都重读一遍」的代价

标准 RAG 的链路固定：文档切块、向量化、查询时取 top-k、把片段塞进上下文、现场综合。它解决了「模型读不到私有文档」，没解决「读过的文档能不能变成结构」。

三个后果：

1. **综合成本重复付。** 一个要综合五份文档的问题，每次提问都要重新定位、拼凑、权衡；第 100 次问和第 1 次一样贵。线上检索的成本结构，[RAG 线上工程实践](/posts/rag-production-practice.html) 有另一组数。
2. **答案随召回波动。** 换一个措辞、换一次 top-k，答案的依据就变了；正确性依赖检索运气，不依赖已确认的结构。
3. **会话结束即归零。** 上一次的分析、对比、结论留在聊天记录里，下一个会话读不到，更不会自动变成下一次的依据。

LLM Wiki 借了编译器与解释器的分工。解释器每次运行都重新求值；编译器先产出一个中间表示，后续优化和执行都针对这个 IR。对应过来：

- wiki 是 IR，是知识的编译产物；
- `index.md` 是符号表，告诉进程有哪些名字、在哪；
- `log.md` 是构建日志，记录每次编译做了什么；
- LLM agent 是编译进程，负责读源、写页、更新索引。

编译不免费。一次性事实查询用 RAG 更便宜。值得编译的是会反复综合、会持续更新、多个会话或多个角色要复用的领域，比如一个团队的产品知识、一个品牌的设计规范、一个项目的决策史。

## 三层：原件、派生页、写法约束

目录结构可以自己定，三层职责是固定的。

1. **原始层只读。** 文章、论文、网页剪藏、PDF 原样放在 `raw/`，不编辑、不改名、不加注释。它是唯一事实源，wiki 写坏了可以整层重编。agent 对 raw 只有读权限，这一点要在工具层强制，不能靠提示词自觉。
2. **派生层由 agent 全权维护。** wiki 页面是 markdown，按页面类型分目录：来源摘要、实体、概念、对比、总览。人可以读、可以批注，但不手写页面，否则下次摄入会和手写内容打架。
3. **schema 约束写法。** `AGENTS.md` 或 `CLAUDE.md` 规定目录结构、front matter 字段、wikilink 格式、矛盾怎么标、一次摄入的工作流、日志行格式。它把通用模型变成一个有纪律的维护者。

三层分开的好处是可替换：换一个 viewer 不影响内容，换一个 agent 不影响约定，改 schema 可以只重编受影响的部分。wiki 整个目录是 git 仓库，每次摄入一个 commit，diff 就是这次知识变更的审计记录。

另有两个导航文件，不存知识，只存「去哪找」：

- `index.md` 是内容目录，按主题分组，每条一句摘要加链接。每次摄入都更新它。
- `log.md` 只追加，每行固定前缀 `## [YYYY-MM-DD] action | title`。要查最近发生了什么，`grep "^## \[" log.md | tail -5` 就够，不需要语义检索。

## 一次摄入改 10–15 页

一次摄入不是「写一个摘要」，是「把新来源插进已有结构」。原文给的经验值是**一个来源通常触及 10–15 个 wiki 页面**，这个数字是整套方法的核心，也是主要成本。

流程可以拆成五步：

1. **读 schema 和 index。** 先知道当前有哪些页面、命名怎么定，避免新建一个重复页。
2. **读原文，抽事实。** 实体、概念、主张、数据、引用出处，逐条能落回原文位置。
3. **在 index 里找命中页。** 这一步是目录检索，不是向量检索：新来源提到的实体，是否已有页面；已有页面里有没有相反结论。
4. **决定 create、update 还是 merge，然后写扩散。** 新实体建页，已有实体改页，主题总览修订，相关概念页补交叉引用。写扩散的页数要设上限，超过就说明这次摄入粒度太粗，应该拆源。
5. **收尾。** 标矛盾、补入链（新页面至少被一个已有页面引用）、更新 index、追加 log、commit。

举个具体例子。一篇讲某公司新一轮融资的文章进来，会被拆到这些页面：

- 公司页：融资轮次、估值、时间、投资方；
- 创始人页：新增的头衔或持股变化；
- 投资方页：投过哪些公司，这次是哪一轮；
- 赛道页：这一轮的估值在赛道里处于什么位置；
- 时间线页：补一条事件；
- 总览页：修订「当前格局」那一段；
- 矛盾标记：如果上一轮估值和这次披露对不上，在相关页写一段 `⚠️ 冲突`，注明两个来源和日期，不擅自选一个。

成本量级：15 页 × 每页 1–2k token 的输出，加上读原文和读候选页的输入，一个来源大约 20–40k token。这就是原文建议一次只摄一个源、且人在环的原因。批量摄入会让模型在没读完全部候选页时就开始写，错误会直接进结构。

## 检索：先读目录，再下钻

wiki 的检索不是向量优先，是目录优先。

一次查询走三跳：

1. 读 `index.md`，按标题和一句摘要选 3–5 个候选页；
2. 读候选页，确认哪几页真正相关，顺着 wikilink 再走一层；
3. 答案里每个结论都带页面链接，页面里再带原始来源链接，能一路退回 `raw/`。

这条链路在**约 100 个来源、数百个页面**以内是够用的。index 一页读完，agent 不用碰向量库。超过这个规模，index 本身会变成需要检索的对象，原文建议换 [qmd](https://github.com/tobi/qmd)：本地 BM25 加向量召回，再加一层 LLM 重排，有 CLI 也有 MCP 接口。

注意 qmd 的位置：它替代的是「读 index」这一跳，不是事实源。事实仍然在 markdown 页面和 raw 里，向量库随时可以重建。这个边界划清楚，才不会退化成「又一个 RAG」。

## 查询也写回

查询不只是读。一次分析如果产生了新结构，比如两个方案的对比表、一组跨页面的因果链、一个此前没人写过的关联，就应该落成一个新页面，带引用，然后更新 index。

回填让探索也复利。三周前问过「这两个品牌的视觉语言差在哪」，今天打开就能读到当时的对比页，而不是再问一遍。它同时给 lint 提供了素材：新页面会暴露旧页面的矛盾。

回填要有合并规则，否则页面会膨胀：

- 同一主题的对比页只保留一页，新结论合并进旧页并标日期；
- 单页超过约 200 行就拆子页，父页只留摘要和链接；
- 纯聊天内容、没有可复用结论的，不回填。

## 页面会腐烂，lint 是维护工序

wiki 会腐烂，而且腐烂是结构性的：一个错链接会被十几个页面引用，越用越像真的。所以原文把 lint 当成固定工序，不是可选项。

lint 查六类问题，按性质分两组：

**结构类**

1. 孤儿页：没有任何入链，查询永远走不到；
2. 被提到但没有页面的概念：正文里反复出现 `[[X]]`，X 页不存在；
3. 缺交叉引用：两个强相关页面互不链接。

**内容类**

4. 矛盾：两个页面在同一事实上给了不同结论；
5. 过期结论：新来源已经推翻，旧页还写着肯定句；
6. 数据缺口：页面声称有数据，但来源链接失效或没给数字。

lint 的产出是工单，不是自动改写。修复本身是一次小摄入：读相关页、改一处、补引用、记 log。改完看 diff，因为 lint 也会编造关系，尤其是「这两个概念相关」这种没有来源支撑的判断。

{{< fig "diagrams/04-lifecycle.svg" "页面的生命周期：新建页必须被入链才能被检索到，lint 与人工复核把页面推向有效、陈旧、被取代或归档" >}}

谁来干活，原文分工很清楚：人选源、提问、判断，agent 摘要、交叉引用、归档、记账。定时任务只做 lint 和日报，不做内容裁决。

## 这套东西什么时候不成立

1. **结构错误会沿链接放大。** RAG 的错误是一次性的，答错就过去了；wiki 的错误会被 10–15 个页面引用，后续摄入在错误关系上继续叠加。缓解手段只有三个：引用必须落到来源哈希、矛盾段显式标注、每次摄入看 diff 并抽样回读原文。没有这三条，wiki 会变成一台高效的错误放大器。
2. **schema 是质量上限。** 约定含糊，不同会话会做相反决策：一个把产品别名合并，一个新建页。对策是把页面模板、front matter 校验、命名规则写进 schema，每踩一次坑回写一条。
3. **规模有拐点。** 20 个来源好管，200 个来源是治理工程：index 读不完、编译窗口不够、页面开始互相矛盾。超过 100 源要加混合检索，超过几百页要分层 index，冷门页面降级为按需编译。
4. **团队要问责结构。** 谁定来源质量、谁拥有 schema、谁裁决矛盾、谁审计幻觉链接。这四个问题没有技术解，只有角色。缺了它们，AI 只是加快了错误传播。
5. **权限不在原文里。** 原文假设单用户本地目录。多租户场景要自己加：页面继承资产节点的 ACL，编译时和检索时各校验一次，跨权限域不聚合。

## 和 RAG、知识图谱、Memory 的边界

| 维度 | RAG | LLM Wiki | 知识图谱 | Agent Memory |
|---|---|---|---|---|
| 写入时机 | 查询时 | 摄入时 | 建模时 | 会话或事件触发 |
| 产物 | 临时上下文 | markdown 页面加链接 | 实体关系三元组 | 分层记忆条目 |
| 检索方式 | 向量 top-k | 目录到下钻 | 图查询 | 混合召回 |
| 错误形态 | 一次性 | 结构性放大 | 关系错误 | 偏好漂移 |
| 规模拐点 | 上下文窗口 | 约百源 | 建模与抽取成本 | 写入质量 |
| 主要成本 | 每次查询 | 每次摄入的写扩散 | 本体设计与抽取 | 去重与维护 |

它们不互斥。常见组合是：wiki 存领域知识，Memory 存用户偏好，向量库做兜底召回，知识图谱只在需要严格关系推理的子域里建。

## 上手路径

1. 选一个窄域，写一页 schema，半天。域选大了 schema 一定空，先从一个产品线或一个项目开始。
2. 一次一源，摄 5–10 个来源，每个 20–40 分钟。每摄完一个，自己读一遍新页面。
3. 每周读一遍最近新增的页面，把不一致的地方写回 schema，1 小时。
4. 每周跑一次 lint，只修结构问题，30 分钟。内容矛盾进待办，别当场改。
5. 到 100 源再加混合检索。在那之前 index 够用，提前上向量只会多一套要维护的东西。

先跑 10 个源，再判断这套东西值不值得扩。跑不动的原因通常不是模型不够强，是来源太杂或 schema 太虚。
