## 一、架构与主循环：51 万行 Harness 怎么转起来

这四道题回答「敲下回车后客户端代码到底干了什么」。Claude Code 因 npm 打包误传 `.map` 文件泄漏的约 51 万行客户端 TypeScript 代码里，约 80% 都在处理超时、中断、配对修复、截断续写和权限门禁，核心循环正常路径只有约 200 行。通用循环概念可对照 [Agent 面试 30 题](https://www.jasoncai.site/posts/agent-interview-30.html) 第一、二节。

### Q1 Claude Code 的四层架构怎么划分？为什么弃用 ReAct 改用 Tool-Use Loop？

Claude Code 客户端分成引擎层、工具层、共享服务层、安全与治理层四块；主循环弃用显式输出 `Thought → Action → Observation` 文本的 ReAct 范式，改用「内部 Extended Thinking + API 原生 `tool_use` + `end_turn` 原语」驱动的 Tool-Use Loop。

四层职责严格隔离。引擎层只管拼装消息、分发工具调用和判断循环起停，不含任何读写文件或搜代码的业务逻辑，新增能力只需往工具池注册新工具，主循环零改动。工具层封装 40 多个工具，并在 TypeScript 类型层面强制每个工具声明三项安全属性：是否只读、是否具破坏性需确认、能否与其他工具并发执行，漏写一项直接编译失败。共享服务层提供统一的模型 API 调用、五层上下文压缩与 MCP 客户端通信。安全与治理层横切罩在全层之上，包含权限判定、生命周期 Hooks 以及基于语法树（AST）检测命令注入和路径逃逸的 Bash 安全模块。

弃用 ReAct 有三个工程原因。早期 GPT-3.5 推理弱，才靠显式输出 `Thought` 文本逼模型分步想；放到跑 50 轮的编程任务里，每轮几百字的思考文本反复留在历史消息中重算计费，白烧几万 Token，还要靠正则切分文本提取动作，格式一歪就解析崩溃。Opus 级模型在内部通过 Extended Thinking 完成深度推理，思考过程不污染外部消息上下文，随后直接返回结构化 `tool_use` 块或 `end_turn` 停止信号，客户端只需 `if/else` 判断即可运转。

| 对比维度 | 传统文本 ReAct | Claude Code Tool-Use Loop |
|---|---|---|
| 推理发生位置 | 显式输出 `Thought` 文本进历史消息 | 模型内部 Extended Thinking（不占应用上下文） |
| 动作解析方式 | 正则或字符串切分提取 Action | API 原生结构化 `tool_use` 块 |
| 终止条件判定 | 匹配 `Final Answer` 等约定词 | 检查返回中是否不含 `tool_use`（`end_turn`） |
| 50 轮累计开销 | 数万额外思考 Token 逐轮复利计费 | 零外部格式胶水开销 |
| 适用模型底座 | 早期弱推理模型 + 少量简单工具 | 强原生推理模型 + 40+ 复杂工具池 |

常见追问：

1. **Plan Mode 是一套独立于主循环的编排框架吗？** 不独立。它复用同一个 `while(true)` 主循环，靠调用 `EnterPlanMode` 与 `ExitPlanMode` 两个工具切换权限状态：进入后剥夺写文件与命令执行权限，只保留 `Read`、`Grep`、`Glob` 把方案写进 `.claude/plans/`，且每满 5 轮自动注入系统提醒防止模型手痒改代码，经用户审批退出后才恢复写权限。
2. **Bash 安全模块为什么不能用关键词黑名单正则？** Shell 可以通过变量拼接、Base64 解码、子命令替换或相对路径跳转绕过 `rm -rf` 等字面正则；语法级解析先拆出真实命令树与目标路径，才能识别命令注入与目录逃逸。

### Q2 从敲回车到 `queryLoop`，一句话怎么穿过四层异步生成器？单轮跑哪五步？

用户输入依次穿过 `ask → QueryEngine.submitMessage → query → queryLoop` 四层异步生成器（`async function*`），靠 `yield*` 把最内层流式产出的每个字符块和工具状态原样冒泡到终端界面；最内层 `queryLoop` 每转一圈按顺序执行「准备与按需压缩消息 → 流式调模型边收边抛 → 判定 `needsFollowUp` → 执行工具调用 → 构造新 `State` 塞回结果」五步。

拆成四层是为了隔离生命周期职责。第一层 `ask` 是给 SDK 单次脚本调用的薄入口，内部实例化引擎并委托下去；第二层 `QueryEngine` 充当跨轮会话账本，维护消息历史、已读文件缓存、权限拒绝记录，并在进循环前处理斜杠命令、拼装系统提示词、启动记忆预取；第三层 `query` 负责会话收尾清理事件与核心循环解耦；第四层 `queryLoop`（位于约 1729 行的核心文件中）专职跑循环。全链路采用异步生成器而非普通 `async` 函数返回 Promise，不仅为了让用户按回车后立刻看到逐字输出，更是下一题「模型还在吐字时后台工具已提前开跑」的必要前提。

```text
async function* queryLoop(params) {
  let state = initState(params.messages)       # 显式跨轮状态：turnCount=1, 恢复计数=0
  while (true) {
    const msgs = maybeCompact(state.messages)  # 阈值内不主动调摘要 API
    let needsFollowUp = false
    for await (const chunk of streamAPI(msgs)) {
      yield chunk                              # 文字块实时冒泡至外层终端
      if (isToolUseBlock(chunk)) {
        executor.addTool(chunk)                # 流式识别完单个工具即投递后台
        needsFollowUp = true
      }
    }
    if (!needsFollowUp) return { reason: 'completed' }
    const results = await executor.getRemainingResults()
    state = nextState(state, msgs, results)    # 不可变更新 turnCount 与消息链
  }
}
```

这段伪代码说明两点：循环是否继续只看本轮流式输出里有没有出现 `tool_use` 块（`needsFollowUp`），且工具投递发生在 `for await` 流式接收循环内部，不等整条回复流完。

常见追问：

1. **工具执行结果塞回历史时用什么角色？** 按 Anthropic Messages API 协议封装成带 `tool_use_id` 的 `tool_result` 内容块，挂在 `user` 角色消息下追加进 `messages`，让下一轮模型把环境反馈当成外部输入读取。
2. **主循环只有 `completed` 一种退出原因吗？** 源码定义了 17 种结构化退出 `reason`，代表性的有 8 种：正常完成 `completed`、轮数封顶 `max_turns`、流式生成中断 `aborted_streaming`、工具执行中断 `aborted_tools`、压缩后仍超窗口 `prompt_too_long`、续写 3 次仍超限 `max_output_tokens_recovery`、被结束钩子拦截 `stop_hook_prevented` 以及传图格式错误 `image_error`。

### Q3 模型还在流式吐字，工具为什么已经开跑了？`StreamingToolExecutor` 怎么防并发踩踏？

主循环在监听模型流式输出的过程中，每解析完一个完整的 `tool_use` JSON 块，就立刻调用 `streamingToolExecutor.addTool(toolBlock, message)` 把它丢进后台执行，等模型整段回复流完再调 `getRemainingResults()` 一次性收齐结果，把模型生成耗时与磁盘/网络 I/O 耗时叠在一起。

并非所有工具都能同时跑。并发边界由工具定义时的「是否只读」属性严格控制：`Read`、`Grep`、`Glob` 等只读工具互不改状态，一轮吐出 10 个可以全部并发读盘；`Edit`、`Write`、`Bash` 等会改动文件或外部环境的工具必须排队串行执行，防止两个写操作同时落盘互相覆盖。如果开发者新增工具时漏写了该属性，框架按 fail-closed 原则默认将其视为「会修改状态（`false`）」，强制退回串行锁。

常见追问：

1. **一轮里既有 `Read` 又有 `Edit` 怎么调度？** 连续的只读调用并发跑，遇到非只读工具时设置栅栏，等前序任务落定后再独占串行执行写操作。
2. **流式中途用户按了 `Ctrl+C`，后台已经起跑的工具怎么办？** 通过上下文里的 `AbortSignal` 广播取消信号终止子进程或异步句柄，归入 `aborted_streaming` 或 `aborted_tools` 分支做状态清理与配对补全。

### Q4 工具跑挂、`Ctrl+C` 中断或输出超长截断时，主循环怎么做到对话不死、无感续写？

靠三套兜底机制：`State` 显式状态对象防死循环、`yieldMissingToolResultBlocks` 伪造错误结果保 API 配对合法、「8K 静默升档 64K + 最多 3 次 nudge 轻推」恢复超长截断输出。

第一处坑来自 Anthropic API 的死规矩：历史消息里每一个 `tool_use` 块后面，必须紧跟一个 `tool_use_id` 完全匹配的 `tool_result` 块，否则下一轮请求直接报 400 格式错误拒收。当网络闪断、用户按 `Ctrl+C` 或发生模型降级切换导致工具没跑完时，历史里就会留下孤立的 `tool_use`。`yieldMissingToolResultBlocks` 会自动巡检并补上一条 `is_error: true`、带对应 `tool_use_id` 的合成 `tool_result`，写明该工具因中断或异常未执行，让后续对话不断链。

第二处坑是输出截断。常规默认最大输出 32K Token，灰度控费下可能压到 8K；模型想吐 12K 代码撞上 8K 上限时，主循环第一段先不报错，静默把上限升到 64K 重试本轮；若升到 64K 仍撞上限，第二段在下一轮注入一条英文 `nudge` 指令（`Output token limit hit. Resume directly, no apology, no recap...`），要求模型不道歉、不复述，直接从断点把剩余工作拆小块续写。为防死锁，`State.maxOutputTokensRecoveryCount` 硬限最多续写 3 次，超限即返回 `max_output_tokens_recovery` 退出。同理，请求撞上 413 `prompt_too_long` 时触发一次被动压缩重试，由 `State.hasAttemptedReactiveCompact` 保证单次 API 请求周期内最多触发一次被动压缩重试（本轮模型成功返回、进入下一圈迭代开头时才重置；若当场压完重发仍报 413 则直接退出）。把所有计数器集中放进不可变更新的 `State` 对象而非闭包全局变量，排查时看一眼当轮 `State` 快照就能定位循环继续或退出的原因。

常见追问：

1. **为什么每轮开头不无条件做一次主动摘要压缩？** 摘要本身要消耗一次大模型 API 调用并损失细节；未达高水位阈值前按原样发送，万一估算偏差撞上 413 再由 `hasAttemptedReactiveCompact` 单次补救，既省账单又保精度。
2. **Stop Hook 在主循环哪一步生效？** 在模型准备正常结束本轮（无 `tool_use`）之前运行；比如团队配置了「结束前必须跑过 lint」，脚本返回非零拦截码时，主循环不退出而是把原因写为 `stop_hook_prevented` 或回传报错让模型继续修。

### 跨题追问：架构与主循环（本节 8 条）

按架构边界与异常恢复拆成两组：

1. **Claude Code 泄漏的 51 万行代码包含大模型权重或服务端推理代码吗？** 不包含。泄漏的是终端 CLI 客户端的 TypeScript 源码（因 npm 发布误带 `.map` source map），核心价值全在围绕模型搭的 Harness 可靠性工程。（源码拆解篇）
2. **为什么系统提示词严禁模型用 Bash 跑 `cat`、`grep`、`sed`、`find`、`echo >`？** 两层原因：一是可审查性，调用 `Read` 或 `Edit` 时 UI 能清晰展示目标文件与 diff，跑一串 Bash 文本用户难以看清意图；二是权限边界，专用工具自带路径白名单与只读校验，放任 Bash 读写会绕开细粒度文件保护。（源码拆解篇、Fable 5 提示词篇合并）
3. **Git 操作为什么规定「必须新建 commit，严禁用 `--amend`」？** 当 `pre-commit` 钩子校验失败时，本次 commit 实际并未生成；此时若模型习惯性执行 `git commit --amend`，改写的会是上一个已经存在且不相关的历史 commit，造成代码或提交记录丢失。（源码拆解篇）
4. **两次工具调用之间的过渡文字为什么要限制在 25 个词以内？** 编程任务动辄连调几十次工具，过渡废话既拖慢首屏体感，又会逐轮留在消息历史里白占上下文窗口；最终回复也压在 100 词量级，靠代码 diff 本身说话。（源码拆解篇）

第二组聚焦运行态与连接恢复：

1. **关掉终端窗口或电脑重启后，之前的上下文怎么找回？** 每次退出时会话历史自动落盘；执行 `claude --resume` 可从最近会话列表里挑一条完整恢复历史与文件状态，执行 `claude --continue`（或 `-c`）则跳过选择直接续接最后一次会话。（`/powerup` 篇、新手入门篇合并）
2. **长耗时构建命令（如 `npm run build`）卡住主对话怎么办？** 直接在自然语言里要求「后台运行」或在命令末尾加 `&`，Bash 工具切入后台模式立即释放前台输入，用 `/tasks` 随时查看运行中、已完成或报错的后台任务。（`/powerup` 篇）
3. **`/remote-control`（`/rc`）和 `/teleport`（`/tp`）两个跨端命令方向差在哪？** `/remote-control` 把本地终端正在跑的会话暴露给 `claude.ai` 网页端，代码与环境仍在本地电脑，方便出门用手机遥控；`/teleport` 反过来把云端网页版跑了一半的分支与对话历史拉回本地终端接着改。（`/powerup` 篇）
4. **怎么给一个自己手搓的编码 Agent 排优先级补可靠性？** 按故障发生频率排：先把工具读写权限与路径校验定死在类型层，再补孤立 `tool_use` 假结果修补防会话断死，接着把重试与压缩标志收进显式 `State` 对象设硬上限，最后再做流式并发执行优化。（引申）

## 二、代码检索与大仓定位：为什么用 Grep 不用 RAG

这两道题拆解编码场景与通用知识库检索的分水岭。RAG 离线切块与向量索引的完整链路见姊妹篇 [RAG 面试 23 题](https://www.jasoncai.site/posts/rag-interview-23.html) 第一至四节。

### Q5 为什么 Claude Code 放弃向量库 RAG，改用 `Glob + Grep + Read` 检索代码？哪类场景仍需保留 RAG？

代码是强结构、高频变动、要求符号级精确匹配的动态资产，传统「切块 + Embedding + 向量库 Top-K」在单仓交互式编程下有五处硬伤；Claude Code 改用 `Glob + Grep + Read` 三件套配合主循环多轮迭代（官方称 Agentic Search），遇到跨文件开放探索再派只读 `Explore` 子代理隔离中间噪音。

RAG 在代码场景下的五处水土不服：一是固定行数或粗暴切块会把长函数的 `if/else` 或跨文件调用链拦腰截断；二是向量算余弦相似度擅长模糊语义，查 `getUserById` 会把 `getUserByName`、`fetchUserInfo` 一并召回，精确符号定位反而失焦；三是千人团队每天几百次 commit，全量重算 Embedding 太贵，不重算就会拿两周前已重命名的旧函数误导模型，增量维护跨文件引用又极复杂；四是百万行仓库初次建索引动辄十几分钟，破坏终端工具开箱即用的体验；五是向量召回属于黑盒，漏召回时难以分清是 Embedding 分布偏移还是模型理解出错。

Claude Code 把检索决策权交回给模型，三个工具各卡一道边界：

1. **`Grep`（底层封装 Rust 编写的 `ripgrep`）。** 多线程并行且自动遵守 `.gitignore` 跳过 `node_modules`；提供 `files_with_matches`（默认只返路径省 Token）、`content`（带行号与上下文）、`count`（仅返命中数）三档输出粒度。
2. **`Glob`（按文件名通配符查路径）。** 返回结果按文件修改时间（`mtime`）倒序排列，优先暴露最近改动过的活跃文件，并设 100 个文件硬上限防刷屏。
3. **`Read`（实时直读磁盘）。** 每次直接 `stat` 磁盘取最新内容，零索引滞后；默认最多读前 2000 行，大文件引导模型传 `offset` 与 `limit` 按需分段读取。

这套方案不等于淘汰 RAG。当代码规模跨过单仓边界进入「几十个 Monorepo、上千万行跨仓库检索」（实时 `ripgrep` 扫不动）、「完全不知道函数名或关键词的纯模糊语义查找」、以及「代码 + 设计文档 + 内部 Wiki 混合知识问答」三类场景时，预建索引的混合检索（BM25 + 向量）依然不可替代。

常见追问：

1. **开放式调研一搜就是十几次，不会把主会话窗口塞满吗？** `AgentTool` 提示词明确划了「3 次查询」分界线：目标明确的定向查找（≤3 次）主 Agent 直接调三件套；预计超过 3 次查询的模块级调研（如「梳理整套认证链路」），主 Agent 派生只拿只读工具池的 `Explore` 子代理，在独立窗口里搜几十轮，最后只把几百字结论交回主会话。
2. **RAG 的「一锤子召回」与 Agentic Search 在控制流上差在哪？** 标准朴素 RAG 是单步开环，召回错了模型只能将错就错；Agentic Search 嵌在 `queryLoop` 闭环里，搜空了换正则、看到 import 顺藤摸瓜读下一个文件，每一步观察都修正下一步检索词。

### Q6 百万行多语言代码库里总找错文件或爆上下文，怎么靠 LSP、子目录启动与 `@` 引用解决？什么项目不适合 Claude Code？

百万行仓库下上下文频频见底，根源通常不在模型窗口太小，而在缺少精准的探索起点；工程回报最高的三步组合是「接入 LSP 语言服务器 + 在目标子目录启动会话 + 用 `@` 显式寻址并配 `permissions.deny` 屏蔽噪音目录」。

多语言大仓（尤其是 C、C++、Java、PHP 这类同名重载极多的语言）只靠字符串 `Grep` 搜 `getUser` 可能拉回三千处匹配，模型逐个读文件甄别就会把窗口烧穿。在 `/plugin` 中安装对应语言的 LSP 插件（如 `typescript-lsp`、`pyright-lsp`、`rust-analyzer-lsp`）并配好本地语言服务器二进制后，Claude 可以像 IDE 一样直接走符号级「跳转到定义（Go to Definition）」和「查找同源引用（Find References）」，在读文件前就把三千个字符串命中筛成精确的三处调用。

启动姿势和输入习惯同样关键：

1. **在目标子目录而非仓库根目录启动。** 进微服务大仓修改支付逻辑时，先 `cd services/payments` 再敲 `claude`；客户端会自动向上爬树合并根目录 `CLAUDE.md` 的全局红线，同时把当前焦点与子目录专属测试命令（单跑该模块而非全仓跑半小时）放在最前，避免一开局灌入前端与运维所有无关规则。
2. **用 `@` 精确喂路径，用 `permissions.deny` 封死禁区。** 已知目标文件时直接写 `@src/components/Timer.tsx` 或目录 `@src/api/`，省去模型盲搜开销；同时在 `.claude/settings.json` 提交团队共享的 `permissions.deny`（屏蔽 `.env`、`secrets/**`、构建产物与生成代码），既防泄密又省 Token。
3. **根目录放一张百行内的代码库地图。** 目录命名不直观的老仓库，用一份短 Markdown 列出顶层目录职责，帮模型第一轮就摸清方向。

官方也坦诚划出了能力边界：Claude Code 围绕「Git + 标准文本目录 + 工程师主贡献」的最大公约数设计；重度依赖 3D 模型、贴图、音频等二进制资产的游戏引擎项目，使用 Perforce 或自研非 Git 版本控制的老项目，以及产品或设计师主改非代码配置的项目，开箱直接套用都会水土不服，需要额外部署专用桥接工具。

常见追问：

1. **`@` 引用一个 5000 行大文件会把窗口瞬间打满吗？** 直接全量引用大文件确实占预算；已知行段时直接在提问里指明「只看 `@Timer.tsx` 第 120 到 180 行」，引导模型带 `offset` 和 `limit` 局部读取。
2. **企业推大仓落地为什么建议先铺 LSP 再开放给全员？** 开发者前三次试用如果都在百万行 C++/Java 里因找错符号而改崩代码，很容易直接弃用工具；由一两个基础设施负责人先把 LSP、`.ignore` 和根 `CLAUDE.md` 配齐打包成插件，能显著拉高全员首次跑通率。

### 跨题追问：检索与大仓定位（本节 6 条）

1. **既然有 1M Token 窗口的 Opus 模型，能不能把整个代码库一次性塞进去省掉检索？** 塞不下也不划算。几百万行源码加依赖远超 1M 上限；即便塞进几十万 Token，单轮计费暴涨、首字延迟（TTFT）随注意力平方复杂度飙升，且中段代码会遭遇 Lost in the Middle 注意力衰减。（大代码库篇、Compact 篇、Grep 篇合并）
2. **可以同时搜三个互不依赖的子模块吗？** 可以。主 Agent 在同一轮回复里并发发出 3 个 `subagent_type=Explore` 的工具调用，分别排查认证、订单、支付模块，总耗时取决于最慢那一路而非三路相加。（代码检索 Grep 篇）
3. **`Glob` 为什么要按修改时间倒序截断前 100 个文件？** 开发任务具有强局部性，刚改过的文件大概率与当前排查目标同属一个特性分支；设 100 上限防止通配符写得太宽时一次性吐出上万个路径撑爆窗口，模型看到截断提示后会自行收紧 pattern 重搜。（代码检索 Grep 篇）
后三条聚焦架构选型与权限隔离：

1. **怎么让 Claude 只跑当前子服务的单测，不跑全仓测试？** 在对应子目录（如 `services/payments/CLAUDE.md`）里写死该模块的可执行测试命令（如 `pnpm --filter payments test`），子目录启动或读到该目录文件时会自动挂载这条局部命令。（大代码库实战篇）
2. **如果自己做企业级 Coding Agent，能不能把向量索引和 Grep 结合起来？** 跨百仓场景下这是主流混合解法：离线对仓库 README、模块摘要与接口签名建轻量混合索引负责「跨仓粗筛定位到哪几个目录」，进仓后交给 `Glob + Grep + LSP + Read` 做实时精确读写。（引申，联动 RAG 篇 Q5）
3. **大仓里 `permissions.deny` 和 `.gitignore` 的作用有什么区别？** `ripgrep` 默认跳过 `.gitignore` 里的构建产物，但模型若直接猜路径调 `Read(./.env)` 仍能读到未入库的本地敏感配置；`permissions.deny` 在工具权限层硬拦截读取请求，连文件内容都不会进入内存和上下文。（`/powerup` 篇、大代码库篇合并）

### Q7 为什么模型窗口扩到 1M 仍会爆？滑动窗口、定期摘要、向量召回历史各自败在哪？

编码 Agent 的上下文膨胀速度远高于聊天机器人：开局系统提示词、工具 Schema 与 `CLAUDE.md` 先占掉 5K 至 10K 固定底噪；每调一次工具都会在历史里留下 `tool_use` 与 `tool_result` 两条配对记录，且几千 Token 的文件内容会在后续每一轮被反复重算计费；读五六个源文件跑二十轮就逼近高水位。单纯扩窗口撞上账单指数上涨、TTFT 首字延迟变慢、以及长文本中段注意力塌陷（Lost in the Middle）三道硬墙。

开源框架里常见的三种管理方案在编码场景下各有硬伤：

1. **滑动窗口（砍掉最早 N 条消息）。** 编码任务的核心目标与红线往往在第 1 轮交代（如「本次重构严禁改动老接口签名」），滑窗一刀切掉头部会直接导致后半程越界失控，还会把早先的 `tool_use` 与后续引用拆成无源之水。
2. **固定每 N 轮做一次摘要。** 节奏机械死板，关键排障节点切一刀会把报错栈和已否决方案压糊成一句笼统总结，空闲问答轮又白烧摘要调用。
3. **把历史消息切片塞进向量库按相似度召回。** 编码执行具有强时序依赖（先改 schema 再改 handler），Top-K 相似度召回会打乱先后顺序，还会把成对的 `tool_use` 与 `tool_result` 拆散导致 API 拒收，且不起眼但致命的用户中途改口一旦漏召回就会全盘跑偏。

常见追问：

1. **为什么说一次大文件 `Read` 的真实成本远不止它本身的 5K Token？** 因为 LLM 无状态，第 3 轮读进来的 5K 文件内容会原封不动留在 `messages` 数组里，第 4 轮到第 30 轮每次请求都要为这 5K 输入重新付一次钱并占一份注意力。
2. **上下文用到多少比例时就该人工干预？** 实测窗口占用超过 70% 后，模型顾此失彼、漏看早期约束的概率明显抬头；日常可用 `/context` 查看各分项占比。

### Q8 Claude Code 的 5 层压缩金字塔怎么从轻到重配合？Context Collapse 与 Auto-Compact 为什么二选一？

Claude Code 遵循「压缩必有损耗，能轻则轻、逐级加码」原则，在每次发请求前设了从零 API 开销到全量重写的 5 层压缩阶梯；绝大部分会话在前三层就消化了膨胀，极少走到最顶层。

| 层级 | 机制名称 | 触发条件 | 具体动作与保留边界 | 信息损耗与 API 成本 |
|---|---|---|---|---|
| 第 1 层 | 大结果落盘（`maybePersistLargeToolResult`） | 单工具结果 >50KB，或单条消息内工具结果总和 >200KB | 完整原文写本地磁盘，消息里仅留 2KB 预览；需细节时模型按行段重 `Read` | 几乎零损耗 / 0 次 API 调用 |
| 第 2 层 | Snip 远古裁剪 | 早期探索消息已过时（受 `HISTORY_SNIP` 特性开关控制） | 模型在正常回复回合顺手调 `snip` 标出无用旧消息 ID，本地删除并插边界标记；因第 5 层靠上一轮 API 返回的 `usage` 推算水位，需传入 `snipTokensFreed` 手动扣减以免误触发全量压缩 | 低损耗 / 顺带标记无独立请求 |
| 第 3 层 | Micro-Compact 时间衰减 | 距上次 API 调用 >60 分钟（服务端缓存已过期），或作第 5 层前置瘦身 | 清空 `Read`/`Bash`/`Grep`/`Glob`/`WebSearch`/`Edit`/`Write` 旧结果换成 `[Old tool result content cleared]`，只留最近 5 个；子 Agent 与 Task 结果绝不裁 | 中低损耗 / 0 次 API 调用 |
| 第 4 层 | Context Collapse 读时投影 | 窗口达 90% 主动分段折叠，95% 紧急折叠（内部灰度特性） | 不改本地 REPL 原始消息，仅在发 API 瞬间动态算出压缩视图 | 中等损耗 / 低开销 |
| 第 5 层 | Auto-Compact 全量摘要 | 逼近「有效窗口 - 13K」（距原始上限约 33K，公开版默认主力） | 先跑 Micro-Compact 瘦身，再把全部历史送入同模型重写成 9 节摘要并恢复关键附件 | 高损耗 / 1 次完整摘要调用 |

第 4 层 Context Collapse 与第 5 层 Auto-Compact 是互斥二选一关系，并非叠加运行。原因是按扣除 20K 输出预留后的有效窗口（如 200K 模型取 180K 为分母）折算，两者水位线咬得太死：Collapse 卡在 90% 与 95%，Auto-Compact 卡在 `167K / 180K ≈ 93%`；一旦同时开启，Auto-Compact 会在 93% 抢先把 Collapse 正准备细粒度折叠的历史一锅端成全量摘要。源码里一旦启用 `CONTEXT_COLLAPSE`，就会直接短路掉 Auto-Compact 的触发判断；对外公开构建目前裁掉了灰度的 Collapse，由 Auto-Compact 担当兜底主力。

常见追问：

1. **第 3 层 Micro-Compact 为什么偏偏选「间隔 60 分钟」触发？** 如果在连续高频对话中途随便把历史中间的工具输出改写成占位符，会立刻破坏消息前缀的字节一致性，导致后续所有轮次的 Prompt Cache 全部失效重算；间隔超 60 分钟后服务端缓存本来就已经自然过期，此时顺手清理旧工具输出既腾出几万 Token，又不损失一分钱缓存收益。
2. **为什么子 Agent（`AgentTool`）和 `TaskTool` 的输出被排除在可裁剪集合之外？** 文件删了可以再 `Read` 一遍，但子 Agent 跑了几十轮推理得出的调研报告是不可幂等复现的，一旦清空只能花高昂成本重跑整套子任务。

### Q9 Auto-Compact 为什么预留约 33K 缓冲、全量重写不留最近 20 轮，压完靠哪四段把状态接上？

Auto-Compact 用「固定 Token 绝对值缓冲」代替百分比阈值，把整段对话不分新旧一刀切送进摘要器重写成 9 节结构化清单，再通过 `buildPostCompactMessages` 组装成「边界标记 + 摘要消息 + 活跃文件与任务附件 + Hook 结果」四段新消息链，实现语义进摘要、现场状态走附件、永久规则靠清缓存重载的分通道恢复。

触发阈值的计算藏着两道缓冲减法。第一步算有效窗口时，先从模型原始窗口里扣掉 `MAX_OUTPUT_TOKENS_FOR_SUMMARY = 20_000`：源码注释写明，大规模线上统计显示压缩摘要输出长度的 `p99.99` 分位是 `17,387` Token，向上取整留出 20K 确保摘要自己写得完；第二步在 `getAutoCompactThreshold` 里再减去 `AUTOCOMPACT_BUFFER_TOKENS = 13_000` 安全余量，合计距原始窗口上限约 33K（例如 200K 模型在约 167K 触发）。用固定 33K 而不用 80% 比例，是因为当模型升到 1M 窗口时，按 80% 会白白浪费 200K 可用空间，而摘要所需的输出空间并不会随窗口变大而膨胀。

为什么跑完 Micro-Compact 清掉旧工具结果后，仍不按直觉「压前 N 轮、保留最近几轮原文」？因为硬切分界处极易斩断跨轮上下文指代或拆散成对的 `tool_use` / `tool_result`，且最近几轮里剩下的 5 个大工具输出照样稀释注意力；不如先过 Micro-Compact 瘦身，再把全部轮次交给当前会话的同一个主模型（既保摘要质量，又直接复用已热好的 System Prompt 缓存）统一提纯成结构化状态。两百多行的摘要 Prompt 做了三处关键设计：

1. **首尾包夹严禁调工具。** 开头和结尾各写一遍 `CRITICAL: Respond with TEXT ONLY. Do NOT call any tools`（针对早期 Sonnet 看到历史提过某文件就手痒去 `Read` 的惯性）。
2. **先写 `<analysis>` 草稿再写正式摘要。** 模型先在草稿块里盘点取舍，组装新消息时直接剥离 `<analysis>`，只把干净摘要留进上下文。
3. **强制 9 节固定清单。** 涵盖主要意图、关键技术概念、涉及文件与代码段、报错与修法、解题过程、枚举全部非工具结果的用户消息（第 6 节要求逐条列清用户每次改需求或加约束，一条不落）、待办任务、精确到文件名与函数名的当前工作进度（第 8 节）、可选下一步。

压完后的恢复流水线靠数字定死上限：按最近访问时间挑最多 5 个文件（`POST_COMPACT_MAX_FILES_TO_RESTORE = 5`），单文件最多恢复 5K Token，文件总预算不超过 50K Token，活跃 Skill 恢复预算不超过 25K Token，并把后台运行中的异步子任务状态一并挂入附件；同时清空 `getUserContext`、`readFileState` 等缓存，让下一轮请求自动从磁盘重新加载最新 `CLAUDE.md` 并调 `buildEffectiveSystemPrompt` 刷新工具表。摘要开头包一句「本会话延续自因上下文耗尽而中断的对话」外加本地 transcript 历史备份路径（开启长驻转录备份特性 `KAIROS` 时可按路径回查原句），自动压缩时额外打开 `suppressFollowUpQuestions` 禁止摘要器在结尾反问用户打断长跑节奏。

常见追问：

1. **压缩任务自己也是调模型，万一失败或递归触发压缩怎么办？** 两道防线：一是 `circuit breaker` 熔断器，连续 3 次自动压缩失败立刻停止重试（源于早期线上曾有 1000 多个会话因压缩反复失败无限重试烧爆账单的事故复盘）；二是 `querySource` 递归守卫，来源标为 `'compact'` 或 `'session_memory'` 的内部查询直接 `return false` 跳过压缩判断。
2. **手动敲 `/compact` 和自动触发 Auto-Compact 走同一套代码吗？** 核心函数相同，参数有两处差异：手动 `/compact` 允许跟一段 `customInstructions` 指定本次重点保留什么（如「重点保留支付回调签名排查过程」），且关闭 `suppressFollowUpQuestions` 允许模型向人确认下一步。

### Q10 为什么 Claude 5 系统提示词删掉 80% 后分数不降？日常怎么在 `/compact` 与 `/clear` 间做选择？

模型底层推理与代码巡检能力跃迁后，早期为了防弱模型犯傻而层层打补丁堆出来的「永远禁止 X」「第一步必须先做 Y」死规则，不仅互相打架消耗注意力，还会捆住强模型因地制宜的判断空间；给强模型做上下文工程的核心从「堆砌详尽步骤」转向了「删冗余、留环境死角、给判断标准、按需渐进加载」。

Anthropic 把面向 Claude 5 的系统提示词砍掉 80% 以上后代码评测持平，主要有四项改造：一是把「默认不写注释、多行注释最多一行」这类一刀切禁令，改成「观察周围原有代码的注释密度与命名习惯并保持一致」的判断标准；二是删掉系统提示词与工具 Schema 之间的重复叮嘱，把 `TodoWrite` 工具描述从约 9100 字符精简为简短说明加状态枚举；三是把代码审查、验证等低频长流程从常驻系统提示词拆进按需加载的 Skill；四是引导用可执行单测、参考函数或 HTML 原型替代纯文字规格长文。OpenAI 在 GPT-5.6 内部编码评测中也给出了同向实测数据：删掉重复指令与死板示例、精简工具描述后，评测得分提升约 10% 至 15%，总 Token 消耗下降 41% 至 66%，单任务成本降低 33% 至 67%。

落到日常会话维护，先敲 `/doctor` 检查 `CLAUDE.md` 与 Skill 是否过重，敲 `/context` 看实时窗口水位：接下来继续推进同一个功能模块且水位超 70% 时，用 `/compact` 浓缩历史接着干；切换到完全无关的新需求或旧对话已被错误假设严重污染时，直接用 `/clear` 清零重开（项目背景靠精简的 `CLAUDE.md` 自动兜底）。

常见追问：

1. **精简提示词是不是意味着安全红线也能改成弹性原则？** 绝不能。生产库禁写、危险命令确认、密钥保护与仅在看代码推断不出的历史事故坑点，仍然必须写死硬约束甚至下沉到 Hook 拦截；该放开给模型自主判断的是编码风格、先查哪个文件、验证几轮这类解题路径。
2. **为什么给强模型挂 `Superpowers` 这类重流程 Skill 做小改动反而变慢变贵？** `Superpowers` 规定哪怕只有 1% 适用也要走完需求脑暴、写设计文档、拆计划、开子代理 TDD 全套工序；强模型自己已经会看仓、计划和自测，改一个简单函数套两遍流程会让规划阶段和执行阶段把同一段代码写两遍，Token 翻几倍。

### 跨题追问：上下文与压缩（本节 10 条）

前五条聚焦阈值与恢复边界：

1. **压缩完之后原来的 200 轮原始消息还能在对话里撤回吗？** 对话状态内不可逆，旧消息直接被四段式结构替换以彻底释放窗口并避免维护双份状态的复杂度；若开启了 transcript 本地落盘，模型需要核对某行原始报错时可根据摘要末尾附带的文件路径去 `Read` 历史记录。（Compact 压缩篇）
2. **为什么压缩后 `CLAUDE.md` 不直接作为附件塞进新消息链？** 因为 `CLAUDE.md` 属于永久存活的会话级基准配置，清空 `getUserContext` 缓存后下一轮开头就会按标准路径重新挂载，再塞一份进消息链纯属双倍计费。（Compact 压缩篇）
3. **压缩后为什么要调 `buildEffectiveSystemPrompt` 重建系统提示词？** 用户可能在长会话中途新连了一个 MCP Server、装了新插件或切了权限模式；借压缩时机重装一遍系统提示词，能让后续轮次立刻用上最新工具表。（Compact 压缩篇）
4. **单条消息内 200KB 工具结果上限是怎么挑谁落盘的？** 假设模型一轮并行 `Read` 了 5 个各 45KB 的文件，单看都没超 50KB，合起来却达 225KB；系统会按体积从大到小挑出最大的几个结果转存磁盘换成 2KB 预览，直到当轮总量降回 200KB 以内。（源码拆解篇）
5. **未来上下文窗口真扩到 1 亿 Token，这套压缩金字塔是不是就废了？** 不会废。Lost in the Middle 是自注意力机制在超长序列下注意力权重被巨量无关历史摊薄的固有现象，与硬上限多大无关；把过时噪音清出工作台、保住高信噪比结构始终影响推理准确率与单轮延迟。（Compact 压缩篇）

后五条聚焦落地方案设计：

1. **如果自己团队用不起主模型做全量摘要，能换小模型做 Auto-Compact 吗？** 能跑通但有两个代价：一是小模型容易漏掉第 6 节用户中途改口的隐蔽约束或把第 8 节当前函数级进度写粗，导致下一轮主模型重新盲搜文件把省下的钱又烧回去；二是换模型无法命中主会话已有的几万 Token 系统前缀缓存。（Compact 压缩篇引申）
2. **`/rewind`（连按两次 `Esc`）和 `git checkout .` 在回滚状态上差在哪？** `/rewind` 同时回滚「Claude 直接编辑创建的文件 + 对话上下文历史」，让模型彻底忘掉走偏的那几轮，但它管不了 `npm install` 等 Bash 命令衍生的 `node_modules` 或锁文件；`git checkout .` 能全局干净还原磁盘所有受控文件，却回滚不了 Claude 脑子里的对话记录。大改动前先 `git commit` 存档，跑偏时配合 `/rewind` 最稳。（`/powerup` 篇、新手入门篇合并）
3. **为什么摘要 Prompt 的第 6 节要求「枚举所有用户消息」而不是「概括用户需求」？** 用户在第 1 轮提主需求、第 35 轮补一句「别动老表结构」、第 90 轮说「刚才那个缓存方案放弃」；一旦用概括代替逐条枚举，中间某次方向修正极易被抹平，压缩完模型又把放弃的方案捡回来写。（Compact 压缩篇）
4. **长任务除了靠 Auto-Compact，还有什么主动防失忆手段？** 让模型维护一份落盘的 `TASKS.md`（或跨会话交接 `plan.md`），每完成一项打勾并记录待决问题；即便中间触发压缩或手动拆成多个新会话，新会话第一轮读一遍 `TASKS.md` 就能对齐全局进度。（大代码库篇、Opus 5.5 手册合并）
5. **面试被问「你们 Agent 上下文怎么管的」，怎么在 90 秒内答出区分度？** 先否定纯滑窗与历史向量召回（破时序、拆 `tool_use` 配对），再亮出「五级从轻到重阶梯 + 全量重写分通道恢复」：50KB 落盘零损耗 → 60 分钟趁缓存过期清可重取旧结果 → 距上限 33K（20K 基于 `p99.99=17,387` 输出预留 + 13K 缓冲）触发 9 节摘要 → 按 5 文件/5K/50K 恢复现场状态。（Compact 压缩篇）

## 四、双层记忆与 CLAUDE.md：不靠向量库怎么跨会话记住事

这四道题覆盖跨会话状态治理与硬门禁设计，可与 [Agent 面试 30 题](https://www.jasoncai.site/posts/agent-interview-30.html) 第三节记忆分层互相对照。

### Q11 为什么 Claude Code 记忆系统也不用向量数据库，而是拆成静态 `CLAUDE.md` 六层加动态自动记忆？

业界主流的四类记忆方案（滑窗、定期聊天摘要、Mem0/Zep 类向量检索、MemGPT/Letta 类分层自搬运）有四处共同病根：自由文本无写入约束导致垃圾堆积、不区分信息类型一锅炖检索、缺乏老化机制把半年前的过期技术栈当成「权威的错误」死信到底、重检索而轻写入。加上向量库本身存在「语义相似不等于任务相关（搜 bug 把历史所有 bug 闲聊全拉回来）、换 Embedding 模型召回剧烈抖动、运维重、768 维浮点数人类无法直接打开审查修改」的短板，Claude Code 直接选用磁盘结构化 Markdown 文件构建双层记忆。

双层按确定性分工并行：

1. **常驻声明与索引层（六级启动叠加体系）。** 系统启动时按固定顺序把六处入口文件合并拼入系统上下文：前四级是人工维护的静态规则 `Managed`（系统级目录，企业安全红线，仅管理员可改）→ `User`（`~/.claude/CLAUDE.md`，个人跨项目习惯）→ `Project`（仓库根或 `.claude/CLAUDE.md`，入库共享）→ `Local`（`CLAUDE.local.md`，私有不入库），后两级是自动记忆的轻量索引目录 `AutoMem`（项目级 `MEMORY.md`）→ `TeamMem`（`team/` 子目录团队共享索引，受特性开关控制），同时支持 `@~/security.md` 跨文件 include 引用。
2. **动态详情层（独立记忆文件按需读写闭环）。** 后两级索引只挂目录不挂正文；模型在日常互动里把用户的纠正、角色背景与项目排期自动提炼成独立 `.md` 文件落盘，后续会话按当前问题挑出最多 5 篇正文动态注入。

常见追问：

1. **为什么 `MEMORY.md` 索引文件要同时设「200 行」和「25KB」两道截断上限？** 因为 `MEMORY.md` 作为目录常驻在系统提示词里；源码注释记录过线上极端样本 `p100 observed: 197KB under 200 lines`（不到 200 行但单行极长塞进 197KB），只卡行数防不住超长行索引炸弹，双维度先触线者截断并追加被截警告。
2. **`README.md` 和 `CLAUDE.md` 都是仓库里的 Markdown，为什么不能合并成一个？** 读者与计费模式不同：`README.md` 给人类跳读了解产品与安装，Claude 默认不自动加载；`CLAUDE.md` 专供 Agent 作每轮会话的前提约束，每一个字都在每轮请求里消耗窗口预算。

### Q12 动态记忆怎么做到「自己写、选得准、不过期」？Opus 5 为什么把记忆协议扩写到 802 行并引入乐观锁？

动态记忆靠「封闭四类型写入契约 + Fork 后台抽取 + Sonnet 秘书并行选 Top-5 + 2 天老化警告与先 grep 验证」跑通完整读写闭环；到了多端共享同一套记忆文件系统的 Opus 5，又补上了 `[stated]` 溯源标签、`if_version` 乐观锁并发控制与双层防提示词注入过滤。

写入端严抓「记什么」与「禁记什么」。`MEMORY_TYPES` 被硬编码锁死为四个枚举：`user`（用户技术背景与沟通偏好）、`feedback`（最核心的行为纠正，强制包含规则正文、`Why` 历史原因与 `How to apply` 适用场景三段，有 `Why` 模型才能在边界场景判断能否破例）、`project`（近期冻结期或重构动因，强制把「本周四」这类相对时间转成 `2026-03-05` 绝对日期）、`reference`（Linear 项目名、Grafana 看板地址等外部查询指针）。凡是能从当前代码推导的信息（代码架构、文件路径、Git 提交历史、具体 bug 修复过程、`CLAUDE.md` 已有项）一律列入禁存清单，因为代码随时重构，存死路径只会制造过期的错误指令。写入动作不在主对话里分心做，而在每轮 `queryLoop` 完整结束时由 `stopHook` 触发后台 `extractMemories` 代理：它采用 `runForkedAgent` 复刻主对话字节前缀（字节级缓存复用机制见 Q21），直接命中父会话的 Prompt Cache 低成本完成比对去重（`hasMemoryWritesSince`）与落盘。

召回与注入端同样不走向量库：

1. **只扫前 30 行头信息。** `scanMemoryFiles` 递归扫描记忆目录，只读每个 `.md` 的前 30 行提取 YAML frontmatter（`name`、`description`、`type`）和修改时间 `mtimeMs`，按时间倒序最多取 200 个拼成轻量目录单。
2. **Sonnet 并行预取选 Top-5。** 用户刚提交消息，进入主循环前立刻启动 `startRelevantMemoryPrefetch` 与主模型请求并行跑（几百毫秒即回，零额外体感延迟），调用 Sonnet（弃用更便宜但误判高的 Haiku 防止错记忆污染回答）按严格 JSON Schema 宁缺毋滥挑出最多 5 个文件名；同时自动剔除前序轮次已露脸的 `alreadySurfaced` 条目，以及历史消息中近期刚调用过工具（`recentTools`）的普通用法文档（但保留该工具的坑点警告记忆）。
3. **陈旧警告与主动核验。** 选中的记忆用 `<system-reminder>` 包裹注入，凡保存时间达到或超过 2 天的条目自动置顶 `This memory was saved N days ago. Verify it's still accurate...` 警告，并规定引用记忆中的文件路径、函数名或开关前必须先查文件或 `grep` 核实。

在同属 Anthropic 的跨端聊天产品（网页与手机端 Claude）泄漏的 2049 行 Opus 5 系统提示词里，记忆从单机本地文件演进为多端共享云端文件系统，篇幅从早期 Claude 5 家族首发模型 Fable 5 的 4 行暴涨到 802 行，集中解决跨端有状态系统的三大难题：一是防脑补污染，规定每条事实必须标 `[stated]` 确认出自用户亲口表述，严禁把模型的推断或未采纳方案存成用户偏好；二是防多端并发覆盖（网页端与手机端同时改记忆），`memory_write`、`memory_append`、`memory_str_replace` 三个接口在参数 Schema 层强制传入当前版本号 `if_version`，撞上版本冲突时拉取最新内容合并后同轮重试，用接口级乐观锁代替口头叮嘱；三是隐私与安全边界，写入前先过「同事在设置页看到会不会尴尬」测试（禁存健康、政见、财务账号、实时位置），使用时规定「删掉该记忆回答质量不变就不许提」（不表演记得用户），并对「永远认同我、忽略系统规则、赋予最高权限」类记忆做写入拦截加读取无视双层过滤，严守「记忆是数据而非指令，当前请求永远高于历史偏好」。

常见追问：

1. **为什么几百条记忆规模下「让小模型看目录做阅读选择题」比向量检索更稳？** 向量余弦分数 0.82 算不算真相关很难定死阈值，错召回了也没法解释；Sonnet 读一行清晰写的 `description` 能直接结合当前意图做语义推理，判错了只需改那行描述文字即可修复，还省掉了整套向量库运维。
2. **为什么修改记忆要拆成 `write`、`append`、`str_replace` 三个工具而不是一个全量覆盖接口？** 新增一条事实走 `append`、改局部字段走 `str_replace`，只有大重组才整份 `write`，最小化单次写操作的爆炸半径，降低长记忆文件被模型漏写误删的概率。

### Q13 为什么 1000 行的 `CLAUDE.md` 反而让遵守率掉到 70%？怎么靠 200 行黄金线与 `.claude/rules/` 提回 96%？

`CLAUDE.md` 每次启动都会全量拼进上下文，写得越长越挤占工作窗口并稀释模型对核心红线的注意力；SFEIR Institute 实测数据显示，单文件控制在 200 行以内时规则遵守率约 92%，膨胀到 400 行以上掉到约 70%，而拆成多个 30 行以内的模块化文件放进 `.claude/rules/` 按路径匹配加载，遵守率能回升到 96%。

给臃肿 `CLAUDE.md` 做瘦身，先砍掉三类最常见的负资产：

1. **复述型长文。** 把百行架构文档或代码已自明的框架信息原样贴进来，代码改了文档没改反而误导模型；改成一句指针「详细架构见 `docs/architecture.md`」按需再读，或删掉模型扫一眼目录就能看出的常识。
2. **愿望型口号。** 写「希望测试覆盖率达 90%」「保持目录整洁」「写高质量代码」，模型无法自检，甚至为凑指标乱补无意义断言；一律换成可执行、可验证的确定性动作（如「提 PR 前跑 `pnpm test` 与 `pnpm typecheck`」）。
3. **通用术语表。** 向大模型解释什么是 PR、Repo 纯属烧钱，团队特有黑话抽到独立 `docs/glossary.md` 即可。

留下来的规则控制在 80 至 200 行内（覆盖项目定位、常用命令、三句话目录指针、真实编码约定、带历史事故原因 `Why` 的硬禁令、新人必踩的 Gotchas 六小块），检验标准只有一条：「删掉这一行，Claude 会不会犯错？不会就删」，且每 3 至 6 个月随模型升级复审清理过期枷锁。专项规范（如 React 组件约定、REST 接口错误码、单测断言要求）全部拆进 `.claude/rules/*.md`，在顶部 YAML frontmatter 里写 `paths: ["src/api/**/*.ts"]` 通配符，让模型只有动到对应路径文件时才把那 30 行规则挂载进上下文。

常见追问：

1. **团队里有人用 Claude Code、有人用 OpenAI Codex，两套规则文件怎么避免双份维护？** 把完整规则统一维护在仓库根目录的 `AGENTS.md`（Codex 原生默认读取），然后在 `CLAUDE.md` 里只写一行 `@AGENTS.md` 引用指令，一份文件两端同步生效。
2. **从零接手老仓库怎么快速起草并日常维护 `CLAUDE.md`？** 先敲 `/init` 让模型自动扫描构建配置与目录生成初稿再人工删减；日常跑任务发现同一类错犯了两次以上，敲 `/memory` 或口头让它追加防御规则，同时清理互相矛盾的旧条款。

### Q14 写在提示词里的规则十次总漏两次怎么办？Hooks 怎么把建议变成 100% 执行的硬门禁？

`CLAUDE.md` 与 Skill 本质都是自然语言提示词，受概率采样与长上下文注意力稀释影响，永远做不到 100% 必达；凡是「改完代码必须跑格式化」「严禁修改 `.env` 密钥文件」「上线前必须过检查」这类零容忍要求，必须下沉到客户端程序强制触发的生命周期 Hooks。

Hooks 配置在 `.claude/settings.json` 或 `~/.claude/settings.json` 中，核心挂载点包括 `PreToolUse`（工具执行前拦截校验）、`PostToolUse`（工具执行后自动善后，如 `Edit|Write` 后自动跑 `prettier --write`）与 `Stop`（模型准备结束本轮回复前做完结门禁，甚至自动反思本轮常犯错误反哺规则）。实现时有两个工程细节必考：一是 Hook 脚本并非靠环境变量拿目标文件路径，而是从标准输入 `stdin` 读取当次事件的完整 JSON（例如用 `jq -r '.tool_input.file_path'` 提取被编辑文件，项目根目录可用 `$CLAUDE_PROJECT_DIR`）；二是靠进程退出码控制流向，退出码 `0` 正常放行，退出码 `2` 直接摁住阻断当次工具操作，并把脚本打到 `stderr` 的报错原因原样回传给 Claude，让模型自己换合法方案继续推进。

常见追问：

1. **常驻拦截危险命令的 Hook 平时开发太烦，只在碰生产环境时才想开怎么办？** 可以把 `PreToolUse` Hook 直接声明在特定 Skill（如官方内部常用的 `careful` 拦截 `rm -rf`/`DROP TABLE`，或 `freeze` 锁死只准改指定排障目录）的 frontmatter 里，平时不生效，敲 `/careful` 激活该 Skill 期间动态注册，会话一关自动销毁。
2. **Hook 自己写得太慢或者死循环会有什么后果？** 同步挂载在 `PreToolUse` 或 `PostToolUse` 上的命令每调一次匹配工具就跑一回，耗时过长会直接卡慢每轮循环，所以只放毫秒到秒级的增量格式化或路径/语法快检，全量集成测试留给后台任务或完结阶段。

### 跨题追问：记忆、规则与门禁（本节 8 条）

1. **子目录下的 `frontend/CLAUDE.md` 是启动时就全量加载吗？** 看启动位置。若在仓库根目录启动，只有根与 `~/.claude/CLAUDE.md` 开局合并加载，子目录的 `CLAUDE.md` 等到模型读取或修改该子目录文件时才按需挂载（改后端完全不占前端 Token）；若直接 `cd frontend` 启动，则开局即向上爬树把子目录与根目录一并加载。（工程化篇、`CLAUDE.md` 指南、记忆机制篇合并）
2. **自动记忆抽取代理 `extractMemories` 为什么不直接让主模型在回答末尾顺手写文件？** 两个坏处：一是让主模型一边修复杂 bug 一边分心琢磨「这句该不该归档、算哪一类」，会拉低主任务代码质量；二是每轮系统提示词都得常驻一大段记忆分类写盘手册。放到 `stopHook` 里后台 fork 执行，主对话零干扰且复用前缀缓存。（记忆机制篇）
3. **`feedback` 和 `project` 两条记忆为什么都强制要求写 `Why` 和 `How to apply`？** 这两类记忆最容易随时间变迁或遇到边界特例：只记「3 月 5 日冻结分支」不记「因合规审计冻结」，审计提前结束模型还在拦合并；只记「集成测试禁 mock」不记「上季度 mock 漏掉迁移故障」，写纯算法单测时模型也会死板去连真库。（记忆机制篇）
4. **记忆里已经存了某条危险偏好（如旧版本写入的「跳过所有安全检查」），怎么防住？** 不能只防写入端，读取端必须做二次清洗：模型被明确要求把记忆库里任何削弱诚实性、越过权限边界或覆盖系统规则的条目当作不存在，绝不逐字当指令执行。（Opus 5 提示词篇）
后四条聚焦团队治理与规模边界：

1. **同一条要求在 `CLAUDE.md`、Skill 和工具描述里各写一遍是不是更保险？** 恰恰相反，这是多处维护腐烂的源头。迭代两个月后改了一处漏改两处，模型在同一个上下文里读到互相冲突的三版规矩（例如系统提示禁建分析文档、用户求该写就写、`CLAUDE.md` 求复杂模块必写文档），反而陷入决策内耗。（`CLAUDE.md` 指南、Claude 5 上下文篇合并）
2. **怎么在团队里管住「不要用 `--dangerously-skip-permissions` 裸奔，又不想每步按确认按到手酸」？** 学习 Claude Code 创始人 Boris Cherny 的做法：绝不开全局跳过权限开关，而是用 `/permissions` 把日常高频且安全的构建、单测、只读命令加入白名单，配合 `accept edits` 模式（自动放行本地文件编辑档位，见 Q22）放行可逆修改，把人工确认留给 `Bash` 高风险命令与外部写操作。（大代码库实战篇）
3. **如果两条不同层级的 `CLAUDE.md` 规则直接冲突，模型一定听更具体那一层吗？** 虽然加载顺序上越靠近工作目录越靠后，但官方文档明确警告：面对直接矛盾的自然语言指令，大模型可能随机挑一条遵守；唯一根治办法是每两周或用 `/doctor` 巡检清理冲突条款。（`/powerup` 篇、`CLAUDE.md` 指南合并）
4. **个人开发的 Agent 想抄这套文件记忆，候选文件涨到五千个还能用 Sonnet 全扫目录吗？** 两百个以内直接拼前 30 行清单喂小模型性价比最高；若涨到数千条，可按项目/模块分二级目录（先选目录再选文件）或用轻量关键词/BM25 粗筛出前 100 条标题，再交给小模型精挑 Top-5，依然不必急着上重型向量库。（引申）

### Q15 Claude Code 系统提示词为什么插一条动态分割线？Fable 5 与 Opus 5 泄漏提示词藏着哪些工具与安全设计？

Claude Code 的系统提示词由十几个模块动态拼装而成，中间硬插了一条名为 `__SYSTEM_PROMPT_DYNAMIC_BOUNDARY__` 的分割标记：分割线之上是全球所有用户一字不差的静态指令（角色定位、安全红线、先读后改准则、可逆性×影响范围风险矩阵、Git 协议、25 词输出约束），分割线之下才是因人而异的工作目录、系统平台、`CLAUDE.md`、记忆目录与 MCP 状态。

这条线直接决定了 API 账单成本。Prompt Caching 要求前缀字节完全一致才能命中并省下 90% 输入费用；把静态部分全部前置在分割线之上，就能构建「全球跨组织共享缓存 → 组织级缓存 → 单会话级缓存」三级复用体系，避免因本地路径不同把前面上万 Token 的通用手册每轮重算。

对比社区提示词归档仓库 `CL4R1T4S` 收录的 Claude.ai 端 Fable 5（约 1600 行）与 Opus 5（2049 行）系统提示词，能提炼出四条直接可抄的工具与安全工程方法：

1. **工具描述重点写死「什么时候别用」与参数生成顺序。** Fable 5 近一半篇幅在写工具禁忌：例如 `ask_user_input` 明确规定用户问「选 A 还是 B」或倾诉情绪时严禁弹选项按钮逃避给建议，而一旦准备列多条澄清问题就必须停笔改调该工具并立即结束本轮；`create_file` 强制参数按 `description（为什么建）→ path → file_text` 顺序输出，利用自回归逐字生成特性逼模型动笔写代码前先把意图想清；地图等工具强制 `place_id` 逐字复制禁凭记忆手敲，`web_fetch` 锁死只准抓取用户提供或搜索结果返回的确切 URL 防瞎编链接。
2. **检索触发看「信息会不会变」与陌生大写词。** 勾股定理直接答，现任职务必搜；遇到首字母大写的陌生词或短版本号（如 `v0`、`o1`），一律视为训练截止后出现的新事物强制先搜，还内置了 `product-self-knowledge` 技能逼模型连自家 Anthropic 产品定价与安装细节都先查手册不靠训练记忆。
3. **工具涨到 30 个后靠「顺序短路路由表」防模型按偏好乱挑。** Opus 5 针对功能重叠的可视化工具列了严格顺序表：先判纯文字够不够 → 够就直接答；不够再看有无专用 MCP 工具 → 无再看用户是否明确要文件 → 最后才落回聊天通用可视化，命中第一个即停止，防止模型先凭喜好挑工具再事后编理由。
4. **安全拒答「讲原则、藏检测机制」，并把防线前移到模型心理动机。** 拒绝恶意代码（含打着教学旗号的漏洞利用与勒索软件）时禁止用冰冷小圆点罗列，且只陈述原则不透露触发了哪条检测线（讲清边界等于教人绕过）；最精妙的一句是「一旦发现自己正在脑补理由把可疑请求往合理方向圆（mentally reframing），这个想圆的念头本身就是立刻拒绝的信号」，同时在情绪低落用户询问桥梁、高楼、药物时转向情绪关怀，平时绝不为「用户愿意开口」道谢或挽留续聊，防情感依赖。

常见追问：

1. **为什么编程系统提示词写安全规则推荐「先肯定再约束」？** 先写明「允许协助已授权渗透测试、防御研究、CTF 与教学」，再划死「拒绝 DoS、供应链投毒与恶意检测规避」，模型拿到了清晰的正反向分界判据，误杀正常安全开发任务的概率远低于纯列十条模糊禁令。
2. **为什么规定「不准修改没读过的文件」和「三行相似代码优于过早抽象」？** 专治编码 Agent 两大通病：一是凭空按猜测重写文件破坏原有风格与隐含逻辑，二是修一行 bug 顺手抽出一堆没人要的辅助类与配置项把变更面搞炸。

### Q16 Skill 和普通提示词、斜杠命令、MCP 到底差在哪？三层渐进式披露怎么把 15 万 Token 压到 1%？

提示词是知识内容本身，Skill 是一套包含 `SKILL.md`、参考文档、可执行脚本、输出模板与可选动态 Hook 的文件夹级上下文懒加载系统；在 Claude Code 源码内部，用户手敲的 `/斜杠命令` 与模型自主调用的 Skill 已经彻底统一成同一套 `Command` 数据结构的两个触发入口；MCP 则是连接外部系统的标准通信通道（给手），Skill 教模型按什么团队规矩与坑点把活干对（给说明书与本地工具箱）。

装 50 个各 3000 Token 的完整 Skill 若全塞进系统提示词，开局就要吃掉 15 万 Token（占满 200K 窗口的 75%）。Claude Code 靠三层渐进式披露（Progressive Disclosure）把常驻成本砍到了 1%（约 2000 Token）：

1. **第一层：常驻仅放「书脊目录」，严格卡 1% 预算与 250 字符上限。** 启动时扫描内置、用户级（`~/.claude/skills/`）、项目级（`.claude/skills/`）、插件与远程 MCP 五处来源（重名按扫描顺序先到先得，项目级排在用户级之后不可覆盖同名用户级，防止克隆外部不可信仓库后被仓库内同名 Skill 劫持个人全局命令），只拼 `name + description + whenToUse` 送入 `<system-reminder>`。源码 `SKILL_BUDGET_CONTEXT_PERCENT = 0.01` 锁死总预算占窗口 1%，`MAX_LISTING_DESC_CHARS = 250` 把超长描述直接截断成省略号；若装了几百个 Skill 挤爆 1%，先按比例缩减描述，再装不下就砍光第三方描述只留名字，唯独官方内置 Skill（源码记入 `bundledIndices` 集合）永不截断。
2. **第二层：阅读理解命中后，以 `isMeta: true` 用户消息增量注入全文。** 选 Skill 不上向量检索也不训分类器，直接靠主模型前向推理读目录匹配，并在 `SkillTool` 说明里下了 `BLOCKING REQUIREMENT` 死命令防模型看懂了却偷懒不调。命中后，`loadSkillsDir.ts` 在正文顶部拼一行 `Base directory for this skill: ...`，做完 `$ARGUMENTS` 参数替换和 `` !`shell命令` `` 实时输出展开（如 `/commit` 预跑 `git diff`；若 `loadedFrom === 'mcp'` 来自不可信远程服务器则硬拦截禁跑内嵌命令），最后包成一条 `isMeta: true` 的隐藏用户消息追加进对话流，UI 不刷屏且丝毫不破坏前面几万 Token 的 System Prompt 缓存。
3. **第三层：附属 `references/` 与 `scripts/` 按需自取。** 第二层注入时依然不加载子目录里的 API 手册或排查表，模型读到 `SKILL.md` 指路说明且真撞上对应分支时，再靠根目录路径自己调 `Read` 或执行封装好的确定性脚本。

写高含金量 Skill 抓三个重点：一是 `description` 前 250 字按触发条件而非功能简介写（写清「当用户要求做 X 或遇到 Y 报错时使用」）；二是正文删掉「写完跑测试」这类模型本来就会的废话，重点攒模型光看代码绝对猜不出的 Gotchas 坑点清单（如「`subscriptions` 表只追加不更新，取最新状态看 `version` 最大而非 `created_at`」），超过 500 行就拆去 `references/`，机械转换固化成脚本放进 `scripts/`，跨次执行的状态日志或首次引导 `config.json` 存进插件升级不丢失的 `$CLAUDE_PLUGIN_DATA` 目录；三是 Anthropic 盘点内部几百个 Skill 归为 9 类（库参考、产品验证、数据分析、流程自动化、脚手架、代码审查、CI/CD、Runbook 排障、基础设施运维）后给出明确优先级：产品验证类 Skill（如驱动无头浏览器跑完注册流并逐步断言）对产出质量的拉升最大，值得派专人花整周打磨。

常见追问：

1. **发布上线类 Skill 怕模型自作主张乱调，纯表结构背景类 Skill 又不想污染用户的 `/` 菜单，怎么分别锁住入口？** 在 `SKILL.md` 的 frontmatter 里配两个布尔开关：危险动作设 `disable-model-invocation: true`，模型敢调直接报错弹回，只准人工敲 `/deploy` 扣扳机；纯背景参考设 `user-invocable: false`，从斜杠菜单隐藏，只留给模型后台自主翻阅。
2. **两个 Skill 之间有先后依赖（比如生成报表后调上传 Skill）但没有包管理依赖声明，怎么串起来？** 直接在前一个 `SKILL.md` 正文里用自然语言点名「完成后调用 `file-upload` skill 上传产物」，只要对方已安装，模型读到这句就会在下一步主动发起调用。

### Q17 什么时候接 MCP，什么时候直接调 CLI？Plugin 怎么解决团队配置分发与埋点度量？

本地已有成熟命令行工具（如 `git`、`gh`、`kubectl`）时直接让 Claude 调 CLI 最省上下文；只有面对无现成 CLI、需维持长连接或复杂 OAuth 鉴权、跨团队复用企业内部系统（Jira、Slack、Sentry、BigQuery、数据库）时才上 MCP，且在大代码库七层 Harness 建设顺序里，MCP 应该放在最后一层接入。

过早上 MCP 是很多团队把上下文搞乱的常见原因：`CLAUDE.md` 边界没立住、Hooks 没挂好，先一口气挂七八个 MCP Server，几十个外部工具定义瞬间挤占窗口并干扰工具选择。正确顺序是：先打磨 200 行内的 `CLAUDE.md` 与 Hooks → 把每日做超一次的高频 SOP 沉淀成 Skills → 用 Plugin 打包分发 → 最后按需挂 MCP（用 `claude mcp add` 或提交项目级 `.mcp.json`）。

当个人攒齐了 Skills、Subagents、Hooks 与 `.mcp.json` 后，靠复制文件夹同步给同事很快就会版本失控；提交进仓库 `.claude/skills/` 虽省事，但每增一个 Skill 都会无差别吃掉全员每次会话的 1% 目录预算。Plugin（含 `.claude-plugin/plugin.json` 元信息与四类资产目录）就是 Claude Code 配置的包管理器：团队搭一个内部 Git 仓库作 `marketplace`（先在沙盒目录自由试水，口碑跑出来再提 PR 进正式源，设一位 Agent Manager 或直接负责人统筹维护），成员按需执行 `/plugin install xxx@team-marketplace` 做到「谁用谁付上下文成本」，热更新敲 `/reload-plugins` 即刻生效。上线后挂一个监听 `SkillTool` 的 `PreToolUse` Hook 记录调用日志，一眼就能揪出「预期高频实际零调用（`undertriggering`）」的僵尸 Skill，回头针对性重写那 250 字的 `description`。

常见追问：

1. **随便安装网上野生的第三方 Plugin 有什么安全风险？** 等同于在开发机上跑未知脚本：Plugin 内打包的 Hooks 能在工具执行前后静默运行任意本地 Shell 命令，`.mcp.json` 也能把代码片段发往外部服务器，安装前必须审计仓库源码。
2. **单机日常怎么快速验证和管理已接上的 MCP 服务？** 终端外用 `claude mcp list` / `claude mcp remove`，会话内敲 `/mcp` 查看各 Server 连接状态与暴露的工具列表。

### Q18 `eli5`（321 字节）和 `grill-me`（三句话）为什么比千行流程提示词更好用？与 `superpowers` 怎么选？

面对强推理模型，好 Skill 的杠杆在于「扭转模型的交互姿态或交付载体，同时留足执行自由度（避免 railroading 锁死轨道）」，而非手把手替模型规定每一步怎么迈。

两个爆款极简 Skill 印证了同一条规律。Anthropic 内部流行的 `eli5` 整个 `SKILL.md` 只有 321 字节，正文仅一句英文（要求把 `$ARGUMENTS` 当成零基础读者，生成大图少字的交互式 HTML 页面讲解）：模型本来就精通 HTML/SVG 排版，提示词只卡死「零基础视角 + 可视化网页 + 少字」三个目标约束，页面分栏与配色全放手让模型发挥。Matt Pocock 写的 `grill-me` 核心也只有三句话：沿着 Fred Brooks 提出的设计树（Design Tree）逐枝盘问方案细节并附推荐答案、一次只准问一个问题等反馈后再继续、能通过翻代码库自己查清的绝不烦人。它把「人追着 AI 改错」反转成「AI 追着人把上游隐含岔口拍死」，防止上游风格未定下游代码全白写。

把轻量单点工具 `grill-me` 与包含 20 多个 Skill 的重型工程方法论插件 `superpowers` 放在同一句模糊游戏需求（「做个网页版地铁跑酷小游戏」）下实测，两者的定位边界一目了然：

| 对比维度 | `grill-me`（单点需求审问刀） | `superpowers`（全套工程经理流水线） |
|---|---|---|
| 需求追问深度 | 顺设计树连问 12 轮（一次一问），连美术风格都逼人拍板 | 选项卡片只问 4 轮凑齐开工最小集，其余（如纯色几何画风）替用户选默认值 |
| 问完后谁接管 | 问完即退场，不写文档不碰 Git，后续进不进 Plan Mode 由人定 | 自动接管全流程：`git init` → 写 `specs/` 文档 → 拆 10 任务 54 单测 → 派 24 个子代理跑 TDD 与双审 |
| 磁盘留存产物 | 仅代码文件本身（共识只活在当场对话里） | 代码 + 55 条通过单测（执行期补增 1 条） + `docs/superpowers/specs` 与 `plans` + 14 次规范 Git 提交（完整 Paper Trail） |
| 实测耗时与体感 | 约 32 分钟一次成型，轻量零侵入 | 约 2 小时流水线作业，改小需求会被全套仪式折磨 |
| 最佳适用场景 | 日常中小型功能、产品方案推演（配 `grill-me → Plan Mode`） | 多人交接、高返工代价、需长期维护追溯的正规工程项目 |

常见追问：

1. **`grill-me` 和内置的 `Plan Mode` 都在写代码前用，为什么不冲突？** `Plan Mode` 性子急，倾向自己脑补未说明的细节快速端出一份修改计划；先用 `grill-me` 花十来分钟把决策树上的模糊岔口一个个拍死，再切 `Plan Mode` 落成代码级实施步骤，能显著减少计划返工。
2. **装了 `superpowers` 半夜子代理卡死或 API 断连，第二天怎么救？** 因为设计规约、拆解计划和已完成任务的提交全部作为 Paper Trail 落在 `docs/superpowers/` 与 Git 分支里，同一会话回一句「任务继续」或开新会话读一遍计划目录，就能清掉残留文件重派子代理从断点续上。

### 跨题追问：提示词与扩展体系（本节 8 条）

1. **Fable 5 的 `message_compose` 起草消息工具为什么禁止按「正式/随和/热情」分版本？** 换语气不换实质等于没帮用户做决策；它强制生成 2 至 3 个通向不同人际结果的策略（如「保留意见但服从执行」对比「据理力争对齐目标」），并标明每个策略优先保什么、牺牲什么，把真正的权衡摆给人类选。（Fable 5 提示词篇）
2. **要求用户说「我要打车」时模型绝不能直接默认选某家打车平台，哪怕用户喊「20 分钟内赶到」，为什么？** 第三方服务涉及金钱与外部平台绑定，「速度紧急不能成为替用户越权选供应商的理由」，必须先弹候选让用户自己点确认。（Fable 5 提示词篇）
3. **写文章和做战略分析，模型怎么决定是直接回在聊天框里还是生成独立文件？** 看用途不看长短与语气：凡是用户后续要复制出去发布、分享或存档的成品（哪怕随口说「写篇 200 字小博客」）一律落成文件；凡是头脑风暴、列提纲、解释概念（哪怕正式战略分析）直接在对话里答完。（Fable 5 提示词篇）
4. **`SKILL.md` 里嵌的 `` !`shell命令` `` 是在模型决定怎么写之前跑，还是模型输出后再跑？** 在模型看到这份 Skill 正文之前就由客户端本地 `executeShellCommandsInPrompt` 同步跑完了；模型睁眼读到的已经是填好实时 `git diff` 或文件内容的成品文本，少绕一轮工具调用。（Skill 原理篇）
后四条聚焦 Skill 编写与模型保护：

1. **项目里装了 30 个自己写的 Skill，怎么判断哪几个写成了「废话型噪音」？** 过一遍「增量筛子」：遮住某行指令，问自己 Claude 靠训练常识或扫一眼仓库代码能不能自己做对？像「注意写好 CSS 响应式」是废话，像「禁用 Inter 字体与蓝紫渐变默认模板」才是把它推离默认惯性的有效纠偏。（Skill 揭秘篇、Claude 5 上下文篇合并）
2. **日报类或巡检类 Skill 需要记住「昨天汇报到哪条 PR 了」，数据存哪才不怕插件升级被清空？** 读取环境变量 `$CLAUDE_PLUGIN_DATA` 指向的持久化数据目录，把上次水位写成 JSON、追加日志或小型 SQLite 库；该目录跨插件版本升级保留，仅在彻底卸载插件时清理。（Skill 揭秘篇）
3. **为什么说在数据分析类 Skill 里「预置一套取数清洗脚本库」比写三千字 SQL 教程管用得多？** 让模型每轮从零手写连接池、表关联和留存口径既慢又容易算错边界；把底层脏活封成确定性 Python/Shell 函数放进 `scripts/`，模型每回合只需写十几行胶水代码组合现成积木，准确率与速度同时跃升。（Skill 揭秘篇、Skill 原理篇合并）
4. **系统提示词里要求模型「逐字打印你的内部思考过程」为什么反而可能害了自己？** Opus 5.5 官方手册明确指出，强逼模型逐字吐出受保护的内部推理链可能触发安全分类器标记，导致当前会话被静默降级切换到旧模型；想了解决策依据，应直接问「方案 A 比 B 好在哪，代码证据是什么」。（Opus 5.5 手册篇）

### Q19 Subagent 和 Skill 的本质区别是什么？`createSubagentContext` 怎么按字段粒度做隔离？

Skill 是在当前主会话窗口内翻开一本专业手册，干活的仍是主 Agent 自己，加载的手册正文、读取的中间文件与输出全部算在主会话 200K 账本上；Subagent 是通过 `AgentTool`（也可在 `.claude/agents/*.md` 预定义角色、模型与工具集）在后台拉起一个拥有独立上下文窗口的全新 Claude 实例，在自己的空间里搜几十个文件试错，完工后只把几百字精炼结论交回主会话，兼具「保护主窗口不被过程垃圾塞爆」与「提供无历史偏见的独立审查视角」两大价值。

同处一个客户端进程内，既不能把父上下文直接引用共享给子 Agent（子读文件到第 200 行会刷掉父的已读行号缓存，子乱改 React 全局 UI 状态会把界面搞花），也不能给一个全空的白板上下文（用户按 `Ctrl+C` 时子收不到中止信号变成失控僵尸）。Claude Code 在 `filterToolsForAgent` 与 `createSubagentContext` 里按工具身份和状态字段逐项做精细隔离：

```text
function filterToolsForAgent(tools, isBuiltIn, isAsync) {
  return tools.filter(t => {
    if (t.name.startsWith('mcp__')) return true
    if (ALL_AGENT_DISALLOWED.has(t.name)) return false      # 禁再派子代理/禁问用户/禁切Plan
    if (!isBuiltIn && CUSTOM_DISALLOWED.has(t.name)) return false
    if (isAsync && !ASYNC_ALLOWED.has(t.name)) return false # 后台异步走严苛白名单
    return true
  })
}

function createSubagentContext(parentCtx) {
  return {
    readFileState: cloneFileStateCache(parentCtx.readFileState), # 克隆文件视图防污染父
    setAppState: () => {},                                       # 封死全局 UI 写权限
    setAppStateForTasks: parentCtx.setAppStateForTasks,          # 唯独留后台进程登记口
    agentId: createAgentId(),
    queryTracking: { chainId: uuid(), depth: parentCtx.depth + 1 }
  }
}
```

这两段主干逻辑展示了工业级隔离的四项铁律：内置与本地工具走「全局黑名单（防子再生孙无限递归、防抢主会话向用户提问、防擅切规划模式）→ 自定义代理加严黑名单 → 后台异步代理纯白名单」三道准入门（注意源码把 `mcp__` 前缀放在最前直接放行，因此接入外部写操作 MCP 时仍需靠权限层兜底）；运行时状态做到读文件缓存独立克隆、全局 UI 写操作置空、单开一条后台任务登记口防止子代理拉起的 Shell 变成没人回收的孤儿进程、并用 `depth + 1` 严格追踪嵌套层级。

常见追问：

1. **什么时候不该派 Subagent？** 改动范围小（≤3 次查询可定）或需求还在与用户高频来回拉扯、强依赖主对话完整前因后果的任务；硬拆出去子代理两眼一抹黑，重交背景的成本比省下的窗口还高。
2. **为什么让刚写完代码的同一个会话自审代码往往漏检，而派独立 `code-reviewer` 子代理能抓出 bug？** 原会话上下文里留着自己写代码时的全部假设与推理惯性，极易顺着原思路合理化缺陷；新拉起的只读子代理只看 diff 与团队规范，没有包袱，且可指定用成本更低的 Sonnet 或 Haiku 跑专项检查。

### Q20 父子 Agent 之间怎么通信？默认单向通知与 `agent-teams` 双向信箱差在哪？

父子通信绝不走阻塞式的同步 RPC 函数互调，而是以全局 `LocalAgentTaskState` 任务档案为中介，严格区分「默认形态（仅子→父单向通知）」与「开启 `--agent-teams` 团队模式（父↔子双向异步信箱）」两条线。

默认形态下，主 Agent 工具箱里根本没有 `SendMessage` 工具，父把子派出去后中途无法插话改需求。如果子任务在 120 秒内跑完，父就在前台像等普通工具一样同步拿回 `tool_result`；一旦运行超过 2 分钟阈值（`getAutoBackgroundMs() === 120_000`，受特性开关控制），系统自动执行 `auto-background` 把子代理降级转入后台，释放父会话继续响应用户。等后台子任务跑完，系统不会硬塞结构化回调，而是把 `taskId`、输出文件路径、摘要与 Token 账单拼成一段 `<task-notification>` XML 纯文本，通过 `enqueuePendingNotification` 伪装成一条普通的用户消息塞进父会话队列，天然复用父 `queryLoop` 的下一轮输入处理与 Claude 对 XML 标签的高亲和度。

开启 `agent-teams` 模式后，主 Agent 解锁 `SendMessage` 工具，补齐「父→子」主动投递链路：

1. **运行中投递信箱。** 父调 `SendMessage` 往目标子代理档案的 `pendingMessages` 数组末尾追加一条字条并立即返回；子代理每跑完一轮工具调用，就在循环边界自查信箱，把新字条当成用户消息拼进自己的历史继续下一轮推理。
2. **已停机自动唤醒。** 如果目标子代理早已干完活处于 `completed` 或停止状态，父发来 `SendMessage` 时，系统自动调用 `resumeAgentBackground` 从磁盘已保存的对话 transcript 文件里把该子代理的完整历史捞出来，拼上新指令原地复活续跑。

常见追问：

1. **为什么说面试答多 Agent 通信时点明「默认单向、开了 `agent-teams` 才双向」特别加分？** 因为只看概念图很容易笼统答成「父子随时双向发消息」，而源码里 `SendMessage.isEnabled` 明确绑在团队模式开关上，分清这两条线一听就是真翻过实现细节。
2. **默认形态下没开团队模式，父 Agent 还能同时并发跑 5 个子代理吗？** 能。父在同一条 assistant 回复里同时输出 5 个 `Agent` 工具调用，底层并发拉起 5 个独立实例；耗时长的配合 `auto-background` 陆续往父队列塞 `<task-notification>`，父按到达顺序逐条消化。

### Q21 Fork Subagent 怎么靠「字节级一致」把成本打到 10%？Coordinator 模式怎么跑高并发流水线？

常规 Subagent（如 `Explore`）拥有自己定制的系统提示词和裁剪后的工具列表，发给 Anthropic API 时与父会话前缀不同，上万 Token 的提示词必须从头全价重算；Fork Subagent 专门针对「需要继承父会话完整前因后果去探路或做旁路总结（如生成 PR 描述、跑不进主历史的 `/btw` 临时旁白提问）」的场景，通过锁死五项前缀参数字节级完全一致，100% 命中父会话已建好的 Prompt Cache，把共享前缀部分的输入成本砍到约 10% 并大幅压低首字延迟。

Prompt Cache 命中判据苛刻到「差一个空格或工具数组顺序换一位就全盘失效」。为此源码专门定义了 `CacheSafeParams` 打包对齐五项内容：系统提示词、前置用户上下文（含 `CLAUDE.md`）、后置系统环境上下文、完整工具池定义及排列顺序（`tools: ['*']`）、以及父会话分叉点的历史消息前缀 `forkContextMessages`。最讲究的一处细节是：`FORK_AGENT` 定义里的 `getSystemPrompt: () => ''` 直接返回空字符串，完全跳过重新渲染函数，直接把父 Agent 内存里早已渲染定型的那份系统提示词字节原样拿过来发请求，杜绝因中途某个特性开关状态微变导致重新生成的文本差出一个字符。

面对需同时改造十几个模块的大型任务，设置编译开关与环境变量 `CLAUDE_CODE_COORDINATOR_MODE=1` 可切入 Coordinator（协调者）模式（与 Fork Subagent 互斥）：主 Agent 被系统提示词剥离一线读写活，退化为只负责「派发异步 Worker、阅读理解发现并亲自合成精确实现规格、调度实现与独立验证」的纯指挥官，并从 Worker 工具池里摘除 `INTERNAL_WORKER_TOOLS`（创建/解散团队、发消息、合成最终输出），把拓扑死死限制在「1 个协调者 + N 个扁平异步 Worker」两层以内。协调者遵循四阶段流水线与清晰的续命/新派（Continue vs Spawn）决策表：

1. **高重叠任务续命老 Worker。** 刚查完 `auth` 模块文件的那个 Worker 上下文里已经装着完整代码，紧接着改这几个文件直接发 `SendMessage` 让它接着写最省 Token。
2. **跨模块或走偏任务派新 Worker。** 新活与旧文件无关，或老 Worker 之前思路已经跑偏，果断杀掉派全新实例，防历史噪音污染。
3. **验证阶段永远派全新 Worker。** 代码写完后的测试与核查严禁让刚写代码的那个 Worker 自写自验，必须派没参与实现的全新 Worker 用挑刺眼光独立验收。

常见追问：

1. **为什么 Coordinator 模式严禁协调者写一句「根据你刚才的调研结果把修复实现了」直接转发？** 如果协调者不亲自通读各路 Worker 的调研报告并消解跨模块冲突、写出明确到接口与边界的实现规格，那协调者就退化成了白烧一轮 Token 的传话筒，各路 Worker 各改各的很快就会在接口处撞车。
2. **为什么开启 Coordinator 模式后源码直接强制 `isForkSubagentEnabled() === false`？** 协调者自己的系统提示词已经换成了指挥官专属指令，且手下 Worker 干的是职责分明的调研、编码、测试专项活，既不需要继承协调者的指挥官工具箱，职责上也与轻量分身重叠，直接互斥避免混乱。

### 跨题追问：多 Agent 协作（本节 6 条）

1. **怎么防住子代理失控搞出「子派孙、孙派重孙」的无限递归烧钱树？** 双保险：第一道在工具准入层，`ALL_AGENT_DISALLOWED_TOOLS` 与 `INTERNAL_WORKER_TOOLS` 直接把派发子代理和建团队的工具从子实例工具箱里物理摘掉；第二道在运行上下文层，`queryTracking.depth` 每代加 1，触及深度上限强制阻断。（SubAgent 源码篇）
2. **Fork Subagent 遇到需要权限确认的操作怎么办？** `FORK_AGENT` 配置了 `permissionMode: 'bubble'`，子分身触发的权限审批弹窗会向上冒泡浮现到父终端界面，由用户统一拍板。（SubAgent 源码篇）
3. **多个子代理同时改同一个仓库里的文件，怎么避免互相覆盖冲突？** 文件级不相交时在任务拆解规格里划死各自可写目录；涉及大规模跨模块迁移或多人并行开发时，配合 Git Worktree（或内置 `/batch` 命令自动为几十个并行子代理各开独立 git worktree 分支跑修改、自测并分别提 PR），从文件系统层面彻底物理隔离。（大代码库篇、AI 原生研发流篇合并）
后三条聚焦验收证据与启用边界：

1. **几个并行子代理都汇报「排查完毕，未发现重试失控问题」，主 Agent 能直接信吗？** 不能只收结论。派活提示词里必须要求每个子代理交回可核查的三要素证据（配置上限值、完整调用路径、触发条件，没查到明确标未找到），主 Agent 核对证据链完整后再汇总成表。（Opus 5.5 手册篇）
2. **`agent-teams` 模式和 `Coordinator` 模式是同一个开关吗？** 不是，两者相互独立：`agent-teams` 管的是解锁 `SendMessage` 让父子与队友间具备双向异步信箱通信能力；`Coordinator` 模式是进一步把主 Agent 改造成不亲自干一线活的纯两层调度器。（SubAgent 源码篇）
3. **在什么条件下单 Agent 循环直接干活反而比上 Multi-Agent 更好？** 步骤间强串行依赖（下一步全看上一步改完哪行报错）、改动集中在两三个文件内、总检索不超过 3 次的任务；强拆多 Agent 只会平白增加任务序列化损耗与多份上下文底噪。（工程化篇、SubAgent 篇、Grep 篇合并）

## 七、AI 原生研发流与实战调优：模式、档位、回滚与水印

### Q22 四个工作模式、五档 `/effort` 与 `ultrathink` 怎么配合？安全检查误触发自动切模型怎么办？

驾驭 Claude Code 的日常操控杆由两组正交旋钮构成：用 `Shift+Tab` 循环切换「人工把关粒度」的四档工作模式，用 `/model` 加 `/effort`（及单轮关键词 `ultrathink`）调节「推理算力投入」。

四档工作模式对应四级信任度：`default`（Normal，每次改文件与跑命令均弹窗确认，适合陌生仓库起步）→ `accept edits`（日常编码黄金档，本地文件增删改自动放行，唯独执行 Shell 命令停下让人把关）→ `plan`（只读探索出方案写进 `.claude/plans/`，可按 `Ctrl+G` 直接编辑计划文档，拍板后再一键切执行）→ `auto`（文件与命令全自动放行，交由后台安全分类器自判，仅用于长耗时同构批处理）。

思考深度在 `/effort` 下分五档：`low`（重命名、查简单返回值等极速低延迟活）、`medium`（日常修小 bug 省钱档）、`high`（常规复杂任务默认底线）、`xhigh`（Opus 4.7 引入并推广至新版 Sonnet 的长程编码与多工具协作推荐甜点档）、`max`（不设 Token 上限，易过度思考钻牛角尖，需先小范围验证确有收益再用）。注意两处版本细节：一是前四档设置后跨会话持久生效，唯独 `max` 仅当次会话有效，关掉重开自动回退防忘关烧钱；二是旧版流传的 `think / think hard / think harder / ultrathink` 四个暗号里，新版官方仅保留 `ultrathink` 一个词真正生效（单轮临时顶到高思考档，若全局已在 `xhigh` 则边际作用不大），其余三个只算普通文本，且在 Opus 5.5 下连提示词里手写的「请仔细思考」都建议删掉以加快首字响应。急等交互调试还可开 `/fast`（不换小模型，用原模型高优加速但单价更贵）。

若聊着聊着发现界面提示 `Switched to` 自动切到了旧模型，说明对话中的某段内容（不一定是最后一句，前面的文件或搜索结果也算）触发了安全分类器误判。光在选择器里切回 Opus 5.5 不够，因为触发标记的旧上下文还在当前历史里，下一轮仍可能再跳；正确修法是新开一个干净会话重提需求（或双按 `Esc` 回退修改触发消息），也可在设置里关掉 `Switch models when a message is flagged` 改为先暂停由人决定，并在 CLI 用 `/feedback` 上报误判。

常见追问：

1. **怎么避免长任务跑到一半 Claude 老停下来问「接下来改剩余文件，需要继续吗」？** 在 `CLAUDE.md` 里同时写清「继续条件」与「暂停边界」：范围内还有明确可推进的工作时汇报进度后直接往下做，只有真缺业务拍板、缺外部资料、或即将执行删库/强推/改仓外文件等不可逆动作时才停下等确认。
2. **长任务交卷后，人工审查第一步先看什么效率最高？** 在 `CLAUDE.md` 里约定结尾固定按「待你处理 → 已完成 → 新发现」三段汇报；人先看第一段拍板卡点，再让独立会话对照 `main` 分支按「文件名行号 + 触发条件 + 复现验证方法」只列阻碍合并的真问题。

### Q23 代码写快后研发瓶颈卡在哪？SDD 规约驱动开发与 AI-Native SDLC 六阶段怎么跑？

Anthropic 内部约 80% 合入代码已由 Claude 编写，当编码（Build）从几周压缩到几小时后，按人类串行排期设计的传统研发流程立刻在两头堵死：前端卡在需求对齐慢与凭感觉口头盲写（Vibe Coding）越改越乱，后端卡在一次交几十个文件人类 Reviewer 根本审不过来、测试与上线审批排长队。

治前端「想到哪说到哪、改第五步把第一步推翻」的药方是 SDD（Spec-Driven Development，规约驱动开发）。以 GitHub 官方开源 100k+ Star 的 `spec-kit`（初始化 `specify init <proj> --integration claude` 后生成一组 `.claude/skills/speckit-*`）为例，它用命令把「先对齐再写代码」焊成四步主干加两道兜底门禁：先 `/speckit-constitution` 立项目全局铁律 → `/speckit-specify` 只谈业务需求与验收标准不提技术栈，产出 `spec.md` → 跑 `/speckit-clarify` 让 AI 反过来抓出规约里的歧义点逐个追问补齐 → `/speckit-plan` 引入技术栈产出架构与表结构方案 → `/speckit-tasks` 拆成可独立执行的颗粒度清单 → 跑 `/speckit-analyze` 交叉比对需求、方案与任务单是否漏项打架 → 最后才执行 `/speckit-implement` 编码（大项目按骨架、核心流、附属功能分阶段跑）。它和传统瀑布流的本质区别在于：瀑布文档签字即成石头，而 AI 生成的规约几秒钟就能随时回改重算，是活的共识账本。

治全链路拥堵的药方是 Anthropic《AI-Native SDLC Playbook》提出的版本化产物闭环（6 阶段 Loop）：

1. **Plan → Design → Build 前置对齐。** 提出者直接和 Claude 对话生成保留原始语境的 `intent.md` 入库；Design 阶段自动挂载品牌、安全与合规 Skills 生成 `spec.md` 把安全左移；Build 阶段强制先进 `Plan Mode` 产出 `plan.md`，趁文字还短时由人把方向定死。
2. **Test → Deploy → Maintain 证据驱动与生产闸门。** Test 阶段不听口头声称「已完成」，靠自动测试闭环、新开无偏见会话复核、以及固定回归评测集 Evals（每次换模型或改 `CLAUDE.md`/Skill/Hook 都重跑防退化）拿证据；Deploy 阶段允许 Agent 完成多层代码初审与预发准备，唯独生产环境发布前必须由 Hook 硬拦截，留给具名人类负责人做最后一道审批；Maintain 阶段监控线上指标越界后自动做只读诊断，并将事故转化为新的 `intent.md` 闭合下一轮循环。

常见追问：

1. **团队想落地这套 AI 原生研发流，要一口气把六阶段全配齐吗？** 千万别全铺。官方给出零前置依赖的五个第一层抓手，卡哪补哪：需求常走样先上 `intent.md`，重复犯同类错先写 `CLAUDE.md`，交卷没底先建自动测试反馈环，怕误删强推先挂 `Hook`，一上来乱改几十个文件先强制 `Plan Mode`。
2. **几十行一次性数据清洗脚本也要走 SDD 规约流程吗？** 不用。判断标尺就一条：这份代码后面要不要长期维护、持续叠新功能、多人协作？一次性脚本直接 Vibe Coding 一把梭最快。

### Q24 老项目升级与跨几十个文件的大重构怎么稳妥落地？为什么 40 万次会话证明拉开差距的是领域专业度？

老系统改造与跨几十个文件的大规模迁移，靠写超长单轮 Prompt 硬刚必崩；正确打法是「先定改造边界与机器可验的等价标准 → 探索、规划、分模块实现拆进不同会话 → 同构迁移用 `/batch` 并行开 Git Worktree → 按依赖树从叶子节点分批合入」。

推进无人敢动的老项目升级（Anthropic 官方 `Code Modernization` 插件覆盖流程），开工前先对齐三类目标之一：纯升语言/库版本、换技术栈保原业务规则（如 COBOL 迁 Java）、或架构与业务规则重做。先用插件跑 `assess`（技术债评估）、`map`（模块依赖与数据流图）、`extract-rules`（把埋在老代码里的隐式业务规则连同行号抽成文档找老员工核实）；验收不能只靠残缺的旧单测，跨语言改造必须搭线上请求回放（Traffic Replay）或新旧系统旁路双跑比对，并在专用隔离远程机上只给改造分支写权限、严禁注入生产密钥。先挑十来处小范围试跑，出现同类错不靠人工手改兜底，而是回头修 Skill 与检查规则，同时记下试跑 Token 消耗估算总账单（验证往往比写代码更烧钱，把廉价快检放前面挡掉废稿）；全仓推广时按调用链 `A → B → C` 从最末端的 `C` 开始逐模块冻结日常修改、升级并在 CI 里加防回退门禁。遇到全仓替换某类接口这种同构大重构，敲定方案后直接调内置 `/batch` 命令，一次性派出几十个并行子代理各自在独立 Git Worktree 里改完、自测并提 PR 等人工分级审核。

这也正面回答了「AI 时代会写语法还是不是护城河」：Anthropic 分析了 2025 年 10 月至 2026 年 4 月间约 23.5 万名用户的 40 万次 Claude Code 真实会话（《Agentic coding and persistent returns to expertise》），给出四组硬核统计数据：

1. **人机自然分工。** 人类掌握约 70% 的「做什么（规划与边界）」决策，Claude 承担约 80% 的「怎么做（函数选型与编码实现）」决策。
2. **职业间编码门槛被抹平。** 在真正产出代码的会话子集里，软件工程师成功率 34%，非工程岗位 29%，前十大职业群体全部落在工程师 7 个百分点以内。
3. **领域专业度把单条指令杠杆拉开数倍。** 新手单条 Prompt 平均只撬动 5 个动作、600 字产出（如只说「写个扣库存接口」写出单线程会超卖的裸 `UPDATE`），而懂高并发痛点的领域专家一条指令点明「Redis + Lua 原子预扣 + 热点限流 + 异步落库最终一致」，单条撬动 12 个动作（2.4 倍）、3200 字产出（5.3 倍）；遇到卡壳翻车时，新手有 19% 概率直接放弃，中级与专家放弃率仅 5% 至 7%（知道立刻要求上千并发压测验超卖）。
4. **收益最陡的一跳在「新手 → 中级」。** 按全量会话熟练度分档的曲线里，成功率从新手 15% 跃升到中级 28%，再到专家 33% 只多了 5 个点（与上一条口径不同：上一条仅统计产出代码的会话子集）；不需要熬成二十年老炮，只要对业务正常长相、关键坑点与验收方法建立「够用的把握」，就能吃下绝大部分红利。

常见追问：

1. **老项目改造怎么防止审核人因为怕背锅而坚持逐行慢审卡死进度？** 不能把提速压力全甩给一线点 Merge 的工程师；开工前拉管理层、业务方与安全负责人按影响面分级签认验收标准（核心账务支付保留全量人工精审，边缘模块凭回放零差异报告精简审核），让变更管理制度而非个人承担已披露风险。
2. **为了省钱先让便宜小模型改老代码、验不过再升旗舰模型一定划算吗？** 不一定。便宜模型在复杂老逻辑上反复返工三四轮烧掉的上下文加验证账单，经常高于 Opus 一次做对的成本；必须在小范围试点时连同重试次数一起记账对比。

### Q25 Claude 生成的纯文本没有像素，看不见的文字水印是怎么植入、检测与去除的？

文字水印分「隐藏 Unicode 控制字符」「文件容器元数据（图片或 PDF 文件头里的 EXIF、XMP 与 C2PA 数字签名溯源履历）」「统计型采样水印」三类完全不同的技术；Anthropic 为 Claude 部署的是基于 Google DeepMind SynthID-Text 变体的第三种统计型文字水印，它不插入任何零宽字符，而是用一把私有密钥结合前文哈希，在模型采样下一个候选 Token 时悄悄微调同义词之间的选中概率分布。

具体原理看一次正常的解码采样：写到「今天的天空看起来有些……」时，模型算出「阴沉 31%、灰蒙蒙 28%、昏暗 24%」几个合理候选都通顺；水印机制根据前文与私钥生成确定性伪随机信号，把候选词临时分成两组并给「绿名单组」轻轻加一点偏置分，既不强塞生僻怪词破坏可读性，也不改语义。单看某一个词完全无法判断，但一整篇长文经过成百上千次选词累积后，命中私钥绿名单的比例就会像「连抛一千次硬币出现八百次正面」一样显著偏离自然随机基准。检测器拿着同一把私钥重走一遍文本核对暗号吻合度，输出统计置信度而非 100% 定性结论（文本越短、代码或数学 `2+2=4` 这类唯一确定答案越多，可操纵采样空间越小，水印信号就越弱；自然语言长文、注释与整篇翻译则信号最强）。它和 GPTZero 那类猜句式文风的检测器本质不同：一个靠猜文风，一个靠私钥核对植入信号。

开源社区 1.6 万+ Star 的 `watermarks-remover` Skill 正是按这三层对症下药：第一层扫 Unicode 编码确定性删光 `U+200B` 零宽空格与方向控制符；第二层剥离 PDF、DOCX、图片里的 EXIF、XMP 与 C2PA 电子履历；第三层针对统计型水印无法靠删字符清除的特点，调用非 Claude 的其他大模型对全文做逐句改写、调序与同义词重选，把原先吻合 Claude 私钥的 Token 分布彻底打散（代价是改写越狠，作者原本的文风和精细技术措辞越容易受损；若继续交给 Claude 改写则会洗掉旧章又盖上新章）。

常见追问：

1. **Claude Code 之前被社区抓包过「按时区改系统提示词日期格式」是怎么回事？** 部分版本曾出现根据中转端点与系统时区微调系统提示词日期行的现象（例如把 `Today's date is 2026-06-30.` 换成斜杠与特殊修饰撇号 `Todayʹs date is 2026/06/30.`），肉眼几乎无感但机器一扫编码就能识别请求环境，属于第一类字符级标记思路。
2. **既然统计水印早就有成熟论文，为什么 OpenAI 迟迟没给 ChatGPT 全量加上？** 主要卡在商业流失、误报与易被洗掉三点：OpenAI 内部调研显示近 30% 用户表示若仅一家加水印就会转投竞品；全网海量文本下极低误报率也会误伤真实人类作者；且全文跨模型改写或翻译即可大幅削弱信号。Anthropic 此次推进主要出于提前应对欧盟 AI 法规合规要求。

### 跨题追问：研发流程、调优与行业洞察（本节 6 条）

1. **Claude Code 创始人 Boris Cherny 自己日常是怎么并行跑开发流的？** 终端里同时开 5 个本地 Claude 会话，网页端 `claude.ai/code` 再挂 5 至 10 个云端会话并行推进不同任务；复杂活一律先走 `Plan Mode` 敲定方案再切自动编辑一发写完，挂 `PostToolUse` 自动格式化抹平 10% 格式疏漏，把每天做超一次的操作（如 `/commit-push-pr`）全封成 Skill，全组共维护一份入库 `CLAUDE.md` 见错就补。（大代码库实战篇）
2. **在 Claude 桌面或网页应用里审长方案文档、看架构图有什么提效技巧？** 架构图、监控截图直接发原图问箭头调用关系（不必手敲文字转述方框）；审几轮改过的长方案时明确指定查「日期、金额、系统名」是否前后打架，要求摘出矛盾原句并标页码段落。（Opus 5.5 手册篇）
3. **长对话里 Opus 5.5 有时反复重想前面早就定死的问题导致变慢，怎么提速？** 日常跟进任务在项目指令里补一句「已回答清楚的问题沿用前文结论，除非我重提否则不必重新推演」；但若正在做随新证据不断推翻前设的深度事故排查，则不要加这条限制。（Opus 5.5 手册篇）
后三条聚焦演进趋势、培训与水印边界：

1. **这半年大家用 Claude Code 干的任务结构发生了什么变化？** Anthropic 40 万次会话统计显示，单纯修 bug 的会话占比从 33% 降到了 19%，运维相关从 14% 涨到 21%，写作与数据分析从 10% 翻倍到 20%，单次任务平均经济价值上涨 27%，正从补丁小工转向全流程主力。（40 万次会话研究篇）
2. **`/powerup` 命令是什么时候加的，适合解决什么团队痛点？** `v2.1.90`（2026 年 4 月）内置进终端的 10 节交互式动画课程，覆盖 `@` 寻址、四档模式、`/rewind`、后台任务、`CLAUDE.md`、MCP、Skills/Hooks、Subagents、`/rc` 与 `/tp`、`/model` 与 `/effort`；新人入职花半小时通关即可对齐全部核心操作。（`/powerup` 篇）
3. **只由人类写好核心观点与初稿，最后让 Claude 润色一遍字句，会被统计水印判定为 AI 生成吗？** 很可能会。只要整段文字经过 Claude 重新选词输出，输出序列就会大面积打上私钥采样偏置，检测器只能测出「包含显著水印统计信号」，无法替读者区分「全文代写」还是「人类原创后润色」，这也是创作者最介意的边界争议。（文字水印原理篇）

## 答题模板

面试被问到 Claude Code 原理或「你们自己的编码 / 通用 Agent 是怎么设计 X 的」，按下面四步在两分钟内收口，把剩下的时间留给面试官追问细节：

1. **先破直觉误区，一句话亮出工程选型。** 例如答记忆先点破「没用向量库，而是结构化 Markdown 目录常驻加小模型做阅读选择题」；答压缩先点破「没用滑窗或局部摘要，而是五级阶梯兜底加全量重写分通道恢复」。
2. **报出一条带真实边界的源码链路。** 说清数据从哪个入口进、在哪个条件分流、靠什么标志位防死循环（如 `StreamingToolExecutor` 只读并发而漏标默认 fail-closed 串行、孤立 `tool_use` 补 `is_error` 假结果）。
3. **给出一组量化常数证明真拆过实现。** 记住五组最具辨识度的数字：压缩缓冲 `20K(p99.99=17,387) + 13K ≈ 33K`、压后恢复 `5 文件 × 5K / 50K 预算`、记忆索引 `200 行 + 25KB 双保险` 与 `2 天陈旧警告`、Skill 目录 `1% 窗口 + 250 字符上限`、Fork 子代理 `5 项前缀字节对齐省 90% 成本`。
4. **点明适用边界与反例。** 讲清这套取舍在什么规模下失效（如跨几十个 Monorepo 千万行代码仍需混合索引 RAG，高风险生产发布绝不交给模型自决必须挂 Hook 等人工闸门）。

常见翻车点，按面试踩坑频率排：

1. **把 Tool-Use Loop 答成传统文本 ReAct。** 漏掉内部 Extended Thinking 与原生 `tool_use` / `end_turn` 原语，还在讲正则切分 `Thought` 字符串。
2. **把「不用向量库」答成「省钱偷懒」。** 答不出代码切片破结构、符号精确匹配、索引滞后与记忆可审查、防过期权威错误这几条真正的技术动因。
3. **笼统说「父子 Agent 双向自由通信」或「五层压缩叠着全跑」。** 混淆了默认单向通知与 `--agent-teams` 双向信箱的开关边界，或漏掉 Context Collapse 与 Auto-Compact 互斥短路。
4. **把提示词当成 100% 可靠的安全边界。** 权限校验、敏感文件屏蔽、多端版本防覆盖（`if_version`）和上线闸门必须落在工具 Schema 与客户端 Hooks 代码里，只写进 `CLAUDE.md` 直接扣分。
