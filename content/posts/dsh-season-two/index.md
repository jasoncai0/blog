> 源码版本：DeepSeek Harness `0.2.2-rc.1`，commit `fcc0ad46`（工作区 `harness-research/deepseek-harness/`）。正文行号以该 commit 为准。
> 第二季第 0 篇，导览。第一季从这里开始：[《一个 Agent Harness 的解剖》](/posts/dsh-architecture-anatomy.html)。

第一季写完 21 篇，主线是清楚的：一条用户输入怎么变成日志，日志怎么变成请求，请求怎么变成工具调用，工具结果怎么回到下一轮。读完那一季，你能解释 DSH 为什么把 `turn` 和 `step` 分开，为什么工具失败要写成 `tool/result` 而不是抛异常，为什么压缩要用位置替换。

但那条主线两侧还有东西没讲。模型适配器怎么接进来，浏览器里的对话界面怎么把事件画成消息，`bash` 到底跑在哪个进程里，MCP 服务器掉线时模型看到什么，Skill 的文件怎么变成提示词，斜杠命令为什么不经过模型，进程启动时 370 个包按什么顺序装配。这些不是边角料，它们是让主线能跑起来的环境。

{{< fig "diagrams/01-map.svg" "第一季的主干与第二季八块的位置关系。底部三张全图分别落在旅程、状态与扩展点，不在主干上。" >}}

第二季做两件事：补齐八块模块，再画三张全局图。八块各自独立成篇；三张图把整套系统当一个整体看，回答三个问题：一次请求的完整路径是什么，状态归谁所有，想加一个功能应该挂在哪里。

## 0. 结论

第一季的结论是「Agent 是围绕模型的一圈记账与边界」。第二季补的是这圈边界的外侧：模型从哪来，界面在哪，进程在哪跑，外部能力怎么接，启动时谁装配了谁。

三张全局图分别对应对边界的三种问法：

- 请求旅程：一次按键到第一个 token，中间经过哪些进程、协议与日志点。
- 状态所有权：会话日志、投影、进程内激活状态、UI store，各由谁写、谁读、失效时谁负责。
- 扩展点地图：想加模型、加工具、加界面、加协议，分别该挂哪个 seam，哪些改动会破坏可重放性。

## 1. 第一季留下了什么

第一季 21 篇可以按五层归类，第二季不重复这些内容，只在下游引用。

| 层 | 篇目 | 回答的问题 |
| --- | --- | --- |
| 总览 | 01 解剖 | 370 个包怎么组成一个产品，为什么没有内核 |
| 记账 | 02 事件日志、06 状态机、08 失败恢复 | 什么算事实，失败怎么留下记录，崩溃后谁来收尾 |
| 输入 | 03 收件箱、04 取消与 steering、05 人在环里 | 消息排在哪，取消传到哪，审批卡在哪个阶段 |
| 执行 | 07 请求组装、09 注册表、10 流水线、11 边界、12 结果 | 模型看到什么，工具怎么被调用，结果怎么被裁剪 |
| 委派与记忆 | 13 子代理、14 控制、15 team、16 外层机制、17 记忆、18 注入、19 压缩、20 召回 | 谁来做，做过的事怎么留下来 |

这张表本身也暴露了缺口。模型、界面、进程、外部协议、启动过程都不在表里，因为第一季把它们当成了「已经存在的环境」。第二季把这五个词拆开。

## 2. 第二季补哪八块

八块的选择标准是：它们各自有一组独立的包、独立的失败模式，而且都能被单独替换。

| 模块 | 篇目 | 核心问题 | 为什么值得单独一篇 |
| --- | --- | --- | --- |
| 模型层 | S2-2 | 适配器怎么接，路由在哪定，帧怎么流，token 怎么算 | 换模型是产品级改动，不只是换个 URL |
| 客户端 | S2-3 | 60 个 `ui-*` 包怎么拼出一个对话界面 | 客户端拿到的是事件，自己拼消息就会与日志分叉 |
| 执行环境 | S2-4 | `fs`、`shell`、`terminal`、`sandbox` 四个 seam 怎么分工 | 远端沙箱一换，工具、终端、LSP 要一起搬 |
| MCP | S2-5 | 外部服务器怎么变成模型可见的工具 | 连接是长生命周期的，工具列表会变 |
| Skill | S2-6 | 程序性记忆怎么加载、怎么渐进披露 | 它是提示词的一种来源，不是工具 |
| 交互面 | S2-7 | 命令、plan、todo、提问怎么与循环配合 | 这些交互不走模型，却要影响模型的下一步 |
| 宿主组装 | S2-8 | 进程启动时谁装配谁，patch 怎么覆盖 | 一切皆插件的前提是有一个可预测的装配顺序 |
| 嵌入协议 | S2-9 | SDK、ACP、gateway 三种嵌入的边界 | 同一套事件要过线，序列化边界就是契约边界 |

八篇之外还有第 10 篇，它不讲新模块，只画全局图：状态所有权、扩展点决策树、失败分类。三张图放在同一篇里，因为它们回答的是同一类问题：这套系统的边界画在哪。

## 3. 三张全局图

三张图分别在第 1 篇与第 10 篇。这一篇另给一张时间尺度图，先把八块的生效位置摆开。

请求旅程回答「延迟花在哪」。从浏览器按键开始，到 WebSocket 上的 RPC、会话控制器、`agent.followup()`、`turn/step`、`assemble`、provider 流、`session.event` 推送、客户端渲染，每一段都能指出是本地计算、等网络还是等模型。它也解释了为什么取消能从 UI 一路传到 provider 的 `AbortSignal`，以及断线重连后客户端靠什么补齐状态。

状态所有权回答「谁能改什么」。会话日志只追加，投影是纯函数，进程内的激活状态（`armed`、`AbortController`、`pending` 队列）不参与回放，UI store 只是视图。把这四类状态混在一起，就会出现「刷新后审批记录消失」「重启后目标自己跑起来」这类问题。

扩展点地图回答「加功能挂哪」。第一季 01 给过一张归属表，第 10 篇把它升级成决策树：先判断要不要持久化，再判断是不是模型可见，最后判断属于哪个 seam。走完三步，大多数「要不要改 loop」的问题会自己消失。

{{< fig "diagrams/03-time-axes.svg" "五个时间尺度上的机制分布。越往右越频繁，越往上影响面越大；空格代表该尺度上不参与。" >}}

读这张图的一个用处是排除错位的方案：把「压缩」当成降低单次调用延迟的手段，就是把最右列的工具放进了第三列的问题。

## 5. 读之前需要知道的三件事

**术语按第一季的用法。** turn 是一次对已接纳输入的排空，step 是一次模型请求加它引发的工具，attempt 是同一步内的一次提供方调用。日志指 `SessionEvent` 的只追加序列，surface 指日志折叠出的消息面，投影指从事件到消息的纯函数。

**行号会漂。** 所有行号以 `fcc0ad46` 为准。第二季的篇目里，凡是靠类型定义就能说清的地方，优先引类型而不是行号；凡是必须指实现的，给出文件与函数名，行号只作辅助。

**图里的数字是实测。** 370 个包、53 个 group、459,846 行 `src/*.ts`、14 个持久事件、31 个 `tool-*` 包、60 个 `ui-*` 包，都是在这个 commit 上数出来的。第二季新增的模块会给出各自的包数，口径相同。

## 6. 设计取舍

八块按模块边界切，不按包清单切。按包写会得到 370 节，读者记不住；按模块写，每块能独立回答「它为什么存在、坏了会怎样」。

先写旅程再写模块。没有 S2-1 的坐标系，后面每一篇都会变成局部细节的堆叠；有了它，读者知道某个机制挂在哪一段。

地图放最后。S2-10 要引用前九篇的具体例子才不会空泛，所以它不能当导读。

每篇固定四张图。图不是装饰，是迫使作者回答「边界在哪、顺序是什么、失败后回到哪」的检查表。

行号与类型双引用。类型能跨版本存活，行号只能证明「这个 commit 里它在这」。两者都给，读者才能既读得快又验得准。

## 7. 踩坑点

把 S2-10 当成新模块。它不讲新能力，讲的是已有能力之间的所有权与挂载点。

把客户端当成渲染层。客户端持有事件窗口与投影状态，重连、去重、乱序都发生在这一侧。

把 MCP 当成普通 RPC。连接是长生命周期的，工具列表会在会话中途变化，模型看到的 schema 也就有版本。

把 Skill 当成工具。Skill 是提示词与文件的加载方式，不产生 `tool/call`，也不能被审批拦截。

把宿主组装当成启动脚本。装配顺序决定谁能看见谁，patch 的覆盖顺序决定最终配置，这两件事都在进程启动之前完成。

## 8. 写作与证据约定

每篇的结构一致：先给机制，再给源码，再给「不这样会出什么事」。固定的三节是设计取舍、踩坑点、源码索引。取舍一节写清选了什么、放弃什么、什么场景该反悔；踩坑点写的是读源码时容易误判的地方，不是泛泛的最佳实践。

图分四类：架构图说明模块边界，时序图说明调用顺序，状态机说明生命周期，模块图说明包与依赖。每张图都尽量落在一个具体问题上，比如「审批为什么必须在 guards 之前」「压缩的三个入口分别挂在哪个事件」。
