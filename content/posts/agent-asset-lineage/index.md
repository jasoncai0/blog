> 11 月 3 日上午，退款 Agent 的人工通过率从 62% 掉到 55%。模型没换，prompt 没改，Agent 版本也没动。唯一变的是当天凌晨重建的一份退款政策知识库。团队还是花了六个小时才把两件事连起来——不是因为缺监控，而是因为发布单、网关日志和评估报表各自记了这件事的一部分，却没有一个共同的版本坐标。

这不是一个「赶紧上个图数据库」的故事。真正缺的东西很朴素：**每次运行到底用了哪几个版本，以及这些版本之间是什么关系。** 前者是一份运行清单，后者是三张语义不同的图。把这两样做对，再谈遍历和算法。

## 0. 六小时，三个坐标

把时间线摊开，事情并不复杂：

| 时间 | 发生了什么 | 当时留下的记录 |
| --- | --- | --- |
| 11-02 20:00 | `support-refund` 发布 v7 | 发布单写的是 `kb: refund-policy@stable` |
| 11-02 21:04 | 运行 `r-881`，通过率 62% | 网关 span 有 `kb.search`，没有 kb 版本号 |
| 11-03 04:00 | `refund-policy` 重建为 11-02，改了 38 段 | kb 服务自己的变更日志 |
| 11-03 09:12 | 运行 `r-902`，通过率 55% | 评估看板只有总分，没有绑定 kb 版本 |
| 11-03 16:30 | 人工回放 12 条 case，确认根因 | 一张临时拼起来的表格 |

前三份记录都没有错，但分别用了三个坐标：发布单用别名，网关日志用调用名，评估报表用时间窗。**没有任何一份能单独回答：11 月 3 日 9 点这次运行，到底用了哪一版退款政策。**

更麻烦的是，即使把三份记录拼起来，也会得到两种互相矛盾的答案。发布单说依赖 `refund-policy@stable`，听起来像「已经声明了」；但声明的是一个会移动的指针，不是版本。网关说调用了 `kb.search`，听起来像「观测到了」；但没有版本号，观测到的只是一次调用，不是一条可追溯的边。评估说分数从 0.74 掉到 0.71，听起来像「证据」；但两次评估用的数据集和 grader 不是同一版，分数本来就不可比。

这就是为什么我倾向于把 Agent 血缘拆成三张图，而不是一张大图。

## 1. 数据血缘为什么不够

数据血缘那一套已经很成熟：dbt、OpenLineage、DataHub 从 SQL 和任务定义里解析出表、字段、作业之间的依赖，告诉你「这张表变了，下游哪几张报表会坏」。它的前提是：依赖写在 SQL 里，执行是确定性的，失败通常会报错。

Agent 资产不满足这三条。

| 维度 | 数据血缘 | Agent 血缘 |
| --- | --- | --- |
| 节点 | 表、字段、任务 | prompt、tool、kb、model、policy、agent、dataset、grader |
| 边从哪来 | SQL / AST 静态解析 | 声明、运行时 span、评估与事故记录，三套 |
| 版本是什么 | 表结构 + 分区 + 快照 | 内容 hash + 依赖闭包 |
| 变更频率 | 天到周 | 小时到天 |
| 失败形态 | 任务报错、数据为空 | 不报错，质量慢慢漂移 |
| 主要读者 | 数据工程师 | Agent owner、on-call、评估、安全、财务 |

更根本的差别在问题。数据血缘主要回答「下游是谁」，Agent 血缘至少要回答三个：

1. **发布前**：这次改 prompt / tool / kb / model，会碰到哪些 Agent、哪些环境、哪些租户？
2. **出事后**：这一次运行，实际用了哪几个版本？和上一次差在哪？
3. **审计时**：这个版本当时凭什么被批准？评估用的数据集和 grader 是哪一版？

这三问对应三种边。声明边说「应该」，运行边说「实际」，证据边说「凭什么」。把它们塞进同一张 `depends_on` 表，最常见的结果是：发布门禁把观测到的调用当成声明的依赖，于是永远放行；事故分析把声明的依赖当成实际调用，于是永远找不到根因。

三张图可以共用一套版本 id，但不应该共用边的语义、保留期和权限。

## 2. 三张图

{{< fig "diagrams/01-three-planes.svg" "同一个 Agent 的三张血缘图。A 声明图回答发布时承诺依赖谁，B 运行图回答过去七天实际用了谁并暴露未声明的影子依赖，C 证据图回答凭什么信它。三张图共用 asset_id / version_id，但边的语义、保留期和读者都不同。" >}}

### 2.1 声明图：发布时承诺依赖谁

声明图在发布流水线里生成，输入是 `agent.yaml`、工具清单、镜像 digest 和 CI 解析出来的 lockfile。边只有几种：

- `depends_on`：Agent 版本依赖某个 prompt / tool / kb / model / policy 版本；
- `derives_from`：新版本从旧版本派生，保留 diff 和审批；
- `bundles`：Agent 把另一个 Agent 当工具用；
- `exposes`：MCP server 暴露某个 tool。

声明图的价值在发布前：引用的版本不存在、闭包 hash 变了但没有 review、许可证不合规、必填依赖缺失，都可以在这一步阻断。它也是运行 BOM 的基线——发布时解析出来的精确版本，就是运行时应该用的版本。

但声明图只是承诺。作者忘了写的、运行时才发现的、通过 MCP 动态注册的工具，都不在图上。声明图回答「应该」，不回答「实际」。

### 2.2 运行图：过去七天实际用了谁

运行图从网关和编排器的 span 里长出来。一个 Agent 调到另一个 Agent、一次工具调用、一次知识库检索，都是一条边。边上聚合的是调用次数、错误率、p95、token 和首次/最后出现时间。

它解决声明图解决不了的三件事：

- **影子依赖**：声明里没有、运行里有的边。比如退款 Agent 有 12% 的流量绕过内部 kb，直接调 vendor 的 `/v2/policy`。这不是「实现细节」，是发布风险、权限风险和成本风险。
- **僵尸依赖**：声明里有、运行里 30 天零调用的边。它可能是忘了删，也可能是权限开大了。清退清单从这类边开始。
- **版本漂移**：声明写 `stable`，运行解析到 11-02；下一次解析可能到 11-03。漂移不是错误，但必须可见。

运行图也有它的问题：采样、缺失属性、异步调用、重试。它是抽样，不是全量。所以它适合回答「实际发生了什么」，不适合单独承担审计。

### 2.3 证据图：凭什么信它

证据图接的是评估服务、事故系统、审批系统和红队记录。它记录的不是「谁依赖谁」，而是「谁对谁的判断」：

- `eval_run`：在某版 dataset、某版 grader 下，对某个 Agent 版本跑出的分数和样本量；
- `incident`：某次事故关联到哪些版本、影响了哪些租户；
- `approval`：谁在什么时候批准了哪个版本上线；
- `waiver`：谁批准了哪条规则的例外。

证据图最容易被低估。事故复盘时，大家会去看运行图找「变了什么」；但决定「这个变化是不是坏事」的，是证据图。没有证据图，团队只能凭感觉说「分数掉了」，然后被一句「那次评估用的是旧数据集」顶回来。

证据图回答「凭什么」，不回答「是什么」。

### 2.4 共用什么，不共用什么

三张图共用两样东西：

- **`asset_id`**：资产的身份，跨版本稳定。比如 `kb:refund/refund-policy`。
- **`version_id`**：版本的唯一标识，内容寻址。比如 `sha256:8f3c…`。

不共用的是边。声明边和观测边可以指向同一对版本，但必须是两行：`plane` 不同，置信度不同，保留期不同，谁能看也不同。证据关系则走单独的 `evidence_link`，因为 eval run、incident 不是目录里的资产，硬塞进资产表会把盘点、权限和 owner 全搅乱。

一句话：**三张图是逻辑视图，不是三张可以随便 join 的物理表。**

## 3. 元模型

{{< fig "diagrams/02-metamodel.svg" "元模型。asset 通过 1:N 拥有不可变的 asset_version；asset_edge 的两端都是版本，并携带 type、plane、confidence 与 evidence_ref；run 只引用精确版本，run_usage 是这次运行的 BOM；usage_daily 保存按天聚合。方向统一为 consumer → provider。" >}}

### 3.1 六个核心实体

| 实体 | 主键 | 作用 | 不该放什么 |
| --- | --- | --- | --- |
| `asset` | `asset_id` | 身份、owner、状态、租户 | 具体内容 |
| `asset_version` | `version_id` | 不可变内容、hash、payload 指针 | 运行状态 |
| `asset_edge` | `(src, dst, type, plane, env)` | 版本间依赖，含置信度与证据 | 每次调用的明细 |
| `run` | `run_id` | 一次运行，绑定 agent 版本与解析快照 | 大量业务字段 |
| `run_usage` | `(run_id, version_id, role)` | 这次运行用了哪些版本 | 逐 token 记录 |
| `usage_daily` | `(day, src, dst, type, env)` | 按天聚合的调用、错误、token | 审计级原始数据 |

证据关系单独一张 `evidence_link(subject_version_id, evidence_type, evidence_id, relation, created_at)`。它不参与依赖遍历，但参与「这个版本能不能上线」的判断。

### 3.2 两种 hash，别只算一种

`version_id` 用内容 hash 生成：把 prompt 文本、tool schema、kb 快照 manifest、model id 和参数归一化，算 `sha256`。这样同样的内容只存一份，跨环境、跨租户可以去重。

但只有内容 hash 不够。举个例子：prompt v12 的文本一个字没改，依赖的 tool 从 v2 升到 v3。内容 hash 相同，版本 id 也相同，可这两次发布的行为可能完全不同。

所以还需要一个 `closure_hash`：把自身的内容 hash 和直接依赖的 `closure_hash` 排序后再 hash 一次。发布时锁的是 `closure_hash`，不是单个 `version_id`。依赖成环时（Agent 互相当工具），先缩点或只对 DAG 部分算闭包，否则递归不收敛。

- `content_hash` 负责去重和内容寻址；
- `closure_hash` 负责「这一整套东西」的可复现性；
- 两个都存，查询时按需用。

### 3.3 边的方向：consumer → provider

统一成一条：`src` 是使用者，`dst` 是被依赖方。`agent v7 → tool refund.create v3` 读作「v7 依赖 v3」。

影响分析反向走：从被改的版本出发，找 `dst_version = 当前版本` 的边。这样写入只有一种方向，反向查询靠 `dst_version` 索引。不要在表里同时存正向和反向两份；重复存储迟早会不一致。

### 3.4 别名只解析一次

`stable`、`prod`、`latest` 是别名，不是版本。它们可以出现在作者写的 manifest 里，但必须在运行开始时解析一次，把结果写进 `run.resolution`。之后所有查询都按精确版本走。

别名历史单独一张表，记录「什么时候、谁、把哪个别名指到了哪个版本」。没有这张表，三个月后你无法解释「为什么 11 月 3 日的运行用了 11-02 的 kb」。

用别名做 join 键是事故分析里最常见的坑：今天的报表和昨天的报表对不上，不是因为数据错了，而是因为别名移动了。

### 3.5 粒度：版本级，不是消息级

血缘的节点是版本，边是版本间的关系。不要为每条消息、每个 token 建边，否则边表会被调用量淹没，遍历也会慢得没法用。

运行内部可以细：每个 span 记 `run_id`、`version_id`、`role`、耗时、token。写入 `run_usage` 时按 `(run_id, version_id, role)` 聚合，保留调用次数和错误数。这样既知道「用了谁」，也知道「用了多少次」，但不会把图变成日志。

## 4. 采集

{{< fig "diagrams/03-ingestion.svg" "四路采集：发布流水线提供声明边，网关与编排器提供观测边，静态扫描提供候选边，评估/事故/审批提供证据；经过归一化、身份解析和入图三道处理，再由四个上线门槛把关。" >}}

### 4.1 四路数据

**发布流水线。** 输入是一份作者写的 manifest：

```yaml
name: support-refund
version: 7
model: deepseek-chat@2026-09
prompt: support-system@v12
tools:
  - refund.create@v2
  - refund.query@v3
kb:
  - refund-policy@stable
```

CI 把 `stable` 解析成精确版本，生成 `agent.lock`，写声明边；如果引用的版本不存在，或者 `closure_hash` 变了却没有对应的 review，构建失败。这一步的产出同时也是运行 BOM 的基线。

**网关 / 编排器。** 每个 span 至少带这些属性：

```json
{
  "run.id": "r-902",
  "agent.version": "support-refund@v7",
  "gen_ai.request.model": "deepseek-chat-2026-09",
  "tool.name": "refund.create",
  "tool.version": "v2",
  "retrieval.kb": "refund-policy@11-02",
  "tenant": "cn"
}
```

网关能注入的尽量在网关注入，不要指望每个 SDK 都自觉。缺失版本属性的 span 不是废物：可以按「部署时间 + 资产名」反推，但只能给 0.6 的置信度，并且标成「推断」。

**静态扫描。** 扫 prompt 里的 include、代码里的 tool import、MCP manifest 里的 server URL，产出候选边。它的价值是发现「作者没声明、但代码里确实引用了」的依赖；它的风险是误报，所以置信度给 0.4–0.7，进人工确认队列，不直接进发布阻断。

**证据系统。** 评估服务在跑完 eval 后发事件，带上 dataset 版本、grader 版本、样本量、分数；事故系统在结案时关联版本；审批系统在通过时写 approval。它们都指向精确版本，不指向别名。

### 4.2 身份解析

四路数据汇合时，最难的不是解析格式，是判断「这两个名字是不是同一个东西」。

- **同名不同物**：两个团队都叫 `refund-policy`。用 `namespace + kind + owner` 区分，别用显示名做主键。
- **同物不同名**：`refund-policy`、`refund_policy`、`kb://refund/policy` 可能是一份资产。用 digest、URL 归一化和别名表合并。
- **版本别名**：`stable` 指向哪个版本，要在解析时确定，并记录历史。
- **环境**：`prod/cn` 和 `staging` 是两条边，不是同一条边的两个属性。环境进主键。

置信度规则可以很简单：声明边 1.0；带版本属性的观测边 1.0；按时间反推的观测边 0.6；静态推断 0.4–0.7。低置信边不进发布阻断，但必须出现在影响面里，标成「可能」。

### 4.3 四个门槛

采集质量用四个数看住，多了没人看：

| 指标 | 门槛 | 不达标怎么办 |
| --- | --- | --- |
| 未解析调用率 | < 2% | 补 SDK / 网关属性，别急着做推断 |
| 声明覆盖率 | > 95% | 把 manifest 变成发布必填项 |
| 影子边 owner 覆盖 | 100% | 没 owner 的影子边按安全事件处理 |
| 断链数 | 0 | 引用了不存在的版本，直接阻断发布 |

「断链数为 0」听起来很严，其实最容易做到：写边之前先查版本表，外键会替你挡住。

### 4.4 先算写入量

假设 40 个 Agent、每天 30 万次运行、平均每次 8 次工具或检索调用。如果每次调用写一条边，一天就是 240 万条。这个量不是不能存，但没必要：绝大多数边是重复的。

按分钟聚合，再 upsert 到 `asset_edge` 和 `usage_daily`，一天只有几千次写入。边表保持在万级，`usage_daily` 一个月几十万行，Postgres 完全够用。

**先算写入量，再选存储。** 很多「必须上图数据库」的结论，是没做聚合导致的。

## 5. 存储：先把 Postgres 用满

### 5.1 表

```sql
create table asset_version (
  version_id   text primary key,
  asset_id     text not null references asset(asset_id),
  content_hash text not null,
  closure_hash text not null,
  payload_ref  text not null,
  status       text not null,
  created_at   timestamptz not null
);

create table asset_edge (
  src_version  text not null references asset_version(version_id),
  dst_version  text not null references asset_version(version_id),
  type         text not null,
  plane        text not null,
  env          text not null,
  confidence   numeric(3,2) not null,
  evidence_ref text,
  first_seen   timestamptz not null,
  last_seen    timestamptz not null,
  retired_at   timestamptz,
  primary key (src_version, dst_version, type, plane, env)
);

create index on asset_edge (dst_version, type);
create index on asset_edge (src_version, type);
```

`run` 和 `run_usage` 按月分区；`usage_daily` 也按月分区。`asset_edge` 不分区，但观测边可以按 `last_seen` 归档。

### 5.2 影响分析

```sql
with recursive impact as (
  select $1::text as version_id, 0 as depth, array[$1::text] as path
  union all
  select e.src_version, i.depth + 1, i.path || e.src_version
  from impact i
  join asset_edge e on e.dst_version = i.version_id
  where e.retired_at is null
    and e.plane in ('declared', 'observed')
    and i.depth < $2
    and not e.src_version = any(i.path)
)
select version_id, min(depth) as depth
from impact
group by version_id
order by depth;
```

三个细节：`path` 防环；`depth` 有上限（默认 2，最多 3）；`plane` 显式列出，避免以后加第三种平面时误入。真实查询还要加 `env` 和租户过滤，以及在返回前做权限裁剪。

### 5.3 为什么先不上图数据库

- 写入是 upsert，读是 1–2 跳；Postgres 的递归 CTE 加 `dst_version` 索引足够。
- 事务边界简单：`run`、`run_usage`、`asset_edge` 可以在一个库里的一个事务写完，不需要双写。
- 运维成本低：备份、监控、权限、审计，团队已经会了。
- 真正难的是身份和版本，不是遍历。图数据库不会替你解决「两个 refund-policy 是不是同一个」。

什么时候再考虑换：遍历深度经常超过 3 跳、边数上亿、p95 超过 200ms，或者需要路径解释和子图匹配。到那时也建议只把图数据库当读模型，Postgres 仍是事实源。

### 5.4 保留与一致性

- 原始 span 进对象存储，保留 30 天；需要重放时按 `run_id` 取。
- `usage_daily` 保留 13 个月，够做同比和季度复盘。
- `run_usage` 热存 13 个月，冷存 7 年；审计要求长的行业按合规要求走。
- 证据记录只追加，带 hash 链；不要用「更新」覆盖审批结论。
- 边不物理删除，用 `retired_at` 标记退役；删除会让历史影响分析断链。
- 写入用 outbox 或幂等 upsert；晚到的 span 只更新 `last_seen`，不改 `first_seen`。

## 6. 运行 BOM

{{< fig "diagrams/04-timeline.svg" "版本时间线与两次运行的 BOM。版本是不可变区间，运行是线上的点；r-881 与 r-902 的 BOM 只差 kb 一个版本，这就是可归因的最小差分。" >}}

运行开始时，编排器做三件事：解析别名、写 `run`、写 `run_usage`。这份清单就是这次运行的 BOM：

```json
{
  "run_id": "r-902",
  "agent_version": "support-refund@v7",
  "resolved_at": "2026-11-03T09:12:03+08:00",
  "env": "prod/cn",
  "items": [
    {"role": "prompt", "asset": "support-system", "version": "v12"},
    {"role": "tool", "asset": "refund.create", "version": "v2"},
    {"role": "kb", "asset": "refund-policy", "version": "11-02"},
    {"role": "model", "asset": "deepseek-chat", "version": "2026-09"}
  ]
}
```

三个约束：

1. **写在第一个 token 之前。** 如果解析失败，生产环境 fail-closed，直接不跑；预发可以降级，但要标 `degraded=true`，并且这份运行不能进评估样本。
2. **只记精确版本。** BOM 里出现 `stable` 就算 bug，监控应该直接告警。
3. **BOM 和日志分开。** BOM 是输入清单，日志是输出记录。把两者混在一张宽表里，查询会越来越慢，保留策略也没法分开。

BOM 最实用的能力是 diff：`GET /runs/r-881/diff/r-902` 返回新增、删除、变更的版本。事故分析里，先看 diff，再看指标，比在几万条日志里翻要快得多。

BOM 也有边界。它固定的是输入，不是输出。模型温度、供应商侧更新、检索索引变化、工具副作用，都可能让「同样的 BOM」跑出不同的结果。所以它承诺的是**输入等价回放**，不是逐字节复现。这个区别要在审计口径里写清楚，否则迟早有人拿「复现失败」来质疑整套系统。

## 7. 场景

| 场景 | 先看哪张图 | 方向 | 产出 |
| --- | --- | --- | --- |
| 发布前影响分析 | 声明 + 观测 | 反向 | 阻断 / 灰度 / 告警 |
| 线上根因定位 | 运行 + 证据 | 时间窗 + BOM diff | 嫌疑版本排序 |
| 复现与审计 | 证据 + BOM | 精确版本 | 输入等价回放 |
| 评估门禁 | 证据 | 同 dataset / grader | 可比分数 |
| 成本归因 | 运行 | 按版本聚合 | 单位任务成本 |
| 权限与安全 | 声明 + 观测 | 反向可达 | 授权或收口 |
| 资产盘点与清退 | 声明 + 观测 | 双向 | 候选清单 |

### 7.1 发布前影响分析

{{< fig "diagrams/05-impact.svg" "一次 kb 重建的影响面。影响沿依赖的反向传播，深度默认 2：3 个直接消费者、3 个下游 Agent、3 个产品面；门禁按生产环境、影响深度和影子依赖决定阻断、灰度或告警。" >}}

这是血缘最容易被感知的价值。kb 要重建、prompt 要改、tool 要升级，发布前先问：谁会受影响？

查询从被改的版本出发，反向遍历 `asset_edge`，深度默认 2。结果按环境、owner、关键级别分组，分成两类：

- **阻断项**：生产环境、深度 ≤ 2、关键级别 S1/S2，或者存在未声明的影子依赖；
- **提示项**：预发、测试、低关键级别，或者只有推断边。

门禁规则不需要很复杂，图里那三条够用：

1. `prod` 且深度 ≤ 2 → 阻断（S3/S4 走 owner 豁免），要求回滚演练、影子依赖清零；
2. 影子依赖未声明 → 先补声明，再灰度 5%；
3. 仅 `staging` → 告警并通知 owner，不阻断。

影响面是「可能受影响」，不是「一定出错」。它的作用是决定先看谁、先拦谁，不替代评估。把这句话写进产品文案，能省掉很多「你凭什么说我的 Agent 有问题」的争论。

度量上，别只看「查得快不快」，要看两个质量指标：影响集的召回（事后确认受影响的 Agent 里，有多少提前被列出）和误阻断率（被拦下但事后证明无关的比例）。前者靠事故复盘回填，后者靠 owner 申诉统计。

### 7.2 线上根因定位

事故来了，按这个顺序走：

1. 用时间窗查 `run`，拿到受影响的 `run_id` 列表；
2. 对基线运行和故障运行做 BOM diff，得到「变了什么」；
3. 用运行图看这些版本的实际调用量、错误率和延迟，排掉「变了但没被用到」的；
4. 用证据图看这些版本最近的评估、事故和审批，判断「变化是否可能变坏」；
5. 回放 10–20 条代表性 case，确认因果。

第 2 步是关键。没有 BOM，团队只能猜「可能是模型」「可能是 prompt」，然后一个个排除；有 BOM，diff 会直接把范围缩到一两个版本。上面那个案例里，两次运行的 BOM 只差 `kb: 11-01 → 11-02`，其余四项完全相同。剩下的工作不是「找根因」，是「确认这个根因」。

运行图在这一步还有个别的作用：找影子依赖。如果 diff 里没有可疑版本，但通过率确实掉了，去看 `observed` 边里最近新出现、或者调用量突增的边。影子依赖常常是「没发布，但行为变了」的来源。

### 7.3 复现与审计

审计问题通常长这样：**「11 月 3 日 9 点 12 分，这个 Agent 为什么批准了这笔退款？」**

要回答它，需要四样东西：BOM、输入、工具返回、模型参数。BOM 告诉你用了哪版 prompt / kb / tool / model；输入和工具返回告诉你当时看到了什么；模型参数告诉你当时怎么采样。四样凑齐，才能在沙箱里做一次输入等价回放。

三个现实约束：

- **供应商模型会漂移。** 同一个 model id，供应商侧可能已经换了权重。BOM 里记 `model_snapshot`（如果供应商提供）和调用时间；没有 snapshot 就标「不可精确复现」。
- **工具副作用不能重放。** 退款、发券、发消息这类写操作，回放时要走 mock 或 dry-run，不能真的再退一次。
- **保留期要写进合规口径。** 证据 7 年、BOM 13 个月热存 + 7 年冷存、原始 span 30 天，这三个数字要在审计文档里对齐，不能到用时才发现日志已经删了。

不要承诺「完全复现」。承诺「输入等价回放 + 差异说明」，比承诺「一模一样」更可信。

### 7.4 评估门禁

评估本身也需要血缘。一次 eval run 至少绑定：Agent 版本、dataset 版本、grader 版本、prompt 版本、kb 版本、model 版本、样本量。

最常见的错误是比较了不可比的分数：上一次用 dataset v4 + grader v2，这一次用 v5 + v3，然后说「提升了 3 个点」。这不是提升，是换了一把尺子。血缘的作用是先把尺子对齐，再谈分数。

门禁可以设三条：

- 变更涉及的资产，评估覆盖率 ≥ 90%；
- 分数变化超过阈值，且样本量足够（置信区间不跨 0）；
- 评估集与 kb / prompt 没有明显重叠，避免污染。

第三条越来越重要。知识库重建后，评估集里的问题可能正好被新 kb 覆盖，分数虚高；反过来，评估集可能泄漏进 prompt 的 few-shot。血缘能查出「评估集版本」和「kb 版本」的内容重叠，这是纯看分数发现不了的。

### 7.5 成本归因

`usage_daily` 按 `(day, src, dst, type)` 聚合了调用次数、token 和错误数，天然适合做成本归因：

- 按 Agent 版本看，哪次发布让单次任务 token 涨了 30%；
- 按租户看，哪个客户在替共享 prompt 的长上下文买单；
- 按工具看，哪个检索调用最贵、但命中率最低；
- 按成功任务看，单位成功成本比单位调用成本更有意义。

注意两点：价格表要版本化，别用今天的单价去算半年前的账；共享成本（比如公共 prompt、公共索引）要有分摊规则，否则每个团队都觉得自己不该付。

### 7.6 权限与安全

血缘图是一张可达性图。反过来用，它能回答：**「哪些 Agent 能碰到这份数据 / 这个工具？」**

三个具体用法：

- **权限变更影响面**：某个 tool 的 OAuth scope 要收窄，先反查所有依赖它的 Agent，再排期；
- **影子出口**：观测图里出现了未声明的外部 API 调用，可能是数据外泄，也可能是供应商依赖，先补声明再评估；
- **最小权限**：声明了但 30 天零调用的 tool，是权限过大的候选；反过来，观测到但没声明的 tool，是绕过审批的候选。

多租户系统里，`env` 和 `tenant` 必须进边的主键或过滤条件。别用一个全局图回答所有租户的问题，返回前一定要做权限裁剪。

### 7.7 资产盘点与清退

血缘还能当盘点工具：

- **僵尸依赖**：声明了、30 天零调用，进清理候选；
- **孤儿资产**：没有 owner、没有被任何版本引用，进归档候选；
- **重复资产**：内容 hash 相同但 asset_id 不同，合并或建别名；
- **过期版本**：还在被生产运行引用，但已经标记 deprecated，排升级；
- **删除影响**：删一个 kb 版本之前，先反查还有哪些 run / agent 引用它。

删除要软删。`retired_at` 标记退役，版本和边都留着；物理删除会让历史 BOM 指向不存在的版本，审计直接断链。

## 8. 常见的坑

1. **三张图合成一张。** 用同一个 `depends_on` 同时存声明和观测，发布门禁和事故分析必然打架。`plane` 不是标签，是语义。
2. **只记 Agent 版本。** 运行日志里只有 `agent=v7`，没有 prompt / kb / tool 版本，等于没有 BOM。
3. **用别名做外键。** 今天的 `stable` 和昨天的 `stable` 不是一个版本，历史查询会漂移。
4. **边方向混用。** 有人按「上游 → 下游」写，有人按「使用者 → 被依赖」写，影响分析算出来是反的。
5. **每次调用写一条边。** 写放大、遍历慢、存储贵；先聚合再 upsert。
6. **只做声明图。** 影子依赖永远不可见，事故时只能猜。
7. **置信度不落库。** 推断边和声明边同等对待，门禁要么误杀要么放行。
8. **资产没有 owner。** 影响分析列出了名字，但没人接，门禁形同虚设。
9. **一上来就上图数据库。** 身份没归一、版本没做对，换什么库都查不准。
10. **把血缘当监控。** 血缘是结构，监控是时序；只有结构没有指标，定位不了「什么时候变坏」。

## 9. 落地顺序

不要从「全量资产」开始，从一个高价值 Agent、三类资产、一个环境开始。

| 阶段 | 时间 | 做什么 | 退出条件 |
| --- | --- | --- | --- |
| 0 | 2 周 | 统一 asset_id / version_id；发布时写 BOM；run 开始快照 resolution | Top 10 Agent 的 BOM 完整率 > 95% |
| 1 | 1 个月 | 声明图接 CI；影响分析 API；门禁先 warn-only | 影响查询 p95 < 2s；误报可解释 |
| 2 | 1 个季度 | 运行图接网关；影子依赖报告；BOM diff 进事故手册 | 未解析率 < 2%；影子边有 owner |
| 3 | 持续 | 门禁转 enforce；成本归因；权限复核；清退 | 阻断有申诉通道；审计可回放 |

度量别贪多，六个够用：声明覆盖率、未解析率、影子边 owner 覆盖、影响分析召回、MTTR、输入等价回放成功率。

组织上，平台团队管 schema、采集和 API；资产 owner 管自己资产的版本、别名和证据；安全团队管权限边和影子出口。三张图分别归三个角色维护，但共用一套 id，这是能长期运转的前提。

## 10. 没解决

- **非确定性。** 同样的 BOM 也可能跑出不同结果。血缘能缩小范围，不能保证复现。
- **供应商漂移。** 模型、向量化服务、外部 API 都可能在你不发版的时候变化。只能记录调用时间和快照，无法完全控制。
- **跨组织血缘。** 供应商的模型内部依赖、SaaS 工具的后续链路，拿不到就是拿不到；只能在边界上标「外部依赖，不可见」。
- **采样偏差。** 运行图来自采样，低频但关键的调用可能被漏掉；影响分析要结合声明图，不能只看观测。
- **评估污染。** 评估集和 kb / prompt 的重叠检测，目前只能做文本级近似，语义级还很难。
- **人的纪律。** 再好的 schema，也挡不住 owner 不写 manifest、不审别名、不看影子边。门禁和巡检只能降低概率，不能消灭。

如果只记一句：**先把版本 id 和运行 BOM 做对，再谈图算法。** 血缘的价值不在于画出一张漂亮的图，而在于事故发生时，你能在十分钟内说出「这次运行用了哪几个版本，和上一次差在哪」。
