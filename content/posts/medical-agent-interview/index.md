> 四月那场 QCon 北京，蚂蚁的阿福把医疗 Agent 从 0 讲到生产。我把实录读了三遍，又对着自己的简历看了一遍，发现它是一份现成的面试题纲：整场分享里，凡是能含糊的地方，讲者都给了数字。
>
> 于是按“分享的六段 × 简历的六块”拆成 18 道题。每题四段：考察什么、采分点、参考答案、下一层追问，最后是坑。
>
> 文中标“分享里”的数字来自公开实录，其余是我按公开参数粗算的，算错了算我的。

## 为什么拿医疗当题库

医疗是个放大器。零容错、循证、合规、几十年的病程，这四条把 Agent 的每个弱点都放大一遍：

- 评测不严会出人命，所以“差不多对”在这里不成立；
- 上下文塞多了就找不到重点，而一次问诊的信息量天然是别的场景的好几倍；
- 记忆记错一个，推荐的就是禁忌药；
- 推理慢两秒，用户就关掉对话框。

能在这里跑通的方案，换到别的行业基本是降维；反过来，在这里说不清的地方，面试里也藏不住。

这场分享的六段分别是：痛点与范式、技术体系与评测、上下文工程、从 RAG 到 Agentic RAG、记忆与个性化、训推优化。我简历上的六块是：资产与权限树、渐进式上下文加载、Agent 运行时、Memory 与画像、LLM Gateway、商业化指标。两边一对，题就出来了。

| 轮次 | 主题 | 分享里的锚点 | 简历里的锚点 |
| --- | --- | --- | --- |
| 1 | 范式与评测 | 12 天→小时、rubric、badcase 分拣 | 商业化指标的 AB 口径 |
| 2 | 上下文 | 32–64K、压缩触发、渐进披露 | 资产树、渐进式加载、Token 预算 |
| 3 | Agentic RAG | 三跳问题、合成难问题、证据融合 | 资产检索、混合召回 |
| 4 | 记忆 | 遗忘、主体、授权、冲突 | Memory 分层、画像标签 |
| 5 | 推理性能 | KV cache、PD 分离、投机解码 | Gateway、亲和路由 |
| 6 | 简历对账 | 指标与边界 | 60% / 35% / 30%、协同画布 |

**怎么用**：先遮住答案，自己说 90 秒；再对照采分点；最后看坑。采分点不是标准答案，是面试官心里的勾选框——说到了就打勾，说不清就没打。

## 0. 先定判分契约

面试官不需要听完所有细节，他只判断三件事：**这事是不是你做的**、**你知不知道它为什么这样设计**、**出了问题你能不能兜住**。所以每道题我都按三档准备：

- 及格：能说出对象、动作、边界，不混淆概念；
- 加分：能给出数字、取舍和失败案例；
- 否决：把工程问题答成工具名，或者把指标口径说不清。

下面每题不再重复这三档，只在“坑”里标否决项。

## 第 1 轮：范式与评测

这一轮看起来在聊理念，其实在筛一件事：你有没有被线上打脸过。

### Q1 一次迭代从两周压到两天，快在哪？

**考察**：经历过范式迁移，还是只换了工具。

**采分点**：

- 改动的单位变了：从改代码变成改 prompt、改检索、加工具、换模型；
- 反馈信号变了：从 QA 用例变成 benchmark + badcase；
- 组织变了：评测不再只是质量部门的事；
- 代价说清楚了：不确定性上升，所以要围栏、灰度、回滚。

**参考答案**：

分享里给了三代研发范式的对比，这是最好的骨架：

| 范式 | 节奏 | 靠什么判断好坏 | 适合什么 |
| --- | --- | --- | --- |
| 传统 TDD | 一个功能 2 周–1 个月 | 人工 QA、测试用例 | 需求确定 |
| 搜索推荐 | 一周 1–2 次 | 特征工程 + AB，看 CTR/CVR | 目标可量化 |
| Agent | 以天为单位 | Benchmark 牵引 + Badcase 纠偏 | 目标开放、长尾多 |

快的原因不是“写代码快了”。写代码从来不是瓶颈。快在试错闭环缩短了：改一句 prompt 半小时能跑完一遍评测；换一个检索策略，重建索引再测；换模型才需要重跑全量 benchmark。每次改动的验证成本，从“一次发布加一周观察”降到“一次评测加一小时”。分享里给的数字更具体：自动化评测把一轮从 12 天压到小时级。

分享里还有一句可以当加分项：往 Harness 的方向走，普通工程师能提效两到三成，强的人能到十倍。差别不在会不会用工具，在于能不能把“目标 + 上下文 + 验证标准”说清楚。

**下一层追问**：什么改动不值得走 benchmark？

答：纯文案、样式、交互。凡是可能改变医学事实的——剂量、禁忌、适应症、转诊阈值——都必须走。

**坑**：答“我们用了 Claude Code / Cursor”。工具提升的是编码环节，不是迭代闭环。面试官接着问“那评测呢”，就露馅了。

### Q2 医疗要“确定性”，可模型是概率的，你怎么定义确定性？

**考察**：会不会把工程问题偷换成“调低 temperature”。

**采分点**：

- 确定性 ≠ 输出逐字一致；
- 分三层：证据、推理、行为；
- 可复现指的是“同样的证据下不给出互相矛盾的结论”；
- 拒答和转诊是规则，不是模型的心情。

**参考答案**：

医疗说的确定性，是这三件事：

1. **证据确定**：每个结论能落到指南、说明书、文献的具体条目，引用点得开。
2. **推理确定**：同样的输入、同样的证据，走同样的推理路径。温度低只是其中一小步，更关键的是检索结果稳定、槽位结构化、模板固定。
3. **行为确定**：什么情况下必须拒答、必须转诊、必须叫人工，写死在流程里。

分享里的原话大意是：确定性不是输出一致，而是可解释、可复现、符合指南的推理链。

**原理**：temperature=0 只关了采样随机性。批量推理时 kernel 的非确定性、不同的 batch 组合、不同的并行度，仍会让 logits 有微小差异；更根本的是，检索结果一变，输入就变了。所以确定性要靠约束输入和约束流程，不是靠约束采样。

**下一层追问**：怎么验证“推理链符合指南”？

答：把指南拆成 rubric，用 LLM judge 判每条是否被引用、是否被正确引用，再抽样人工复核。这就是下一题。

**坑**：只答“temperature 设 0、top_p 设 1”。这是标配，不是答案。

### Q3 “感冒怎么治”这道题，怎么判它答对没答对？

**考察**：会不会写 rubric；知不知道 rubric 和参考答案的区别。

**采分点**：

- 必答、加分、一票否决三档；
- 一道题挂多条维度；
- judge 要能勾选，不能是“整体感觉”；
- 有区分度；
- 人和机器校准过。

**参考答案**：

rubric 是把“答得好”拆成一组可判定的命题。以感冒为例：

| 档位 | 判定项 | 为什么 |
| --- | --- | --- |
| 必答 +1 | 说明自限性、多数情况可自愈 | 缺这条就是过度医疗 |
| 必答 +1 | 建议休息、补水、必要时对症 | 缺这条是只开药 |
| 加分 +0.5 | 点出需要就医的危险信号 | 高热不退、呼吸困难、婴幼儿 |
| 否决 −1 | 滥用抗生素、编造剂量 | 一条就判不合格 |

三个细节：

- 否决项要独立于总分。九条对一条错，如果只是扣分还是高分；医疗里这条必须一票否决。
- 一道题挂多条 rubric：有效性、安全性、循证性、完整性各一条，别合成一个 0–100。
- 判的人通常是模型，标准是人写的。先做人际一致性（两个医生判同一批答案，一致率够不够），再做人与机器的一致性。分享里说，每个场景要校 1–2 个月。

外面看到的是一张表，里面其实有五个字段：

| 字段 | 写什么 | 合格的样子 |
| --- | --- | --- |
| id | 稳定编号，进 benchmark 后不改名 | R-007 |
| 命题 | 一个能被证伪的判断 | 回答给出了非药物干预建议 |
| 档位 | 必答 / 加分 / 否决，带权重 | 必答 +1 |
| 证据 | 必须落到哪类来源才算数 | 引用指南或说明书的具体条目 |
| 反例 | 什么表述不算通过 | 只写“多喝热水”不算非药物建议 |

**它从 badcase 长出来，一共五步**：把一周的错例按“错在哪”聚类（漏禁忌、编剂量、答非所问、过度自信）；每组抽三五条，写成“必须出现 / 必须不出现”的句子；找两个医生盲判一百条，算一致率，低于 0.8 的条目改措辞或拆细；让 LLM judge 判同一批，分歧样本回流改 rubric 而不是改 judge；给每条打版本号，改了要重跑历史集，否则前后不可比。

**评分怎么聚合**：加权和只在同一维度里用；跨维度不平均，安全 0 分不能靠有效性 100 分拉回来；否决位是一条独立的布尔，最终结果 = 否决位通过 AND 加权和过线；每条判定项单独统计通过率，用来算区分度——强模型和弱模型在这条上差不到 5%，这条基本没有信息量。

**judge 只判单条，不打总分**：输入答案和检索到的证据，让它逐条输出 pass / fail / unknown，并引用答案里的原句；unknown 单独统计，通常说明 rubric 写得含糊，不要并进 fail。

**四个常见失败**：长度偏置（长答案更容易被判 pass）、格式偏置（有表格就加分）、自我偏好（同源模型互捧）、rubric 漂移（模型换了、rubric 没跟着换）。

**原理**：为什么不用一个分数？分数不可解释、不可定位、不可比较。rubric 把质量变成一组命题，错在哪一条，能直接归因到“检索没召回禁忌”还是“模型编了剂量”。分享里有句话很狠：所有模型都 80 分，这套题就废了——区分度是 rubric 的第一指标。

**下一层追问**：rubric 从哪来？

答：从 badcase 反向提炼。先有线上错例，再抽象成判定项，不是先拍脑袋写一百条。

**坑**：写成“回答准确、专业、全面”——不可判定；或者只写必答不写否决。

## 第 2 轮：上下文工程

医疗的一次问诊，信息量是别的场景的好几倍：症状、检查、用药、既往史，还有 PDF 和图文报告，全是多轮。

### Q4 模型标称 128K，你为什么把上下文压到 32–64K？

**考察**：有没有算过账，还是“能塞就塞”。

**采分点**：

- 位置偏差：中间的信息召回最差；
- 干扰：无关内容会稀释注意力；
- 成本：首字延迟和显存随长度涨；
- 做法：结构化 + 非结构化混合，关键信息放头尾。

**参考答案**：

三个原因，按重要性排：

1. **位置偏差**。长上下文里，开头和结尾的信息召回最好，中间最差，这是 U 型曲线。分享里说，国内模型标称 128K、256K，但到 64K 就开始 lost in the middle，recall 和准确率一起掉，最佳区间是 32–64K。
2. **干扰**。几十页指南里，跟这次问题相关的可能就两段，其余全在 attention 里分摊权重。信息越密，稀释越明显。
3. **成本**。prefill 的 attention 是 O(L²)，KV 是 O(L)，首字延迟和显存都随长度涨。

做法是分享里那句“20–30% 关键信息结构化，其余非结构化”：症状、指标、用药、过敏做成槽位，指南和报告留原文；关键信息放头尾；指南按章节渐进披露。完全结构化不行，规模上不去；完全不结构化也不行，模型抓不住。

**原理**：softmax 归一化会把注意力摊薄，长度翻倍，每个 token 分到的权重就少一半；位置编码在训练分布之外还会衰减。自测方法很简单：needle-in-a-haystack，把一句关键事实放在不同位置，看召回怎么变。

**下一层追问**：那 32K 和 64K 怎么选？

答：看任务。单轮问答 8–16K 就够；带完整病历和指南章节的，32K 起步；超过 64K 要有明确的收益证据，否则先想怎么拆。

**坑**：说“越大越好，反正不要钱”；或者“全塞进去让模型自己找”。

### Q5 压缩什么时候触发？压的时候留什么？

**考察**：有没有把压缩当成一个有损变换来设计。

**采分点**：

- 触发点至少三类：轮次、Token 阈值、任务边界；
- 用户的原始问题不能摘要；
- 结构化槽位和未解决的冲突要留；
- 寒暄、重复、原始 JSON 可以丢；
- 丢了要留索引，能回取；
- 阈值是实验搜出来的。

**参考答案**：

分享里的三个触发点：第 1 轮先压一次（把开场白和系统提示压成骨架）、第 12 轮按轮次策略压、上下文到 20K 时按阈值压。阈值不是拍的，是自动化实验加评估搜出来的。

他特别强调一句：压缩时保留全部 user query。因为用户的问题比模型的回答更重要。举个例子：第 3 轮用户说“我怀孕 7 个月”，第 15 轮问“这个药能吃吗”。如果压缩把孕周摘要掉了，后面所有回答都是错的，而且错得很自信。

落地时我会这么留：

- 记忆条目带 source_turn，能回到原话；
- 摘要保留结论和引用编号，不保留推理过程；
- 工具返回的原始 JSON 只留 index，需要时再取；
- 用户明确否认过的内容，压缩后要留一个“已否认”的标记。

**原理**：压缩是有损变换，损失函数不是 token 数，是“后续 N 轮的可答性”。所以评估压缩策略要用下游指标——压缩完再问一组固定问题，看答对率——而不是看摘要写得多通顺。

**下一层追问**：压缩和摘要模型用同一个吗？

答：可以不同。摘要用小模型或规则，判“值不值得留”用主模型；但摘要的 prompt 要和主任务的 rubric 对齐，否则它会把医学上关键、语言上平淡的那句删掉。

**坑**：固定 8K 阈值不看场景；压缩后不留原文索引，回溯不了；把 user query 也摘要了。

### Q6 渐进式披露和 RAG 有什么区别？你的资产树是不是同一件事？

**考察**：能不能把两个相似的概念拆开，并且落到自己的项目上。

**采分点**：

- 谁决定召回：模型还是检索器；
- 目录先行，逐层下钻；
- 多轮、可回退；
- 成本结构不同；
- 能说出自己项目里的具体形态。

**参考答案**：

我简历里的资产树是 Discovery → Activation → Execution：先返回树的摘要（有哪些 Brand、哪些素材库），模型选一个子树，再 list，再 get 具体资产。RAG 是一次 top-k，检索器决定拿什么，一次定生死。

区别在决定权：

- RAG：检索器决定，模型被动接收，错了只能重查；
- 渐进式：模型决定看哪一层，可以先看目录再决定读不读，读错了能退回上一层。

医疗里的对应形态：先给指南的目录（章、节），模型判断这次要读哪章，再取那一节；而不是把 50 页 PDF 切块全塞进去。子 Agent 也是同一思想：子 Agent 返回 index 不返回原文，主上下文需要时再 retrieve——这样主上下文只花一份索引的钱。

**原理**：上下文是预算，不是容量。每注入一段内容，都要回答“这 token 对当前决策有用吗”。渐进式披露把这个判断交给模型，RAG 把它交给检索器；前者更贵（多轮），后者更便宜但更粗。

**下一层追问**：什么场景下不该用渐进式？

答：单跳事实问答、语料很小、延迟敏感。多一轮就多一次 TTFT，用户等不起。

**坑**：说“渐进式加载就是分页/懒加载”——那是接口设计，不是上下文设计。

## 第 3 轮：Agentic RAG

这一轮的题眼是一句话：普通 RAG 把检索当输入，Agentic RAG 把检索当手段。

### Q7 “肝功能不好又发烧，吃什么药、怎么吃、怎么报销”，普通 RAG 会怎么错？

**考察**：能不能把一句用户话拆成多跳，并且知道每一跳落在哪个库。

**采分点**：

- 三跳：禁忌、剂量、报销；
- 一次 top-k 只能命中一跳；
- 条件词在 embedding 里会被主问题盖过；
- 库不同，不能合并成一个索引；
- 错了还答得很顺，这是最危险的。

**参考答案**：

拆开看：

- 第一跳，“肝功能不好 + 发烧” → 对乙酰氨基酚要不要减量、有没有禁忌 → 药品说明书库；
- 第二跳，“怎么吃” → 剂量、疗程、监测 → 说明书加指南；
- 第三跳，“怎么报销” → 医保目录、门诊统筹、起付线 → 医保政策库。

一个向量库一次 top-k，只能命中其中一段。更麻烦的是，“肝功能不好”是条件不是关键词，在 embedding 里会被“发烧吃什么药”盖过去。最后模型拿到一段退烧药说明，答得挺顺，但漏了禁忌——这是最危险的错：看起来对。

**原理**：检索是用一次相似度近似一次推理。多跳需要组合，而组合关系不在向量空间里。你把三个子问题拼成一句话去检索，得到的向量是三个意图的平均，哪个都不像。

**下一层追问**：那多建几个索引，并行查三次行不行？

答：行，但那是“路由”，还没到 agentic。真正的差别在“查完发现不够，要不要再查一次”，这个判断得由模型做。

**坑**：说“chunk 切小一点加 rerank”。那是召回精度，不解决缺跳。

{{< fig "diagrams/04-rag-vs-agentic.svg" "同一条三跳问题：上面一次到底，只召回一跳；下面循环到证据够，三个开关交给模型。" >}}

### Q8 怎么让模型学会“该多查一次”？

**考察**：知不知道 agentic 行为是训练出来的，不是 prompt 出来的。

**采分点**：

- 先有足够难的问题；
- 合成路径：知识图谱抽最长子问题链，再模糊化条件；
- 轨迹合成：强模型蒸馏、思路链重写；
- 有工具环境，奖励能区分“查对了”和“猜对了”；
- 评测要测轨迹，不只测答案。

**参考答案**：

分享里的路径是这样的：2025 年 6 月启动，先发现一次检索覆盖不了多跳和 corner case，然后问题变成“去哪找足够难的问题”。

做法是从知识图谱里抽最长子问题链，再把关键条件模糊化：不说“肝功能不好”，说“最近体检转氨酶偏高”；不说“我在吃华法林”，说“我在吃一种抗凝药”。模型必须追问或者多查才能答对。答对之后继续加难度，形成课程。

轨迹用强模型合成：在线蒸馏、思路链重写。他们试下来的选型是，写作和战略分析用 Gemini，强工具调用用 Claude，交互和写 HTML 用 Gemini。

结果：6 个人 2–3 个月刷到 SOTA，开源了数据、训练框架和技术报告。讲者那句话我记到现在：后来者只有把细节公开得更详细，别人才会关注。

**原理**：agentic 行为不是 prompt 出来的，是问题难度逼出来的。训练题一次检索就够，模型永远学不会第二次检索；奖励只看答案，模型会学会“猜对”而不是“查对”。

**下一层追问**：怎么防止它过度检索？

答：奖励里加成本项（token、时延），评测里加“必要检索次数”的上界；线上加预算和超时，超了就降级到一次检索加免责声明。

**坑**：在 system prompt 里写“你可以多次检索”。没有奖励信号区分，模型要么不查，要么查到死循环。

### Q9 指南说 A，说明书说慎用，医保只报 C，三路证据打架怎么办？

**考察**：有没有处理过真实的证据冲突，还是假设知识库永远一致。

**采分点**：

- 权威分层：指南 > 说明书 > 文献 > 医保政策；
- 时效和版本；
- 安全优先于经济；
- 冲突要显式呈现，不能悄悄选一个；
- 有裁决机制和校准。

**参考答案**：

不能投票，也不能取“检索分最高”——不同库的分数不可比。

我的做法是四步：

1. 每条证据带来源、版本、日期、适用人群；
2. 按临床优先级排：禁忌 > 适应症和剂量 > 报销。报销是经济问题，不能覆盖安全问题；
3. 裁决不了就显式呈现分歧，比如“指南推荐 A，但说明书对肝功能不全者建议减量”，让医生或用户决定；
4. 用强模型做 pairwise 判断，再和专家标注对齐，定期校准。

分享里的说法是“业务分 + 权威分”，冲突时专家裁决，或者用强模型打分再和专家比一致性。

**原理**：证据融合的本质是排序，不是平均。平均会把“禁忌”和“可以”折中成“慎用”，这在医疗里是错误答案。

**坑**：说“取置信度最高的”；或者说“让模型自己判断”——没有校准就是掷骰子。

## 第 4 轮：记忆与个性化

分享里有一句判断：现在国内外的记忆都做得不是特别好。所以这一轮不指望你背方案，指望你说清楚难点在哪。

### Q10 记忆最难的不是存，是什么？

**考察**：有没有把记忆当成一个生命周期来设计。

**采分点**：

- 主体：谁在说，说的是谁；
- 冲突：自述和检查不一致；
- 授权：买过药不等于授权；
- 过期：病好了要忘；
- 漂移：上百轮之后话题已经偏了。

**参考答案**：

四个问题，按出事的概率排：

1. **主体**。“我女儿”可能有两个；替人咨询要先确认是谁。分享里的策略很保守：100% 确认才结合，不确认就不用。他还点评了 Gemini “做得比较激进，每次过度结合身份”。
2. **冲突**。自述血压高，这次量出来 118/76；自述过敏，报告里没有。冲突要显式问用户，不能取平均。
3. **授权**。买过某个病种的药，不等于授权拿它做个性化推荐。分享里说医疗数据泄露超过 50 条可能坐牢，这不是夸张。
4. **过期**。感冒好了，“正在感冒”就不能再出现在下一次问诊里。

再加一个工程问题：七八十到上百轮的话题漂移，召回要按当前病程，不是按相似度。

**坑**：说“上个向量库做 RAG”。那是检索，不是记忆。记忆要回答三个问题：写什么、信谁、什么时候删。

### Q11 为什么说遗忘比记住更重要？怎么设计遗忘？

**考察**：知不知道医疗记忆的错误代价是不对称的。

**采分点**：

- 病程结束要归档；
- 授权撤销要级联失效；
- 用户否认优先；
- 衰减按事件不按时间；
- 可追溯、可删除、有审计。

**参考答案**：

医疗记忆的错误代价不对称。记住一条过期的“正在感冒”，可能推出错误的用药建议；记住一个未授权的病种，是隐私事故。所以遗忘不是清理，是正确性的一部分。

三个开关：

- **病程结束**：episode 关闭，记忆归档，不再进召回；
- **授权撤销**：某家医院的授权一撤，召回路径立刻断；
- **用户否认**：“我没得过”优先于任何抽取结果，能改、能删、能追溯改过什么。

技术上，条目带 episode_id、来源、有效期；衰减按事件不按时间。感冒的病程是七天，不是 TTL 三十天；高血压的记忆不该衰减，但每次测量要覆盖旧值。

**原理**：记忆的新鲜度是事件函数，不是时间函数。用 TTL 一刀切，对急症太慢，对慢病太快。

**下一层追问**：删了之后，模型还会不会“记得”？

答：会。微调过的模型参数里可能还有；所以敏感数据不能进训练集，或者要能证明它没进。这是记忆和训练数据治理的交界。

{{< fig "diagrams/05-memory-lifecycle.svg" "记忆的难点在中间三步：主体、冲突、遗忘；存下来只是开始。" >}}

### Q12 解释性和隐私打架，你站哪边？

**考察**：有没有在真实产品里做过取舍。

**采分点**：

- 对用户分层披露；
- 对审计保留全链路；
- 敏感病种默认不参与；
- 用户可控，能关。

**参考答案**：

例子：男性用户被推荐了某个隐私用药，因为买过。你说“因为你买过”，用户会炸；你什么都不说，又不可解释。

做法是分层：

- 对用户：粗粒度理由，“根据你的用药记录”，可以关闭；
- 对医生和审计：完整链路，能追到具体条目和授权时间；
- 敏感病种：默认不参与个性化，除非明确授权。

分享里提到一个矛盾：男性隐私用药的推荐理由，说出口会激怒用户。这不是技术问题，是产品边界问题。我的判断是：可解释性对监管和对用户是两个版本，不能共用一个。

**坑**：说“我们完全透明”；或者说“我们不做解释”。前者在医疗里会伤人，后者合规过不了。

## 第 5 轮：推理性能

这一轮是给做基础设施的人准备的。答不上来不丢人，答“加机器”就丢人了。

### Q13 为什么说“改上下文策略，千万别把 KV cache 搞丢”？

**考察**：会不会算 prefill 和 KV 的账。

**采分点**：

- KV 大小随层数、KV head、head_dim、长度线性涨；
- prefill 是计算密集，重算就是白烧钱；
- 前缀稳定才有缓存命中；
- 路由要按前缀亲和；
- 知道哪些改动会让缓存失效。

**参考答案**：

先算账。70B 级 GQA 模型，80 层，8 个 KV head，head_dim 128，FP16：

- 每 token 的 KV ≈ 2 × 80 × 8 × 128 × 2B ≈ 320KB；
- 32K 上下文 ≈ 10GB，这还没算权重和激活；
- 重算一遍 32K 的 prefill ≈ 2 × 70B × 32K ≈ 4.6 PFLOP，按有效 400 TFLOPS 算，十几秒。

所以缓存命中率直接决定成本和首字延迟。工程上三件事：

- 前缀稳定：system prompt、工具定义放最前，时间戳、UUID、随机 id 放最后；
- 路由亲和：同一会话、同一前缀尽量打同一副本；
- 失效预案：压缩、换模型、改工具都会让缓存失效，提前预热。

**原理**：prefill 的算力花在矩阵乘上，decode 的瓶颈在 HBM 带宽。KV cache 是把 prefill 的结果存下来，让 decode 不用重算；丢了它，等于每个 token 都重新读一遍整个上下文。

**坑**：把时间戳放 system prompt 第一行——每个请求前缀都不同，命中率归零；或者按轮询路由，同一会话打到不同副本。

{{< fig "diagrams/06-prefill-decode.svg" "两段负载两种瓶颈：Prefill 吃算力，Decode 吃带宽；PD 分离就是各买各的卡。" >}}

### Q14 PD 分离为什么能省？什么时候不划算？

**考察**：知不知道架构优化的边界。

**采分点**：

- prefill 计算密集，decode 带宽密集；
- 混部会互相干扰，TPOT 抖动；
- 可以按瓶颈选异构卡；
- KV 跨节点传有成本；
- 规模小的时候是负收益。

**参考答案**：

同卡混部时，一个长 prefill 会把 decode 卡住，TPOT 抖动，用户能感觉到“打字一顿一顿”。分开之后，prefill 池堆 FLOPS（分享里提到寒武纪这类卡），decode 池堆 HBM 带宽和容量，各自扩缩。

代价是 KV 要跨节点传，走 RDMA 或 NVLink，带宽和延迟都是钱。请求短、并发低、KV 传得比算得慢的时候，分离是负收益。分享里还提到多模态要拆成 EPD，因为 encoding 是第三种负载。

**下一层追问**：怎么判断该不该分？

答：看两个比值——prefill 时间占端到端时间的比例，和 KV 传输时间占 prefill 时间的比例。前者高、后者低，才值得分。

**坑**：说“分离一定更快”。

### Q15 投机解码什么时候会变慢？

**考察**：知不知道加速手段的适用条件。

**采分点**：

- 接受率低就白干；
- draft 模型太大，验证成本盖过收益；
- batch 已经很大，GPU 没空闲算力；
- 要保证分布不变，不能改答案。

**参考答案**：

投机解码是小模型先猜 k 个 token，大模型一次验证。加速比大致是 (1−α^(k+1)) / ((1−α)(1+c))，α 是接受率，c 是 draft 的相对成本。α 低、c 高，收益就没了。

三种会变慢的情况：领域不匹配（医疗术语多，通用 draft 猜不准）、draft 模型太大、batch 已经跑满（没有空闲算力做验证）。

工程上：用领域 draft 或 n-gram / prompt lookup；看 P99 TPOT，不看平均 token/s；分享里提到 SpecFog 开源的百灵 1T 方案，50 token/s 提到 120 token/s，约两倍。

**坑**：拿平均吞吐当唯一指标，P99 炸了用户照样骂。

## 第 6 轮：简历对账

前五轮考通用能力，这一轮考“你说的和做的是不是一回事”。

### Q16 你的 Gateway 做“按模型/租户/会话亲和路由”，KV cache 亲和具体怎么做？什么时候失效？

**考察**：简历上的词，能不能落到实现。

**采分点**：

- 两级亲和：会话粘性 + 前缀哈希；
- 冲突时谁优先；
- 负载和热点怎么处理；
- 失效场景；
- 有观测指标。

**参考答案**：

两级。第一级会话 id 做 sticky，保证同一通对话落在同一副本；第二级 prefix hash（模型 + system prompt + 工具定义 + 历史前缀）做亲和，让共享同一前缀的请求聚到一起。冲突时前缀优先，因为省的是 prefill，那才是大头。

失效场景：换模型、改 system prompt、工具列表变化、上下文压缩、副本重启。压缩导致的失效最容易被忽略——压缩前后前缀完全变了，缓存全丢，首字延迟会突然涨一截。

观测三个指标：缓存命中率、TTFT 的 P50/P99、每个副本的 prefix 分布。命中率掉了，先查前缀是不是被动态内容污染。

**坑**：只做 session sticky 不做 prefix，多租户共享 system prompt 时浪费；或者 sticky 太硬，热点打爆一个副本。

### Q17 资产树和渐进式加载搬到医疗，会哪里坏？

**考察**：能不能把上一个领域的方案迁移，并且知道哪里不适用。

**采分点**：

- 树不是用户建的，是医学分类；
- 权限主体从租户变成患者；
- 指南有时效，节点要带版本；
- 血缘变成证据链；
- 用户不知道自己要什么。

**参考答案**：

我的资产树假设“用户知道自己有什么”，医疗用户不知道。所以至少有五处要改：

- 树由医学分类生成（疾病、部位、检查、用药），不能靠用户建文件夹；
- 权限主体从租户变成患者，还要区分本人、家属、医生；
- 指南有时效，树节点带版本，旧版本不能静默召回；
- 资产的“血缘”变成“证据链”：这条结论引用了哪版指南的哪一节；
- 用户不知道自己要什么，所以要有“猜你想问”，但不能猜病。

**坑**：直接把“文件夹”当“病历”。

### Q18 你简历上的 60%、35%、30%，和医疗 Agent 的指标怎么分开？

**考察**：数字的口径意识。

**采分点**：

- 系统指标和效果指标分开；
- 结果、过程、安全三层；
- 分母和反事实说清楚；
- 安全指标一票否决。

**参考答案**：

我简历上的数字是系统指标：查询性能 +60%、资源利用率 +35%、云实例降本 30%。它们回答“系统更快更省”，不回答“Agent 更好”。

医疗 Agent 要三层：

- 结果：任务完成率、转诊率、复诊率、人均节省时间；
- 过程：首答有用率、追问轮数、引用可点开率、检索命中率；
- 安全：禁忌命中率、高危识别召回、越权访问率、伤害率。

面试里要主动说口径：60% 是 P99 还是平均，分母是什么，有没有做反事实。安全指标是一票否决，不参与加权。

**坑**：拿满意度当唯一指标；或者拿 benchmark 分数当线上效果。
