> 同一个文件，两个人同时改，最后必须长出同一个结果。这句话听着简单，里面其实压着三个问题：**并发怎么定序**、**冲突谁裁决**、**历史怎么压缩**。OT、CRDT、LWW 是三种截然不同的回答方式——而且严格说它们并不在同一个层级上：前两个是合并机制，LWW 是 CRDT 里最省事的那一个特例。下面把它们拆开，讲清各自在保证什么、放弃了什么、在什么规模上会崩；然后叠成一台服务端、拆到多实例，最后对比 Yjs 与 Automerge，给一张按两个维度切的选型矩阵。

## 0. 三个问题，三种回答

先把「对」这个字拆开。一个协同编辑系统要同时满足两件事，而这两件事经常被混为一谈：

- **收敛**（convergence）：所有收到同一组更新的副本，最终状态逐字节相同。这是底线，不满足就不配叫协同编辑。
- **意图保留**（intention preservation）：并发操作的效果没有被扭曲。收敛只说「大家一样」，意图说「大家一样，而且都对」。

收敛是必要条件，不是充分条件。一个系统完全可以把所有人的编辑都丢掉，它依然完美收敛。**LWW 就站在这个极端上。**

举个最小的例子。基础文本是 `ab`，Alice 在 a 后面插入 `X`，Bob 同时在同一个位置插入 `Y`。合并之后可能长成三种样子——三种都收敛，区别只在最后一种。

{{< fig "diagrams/01.svg" "同一次并发插入，三种合并策略的结局" >}}

三种结果都收敛，所有副本最后都会得到同一个字符串。区别只在第三种：**Bob 的 `Y` 凭空消失，界面上不会出现任何提示**。这就是 LWW 在「整篇文档」这个粒度上的行为——它没有解决冲突，它取消了冲突。

于是三个问题浮出来，任何一个协同系统都得把它们答完：

1. **谁定序**。两个互相看不见的操作，谁在前？所有副本必须给出同一个答案，否则同一份输入会长出两棵树。
2. **冲突谁赢**。两个写落在同一个语义位置上，最终值取谁？
3. **历史留多少**。后来加入的、断线重连的副本，凭什么只拿一小段增量就追上？你为此要一直保留多少操作记录？

OT 的办法是**找人代答第一个问题**：让一个中心节点替所有人定序，再用变换函数把「基于旧顺序的操作」翻译到「新顺序」上。CRDT 的办法是**把第一个问题删掉**：给操作本身带上足够的信息（全局 ID、因果依赖），使得无论按什么顺序合并，结果都唯一。LWW 的办法是**把第二个问题删掉**：不比语义，只比时间戳，大的赢。

一句话对照

OT 用中心化换低开销和强意图；CRDT 用元数据换去中心和离线；LWW 用数据换实现简单。三者不是同一层的竞品，而是三种不同的「默认答案」。

## 1. OT：把操作翻译到新的顺序上

OT（Operational Transformation）是这个领域最老的一支。1989 年 Ellis 和 Gibbs 的 dOPT 是它的起点，Google Docs 让它成了工业界最眼熟的方案。

它的模型只有三样东西：文档状态 `S`、版本号 `r`、操作 `op`。每个操作都带着「我基于哪个版本」出发。服务端替所有人定序：它维护一条串行的操作历史，收到一个基于 `r` 的操作时，如果服务端已经跑到 `r+k`，就把它依次对着 `r+1 … r+k` 逐个做变换，得到 `op′`，应用，版本推进到 `r+k+1`，再广播出去。

TP1 · 变换的正确性条件

对任意并发的一对操作 `a`、`b`，必须存在 `a′`、`b′`，使得 `S · a · b′ = S · b · a′`——先应用 a 再应用「被 b 变换过的 b′」，等于先应用 b 再应用「被 a 变换过的 a′」。

直觉是：不管你先应用谁，只要把另一个「挪一挪」再应用，最终状态就一样。这个「挪一挪」就是 transform。它保证收敛，但只在**两个**操作之间成立。三个以上并发时还需要 TP2（多次变换的顺序一致性）——这是 dOPT 之后被反复修补的地方，也是 OT 实现最容易埋雷的地方：**错误不会在单测里暴露，只会在某次三方并发时让两个副本悄悄分叉**。

把变换规则摊开看，格子并不多。下面是文本编辑最常见的两种操作（`insert(i,s)` 在第 i 个字符前插入，`delete(i)` 删除第 i 个字符）：

| a（后来的） ＼ b（先应用的） | `insert(j, t)` | `delete(j)` |
| --- | --- | --- |
| `insert(i, s)` | i < j 保持 i；i > j 变 i+1；i = j 时按 clientId 定序，被排到后面的那个 +1 | j < i 变 i−1；j ≥ i 保持 i |
| `delete(i)` | j ≤ i 变 i+1；j > i 保持 i | i < j 保持 i；i > j 变 i−1；i = j 时是 no-op |

注意 `i = j` 那一格：**它不是数学问题，是产品决策**。两个人同时往同一个位置打字，谁的字在前？常见做法是比 replicaId，保证所有副本算出的答案一致。这也正是 OT 的好处——这个决策是显式的、可测的、可以按产品需要改的。

但这张表只有两种操作。完整的变换矩阵有 T² 个格子，每加一种操作（格式化、批注、表格结构、图片）就要补一行一列，每个格子都要证明它对所有边界成立。这是 OT 最大的隐性成本：**复杂度随操作类型平方增长，而正确性没有任何编译器能替你检查**。

{{< fig "diagrams/02.svg" "OT 的一次完整往返：服务端变换一次，客户端再变换一次" >}}

代价清单可以列得很短，但每一条都很硬：

- **中心节点**：单点，也是容量上限。文档要按「一个文档一个会话进程」切分，文件大到一定程度就得拆。
- **变换矩阵**：如上，T² 个格子，每个都要证明。
- **历史**：服务端必须保留从最慢客户端版本起的全部操作。GC 的前提是所有客户端都确认过某个版本——一个长期离线的客户端会把整条历史钉住。
- **离线**：离线太久、历史被裁掉，客户端回来时只能整篇重新同步。这是 OT 最硬的短板。
- **客户端复杂度**：要维护待确认队列，并对队列里的每个操作做变换；收到远端操作时还得知道自己哪些本地操作已经发出去、哪些还在路上。

换来的是三样东西：元数据极小（一个操作就是「插入/删除 + 位置」），意图可以做得很细（每条变换规则都是可测的产品决策），服务端是唯一真相（权限、审计、限流、回放全在一个地方）。

所以 OT 的适用面其实很清楚：**有一个天然的中心、文档很大、并发很高、元数据开销敏感、而且不需要长离线**。Google Docs 基本上全中。

## 2. CRDT：把「顺序」从算法里删掉

CRDT（Conflict-free Replicated Data Type）走的是反方向：既然定序这么贵，那就别定序。做法是给每个操作配上足够的信息，使得**无论按什么顺序、收到几次、收到哪一部分，合并结果都唯一**。

数学要求很简洁：合并函数必须满足三条代数性质。

| 性质 | 含义 | 它替你挡掉了什么 |
| --- | --- | --- |
| 交换律 | `merge(a, b) = merge(b, a)` | 消息到达顺序任意 |
| 结合律 | `merge(merge(a, b), c) = merge(a, merge(b, c))` | 消息可以分批、可以被中间节点转发 |
| 幂等 | `merge(a, a) = a` | 消息可以重复投递 |

三条一满足，强最终一致（strong eventual consistency）就是定理，不是祈祷：任何两个收到同一组更新的副本，状态必然相同。注意「同一组更新」这个前提——CRDT 不保证所有副本同时一致，只保证「在你看到的东西一样之后，结果一样」。

实现上有两种形态。状态型（CvRDT）在副本之间传整个状态，merge 求并：抗丢包、抗重复、抗乱序，代价是状态可能很大，于是有了 delta-state 变体（只传增量，但合并仍是状态合并）。操作型（CmRDT）传操作，要求恰好一次、因果有序投递：消息小，但对传输层有要求。

从最简单的数据类型到最难的，难度是一条陡峭的曲线：

| 数据类型 | 合并方式 | 典型用途 |
| --- | --- | --- |
| LWW-Register | 取时间戳最大的那个值 | 配置、状态位、presence |
| G-Counter / PN-Counter | 每个副本一个计数，求和（差值） | 点赞数、库存扣减 |
| G-Set / 2P-Set / OR-Set | 并集 / 删除优先 / 添加优先 | 标签、群成员、封禁名单 |
| 序列（text / list） | 见下文 | 正文、代码、表格列 |

真正难的只有最后一行，原因一句话：**位置不能是索引**。

「在第 5 个字符后插入」这句话在并发下没有意义——别人在你前面插了一个字符，你的 5 就指向别的地方了。所以序列 CRDT 必须把位置表达成「相对于某个元素」，而那个元素要有全局唯一的 ID。

RGA（Replicated Growable Array）是最容易讲清的一种。每个字符是一个节点，带一个全局唯一 ID（通常写成 `(副本, 序号)`）和一个「插在谁后面」的引用。插入就是新建一个子节点；同一个父节点下的并发插入，兄弟之间按 ID 全序排；遍历这棵树就是文档顺序。

删除不是删节点，是打**墓碑**（tombstone）。原因很实际：并发的插入可能还把这个字符当作锚点，真删掉，那个插入就无处安放。

{{< fig "diagrams/03.svg" "RGA：ID、锚点引用与墓碑，以及它们如何线性化成同一份文本" >}}

其他几种序列 CRDT 的取舍，一句话各自记一下：

- **Logoot / LSEQ**：给每个位置一个稠密有序的标识符，任意两个之间总能再插一个。好处是插入不依赖墓碑；坏处是标识符会越插越长，而且交错严重。
- **YATA（Yjs）**：每个元素记录左右两个 origin，整合时扫描解决冲突。工程上最成熟的一种，元数据紧凑、二进制编码、生态完整。
- **Fugue**：把「交错」形式化，追求最大不交错（maximal non-interleaving），是这几年比较有影响的一个改进。

交错（interleaving）值得单独说一句，因为它是文本 CRDT 最丢人的一类 bug。基础 `ab`，A 在 a 后插入 `12`，B 在 a 后插入 `34`。期望是 `a12 34 b` 或 `a34 12 b`——两个人各自的一串保持连续。朴素的 RGA 可能给出 `a 1 3 2 4 b`，两个用户的字符互相穿插。在文本上，这就是乱码。

代价清单：

- **元数据**：每个字符一个 ID，加上引用和墓碑位。Yjs 靠二进制结构压到每字符几字节，Automerge 用列式编码——但它仍然比 OT 的「位置 + 内容」贵一个量级。
- **墓碑**：删得越多，结构越大。GC 需要「因果稳定」（所有副本都见过这次删除），实际系统经常不做，靠定期快照重启。
- **可调试性**：二进制 update，抓包看不懂，得专门写可视化工具，否则线上出问题只能靠猜。
- **语义边界**：CRDT 保证的是「合并正确」，不是「语义正确」。两个人同时改标题，一个整段换成 A，一个把段中某个词换成 B，合并结果在字符层面完全合法，在人看来可能是胡话。

最后这一条，正是 LWW 出场的地方——不是因为 LWW 更聪明，而是因为**在某些粒度上，「合并」本身就是错的问题**，这时候「挑一个赢」反而是对的。

## 3. LWW：不解决冲突，取消冲突

LWW（Last-Write-Wins）的做法简单到不像一种算法：每次写带一个时间戳，合并时取最大的那个。

它当然是合法的 CRDT——`max` 满足交换、结合、幂等。所以准确地说，**LWW 不是与 OT、CRDT 并列的第三种算法，它是 CRDT 里的一个寄存器类型（LWW-Register），也是元数据最少的那个**。它把整个合并问题压缩成一次整数比较：无历史、无结构、无协商。

时间戳从哪来，决定了它会怎么错：

- **物理时钟**：直接读本机时间。最省事，也最容易被骗——手机漂移、NTP 回拨、时区配错、虚拟机暂停，都能让时间倒流。
- **Lamport 时钟**：只保因果，不反映真实时间。它回答的是「谁在谁之后被看见」，不是「谁在几点写的」。
- **HLC（混合逻辑时钟）**：物理时间 + 逻辑计数。既保因果，又贴近墙钟，是目前工程上的默认选择。

{{< fig "diagrams/04.svg" "时钟偏斜如何吃掉一次因果上更晚的写，以及三种时间戳的补救边界" >}}

关键区别在这里：如果 Bob 是在**看见** Alice 的改动之后才写的，这两次写就不是并发关系，Bob 的必须赢——这跟时间戳大小无关，这是因果。用物理时钟做 LWW，会把这种「因果上更晚的写」一起丢掉。HLC 能修这一半：它保证「看见过就一定更大」。但它修不了另一半——**两个真正并发的写，仍然会被静默丢掉一个**，而且用户看不到任何提示。

所以真正的问题不是「用不用 LWW」，而是**一条记录有多大**。这是 LWW 唯一真正的旋钮：

| 粒度 | 等价于 | 并发的代价 |
| --- | --- | --- |
| 整篇文档一条 | 全文覆盖 | 一个人的整段工作消失 |
| 一个对象一条 | 属性整包覆盖 | 改 A 属性会冲掉并发的 B 属性 |
| 一个字段一条 | LWW-Register | 只有同字段并发才丢，通常可接受 |
| 一个元素一条 | LWW-Element-Set | 只有并发增删同一元素才丢 |

粒度越细，冲突越少，元数据越多。这条曲线就是 LWW 的全部工程学——它没有算法上的深度，只有建模上的判断。

Figma 是这个旋钮的教科书案例。据其工程博客，他们评估过 OT 和 CRDT，最后选的是**每个 (对象, 属性) 一条 LWW，加一个单写者的服务端**：两个人同时改同一个矩形的 fill，后到的赢；一个人改 fill、另一个人改 width，两个都保留。设计文件的属性级冲突本来就少，而且改错了立刻看得见（设计师会再改一次），所以「丢失更新」在这个域里几乎不构成问题。

有意思的是，他们并没有把 CRDT 全部扔掉，而是留下了两件东西：**对象 ID**（不用数组下标定位元素，并发插入不会互相顶掉）和 **fractional indexing**（子元素顺序用两个邻居之间的分数表示，任意两个之间都能再插一个）。也就是说，LWW 负责属性、类 CRDT 的标识负责结构——两个粒度用两套机制，各管各的。

反例是集合。LWW-Element-Set 用一个时间戳决定某个元素在不在集合里，两个人对同一个元素并发操作会互相覆盖。OR-Set 用唯一 tag 解决：每次 add 带一个新 tag，remove 只移除自己看见的那些 tag，并发的 add 永远不会被误删——这就是「添加优先」语义。选 add-wins 还是 remove-wins 是产品问题：购物车要 add-wins，封禁名单要 remove-wins。

**LWW 合适的地方**：配置、开关、状态位；presence、光标、在线状态（本来就只关心最新值，而且不该持久化）；单调覆盖的 UI 状态（主题、折叠、最后阅读位置）；单写者场景（其实没有并发，LWW 只是给重放提供了幂等）。

**LWW 是灾难的地方**：文本正文（整段消失）；列表与集合（元素消失且无提示）；需要审计的字段（谁改的被覆盖，追不回来）；任何用户会问「我刚才写的东西去哪了」的地方。

三个问题

每次有人提「用时间戳取最新就行」，先问三句：并发的那次写，怎么让用户知道它没了？时钟错了怎么办？这条记录里到底装了几个人多少工作？

## 4. 放在一起看

先把分类说清楚，因为这是最常见的误解：「OT / CRDT / LWW 三选一」这个说法本身就不成立。

{{< fig "diagrams/05.svg" "分类学：LWW 位于 CRDT 之下，而不是与它并列" >}}

OT 和 CRDT 是两种**合并机制**——一个靠中心定序加变换，一个靠代数性质。LWW 则是 CRDT 里的一个**数据类型**。真正正交的两个维度是：**要不要中心节点**，以及**冲突的粒度有多细**。按这两个维度切，市面上的方案基本都能落进四个格子里。

{{< fig "diagrams/06.svg" "按「要不要中心」与「冲突粒度」切的四个格子" >}}

| 维度 | OT | CRDT（序列） | LWW |
| --- | --- | --- | --- |
| 收敛保证 | 依赖实现正确（TP1 / TP2） | 数学保证（交换 / 结合 / 幂等） | 数学保证 |
| 意图保留 | 强，规则可定制 | 中到强，取决于类型设计 | 无 |
| 中心节点 | 必须有 | 不需要 | 不需要 |
| 离线编辑 | 弱，受历史窗口限制 | 强，时长几乎无上限 | 强 |
| P2P / 端到端 | 难 | 天然 | 天然 |
| 单次更新开销 | 极小（op + 版本号） | 中（ID + 引用 + 墓碑） | 极小（值 + 时间戳） |
| 状态增长 | 与活跃副本数和窗口相关 | 与文档大小成正比 | 几乎为零 |
| 冲突可见性 | 不可见，但结果通常对 | 不可见，结果通常对 | 不可见，结果可能错 |
| 主要风险 | 变换函数写错，副本静默分叉 | 元数据膨胀、GC 停顿 | 静默丢写 |
| 典型实现 | Google Docs、ShareDB、ot.js | Yjs、Automerge、Fugue | Firestore、Cassandra、Figma 属性 |

一句话判断：OT 用**中心化**换低元数据和强意图；CRDT 用**元数据**换去中心和离线；LWW 用**数据**换实现简单。三者都不便宜，只是把代价记在了不同的账本上。

还有一个常被忽略的维度：**冲突可见性**。三者都会让冲突然消失——OT 和 CRDT 是把它化解掉，LWW 是把它藏起来。用户能感知的差别不在「有没有冲突」，而在「冲突之后我还能不能找回我的东西」。这也是为什么真正成熟的产品会在算法之上再叠一层：操作历史、版本回滚、误删恢复。算法保证一致性，产品保证可解释性。

## 5. 叠加：CAS 装在里面，LWW 装在外面

前面几节把它们拆开看，但工程里很少只用一种。最常见的组合是在 LWW 里套一个 CAS：对外的语义还是「时间戳大的赢」，对内的更新用 CAS 保证不丢。

这件事很容易被说反。**服务端之所以是唯一写者，是拓扑决定的，不是 CAS 造的**——一个进程、一份状态、一条到达顺序，这才有了全序。CAS 只负责把「读当前值 → 比较时间戳 → 发布新值」这三步在并发下压成一步。没有它，两个 handler 会同时读到 v7、同时认为自己是 v8；有了它，只有一个能成功，另一个退回去重读。

### 5.1 两层各管一件事

| | 内层 CAS | 外层 LWW |
| --- | --- | --- |
| 回答什么 | 这次写能不能落地 | 最终显示哪个值 |
| 失败长什么样 | 一次 false，重来 | 没有失败，只有覆盖 |
| 谁看得见 | 只有服务端 | 客户端——他收到的是赢家 |
| 代价 | 一个重试循环 | 输掉的写永久消失 |

由此有一个推论：**CAS 暴露在接口上，客户端看到 409；CAS 藏在服务端里，客户端只看到 200 和一个赢家**。同一个内核，两种产品语义。`If-Match` / ETag 是前者，Figma 的多人协作是后者。

Figma 的形状值得单独说：每个文件一个单写者进程，进程内天然有全序，不需要任何分布式协议；属性级 LWW 给细粒度覆盖；CAS 和锁只用来守住进程内那几个共享结构。三层各司其职，谁也没替谁干活。

{{< fig "diagrams/07.svg" "一次并发写的完整路径：内层 CAS 定序，外层 LWW 判胜负，客户端只感知上面那层" >}}

### 5.2 三道门，不是一道

「这次写能不能成功」常被当成一个问题，其实是三道并列的门：

| 门 | 判什么 | 谁设的 | 失败的样子 |
| --- | --- | --- | --- |
| 粒度门 | 是不是同一个 CAS 单元 | 数据模型 | 不是同一个单元，根本没有冲突 |
| 戳门 | 新戳是否大于单元当前戳 | LWW | 落败但不报错，请求照样成功 |
| 版本门 | baseVersion 是否等于当前版本 | 乐观锁 | 409，写被拒绝 |

三个常见误读，都出在把这三道门当成一条因果链：

- 「B 拿着旧版本去改别的字段也能成功，是因为它的时间戳更新」——不。是因为它改的是**另一个 CAS 单元**，粒度门就没关上过；而且服务端根本没检查 version，版本门压根没装。戳只决定同一个单元里留谁的。
- 「CAS 保证了写操作的顺序」——CAS 保证的是「每一次读-比-写在一个确定时间点生效，所以任意两次写不会同时生效」。全序是它的推论，而且是**到达序**，不是戳序。
- 「LWW 保证写尽可能不冲突」——「尽可能」是启发式的口气。LWW 的保证是硬的：必然收敛、必然有唯一赢家、冲突必然不暴露。

版本门装了会怎样？想象一个文档级的版本号 `If-Match: 7`：A 和 B 各改一个完全不同的字段，只要两人都基于 v7，第二个提交的照样 409。粒度门开着，版本门照样能把人挡在外面——**这两道门不是同一件事，装哪个是产品决策**。

### 5.3 时间戳是三个字段

`1002.0@B` 这行字常被读成「把 B 设成 1002」或「1002 这一刻操作 B」，都不是。

- `physical`：物理毫秒。真实的 HLC 是 13 位，例子里的 1002 只是演示用。
- `logical`：同一毫秒内的第几次事件。它不是小数位——`1002.10` 是「物理时间 1002 的第 10 个事件」，不是 1002.1。
- `replicaId`：产生这个戳的副本。它标的是「谁写的」，不是「写的哪个元素」。

排序规则只有一条：先比 `physical`，再比 `logical`，最后比 `replicaId`。

第三个字段存在的理由不是「标明作者」，而是**让全序没有相等项**。少了它，两个副本在同一毫秒写同一个字段会拿到相等的戳，各自按自己的到达顺序选赢家，然后分叉。HLC 的 `observe` 负责另一半：看见过的一定更大，因果不会倒流。

### 5.4 ack 是会被撤销的

这是 LWW 和 OT 最深的一道缝。

OT 的 ack 意味着「你的操作进入了唯一的历史，位置是第 X 个」。这个操作不可撤销，后来的操作只能叠加在它旁边。LWW 的 ack 意味着「你的值在这一刻最大」，它随时可能被一个更大的戳替换掉。

所以「A 写入成功，然后对状态丢失无感」不是 bug，是这套语义的默认行为。要补，得把三件事分开：

- **检测**：服务端知道吗？知道。覆盖就发生在它的 CAS 循环里，被替换的是 `cur.value()`。
- **送达**：能送到 A 手上吗？在线靠广播，离线靠日志补拉。
- **落账**：A 已经关掉编辑器了呢？没对象可通知，只能留记录，等他下次打开。

多实例会把这件事变糟。A 写 east 返回 200，B 写 west 返回 200，两个实例都没看见对方，覆盖发生在复制的那一刻。**检测点从「写入时」漂移到了「合并时」**——所以合并必须走和写同一条带日志的路径，否则异步复制一定把可观测性丢掉。

补救从轻到重：

1. ack 里带上 `displaced`：你这次写顶掉了谁。这让「我覆盖了别人」可追溯。
2. 广播带 `replacedStamp`，客户端自查被顶掉的是不是自己。
3. 日志加 seq，支持 `since(lastSeen)` 补拉。这是唯一能覆盖「离线期间被顶」的手段。
4. 保留被覆盖的值，做版本历史。只通知「你被覆盖了」是最差的体验——用户知道了也无能为力。
5. 换语义。审计、合同、金额这类不能静默丢失的字段，不该用纯 LWW。

还有一个陷阱：如果给 A 一个「恢复我的 A1」按钮，它只能用新戳重放，于是又覆盖了 B；B 再恢复，再覆盖 A。恢复必须是显式的人类动作，或者干脆用 CRDT 让两个值都留下。

## 6. 工程里真正咬人的七件事

选完算法只是开始。下面这些事，选哪家都会遇到，而且它们比算法本身更常导致线上事故。

### 6.1 快照与压缩

CRDT 的更新不能无限追加。Yjs 用 `encodeStateAsUpdate` 把当前状态编码成一个快照，之后就可以丢弃之前的增量；OT 的服务端也要在「所有在线副本都确认过某个版本」之后裁掉历史。没有这一层，内存和存储会随会话时长线性增长——一个开了几个月、每天几十人编辑的文档，加载和合并都会慢到不可用。

### 6.2 离线重连

这是 CRDT 最实在的优势，也是最容易被低估的复杂度。OT 客户端离线太久，服务端历史已被 GC，回来只能整篇拉取；CRDT 客户端把本地 update 直接喂进去 merge 就行。但「merge 就行」有个前提：本地与服务端对文档结构的理解不能漂移。所以真正要设计的是**离线期间的结构变更怎么兼容**，而不是「怎么合并」。

### 6.3 undo / redo

文本 CRDT 里的撤销不是「反向应用操作」。你撤销的应该是「你自己」的改动，而且不能把别人同时做的改动一起撤掉。Yjs 的 UndoManager 靠 origin 追踪每个操作的来源，只回滚本地的；OT 里一般用本地栈，撤销操作也要再走一遍变换。两者都不支持「撤销别人」——这不是技术限制，是产品边界。

### 6.4 presence 与文档分离

光标、选中、在线状态、正在输入，这些是高频、易失、丢了无所谓的。绝对不要写进文档 CRDT 或操作历史：它们会污染元数据，也会让「历史」失去意义。单独走一个 ephemeral 通道（Yjs 的 awareness 协议就是干这个的），断了就当没有。

### 6.5 权限

合并算法只保证收敛，不保证「这个用户有权改这段」。权限必须在写入路径上做，而且要保证合并之后仍然可判定：如果 A 无权改第 3 段，而 B 的并发操作把第 3 段移到了别处，合并后 A 的越权改动还能被识别出来吗？这是很多 CRDT 系统最容易被忽略的洞——**它们把「合并」当成了「授权」**。

### 6.6 收敛测试

收敛 bug 是静默的：两个副本看起来都正常，只是内容不同，而且往往要在几百次并发之后才复现。可靠的测试方法基本只有一个：**随机生成并发操作序列，对任意交错执行，断言最终状态哈希相同**。Yjs 和 Automerge 的测试套件核心就是这个。如果你的协同系统没有这类 fuzz 测试，那它实际上等于没有测试。

### 6.7 安全

CRDT 的 update 是结构化二进制，恶意客户端可以构造指数级膨胀的更新——超深的引用链、超长的墓碑链、巨量的并发兄弟节点。合并过程会把它当真，然后吃掉全部内存。所以要限大小、限深度、限节点数，并且把合并放进可中断的沙箱或独立进程，而不是在主线程里 `merge` 一个来路不明的 blob。

## 7. 多实例：写者从一个变成一群

上一节的服务器只有一个进程，一把锁就够。真实系统里你至少跑三个实例——高可用、多可用区、滚动发布——客户端也真的会打到任意一个。这时候「唯一写者」是一句需要兑现的话，不是一句描述。

兑现的方式只有两种形状：

- **都能接写，但不能都定序。** 所有实例都接收请求，但同一个分片只有一条日志，写必须经 leader 提交。这是 Raft 系存储、以及所有「把 LWW 当接受准则」的服务端的形状。
- **都能接写，也都独立合并。** 服务端不判断顺序，只负责存快照、转发增量。这是 Yjs / Automerge 的服务端的形状——它退化成了一台中继。

两种形状的代价不在一个地方：前者的复杂度在写入路径（提案、多数派、选主），后者的复杂度在合并与 GC。

还要先分清「多实例」指的是什么。按文档分片之后，每个分片本来就只有一个写者，分片之间互不相干——Figma 是每个文件一个进程，文件与文件之间没有关系。真正难的是**同一个分片**上的多实例。

{{< fig "diagrams/08.svg" "多实例下的一次写入：转发、提案、提交、广播，以及超时重发落到别的实例上时的去重" >}}

图里只有一处新东西：写要经过 leader，但**客户端不必知道谁是 leader**。它连的是实例 A，A 转发；A 也可能在下一分钟变成 leader，或者客户端重连时直接连到 B。对客户端而言，这仍然是一次「发出去、拿到 200、然后收到广播」的调用。

相对单实例版，有三处必须改。

**一、去重必须放进状态机。** 「同一个请求只处理一次」不能靠在入口处记一张内存表：重试可能落到另一个实例，也可能落到刚选出来的新 leader。判定要在 apply 里做——日志里已经出现过 `(clientId, clientSeq)`，就直接返回第一次的结果，不再提案。

顺序反了会怎样？真正的坏剧本是**重试超车**：用户先发 X，ack 丢了；用户接着发 Y，成功；X 的重试这时才到，拿到一个新时间戳，把 Y 顶掉。用户看到的是自己刚删掉的旧值又跳了回来。去重进了状态机之后，X 的重试命中第一次的记录，直接返回，不会二次提案。

**二、快照必须带上那张去重表。** 日志截断之后，去重表是唯一还记得「这个请求来过」的地方。漏了它，截断后的第一次重试就会重新提案、拿到新时间戳，照样超车。这个 bug 只在「截断 + 重试」的交集里出现，正常测试跑一辈子也碰不到。

**三、游标用 index，不用时间戳。** 单机版里没有别的坐标，时间戳既是版本也是位置；有了复制日志之后，index 才是「第几条」这个问题的唯一答案，时间戳只回答「谁的值更新」。用时间戳当游标还会踩一个坑：某个副本的 highWater 可能比另一个副本的真实进度高，客户端换实例之后就会静默漏数据——不报错，只是少了一段。

两条边界也跟着变了。

**ack 变强了一点，但没有变性质。** 多数派持久化之后才回 200，所以 ack 不会再因为「这个进程崩了」而消失；但「后来的写能覆盖它」这一点没变——上一节说的「ack 可撤销」依然成立，只是撤销它的从一台机器变成了一个集群。

**读要先说清要哪一种。** 线性一致读（read-index，或者 leader 持租约）、会话一致读（客户端带一个 `minIndex`，任意副本都等 apply 追到再返回）、陈旧读（就近返回，可能落后）。协同编辑产品绝大多数用第二种：用户能接受「我刚写的东西在别人那里晚 50ms 出现」，不能接受「我刷新一下，自己的编辑没了」。

代价也清楚：写延迟变成一次多数派往返（同区域多可用区通常几毫秒到十几毫秒，跨区域就是几十上百毫秒）；可用性变成多数派存活（三个实例挂两个就写不进去，哪怕客户端还连着活着的那个）；选主的那几百毫秒里写不可用。协同编辑通常扛得住，因为客户端本来就把操作先排进本地队列。

这一节所有的复杂度，都来自「必须先定序、再合并」。如果算法本身不需要定序，整节可以删掉。

## 8. Yjs 与 Automerge

前七节讲的是怎么自己造。真做产品时，绝大多数人不会自己写 CRDT，而是在 Yjs 和 Automerge 之间选。

两个都是序列 CRDT，都不需要中心定序——所以服务端可以是上一节的第二种形状：一台中继。两者都脱胎于 RGA 那一套「按锚点插入」，区别在锚点怎么记：Yjs 的 YATA 给每一项记左右两个锚点（`origin` / `rightOrigin`）；Automerge 的位置来自 opId，谁覆盖谁则看后继集合。

但选型时分不出胜负的地方不在这里。两者的真正分界线是**什么算文档**：

- **Yjs：文档就是当前结构。** 一条 Item 链表，删除的内容会被回收成占位符。历史不是要保留的东西。
- **Automerge：文档是变更的历史。** 当前状态只是 change DAG 的一个投影，所以你可以把文档检出到任何一个历史点。

{{< fig "diagrams/09.svg" "两种真源：左边 Yjs 的文档是一条带锚点的 Item 链，右边 Automerge 的文档是 change 组成的哈希图" >}}

| | Yjs | Automerge |
| --- | --- | --- |
| 序列算法 | YATA，每项记左右锚点 | op-set 按 opId 排序，RGA 系 |
| 标识 | `(client, clock)` | `(counter, actor)` |
| 存什么 | Item 链 + 删除后的占位 | 列式存储的 op-set + change 哈希图 |
| 删除 | 内容可回收（`doc.gc`） | op 永久留在历史里 |
| 同步 | 交换 state vector，补差集 | 交换 change 图，缺哪支补哪支 |
| 历史能力 | 不内建，要自己记 update | 内建：`getHistory` / `diff` / 按哈希检出 |
| 体积 | 增量很小；长会话要自己做快照 | 随历史单调增长，可 compact |
| 形态 | TypeScript 为主，另有 Rust 端口（y-crdt） | Rust 核心 + WASM 绑定 |
| 生态 | y-websocket / y-indexeddb / y-prosemirror / y-monaco | automerge-repo 及其存储、同步适配器 |

三个维度值得展开。

**同步协议。** Yjs 的同步是「我有哪些 clock，你补给我没有的」——一条 state vector 换一段差集，消息大小随客户端数走。Automerge 的同步是「我有哪些 change 哈希」，能精确到分支，代价是协商本身要传的东西随变更数走。两边都是「传缺少的」而不是「传全部」，但常数差得不少。

**体积与历史是同一件事。** Yjs 的 GC 意味着删掉的东西真的没了。要支持版本历史，你得在外面存 update 或者定期打快照——这活不白干，但也确实是你自己干。Automerge 天生就是一本账，代价是文档随历史一直长，需要 compact。所以「谁更省」得先问「你要不要那本账」：不要，Yjs 的历史就是纯开销；要，Automerge 那边是白送的。

**交错。** 两者对同一位置的并发插入都不是零交错——YATA 的双锚点降低了概率，但在特定并发形状下仍然会交错（Fugue 那篇论文专门对比过 Yjs 与 Automerge，两者都不为零）。生产上的缓解手段一致：把一次连续输入合成一个操作，而不是一个字符一个操作。

所以选型不是比算法，是回答三个问题：

1. **你要不要历史？** 要做版本、审计、分支、时间旅行，Automerge 白送；不要，Yjs 更轻。
2. **文档多大、并发多密？** 长文档、高频输入、白板这类场景，Yjs 的体积优势会被放大；历史越长，Automerge 那份账单越显眼。
3. **端上跑什么？** 两者都能在浏览器里跑，但 Yjs 在 JS 里是原生的，Automerge 要过一层 WASM 边界。

一句话：**Yjs 优化的是「把状态同步得最便宜」，Automerge 优化的是「把历史保存得最完整」**。这不是快慢之争，是账本记在哪的问题。

也正因如此，上一节那些工程事项在两边长得不一样：快照压缩在 Yjs 是 `encodeStateAsUpdate`，在 Automerge 是 compact；撤销在 Yjs 靠 `UndoManager` 按 origin 过滤，而在 Automerge 里，你更可能是直接拿历史做「回到某个版本」——那是另一类产品功能，不是快捷键。

## 9. 一页速查

把上面所有内容压成一张表，按「你要做的东西」查：

| 你要做的东西 | 默认选择 | 关键理由 |
| --- | --- | --- |
| 多人实时编辑文本，服务端可定序、元数据敏感 | OT | 每个字符不背 ID，历史由服务端兜底 |
| 多人实时编辑文本，要离线 / P2P / 端到端加密 | CRDT 序列（Yjs） | 无中心，离线时长几乎无上限 |
| 结构化表单 / 画布的属性 | 字段级 LWW + 服务端校验 | 冲突粒度天然细，实现成本最低 |
| 计数、集合、开关 | PN-Counter / OR-Set / LWW-Register | 别用整条记录的 LWW 去覆盖一个集合 |
| presence / 光标 / 正在输入 | LWW + 不持久化 | 只关心最新值，本来就不该进历史 |
| 需要知道「谁覆盖了谁」 | LWW + 覆盖日志 + 版本历史 | ack 只承诺「此刻被接受」，不承诺「不被撤销」 |
| 多实例部署、要读写分离 | 按文档分片 + 每片一条复制日志 | 顺序由日志给，实例只负责转发 |
| 不想自己写 CRDT | Yjs（要省） / Automerge（要历史） | 分界线是「历史算不算文档的一部分」 |
| 权限、审计、计费 | 服务端权威，不进 CRDT | 合并保证不了授权，也保证不了可追溯 |

最后回到开头那个问题：协同编辑难的不是「合并」，而是**决定什么该被合并、什么该被问、什么该被拒绝**。

三种算法是三种默认答案：OT 默认「中心说了算」，CRDT 默认「结构说了算」，LWW 默认「时间说了算」。产品真正要设计的，是这些默认答案出错时的兜底——用户能不能看见冲突、能不能找回被覆盖的内容、能不能在事后解释「为什么最后是这个结果」。

算法决定副本会不会分叉；产品决定用户会不会骂人。这两件事经常被同一句「用 CRDT 吧」糊过去。
