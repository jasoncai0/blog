资产系统现在做的是「查得到」：结构化查询加向量召回，按需注入。它没做的是「越用越懂」：同一批素材被反复重新理解，品牌约束散在多个节点里，跨项目的矛盾没人裁决。

[上一篇](/posts/llm-wiki.html)拆了 LLM Wiki 的机制：原件只读、页面由 agent 维护、摄入时写扩散、查询走目录、lint 定期修。这篇把它落到一个真实系统里：资产树、权限树、血缘、协同画布、设计 Agent。改造的难点不在页面怎么写，在权限、规模、成本这三件原文没展开的事。

## 结论先行

**结构**

1. **原件不可变。** 上传素材、生成产物、品牌资料按 sha256 落对象存储，版本只增不改。页面写坏可以整层重编，原件不能。
2. **Wiki 是资产树旁的派生层。** 不塞进树节点，单独存页面表，按 `asset_id` 关联。树管组织、权限、分发，页面管语义、关系、约束。
3. **页面类型固定七类。** 品牌、产品、项目、素材、风格、对比、约束，每类一个模板，front matter 走校验器，不允许自由发挥。
4. **双存储单向。** Postgres 是事实源，markdown 是投影。页面可以全量重建，禁止双向同步，否则一致性永远对不上。

**运行**

5. **写扩散按热度排队。** 单次上限 15 页，被引用多的资产先编译，冷资产延迟到被检索时再编。
6. **权限两层校验。** 编译时按 `acl_domain` 过滤素材，检索时再按租户、资源树、权限树校验；跨权限域不聚合，拆成多页。
7. **检索仍走目录第一跳。** 资产目录按租户、品牌、项目分层，向量只做候选扩展，不当事实源。
8. **巡检复用 Review Agent。** 规则引擎裁决冲突，模型只提议；工单分级，只对可回滚的结构问题自动修，事实性结论一律进人审。

## 现状：查询时组装

现有的资产层有五个部件：租户资源树（同一棵树承载 Brand、角色、产品，个人空间、团队空间、素材库复用同一模型）、权限树（资产、会话、团队空间共用一套鉴权）、血缘（记录生成来源、引用、编辑链路）、渐进加载（Discovery → Activation → Execution，按需逐级注入）、向量检索。

这套结构解决了「找得到」和「有权限地用」，但三个缺口在任务一多就暴露：

1. **语义不沉淀。** 同一张品牌图，这次理解成「新品主视觉」，下次理解成「活动物料」，两次结论都不写回结构。第 100 次任务还在重新理解同一批素材。
2. **跨资产矛盾没有裁决。** 品牌规范写主色是 `#1B4D3E`，某个旧项目页写 `#17453A`，检索各返回一半，模型自己权衡，最后两个任务用了两种绿。
3. **注入成本随任务涨。** 每次拼 3 条资产片段进上下文，片段之间没有关系，模型要自己判断谁和谁相关。加一条素材，就多一份重新判断的成本。

这不是检索问题。检索解决「找得到」，缺的是「编译过」：把素材里的实体、约束、关系，在入库时写成结构，查询时只读结构。

## 映射：原件、页面、规范、目录、日志

| LLM Wiki | 资产系统 | 存放 | 谁写 |
|---|---|---|---|
| raw sources | 资产原件：上传素材、生成产物、品牌资料 | 对象存储 + sha256 + 版本 | 运行时写一次，之后只读 |
| wiki 页面 | 资产页面：七类语义页 | `asset_page` 表 + markdown 投影 | 编译 worker |
| schema | 资产规范：页面模板、命名、引用、权限、矛盾规则 | 代码仓库，版本化评审 | 人，随迭代改 |
| `index.md` | 资产目录：租户 → 品牌 → 项目 | `asset_index` 物化视图 | 编译 worker |
| `log.md` | 资产操作日志：入库、编译、引用、回写 | `asset_oplog` 表，可导出 | 运行时事件 + worker |

映射不是逐字翻译。资产系统比个人 wiki 多三样东西：权限、血缘、高频写入。这三样决定了后面所有的设计取舍。

## 页面模型

七类页面，各自存一种稳定的判断：

1. **brand 品牌页**：定位、主色与辅色、字体、logo 用法、禁用示例、语气。一个品牌一页。
2. **product 产品页**：产品是什么、卖给谁、关键卖点、可用素材、和相邻产品的差异。
3. **project 项目页**：目标、时间、参与角色、产出物、复盘结论。项目结束后不删，转 archived。
4. **asset 素材页**：一张图或一段视频的 caption、尺寸、色板、可复用场景、来源与生成参数。
5. **style 风格页**：视觉语言的描述、参考图、适用与不适用的场景。跨项目复用最多。
6. **comparison 对比页**：两个品牌、两个风格、两个版本的差异表。查询产物回填的主要落点。
7. **constraint 约束页**：硬规则，比如「主标题必须留 24px 安全边」「禁止把 logo 放在纯红底上」。规则引擎直接读这一页。

front matter 是契约，不是注释：

```yaml
page_id: brand_acme
type: brand
tenant_id: t_1024
acl_domain: ["team_42", "project_88"]   # 所有被引用资产 ACL 的交集
asset_ids: [asset_9781, asset_9782]
lineage_edges:
  - {type: derived_from, from: asset_9781, to: brand_acme}
source_hashes: [sha256:9f2c..., sha256:41ab...]
version: 3
status: active            # 页面态：draft | active | stale | superseded | archived
last_verified: 2026-11-18
embedding_ref: vec_7f31
```

正文固定六段：定位、事实、约束、关联、矛盾、来源。关联用稳定 ID 的 wikilink，`[[asset:9781]]`，不用标题。标题会改，ID 不会。

血缘在页面里是投影，在边上才是事实：`derived_from`（由谁生成）、`references`（引用了谁）、`variant_of`（谁的变体）、`supersedes`（取代了谁）。反向追溯走边表，页面只展示一跳，避免渲染时递归爆炸。

权限取交集而不是并集。一个页面如果引用了两个权限域的资产，`acl_domain` 取两者交集；交集为空就不生成这一页，改成每个域各一页，再加一个不带内容的索引页。这条规则牺牲了「一页看全」，换的是不越权聚合。

## 四条链路

**摄入编译。** 资产入库事件进队列，去抖 30 秒合并同一批上传；worker 解析内容、抽实体、在目录里找命中页、决定 create/update/merge、写扩散、裁决冲突、更新目录与日志、写血缘边。超过 15 页就拆批，不硬写。

**检索注入。** 三档对应原来的渐进加载：Discovery 读目录，拿 3–5 个候选页和一句摘要；Activation 读整页，拿约束、事实、关联；Execution 才取原件细节（色值、字体文件、图片裁切）。每档都有 token 预算，超了就降档，不截断关键约束。目录这一跳的具体做法，站内 [目录即索引](/posts/asset-tree-progressive-retrieval.html) 已经拆过一遍。

**回写。** Agent 产物落画布，保存时发 `artifact.created`；引用关系（谁用了哪张图）作为 `references` 边回写；调用结果（哪个工具在什么输入下成功）进日志。回写触发增量编译，只更新受影响的页面。

**巡检。** Review Agent 原来扫画布，现在扩到资产页：孤儿页、断链、缺页（被引用但没建页）、过期（`last_verified` 超 30 天）、冲突（规则引擎判不了）、权限漂移（页面 ACL 与资产树不一致）、血缘缺口。规则先跑，模型只对可疑项提议，工单分级。自动修只碰补链、改状态、合并重复页这类可回滚动作，不改事实性结论。

## 页面状态

资产页有七个状态，和原文的草稿/有效/陈旧不完全一样，多了编译队列和权限复核：

`queued` 待编译 → `compiling` 编译中 → `draft` 待校验 → `active` 有效 → `stale` 陈旧 → `superseded` 被取代 → `archived` 归档。规则引擎判不了的冲突进 `review`，挂起等人裁决。

关键约束：`active` 是唯一会被检索优先命中的状态；`stale` 仍可读，但答案必须带冲突提示；`archived` 从目录移除，边表保留，反向追溯还能走。

## 接入设计 Agent 的七个改造点

按现有七层，逐层说改什么：

| 层 | 改造 | 交付物 |
|---|---|---|
| L0 模型层 | 编译、查询、裁判三档路由；编译走批处理模型，查询走低延迟模型，裁判走小模型加规则 | 路由配置与预算 |
| L1 上下文层 | 三档注入器：目录摘要 → 页面正文 → 原件细节；每档独立预算 | 注入 API，p95 ≤ 120ms |
| L2 资产层 | 新增页面表、编译队列、目录物化视图、操作日志、页面级向量 | 迁移脚本与容量评估 |
| L3 能力层 | 五个 MCP 工具：`search_assets`、`read_asset_page`、`write_asset_page`、`ingest_asset`、`lint_assets`；Skill 描述指向页面 | 工具契约与权限声明 |
| L4 编排层 | 读路径钩子（目录第一跳）、回写钩子（产物事件）、编译去抖 | 灰度开关 |
| L5 评估层 | 巡检规则集、编译质量指标、工单看板 | 日报与告警 |
| L6 治理层 | schema 版本、页面模板、灰度、回滚、审计 | 发布流程 |

对 Agent 来说，变化最大的是 L3：以前它调 `search_assets` 拿片段，现在先调目录、再读页面、最后才取原件。工具数量没变多少，调用顺序变了，权限校验点从一次变成两次。

## TODO 分期

完整清单 26 项，含依赖、工时、验收，单独整理成文档。这里给分期和关键交付：

| 阶段 | 周期 | 关键任务 | 完成标准 |
|---|---|---|---|
| P0 契约与存储 | 2 周 | 页面 schema、原件不可变、资产事件表、页面表与投影迁移、ACL 字段 | 任一资产可追溯到原件哈希；跨租户读取单测全拒 |
| P1 编译链路 | 3 周 | 内容理解、实体链接、页面规划、写扩散执行器、冲突裁决、目录与日志 | 单素材 P95 ≤ 60s；重复摄入不产生重复页 |
| P2 检索与注入 | 3 周 | 分层目录、检索 API、页面向量、三档注入器、引用可解释 | 注入 token 降 30%；越权召回 0 |
| P3 回写与巡检 | 3 周 | 产物回写、引用边、巡检规则、工单分级、生命周期 | 页面巡检覆盖 100%；误报 < 10% |
| P4 接入与灰度 | 2–3 周 | 工具注册、读路径接入、Skill 指向页面、指标、回滚 | 5% 灰度 24h 无 P0；回滚 < 5 分钟 |

依赖关系是串行的：P0 的 ACL 字段不定，P1 的编译结果就没法落库；P1 的目录不产出，P2 的检索没有第一跳。想并行的只有 P3 的巡检规则和 P2 的注入器，前者只读页面，后者只读目录。

## 风险与取舍

| 风险 | 触发条件 | 对策 |
|---|---|---|
| 写扩散成本失控 | 批量上传、一个品牌几百张图 | 热度队列、30 秒去抖、单次 15 页上限、冷资产懒编译 |
| 结构错误放大 | 实体链接错一次，十几个页面引用 | 规则引擎先裁、模型只提议、diff 必看、每周抽样回读原件 |
| 权限泄漏 | 跨域引用、页面聚合多个项目 | ACL 取交集、为空拆页、编译与检索双点校验、审计日志 |
| 双写不一致 | 页面与资产树各自更新 | 单向投影、全量重建任务、按 `source_hashes` 校验 |
| 冷启动 | 新租户没有页面 | 模板兜底、懒编译、目录先返回原件摘要 |
| 页面膨胀 | 回填太多对比页 | 同类合并、单页 200 行上限、季度归档 |
| 编译延迟 | 高峰上传 | 异步队列、优先级、前端先给原件级结果 |

最需要提前想清楚的是权限。原文假设单用户本地目录，没有 ACL 概念；资产系统里一个页面可能引用三个项目的素材，交集为空时是拆页还是拒绝生成，要在 P0 就定，不能等到联调。

## 验收指标

1. **编译覆盖率**：新资产 24 小时内生成页面 ≥ 95%。
2. **页面新鲜度**：`last_verified` 中位数 ≤ 14 天，超过 30 天的页面进巡检工单。
3. **检索命中率**：同一批任务，top-5 命中相关页面的比例比纯向量基线高 15%。
4. **注入成本**：单任务注入 token 降 30%，p95 延迟不超过 120ms。
5. **一次通过率**：设计任务一次通过率提升 8 个百分点。
6. **巡检质量**：误报率 < 10%，自动修复回滚率 < 2%。
7. **权限**：越权召回 0，跨租户聚合 0。
8. **可回滚**：关闭 wiki 层后 5 分钟内退回纯检索链路。

## 和原文的四个偏离

1. **写者无人监督。** 原文是人选源、agent 写、人读；这里是运行时事件触发写入，没人逐条看。所以要队列、去抖、预算、页数上限，把「写」变成可限流的工序。
2. **权限是硬约束。** 页面继承资产 ACL，编译时过滤、检索时再校验。原文的「wiki 全量可读」在多租户里不成立。
3. **规模起点更高。** 单租户可能几千资产，目录一页读不完。分层目录加向量兜底，但第一跳仍然是目录，不然就退回 RAG。
4. **页面同时给人读和给 agent 读。** front matter 必须是机器契约，字段缺失直接校验失败；正文可以给人读，但结构要能被解析。

原文的 wiki 是个人知识库，坏了重来成本低。资产 Wiki 是生产系统的一部分，一次越权或一次错误聚合的代价，比少几个页面大得多。

先做 P0 和 P1，用 100 个真实资产验证编译质量，再谈接入。编译质量不过关，接进去只会让设计 Agent 更快地引用错东西。
