## 一、定位与边界

这五道是地基。RAG、微调、长上下文、Agent 自主搜索，四个东西经常被混着答，混着答就露馅。

### Q1 什么是 RAG？一次完整请求经过哪些步骤？

RAG 是检索增强生成：生成之前先从外部知识库取出相关内容，把内容和问题一起交给模型，让答案建立在证据上。判断一个系统是不是 RAG，看答案有没有外部证据支撑，不是看它有没有接数据库。

完整链路分两段。离线阶段把文档解析、切块、向量化、连同 metadata 入库；在线阶段把问题做改写和指代消解，向量化后召回候选，精排筛掉噪音，按预算拼成 prompt，生成时要求引用来源。两段的失败模式不同：离线错了是知识进不去，在线错了是该用的知识没用上。

常见追问：
1. **「G」在哪一步？** 在最后。没有生成环节，前面两步只是搜索，不是 RAG。
2. **离线阶段能省吗？** 不能，但可以异步。文档一变就重建那一篇的索引，不用全量。

### Q2 RAG 到底解决什么问题？

三件事：知识时效、私有知识覆盖、幻觉。三者的根源是同一个，知识被固化在模型参数里，训练截止之后就冻结了。

幻觉要单独说一句：它是知识缺失的副产品，不是独立问题。模型没有依据时才会编，给了依据仍可能编，但那是另一类问题（生成不遵循），解法完全不同。把这两个混成一件事，就会得到「加一句 prompt 就好了」这种答案。

常见追问：
1. **用了 RAG 幻觉就没了吗？** 不会。检索没召回，模型照样编；召回对了，模型也可能超发挥。
2. **为什么不直接再训练一次？** 成本和周期是一方面，更关键的是没法溯源，也追不上每周都在变的知识。

### Q3 RAG 和微调怎么选？

微调改参数，解决「怎么说」：输出格式、行业语气、固定的推理习惯。RAG 不改参数，解决「说什么」：事实、时效、可溯源的依据。

选择看两件事。知识是不是经常变，变了能不能马上生效；答案需不需要给出处。两个都是「是」，选 RAG。要让模型学会一种稳定的表达方式，微调更合适，因为它把这种模式写进了权重，不占上下文。两者可以叠：微调打底定风格，RAG 补事实。

常见追问：
1. **微调能让模型记住新知识吗？** 能记住一部分，但不可靠、不可更新、不可溯源。用它存事实是拿训练成本换一个不确定的缓存。
2. **RAG 的成本比微调低吗？** 上线成本低，运行成本不一定。每次查询都要检索加长 prompt，量大时这部分是主要开销。

### Q4 窗口都到百万级了，还需要 RAG 吗？

窗口扩大的是「一次能读多少」，RAG 解决的是「该读哪些」。整库塞进去有四个问题：成本随资料量线性涨、无关材料稀释注意力、版本与权限仍需筛选、长文本中段的利用并不可靠。

两者可以配合。常见做法是先检索定位到相关文档，再让模型读完整章节，既省 token 又保留完整性。判断依据是证据够不够，而不是窗口够不够大。

常见追问：
1. **窗口大了，RAG 会不会被取代？** 会取代一部分，比如资料少、需要整体理解的场景。资料多、要溯源、要控成本的场景不会。
2. **长上下文最大的坑是什么？** 中段遗忘和跨段条件漏用。一段说通用规则，另一段写例外，只读到前一段就会答错。

{{< fig "diagrams/05-longctx.svg" "五个维度对比三种做法。结论写在最下面：微调管表达，RAG 管依据，长上下文只留给必须看全的场景。" >}}

### Q5 Agent 能自己搜文件了，预建索引的 RAG 还有用吗？

比的不该是搜索算法，是取资料的流程。资料量大、同类问题反复出现、答案落在明确的知识域里，预建索引把解析和切分的成本摊薄一次，链路也稳定可测。需要沿引用、配置、代码关系一步步追查时，自主检索更灵活，读到什么决定下一步查什么，代价是轮数和成本波动。

工程上常见的组合是：索引负责定位候选文件，Agent 读原文、核对版本、补查关联材料。两者不是替代关系。

常见追问：
1. **怎么判断该用哪种？** 看任务是否需要根据中间结果继续探索。一次问答能定，用索引；要追三层引用，用自主检索。
2. **自主检索的失败模式是什么？** 没想到的目录和关键词就永远找不到，而且每轮都在烧上下文。

### 跨题追问：定位与边界（本节 14 条）

- **只有检索没有生成，还算 RAG 吗？** 不算。检索加排序只是搜索，RAG 的增量在于把证据交给模型生成。面试里把链路说到「搜出文档」就停，等于漏掉最核心的一环。（第 1 篇第 2 问）
- **RAG 是不是就是给大模型接一个知识库？** 是接知识库，但关键在「什么时候接」。离线建库、在线注入，注入的是证据不是参数，这两点缺一个就退化成普通问答。（第 1 篇第 1 问）
- **RAG 是在解决「模型不够聪明」吗？** 不是。模型聪明与否和知识有没有是两个问题。RAG 解决的是知识不在参数里、或者已经过期，跟推理能力无关。（第 2 篇第 2 问）
- **幻觉是不是 RAG 的主要目标？** 不是主目标，是副产品收益。RAG 的第一目标是知识覆盖与时效，幻觉减少是「有依据」带来的副作用。（第 2 篇第 3 问）
- **微调和 RAG 的本质区别用一句话说？** 改不改参数。微调把知识写进权重，RAG 每次现查现用。所有后续差异（更新成本、可溯源、冷启动）都是这一条的推论。（第 3 篇第 2 问）
- **业务数据每周变，每周微调一次行不行？** 成本上不可行，工程上也不该这么干。微调适合稳定的能力，频繁变的事实应该放外部索引。（第 3 篇第 3 问）
- **微调出来的答案能溯源吗？** 不能。权重里没有「这条来自哪份文档」的信息。要给出处，只能靠检索。（第 3 篇第 3 问）
- **那微调还有什么用？** 定风格和格式最有用：固定的输出结构、行业语气、领域内的推理习惯。这些用 RAG 塞例子也能做，但每次都要占上下文。（第 3 篇第 4 问）
- **先微调再 RAG，顺序有讲究吗？** 有。微调定「怎么说」，RAG 供「说什么」，先定表达再补事实，评测时能分开归因。反过来做，风格问题会被误判成检索问题。（第 3 篇第 3 问 引申）
- **窗口够大，是不是可以不切块直接全塞？** 容量够不代表能用好。无关材料稀释注意力，版本、权限、生效范围也没人筛。全塞的结果通常是「答得像，但引错版本」。（第 22 篇第 2 问）
- **长上下文和 RAG 哪个更准？** 看任务。资料少、要整体理解，全文更准；资料多、要溯源、要控成本，检索更稳。工程上常用「先检索定位、再读完整章节」的混合。（第 22 篇第 4 问）
- **RAG 会不会被长窗口取代？** 一部分场景会。取代不了的是「资料量远超窗口」和「必须给出处」这两类。（第 22 篇第 1 问 引申）
- **Agent 自主搜索和 RAG 是替代关系吗？** 不是。一个解决「资料怎么组织」，一个解决「下一步该查什么」。索引定位候选、Agent 读原文核对，是常见组合。（第 23 篇第 4 问）
- **什么任务根本不需要 RAG？** 资料量小、一次能读完、答案靠推理不靠查证的任务。硬上 RAG 只是多一层可能出错的路由。（第 23 篇 引申）

## 二、切分与入库

切分决定知识以什么粒度进入系统。这一步错了，后面的向量、检索、rerank 都救不回来。

### Q6 chunk 怎么切？粒度怎么定？

一条记录有三部分：向量用于检索，原文用于喂给模型，metadata 用于过滤和溯源。三者缺一不可，只存向量等于找到位置却读不到内容。

粒度没有标准答案，500 到 1000 token 是常见起点，但更重要的是按文档类型选策略：通用文本用固定大小加重叠，有标题结构的按段落或标题切，代码按函数切，表格整块保留，既要精度又要上下文就用父子切割。判断标准只有一条：一个 chunk 能不能独立回答一个问题。

常见追问：
1. **整篇存行不行？** 不行。整篇压成一个向量，细节被平均掉，检索定位不到具体段落，而且 embedding 有输入长度上限。
2. **chunk 越小越准吗？** 不是。太小语义不完整，模型拿到碎片看不懂，召回率反而掉。

### Q7 语义被切断怎么办？

两个方向。切的时候别在语义中间下刀：重叠能把跨边界的内容保住，按句子、段落边界切能从源头避免拆散。切完之后再把上下文补回来：句子窗口检索命中一句就带回周围几句，父子切割用小块检索、大块返回。

更进一步的做法是 Contextual Retrieval：向量化之前，先让模型看着整篇文档给每个 chunk 生成一段背景说明，把背景和 chunk 拼在一起再向量化。它解决的是孤立 chunk 没头没尾的问题，代价是每块一次模型调用，用 prompt caching 能把成本压下来。

常见追问：
1. **重叠切多少？** 10%–20% 是常见区间。重叠太多等于重复入库，检索时同一段内容会占满候选位。
2. **这些方案能叠加吗？** 能。语义边界切分 + 父子切割 + contextual 背景，是常见的三层组合，成本也逐层上升。

{{< fig "diagrams/02-chunking.svg" "五种切分策略落在一根轴上：越往右块越大、上下文越完整，代价是重复入库、额外调用与更钝的定位。落地顺序是先结构边界，再父子，最后上下文增强。" >}}

### 跨题追问：切分与入库（本节 15 条）

- **整篇文档压成一个向量行不行？** 不行。细节被平均掉，检索定位不到具体段落，而且 embedding 有输入长度上限，长文档根本塞不进去。（第 4 篇第 2 问）
- **chunk 设 50 token 行不行？** 不行。一句话都没说完，语义不完整，模型拿到碎片读不懂。小 chunk 提升的只是「定位精度」，代价是「可读性」。（第 4 篇第 3 问）
- **固定大小切分的缺点是什么？** 会在句子、段落、表格中间下刀。加 overlap 能缓解跨边界丢字，但解决不了「一个完整语义被拆成两半」。（第 4 篇第 4 问）
- **overlap 是不是万能兜底？** 不是。它只保证边界文字不丢，两段各自看仍然不完整。而且重叠太多等于重复入库，检索时同一内容占满候选位。（第 5 篇第 2 问）
- **句号切分就够了吗？** 不够。条款、列表、表格里的一句话可能跨行跨段，按标点切会把条件句和结论句拆开。结构感知（标题、列表、表格）比标点更可靠。（第 5 篇 引申）
- **句子窗口检索怎么工作？** 索引时按句子建块，返回时把命中句前后各 N 句一起带回。检索精度来自句子，可读性来自窗口。（第 5 篇第 3 问）
- **父子切割和句子窗口差在哪？** 父子是两块独立存储，父块不参与检索；句子窗口是同一块里存窗口。前者适合长父块，后者实现更简单。（第 5 篇第 3 问）
- **Contextual Retrieval 到底加了什么？** 给每个 chunk 生成一段「它在全文里讲什么」的背景，拼在块前面一起向量化。解决孤立块没主语、没前提的问题。（第 5 篇第 3 问）
- **给每块生成背景，成本扛得住吗？** 每块一次模型调用，全量重建很贵。两个办法：用 prompt caching 把整篇文档缓存住，只让块内容变；或者只对长文档、结构复杂的文档做。（第 5 篇第 3 问）
- **命题化切割是什么？** 把段落拆成一条条独立命题再入库。检索粒度最细、指代最少，代价是块数量暴涨、上下文被切碎。（第 5 篇小节设问）
- **代码怎么切？** 按函数或类切，保留签名和注释。按行数切会把函数体和它的调用约定分开，检索到也没用。（第 4 篇第 4 问）
- **表格怎么切？** 整表保留，或者按行切但每行带上表头。丢掉表头的那一行，数字就没有意义了。（第 4 篇小节设问）
- **chunk 大小和 topK 有关系吗？** 有。块小就要多召回几条才凑够信息量，块大就少召几条。两者要一起调，不能单独定。（引申）
- **metadata 该存什么？** 来源文件、页码、章节路径、版本、生效时间、权限标签。前四个用于溯源，后三个用于过滤，缺了就只能靠相似度硬排。（第 4 篇第 1 问、第 21 篇）
- **切分效果怎么验证？** 抽一批真实问题，看正确段落能否被单独召回。如果答案总是横跨两三个块，说明该用父子或者加大 overlap。（引申）

## 三、向量化

向量化决定「语义相近」这件事在你的语料上成不成立。模型选错，后面所有调优都是在错的地基上刷墙。

### Q8 Embedding 是什么？模型怎么选？

Embedding 把文本映射成向量，语义相近的文本在向量空间里距离也近。RAG 的语义检索就是靠这个性质，不是关键词匹配。

选模型看三个维度：语言（中文场景 BGE 系列通常优于通用模型）、维度（越高精度越好，存储和检索成本也越高）、最大输入长度（决定 chunk 的上限）。第四个维度最容易被忽略：不要只看 MTEB 这类通用榜单，要在自己的业务数据上跑 Hit@K 和 MRR，榜单不能代表你的语料。

常见追问：
1. **维度越高越好吗？** 不是。检索精度提升有限，存储和内存是线性涨的，高维还更容易受维度灾难影响。
2. **换 embedding 模型要重建索引吗？** 必须。不同模型的向量空间不通用，混着用等于随机检索。

### Q9 算法几代演进？为什么 RAG 用 SBERT 这类？

三代。静态词向量（Word2Vec、GloVe）一词一向量，多义词处理不了。上下文向量（ELMo、BERT）同一个词在不同语境下不同，表达能力强了，但它是 token 级输出，比较两句相似度要把两句拼起来跑一次，百万文档就是百万次。句子级对比学习（SBERT、SimCSE、BGE）专门为相似度任务训练，双塔结构让文档向量可以离线预计算，查询时只算一次。

RAG 用第三代不是因为它更先进，是因为只有它满足「预计算 + 单次查询」的工程约束。

常见追问：
1. **双塔和 cross-encoder 差在哪？** 双塔各自编码再算相似度，可以预计算；cross-encoder 把问题和文档拼在一起过模型，准但慢，所以放在 rerank 那一层。
2. **BGE 为什么在中文上好？** 训练语料和对比学习的目标更贴中文检索任务，不是架构上有什么魔法。

### 跨题追问：向量化（本节 14 条）

- **「把文本变成向量」这句话为什么不够？** 缺了关键性质：语义相近的文本向量距离也近。没有这个性质，向量只是一串数字，检索无从谈起。（第 6 篇第 2 问）
- **OpenAI 的 embedding 中文一定不如国产吗？** 不一定，但中文检索任务上 BGE 系列通常更稳。判断依据只能是自己的评测集，不是厂商宣传。（第 6 篇第 2 问）
- **MTEB 排行能直接当选型依据吗？** 不能。榜单是通用数据集，你的业务是医疗、法律还是电商，分布完全不同。要在业务数据上跑 Hit@K、MRR。（第 6 篇第 3 问）
- **Hit@K 和 MRR 分别说明什么？** Hit@K 看正确答案有没有进前 K，衡量覆盖率；MRR 看它排多靠前，衡量排序质量。两个一起看才知道是没召回还是排太低。（第 6 篇第 3 问）
- **维度是不是越高越好？** 不是。精度收益递减，存储和内存线性涨，高维还会加重维度灾难。1024 维是常见折中。（第 6 篇 引申）
- **换 embedding 模型要重建索引吗？** 必须。不同模型的向量空间不通用，旧向量和新查询不在一个坐标系里，混用等于随机检索。（引申）
- **能不能用一个大模型同时做 embedding 和生成？** 技术上可以，工程上少见。检索要求向量可预计算、维度低、速度快，和生成模型的取向相反。（引申）
- **Word2Vec 为什么不能做语义检索？** 一词一向量，「吃苹果」和「苹果手机」里的苹果完全一样，多义词处理不了。它的训练目标也不是句对相似度。（第 7 篇第 2 问）
- **BERT 为什么不能直接拿来做检索？** BERT 输出 token 级向量，比较两句要把两句拼起来跑。百万文档就是百万次前向，延迟不可接受。（第 7 篇第 3 问）
- **SBERT 的关键改动是什么？** 双塔加句对对比学习。问题和文档分别编码，文档向量可以离线算好，查询时只算一次，再算余弦距离。（第 7 篇第 3 问）
- **SimCSE 又解决了什么？** 用 dropout 做正样本构造，训练更简单、更稳。它证明了对比学习的质量比复杂的训练目标更重要。（第 7 篇小节设问）
- **BGE 相比 SBERT 强在哪？** 训练数据规模、中文语料、指令式检索训练。架构差别不大，数据和目标函数的差别大。（第 7 篇小节设问）
- **embedding 需要微调吗？** 领域词差异大（医疗、法律、内部黑话）时值得。做法是对比学习加难负样本，成本比全量微调低得多。（引申）
- **向量归一化是必须的吗？** 用余弦相似度时是。不归一化就变成点积，长文本天然占优，排序会被长度带偏。（引申）

## 四、索引与存储

向量库解决「在上亿条里找最像的几条」。选型和运维的问题，比算法本身更容易在面试里翻车。

### Q10 向量数据库是什么？和 MySQL、ES 有什么区别？

核心能力是近似最近邻搜索（ANN），用 HNSW 或 IVF 这类索引，在百万到亿级的向量里快速找出最相似的若干条。关系库的 B+ 树对高维向量基本失效，ES 的向量检索是后加的补丁，数据量一大性能撑不住。

选型看规模和运维：本地开发用 Chroma，中小生产用 Qdrant，超大规模用 Milvus，不想运维用 Pinecone，已有 PostgreSQL 就用 pgvector 少引一个组件。

常见追问：
1. **HNSW 和 IVF 怎么选？** HNSW 查询快、内存占用高、增删友好；IVF 需要训练聚类、内存省、召回受 nprobe 影响。数据量不大优先 HNSW。
2. **向量库能代替全文检索吗？** 不能。精确词、型号、错误码这些还是要靠 BM25，所以生产上是两套并存。

### Q11 生产上怎么用？碰到过什么瓶颈？

百万级、1024 维、HNSW，P50 在 20 到 50 毫秒，这是常见量级。两个瓶颈最典型。

内存：百万条 1024 维 float32 光原始向量就是几个 GB，开标量量化（SQ8）压成 int8，内存降到四分之一，召回损失通常可以接受。写入：大批量写入会触发段合并，查询延迟抖动，解法是低峰分批写。汇报要给 P50、P99、QPS，不要用「感觉挺快」。

常见追问：
1. **量化会掉召回吗？** 会，通常几个点。用业务评测集验证，掉了就调召回数或换二值量化之外的方案。
2. **什么时候该分片？** 单机内存放不下索引，或写入吞吐成瓶颈时。分片之后要处理跨片召回与合并。

### Q12 什么时候该上图数据库？

需要多跳关系推理的时候。向量检索只能做单跳，找和问题直接相关的段落，答案藏在实体关系链上的问题它答不了，比如「A 的投资方和 B 有什么交集」，答案不在任何一段文字里。

典型场景：企业关系、医疗知识图谱、代码依赖、供应链溯源。代价是抽取 schema、维护实体对齐、更新链路更重。不是所有带实体的查询都要上图，单跳能答的别上。

常见追问：
1. **GraphRAG 和用图数据库是一回事吗？** 不完全是。GraphRAG 更强调社区发现加层次摘要，用于全局性问题；图数据库解决的是多跳查询。
2. **什么时候不值得上图？** 实体关系稀疏、问题基本都是单跳、团队没有维护图谱的人。

### 跨题追问：索引与存储（本节 14 条）

- **MySQL 加个向量字段算向量数据库吗？** 不算。存得下和搜得快是两件事。关系库没有面向高维的 ANN 索引，LIKE 做的是字符串匹配，不是相似度。（第 8 篇第 2 问）
- **ES 不是也能做向量检索吗？** 能，但那是后加的补丁。数据量一大、并发一高，性能就撑不住，向量也不是它的原生数据结构。（第 8 篇第 3 问）
- **选型该看哪些指标？** 数据规模、延迟与 QPS、内存占用、是否要分布式、是否需要过滤与混合检索、运维成本。看 Star 数不算指标。（第 8 篇第 3、4 问）
- **Chroma 能上生产吗？** 小规模、单机、内部工具可以。百万级、高并发不行，它没有分布式和读写分离。（第 8 篇第 4 问、第 9 篇第 2 问）
- **HNSW 的原理一句话？** 分层可导航小世界图。上层稀疏做跳跃，下层稠密做精找，查询复杂度近似对数。（第 8 篇小节设问）
- **IVF 的原理一句话？** 先聚类成若干桶，查询时只扫最近的 nprobe 个桶。内存省，但需要训练，召回受 nprobe 影响。（第 8 篇小节设问）
- **HNSW 的代价是什么？** 内存。图和向量都要常驻，百万级就很可观。还有删除不友好，通常用标记删除加定期重建。（第 8 篇小节设问）
- **生产上延迟怎么报？** 报 P50、P99 和 QPS，按数据量和索引参数一起报。「感觉挺快」不是指标。（第 9 篇第 3 问）
- **内存扛不住怎么办？** 标量量化（float32 → int8）能压到四分之一，二值量化更狠但召回掉得多。也可以降维或换 IVF。（第 9 篇第 4 问）
- **批量写入为什么会影响查询？** 写入触发段合并，合并期间 IO 和 CPU 被占。解法是低峰写入、控制批次大小、必要时写入与查询分离。（第 9 篇第 4 问）
- **什么时候该分片？** 单机内存放不下索引，或者写入吞吐成瓶颈。分片后要处理跨片召回和结果合并，复杂度上一个台阶。（引申）
- **图数据库解决的是什么问题？** 多跳关系推理。向量只能找「和问题相关的段落」，答案藏在实体与边上的问题它答不了。（第 16 篇第 2 问）
- **多检索几次能不能代替图？** 不能。你连实体之间的边在哪都不知道，第二次检索无从下手。图的价值就是边是显式存的。（第 16 篇第 3 问）
- **什么时候不值得上图数据库？** 实体稀疏、问题基本单跳、没人维护 schema 的时候。上图之后实体对齐和更新链路都会变重。（第 16 篇小节设问）

## 五、在线链路：检索与排序

这一段是系统的主干。用户感知到的「答得准不准、快不快」，八成由这一段决定。

{{< fig "diagrams/03-funnel.svg" "候选两百条一路收到进 prompt 的六条。四道闸门各对应一类失败：漏在库外、被热门块挤掉、精排排错、被预算裁掉。" >}}

### Q13 在线链路有哪几步？

六步：Query 预处理（改写、指代消解）、向量化、多路召回、精排、prompt 拼装、生成加溯源。

容易被跳过的是第一步和第五步。用户问「上次说的那个方案」，不做指代消解，向量库根本查不到；召回十条内容直接拼进 prompt，顺序和预算不管，模型会挑最容易读的那条，不是最相关的。

常见追问：
1. **哪一步最值得优化？** 召回质量。召回没有正确内容，后面所有环节都在优化噪音。
2. **rerank 一定要有吗？** 候选多、相关性区分度低的时候要。候选只有三五个且质量高，可以省。

### Q14 向量检索和关键词检索的区别？为什么要混合？

BM25 靠词频和逆文档频率，精确命中强，遇到同义词就没辙。向量检索靠语义距离，换个说法也能匹配，但遇到型号、缩写、数字、错误码容易漏。

混合检索两路都跑，用 RRF 融合。RRF 按名次而不是按分数合并，避开了两路分数量纲不一致的问题。生产上这几乎是默认配置。

常见追问：
1. **「M4 Pro 芯片参数」为什么向量召回不到？** 型号在向量空间里没有稳定的语义位置，它更像一个符号。关键词检索反而秒中。
2. **混合之后还要 rerank 吗？** 要。融合解决覆盖，rerank 解决精度，两件事。

### Q15 Query 改写有哪些方法？

四类加一类。直接改写（口语转书面、补全省略）、Query 扩展（补同义词和相关词）、HyDE（先让模型生成一个假设答案，用答案的向量去检索）、Step-back（把具体问题抽象一层，先取背景知识）、多 Query（生成几个版本分别检索）。

指代消解是前置条件，不是可选项。改写有没有效，看它是否改变了检索目标；只把句子改通顺，召回不会变。

常见追问：
1. **HyDE 什么时候有用？** 问题短、和文档表述差异大时。代价是多一次生成，答案编得离谱时会把检索带偏。
2. **改写会不会引入错误？** 会。改写结果和原问题一起召回，或者对改写做相关性校验，别只信模型。

### Q16 多路召回怎么做？调大 topK 为什么没用？

三路：向量、BM25、多 Query 扩展。合并用 RRF，之后进 rerank。

调大 topK 没用，因为相似度分布在尾部很平，第 20 名和第 200 名的分数差不多，多出来的只是噪音。真正的问题是正确答案根本不在候选集里，这种情况要改召回路径（换检索方式、改写 query、加元数据过滤），不是调 K。

常见追问：
1. **RRF 的 k 取多少？** 常用 60。它控制名次衰减的陡缓，取值对结果影响不大，别在这上面调参。
2. **多路召回的成本怎么控？** 每路各召回几十条就够，融合后再精排。不要每路都拉几百条。

### Q17 检索效果不好，怎么系统性优化？

四层。索引层：切分策略、embedding 选型、metadata、多向量表示。查询层：改写、扩展、HyDE、指代消解。召回层：混合检索、多路、元数据过滤。重排层：cross-encoder 或 LLM rerank、阈值截断。

单层优化收益有限。线上顺序是先保覆盖（索引加多路），再保精度（rerank），最后才动查询层，因为查询层要额外一次模型调用。

常见追问：
1. **怎么定位是哪一层的问题？** 先看该召回的在不在候选里（召回率），再看候选里排第几（MRR），最后看进了 prompt 的内容模型用没用。
2. **rerank 模型怎么选？** 中文场景看业务评测集上的 NDCG，别看参数量。延迟敏感就用小模型或蒸馏版。

### 跨题追问：在线链路（本节 16 条）

- **用户问「上次说的那个方案」，检索怎么做？** 先做指代消解，用会话历史把指代补全，再向量化。不补全，向量库拿到的是一个没有主语的句子。（第 10 篇第 2 问）
- **Query 改写是不是就是口语转书面？** 那只是最浅的一层。改写的目标是缩小「用户问法」和「文档写法」的语义鸿沟，可能要做扩展、抽象、假设答案。（第 12 篇第 2 问）
- **HyDE 的原理是什么？** 先让模型生成一个假设答案，假设答案的表述往往和文档更像，用它的向量去检索。代价是一次生成，编得离谱会带偏。（第 12 篇第 3 问）
- **Step-back 什么时候用？** 问题太具体、文档只讲通用原理时。先抽象一层取背景，再回到具体问题。（第 12 篇第 3 问）
- **多 Query 扩展开几个合适？** 三到五个。多了召回噪音和延迟都涨，融合时也难分辨哪路有效。（第 12 篇小节设问）
- **「RTX 4090 功耗」为什么向量召回不到？** 型号在向量空间没有稳定语义位置，它更像符号。关键词检索能秒中，所以混合是默认配置。（第 13 篇第 2 问）
- **RRF 为什么按名次不按分数？** 两路的分数量纲不同，BM25 分数无上界、余弦在 0 到 1 之间，直接加权没有意义。按名次合并绕开了这个问题。（第 13 篇小节设问）
- **RRF 之后还需要 rerank 吗？** 需要。融合解决覆盖，rerank 解决精度，两件事。cross-encoder 能看到问题和文档的交互，判断更准。（第 13 篇小节设问）
- **rerank 用 cross-encoder 还是 LLM？** 延迟敏感用 cross-encoder 小模型，追求质量用 LLM，但 LLM 慢且贵。生产上常用 cross-encoder 打底。（第 14 篇第 3 问）
- **rerank 的候选留多少？** 融合后几十条进 rerank，截到五到十条进 prompt。太多会稀释注意力，太少容易漏。（第 14 篇第 2 问）
- **topK 调大为什么救不回正确答案？** 相似度尾部很平，第 20 名和第 200 名分数差不多。多召回的只是噪音，答案根本不在候选集里。（第 13 篇第 3 问）
- **召回对了但答错，算哪一环的问题？** 生成层的遵循问题。看 prompt 有没有强约束、有没有引用核查、上下文是不是被无关内容挤掉了。（第 17 篇第 2 问）
- **prompt 拼装要注意什么？** 顺序（当前问题放最后）、预算（给输出留位置）、引用格式（让模型能标出处）、去重（同一段别重复塞）。（第 10 篇第 3 问）
- **多路召回的成本怎么控？** 每路召回几十条就够，融合后精排。不要每路都拉几百条，然后再截断。（引申）
- **在线链路里哪一步最慢？** 通常是生成，其次 rerank。检索本身在毫秒级，rerank 是几十到几百毫秒，生成是秒级。优化要看整体 TTFT 而不只是检索。（第 10 篇 引申）
- **缓存能加在哪？** query 向量、召回结果、rerank 结果都能缓存，按 query 归一化后的 key 存。注意文档更新时要失效对应缓存。（引申）

## 六、生成与可信

检索对了，答案仍可能错。这一段讲两类错误：模型不照着说，和资料本身互相矛盾。

### Q18 RAG 的幻觉怎么治？

两个来源。检索层没召回到相关内容，模型拿自身知识硬编；生成层召回到了但没严格遵循，在原文基础上加了推断。两类解法不同，混着答就会答成「加一句 prompt」。

四个手段：prompt 强约束（只准依据资料，没有就说没有）、检索质量门控（rerank 分数低于阈值直接拒答）、生成后引用核查（每条关键结论要能在 chunk 里找到出处）、结构化输出带来源编号（JSON 里强制 citation）。成本最低、上线前必做的是前两个。

常见追问：
1. **门控阈值怎么定？** 在业务数据上画分数分布，取能挡住明显不相关、又不会误杀正确召回的位置。
2. **引用编号能防编造吗？** 只能防「没出处」，防不了「出处和结论不符」，所以还要做引用核查。

### Q19 知识库两份文档说法不一样，信谁？

不看相似度。相似度只说明相关，不说明权威、时效、适用。处理顺序：先看适用范围（用户、地区、产品、时间），再看权威等级和版本状态，最后看生效区间。

同等权威且同时有效的两份材料仍然矛盾，系统不该偷偷二选一，要明确告诉用户存在冲突、分别引用依据，必要时转人工。工程上要有元数据「身份证」（来源、负责人、发布时间、版本、状态）、冲突检测、灰度发布、版本回滚和专项评测。

常见追问：
1. **群聊截图和正式制度冲突呢？** 截图相关度高但没有权威等级，制度优先。所以权威等级必须入库，不能靠模型临场判断。
2. **总部新规能覆盖地区细则吗？** 不一定。发布日期新不代表适用范围更准，地区细则在有效期内应优先。

### 跨题追问：生成与可信（本节 15 条）

- **检索做得好就不会幻觉了吗？** 不会。召回到了模型也可能超发挥，这叫生成层幻觉。两类幻觉来源不同，解法不同。（第 17 篇第 2 问）
- **加一句「只准根据资料回答」够吗？** 不够，但没有更便宜的起点。它是必要条件不是充分条件，还得配门控和核查。（第 17 篇第 3 问）
- **检索质量门控怎么做？** 用 rerank 分数设阈值，低于阈值直接拒答或澄清。阈值在业务数据上画分布定，不能拍脑袋。（第 17 篇第 4 问）
- **拒答会不会让体验变差？** 会，但比编一个错误答案便宜。拒答时给「没找到相关依据」加建议的追问方向，比一句「不知道」好。（第 17 篇第 4 问）
- **引用编号能防什么？防不了什么？** 能防「没有任何出处」的编造，防不了「出处和结论不符」。后者要靠引用核查逐条比对。（第 17 篇小节设问）
- **引用核查用模型还是规则？** 能用规则先规则（关键字段、数字、条款号是否出现在命中块里），剩下的用模型判。全量模型核查成本高。（引申）
- **幻觉能评测吗？** 能。构造无答案问题看拒答率，构造有答案问题看引用命中率，再加人工抽检一致性。（第 17 篇小节设问）
- **相似度最高的文档一定对吗？** 不一定。相似只说明相关，不说明权威、时效、适用。群聊截图可能和问题一字不差，但不能覆盖制度。（第 21 篇第 2 问）
- **冲突时先看什么？** 先看适用范围：用户、地区、产品、时间。再看权威等级和版本状态。相似度排在最后。（第 21 篇第 3 问）
- **总部新规和地区细则冲突呢？** 不一定是新的赢。地区细则在有效期内且适用范围更具体，应该优先。判断依据是范围不是日期。（第 21 篇第 3 问）
- **两份同等权威的文件矛盾怎么办？** 不偷偷二选一。明确告知存在冲突，分别引用两边依据，必要时转人工。生产系统不该把知识治理甩给一次生成。（第 21 篇第 4 问）
- **元数据要存哪些才够判断？** 来源、负责人、发布时间、生效区间、版本、地区、产品、状态。缺一个，冲突时就少一个判据。（第 21 篇小节设问）
- **冲突能自动检测吗？** 部分能。同一实体同一属性的不同取值可以规则检测，语义矛盾要靠模型比对。检测到之后进灰度而不是直接上线。（第 21 篇小节设问）
- **怎么证明冲突处理真的有效？** 评测集里专门放「有冲突的题」，看系统是选对依据还是选相似度最高的。这是专项指标。（第 21 篇小节设问）
- **知识库里有错误内容怎么办？** 灰度发布、版本回滚、定期抽检。错误知识进了索引，比模型幻觉更难发现，因为有出处反而更可信。（引申）

## 七、运行、评测与演进

前六段讲怎么搭，这一段讲怎么知道它坏了、怎么修、怎么不让它越来越差。

### Q20 怎么评测 RAG？

两层。检索层看该召回的有没有召回到：Hit@K、MRR、Context Recall。生成层看答案对不对、有没有幻觉、相不相关：Faithfulness、Answer Relevancy、Context Precision，常用 RAGAs 这套。

关键不是总分，是能定位到环节。线上指标才是最终标准：点踩率、追问率、转人工率、无答案率。离线评测集小、真值贵，用 LLM 打分要先和人工对齐一致率。

常见追问：
1. **没有标注数据怎么办？** 先用线上 badcase 和真实请求建集，合成样本只作补充。合成数据容易和真实分布脱节。
2. **指标之间冲突怎么取舍？** 先看 Faithfulness 这类硬指标，再看相关性。答得相关但没依据，比答得不全更危险。

### Q21 文档更新了，怎么增量索引？

文档内容 hash 或版本号 + 变更感知（轮询、CDC、消息队列）→ 命中变更就删掉该文档的旧 chunk，重新切分入库。不要做逐 chunk 的 diff，文档一变，切分边界全变，旧 chunk 和新 chunk 对不上。

实时性要求高的走事件驱动，秒级入库；一般场景按小时轮询就够。全量重建是最后手段，代价大且切换期间要保证查询不中断。

常见追问：
1. **删除怎么处理？** 软删加版本号，检索时过滤。物理删除要等索引合并，期间可能召回已删内容。
2. **灰度怎么切？** 新旧索引并行，按流量或按文档域切，出问题按版本回滚。

### Q22 高级范式有哪些？各自解决什么？

Self-RAG：模型自己判断要不要检索、检索结果好不好、答案有没有依据。CRAG：检索质量差时纠错或降级到网络搜索。GraphRAG：社区发现加层次摘要，解决「整个语料讲了什么」这类全局问题。Agentic RAG：把检索做成多轮决策，边查边改问题。

选型看问题类型。局部事实查询用基础 RAG 就够；全局概括用 GraphRAG 或分层摘要；多跳、需要边查边判断的用 agentic。范式越复杂，成本和不可控性越高。

常见追问：
1. **Self-RAG 怎么训练？** 需要带反思标记的数据，用模型自己生成再过滤。工程上常用 prompt 版近似，效果打折但上线快。
2. **GraphRAG 的成本在哪？** 建图的实体抽取和社区摘要，一次全量构建很贵，而且文档更新要增量维护。

### Q23 实际落地最难的是什么？

三块。文档预处理：PDF 的表格、扫描件、嵌套结构、页眉页脚，处理不好就是垃圾进垃圾出。检索调优：召回是整个系统的天花板，但问题可能出在切分、embedding、改写任何一环，归因难。效果评估：真值贵、标准主观，不知道哪坏了，优化就靠猜。

排查顺序固定：先看解析出来的文本对不对，再看该召回的在不在候选里，最后看模型有没有用给它的证据。三步都过还答错，才轮到 prompt 和模型。

常见追问：
1. **哪一块投入产出比最高？** 文档预处理。解析质量差，后面所有环节都在给脏数据做补偿。
2. **小团队怎么起步？** 先用固定切分加混合检索加 rerank，把评测集建起来，再谈改写和图谱。

### 跨题追问：运行、评测与演进（本节 16 条）

- **靠用户投诉来评估行不行？** 不行。投诉之前已经有人被错误答案坑过，而且不投诉的人可能直接不用了。这叫亡羊补牢，不叫评估。（第 18 篇第 2 问）
- **几十条样本加人工抽查够吗？** 不够。样本太少没有统计意义，人工标准不一致，换个人结论就变。要有可量化、能定位环节的指标。（第 18 篇第 3 问）
- **检索层用哪些指标？** Hit@K、MRR、Context Recall。前两个看找没找到、排得靠不靠前，第三个看该带的证据有没有全带进上下文。（第 18 篇小节设问）
- **生成层用哪些指标？** Faithfulness、Answer Relevancy、Context Precision，RAGAs 的三个核心。再加人工抽检对齐一致率。（第 18 篇小节设问）
- **指标能定位到哪个环节？** 用矩阵定位。召回低但 Faithfulness 高，说明找到的它都用了，只是没找全；召回高但 Faithfulness 低，说明找到了没用对。（第 18 篇第 3 问）
- **没有标注数据怎么建集？** 从线上真实请求和 badcase 里抽，人工标关键结论和依据。合成数据只能补充边界情况，不能当主力。（第 18 篇小节设问 引申）
- **LLM 打分可信吗？** 校准过才可信。同一批样本人工打一遍看一致率，低于阈值就换评分规则或拆细维度。（第 18 篇小节设问）
- **线上看什么？** 点踩率、追问率、转人工率、无答案率、单次回答的 token 成本。离线指标只是辅助。（第 18 篇小节设问）
- **文档改了一段，能只更新那几个 chunk 吗？** 不能。内容一变切分边界就变，旧 chunk 和新 chunk 对不上。按文档粒度重建，不是按 chunk 粒度 diff。（第 19 篇第 2 问）
- **怎么感知文档变了？** 轮询（定时扫 hash）或事件驱动（CDC、消息队列）。实时性要求高走事件，一般场景按小时轮询就够。（第 19 篇第 3 问）
- **文档 ID 和 chunk ID 怎么设计？** 文档 ID 稳定不变，chunk ID 由「文档 ID + 版本 + 序号」生成。这样删除和重建是幂等的，不会留孤儿向量。（第 19 篇小节设问）
- **全量重建什么时候用？** 换了 embedding 模型、改了切分策略、索引结构升级。这几种没法增量，只能重建，期间要保查询不中断。（第 19 篇小节设问）
- **删除文档怎么处理？** 先软删标记，检索时过滤，再异步物理删除。物理删除要等索引合并，期间仍可能召回。（引申）
- **Self-RAG 和普通 RAG 的差别？** 多了两个判断：要不要检索、检索结果够不够好。模型自己决定，不是固定流程。（第 15 篇第 3 问）
- **CRAG 解决什么？** 检索质量差时的降级：改写重查、换数据源、退到网络搜索。它把「检索失败」当成一个需要处理的状态。（第 15 篇第 3 问）
- **什么任务适合 GraphRAG？** 全局性问题，比如「这批文档讲了哪几个主题」。社区发现加层次摘要能答这类问题，局部事实查询用它就浪费了。（第 15 篇小节设问）

## 合并说明：同一件事的不同问法

原站 23 篇，每篇开头 3 到 4 轮面试官追问，正文里还有 124 个设问式小标题。逐条收进来接近 200 条，多数是同一件事换个说法。合并规则和 Agent 那篇一致。

1. **同一个机制在不同层被问到，按「谁负责」归位。** 语义截断在切分篇和检索篇各问了一遍，答案的两个侧面（切的时候怎么避免、切完怎么补）分开放在第二节。

## 答题模板

23 道背完，落到一个能复用的结构上。面试官听的是判断力，不是零件清单。

1. 一句话定义，说清它相对什么而存在。
2. 一次数据流，从文档进来到答案出去，能画出来最好。
3. 一个取舍，为什么不用另一种方案，代价是什么。
4. 一个项目证据，数字、报错、上线后的变化，有一个就够。

四个部分讲完通常两分钟。剩下的时间等追问，追问才是真正打分的部分。

常见翻车点，按被追问的概率排：

1. 只报名词不讲链路。说「有切分、embedding、向量库」，追问一句「一条 query 怎么走」就断。
2. 把 RAG 说成搜索。没有生成环节，前面两步只是检索。
3. 只答向量检索。不问混合检索的团队很少，答不出 BM25 就露了。
4. 幻觉只答 prompt。检索门控和引用核查才是硬手段。
