> 简历是写给 HR 的，追问是留给事实的。
>
> 这篇拿我自己那份三页简历当靶子，按「Ownership / Metric / Technical / Architecture / Result」五类 Claim 逐轮深挖。规则只有三条：**一次只问一个问题**；**答案必须落到对象、动作、边界**；**报出的数字必须能说清口径**。
>
> 文中的业务数字来自简历，代码和参数是脱敏后的示意实现，不是线上原样。凡是我当时没答上来的，我用「坑」标出来。

## 0. 先定契约：什么答案算过

面试官不需要听完所有细节，他只需要判断三件事：**这事是不是你做的**、**你知不知道它为什么这样设计**、**出了问题你能不能兜住**。所以每道题先锁一个内部契约，再开口。

| Claim 类型 | 典型写法 | 我会怎么追 | 答不上来说明什么 |
| --- | --- | --- | --- |
| Ownership | 负责、主导、参与 | 个人边界、亲自写的模块、谁做的决策 | 团队成果被算成个人成果 |
| Metric | 提升 60%、降本 30% | baseline、分母、周期、埋点来源 | 数字是别人算的，或口径不清 |
| Technical | 用了 ClickHouse、接了 MCP | 输入输出、为什么是它、换一个会怎样 | 只会名词，不会取舍 |
| Architecture | 分层、渐进式、统一鉴权 | 组件、数据流、边界、故障态 | 画得出框图，讲不出失败路径 |
| Result | 上线、被多少人在用 | 谁在用、怎么衡量、你的动作占比 | 交付了但没闭环 |

一个残酷但有用的自检：**把简历上每个形容词划掉，看剩下的名词和动词还成不成立**。「主导了资产体系的重构」划掉「主导」还剩「资产体系重构」；如果连重构了什么、旧的是什么样都说不清，这句就该删。

## 1. 第一轮：十分钟筛人

这一轮不问技术，只确认「这个人是不是真的在这个项目里」。

### Q1：用一句话说清你负责什么，不要出现「参与」两个字

**考察**：Ownership。含糊词是第一个红旗。

**参考回答**：

> 我在 Lovart（LiblibAI 的 AI 设计产品）负责 Agent 能力层。具体三块：**Agent 前台**——资产和权限树的建模、渐进式上下文加载、协同画布；**Agent 运行时**——Skill 的封装与权限模型、工具与 MCP 接入的鉴权、Context 与 Memory 的注入；**业务支撑**——商业化中台那几条主线。换句话说，模型不是我们的，我们把「模型能碰到什么、怎么碰到、碰完存哪」这三件事做出来。

注意这里的结构：**边界（哪三块）+ 反面定义（模型不是我们的）**。反面定义很关键，它一次划掉了「调 API」的嫌疑。

**下一层追问**：那这三块里，哪一块是你从零写的，哪一块是接手改造的？

**坑**：很多人会说「我负责 Agent 平台的架构设计」——这句话在面试官耳朵里等于「我没写代码」。诚实的分法是：从零建的、接手重构的、只做评审的，三种要说清楚。

### Q2：同一棵树承载 Brand、角色、产品，为什么不是三张表三个接口？

**考察**：Architecture。这是简历里最容易被当成「过度设计」的一句。

**参考回答**：

> 因为这三者的**生命周期和权限模型是同一个**，差异只在「节点上挂什么属性」。Brand 挂 logo、字体、色板；角色挂三视图、性格设定；产品挂外观参考。如果我做三张表，就要写三套增删改查、三套权限、三套级联删除，然后在「一个项目同时引用 Brand 和角色」的时候再拼一次。
>
> 一棵树的代价是「属性变宽」，我用 `node_type` + 一张扩展表解决；三张表的代价是「关系变多」，这个补不回来。

**下一层追问**：那树的深度是固定的吗？用户能不能自己在 Brand 下面再建文件夹？

**坑**：答成「统一建模更优雅」就废了。要答**代价对比**：统一的是权限和生命周期，付出的是属性表的宽度；分裂的是查询，永远补不回来。

### Q3：渐进式加载听起来就是 RAG，它和 RAG 差在哪？

**考察**：Technical。这是整份简历的技术命门，答不好后面全塌。

**参考回答**：

> 差在**谁决定召回什么**。RAG 是检索器决定：拿 query 去向量库 top-k，把 k 条塞进上下文，模型只能看这些。渐进式加载是**模型自己决定**：我先把树的结构摘要给它——「中式下面有园林、武侠、夜景三个子树，各 12/8/5 个资产」——它觉得需要园林，再调 `list` 展开园林；觉得要具体某张图，再调 `search` 取。
>
> 前者是「我把答案递给你」，后者是「我给你一张地图和一个望远镜」。地图的 token 成本是固定的几十个，望远镜按需付费。RAG 一次召回错了就全错，渐进式加载走错一步还能退回来。

**下一层追问**：那如果模型不知道自己要什么，永远在地图层面晃呢？

**坑**：把渐进式加载说成「分页查询」——那是接口设计，不是上下文设计。区别在于**每一层返回的东西都是给模型读的自然语言摘要，不是 JSON 数组**。

## 2. 第二轮：资产、权限、Skill

这一轮开始动真格。简历上写「Agent 前台：资产和权限树 + 渐进式上下文加载 + 协同画布」，这三个词每个都能问半小时。

### Q4：树怎么存的？子树移动怎么办？

**考察**：Technical + 数据建模的落地能力。

**参考回答**：

> 邻接表（`parent_id`）+ **物化路径**（`path`，形如 `/t_1024/brand/b_88/logo/`）。邻接表保证写入简单，物化路径保证「取整棵子树」是一次前缀查询，不用递归。
>
> 代价是移动子树要重写路径。我的处理是：移动是低频操作，走异步任务，先把子树 `path` 前缀批量 `REPLACE` 成新前缀，再更新 `parent_id`，整个过程在一个事务里，失败回滚。深度上限 6 层，超过就拒绝——不是为了性能，是为了让「无限嵌套」这种需求在设计阶段就被挡回去。

```sql
-- 取某棵子树（走 path 前缀索引，一次范围扫描）
SELECT id, node_type, name, depth
FROM asset_node
WHERE tenant_id = :tenant
  AND path LIKE :prefix || '%'
  AND deleted_at IS NULL
ORDER BY path
LIMIT :limit;

-- 移动子树：先改前缀，再改 parent_id，同一事务
UPDATE asset_node
SET path = :new_prefix || substring(path FROM length(:old_prefix) + 1)
WHERE tenant_id = :tenant AND path LIKE :old_prefix || '%';
```

**下一层追问**：`LIKE 'prefix%'` 在多大基数下会退化成全表扫？

**坑**：只说「用递归 CTE」不说代价。递归 CTE 每层一次索引查找，深度 6 就是 6 次；物化路径是 1 次范围扫描，但写入放大。**要能说出你为哪个场景选了哪个**，而不是背「推荐使用闭包表」。

### Q5：模型怎么「知道」树里有什么？给我一段真实的上下文

**考察**：是不是真的做过渐进式加载，还是纸上谈兵。

**参考回答**：

> 分三层注入，每层的粒度不同：
>
> 1. **根层地图**（常驻，约 200 token）：租户下有哪些场景、每个场景几个资产、最近改动时间。
> 2. **展开层**（模型调 `list_assets` 后注入）：某个子树下的节点列表，每个节点一行「名字 + 类型 + 一句话描述 + 子节点数」。
> 3. **叶子层**（模型调 `get_asset` 或 `search_assets` 后注入）：单个资产的完整描述或缩略图引用。
>
> 用户说「想要一套中式园林风格」，模型看到根层地图里有「中式（3 个子树，38 个资产）」，调 `list_assets(path='/brand/b_88/中式')`，拿到「园林 / 武侠 / 夜景」，再展开园林。三次工具调用，上下文里最终只多了园林那 12 条描述，而不是整个 38 条。

```python
# 根层地图：一次查询拼出所有人能读的摘要
def root_map(tenant_id: str) -> str:
    rows = db.query("""
        SELECT s.name, s.path,
               count(a.id) AS n,
               max(a.updated_at) AS touched
        FROM asset_node s
        LEFT JOIN asset_node a
               ON a.path LIKE s.path || '%' AND a.node_type = 'asset'
        WHERE s.tenant_id = %s AND s.node_type = 'scene' AND s.deleted_at IS NULL
        GROUP BY s.name, s.path
    """, (tenant_id,))
    lines = [f"- {r.name}（{r.n} 个资产，最近改动 {r.touched:%m-%d}）" for r in rows]
    return "\n".join(lines)
```

**下一层追问**：如果用户在根层就问「有没有赛博朋克」，而赛博朋克藏在第三层，模型怎么找到？

**坑**：只写「用向量检索兜底」不够。真正的答案是**双通道**：结构化路径走 `list`，语义查询走向量；向量命中后返回的是**带路径的结果**，模型据此判断要不要展开父节点。缺一半，长尾需求就漏。

### Q6：权限三层到底是哪三层？给我一个越权用例

**考察**：Architecture + 安全。简历写「按租户 / 资源树 / 权限树三层校验」，这句话必须能展开成一棵判断树。

**参考回答**：

> 三层是**从粗到细的短路判断**，任何一层不过就直接拒：
>
> - **租户层**：token 里的 `tenant_id` 必须等于资源所属租户。这一层挡的是「跨租户」，最便宜，先做。
> - **资源树层**：资源路径必须落在「这个人能看的路径前缀集合」里。个人空间只能看 `/t_x/u_y/`，团队空间看 `/t_x/team_z/`，素材库看 `/t_x/lib/`。
> - **权限树层**：命中路径之后再看动作——`view / edit / delete / share`，由角色（owner / editor / viewer）+ ACL 覆盖共同决定。
>
> 越权用例：A 团队的 editor 拿到了 B 团队某张图的 asset_id，直接调 `get_asset`。第一层过（同租户），第二层挂（路径不在他的前缀集合里）。如果只在第三层做角色判断，这张图就被读走了——**角色是动作维度的，路径是范围维度的，缺一维就是漏洞**。

```python
def can(actor, action: str, asset_path: str) -> bool:
    if not asset_path.startswith(f"/t_{actor.tenant}/"):
        return False                              # 租户层
    if not any(asset_path.startswith(p) for p in actor.scope_prefixes):
        return False                              # 资源树层
    for acl in actor.acls_for(asset_path):        # 权限树层：就近覆盖
        if acl.action == action:
            return acl.allow
    return action in ROLE_ACTIONS[actor.role_for(asset_path)]
```

**下一层追问**：`scope_prefixes` 存在哪？用户被移出团队时怎么立刻失效？

**坑**：把「角色」当权限。角色是**动作集合**的别名，不是范围。另一个坑是缓存：把 `can()` 结果缓存 5 分钟，用户被踢出团队后还能读 5 分钟——要么按 `(user, team)` 版本号失效，要么 TTL 压到秒级并接受一次放大。

### Q7：Skill 凭什么算资产？它和 Prompt 模板有什么本质区别？

**考察**：Technical + 抽象能力。简历写「Skill 与资产共用同一套描述与权限模型」，这是最容易被追问「凭什么」的一句。

**参考回答**：

> 因为 Skill 的**生命周期和资产一模一样**：有归属（谁的）、有可见范围（谁能用）、有版本、能被引用、能下架。区别只在内容形态——资产存的是「素材」，Skill 存的是「一段可执行的能力描述」。
>
> 和 Prompt 模板的本质区别是**它有契约**：输入 schema、输出 schema、需要的权限、失败怎么报。Prompt 模板是文本，模型读不懂就瞎编；Skill 是接口，模型走的是 tool call，参数不对在网关就被拦了。

```yaml
# skill.yaml —— 描述与权限是同一份，资产系统直接复用
name: brand.gen_poster
version: 3
when_to_use: 用户要求"按品牌规范出一张海报"，且已有 brand_id
inputs:
  brand_id: {type: string, required: true}
  brief:    {type: string, required: true}
  ratio:    {type: enum, values: ["1:1", "3:4", "16:9"], default: "3:4"}
requires:
  scopes: ["asset:read:/t_{tenant}/brand/", "model:image"]
outputs:
  artifact: {type: asset_ref, node_type: poster}
```

**下一层追问**：`when_to_use` 是自然语言，模型怎么在几十个 Skill 里挑对？挑错了怎么办？

**坑**：把 Skill 说成「提示词封装」。真正的分水岭是**能不能在调用前做鉴权和参数校验**——不能，它就只是文本，不配进资产体系。

### 这一轮的三个坑

1. **树模型只答选型不答代价**。面试官不关心你知道几种树，关心你为什么在这个场景放弃另外两种。
2. **权限只答「有校验」不答「哪一层挡什么」**。三层不是三个 if，是三次不同维度的短路。
3. **渐进式加载讲成接口分页**。它的产出必须是「给模型读的摘要」，不是「给前端渲染的 JSON」。

## 3. 第三轮：运行时——Context、Memory、Gateway、MCP

简历上这一节的标题是「Agent 运行时：Skill / Memory / Tools」，只有四条，但每一条都能拆出半小时。

### Q8：上下文预算怎么分？超了先砍谁？

**考察**：Context Engineering 的工程化程度。会背「滑动窗口」的人很多，能说清裁剪顺序的人很少。

**参考回答**：

> 先分桶，再定裁剪顺序。桶是：system + 工具 schema（固定）、常驻记忆（画像摘要）、资产摘要（可展开）、对话历史（可压缩）、输出预留。
>
> 裁剪顺序严格按「丢了会不会立刻出错」排：**先丢低分历史 → 再压历史成摘要 → 再收资产摘要 → 最后才动常驻记忆**。品牌约束这类东西是 pin 的，预算再紧也不裁——它不是「参考信息」，是「合规要求」。
>
> 历史打分用三个信号：是否被引用过、时间衰减、是否包含用户明确指令（「以后都这样」）。第三类是硬保留。

```python
BUCKETS = [  # (名称, 占比, 可否裁剪, 裁剪优先级；数字越小越先砍)
    ("system",   0.12, False, 99),
    ("pinned",   0.08, False, 99),   # 品牌约束、用户显式指令
    ("memory",   0.12, True,   3),
    ("assets",   0.28, True,   2),
    ("history",  0.30, True,   1),
    ("reserve",  0.10, False,  99),  # 输出预留，永远不动
]

def fit(budget: int, parts: dict) -> dict:
    for name, ratio, shrinkable, _ in sorted(BUCKETS, key=lambda b: b[3]):
        cap = int(budget * ratio)
        if shrinkable and parts[name].tokens > cap:
            parts[name] = parts[name].compress_to(cap)
    return parts
```

**下一层追问**：压缩历史时，把哪几条挑出来合成摘要？怎么保证摘完还能回答「第三步为什么改了颜色」？

**坑**：只按 token 数裁剪，不看内容。更隐蔽的坑是**压缩顺序导致指令丢失**：用户在中途说过「不要用渐变」，被压进摘要时抹掉了，模型后面就开始加渐变。这类指令必须打标进 pinned 桶。

### Q9：Memory 里到底存什么？怎么防止模型把自己的输出当事实？

**考察**：Memory 的写入策略。这是判断一个人有没有真正做过 Memory 的分水岭。

**参考回答**：

> 存四类，且**只在四个时机写**：
>
> - **偏好**（命题级）：「这个用户偏好左图右文」——从用户多次显式选择里抽，置信度带权重。
> - **情节**（事件级）：这一轮做了什么、为什么改——只追加，供回放。
> - **程序**（Skill 级）：哪类需求用哪个 Skill 成功率高。
> - **资产**（状态级）：产物本身，不进记忆，进资产树。
>
> 防污染的第一条铁律：**模型自己的输出不进语义记忆**。模型生成的文案、配色建议，只能进情节记忆当「这次做过什么」，不能进偏好记忆当「用户喜欢什么」。否则三轮之后，模型在跟自己的回声对话，所有人长一个样。
>
> 第二条：偏好要**多次一致**才升级置信度，单次不算。第三条：用户否定的偏好要能下线，不是只加不减。

**下一层追问**：用户说「以后都用深色」，这算偏好还是指令？存哪？

**坑**：把对话历史当记忆。历史是**上下文**，记忆是**跨会话的结论**。另一个坑是只写不删——记忆库越大召回越差，必须有过期和合并。

### Q10：LLM Gateway 的缓存亲和，怎么算命中？什么情况下会崩？

**考察**：这是简历里最「工程」的一条，也是最能区分「懂原理」和「配过参数」的一条。

**参考回答**：

> 命中靠的是**前缀完全一致**，所以 cache key 必须把影响前缀的所有东西都算进去：模型、system prompt 哈希、工具 schema 哈希、以及对话前若干轮的哈希。少算一项，就会「看起来命中、实际全 miss」，账单不降反升。
>
> 亲和路由是第二层：同一个 key 尽量打到同一台上游实例，因为 KV cache 在实例内存里，换台机器就没了。用一致性哈希，key 是 `prefix_hash`，实例扩缩容时只迁移一部分。
>
> 崩的三种情况：**热点**（一个大客户占满一台实例）、**扩容**（新实例冷启动，缓存全空）、**模型切换**（换了版本，前缀全变）。对策分别是：热点做 key 分片、扩容预热（用历史高频前缀打一遍）、模型切换做灰度并接受一次全量 miss。

```python
def cache_key(model: str, system: str, tools: list[dict], history: list[dict], n: int = 4) -> str:
    h = hashlib.sha256()
    h.update(model.encode())
    h.update(system.encode())
    h.update(json.dumps(tools, sort_keys=True, ensure_ascii=False).encode())
    for turn in history[:n]:                      # 只取前缀稳定段
        h.update(json.dumps(turn, sort_keys=True, ensure_ascii=False).encode())
    return h.hexdigest()

def route(key: str) -> str:
    ring = consistent_hash_ring(healthy_upstreams())   # 虚拟节点 160/台
    return ring.get_node(key)
```

**下一层追问**：工具 schema 里加了一个可选参数，缓存会怎样？

**坑**：把「命中率提升」当成纯收益。缓存命中率上去之后，**首字延迟会变得很不均匀**（命中的快、miss 的慢），用户能感知到抖动。要在网关做排队和超时预算，不然省了钱、丢了体验。

### Q11：MCP 工具的鉴权怎么落？工具调用越权了怎么办？

**考察**：MCP 是不是真的接进去了，还是只在简历上。

**参考回答**：

> 工具在注册时就要声明 `required_scopes`，运行时由网关**注入调用者身份**，而不是让模型自己传 token——模型传的任何身份字段都不可信。
>
> 三层校验复用资产那套：租户 → 资源树 → 权限树。工具拿到的 `asset_path` 参数在网关侧先做一次前缀校验，再进业务逻辑。审计日志记「谁、用哪个工具、碰了哪个路径、结果」。
>
> 越权用例：模型被诱导去读 `/t_other/` 的图。网关在参数阶段就拦了，业务代码根本收不到这个请求。

**下一层追问**：如果工具需要「代表用户去调第三方」，token 怎么传？

**坑**：把 token 放进工具参数让模型转手——这是 prompt injection 的经典入口。另一个坑是只校验工具级权限，不校验参数里的资源路径，等于门锁了但窗户开着。

### 这一轮的三个坑

1. **缓存 key 漏项**。少算工具 schema，命中率看着有，账单没降。
2. **Memory 只写不删**。三个月后召回质量下降，归因到「模型变笨」。
3. **鉴权放在业务层**。业务代码里一堆 `if not can(...)`，漏一处就是一个洞；应该在网关统一收口。

## 4. 第四轮：协同画布——人和 Agent 同时写同一个文档

简历上写「协同画布：同时承载人与 Agent、人与人的双层协同写入……协同算法保证并发写入下的一致性」。这一段最容易被问穿，因为它同时涉及**分布式一致性**和**AI 写入的不可控性**。

### Q12：协同你选了 OT 还是 CRDT？为什么？

**考察**：Architecture + 是否真的理解取舍。

**参考回答**：

> 画布是**场景图**（节点 + 位置 + 层级），不是纯文本。文本协同里 OT 和 CRDT 都能用，但图结构上 CRDT 的合并语义更自然：每个节点是一个带 id 的寄存器，位置是 LWW-Register，层级是带墓碑的集合。
>
> 选 CRDT 的核心理由是**服务端不想当裁判**。OT 需要中心服务器做 transform，服务端要维护全量历史；CRDT 可以让服务端只做转发和持久化，离线编辑也能合并。
>
> 代价是元数据膨胀和墓碑清理。节点删了不能真删，要留 tombstone 防止并发的「复活」；定期做快照压缩。

**下一层追问**：Agent 一次生成 200 个节点，用户同时在拖一个节点，怎么保证不打架？

**坑**：只说「用了 Yjs」不说为什么。更致命的坑是**把 Agent 的批量写入当成普通用户操作**——它没有光标、没有意图，一次性提交 200 个 op，会把人正在编辑的节点覆盖掉。

### Q13：Agent 的批量写入和人手编辑冲突，具体怎么解？

**考察**：真正做过才答得出的问题。

**参考回答**：

> 三道闸：
>
> 1. **范围锁**：Agent 写入前先申请「节点范围」的软锁（比如「画布左下角 40% 区域」），锁是建议性的，用户操作可以抢占；被抢占时 Agent 的这批 op 先挂起。
> 2. **意图 rebase**：Agent 的 op 带上「相对于哪个快照」，落库前先 rebase 到最新快照上。位置类 op 做平移，结构类 op 做冲突检测，冲突就丢弃这一条并记录。
> 3. **结果可见**：Agent 写入的产物带来源标记，用户可以「只看 Agent 改了什么」并整体撤销——撤销是**按批**的，不是按 op。
>
> 人在回路的关键不是「不冲突」，而是**冲突之后用户能一键回到我想要的样子**。

**下一层追问**：断线重连之后，客户端那批没确认的 op 怎么办？

**坑**：用「最后写入者赢」处理一切。位置可以 LWW，结构不行——两个人在同一层各插一个节点，LWW 会丢掉一个，而且丢得毫无提示。

### Q14：你说「保证一致性」，最终一致的窗口是多久？怎么验收？

**考察**：Metric + 工程严谨性。「保证一致性」是最容易被追问的四个字。

**参考回答**：

> 协同层是强一致的单文档（服务端串行化一个文档的 op），跨文档（同一个资产被两个画布引用）才是最终一致，窗口是秒级。
>
> 验收不看「有没有报错」，看三个指标：**op 往返延迟 P95**、**合并冲突率**（每千次写入的冲突条数）、**回放一致性**（把 op 流重放一遍，结果快照哈希必须等于线上快照）。第三个是真正的兜底——它能在没人报障的时候发现「悄悄分叉」。

**下一层追问**：快照哈希对不上，怎么定位是哪条 op 的问题？

**坑**：把「最终一致」当免责声明。面试官问窗口，你答「很快」，等于承认没测过。

## 5. 第五轮：数字、失败和边界

前四轮考的是「会不会」，这一轮考的是「诚不诚实」。

### Q15：查询性能提升 60%，口径是什么？这 60% 有多少是你的？

**考察**：Metric。这是简历里最容易翻车的一类。

**参考回答**：

> 口径是**创意中心列表页的 P95 查询耗时**，从约 1.2s 降到 500ms 以内，样本是线上 7 天的真实流量，不含缓存命中（缓存命中的请求本来就快，算进去会虚高）。
>
> 我做的部分：把 ClickHouse 的表按「租户 + 时间」重分区，把原来在应用层做的聚合下推成物化视图，以及把「素材 → 创意」的 N+1 查询改成一次 `IN` 批量取。前两项是主要收益，第三项是把长尾砍掉。
>
> 60% 里有多少是我的：分区和物化视图是我设计的，建表和数据回刷是团队一起做的。如果只算「我亲手改的」，大概是 P95 从 1.0s 到 600ms 这一段。

**下一层追问**：物化视图的代价是什么？

**坑**：说「优化了 SQL」。必须说清**优化了哪个查询、慢在哪、改完快在哪**。另一个坑是把「平均耗时」当「P95」——长尾才是用户投诉的来源。

### Q16：云游戏那个 35% 资源利用率，是怎么算出来的？

**考察**：Metric + 归因。

**参考回答**：

> 分母是「已分配实例的可用时长」，分子是「真实有会话占用的时长」。改造前是固定绑定（一个人一台实例，空转也占着），改造后是优先级队列 + 多活调度：会话来了按优先级分配，空闲实例回池。
>
> 35% 的提升主要来自「把空转时间变成可分配资源」，不是把单机跑得更满。成本降 30% 是同一 DAU 下实例数下降的直接结果。
>
> 归因要诚实：调度算法是我写的，但「哪些业务能容忍抢占」是产品和运维一起定的，那部分不算我的。

**下一层追问**：抢占会不会导致用户被踢下线？怎么保证体验？

**坑**：把「利用率提升」说成「性能提升」。利用率是资源效率，性能是延迟吞吐，两个指标经常反向。

### Q17：讲一个你搞砸的线上问题

**考察**：失败复盘。没有事故的人，通常是没上线过。

**参考回答**（示意结构，按真实情况替换）：

> 一次资产树批量迁移，我把 `path` 前缀替换写成了全表更新，漏了 `tenant_id` 条件。测试环境只有一个租户，没暴露。上线后另一个租户的资产路径被改了前缀，表现为「资产还在，但搜不到」。
>
> 定位用了 20 分钟：先看告警（检索失败率突增），再看慢查询日志（没有慢查询），最后比对 op 日志发现路径前缀异常。
>
> 止损是把受影响租户的路径从备份回滚，然后补了三件事：迁移脚本强制带租户参数、灰度先跑单租户、迁移前后做「数量 + 路径哈希」对账。

**下一层追问**：为什么测试环境没发现？

**坑**：把事故讲成「别人的锅」，或者讲完没有机制改进。面试官要的是**你从这次事故里长出了什么习惯**。

### Q18：你前七年做广告、云游戏、数字人，这些跟 Agent 有什么关系？

**考察**：迁移能力。跨行的人一定会被问，答不好就是「你只是想来做 AI」。

**参考回答**：

> 三件事直接搬过来了。
>
> 第一是**资源调度**。云游戏那套「优先级队列 + 空闲回池」和今天做 token 预算、并发会话限流是同一类问题：都是有限资源、不同优先级、要在抢占和体验之间找平衡。区别只是被调度的东西从 GPU 变成了上下文窗口。
>
> 第二是**多租户权限**。广告平台和云游戏都要做租户隔离，Agent 的资产权限树是同一套思路往前推了一步——多了「资源路径」这一维，但「租户 → 范围 → 动作」的结构没变。
>
> 第三是**流式改造**。数字人把端到端时延从 1.5s 压到 800ms，靠的是全链路流式化，不是某一环变快。今天做 Agent 的首字延迟、流式输出、工具调用的并行化，是同一套手感。

**下一层追问**：那反过来，Agent 这块有什么是你以前的经验会误导你的？

**参考回答**（加分项）：会。传统后端习惯「确定性」——同样的输入必须同样的输出，所以会本能地想用缓存、用幂等、用状态机把不确定性消灭掉。但 Agent 的模型输出天然不确定，过度追求确定性会做出一个「看起来很稳、实际很笨」的系统。这一课我交了学费。

**坑**：答「我学习能力强」。这是能力描述，不是迁移证据。

## 6. 反向提问：我问面试官什么

面试是双向的。这几个问题能反向验证团队是不是真的在做 Agent：

- 你们的上下文是「检索塞进去」还是「模型自己展开」？如果是前者，谁决定 top-k？
- Skill 有契约吗？还是把提示词当能力？
- 缓存命中率是多少？miss 的时候延迟抖动怎么处理？
- 用户改坏了 Agent 的产物，能不能一键回到上一版？按什么粒度撤销？
- 这个团队上一次因为「模型幻觉」导致的事故是什么？改了什么？

## 7. 收口：这套题到底在测什么

五轮下来，真正被反复验证的只有四件事：

| 维度 | 表现好的信号 | 危险信号 |
| --- | --- | --- |
| 边界 | 能说清「我写的」和「团队做的」 | 全是「我们」 |
| 取舍 | 能说出放弃了什么、为什么 | 只有优点没有代价 |
| 失败 | 有具体事故、具体止损、具体机制 | 「没出过问题」 |
| 口径 | 数字有基线、分母、周期 | 只有百分比 |

写完这篇我又改了一版简历：把「主导」换成具体的动作，把「提升 60%」补上口径，把「保证一致性」换成「单文档强一致、跨文档秒级最终一致」。**简历上每多一个形容词，面试就多一道题。**

如果这份东西对你有用，把它当靶子：挑三条你最心虚的 Claim，按上面的方式各追两层，你会很快知道哪句该删、哪句该补、哪句得先去补课。
