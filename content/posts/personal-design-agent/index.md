> 做 Lovart 那一年，Agent 是从零搭起来的：资产树、上下文、Skill 与工具、画布协同、评审。产品跑通之后我一直在想另一件事：同一套结构如果只服务一个人，哪些结论会翻转。这篇是推到现在的答案。文中的阈值、预算、工时都是可以直接开工的默认值，不是线上实测。

## 0. 先给结论

个人设计助手不该自己做图。它该做四件事：把一句话变成能执行的规格、知道你的品牌和素材、判断哪版能发、把成品送到该去的地方。像素交给已经存在的设计 Agent。

功能和优先级可以压成一张表，下面九条按「判断错的代价」排。P0 错了要返工重做，P3 是可以晚点再看的调参项。

### P0 · 决定这套东西成不成立

**P0-1 规格没冻结就不开工，没冻结的 run 不进账本。** 「做张活动海报」在冻结之前不是任务，是一句话。规格里至少要定下用途、渠道、尺寸、必含信息、截止这五项；缺两项以上才问，缺一项先出草图再问（§3.1）。不冻就开工的后果是两周的产物全部作废，而且评审阶段所有争论都变成主观的，因为没有一把共同的尺子。

**P0-2 账本只追加，存原件和哈希，不存缩略图和 URL。** 每次生成、每次评审、每次编辑、每次交付都落一条事件，产物原文件落盘并算 sha256（§6）。存 URL 的后果在第三个月出现：外链失效，你再也说不清现在这版是第几版、素材从哪来。没有原件也没法做配对学习，品味模型就没有训练集。

**P0-3 品牌约束同步校验，40 毫秒内出结果。** 色值、字号阶梯、logo 安全区、禁用词、出血边距、字体授权，六类规则走规则引擎，不走模型（§3.4）。漏掉这条的后果不是体验差，是带错色值的图发出去，署名是你。

### P1 · 决定它像不像你的助手

**P1-1 品味模型只从编辑动作学，不问「你喜欢什么」。** 一次「接受前把主色压深一档」就是一条 `(v2 > v1)` 的偏好样本，比任何问卷都准（§8）。走自述路线的后果是得到一个所有人共用的助手，越用越不像你，而且这种偏差自己很难察觉。

**P1-2 精修优先局部重绘，不整张重生成。** 同一张图改标题位置，局部重绘的成本大约是重生成的十分之一，漂移也小。整张重生成的后果是每改一点，其它地方全跟着变，两轮之后你已经找不到原来那版。

**P1-3 单 Agent 先跑通闭环，多候选并行放到 P1 之后。** 两到三个候选能让审美判断变容易，但单价乘 N，而且只有「审美分歧大」的任务才值得（§9）。提前开并行的后果是预算在探索期就烧完，还没有账本可以比较。

### P2 · 决定你每周花多少时间在杂事上

**P2-1 尺寸矩阵和发布回写要自动化。** 一张主图要出公众号封面 900×383、朋友圈 1080×1080、海报 1242×1660。手工导一次二十分钟，一个月八次就吃掉半天。

**P2-2 主动提醒必须有静默阈值。** 「上周那张海报的方图版本还没导出」这类提醒有价值，但没有阈值就是骚扰（§10）。

### P3 · 决定它能不能自己变好

**P3-1 自演进只开 prompt 与路由两层。** 个人的样本量是 n=1，一周十个任务，开多了是在拟合噪声（§9）。等账本攒到两百个已接受产物、误杀率稳定在 8% 以下，再考虑动检索参数。

按这张表怎么用：

1. 前两周只做 P0 三条。目标是「同一个 brief 出三版，能说清每版为什么不行」，不是出图好看。
2. 第三周接一个设计 Agent 的适配器，把闭环跑通。第一个可用版本的标准写在 §4。
3. 品味模型等到账本里有 40 个已接受产物再开。不够就先只跑硬约束，别用十几个样本训一个模型。

## 1. 三个约束变了，三个机制要重写

Lovart 的评测系统里，北极星是任务一次通过率。这个指标在个人助手上不成立，因为分母是 1。

### 1.1 样本量：从统计显著到个体配对

产品里一次通过率是统计量。百万用户摊平之后，5% 的波动能跑出显著性，A/B 测试是标准动作。

个人助手一周做十个任务。要让 A/B 跑出显著性，得等两个月，而这两个月里你的品味已经变了。

所以个人助手不做 A/B，做同 spec 下的配对。每次你在一版上改了一个动作然后接受，就得到一条「这版比上版好」的样本。一次编辑的信息密度远高于一次点赞，因为它带着方向和幅度：主色往深了调、字号降了 2、行距加了 0.05。这些都不是「好」或「不好」，是可以直接进特征的数值。

代价是样本有偏。你只在看不顺眼的时候动手，所以配对样本天然偏向「坏的那一极」。做法是同时采集「未编辑即接受」的样本，作为弱正例，权重降到 0.3。

### 1.2 资产：从导入到沉淀

产品里资产是导入的。租户注册完，引导你上传 Brand Kit，上传完就有一套完整的约束。

个人没有这个仪式。第一次做婚礼请柬时不会想到先建资产树，等做到第五个项目才发现同一批照片被找了五次。

个人助手的资产必须从「使用时沉淀」长出来：每次交付自动把用到的素材、字体、模板挂到项目上，跨项目复用靠召回，不靠整理。整理这件事对一个人来说永远排在待办列表的最后。

### 1.3 时间：从会话到项目

产品里一次会话一个任务，会话结束就归档。个人是一个项目三周，任务之间有依赖：先出海报，再从海报派生朋友圈方图，最后出易拉宝。

这意味着两件事。

账本必须跨会话。spec 要能被继承和派生，派生时只改渠道和尺寸，其余字段继承父级。没有继承的话，每次都要重填一遍用途和必含信息，人就会开始糊弄，spec 很快退化成一句「随便做个图」。

先例必须能被召回。同一类任务做到第三次，助手应该能说出「上次你在这类海报上把标题压到了图片下沿」，而不是从零开始。

### 1.4 能搬的和不能搬的

能直接搬的是分层和钩子：五层记忆的读写节奏、四层 rubric 的分工、调优闭环的七步。这些结构跟用户数无关。

不能搬的是评审的组织方式和数据假设。产品里评审是平台的事，标准由平台定、抽样由人工做、结论进发布门禁；个人助手里你就是裁判，标准要从你的动作里反推，而且反推错了没人告诉你。

## 2. 定位：助手拿四个决定权，不碰画布

先把分工写死，后面所有设计都从这里推。

| 环节 | 你 | 助手 | 设计 Agent |
| --- | --- | --- | --- |
| 做什么 | 判断值不值得做 | 把一句话变成 spec，最多问三个问题 | 不参与 |
| 用谁做 | 例外时指定 | 按能力表路由，管预算 | 声明自己擅长什么 |
| 留哪个 | 最终签字 | 硬约束 + 品味分 + 差异说明 | 出候选 |
| 放哪里 | 确认渠道 | 尺寸矩阵、命名、发布、回写 | 导出原始尺寸 |

四个决定权里，只有「留哪个」不能完全交给助手。它可以给建议、给证据、把明显不行的筛掉，但签字权在你。这不是保守，是因为产物上署的是你的名字，而助手没有声誉可押。

### 2.1 为什么不自建画布

OpenDesign 那条路已经验证过一次：把 agent loop 外包给用户机器上的编码 CLI，自己只做装配，半年能跑起来；自建画布是三年的事。

个人助手更极端。画布是别人的，你只需要两样东西：能读到产物，能读到操作。前者用来评审，后者用来学品味。这两样都能通过适配器拿到，不需要你拥有那棵场景树。

反过来，一旦自建画布，前六个月全在做编辑器：撤销重做、图层、吸附、字体渲染。这些跟「帮你做决定」没有关系。

### 2.2 助手拥有什么

它拥有三样设计 Agent 拿不到的东西。

一是你的历史。所有交付过的产物、所有编辑动作、所有被否掉的版本。这是唯一能反推品味的语料。

二是你的约束。品牌色、字体授权、禁用词、不能出现的竞品 logo。这些是确定性的，不该让模型每次重新猜。

三是你的账。哪个 Agent 在哪类任务上靠谱、单价多少、返工几次。这是路由的依据。

## 3. 七个功能面

{{< fig "diagrams/03-capability.svg" "七个功能面串成一条流水线，账本横在底下承接所有事件。F1 到 F6 都有明确的输入输出，F7 不是环节，是所有环节的落点。" >}}

| 功能 | 输入到输出 | 系统里是什么 | 缺了会怎样 |
| --- | --- | --- | --- |
| F1 收活 | 一句话、截图、链接、文件 → 任务卡 | 结构化 spec + 待确认问题 | 做错方向，两周产物作废 |
| F2 资产与品牌 | 历史产物、导入素材 → 约束与指纹 | 约束块 + 资产树 + 风格指纹 | 每次重找素材，产物不像你的 |
| F3 能力路由 | 任务卡 → 选中的 Agent 与预算 | 能力表 + 打分器 + 预算闸 | 用错工具，单价翻倍 |
| F4 评审 | 候选 → 通过/不通过 + 改哪里 | 三层 rubric + 误杀率 | 你得自己看每一张，助手等于没帮上 |
| F5 精修 | 指令 + mask → 新版本 | 局部重绘 + 增量校验 + 版本树 | 每改一点全图漂移 |
| F6 交付 | 版本 → 渠道尺寸与发布记录 | 尺寸矩阵 + 命名器 + 回写 | 每周两小时手工导出 |
| F7 账本 | 所有事件 → 可重放的投影 | 事件日志 + 产物库 + 索引 | 无法比较、回滚、学习 |

### 3.1 F1 收活：一句话到任务卡

任务卡七个字段：用途、渠道、尺寸或比例、必含信息、风格参照、截止、验收人。

规则有三条：

1. 缺两项以上才问，一次问完，不超过三个问题。
2. 缺一项先出草图再问，因为有些字段你自己也没想清楚，看到图才知道。
3. 「高级感」「有质感」「大气」不进 spec。它们不是字段，是品味模型要学的东西，写进 spec 只会让评审失去依据。

冻结之后 spec 有版本号。所有 run 记录 `spec_rev`，改 spec 要显式升版，不升版的改动视为无效。

### 3.2 F2 资产与品牌

品牌是约束，不是记忆。约束是确定性的，检索一次没命中就是事故，所以它不进召回池，也不参与预算裁切；编译期注入保证模型看得到，产物侧校验保证就算没看也跑不出去。

资产是另一回事。它需要被找出来，所以是检索。但个人资产有个特点：总量小、复用率高、命名混乱。一个两百个素材的个人库，向量召回经常不如「最近三个月用过的」这条时间规则。

风格指纹是这部分最容易被跳过、又最有价值的东西。从历史产物里算六个统计量：主色相与饱和度分布、字号阶梯密度、平均留白率、单版元素数、圆角半径、文案平均句长。它不参与生成，只做两件事：给品味模型当初验，给评审做「明显不像你」的粗筛。

### 3.3 F3 能力路由

能力表每行六个字段：擅长任务、输入形态、输出形态、是否支持局部编辑、P95 延迟、单次单价。

路由分三档，按成本递增：

1. 规则命中就直接走。中文长文案排版走 A，写实场景图走 B，矢量图标走 C。
2. 没命中走打分。每个 Agent 对当前任务类型给 0 到 1 的分，权重放策略仓，可调可回滚。
3. 试跑比较。只在 P2 开，贵三倍，收益在「两个 Agent 都可能做好」的任务上。

预算闸是硬约束，不是建议。单任务默认上限三块钱，超了降到便宜模型或者直接停下问你。不设闸的后果是试跑档一开，一天烧掉一周的预算。

### 3.4 F4 评审

三层，按确定性和延迟排。

第一层硬约束，规则引擎，六类规则，40 毫秒，同步执行。色值是否在品牌色板内、字号是否落在阶梯上、logo 安全区是否被压、禁用词是否出现、出血边距是否足够、字体是否有商用授权。这一层不给分，只给通过和不通过，因为它是确定性的。

第二层品味模型，pairwise 排序，180 毫秒，本地推理，缓存命中率约九成。输入是产物特征加当前 spec，输出是「A 比 B 好多少」，不是绝对分。绝对分没法跨任务比较，也解释不了。

第三层 VLM 抽检，两秒，只对排第一的候选跑，抽 30%。它回答开放问题：标题有没有压到人脸、文字有没有溢出、主体有没有被裁。这一层最贵也最不可靠，所以只兜底，不做主判。

输出不是分数，是一句话加一条定位：哪条规则没过，或者哪个区域有问题。评审结论要能直接喂给精修，否则它只是让你多看一眼。

误杀率是这一层的护栏：助手判不过、但你最终接受了的比例。超过 8% 说明尺子偏了，通常是硬约束写太死，或者品味模型在自己训练集上过拟合。

### 3.5 F5 精修

局部优先。同一张海报改标题位置，局部重绘的单价大约是整张重生成的十分之一，而且改完之后其它区域不变。

增量校验。局部改动只触发受影响的约束，改文字就查禁用词和溢出，改色就查色板。全量重跑六条规则没必要，而且会引入误杀。

版本树。每次精修落一个版本，带父版本指针和一句改动说明。能 diff 才能回滚，能回滚才敢试。

### 3.6 F6 交付

尺寸矩阵是一张表，不是一段代码。主图加渠道，查出目标尺寸、格式、压缩质量、是否需要安全区留白。八个渠道的表大概四十行，写一次用一年。

命名是 `<项目>-<交付物>-<渠道>-v<n>.<ext>`，不允许手写。手工命名的后果是三个月后 `最终版2-副本.png`。

发布要回写。哪天发到了哪个渠道、URL 是什么。这条记录同时是品味模型的强正样本：发出去的东西比点过赞的东西可信。

交付要幂等。同一个 `spec_rev` 加同一个渠道重复交付，只更新记录，不重复创建。

### 3.7 F7 账本

账本不是数据库里的几张表，是这套系统的唯一事实来源。其它所有视图，包括任务列表、版本树、能力排行、风格指纹，都能从它重算。

它要回答三个查询：

1. 这条产物是哪次 run、哪个 spec 版本、哪个 Agent 生成的，用了哪些素材。
2. 同类任务上次是怎么做的，哪一版被接受，改了什么。
3. 哪条约束最常被违反，是约束写错了还是 Agent 能力不够。

## 4. MVP：四档，六周，一张不做清单

| 档位 | 内容 | 判断错的代价 | 工时 | 验收 |
| --- | --- | --- | --- | --- |
| P0 | 任务卡、账本、硬约束校验 | 返工重做，或带错品牌发出去 | 2 周 | 同一 brief 出三版，每版能说清为什么不行 |
| P1 | 单适配器闭环、品味模型 v0、版本树与局部精修 | 助手不像你，越用越别扭 | 3 周 | 同类任务第二次准备时间不超过首次三分之一 |
| P2 | 多候选并行、尺寸矩阵与发布回写 | 预算浪费、每周两小时杂事 | 2 周 | 一张主图导出六个渠道不超过两分钟 |
| P3 | 自演进（只开 prompt 与路由） | 拟合噪声，指标好看但产物变差 | 持续 | 每次改动有 diff、有回放、能回滚 |

六周的排法是重叠的：P0 第二周就开始接适配器，因为硬约束校验需要真实产物才测得出来；P1 的品味模型前三周只采数据不训练，等样本到位再开。

### 4.1 第一个可用版本的三个数

不追「好看」，追三个数：

1. 首版通过率不低于 50%。意思是第一版出来后，你不需要重生成，只需要微调。
2. 平均返工轮数不高于 1.5。返工一轮指一次局部精修，不是整张重来。
3. 误杀率不高于 8%。助手说不行、但你接受了的比例。

这三个数在第六周测一次，之后每两周测一次。它们比分模型准确率有用，因为直接对应你花的时间。

### 4.2 不做清单

1. 不自建画布。适配器能拿到的就用适配器。
2. 不微调模型。样本量与成本都不支持，而且微调会锁死路由。
3. 不做多人协作。个人助手的价值来自单人上下文，加协作会把权限模型带进来。
4. 不做素材市场。素材来源是导入和你自己的历史产物。
5. 不做移动端。做图在桌面上。

## 5. 架构：六层，一条账本

{{< fig "diagrams/04-architecture.svg" "六层结构与两条横切。用户请求从入口层进，向下走到执行层，产物回到账本层；交付层是唯一对外写出的地方。右侧策略仓与观测横切所有层。" >}}

### 5.1 L1 入口层

三种输入：对话、截图或文件、外部链接。输出只有一样东西：任务卡草稿，加最多三个待确认问题。

这一层不做模型选择，不做检索，不做预算判断。它唯一的失败模式是把模糊当明确，所以规则是「宁可多问一句，不要猜」。

### 5.2 L2 决策层

路由、预算、评审编排、什么时候打断你。这一层有三个同步决策点，正好对应一次交付的三个卡口：开工前问不问、候选出来后推哪个、交付前确认渠道。

决策层不生成内容。它输出的是动作：调用哪个适配器、跑哪几层评审、要不要停下来问。

### 5.3 L3 上下文层

编译器。每次调用前重建，不做常驻缓存。

预算是这样分的：约束块 1.2k token 常驻，不参与裁切；历史六轮；资产三条；先例两条。编译 p95 不超过 120 毫秒，超时就退到「约束块加最近三轮」，宁可这轮少带先例，也不能让你盯着转圈。

这一层只读。任何「顺便更新一下画像」都是异步的，写在 turn 结束之后。

### 5.4 L4 执行层

一个设计 Agent 一个适配器。适配器只做三件事：把任务卡翻译成对方的输入，把对方的产物归一化成统一记录，把错误翻译成统一错误码。

适配器里出现业务判断就说明放错了层。比如「如果是海报就走 A」，这属于路由，不属于适配器。

产物必须落原件。对方给的 URL 只能当线索，下载下来算哈希入库才算数。

### 5.5 L5 账本层

事件日志加产物库加索引。索引有两套：图索引查关系（这个素材在哪些交付物里用过），向量索引查相似（上次那版像不像这版）。

账本是唯一可以写的地方。上层所有状态都是它的投影，投影坏了可以重建，事件丢了就真丢了。

### 5.6 L6 交付层

唯一对外写出的地方。尺寸矩阵、命名、格式转换、发布、回写。

这一层要幂等和可追溯。发出去的东西收不回来，所以每次都要记下「什么时候、发到哪、用的哪个版本」。

### 5.7 两条横切

策略仓管所有可调参数：rubric 版本、路由权重、预算阈值、编译预算比例。每个参数有版本号、有 diff、能回滚。个人助手的参数不多，五十个以内，但没有版本控制就会变成「上周好像好一点」这种无法复现的状态。

观测管三件事：每次 run 的 trace、成本、误杀率。个人的数据量小，不用上大盘，一个每天更新的本地报表就够。

## 6. 账本：六张投影表，一条事件流

{{< fig "diagrams/07-data-model.svg" "账本的数据模型。事件表是唯一写入点，六张投影表都从它重放出来；表内箭头标的是外键指向。" >}}

六张投影表：`project`、`deliverable`、`run`、`artifact`、`verdict`、`asset`。`event` 是唯一写入点，只追加，其余六张都从它重放。

```sql
create table event (
  id        integer primary key,
  ts        integer not null,
  actor     text    not null,   -- you | assistant | adapter | reviewer
  type      text    not null,   -- spec.frozen | run.started | artifact.added
                                -- | verdict.recorded | artifact.edited | delivered
  ref       text    not null,   -- 被作用对象的 id
  payload   text    not null,   -- JSON，只写不查
  prev_hash text
);
```

三条约束：

1. 原件不可变。产物只追加，删是写一条 tombstone，不物理删。
2. 哈希去重。同一张图重复生成不重复存，`artifact.sha256` 唯一索引。
3. 投影可重建。`deliverable`、`run`、`verdict` 都能从事件重放，重建脚本是必需项不是可选项。

`payload` 只写不查，查询一律走投影表。这条是后端规范里的老规矩，在个人项目里同样成立：JSON 里做过滤和排序，三个月后自己都看不懂。

## 7. 时序一：一次交付

{{< fig "diagrams/05-delivery-sequence.svg" "一次交付的时序。十四步串起收活、生成、评审、交付四段，红色是同步等待你的地方，虚线是异步。评审的规则层同步，模型层异步预取。" >}}

按阶段拆开看。

**收活（第 1 到 4 步）**。你丢一张截图加一句话，入口层解析出用途是活动海报、渠道是公众号、截止是周三，缺标题文案和主视觉类型。助手问两个问题，你回一句，spec 冻结成 v1。这一轮往返是同步的，只有一次。

**生成（第 5 到 6 步）**。上下文层组装三样东西：约束块、三条资产、两条先例，90 毫秒。路由按规则直接命中海报能力，预算三块。适配器把 spec 翻译成设计 Agent 的输入，跑一次出两个候选。两个候选的原件落盘，算哈希，写 `artifact.added` 两条事件。

**评审（第 7 到 9 步）**。硬约束同步跑六条规则，40 毫秒，两个候选全过。品味模型并行给分，A 0.62、B 0.71，因为它读到 B 的留白率更接近你历史同类产物。VLM 只对 B 跑一次，两秒，发现标题压到了人物肩线。助手把「推荐 B，但标题要上移 24 像素」推给你。

**精修与交付（第 10 到 14 步）**。你把主色压深一档，局部重绘，只触发色板和对比度两条规则。新版本 v3 入账。交付层出三个尺寸，命名，导出，写 `delivered` 事件，记渠道和时间。

整条链路只有三个同步点：spec 冻结、评审硬约束、交付确认。其余全部异步。这个比例是关键，同步点每多一个，等待就多一段，助手就会从「顺手」变成「要等」。

## 8. 时序二：品味模型怎么长出来

{{< fig "diagrams/06-taste-loop.svg" "品味模型的离线闭环。每天凌晨跑一次，只做配对、训练、回放三段，过了闸门才换 rubric 版本，不过就丢弃并记录原因。" >}}

七步，每天凌晨跑一次。

1. 拉前一日的事件。只取 `artifact.edited`、`verdict.recorded`、`delivered` 三类，其余与品味无关。
2. 配对。同一 `deliverable` 同一 `spec_rev` 下，取「被弃用」和「被接受」的相邻两版。跨 spec 版本的不能配对，因为约束变了。
3. 特征。十二维：主色相偏移、字号比、留白率、元素数、对比度、文案平均句长、圆角半径、对齐方式、图占版面比、留白位置、字体对数、行距比。
4. 训练。pairwise 逻辑回归，样本少于两百时加 L2 正则，宁可欠拟合。树模型在这个样本量上会记住项目，不会学到偏好。
5. 回放。上周的五十个任务，用新模型重排候选，看首版通过率有没有升，误杀率有没有升。
6. 闸门。通过率涨五个百分点以上，且误杀率不上升，才换版本。两个条件缺一不可，因为「多拒几个」很容易把通过率刷上去。
7. 写记录。哪几维权重变了、变了多少、回放结论。进策略仓，可回滚。

为什么不上 RLHF 或微调，三个理由：样本量不够、成本不划算、结论不可解释。个人助手最需要的恰恰是第三条，你得知道它为什么觉得这张更好，否则它跟掷骰子没区别。

## 9. 五个取舍

| 取舍 | 选项 | 选哪个 | 理由 | 什么时候翻 |
| --- | --- | --- | --- | --- |
| 画布 | 自建或适配 | 适配 | 半年能跑，对上一句话是三年 | 日交付量超过 20 |
| 评审时机 | 全同步或硬约束同步 | 硬约束同步 | 两秒在等待里，四十毫秒不在 | VLM 降到 300 毫秒 |
| 候选数 | 1、2 到 3、5 | 2 到 3 | 单价乘 N，只有分歧大才值 | 路由能预判分歧度 |
| 部署 | 云或本地优先 | 本地优先 | 素材有版权，历史有隐私 | 出现多设备同步需求 |
| 记忆写入 | 自述或行为 | 行为 | 自述会说谎，行为不会 | 从不 |

## 10. 六个坑

1. **spec 没冻就开工**。表现是跑了两版才发现尺寸不对。修法是把冻结做成硬门禁，没冻结的 run 直接拒绝。
2. **把自述当事实**。「我喜欢极简」这句话进了画像，之后所有产物都往极简走，而你的实际选择是「极简但要有细节」。修法是自述只做候选，要三条行为证据才转正。
3. **评审器和生成器同源**。用同一个模型既生成又打分，它会偏爱自己的输出。修法是评审必须换一家，或者至少换提示词和采样参数。
4. **账本存缩略图**。缩略图省空间，但没法重印、没法算指纹、没法做配对。修法是原件加缩略图两份，缩略图只是索引。
5. **主动提醒没有阈值**。第一天觉得贴心，第三天开始烦。修法是每条提醒带一个衰减：连续两次被忽略，同类提醒停一周。
6. **用产品指标衡量个人助手**。一次通过率在 n=1 上没意义，周留存更没意义（你每天都用）。修法是换成返工轮数和准备时间。

## 11. 如果只做三件事

1. 任务卡。七个字段，冻结才开工。这一条决定了后面所有讨论有没有共同语言。
2. 账本。事件加原件加哈希，只追加。这一条决定了三个月后还能不能改进。
3. 硬约束校验。六类规则，四十毫秒，同步。这一条决定了你敢不敢把东西发出去。

三件事两周能做完，做完之后你会得到一个不好看但可靠的助手。品味模型、多候选、自演进都建在这三件事上，顺序反了就得返工。
