八、这次踩到的坑

1. Spring RestClient 默认发 chunked body

mock 只读 Content-Length，收到空 body，于是 embedding 请求变成 input=[]，应用报 embedding response size mismatch。修复是让 mock 解析 Transfer-Encoding: chunked。生产网关和自建 OpenAI 兼容服务要确认支持 chunked，否则同样会“请求体消失”。

2. ACL 的 tenant baseline 会短路 group 限制

见第五节。ACL 不是“有 tenant 就安全”：如果 tenant 是全员可见的 baseline，group 只是附加可见性，不能再拿它做受限资产。要显式建模 public / tenant / group，或把 tenant 从受限资产的 ACL 里去掉。

3. 纯向量检索对资产 ID 不敏感

q28 查询 asset-1015，纯 kNN 的 Top-5 完全没有 1015；加入 exact-ID 通道后才通过。生产应把 exact/lexical 与 kNN 做 hybrid，而不是期待 embedding 记住主键。

4. 用“资产是否出现”判断旧 chunk 是否删除

kNN 总会返回 top-k，旧资产可能因为语义相近而继续出现。应检查 snippet 文本、chunk id 和 ES 文档计数，而不是仅看 assetId 是否在结果里。

九、限制与下一步

  • LLM 是 mock，只覆盖检索、上下文组装和引用编号；真实生成质量、幻觉率、引用忠实度未测。
  • 数据是 23 个合成资产、28 条 query，规模不足以证明生产召回；需要真实业务黄金集和更难的同义/多跳/否定 query。
  • 单机 ES、1 GB heap、单线程串行请求，没有并发、段合并、缓存和故障注入。
  • 只测了 dense kNN；没有 BM25、hybrid、rerank、MCLS 长文和多向量。
  • exact-ID 是 demo 快捷通道，不是通用 lexical 检索；生产应使用独立 keyword 字段与 hybrid 融合。
